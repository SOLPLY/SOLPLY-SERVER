## 1. 목적과 작업 방식

사용자에게 필요한 정합성과 최신성을 먼저 정하고, 전체를 미리 준비하는 비용과 요청받은 동네를 적재하는 지연을 비교한다. 현재 전체 적재가 빠르거나 상주 메모리가 작다는 사실만으로 동네별 캐시의 우열을 단정하지 않는다. 기존 CPU 사용량/JIT 자원 여유 분석을 대체하지 않는다.

메인 에이전트는 오케스트레이션·설계 검토·최종 계약 검증을 맡는다. 구현과 테스트는 **Claude Opus5 세션**이 수행한다. 설계 합의 뒤 새 메인 Run에서 이어서 구현·검증을 완료했다.

사용자는 GitHub 이슈 작성보다 요구사항, 트레이드오프, 작업 종료 시 기록을 우선한다고 명시했다. 이슈 생성을 선행 차단 조건으로 삼지 않는다. 이미 합의한 설계를 다시 승인받는 절차도 반복하지 않는다. PR·배포는 현재 요청에 포함되지 않는다.

**거리순은 이번 비교·최적화·추가 검증의 범위에서 제외한다.** 기존 동작을 무관하게 변경하지 않는다. 정적 정렬 다섯 축(인기/최신/평점/리뷰 수/북마크 수)을 대상으로 한다.

## 2. 확정 요구사항

### 2.1 탐색의 정합성

- 동일 동네 범위·필터·정렬로 이어지는 스크롤에서 시작 당시의 대상과 순서를 유지한다.
- 요청이 다른 인스턴스로 이동했다고 뒤처진 데이터로 정상 응답해서는 안 된다.
- 생성·삭제·동네 소속·필터 태그·정렬 기준값 등 결과 대상/필터/순서에 영향을 주는 변경은 **영향받은 동네의 버전을 증가**시킨다. 동네 이동은 출발/도착 모두 해당한다.
- 운영자의 무효화 체크 여부에 의존하지 않는다. 변경 성격으로 서버가 판단한다.
- 다음 요청에서 커서의 동네별 버전과 현재 버전이 다르면 탐색 만료/새로고침을 유도한다. 로컬에 이전 버전이 남아 있어도 계속 서빙하지 않는다.
- 이미 버전을 확인한 요청은 그 뒤 변경이 커밋되어도 확보한 일관된 데이터로 응답할 수 있다. 응답 직전까지 최신성을 반복 확인하는 계약이 아니다.
- 구버전 장기 보관, 과거 시점 DB 복원, 버전별 사용 허용 상태값은 두지 않는다. 최신 버전과 커서 비교가 허용 판정이다.

### 2.2 버전과 원본의 일관성

- 원본 변경과 관련 동네 버전 증가는 같은 DB 쓰기 트랜잭션으로 커밋한다.
- 여러 동네 조회는 관련 동네 버전들을 하나의 일관된 DB 읽기 상태에서 관측한다. 순차 독립 조회로 서로 다른 커밋 상태를 섞지 않는다.
- 적재 또한 버전과 원본을 같은 read view에서 읽는다. 요청에서 v10을 봤다는 이유로 나중에 읽은 v11 데이터를 v10으로 표시하지 않는다.
- 동네 이동 전 A와 이동 후 B를 합쳐 중복을 만드는 조합은 금지한다.
- 준비 중 변경된 경우의 첫 페이지 재관측/제한 재시도 등 세부 구현은 1초 예산 안에서 해결한다. 필요한 과거 데이터를 확보하지 못한 경우 새로운 데이터로 구버전 커서를 이어 붙이지 않는다.
- leaf 동네 집합 변화와 커서의 범위 식별은 구현 시 검토한다. 같은 요청 파라미터라도 범위가 달라져 탐색이 조용히 바뀌면 안 된다.

### 2.3 표시값과 배치

- 이름·썸네일만의 변경은 탐색 버전을 올리지 않는다.
- 상세는 정확한 값을 보여 주므로 목록 표시값은 다음 성공한 정기 전체 배치 이후 해당 동네가 재적재될 때까지 지연을 허용한다.
- 정기 전체 배치 성공 시 실제 통계값 변화 여부와 무관하게 **처리 대상 모든 동네의 버전을 증가**시킨다. 표시값만 바뀐 동네를 영구 제외하지 않는다.
- 버전 갱신이 모든 동네의 즉시 재적재를 뜻하지 않는다. 요청이 온 동네부터 준비한다.
- 배치 실패와 후속 적재 실패 때문에 표시 지연은 길어질 수 있다. 고정된 초 단위의 표시 최신성 상한을 약속하지 않는다.
- 이름/썸네일 갱신만을 이유로 짧은 TTL, soft TTL, 별도 revision을 도입하지 않는다.

### 2.4 캐시 미스와 실패

- 현재 버전 데이터가 로컬에 없으면 필요한 동네만 적재한다.
- 캐시 제거/만료만으로 커서를 만료시키지 않는다. 버전이 같으면 재적재 후 이어간다.
- 캐시 미스 적재 대기 상한은 우선 **1초**다. 측정된 응답시간이 아니라 구현·검증할 예산이다.
- 예산을 넘거나 필요한 데이터를 준비하지 못하면 명시적 재시도 가능 오류를 반환한다. 다른 버전 데이터로 성공 응답하지 않는다.
- SQL 실행 외의 작업/커넥션/적재 완료 대기까지 고려한다. DB query timeout만으로 모든 대기가 끝난다고 가정하지 않는다.
- 같은 동네/버전 요청은 적재를 공유하는 방향이다. 요청 하나의 timeout/cancel이 다른 요청의 공용 적재를 취소하면 안 된다.
- 별도 동시 적재 제한과 대기열의 필요성/크기는 미확정이다. 동네 적재 자체의 저비용 가설을 먼저 검증한다.

## 3. 캐시 후보 구조

```text
요청 범위 및 커서 해석
  → 관련 동네 버전을 일관되게 읽음
  → 커서 불일치: 만료
  → 필요한 버전 캐시 조회
      → 있음: 참조를 잡고 정적 정렬/필터/페이지 조회
      → 없음: 해당 동네 원본+버전을 일관되게 적재
  → 실제 확보한 버전으로 응답/다음 커서 생성
```

동네별 불변 장소 객체와 정렬 배열들을 하나의 캐시 항목으로 소유하는 구성을 우선 후보로 둔다. 여러 정렬 배열은 동일 장소 객체를 참조하며 객체를 정렬축마다 복제하지 않는다. 표시값도 우선 함께 보관한다.

`ID 배열 + 전역 객체 맵`은 객체 수를 저절로 제한하지 않는다. 맵/키/조회 비용과 객체 수명 분리 비용도 있다. 따라서 객체 증가 우려만으로 ID 배열을 채택하지 않는다. 비교 근거가 생기면 재검토할 수 있다.

용량 초과 제거는 **Caffeine의 최근성·빈도 기반 정책**에 맡긴다. 상한은 동네 개수보다 보관 비용 가중치(장소 수 또는 추정 바이트)를 후보로 사용한다. 실제 값은 애플리케이션 리소스와 측정으로 정한다. 큰 동네부터 제거하는 정책으로 해석하지 않는다.

캐시 상한은 진행 중 요청의 이전 참조, 적재 중 후보, GC 미회수 객체를 포함한 JVM 힙의 엄격한 상한이 아니다. 일시 공존 비용을 별도로 측정한다.

**TTL/soft TTL은 채택하지 않은 대안이다.** TTL을 짧게 해 아끼는 상주 메모리보다 반복 적재 CPU와 miss 지연이 클 수 있다. 용량 제한만으로 충분한지 먼저 확인한다. 앞선 대화의 30초/60초 제안, 유휴 TTL 제안은 최종 확정 정책이 아니다.

Redis는 이번 설계에 도입하지 않는다. 버전 조회용, 최신 payload 공유용, 과거 payload 보관용을 구분해서 평가했으며, 과거 탐색을 모든 인스턴스에서 보장하기 위해 인프라를 추가할 필요는 현재 요구사항에 없다. Redis가 모든 조건에서 느리거나 이득이 없다고 주장하지 않는다.

## 4. 검증할 트레이드오프

| 판단 | 절약 가능 비용 | 새로 부담할 수 있는 비용 |
|---|---|---|
| 전체 → 동네별 적재 | 미조회 동네 DB 읽기/객체 생성/정렬 | miss 지연, 인스턴스별/동네별 반복 적재 |
| 사전 정렬 | 반복 요청의 정렬 CPU | 조회되지 않는 축의 준비·배열 보관·교체 비용 |
| 요청 시 정렬 | 초기 준비·배열 보관 | 요청량에 비례하는 계산·할당 |
| DB 직접 조회 | 로컬 객체 보관/재구성 | DB 실행·네트워크·결과 매핑 비용 |
| 낮은 캐시 상한/짧은 TTL | 보관 메모리 | 재적재 빈도·CPU·DB 부하·첫 요청 지연 |
| 로컬 캐시 | 추가 공유 저장소·직렬화 경로 없음 | 인스턴스별 준비 시차·중복 적재 |

상위 결과 위주로 조회되고 스크롤이 짧을 가능성은 사용자 가설이다. 운영 측정 사실로 표현하지 않는다. 상위 페이지 반복 조회는 사전정렬 재사용에 유리할 수 있지만, 작은 결과를 위해 모든 축을 만드는 낭비도 비교해야 한다.

## 5. 비교 검증 계획

### 사전 등록한 목적

1. 문제: 전체 재구성이 요청 범위보다 많은 일을 하는지, 사전정렬이 준비 비용을 회수하는지 미확정이다.
2. 가설: 동네 단위는 미사용 데이터 준비를 줄일 수 있으나 반복 miss/갱신에서는 불리할 수 있다. 사전정렬은 교체 전 재사용 횟수에 따라 이득이 바뀐다. 효과 크기는 아직 미측정이다.
3. 대안: 현 전체 스냅샷 기준선, 동네별 사전정렬, 동네 객체+요청 정렬, DB 직접 조회.
4. 주장: 사전정렬의 승리를 입증하려 하지 않는다. 어떤 데이터/요청/변경 조건에서 각 구조가 유리한지 확인한다.
5. 성공 조건: 정합성 계약 충족, 1초 miss 대기 예산 동작 확인, 동일 조건 자원·지연 비교와 원인 귀속. 이득이 없으면 단순한 대안 선택.

### 순서

1. 기준선 코드/실행 환경/데이터/기존 CPU·JIT 문서와 사용 가능한 측정 도구를 고정하고 기록한다.
2. 버전/커서/원본 읽기 계약을 먼저 구현·검증한다. 필요한 최소 비교 경로를 만든다. 네 구조를 동시에 운영 기능으로 영구 유지할 필요는 없다.
3. 후보 간 정적 5축 결과와 커서 페이지가 동등한지 확인한다. 기존 전체 기준선이 새 계약과 다른 지점은 명시하고, 정합성 보정 비용과 조회 전략 비용을 섞지 않는다.
4. 단일 동네 적재와 재사용 비용부터 확인하고, 이후 hit/miss·버전 교체·요청 편중/분산 조건을 비교한다.
5. 준비된 배열 한 벌당 실제 재사용 횟수와 준비 비용 회수 여부를 계산한다. 모든 동네·모든 축을 읽는다는 가정을 고정하지 않는다.
6. 근거가 생긴 뒤 캐시 예산/선적재/동시 적재 제한/TTL 필요성을 선택한다.
7. 선택한 코드, 테스트, 측정 원자료, 채택/기각 이유, 한계를 최종 기록한다.

### 필수 검증 경계

- 원본 변경+버전 커밋/롤백, 동네 이동의 양쪽 버전, 변경 없는 이름/썸네일의 cursor 유지.
- 여러 동네의 read view와 로드 중 버전 변경. 적재 관측 버전 오표기 금지.
- 인스턴스 간 이동, 동일 버전 캐시 eviction 후 재적재, 삭제된 표시 holder 때문에 frozen 대상이 누락되는 기존 경로 제거.
- 정적 5축의 tie-break/필터/커서 등가, 빈 동네와 여러 동네 합집합.
- 같은 동네 적재 공유, 실패전파, 요청 timeout 격리, 오래된 적재가 새로운 캐시를 덮는 경쟁.
- 정기 전체 배치가 표시값만 수정된 동네도 갱신 대상으로 포함.

### 측정과 해석

앱/DB CPU, SQL 및 digest 실행당 비용, 할당량/GC/live heap, hit/miss 지연, 처리량/오류, 배열 재사용 횟수를 연결한다. 기존 로컬 측정 지표 계약을 읽고 반복 재현성 없는 tail 지연을 운영 SLO로 인용하지 않는다. 기존 CPU/JIT 결론을 재설정하는 실험으로 확장하지 않는다.

실제 요청 분포가 없으면 가정한 부하임을 명시한다. 캐시 예산, 반복 수, 데이터 규모, 요청량과 기간은 사용 가능한 환경을 조사해 실행 계획에 수치로 고정한다. 조사는 가능하지만 이 문서 작성 시점에 신규 성능 실험은 수행하지 않았다.

## 6. 현재 구현에서 확인한 출발점

- `domain/place/cache/SortedPlaces.java`: 이미 동네별/정렬축별 배열. 바꾸려는 것은 적재/교체/버전/수명 단위.
- `SnapshotLoader.java`, `SnapshotInstaller.java`, `SnapshotBox.java`: 전체 원본 적재, RR 읽기, 전체 조립, 최신 한 장.
- `service/PlaceListRequestOrchestrator.java`: 요청 metadata 조회, cursorVersion 기준 catch-up, 현재 기본 대기 3초. revision 차이는 요청의 catch-up 기준이 아님.
- `service/PlaceService.java`: 현재 표시 holder에서 값이 없으면 행을 제거함. 새 frozen 대상 계약과 맞춰야 함.
- `cache/metadata/*`: 현재 전역 `(cursorVersion, revision)` 1행. 새 동네 버전 설계와 다름.
- `AdminPlaceService`, `AdminTagService`, `PlaceImageFieldUpdater`: 현재 관리자 선택/표시 patch 경로. 쓰기 분류를 자동 정책으로 바꿔야 함.
- `PlaceStatsBatchProcessor`: 현재 글로벌 ADVANCE. 동네별로 이전할 때 전체 배치의 대상 범위를 보존해야 함.
- `repository/querydsl/PlaceListDbQueryRepository`: 비교 가능한 기존 SQL 후보. 요청 경로 연결/같은 read view/계약 동등성은 별도 구현 검토 필요.
- `build.gradle`: Caffeine 의존성 있음.

로컬 `application.yml`은 ignored 설정이며 annotation 기본 cron과 다르다. 현재 로컬 설정을 운영 실제 주기라고 말하지 않는다. 비밀값을 문서/로그에 복사하지 않는다.

## 7. 종료 시 남길 기록

- 최종 선택과 비교에서 기각한 선택, 그 이유 및 적용 범위.
- 요구사항별 구현 위치와 검증 결과, 실행 명령/형상/실패·skip 여부.
- 캠페인 조건과 원자료 경로, 무효 라운드 및 무효 사유.
- 앱 자원 절약을 DB 비용 이전으로 오해하지 않도록 앱+DB 결과 구분.
- 측정으로 말할 수 없는 것, 운영 실제값 미확인 사항.
- 커서 포맷/마이그레이션/배포 직후 준비 등 전환 영향.
- 최종 cache budget/TTL/선적재/동시 적재 정책과 수치 근거. 미결정인 경우 정직하게 미결정으로 기록.
