## 실행계획을 확인한 이유

이번 작업은 운영 중인 API가 느려져서 시작한 것이 아니다. 아직 실사용 트래픽이 없는 서비스였고,
관측된 성능 문제도 없었다. 대신 인기순 조회 구조를 변경한 뒤, 설계할 때 세운 전제가 실제 쿼리에서도
성립하는지 확인할 필요가 있었다.

인기점수를 요청할 때마다 계산하는 대신 배치가 `place_stats`에 미리 계산해 두고, API는 현재 버전의
통계만 읽도록 구조를 바꿨다. 조회에는 다음 인덱스를 사용하도록 설계했다.

```text
(version, town_id, popular_score DESC, place_id, ...)
```

이 인덱스에 기대한 역할은 명확했다. 현재 버전과 요청 지역으로 범위를 좁히고, 인기점수 순서대로
읽다가 한 페이지에 필요한 11건을 찾으면 멈추는 것이다. 조회에 필요한 값도 인덱스에 포함했으므로
가능하면 테이블 본문을 다시 읽지 않고 처리가 끝나기를 기대했다.

하지만 인덱스를 만들었다고 MySQL이 반드시 의도한 방식으로 사용하는 것은 아니다. 그래서 실제 API가
만드는 SQL에 `EXPLAIN ANALYZE`를 실행했다. 이는 쿼리를 실제로 수행하면서 MySQL이 선택한 실행 순서와
각 단계의 실제 행 수, 반복 횟수, 소요 시간을 보여주는 명령이다. 부하를 측정하려는 것이 아니라 다음
세 가지 설계 가설을 확인하려는 목적이었다.

```text
단일 동네: 인기순 인덱스를 따라 읽고 별도 정렬 없이 11건에서 멈추는가?
여러 동네: 정렬이 필요하더라도 커버링 인덱스 안에서 처리되는가?
태그 필터: 태그 조인 때문에 place_stats 중심의 실행 순서가 바뀌지 않는가?
```

태그가 없는 조회는 예상대로 동작했다. 단일 동네에서는 인덱스에서 11건만 읽고 멈췄고, 여러 동네도
테이블 본문을 조회하지 않은 채 인덱스 엔트리만 정렬했다.

예상 밖의 결과는 태그 필터를 추가했을 때 나왔다. 같은 인기순 조회인데 MySQL이 `place_stats`가 아닌
`place_tag`에서 조회를 시작했다. 그 결과 인기순으로 정렬된 인덱스와 11건을 찾았을 때 멈추는 방식을
모두 사용하지 못했다. 먼저 태그에 연결된 장소 후보를 모으고, 중복을 제거한 다음 인기점수로 다시
정렬하는 실행계획이 선택됐다.

즉 이번 문제는 느린 API를 추적하다 발견한 것이 아니다. 새 조회 구조가 의도대로 동작하는지 검증하는
과정에서, 태그 조건이 붙을 때만 설계의 전제가 깨진다는 사실을 발견한 것이다.

## 태그 필터는 어떻게 생겼나

장소 목록은 메인·서브 태그 조건을 지원한다. 장소와 태그는 다대다 관계이므로 `place_tag`에서 해당
장소에 요청한 태그가 연결되어 있는지 `EXISTS`로 확인했다.

기존 쿼리는 연결된 태그가 활성 상태인지 확인하기 위해 `tags`까지 조인했다.

```sql
EXISTS (
    SELECT 1
    FROM place_tag pt
    JOIN tags t ON t.id = pt.tag_id
    WHERE pt.place_id = p.id
      AND t.id = :tagId
      AND t.active = 1
)
```

## 문제 상황

단일 동네·단일 태그 조회에서는 지역 후보가 100개, 태그 연결 후보가 1,146개였다. 옵티마이저는 더 작은
지역 후보를 주도 테이블로 선택했다.

인기순은 `place_stats`의 랭킹 인덱스에서 장소를 점수순으로 읽고, 각 장소의 태그 연결 여부를 확인했다.
조건을 만족하는 11개를 찾으면 즉시 중단하므로 실제로는 57개만 확인했고 별도 정렬도 필요하지 않았다.

```text
place_stats에서 지역 장소를 인기순으로 조회
→ 장소별 태그 연결 여부 단건 확인
→ 11개를 찾으면 조기 종료
```

최신순도 `places`에서 지역 후보를 먼저 만든 뒤 태그를 확인하고 `created_at` 기준 결과를 구성했다.

하지만 메인·서브A·서브B가 함께 들어오는 복수 태그 조회에서는 실행계획이 태그 주도로 뒤집혔다.

```text
tags 조건 평가
→ place_tag에서 태그 연결을 대량 탐색
→ 장소 테이블을 PK로 반복 조회
→ 지역 조건으로 대부분 제거
→ 복수 태그로 발생한 중복 제거
→ 인기 점수 또는 생성 시각으로 정렬
→ 상위 11개 반환
```

인기순에서는 `place_stats`의 랭킹 인덱스와 조기 종료를 잃었고, 최신순에서도 지역 필터보다 태그 연결
탐색이 먼저 수행됐다. 가장 비싼 조건에서는 `place_tag` 엔트리 10,536건을 읽고 장소를 2,874번 조회한
뒤, 지역 조건을 통과한 약 211건만 남겨 중복 제거와 정렬을 수행했다.

## 원인 분석

당시 `tags`의 34개 행은 모두 활성 상태였으므로 `active = 1`의 실제 통과율은 100%였다. 하지만 MySQL은
`active` 값의 분포를 판단할 통계가 없어 각 조건의 통과율을 10%로 추정했다.

단일 태그는 PK로 조회한 태그 한 행이 상수로 처리돼 다른 태그 집합과 결합되지 않는다. 반면 복수
태그에서는 각각 4개와 6개인 후보 집합이 카테시안 곱으로 결합된다. MySQL이 각 집합의 `active`
통과율을 10%로 과소평가하면서 오차도 함께 곱해졌고, 최종 결과를 실제 24행이 아닌 0.024행으로
예상했다.

```text
지역 후보:      100개 또는 1,800개
태그 후보 예상: 0.024개
```

이 정보를 기준으로 보면 태그부터 시작하는 것이 압도적으로 저렴해 보인다. 옵티마이저가 비합리적으로
동작한 것이 아니라, 부정확한 예상치를 근거로 합리적인 선택을 한 것이다.

따라서 문제의 본질은 다대다 관계 자체가 아니라 다음과 같았다.

```text
불필요한 active 재검증
→ 태그 선택도 오추정
→ 태그 후보의 과도한 과소평가
→ 비효율적인 조인 순서 선택
→ 대량 연결 탐색, PK 반복 조회, 중복 제거 및 재정렬
```

## 검증이 두 겹이었다

여기서 짚어야 할 것은 이 `active` 검사가 **없어도 되는 검사였다**는 점이다.

요청에 실린 태그 id의 존재·활성·타입은 저장소를 호출하기 전에 `TagValidator`가 이미 검증하고 있었다.
비활성 태그 id가 오면 `NOT_FOUND_TAG`로 막히므로 SQL에 도달하는 입력에는 비활성 태그가 없다. 이
검증은 이번 문제 때문에 추가한 것이 아니라 원래부터 있던 것이다.

즉 검증은 처음부터 두 겹이었다. 바깥 겹인 애플리케이션 검증은 이미 완결돼 있었고, 안쪽 겹인 SQL
재검사는 아무것도 더 막지 못하면서 비용만 치르고 있었다. 그런데 그 비용이 "조건 하나만큼 느려진다"가
아니라 **옵티마이저의 판단 재료를 오염시킨다**는 형태였다는 것이 이 문제의 핵심이다.

중복 검증은 보통 무해하다고 여겨진다. 방어적으로 한 번 더 확인해서 손해 볼 것이 없다는 감각이다.
그러나 SQL에서는 조건 하나가 실행계획 전체를 바꿀 수 있고, 그 조건이 선택도를 추정할 수 없는
컬럼이라면 옵티마이저는 추측에 의존하게 된다. 이번 경우 그 추측이 1,000배 어긋났다.

## 조인 순서를 강제하지 않은 이유

처음에는 `place_stats` 또는 `places`를 항상 주도 테이블로 고정하는 방안도 검토했다. 그러나 최적의
시작점은 태그 분포에 따라 달랐다.

```text
흔한 태그
→ 태그 연결 장소가 많음
→ 지역 장소부터 읽고 조기에 종료하는 것이 유리

희귀 태그
→ 태그 연결 장소가 적음
→ place_tag부터 읽는 것이 유리

결과가 없는 태그
→ place_tag부터 읽으면 즉시 종료 가능
```

실제로 장소 주도로 고정했을 때 흔한 태그는 4.2배 빨라졌지만, 희귀 태그(연결 장소 185개)는 약 2배,
결과가 없는 태그는 약 75배 느려졌다. 결과가 없는 태그는 `place_tag`부터 읽으면 0건을 확인하고 즉시
끝나는데, 힌트를 박으면 1,800건을 정렬해 놓고 하나씩 확인하다 아무것도 건지지 못한다.

즉 조인 순서 힌트는 특정 입력만 개선하고, 옵티마이저가 데이터 분포에 따라 계획을 바꿀 가능성을
제거했다. 따라서 빠른 실행계획 하나를 강제하는 대신, 잘못된 선택을 유발한 정보 자체를 바로잡는
방향을 선택했다.

## 해결

`place_tag.tag_id`는 `tags.id`를 참조하는 외래키이므로 연결된 태그의 존재는 이미 보장된다. 그리고
`pt.tag_id`가 곧 태그 id이므로 `t.id = :tagId`는 `pt.tag_id = :tagId`와 같은 조건이다. 조인이 보태던
정보는 `active` 하나뿐이었고, 그것은 위에서 본 대로 중복 검증이었다.

다대다 연결을 확인하는 `place_tag`는 유지하되, 비용 추정을 왜곡하던 `tags` 조인만 제거했다.

```sql
EXISTS (
    SELECT 1
    FROM place_tag pt
    WHERE pt.place_id = p.id
      AND pt.tag_id = :tagId
)
```

이를 통해 다음 효과를 얻었다.

```text
중복된 active 검증 제거
→ 선택도를 추측할 조건 제거
→ 태그 후보 규모 추정 정상화
→ 옵티마이저가 데이터 분포에 맞춰 조인 순서 선택
```

## 결과

전후를 같은 DB·같은 파라미터로 채취했다. 값은 `EXPLAIN ANALYZE` 최상위 노드 시간의 3회 중앙값이다.
최신순 정렬 인덱스까지 정리한 현재 스키마 기준이다.

측정한 요청은 이렇다. 조회 범위는 **동네 1곳**(장소 100개)과 **그 시의 동네 18곳**(장소 1,800개)이고,
태그는 실제 서비스 태그를 그대로 썼다.

| 태그 조합 | 사용자가 고른 것 | 그 태그가 붙은 장소(전국) |
|---|---|---|
| `카페` | 메인 태그 하나 | 1,146곳 |
| `카페` + 옵션 2종 | `카페` + `커피/디저트·작업·독서·힐링` 중 하나 + `시그니처메뉴·감성인테리어·채광좋음·콘센트많음·시간제한없음·바테이블` 중 하나 | 옵션1 각 424~455곳 · 옵션2 각 287~312곳 |
| `음식` + `바/술집` | 희귀한 서브 태그가 붙은 조합 | `바/술집` **185곳** |
| `맛집 · 디저트` | 활성 태그지만 붙은 장소가 없다 | **0곳** |

서브 태그는 타입 내 OR, 타입 간 AND다. 두 번째 줄이 화면에서 칩을 여러 개 눌렀을 때 나가는 가장
무거운 요청이다. 모든 요청은 `LIMIT 11`(첫 페이지 10건 + 다음 페이지 판정용 1건)로 나간다.

| 정렬 | 조회 범위 | 태그 조합 | 후보 → 통과 | before | after | |
|---|---|---|---:|---:|---:|---|
| 인기순 | 동네 1곳 | `카페` + 옵션 2종 | 100 → 10 | 11.30ms | **0.17ms** | **66.5배** |
| 최신순 | 동네 1곳 | `카페` + 옵션 2종 | 100 → 10 | 12.40ms | **0.18ms** | **67.4배** |
| 인기순 | 동네 18곳 | `카페` + 옵션 2종 | 1,800 → 211 | 22.30ms | **4.34ms** | **5.1배** |
| 최신순 | 동네 18곳 | `카페` + 옵션 2종 | 1,800 → 211 | 20.90ms | **2.77ms** | **7.5배** |
| 인기순 | 동네 1곳 | `카페` | 100 → 17 | 0.076ms | 0.082ms | 차이 없음 |
| 최신순 | 동네 1곳 | `카페` | 100 → 17 | 0.143ms | **0.099ms** | 1.4배 |
| 인기순 | 동네 18곳 | `음식` + `바/술집` | 1,800 → 65 | 0.842ms | 0.655ms | 계획 동일 |
| 인기순 | 동네 18곳 | `맛집 · 디저트` | 1,800 → 0 | 0.011ms | 0.016ms | 계획 동일 |

"후보 → 통과"는 조회 범위의 활성 장소 수와 태그 조건을 통과한 장소 수다. 응답은 그중 앞의 10건이다.
100개 중 10개를 고르는 요청이 11~12ms였다는 뜻이고, 그 10개를 찾으려고 `place_tag` 엔트리를
10,536건 훑고 있었다.

**태그가 하나뿐인 조회는 거의 바뀌지 않았다.** 단일 태그에서는 10% 과소평가가 한 번만 적용되므로
태그 후보 추정이 1,146개에서 100여 개 수준으로 줄어들 뿐, 지역 후보 100개보다 작아지지 않는다.
그래서 실행계획이 원래부터 지역 주도였고, 실제로 변경 전후의 실행계획이 노드 단위로 동일하다.
개선은 태그를 여러 개 걸어 오차가 곱해질 때만 나타나며, 이는 원인 분석과 일치한다.

동네 단위 복수 태그 조회에서는 주도 테이블이 지역으로 돌아왔다. 여러 동네를 묶어 조회할 때는 지역
후보 1,800개가 태그 후보 1,146개보다 많으므로 여전히 태그 주도가 선택되지만, 훑는 엔트리가
10,536개에서 1,146개로 줄어 5~7.5배 빨라졌다. 이 선택은 정확한 추정치에 근거한 것이므로 되돌릴
이유가 없다.

**희귀 태그와 결과가 없는 태그에서는 실행계획이 노드 단위로 동일했다.** 두 조합의 시간 차이는
10~20µs 수준으로 측정 노이즈다. 오추정이 판단을 좌우하지 않던 입력에서는 아무것도 바뀌지 않는다는
뜻이고, 이것이 힌트를 사용하는 방식과 갈리는 지점이다.

결과 집합이 바뀌지 않는다는 것은 `PlaceListDbQueryRepositoryIT`와 `PlaceListFlowIT`의 32개 테스트로
확인했다.

## 이 수치로 말할 수 없는 것

- 부하 0에서 단일 쿼리를 잰 값이다. 요청 하나는 이 쿼리 외에도 SQL을 여러 개 사용하므로, 66배는
  전체 응답시간의 배수가 아니라 이 쿼리의 배수다.
- 실제 트래픽에서 태그 필터 조회의 비중을 아직 모른다. 어떤 조합이 얼마나 들어오는지 모르는 상태에서
  잰 값이다.
- 검증 데이터의 `tags` 34개 행이 모두 활성이라 `filtered 10.00`의 오차가 최대인 조건이었다. 비활성
  태그가 섞인 환경에서는 격차가 이보다 작을 수 있다.

## 남는 것

`ANALYZE TABLE tags UPDATE HISTOGRAM ON active`로 통계를 만들어도 같은 결과에 도달한다. 코드를
바꾸지 않아도 되지만 택하지 않았다. MySQL 히스토그램은 자동 갱신되지 않고 `mysqldump`에도 실리지
않아서, 환경을 새로 구성하거나 백업을 복원할 때 누락되면 아무 오류 없이 원래 성능으로 되돌아간다.
조인 제거는 성능이 코드에 담기므로 배포 환경과 무관하게 동일하게 동작한다.

이 개선의 핵심은 조인 순서를 고정한 것이 아니다. 중복된 검증을 애플리케이션 한 곳으로 정리하고,
옵티마이저의 비용 계산을 왜곡하던 불필요한 조인을 제거함으로써 데이터 분포에 따른 실행계획 선택권을
보존한 것이다.

같은 병을 두 번 만났다. 처음에는 부하가 무너지고 나서야 원인을 거슬러 올라가 찾았고, 두 번째는
"조인 순서가 뒤집히지 않는다"를 점검 목록에 적어 둔 덕에 사용자가 겪기 전에 찾았다. 한 번 겪은
결함을 다음 구조에서 확인할 항목으로 옮겨 적는 일이, 결국 두 번째를 훨씬 싸게 만들었다.
