# 2026-08-10 · `place_tag` 태그 방향 인덱스를 커버링으로 — 기각

> 캠페인: [`load-test/campaigns/2026-08-10_place-tag-covering-index`](../../load-test/campaigns/2026-08-10_place-tag-covering-index/)
> **부하 테스트가 아니다.** 인덱스 형태 판정이라 `EXPLAIN ANALYZE`로 답한다 (가이드 §2).
> 처리량·백분위에 대해서는 **아무것도 주장하지 않는다.**
> 채취 2026-08-10, 32건(정렬 2 × 범위 2 × 태그 조합 4 × 인덱스 형상 2) 각 3회.
> 다섯 항목은 측정 전에 등록했다 — 캠페인 README에 있다.
> **제품 코드·마이그레이션은 건드리지 않았다.** 스크립트가 벤치 DB의 인덱스만 오가며 잰다.

**등록 기준으로는 기각이다.** 시 단위 조회는 전부 1.2~1.5배 좋아지지만, 등록해 둔 "어떤 입력도
나빠지지 않는다"가 깨졌다. 그리고 얻는 것의 절대 크기가 0.5~0.6ms인데 **DB는 현재 병목이 아니다**
(2026-08-07 A/B에서 앱 스로틀 66.0% 대 MySQL 1.0%).

**그럼에도 채택했다.** §1~§7은 측정 그대로 두고, 판단이 바뀐 자리만 §9에 덧붙인다 —
사전 등록한 판정을 사후에 고쳐 쓰면 등록의 의미가 사라진다.

## 1. 무엇을 바꿔서 쟀는가

```sql
-- before (현행)
CREATE INDEX idx_place_tag_tag_id    ON place_tag (tag_id);
-- after
CREATE INDEX idx_place_tag_tag_place ON place_tag (tag_id, place_id);
```

`place_tag`의 PK가 대리키 `id`라, InnoDB 보조 인덱스의 리프에는 `(tag_id, id)`만 실린다.
**태그로 장소를 찾는 것이 이 인덱스의 유일한 용도인데 `place_id`가 없다.** 그래서 태그로 찍은
행마다 클러스터드 인덱스를 한 번 더 봐야 한다. 반대 방향 `uk_place_tag_place_tag (place_id, tag_id)`는
이미 커버링이므로, 이 변경은 **비대칭을 맞추는 것**이다.

두 형상 모두 `ANALYZE TABLE place_tag` 직후에 측정했다 — 인덱스를 바꾸면 통계도 함께 바뀌므로
한쪽만 신선한 통계를 갖는 일이 없게 대칭으로 맞췄다.

## 3. 등록한 전제가 이미 무너져 있었다

주장 ①은 2026-08-06 캠페인의 트리에서 읽은 것이었다. 그때 인기순·서울·태그 3개는 이랬다.

```
Covering index scan on pt using uk_place_tag_place_tag   rows=15,461   ← 인덱스를 통째로 훑음
```

**V32 형상에서는 이 노드가 나오지 않는다.** 같은 쿼리의 before가 이렇다.

```
Index lookup on pt using idx_place_tag_tag_id (tag_id=1)   rows=1,146   0.117..0.717ms
```

즉 `place_stats`를 장소당 1행으로 되돌리고 인덱스에서 `version`을 걷어낸 V32가, **의도하지 않게
인기순의 태그 접근 경로까지 바꿔 놓았다.** 전체 스캔을 고르게 만들던 비용 계산이 사라진 것이다.

그래서 ①은 "개선되지 않았다"가 아니라 **"고칠 대상이 이미 없다"**로 판정한다. 이 캠페인이 답한
질문은 남은 하나 — 비커버링 조회를 커버링으로 바꾸면 무엇이 달라지는가 — 뿐이다.

## 4. 결과

시간은 `EXPLAIN ANALYZE` 최상위 노드 actual time의 **3회 중앙값**(ms)이다.
**판정은 시간이 아니라 플랜 형상으로 한다** (등록 시 "2배 미만 예상"으로 기록해 둔 대로다).

### 4.1 시 단위 18곳 — 전부 좋아졌다

| 정렬 | 태그 조합 | before | after | |
|---|---|---:|---:|---|
| 인기순 | `카페` | 1.70 | **1.34** | 1.3배 |
| 최신순 | `카페` | 1.90 | **1.53** | 1.2배 |
| 인기순 | `카페` + 옵션 2종 | 2.66 | **2.02** | 1.3배 |
| 최신순 | `카페` + 옵션 2종 | 2.97 | **2.43** | 1.2배 |
| 인기순 | `음식` + `바/술집` | 0.741 | **0.507** | 1.5배 |
| 최신순 | `음식` + `바/술집` | 0.909 | **0.683** | 1.3배 |
| 인기순 | `맛집 · 디저트`(0건) | 0.0222 | 0.0188 | 노이즈 |
| 최신순 | `맛집 · 디저트`(0건) | 0.0170 | 0.0213 | 노이즈 |

**주도 테이블은 여덟 칸 모두 그대로다.** 바뀐 것은 `pt` 접근 노드 하나다.

```
before  -> Index lookup on pt using idx_place_tag_tag_id (tag_id=1)          rows=1,146  0.117..0.717ms
after   -> Covering index lookup on pt using idx_place_tag_tag_place (...)   rows=1,146  0.0265..0.157ms
```

같은 1,146행인데 **0.717 → 0.157ms, 4.6배**다. 이 차이가 곧 "행마다 붙던 숨은 클러스터드 조회"의
크기이고, 주장 ②가 말한 것이 이것이다. 최신순도 같다(0.774 → 0.179ms).

전체 시간이 1.2~1.3배에서 그치는 이유는, 이 노드 뒤에 붙는 1,146번의 `places`/`place_stats`
PK 조회(약 0.8ms)와 정렬이 그대로 남기 때문이다. **없앤 것은 태그 쪽 절반이지 조회 전체가 아니다.**

### 4.2 동네 1곳 — 여기서 깨졌다

| 정렬 | 태그 조합 | before | after | 플랜 |
|---|---|---:|---:|---|
| 인기순 | `카페` | 0.0928 | 0.0910 | 동일 |
| 최신순 | `카페` | 0.126 | 0.0917 | 동일 |
| 인기순 | `카페` + 옵션 2종 | 0.177 | 0.165 | 동일 |
| 최신순 | `카페` + 옵션 2종 | 0.179 | 0.229 | 동일 (§4.4) |
| 인기순 | `음식` + `바/술집` | 0.139 | 0.125 | 동일 |
| **최신순** | **`음식` + `바/술집`** | **0.172** | **0.352** | **뒤집힘** |
| 인기순 | `맛집 · 디저트`(0건) | 0.0144 | 0.0219 | 동일 |
| 최신순 | `맛집 · 디저트`(0건) | 0.0120 | 0.0245 | 동일 |

동네 1곳은 태그를 걸어도 지역 주도가 유지되던 자리다. 한 칸만 빼고 그대로였다.

```
before  -> Limit: 11                                             (정렬 노드 없음)
            -> Covering index lookup on p using idx_places_town_active_created
                                     (town_id=301, active=1) (reverse)   rows=100
                -> Single-row covering lookup on pt (place_id=p.id, tag_id=21)   loops=100

after   -> Limit: 11
            -> Sort: p.created_at DESC, p.id DESC                ← 정렬이 새로 생겼다
                -> Covering index lookup on pt using idx_place_tag_tag_place (tag_id=21)  rows=185
                    -> Single-row lookup on p using PRIMARY      loops=185   ← 179건이 버려진다
```

**태그 쪽을 싸게 만들자 옵티마이저가 그쪽으로 기울었다.** 그런데 이 입력에서는 지역이 100곳이고
태그가 185곳이라 태그 주도가 틀린 선택이고, 게다가 `idx_places_town_active_created`를 역방향으로
읽으면 공짜로 얻던 `created_at DESC` 순서까지 잃어 **정렬 노드가 새로 생겼다.**

옵티마이저는 after를 더 싸다고 봤다(추정 비용 115 → 91.2). 실제로는 3배 느렸다.
**정렬을 공짜로 얻는다는 이점이 비용 모델에 제대로 반영되지 않는다.**

### 4.3 이것이 힌트를 기각했던 이유와 같은 모양이다

2026-08-06에 `JOIN_PREFIX(ps)`를 기각한 근거는 "특정 입력만 개선하고 다른 입력을 망가뜨린다"였다.
커버링 인덱스는 계획을 강제하지 않고 재료만 바꾸는 처방이라 그 함정에서 자유로울 것으로 봤는데,
**접근 경로를 싸게 만드는 것도 옵티마이저를 특정 방향으로 기울인다**는 점에서 같은 부작용을 냈다.

차이는 크기다. 힌트는 결과 0건 태그에서 **75배** 손해였고, 이 인덱스는 희귀 태그 한 조합에서
**2배**(절대 +0.18ms)다. 그래도 등록해 둔 조건 ③은 "나빠지지 않는다"였고, 깨졌다.

### 4.4 "동일"로 읽은 근거와 읽지 못한 것

결과 0건 태그(네 칸)는 시간이 1.3~2배로 흔들리지만 **절대값이 12~25µs**라 노이즈로 본다.
`rows=0`을 확인하고 즉시 끝나는 트리가 두 형상에서 같다.

**최신순·동네 1곳·태그 3개(0.179 → 0.229)는 설명하지 못했다.** 트리가 노드 단위로 완전히 같은데
after 3회(0.229 / 0.227 / 0.238)가 before 3회(0.177 / 0.179 / 0.210)보다 일관되게 높다. 같은 일을
하는데 시간만 다르므로 계측 순서나 버퍼 상태를 의심하지만, 확인하지 않았다. 판정은 트리를 따라
"동일"로 두되 이 어긋남을 기록해 둔다.

## 5. 측정만 놓고 보면 채택할 이유가 약하다

| | 얻는 것 | 잃는 것 |
|---|---|---|
| 시 단위 8칸 | 1.2~1.5배 (절대 0.2~0.6ms) | — |
| 동네 1곳 7칸 | 미세하거나 없음 | — |
| 동네 1곳 · 최신순 · 희귀 | — | **2배** (절대 +0.18ms), 플랜 뒤집힘 + 정렬 추가 |

여기에 세 가지를 더 놓는다.

1. **DB는 지금 병목이 아니다.** 2026-08-07 A/B는 서울 전체 + 태그 3개 조합을 가중치 40%로 치는
   시나리오였는데, 그 부하에서 앱 스로틀 66.0% 대 MySQL 1.0%였다. 버퍼풀 적중 100%, 락 대기 0.
2. **얻는 것이 절대 0.5ms 안팎이다.** 요청당 커넥션 점유가 1.88ms인 것과 견주면 무시할 크기는
   아니지만, 그 몫을 부하 중 digest로 확인하지 않은 채 채택할 이유는 없다.
3. **V32가 이미 큰 몫을 가져갔다.** 이 캠페인이 겨냥한 15,461 전체 스캔은 손대기 전에 사라져 있었다.

## 6. 이 채취로 말할 수 없는 것

- **부하 중 효과를 모른다.** 부하 0에서 단일 문장을 잰 CPU 시간이다. 동시성이 올라가면 클러스터드
  인덱스 재방문의 래치 경합이 달라질 수 있는데, 그건 이 방법으로 안 보인다.
- **쓰기 비용을 재지 않았다.** 인덱스 리프가 행당 8바이트 늘어나는 계산은 했으나(15,461행 ≈ 124KB),
  `place_tag` INSERT·DELETE의 실제 비용 변화는 측정하지 않았다.
- **플랜 뒤집힘이 다른 희귀 태그에서도 일어나는지 모른다.** 뒤집힌 조합은 `바/술집`(185곳) 하나다.
  더 희귀한 태그(예: 20곳)라면 태그 주도가 옳은 선택이 되므로 뒤집힘이 손해가 아닐 수 있다.
  **임계가 어디인지 재지 않았다.**
- **§4.4의 어긋남(트리는 같은데 3회가 모두 높다)을 규명하지 못했다.**
- **결과 집합 불변(주장 ④)을 확인하지 않았다.** 마이그레이션을 만들지 않아 IT를 돌릴 대상이 없다.

## 7. 남는 것

1. **`idx_place_tag_place_id (place_id)`가 `uk_place_tag_place_tag (place_id, tag_id)`의 프리픽스와
   겹친다.** 이번 채취에서 눈에 띈 것으로, 지우면 쓰기 비용과 저장 공간이 준다. 별개 사안이라
   여기서 다루지 않았다.
2. **뒤집힘의 임계 탐색.** 태그 규모를 20 / 50 / 100 / 185로 놓고 어디서 지역 주도가 유리해지는지
   보면, 채택 여부를 "나빠지는 입력이 있다/없다"가 아니라 크기로 판단할 수 있다.
3. **뒤집힘이 실트래픽에서 얼마나 발생하는지 모른다.** 채택했으므로(§9) 이제 이건 감수한 위험이다.
   최신순 + 동네 1곳 + 희귀 서브태그가 얼마나 오는지는 실트래픽 관측이 답할 문제다.

## 9. 채택 결정 (2026-08-10, 측정 이후)

**등록한 기각 조건을 알고 뒤집었다.** 근거는 셋이다.

1. **인덱스 형태가 틀린 것은 사실이고, 그 사실은 트래픽과 무관하다.** `(tag_id)` 단일 컬럼이
   `place_id`를 못 싣는 것은 튜닝 선택이 아니라 빠뜨린 것에 가깝다. 반대 방향은 이미 커버링이다.
2. **손해의 절대 크기가 +0.18ms이고 한 조합이다.** 반면 이득은 시 단위 8칸 전부이고, 그중 서울
   전체 + 흔한 태그는 무태그 다음으로 트래픽이 몰릴 경로다.
3. **되돌리기가 마이그레이션 한 줄이다.** 실트래픽에서 뒤집힘이 문제가 되면 그때 되돌린다.

**감수하는 것을 다시 적어 둔다** — 최신순 · 동네 1곳 · 연결 185곳짜리 서브태그에서 주도 테이블이
지역에서 태그로 뒤집히고 `Sort` 노드가 생긴다(0.172 → 0.352ms). 뒤집힘의 임계(연결 몇 곳부터
태그 주도가 옳아지는가)는 **재지 않았다.** 185는 지역 후보 100보다 크므로 틀린 선택이 맞지만,
더 희귀한 태그에서는 같은 뒤집힘이 옳은 선택일 수 있다.

적용한 것:

| | |
|---|---|
| 마이그레이션 | `V33__make_place_tag_tag_index_covering.sql` — `(tag_id, place_id)` 생성 후 `(tag_id)` 제거 |
| 엔티티 | `PlaceTag`의 `@Index`를 `idx_place_tag_tag_place`로 교체 |
| 검증 | `PlaceListDbQueryRepositoryIT` 17 · `PlaceListFlowIT` 17 · `PlaceListSqlCountIT` 3 = **37개 전부 통과** (주장 ④) |

`idx_place_tag_place_id`의 중복 제거는 **함께 넣지 않았다.** 재보지 않은 변경을 잰 변경에 묶으면
회귀가 났을 때 원인을 가를 수 없다.
