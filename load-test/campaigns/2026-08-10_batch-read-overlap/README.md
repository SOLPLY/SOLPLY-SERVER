# 통계 배치와 읽기 트래픽 겹침 — 결합 vs 분리 저장 구조의 격리 검증 (사전 등록)

> **이 문서는 첫 측정 이전에 작성됐다.** 결과를 보고 고치지 않는다.
> (측정 전 수정 1회: 안정성 주장·스로틀 게이트 추가 — 사용자 지시, 첫 라운드 이전)
> 이슈 없이 진행한다(사용자 지시). 산출물은 캠페인 디렉터리와 `docs/perf/2026-08-10-batch-read-overlap.md`.

## 0. 이 캠페인이 채우는 논증의 자리

설계 서사의 마지막 화살표를 실측으로 채운다:

```text
실시간 증분 갱신 → 정적 데이터 페이지까지 상시 쓰기 영향권      (기각됨)
→ 실시간을 유지할 가치가 없다 → 배치 사전 집계                  (검증됨: 기존 캠페인)
→ 그런데 배치여도 통계가 places 안에 있으면
  배치 창 동안 같은 문제가 생기지 않나?                          (★ 이번 측정)
→ 그래서 place_stats 분리                                        (현행)
```

집계 방식(배치)의 근거는 이미 검증됐다. 이번에 재는 것은 **저장 구조 분리의 근거** 하나다.

## 1. 문제

통계(북마크 수·리뷰 수·평점·인기점수)를 `places`에 비정규화하면, 배치가 전 행을
UPDATE하는 창 동안 **정적 데이터(장소명·주소·좌표)가 담긴 16KB 페이지가 통째로 더티**가
되고, 그 페이지를 읽는 동시 요청이 언두 순회·페이지 래치·flush I/O의 영향권에 든다는
우려가 분리의 근거였다. 이 근거는 지금까지 이론이었고 실측 수치가 없다.

## 2. 원인 가설

1. **결합 구조**: 전 행 배치 UPDATE는 `places` 클러스터드 페이지 전체를 더티로 만든다
   (변경분은 통계 컬럼뿐이어도 더티는 페이지 단위다). 배치 창의 동시 읽기는 places
   행에서 언두 체인을 순회한다.
2. **분리 구조(현행)**: 같은 배치가 `place_stats` 페이지만 더티로 만들고, `places`
   페이지는 클린으로 남는다. 정적 데이터 읽기는 배치 창에도 영향권 밖이다.
3. 읽기끼리는 공유 래치라 경합이 없다 — 경합이 존재할 수 있는 창은 배치 겹침뿐이다.

## 3. 기술적 선택 (비교 대상)

서빙 경로를 고정하고(제품 코드 무변경) **배치 쓰기의 착지점만** 바꾼다.

| 팔 | 배치 착지점 | 실현 방법 |
|---|---|---|
| **B-분리** (현행) | `place_stats` | 카운트 배치와 동일한 UPSERT+DELETE 문장을 수동 발화 |
| **A-결합** (흉내) | `places` | 벤치 DB 전용 더미 통계 컬럼 5개 + 미러 커버링 인덱스에 같은 집계를 UPDATE |
| **P-양성 대조** | `place_stats` 핫 페이지 | 인접 place_id에 동시 20 커넥션 증분 UPDATE 폭주 — 계측 검출력 증명 전용 |

- 두 팔의 집계 서브쿼리(북마크 약 1,040만 행 스캔)는 동일하다 — 다른 것은 착지점뿐.
- 서빙은 두 팔 모두 `skeleton-source=entity`로 고정한다. 스냅샷 캐시가 켜져 있으면
  읽기가 `places`를 아예 읽지 않아 결합 팔의 충돌이 관측 불가능하고, 결합 가설의 세계에는
  그런 캐시가 없다. ENTITY 모드가 "places를 JOIN해 읽는" 가설의 세계에 대응한다.
- **캐시 변수의 처리**: 골격 캐시는 이 실험이 재려는 문제를 가릴 수 있는 교란 변수라
  끄고 잰다. 이 선택은 안정성 주장을 약화시키지 않는다 — ENTITY는 현행 서빙보다 DB 읽기가
  엄격히 많은 경로이므로, **캐시 없이 안정이면 캐시 켠 운영 구성은 더 안정**이다(하한 논증).
- 실배치 cron은 라운드 오염 방지를 위해 비활성한다(`count-cron`/`score-cron` = `-`,
  Spring CRON_DISABLED). 부팅 백필은 그대로 두어 데이터를 채운다.

## 4. 검증할 주장

> **① 동일 읽기 부하·동일 집계 배치에서, 분리 구조는 `places` 페이지를 클린으로 유지하고
> 결합 구조는 정적 데이터 페이지를 대량 더티로 만든다. ② 분리 구조(현행)는 배치 창에서도
> 목표 부하를 오류 없이 안정적으로 처리한다. 배치 창의 읽기 비용 차이는 원인 지표
> (언두 페이지 읽기·래치 대기·창 내 실행당 레이턴시)로 기록한다.**

갈래를 미리 적는다:

- (a) 더티 격리 재현 + 결합 팔에서만 읽기 원인 지표 악화 → 분리 근거 성립, 서사 그대로
- (b) 더티 격리는 재현되나 읽기 원인 지표가 두 팔 모두 바닥(검출 한계 아래) → 분리의
  실증 근거는 "페이지 오염 격리"까지이고, "읽기 지연 방어"는 현 규모에서 주장하지 않는다
- (c) 분리 팔에서도 places 더티가 다수 → 가설 자체를 재검토(예상 밖 쓰기 경로 규명 먼저)
- (d) 양성 대조에서 래치·언두 카운터가 안 움직임 → **본 라운드 진입 금지**, 계측 구성 수정

## 5. 성공 조건과 지표 계약

효과 크기 예상: 더티 census는 **자릿수 차이(0 vs 수백 페이지)** — 호스트 노이즈와 무관한
결정론적 지표라 환경 통제를 최소로 한다. 읽기 레이턴시 영향은 2배 미만이 예상되므로
가이드 A.1에 따라 **클라이언트 응답시간으로 판정하지 않는다.**

| 구분 | 지표 | 출처 |
|---|---|---|
| **1급 (판정)** | 배치 직후 테이블·인덱스별 더티 페이지 수 | `INNODB_BUFFER_PAGE` census (배치 커밋 직후) |
| **1급 (판정)** | 배치 창 vs 대조 창의 읽기 문장 실행당 레이턴시·rows | digest 창 스냅샷 (DB 내부 측정 — 앱 스로틀 무관) |
| **1급 (판정)** | 언두 페이지 읽기, 히스토리 리스트 길이, 전역 더티 페이지 수 | `INNODB_METRICS`·global status 1초 샘플러 |
| **1급 (판정)** | InnoDB synch 대기(COUNT·SUM_TIMER) 창 diff | `events_waits_summary_global_by_event_name` |
| ~~전역 rwlock spin/os-wait~~ | `INNODB_METRICS` `innodb_rwlock_*` — **판정 제외.** 이 빌드(8.0.46)에는 페이지 래치 인스트루먼트(`buf_block_lock`)가 없어 근사 후보로 넣었으나, 검출력 게이트(초당 7.2만 UPDATE 폭주)에서도 **전부 0으로 무반응**임이 판명됐다. 래치 증거의 정본은 위 PFS synch 창 diff(게이트에서 1.25억 회/4.97초 반응 확인)다 | 기록만 |
| 참고 | p50, 앱 스로틀, 배치 소요 시간 | Artillery·cgroup `cpu.stat` |
| **주장하지 않음** | p95·p99, 처리량 절대값, flush I/O 절대값(로컬 디스크) | 재현성 미증명·단일 호스트 |

**성공 조건 (상대 조건):**

1. **격리 주장**: B-분리 라운드에서 배치 직후 `places` 더티 페이지 ≈ 0(바닥값 수준)이고
   `place_stats`만 더티, A-결합 라운드에서 `places` 더티 페이지가 자릿수로 크다 —
   두 라운드씩 재현되면 성립.
2. **검출력 게이트**: P-양성 대조에서 래치 대기·언두 카운터·히스토리 리스트가 움직인다.
   이 게이트를 통과하기 전의 0은 판정에 쓰지 않는다.
3. **안정성 주장(B-분리)**: 배치 창을 포함한 measure 구간에서 실패 0·도착률 결손 ≤2%,
   배치 창의 읽기 문장 실행당 레이턴시가 대조 창 대비 자릿수 악화 없음 — 2라운드 재현 시
   "캐시 없이도 목표 부하에서 배치 겹침 안정"이 성립하고, 캐시 켠 운영 구성은 하한 논증으로
   덮인다.
4. 읽기 영향(창 내 실행당 레이턴시·언두 읽기)은 관측값으로 기록하되, 간극이 산포 안이면
   "구분 불가"로 적는다 — 그것도 결과다.

## 6. 라운드 프로토콜

시나리오는 직전 캠페인 `mode-fixed-300.yml`을 본으로 하되 **measure를 60→120초로 연장**한다
(배치 창이 들어갈 자리). 사다리 w1~w5(150초)는 그대로, 전부 측정 제외.

한 라운드 안에 **대조 창과 배치 창이 함께 들어간다** — 별도 무배치 라운드를 두지 않고
같은 라운드의 앞 구간이 바닥값을 제공한다.

```text
t0        Artillery 시작 (사다리 150s)
t0+150    measure 진입 (300 arrivals/s 정상상태)
t0+160    [대조 창] waits C0 스냅샷 + digest 비움
t0+175    [대조 창 끝] digest 덤프(control) + waits C1
t0+190    [배치 창] census(pre) + waits B0 + digest 비움 → 배치 발화 (블로킹, 소요 기록)
커밋 직후  digest 덤프(batch) + waits B1 + census(post)
t0+270    measure 종료 → metrics-snapshot report
```

- 언두 샘플러(1초 간격: 히스토리 리스트·언두 페이지 읽기·전역 더티 페이지·Threads_running)는
  라운드 내내 돈다.
- P 라운드는 t0+190에 배치 대신 15초 폭주를 발화한다.
- census는 버퍼 풀 전수 조회라 무겁다 — **배치 커밋 직후에만** 실행하고, 그 이후 구간의
  레이턴시는 어느 창에도 넣지 않는다.

**라운드 구성과 순서** (라운드 간 60초 휴식):

```text
r0 (폐기)   B-분리 — JIT 워밍업 + 프로토콜 리허설
r1 B-분리   r2 A-결합   r3 B-분리   r4 A-결합     ← 교대 배치로 드리프트 균등화
r5 P-양성대조                                      ← 마지막 (카운트 오염이 본 라운드에 안 닿게)
```

판정 지표가 결정론(더티 census 0 vs 수백)이라 팔당 2회 재현으로 충분하다고 사전에 정한다.
P 라운드의 `bookmark_count` 오염은 다음 B 배치 문장 1회 발화로 재계산·복구한다(캠페인 종료 시).

**무효 조건** — 직전 캠페인 규칙 재사용: cgroup 기준 상한 초과, 도착률 결손 >2%, 호스트
스톨 서명(앱·DB 동시 급등), 컨테이너 재시작. 추가: **실배치 cron 발화가 로그에 보이면
그 라운드 무효**(비활성 설정이 안 먹은 것). 오염 구간만 잘라내지 않는다 — 라운드 폐기 후 재실행.

**스로틀 게이트 (부하점 확정)**: 배치 창의 읽기 지연이 CPU 포화 지연과 섞이면 안 되므로,
r0(폐기 라운드)의 measure 구간에서 앱 cgroup `cpu.stat` 스로틀 비율이 **5%를 넘으면 부하를
300 → 240 arrivals/s로 내리고 전 라운드를 같은 부하점에서 다시 시작한다.** ENTITY 300의
근거는 08-09 캠페인(같은 시나리오·같은 사다리에서 entity 300 유효 라운드 성립, 붕괴는
420)이지만, 이 게이트가 실측으로 확정한다. 팔 간 비교는 반드시 동일 부하점에서만 한다.

## 7. 형상과 환경

- 브랜치 `develop` (제품 코드 무변경). 커밋 해시는 실행 시각에 기록.
- 벤치 스택: `docker/docker-compose.bench.yml` (앱 2vCPU/2G, MySQL 8.0 2vCPU/3G·버퍼풀 2G).
- 앱 기동: `BENCH_APP_JSON='{"solply.place-list.skeleton-source":"entity","solply.place-stats.count-cron":"-","solply.place-stats.score-cron":"-"}'`
  + `up -d --force-recreate` (`docker restart`로는 환경변수 미반영).
- 전환 검증은 설정값이 아니라 실행된 SQL로 한다: digest를 비우고 요청 1건 → 페치조인+
  이미지 문장이 보이면 ENTITY. p6spy OFF는 로그로 검증.
- A팔 스키마는 벤치 DB에만 수동 적용(`bench/10-colocated-schema.sql`), 종료 후
  `bench/90-colocated-rollback.sql`로 제거. Flyway 이력에 넣지 않는다.
- performance_schema synch 인스트루먼트는 기본 비활성 → `tools/enable-instrumentation.sql`로
  켠다. 계측 오버헤드는 모든 라운드에 동일하게 얹히므로 팔 간 비교에는 영향 없고,
  이 캠페인의 절대 레이턴시는 다른 캠페인과 비교하지 않는다.

## 8. 이 테스트로 말할 수 없는 것 (사전 선언)

- **A팔은 결합 비용의 하한이다.** 서빙 경로가 고정이라 랭킹 스캔은 여전히 `place_stats`
  인덱스를 읽는다. 진짜 결합 설계라면 랭킹 커버링 인덱스도 `places`에 있어 그 인덱스
  재작성 충돌까지 places 쪽으로 옮겨온다 — 그 몫은 이 실험에 없다.
- flush I/O·체크포인트 거동의 절대값 — 로컬 Docker 디스크라 운영 스토리지를 대표하지 않는다.
- 꼬리 지연(p95/p99) — 이 호스트에서 재현성이 증명된 적 없다.
- 실배치 스케줄(매시 30분)과 실트래픽 피크의 실제 겹침 확률·빈도 — 이건 운영 관측의 몫이다.
