## 0. 무엇을 물었나

직전 캠페인([최소 안정성 확인](2026-08-06-minimal-stability-final.md))은 부하 두 점(120·300)만 봤고
자원 지표를 **라운드 시작/종료 누계 차분**으로만 남겼다. 그래서 "앱 CPU가 병목"이라는 결론은
얻었어도 *어디서부터* 꺾이는지, 그 순간 큐·컨텍스트 스위치·GC가 무엇을 했는지는 알 수 없었다.

이 문서는 그 빈칸을 **계단 하나 안의 1초 해상도 시계열**로 채운다. 개선하지 않고, A/B도 하지
않는다. 다섯 가지 포화 징후를 재고 판정만 한다.

## 4. 판정 (사전 등록 §5 — 임계는 측정 전에 못 박았고 고치지 않았다)

| # | 규칙 | 결과 |
|---|---|---|
| **P1** | 도착 ≥1.2배인데 실제 HTTP req/s <1.05배 | **불성립** — 모든 전이에서 처리량이 도착률과 같은 배수로 늘었다 (S4→S5: 도착 ×1.20, req/s ×1.20) |

| **P4** | knee 계단에서 PSI·ctxt·JVM threads 중 **2개 이상** ≥1.3배 | **불성립 (1/3)** — PSI some ×6.65만 충족. ctxt ×0.97 · JVM threads ×1.00 |
| **P5** | DB 절대 코어 <1.0 **그리고** throttled <5% **그리고** 락 대기 0 | **S1~S3 성립 · S4·S5 불성립** — 락·스로틀 조건은 전 계단 충족하나 **절대 코어가 S4 1.091 · S5 1.383으로 1.0을 넘었다** |

### P3가 두 곳에서 걸렸으나 knee는 하나다

분석기는 `S2→S3`도 knee 지수 15.99로 잡았다. **이것은 지속되는 knee가 아니다.** S3의 대표
버킷 두 개의 p95가 `[149.9, 10.1]`로 한 자릿수 대 세 자릿수를 오갔고, 같은 계단의 **p50은
5→6 ms로 사실상 불변**이다. 즉 단일 버킷의 일시적 튐이다.

이 저장소의 지표 계약에서 **p95·p99는 "참고·인용 금지"**다([가이드 A.3](load-test-guide.md)) —
S3의 버킷 간 15배 산포가 바로 그 계약의 근거를 이 라운드에서 재현한 것이다. 그래서 knee 판정의
정본은 **1급 지표인 p50**으로 읽는다.

```
계단별 p50 (ms):   warmup 5 → S1 4 → S2 5 → S3 6 → S4 6 → S5 156
```

**S5에서만 꺾인다.** 처리량은 1.20배 느는데 p50이 26배 뛴다.

### P4가 불성립인 이유는 "안 올랐다"가 아니라 "이미 포화였다"

knee 계단에서 세 프록시 중 하나만 1.3배를 넘겼다. 원인은 나머지 둘이 **knee보다 두 계단
먼저 천장에 닿았기** 때문이다.

- **JVM live threads:** 32 → 32 → 39 → **73 → 73 → 73**. S3에서 이미 상한이다
  (`SERVER_TOMCAT_THREADS_MAX=50` + 플랫폼 스레드). 더 오를 자리가 없다.
- **context switch:** 8.1k → 13.9k → 19.2k → 24.5k → **29.8k → 29.0k**. S4에서 평탄해지고
  S5에서 오히려 미세하게 준다 — 스레드가 늘지 않으니 스위치도 늘지 않는다.
- **앱 CPU pressure(some):** 0.1 → 0.2 → 0.3 → 4.7 → 4.4 → **29.6%** (full은 26.1%).
  유일하게 knee에서 6.65배 뛴다.

사전 등록 규칙은 세 프록시가 **함께 단조 증가**할 것을 가정했는데, 실제로는 스레드 풀이 먼저
포화하고 그 다음에 CPU 대기가 폭발하는 순서였다. **규칙을 고치지 않고 불성립으로 남긴다** —
대신 무엇이 규칙의 가정을 깼는지를 기록한다.

1초 해상도로 보면 S5의 실체가 더 분명하다(부하 개시 후 초, `results/metrics/sat-step-1.app1s.tsv`):

```
t=150  1.436코어   throttled   0%   PSI  0.5%   runq  3
t=153  1.950코어   throttled  60%   PSI  7.9%   runq  5
t=157  1.923코어   throttled  70%   PSI 12.8%   runq  2
t=163  2.017코어   throttled 100%   PSI 55.7%   runq 23
t=166  2.057코어   throttled 100%   PSI 59.8%   runq 24
t=172  2.050코어   throttled 100%   PSI 50.4%   runq 15
t=180  1.920코어   throttled 100%   PSI 47.3%   runq 23
```

**S5 후반은 CFS 주기의 100%가 스로틀된다.** 앱은 쿼터에 완전히 묶여 있다.

### P5가 불성립인 이유는 임계가 좁았기 때문이다 — 비대칭은 그대로 보인다

S4·S5에서 DB 절대 코어가 1.0을 넘어 사전 등록 조건을 못 맞췄다. 그러나 **"DB가 병목인가"에
대한 답은 여전히 아니오**다. 같은 계단에서:

| | 앱 | MySQL |
|---|---:|---:|
| 절대 코어 (S5) | 1.898 / 2.0 = **94.9%** | 1.383 / 2.0 = **69.2%** |
| throttled period (S5) | **66.0%** | **1.0%** |
| CPU pressure some (S5) | **29.6%** | 2.8% |
| 디스크 읽기 · 락 대기 · tmp disk table | — | **0 · 0 · 0** (버퍼풀 hit **100.0000%**) |

**스로틀 비율이 66배 차이 난다.** DB는 일을 더 했지만 자기 쿼터 안에서 여유롭게 했고, 앱은
쿼터에 눌렸다. 사전 등록의 `<1.0 코어`는 "DB가 노는가"를 재려던 임계인데 실제로 재야 했던 것은
**쿼터 대비 압박**이었다. 임계를 사후에 바꾸지 않고, 불성립으로 적고 위 표를 함께 싣는다.

## 5. Q1이 "부분"인 이유 — 천장에 닿았지만 평탄화는 아직

P1이 불성립이라 "처리량이 평탄해졌다"고 말할 수 없다. 그런데 S5는 분명히 천장이다
(스로틀 100%·쿼터 94.9%). 이 둘이 모순이 아닌 이유는 **Artillery가 개루프(open-loop)**이기
때문이다 — 도착은 서버 상태와 무관하게 계속 들어오고, 서버가 못 따라가면 처리량이 아니라
**지연과 적체**가 먼저 늘어난다.

버킷별 요청 vs 응답이 그 순간을 잡았다:

```
rel(s)   요청   응답   차이     p50
  141   4740   4740      0      6ms
  151   5534   5531     +3      7ms
  161   5557   5437   +120    156ms     ← 처음으로 응답이 요청을 못 따라간다
  171   5117   5245   -128    284ms     ← 라운드 종료 후 밀린 것을 마저 흘려보낸다
```

라운드 전체로는 요청 58,604 = 응답 58,604으로 **하나도 잃지 않고 전부 200으로 끝났다.**
즉 S5는 **붕괴가 아니라 붕괴의 시작점**이다. 20초 창 안에서는 처리량이 아직 도착률을 따라가고,
그 대가를 p50 26배가 치렀다.

**따라서 "처리량 평탄화"는 이 라운드의 부하 범위(도착 ≤360/s) 밖에 있다.** 그 지점을 재려면
더 높은 계단이 필요한데, 이 캠페인은 계단 하나만 돌린다는 사전 등록을 지켰다.

## 6. 요청당 CPU — 천장이 산술로 설명된다

가이드 §4("CPU 사용률만 비교하면 부하량의 영향을 받으므로 요청당 CPU 시간을 함께 본다")를 따라
계단마다 **요청당 CPU**를 냈다.

| 계단 | HTTP req/s | 앱 코어 | **앱 CPU ms/요청** | DB 코어 | **DB CPU ms/요청** |
|---|---:|---:|---:|---:|---:|
| warmup | 94.8 | 0.320 | 3.38 | 0.190 | 2.00 |
| S1 | 187.8 | 0.502 | **2.67** | 0.338 | 1.80 |
| S2 | 277.4 | 0.731 | **2.64** | 0.511 | 1.84 |
| S3 | 371.4 | 1.211 | 3.26 | 0.780 | 2.10 |
| S4 | 463.9 | 1.501 | 3.24 | 1.091 | 2.35 |
| S5 | 554.5 | 1.898 | 3.42 | 1.383 | 2.49 |

부하가 5.9배 오르는 동안 요청당 앱 CPU는 **2.64 ~ 3.42 ms**에 머문다(평균 3.05 ms).
**요청이 비싸져서 무너지는 것이 아니라, 같은 가격의 요청이 쿼터를 다 쓴 것이다.**

> 산술: 2,000 ms/s ÷ 3.05 ms = **약 657 HTTP req/s** (도착으로는 약 424/s).
> 관측 최대 554.5 req/s가 그 84%이고, 그 지점의 실측 쿼터 사용률이 94.9%다.
> 두 값의 차이는 스로틀 대기가 CPU 시간으로 계상되지 않기 때문이다 — **이 추정은 상한의
> 대략적인 눈금이지 SLO가 아니다.** 단일 라운드이고 재현성을 증명하지 않았다.

S3~S5에서 요청당 CPU가 2.64 → 3.4 ms로 약 28% 오르는 것도 보인다. 스로틀·큐잉 상태에서
스케줄링·컨텍스트 스위치가 붙는 몫으로 보이지만, **프로파일이 없어 귀속을 확정하지 않는다.**

## 7. Q5(프로파일)를 측정하지 못한 이유

앱 이미지는 **JRE 형상**이라 러닝 JVM에 붙을 수단이 전부 막혀 있다.

| 경로 | 상태 |
|---|---|
| `jcmd JFR.start` | `/opt/java/openjdk/bin`에 `java`·`jfr`만 있고 **`jcmd` 없음** |
| Attach API (`com.sun.tools.attach`) | **`jdk.attach` 모듈 부재** (`jdk.jfr`은 있으나 시작 트리거가 없다) |
| HotSpot attach 소켓을 셸로 직접 | BusyBox `nc`가 **유닉스 소켓(`-U`) 미지원** |
| `-XX:StartFlightRecording` | JVM **기동 인자** → 컨테이너 재생성 필요 → 측정 대상인 "지금 워밍업된 앱"이 사라진다 |

원자료: [`results/profile/jfr-capability.txt`](../../load-test/campaigns/2026-08-06_app-saturation-diagnosis/results/profile/jfr-capability.txt).

**actuator·JVM 지표로 특정 작업의 CPU 비중을 추정해 채우지 않았다.** Q5는 미측정이다.
필요하다면 별도 캠페인에서 JFR을 켠 형상으로 기동해 재야 한다(형상이 달라지므로 이 라운드의
수치와 직접 비교하면 안 된다).

## 8. 곁다리 확인 — 플랜은 흔들리지 않았다

원인 지표를 `performance_schema` digest의 **실행당** 값으로 봤다(전역 카운터 ÷ 요청 수는
요청 믹스 변화에 오염되므로 쓰지 않는다 — 가이드 §5).

- **요청당 statements 11.68** — 직전 캠페인의 11.70(120·300 양쪽)과 사실상 동일.
- 태그 필터 문장의 **실행당 149.7행**, `tags` 조인 **부재** 확인(`b24185a` 개선이 부하에서도 유지).
- 버퍼풀 hit **100.0000%** · 디스크 읽기 **0** · `created_tmp_disk_tables` **0** · 락 대기 **0**.

즉 **S5의 붕괴 조짐은 쿼리·플랜 쪽 회귀가 아니다.**

## 9. 이 테스트로 말할 수 없는 것

- **운영 절대 용량.** 부하생성기(Artillery)가 측정 대상과 같은 macOS 호스트에서 돈다. 라운드
  동안 호스트 load average가 **2.87 → 12.60**으로 올랐다. 여기서 나온 554 req/s·657 req/s
  추정은 **이 환경의 눈금**이지 운영 용량이 아니다.
- **재현성.** 단일 라운드다. 계단 간 비교는 같은 라운드 안이라 조건이 같지만, 라운드 간 산포는
  재지 않았다. 그래서 **어떤 수치도 SLO로 승격하지 않는다.** p95·p99는 지표 계약대로
  참고값이고, S3의 버킷 간 15배 산포가 그 이유를 다시 보여줬다.
- **knee 이후.** 처리량이 실제로 평탄해지고 무너지는 지점은 도착 360/s 위에 있다 — 재지 않았다.
- **원인의 내부 분해(Q5).** 어떤 코드가 그 3.05 ms를 쓰는지는 프로파일이 없어 모른다.
- **장시간 성질.** 계단이 30초다. 누수·GC 악화는 검증 대상이 아니다.
- **계측 비용.** 초당 actuator 스크레이프 1회(앱 tomcat 스레드 1개 점유)와 MySQL 상태 질의
  1회(커넥션 1개 상주)가 측정 대상 안에서 돌았다. 최대 부하 554 req/s 대비 작지만 0은 아니다.

   하고 넘지 않았다.
2. **JFR을 켠 형상으로 별도 캠페인**을 열어 3.05 ms의 내역을 분해한다(Q5).
