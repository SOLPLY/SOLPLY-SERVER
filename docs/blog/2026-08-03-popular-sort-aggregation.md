# 인기순 정렬을 요청마다 계산하지 않기로 했다

SOLPLY는 혼자 가기 좋은 장소와 코스를 추천하는 서비스다. 장소 목록에는 최신순뿐 아니라
북마크와 리뷰를 반영한 인기순이 필요했다. 문제는 인기순이 단순한 컬럼 정렬이 아니라는 점이었다.
시간이 지나면 북마크의 영향은 줄어들어야 했고, 사용자가 무한 스크롤을 내리는 동안에는 순서가
바뀌지 않아야 했다.

이 글은 인기순 조회를 구현하면서 정한 트래픽과 서버 환경, 요청 시점 집계를 버리고 배치 사전
집계를 선택한 이유, 배치 전환 중에도 스크롤 순서를 유지한 방법, 그리고 목표 부하에서 구조를
검증한 과정만 다룬다. 태그 필터의 조인 순서와 실행계획 개선은 별도 글에서 다룬다.

## 먼저 목표를 정했다

실사용자가 없는 서비스였기 때문에 관측된 트래픽으로 서버를 산정할 수는 없었다. 대신 어느 정도의
사용자를 감당할 서비스를 만들 것인지 먼저 가정했다.

```text
DAU 200,000명 × 하루 목록 탐색 30회 ÷ 86,400초 × 피크 계수 5
≈ 피크 시간대 목록 탐색 347회/s
```

정밀한 용량 예측이 아니라 규모를 정하기 위한 가정이다. 부하 도구의 단계 구성이 쉬운
`300 arrivals/s`를 최소 검증 지점으로 정했다. 최종 시나리오에서는 한 번의 도착이 첫 페이지와
커서 페이지를 포함해 평균 1.55개의 HTTP 요청을 만들었으므로, 이는 실제로 약 467 HTTP req/s에
해당한다.

여기서 `arrivals/s`와 `HTTP req/s`를 구분해야 한다. 앞의 값은 사용자 흐름이 시작되는 속도이고,
뒤의 값은 그 흐름이 서버에 만든 실제 요청 수다. 이후의 용량 수치는 둘을 함께 표기한다.

## 고가용성보다 단순한 운영 구조를 택했다

결제나 주문처럼 잠깐의 중단이 금전적 정합성 문제로 이어지는 서비스가 아니다. 따라서 처음부터
다중 인스턴스, DB 복제, 분산 캐시를 운영하기보다 edge 프록시 뒤에 애플리케이션 한 대와 MySQL
한 대를 두는 구조로 시작했다. 이중화는 사용자와 장애 비용이 그 복잡성을 정당화할 때 도입하기로
했다.

벤치마크의 최초 자원 상한은 다음과 같았다.

| 구성 | CPU | 메모리 | 내부 예산 |
|---|---:|---:|---|
| 애플리케이션 | 2 vCPU | 2 GiB | JVM 최대 힙 1.25 GiB, Tomcat 50 threads, Hikari 10 |
| MySQL | 2 vCPU | 3 GiB | InnoDB buffer pool 2 GiB, max connections 200 |

이 값은 실사용 관측으로 도출한 정답이 아니다. 단일 서버 안에서 병목을 드러낼 수 있도록 시작점을
제한한 것이다. 앱 메모리는 2 GiB 중 1.25 GiB만 힙에 배정해 metaspace, thread stack, direct
buffer와 JVM 자체 메모리를 남겼다. DB는 3 GiB 중 2 GiB를 buffer pool에 배정해 데이터 캐시
공간과 MySQL 프로세스의 나머지 메모리를 분리했다. CPU는 앱과 DB에 각각 2 vCPU를 주고 어느
계층이 먼저 포화되는지 측정했다.

데이터는 장소 6,320개, 사용자 100,001명, 북마크 약 1,040만 건을 사용했다. 운영 데이터는
없지만, 집계 비용이 작은 샘플 데이터에 가려지지 않도록 행동 이력을 의도적으로 크게 만들었다.

## 요청마다 계산하는 비용은 데이터와 함께 증가했다

인기순이 없을 때 북마크는 존재 여부만 확인하면 됐다. 인기순을 추가하자 장소별 북마크를 세고,
작성 시각에 따라 감쇠한 값을 더한 뒤 정렬해야 했다.

이를 조회 요청 안에서 계산하면 사용자가 목록을 열 때마다 같은 원본 이력을 다시 집계한다. 서울
단위 조회 한 번에서 장소 435곳과 연결된 북마크 인덱스 엔트리 약 325만 개를 읽는 것을 확인했다.
장소나 북마크가 늘수록 요청 비용도 함께 증가하는 구조였다.

반면 인기순은 매 요청마다 새로 계산할 만큼 신선할 필요가 없었다. 다수 사용자의 누적 행동으로
만들어진 상위권은 몇 분 사이에 크게 변하지 않고, 사용자는 한 시간 전의 순위를 오류로 인식하지
않는다. 그래서 원본 이력은 주기적으로 한 번만 집계하고, 온라인 조회는 계산된 결과만 읽도록
분리했다.

```text
북마크·리뷰 원본
        │
        │ 매시 배치 집계
        ▼
   place_stats
        │
        │ 온라인 조회는 결과만 읽음
        ▼
   인기순 장소 목록
```

## 계산은 데이터가 있는 DB에서 끝냈다

배치를 애플리케이션에서 계산하는 방법도 검토했다. 하지만 어느 쪽에서 계산하더라도 원본 행은
먼저 DB가 읽어야 한다. 애플리케이션으로 가져오면 그 위에 네트워크 전송, JDBC 변환, Java 객체
생성, 힙 사용과 결과 재저장 비용이 추가된다.

점수 계산은 `GROUP BY`, `SUM`과 시간 감쇠로 표현되는 관계형 집계였다. 복잡한 모델 추론이나
외부 데이터 결합도 없었다. 따라서 `INSERT ... SELECT` 한 문장으로 DB 내부에서 집계와 저장을
끝내고 애플리케이션은 배치의 시작과 전환만 관리하게 했다.

이 선택은 DB 계산이 언제나 우월하다는 뜻이 아니다. 행별 연산이 복잡해지거나, 배치가 온라인
쿼리와 DB CPU를 두고 경쟁하거나, 여러 워커로 나눠야 할 정도로 커지면 계산 위치를 다시 검토해야
한다. 현재 규모에서는 원본을 애플리케이션으로 옮기지 않는 편이 단순하고 저렴했다.

## 파생 결과는 별도 통계 테이블에 저장했다

계산 결과를 `places`에 컬럼으로 붙이지 않고 `place_stats`라는 별도 테이블에 저장했다. 장소는
원본이고 인기점수, 북마크 수, 리뷰 통계는 언제든 원본 행동에서 다시 만들 수 있는 파생 데이터다.
정확도와 갱신 주기가 다른 값을 원본과 분리하면 배치를 실패 후 다시 실행하거나 새 계산식을
적용하기도 쉬워진다.

Redis sorted set도 후보였지만 선택하지 않았다. 시간 감쇠 점수는 시간이 지나면 저장된 값 자체가
낡기 때문에 원본 DB에서의 재계산은 사라지지 않는다. Redis를 추가하면 DB에서 계산한 결과를 다시
캐시에 복제하고 무효화하는 계층이 생긴다. 목표 부하에서 DB 정렬이나 조회가 병목이라는 증거가
없는 상태에서는 운영 복잡도를 늘릴 이유가 없었다.

## 인기와 평판의 시간 특성을 분리했다

최종 점수는 북마크와 리뷰를 서로 다르게 다룬다.

```text
인기점수 = 북마크 가중치 × ln(1 + Σ 북마크 시간 감쇠)
         + 리뷰 가중치 × (베이지안 조정평점 - 전체 평균평점)
```

북마크는 최근 관심을 나타내므로 시간이 지나면 영향이 줄어든다. 반면 리뷰는 장소에 대한 누적된
평가다. 리뷰까지 감쇠시키면 소수의 최근 리뷰가 다수의 과거 평가를 지나치게 덮을 수 있어 시간
감쇠를 적용하지 않았다. 리뷰 수가 적은 장소의 극단적인 평점이 상위권을 차지하지 않도록 실제
구현에서는 베이지안 평균을 사용했다. 북마크 합에는 로그를 적용해 행동 수가 많은 장소의 점수가
무한히 선형 증가하지 않게 하고, 범위가 제한된 리뷰 축이 완전히 묻히지 않도록 두 축의 크기를
맞췄다.

핵심은 정확한 상수보다 각 신호의 의미에 맞는 시간 특성을 정의한 것이다. 계산식이 바뀌어도
`place_stats`는 원본에서 다시 생성할 수 있으므로 온라인 조회 계약은 변하지 않는다.

## 증분 갱신 대신 멱등한 전량 배치를 택했다

북마크가 추가될 때마다 통계를 `+1` 하는 증분 방식은 숫자를 더 빨리 반영할 수 있다. 대신 이벤트
누락, 중복 처리, 배치와 증분 갱신의 경합, 음수 방지와 재처리 정책이 필요하다.

즉시 반영이 꼭 필요한 것은 사용자가 방금 누른 북마크의 체크 상태다. 이것은 원본 북마크에서 바로
보여줄 수 있다. 목록에 표시되는 누적 수와 순위는 한 시간 이내 지연을 허용했다. 그래서 통계의
쓰기 경로를 매시 전량 배치 하나로 통일했다.

전량 배치는 같은 기준 시각과 원본으로 여러 번 실행해도 결과가 같고, 중간에 실패하면 다시
실행하면 된다. 북마크의 90일 반감기만 보면 한 시간마다 계산할 필요는 없지만, 신규 장소와 관리자
비활성화가 목록에 반영되는 지연을 한 시간 안으로 제한하기 위해 매시 실행한다.

배치 트랜잭션은 `READ COMMITTED`에서 실행하고 집계 대상에 기준 시각 상한을 둔다. 기본
`REPEATABLE READ`에서 집계 갱신을 실행했을 때 대량의 next-key lock이 발생했던 문제를 피하면서,
한 회차가 어떤 원본 범위를 계산했는지도 명확하게 만들었다.

## 배치 전환 중인 무한 스크롤은 버전으로 고정했다

배치가 기존 통계 행을 제자리에서 갱신하면 사용자가 첫 페이지를 본 뒤 다음 페이지를 요청하기
전에 순서가 달라질 수 있다. 이전 점수로 발급한 커서를 새로운 순서에 적용하면 중복이나 누락이
생긴다.

이를 막기 위해 배치 한 회차의 결과를 하나의 불변 버전으로 저장했다.

```text
13:30             14:30             15:30
v1 생성   ──────> v2 생성   ──────> v3 생성 후 v1 삭제
   └─ v1에서 시작한 스크롤은 v2가 생겨도 계속 v1을 조회
```

`place_stats`의 키에는 장소와 버전이 함께 들어간다. 배치는 새 버전의 행을 모두 작성한 뒤 현재
버전 포인터를 전환한다. 커서는 자신이 발급된 버전을 포함하고 이후 페이지도 같은 버전만 조회한다.
현재와 직전 두 버전을 보관하며, 그보다 오래 방치된 커서는 새 좌표계에 억지로 연결하지 않고 첫
페이지부터 다시 시작하게 한다.

조회 인덱스는 버전과 지역 조건 뒤에 점수와 장소 ID를 둬 keyset pagination의 정렬을 지원한다.
여러 동네를 한꺼번에 조회하는 시 단위 목록에는 작은 filesort가 남지만 대상이 수백에서 약
1,800행이어서 수용했다. 이를 없애기 위한 비정규화는 실측 문제가 생길 때로 미뤘다.

## 정확성, 실행계획, 부하를 서로 다른 질문으로 검증했다

먼저 통합 테스트로 다음 계약을 확인했다.

- 새 버전 작성이 실패하면 현재 버전이 바뀌지 않는다.
- 새 버전을 완성한 뒤에만 현재 버전 포인터가 전환된다.
- 전환 전에 발급한 커서는 전환 후에도 직전 버전으로 다음 페이지를 조회한다.
- 보관 범위를 벗어난 커서는 명시적으로 만료된다.
- 같은 기준 시각으로 배치를 다시 실행해도 결과가 달라지지 않는다.

실행계획에서는 단일 동네와 시 단위, 첫 페이지와 커서 페이지가 의도한 통계 인덱스를 사용하는지,
실제로 몇 행을 읽고 어디에서 filesort가 발생하는지 확인했다. 실행계획의 세부적인 태그 조인 문제와
개선 과정은 이 글의 범위에서 제외한다.

마지막으로 최종 코드와 북마크 약 1,040만 건 데이터에서 짧은 최소 안정성 부하 테스트를 했다.

| 조건 | 결과 |
|---|---|
| 앱 2 vCPU, 300 arrivals/s | 요청은 모두 성공했지만 CPU 스로틀과 꼬리 지연이 발생 |
| 앱 4 vCPU, 300 arrivals/s | 약 467 HTTP req/s, 35,332건 전부 200, 실패 0 |
| 4 vCPU 응답시간 | p50 6ms, p95 13.9ms, p99 59.7ms |
| 4 vCPU 앱 CPU | 평균 1.198 core, 스로틀 주기 0.8% |
| MySQL | 평균 0.766 core, 락 대기·디스크 임시 테이블·버퍼풀 디스크 읽기 0 |

2 vCPU에서 앱 CPU 상한만 4 vCPU로 올리자 스로틀 주기는 18.2%에서 0.8%로, p99는
391.6ms에서 59.7ms로 줄었다. DB 구조나 데이터는 바꾸지 않았다. 목표 부하의 병목은 인기순
집계 구조나 DB가 아니라 애플리케이션 CPU 예산에 가까웠다.

이 결과는 약 1분의 짧은 로컬 테스트이므로 장시간 운영 SLO를 보장하지 않는다. 또한 실행 중인
컨테이너의 CPU 쿼터만 4 vCPU로 변경했기 때문에 JVM을 처음부터 4 vCPU 환경으로 기동한 실험도
아니다. 다만 목표 부하를 오류 없이 처리했고, DB가 포화되지 않았으며, 앱 CPU 상한을 풀었을 때
꼬리 지연이 함께 줄었다는 방향은 확인했다.

## 측정 결과 캐시는 도입하지 않았다

목표 부하에서 MySQL은 여유가 있었고 실행계획도 부하에 따라 흔들리지 않았다. 따라서
`place_stats_meta`나 인기순 첫 페이지를 캐시해 얻을 이익보다 무효화, 정합성, 장애 지점과 운영
복잡도가 더 컸다. Redis도 실제 사용처가 없어 실행 환경에서 제거했다.

캐시는 트래픽이 더 커져 DB CPU, 커넥션 대기나 반복 조회 비용이 병목으로 관측될 때 다시 검토한다.
측정 없이 캐시를 추가하지 않은 것도 이 설계의 결론이다.

## 다음 질문은 온라인 조회가 아니라 배치의 성장 비용이다

온라인 조회는 목표 부하를 처리했지만, 배치는 여전히 원본 행동 이력을 전량 스캔한다. 시간 감쇠를
적용한 북마크는 충분히 오래되면 인기점수에 거의 기여하지 않는다. 그런데도 데이터가 계속 쌓이면
기여도가 사실상 0인 행까지 매시간 읽게 된다.

다음 작업에서는 오래된 행동 데이터의 비율을 단계적으로 늘려 배치 소요시간과 실제 스캔 행 수가
어떻게 증가하는지 측정한다. 그 다음 인기점수 집계에만 시간 컷오프를 적용해 최근 범위만 읽는
방식과 비교한다. 누적 북마크 수는 전 기간 집계가 필요하므로 점수와 카운트의 스캔을 분리할
실익도 함께 검증한다.

성공 기준은 단순히 배치가 빨라지는 것이 아니다. 컷오프 전후의 점수 오차 상한을 계산하고,
실제 데이터에서 top-K 순위가 같은지 확인해야 한다. 정확성을 지키면서 데이터 증가에 따른 비용만
제한할 수 있을 때 그 변경을 채택한다.
