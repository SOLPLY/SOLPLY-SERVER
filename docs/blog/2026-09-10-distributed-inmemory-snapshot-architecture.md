# MySQL 발행물을 공유하는 분산 인메모리 스냅샷 구조

작성일: 2026-09-10 · 구현 기준: 2026-09-12

솔플리의 장소 목록은 각 API 서버의 메모리에서 정렬·필터·페이지 탐색을 수행한다.
서버들은 MySQL에 저장된 완성된 발행물을 복원해 같은 조회 데이터와 커서 버전을 사용한다.
MySQL은 원본뿐 아니라 재생성 요청, 완성된 데이터, 현재 발행 포인터를 보관한다.

이 글은 현재 코드의 생성·발행·복원 경로를 설명한다. 여러 서버가 실행될 때도 사용할 수
있는 구조이며, 별도 빌더 서버나 Redis 배포 저장소를 필수 인프라로 전제하지 않는다.
로컬 배열과 관리자 부분 수정의 비용은
[메모리 조회 모델과 Heap·GC 설계](2026-09-09-admin-rebuild-tradeoff.md)에 정리한다.

## 1. 요청 처리와 데이터 갱신의 역할

```text
사용자 앱
  → Nginx
  → SOLPLY API 서버
      ├── 인증: Access JWT 검증
      ├── MySQL: 동네·태그 조건 검증, 사용자별 북마크 여부
      ├── 로컬 메모리: current Snapshot으로 장소 페이지 탐색
      └── 일반 첫 페이지 또는 커서 불일치
            → MySQL 현재 발행 확인
            → 로컬이 뒤처졌으면 공유 적재를 기다려 페이지 재구성
  ← 목록·이미지 URL·커서

사용자 앱
  → CloudFront → S3 이미지 저장소

SOLPLY 서버의 스케줄 작업
  → 통계 집계 + 재생성 요청 기록       [MySQL]
  → 요청을 모아 스냅샷 생성·발행       [MySQL]
  → 각 서버가 발행물을 자기 힙에 설치  [서버별 메모리]
```

목록의 정렬·필터·페이지 탐색은 메모리에서 처리하지만, 요청 전체가 DB 없이 실행되는 것은
아니다. 이미지 URL은 서버가 조합하고 실제 이미지는 앱이 요청한다. 소셜 로그인 제공자나
AI API는 이 목록 조회·통계 집계·스냅샷 발행 경로에 참여하지 않는다.

스냅샷 발행과 복원에는 Redis가 필요하지 않다. 서버 간 공유 기준과 실패 후 재시도 근거가
MySQL에 있기 때문이다. 이는 서버의 다른 기능에서 Redis를 사용하는지와 별개의 문제다.

## 2. MySQL에는 무엇을 저장하는가

| 테이블 | 역할 |
|---|---|
| 장소·동네·태그·북마크·리뷰 원본 | 도메인 데이터의 기준 |
| place_stats | 목록에서 사용하는 집계 결과와 인기 점수 |
| bookmark_count_events | 아직 소비하지 않은 북마크 증감 이벤트 |
| place_list_rebuild_requests | 재생성 요청 번호와 처리 완료 번호를 보관하는 한 행 |
| place_list_publications | 완성된 payload와 발행·커서 버전 정보 |
| place_list_publication_pointer | 현재 발행 행을 가리키는 한 행 |
| shedlock | 동일 스케줄 작업의 인스턴스 간 실행 조율 |

발행 데이터는 다음 정보를 가진다.

```text
place_list_publications
  id                발행 식별자, INSERT의 AUTO_INCREMENT로 발급
  cursor_version    목록 커서가 참조하는 버전
  format_version    payload 해석 규칙
  entry_count       장소 엔트리 개수
  payload_bytes     압축한 데이터 크기
  payload_sha256    저장 바이트의 무결성 확인 값
  payload           gzip(JSON), LONGBLOB
  published_at      발행 시각
```

JSON에는 장소의 정렬·필터·커서 판정에 필요한 값과 장소 표시값·태그 맵을 넣는다.
Java 객체의 내부 메모리 구조를 저장하지 않는다. 각 서버는 저장된 값을 객체로 복원하고
같은 정렬 규칙으로 배열을 구성한다. 호환되는 형식과 해석 규칙을 사용하는 서버들은 같은
발행물에서 같은 순서를 얻는다.

정렬 기준 변경은 JSON 필드 이름이 같아도 의미가 바뀐 것이다. 형식 호환성에는 필드의
존재뿐 아니라 수치 단위, 필터와 정렬·동점 처리 규칙도 포함된다.

### 발행 ID와 커서 버전은 구분한다

발행 ID는 각 서버가 새 데이터를 받아야 하는지 판단하는 값이다. 커서 버전은 요청의
정렬·필터 기준을 식별한다. 구조 발행은 자신의 발행 ID를 커서 버전으로 사용하고,
표시값만 바뀐 발행은 앞선 커서 버전을 이어받는다.

```text
발행 ID 100 / 커서 버전 100 / 장소 이름 A
  → 표시값 수정
발행 ID 101 / 커서 버전 100 / 장소 이름 B
  → 정렬·필터 기준 갱신
발행 ID 102 / 커서 버전 102
```

따라서 이름이나 썸네일 수정도 다른 서버로 전달하면서 커서를 유지할 수 있다.
별도의 번호 발급 전용 테이블을 쓰지 않으며, 현재 발행물은 명시 포인터로 선택한다.
AUTO_INCREMENT의 크기만으로 커밋·채택 순서를 판단하지 않는다.

## 3. 통계와 재생성 요청을 함께 커밋한다

북마크 원본 변경과 아웃박스 이벤트 생성은 하나의 트랜잭션이다. 등록은 +1, 해제는 -1을
기록한다. 델타 배치는 이벤트들을 이번 회차 UUID로 표시하고 DB에서 장소별로 합산한다.

```text
북마크 델타 트랜잭션
  → 이번 회차의 이벤트에 UUID 표시
  → 표시된 PLACE 이벤트를 장소별 SUM(delta)로 집계
  → place_stats에 반영
  → 같은 UUID의 이벤트 삭제
  → 재생성 요청 번호 증가
  → 함께 커밋
```

UUID는 집계 대상과 삭제 대상을 일치시키는 표식이다. 해당 이벤트 행의 잠금은 커밋·롤백까지
유지한다. JDBC 반영을 1,000장소씩 나눠 실행해도 중간에 커밋하지 않는다. 스냅샷 생성까지
이 트랜잭션을 열어 두는 것은 아니다. 빈 소비 회차는 재생성 요청도 남기지 않는다.

리뷰는 원본을 전량 집계해 리뷰 수·평균 평점을 갱신하고 같은 트랜잭션에서 요청을 남긴다.
리뷰 아웃박스는 두지 않는다. 인기 점수와 안전망 집계도 자신의 통계 쓰기와 요청을 함께
커밋한다.

| 작업 | 기본 실행 시각 | 실행 조율 |
|---|---|---|
| 북마크 델타 | 매시 15분 | place-stats-bookmark-delta |
| 리뷰 수·평균 평점 | 매시 30분 | place-stats-count |
| 인기 점수 | 매일 01:00 | place-stats-score |
| 카운트 안전망 | 매일 01:45 | place-stats-count-safety |

통계 회차는 기본 최초 실행 포함 3회, 실패 후 5초 대기로 재시도한다. 재시도는 실패한
트랜잭션이 끝난 뒤 새 시도로 실행한다. 실패 횟수를 소진하면 다음 정기 실행까지 작업이 남는다.
잠금 유지 비용과 사용자 쓰기 지연이 충분히 작다는 부하 측정 결론은 아직 없다.

## 4. 요청을 모아 완성된 발행물을 만든다

생성 스케줄러는 기본 5초 간격으로 실행한다. 공유 ShedLock 이름은
`place-list-snapshot-publish`이다. 요청 번호와 처리 완료 번호가 같으면 원본 전량 조회와
payload 생성을 하지 않는다.

```text
미처리 요청 확인
  → 처리할 요청 번호 R 확보
  → 후보를 만들기 전 현재 발행 ID P 확보
  → 원본·place_stats·표시값을 읽어 후보 구성
  → JSON 직렬화·gzip 압축
  → 발행 트랜잭션
      ├── payload INSERT
      ├── 커서 버전 확정
      ├── 현재 포인터가 P일 때만 새 발행 ID로 교체
      └── R까지 요청 처리 완료
  → 함께 커밋
```

원본 조회와 인코딩 동안 발행 포인터의 DB 행 잠금을 계속 잡지는 않는다. 대신 발행할 때
조건부 갱신으로 기준이 그대로인지 판정한다. 다른 발행이 먼저 끝났으면 후보 INSERT까지
롤백하고 다시 최신 기준에서 처리한다. ShedLock의 실행 조율과 별도로 이 조건이 오래된
후보의 덮어쓰기를 막는다.

발행과 요청 완료는 `REQUIRES_NEW`, `READ_COMMITTED`인 하나의 트랜잭션에서 수행한다.
관리자 afterCommit 경로에서도 완료된 원본 트랜잭션에 다시 붙지 않도록 새 트랜잭션을 연다.
생성 중 요청 R+1이 커밋되면 R까지만 완료 처리하므로 다음 회차가 남은 변경을 읽는다.

통계의 afterCommit 알림은 사용하지 않는다. 원본과 함께 저장된 요청을 생성 스케줄러가
확인하므로 서버가 커밋 직후 종료돼도 재생성 근거는 DB에 남는다.

## 5. 관리자 수정도 공유 발행물을 거친다

관리자 쓰기 트랜잭션은 원본을 변경하고 재생성 요청을 기록한다. 요청 저장 전에 JPA 변경을
flush하며, 요청 기록은 열린 트랜잭션에 참여해야 한다. 관리자 afterCommit 훅은 변경된 ID를
다시 읽어 부분 수정 후보를 만들고 빠르게 발행하는 경로다.

```text
원본 변경 + 재생성 요청 커밋
  → 최신 공유 발행물을 기준으로 부분 수정 후보 계산
  → 발행 트랜잭션 성공
  → 공통 설치 경로로 로컬 반영
```

자신의 요청 바로 전까지 처리가 끝났고 이후 요청이 없을 때만 관리자 훅이 요청 완료를
표시한다. 앞선 통계 요청이나 다른 관리자 요청이 남아 있으면 부분 수정만으로 완료 처리하지
않는다. 생성 스케줄러가 미처리 요청을 모아 원본 전체에서 후보를 만든다.

부분 수정 후보도 전체 payload로 저장한다. 원본 조회와 배열 수정 범위를 줄이는 것과
저장·다운로드 바이트 수를 줄이는 것은 구분해야 한다. 발행 충돌·실패 전에는 로컬에 후보를
공개하지 않으며, 발행 성공 후 설치 실패는 각 서버의 설치 재시도로 복구한다.

## 6. 각 서버는 발행물을 복원한다

모든 인스턴스에는 기본 5초 간격의 설치 스케줄러가 있다. 자신이 발행한 서버도 같은
복원 경로를 쓴다. 이 작업에 공용 ShedLock을 걸면 다른 인스턴스의 메모리가 갱신되지
않으므로, 설치는 각 서버가 독립적으로 수행한다.

설치 폴과 사용자 요청은 `SnapshotLoadCoordinator`의 진행 중인 Future를 공유한다.
`AtomicReference`의 CAS로 적재 시작자를 한 명만 정하고, 나머지는 같은 결과를 기다린다.
다운로드하는 동안 로컬 잠금을 계속 잡는 방식은 아니다. 실제 적재는 전용 스레드 한 개와
길이 1인 큐에서 실행하며, 폴은 적재가 끝날 때까지 스케줄러 스레드를 붙잡지 않는다.
관리자 훅과 기동 복원은 직접 설치한다. 특히 관리자 훅이 로컬 잠금을 잡은 채 다른 적재
스레드를 기다리면 교착될 수 있으므로 이 Future를 공유하지 않는다.

```text
현재 발행 ID 조회
  ├── 이미 설치한 ID → 종료, payload는 읽지 않음
  └── 새 ID
        → 포인터와 payload를 JOIN 한 문장으로 다운로드
        → 체크섬·형식·필수 데이터 검증
        → 압축 해제·객체·정렬 배열 구성
        → 로컬 갱신 잠금 안에서 발행 ID 재확인
        → 표시 홀더 갱신, current 채택, 설치 ID 기록
```

다운로드와 디코딩이 끝나는 사이 더 최신 발행물이 설치됐을 수 있다. 로컬 잠금 안에서
설치 ID를 비교해 늦게 도착한 데이터가 current와 표시값을 되돌리지 못하게 한다.
표시값과 current는 개별 참조이며 모든 독자에게 한 번에 바뀌는 하나의 객체는 아니다.
조회는 자신이 확보한 Snapshot으로 정렬 기준을 유지하고 표시값은 홀더에서 읽는다.

지원하지 않는 형식, 손상된 바이트, 필수 데이터 오류나 다운로드 실패가 있으면 기존
설치 상태를 유지하고 다음 폴에서 다시 시도한다. 설치할 수 있는 데이터를 갖추기 전에
설치 ID부터 올리지 않는다.

현재 발행물을 내려받는 경로는 포인터와 payload를 한 SQL 문장으로 읽는다. 발행 후
이전 행을 정리하는 동안 둘이 어긋나는 조회를 피하기 위해서다. 포인터의 외래 키는 현재
발행 행의 삭제를 막는다. 정리 실패는 이미 커밋한 발행을 실패로 바꾸지 않으며, 이후 정리
기회에 다시 시도한다. 이전 발행 행이 남아 있어도 과거 커서 조회용으로 사용하지 않는다.

## 7. 신규 인스턴스와 커서의 수명

신규 서버는 마지막 발행물의 내용과 커서 버전을 그대로 복원한다. 원본에서 별도의 값을
재집계하거나 복원할 때마다 새 버전을 발급하지 않는다. 복원한 발행물이 호환되고 같다면
인스턴스 교체 자체로 진행 중인 커서가 달라지지 않는다.

```text
기동
  ├── 발행물 있음
  │     → 동일 내용·버전 복원
  │     → 현재 발행 상태 재확인
  │     → 준비 완료
  └── 발행물 없음
        → 발행자와 같은 ShedLock으로 최초 생성 시도
        → 포인터가 아직 비어 있을 때만 최초 발행 커밋
        → 자신 또는 다른 서버가 발행한 결과 복원
        → 준비 완료
```

최초 복원을 마치지 못하면 빈 목록 모델로 요청을 받지 않도록 기동이 실패한다.
최초 발행 대기의 기본 제한은 60초이며, 이는 모든 DB 호출과 후보 계산을 강제로 중단하는
기동 전체 시간 상한은 아니다. 최초 발행 직후에도 설치 전 한 폴 간격을 기다릴 수 있다.

같은 JVM에 두 노드를 구성한 시험에서 후보 계산이 중복된 회차가 관찰됐다. 원인은
규명되지 않았으며 ShedLock 자체의 실패로 단정하지 않는다. 해당 시험에서도 커밋된 최초
발행 한 건과 두 노드의 동일 복원은 확인했다. 최종 발행 선택은 포인터 조건부 갱신으로 보호한다.

서버별 폴링과 복원 시점은 같지 않다. 따라서 로컬 버전 불일치만으로 커서를 만료시키지
않고, 공유 현재 버전과 비교해 인스턴스의 적재 지연을 구분한다.

```text
일반 첫 페이지 요청
  → 기존 요청 검증과 응답 구성
  → MySQL 현재 발행 ID 확인 (payload 제외)
      ├── 이미 관측한 발행 이상을 설치함 → 응답
      └── 로컬이 뒤처짐 → 공유 적재를 시작하거나 합류 → 응답 다시 구성

커서가 있는 요청
  ├── 로컬 커서 버전과 일치 → 기존 조회, 추가 발행 조회 없음
  └── 불일치 → MySQL 현재 커서 버전 확인
        ├── 요청 커서와 다름 → PLACE-006, 첫 페이지 재조회
        └── 요청 커서와 같고 로컬이 뒤처짐
              → 같은 적재 Future에 합류 → 동일 커서로 조회 재개
```

북마크 검색은 별도의 DB 조회 경로를 유지하며 발행 확인을 추가하지 않는다. 첫 페이지는
표시값 변경도 따라잡아야 하므로 커서 버전이 아닌 발행 ID를 비교한다. 처음 관측한 발행을
기준으로 삼고 이후 발행을 계속 추적하지 않는다. 이 경로에서는 첫 응답 구성이 낡았으면
재구성하므로 동네·북마크 등의 DB 조회가 반복될 수 있다.

적재 대기의 기본 설정은 `solply.place-list-snapshot.request-wait-timeout-ms=2000`이다.
서블릿 비동기 응답을 사용하며, 적재를 기다리는 동안 요청 스레드를 점유하지 않는다. 기다림 실패나
제한 시간 초과는 `PLACE-007`(503)로 반환한다. 클라이언트는 현재 목록을 유지하고 같은
커서로 재시도해야 한다. 첫 페이지 요청도 같은 조건에서 503을 받는다. 한 요청의 시간
초과는 공유 적재를 취소하지 않으므로 다른 요청과 후속 폴은 계속 그 결과를 이용한다.

대기 예산에는 적재 시간뿐 아니라 응답 재개용 실행기의 큐에서 기다리는 시간도 포함한다.
시간 초과 응답은 그 큐를 거치지 않고 완료하므로 큐 정체가 503 통보까지 막지 않는다.
이미 시간 초과된 요청이 큐에서 늦게 실행되면 DB 재조회를 건너뛴다. DB 재조회는 적재·타이머
스레드에서 수행하지 않으며, 이미 시작된 재조회는 대기 제한으로 강제 중단하지 않는다.

이것은 현재 공유 발행물의 적재 지연을 완화하는 경로다. 과거 발행물을 복원하거나 이미
교체된 커서를 계속 살려 두지는 않는다. 대기 중 구조 발행이 다시 바뀌면 커서가 실제로
만료될 수 있다. 초기 동기 DB 조회와 네트워크 전달까지 포함한 전체 HTTP 지연을 2초로
보장하는 설정도 아니다.

## 8. 실패 복구와 자원 비용의 범위

| 실패 지점 | 남는 상태와 후속 처리 |
|---|---|
| 통계 트랜잭션 실패 | 통계·아웃박스 소비·재생성 요청 함께 롤백, 통계 재시도 |
| 원본 읽기·압축 실패 | 현재 발행 유지, 요청은 미처리로 남음 |
| 발행 CAS 충돌 또는 발행 트랜잭션 실패 | 새 payload·포인터·완료 표시 함께 롤백 |
| 관리자 커밋 뒤 훅 실행 전 종료 | 원본과 요청은 남음, 생성 스케줄러가 처리 |
| 발행 후 서버의 다운로드·설치 실패 | DB 발행은 유지, 각 서버가 설치 재시도 |
| 이전 발행물 정리 실패 | 현재 발행 유지, 이전 행은 후속 정리 대상 |

통계 실행과 스냅샷 생성은 기본 스케줄러 스레드를 공유하므로 긴 작업이 다른 작업을
늦출 수 있다. 설치 폴은 전용 적재 스레드에 작업을 맡기고 반환한다. 스케줄러 풀 자체를
확대하지는 않는다. 기본 5초 폴은 반영 지연의 보장 상한이 아니며 원본 조회·압축·DB 쓰기와
적재 시간, 앞 작업의 대기가 더해진다.

MySQL에 payload를 저장하면 발행 내용·포인터·요청 완료를 로컬 트랜잭션으로 묶을 수 있다.
그 대가로 DB가 전체 payload 쓰기와 각 서버의 다운로드를 처리한다. 표시값 수정도 전체
payload를 저장하므로 요청 빈도와 데이터 크기를 함께 봐야 한다.

합성 1만 엔트리의 JSON은 3,548,602바이트, gzip 저장 바이트는 422,779바이트였다.
이는 고정 픽스처의 크기이며 실제 데이터의 압축비나 운영 처리량을 보장하지 않는다.
운영 판단에는 실제 payload 크기와 DB의 전송 제한, 반복 발행 비용, 여러 서버의 다운로드,
복원 중 힙 최대 점유와 사용자 요청 지연을 함께 측정해야 한다.

이 구조는 공유 발행물을 복원해 같은 상태로 수렴하게 한다. 모든 서버의 메모리를 동시에
바꾸거나, 현재 버전이 교체돼도 과거 커서를 계속 사용할 수 있게 하는 계약은 아니다.

기능 검증은 [적재 대기 설계](../design/2026-09-12-snapshot-request-catch-up.md)와 [605개 테스트 결과](../verification/2026-09-12-snapshot-request-catch-up.md)를 참고한다. 삭제된 장소는 정렬 엔트리뿐 아니라 발행 payload의 표시값에서도 제거하며, 복원한 홀더까지 그 결과를 검증한다.
