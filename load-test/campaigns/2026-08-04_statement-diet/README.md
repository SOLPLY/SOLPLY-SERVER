# 2026-08-04_statement-diet — 요청당 SQL 18→12 검증 (C3+C1+C2)

> **사전 등록 문서다** (2026-08-04, 측정 전 고정). 코드 진단(트랜잭션 제어 문장 10개의
> 발생 원인)에서 도출된 변경 묶음의 효과를 검증한다. 판정 지표는 응답시간이 아니라
> **digest 문장 수**다 — 효과 크기가 2배 미만이므로 가이드 A.1 밴드에 따라 원인 지표로만
> 판정하고 처리량·지연은 주장하지 않는다.

## 1. 문제

인기순 목록 요청 1건이 SQL 18문장을 만든다. 그중 10개(56%)가 데이터를 한 행도 읽지 않는
트랜잭션 제어 문장(SET autocommit ×4, SET SESSION TRANSACTION ×4, COMMIT ×2)이고,
장소+태그 로딩의 DISTINCT는 지울 행이 구조적으로 없는데 요청당 임시테이블 1개를 만든다.
단, 서버 대기시간 기준 제어 문장의 비중은 15%(917µs/6,125µs)다 — 이 개선의 이득은
DB CPU 대세가 아니라 왕복 수·커넥션 점유 단축이다 (과대평가 금지, 진단 §3).

## 2. 원인 (가설 아님 — 코드·바이트코드로 확정, 2026-08-04 진단)

- **트랜잭션이 요청당 2개**: A = 인증 유저 로드가 Spring Data `SimpleJpaRepository`의
  클래스 레벨 `@Transactional(readOnly=true)` 기본값으로 여는 것(서비스 애노테이션 아님),
  B = `PlaceService` 클래스 `@Transactional(readOnly=true)`. 트랜잭션당 제어 5문장
  (Hibernate autocommit 토글 2 + Spring readOnly 전파·원복 2 + COMMIT 1).
- **towns 2문장**: 존재 검증(COUNT)과 leaf 확장(parent_id)이 별도 왕복. 정보는 중복이
  아니나(leaf 자기 자신 규칙) 한 문장으로 표현 가능.
- **DISTINCT**: fetch join 행이 (place, place_tag) 조합으로 이미 유일 — digest
  `SUM_CREATED_TMP_TABLES` ≈ 요청 수로 확인된 순수 낭비.

## 3. 기술적 선택

| | 변경 | 문장 효과 |
|---|---|---|
| C3 | `selectDistinct`→`select` + `toMap` 병합 함수 | 0 (임시테이블 1→0) |
| C1 | 인증 유저 조회를 무트랜잭션으로 (`propagation=SUPPORTS` 전용 메서드, `@Where` 유지) | **-5** (제어 10→5) |
| C2 | towns 존재 검증+확장 1문장 통합 (active 비대칭 보존) | **-1** |

기각/보류: C5(전역 autocommit — 무트랜잭션 쓰기 함정), C6(유저 캐시 — C1 후 한계효용
1문장), C7(meta 단독 캐시 — 세대 어긋남, 단 ②b 페이지 캐시 설계 안에서는 해소됨),
C4(`readOnlyPropagatesToServer=false` — InnoDB read-only 최적화와 교환이라 **별도 측정**).
`readOnly=true` 자체는 유지 — Place 엔티티 페이지가 영속성 컨텍스트에 오르므로
스냅샷·dirty checking 절감이 실재한다.

## 4. 검증할 주장

**같은 응답을 더 적은 DB 작업으로 만든다.** 요청당 statements 18.16 → **12.16 (정확히 -6)**,
임시테이블 1 → 0. 응답 의미(JSON)·보안 의미(탈퇴 유저 거부, admin 차단)는 불변.

## 6. 프로토콜

- **A(기준선)는 재측정하지 않는다** — `2026-08-04_saturation-amplification/results/digests/amp300-r2`
  를 정본으로 재사용한다 (동일 시나리오·동일 이미지 계열·플래그 off, statements 18.16 실측).
- **B(패치)**: C3+C1+C2 적용 빌드로 `place-list-popular-readonly-300.yml`(도착 300/s, 비포화
  확인 완료 지점) **2라운드**. 판정 지표(문장 수)는 JIT와 무관하게 라운드 간 ±0.3% 재현되므로
  두 라운드 모두 판정에 쓰고, CPU·p50은 r1을 워밍업으로 참고 제외.
- 계측: digest TRUNCATE/덤프(진단 캠페인 tools 재사용) + metrics-snapshot + sampler +
  cgroup cpu.stat. 형상: FORCE INDEX 토글 off(기본값) 유지.
- 정합성 게이트(ⓓ)는 부하 전에 A 이미지 → B 이미지 순차로 같은 요청 세트를 쏴서 diff.
