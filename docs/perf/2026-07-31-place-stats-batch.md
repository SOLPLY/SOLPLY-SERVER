# place_stats 배치 — 기각 근거 실측 (Task 8)

> 캠페인: [`load-test/campaigns/2026-07-31_place-stats-batch/`](../../load-test/campaigns/2026-07-31_place-stats-batch/)
> 측정일: 2026-07-31 / 설계: [복합 점수 설계](../superpowers/specs/2026-07-30-place-popular-score-design.md)
>
> **이 측정은 부하 테스트가 아니다.** Artillery를 쓰지 않았다 — 근거는 §1.

## 0. 문제

인기순 복합 점수는 `place_stats` 별도 테이블 + 하루 1회 전량 재계산으로 구현됐다.
이 구조는 세 대안을 기각하고 나온 것인데, **기각 근거 중 실측으로 뒷받침된 것이 사실상 없었다.**

| 기각한 대안 | 당시 근거 | 상태 |
|---|---|---|
| 실시간 집계 (캐시 미스마다 COUNT) | v0 부하 테스트 (성공률 1.6%) | 결론은 있으나 **원인 지표가 없었다** |
| `places`에 비정규화 카운터 | 설계 §2.3 — 축이 스키마에 샌다 / 2급 데이터 / 정확도 요구 분리 | **전부 설계 원칙. 성능·락 근거는 없었다** |
| 증분 갱신 | 장애 복구 시 drift (§2.5) | 논증. 이번 범위 아님 |

채택안의 **비용**도 환경이 셋으로 갈려 있었다 — 배치 6.0~6.2초는 버퍼풀 1G에 시드 미보존,
FK 부모 S락 320은 마이그레이션 기본 데이터만 있던 DB, 그리고 `place_reviews` 락은
**한 번도 측정된 적이 없었다**(그 DB에 리뷰가 0건이었다).

복합 점수는 신규 기능이라 비교할 before가 없다. 그래서 이 문서의 목적은 개선 증명이 아니라
**기각한 대안이 왜 나쁜지, 채택안의 비용이 무엇인지 숫자로 남기는 것**이다.

## 1. 왜 부하 테스트가 아닌가

[가이드 §2](load-test-guide.md)로 판정했다. 7개 항목 중 Artillery 부하가 필요한 것은 0개였다.

| # | 항목 | 쓴 방법 |
|---|---|---|
| 1 | 배치 소요·멱등성 | 단발 실행 4회 + 지문 비교 |
| 2 | 실시간 COUNT 비용 | `EXPLAIN ANALYZE` |
| 3 | 비정규화 카운터 락 경합 | 동시 DB 세션 실험 |
| 4 | 인덱스 커버링 유지 | `EXPLAIN` |
| 5·6·7 | 리뷰 락 / FK 부모 S락 / History list length | 락 덤프 |

**항목 2의 부하는 이미 [2026-07-29 캠페인](2026-07-place-popular-sort-benchmark.md)이 끝냈다** —
v0는 성공률 1.6% / p99 9.8초로 기각됐다. 이번에 잰 것은 그 결론의 *원인 지표*다.

### 재현이 아니다

브리프에 "기존 실측 재현"이라는 표현이 있었으나 정확하지 않다. **재현인 항목은 하나도 없다.**

| 성격 | 항목 |
|---|---|
| **최초 측정** — 존재한 적 없는 값 | 3(구현된 적 없는 구조를 *만들어서* 잰다) · 5 · 7 |
| **새 환경 확정치** — 과거 값은 폐기, 비교하지 않음 | 1 · 6 |
| **미완 검증** — 아직 안 한 것 | 2 · 4 |

항목 3이 "재현"이 아닌 것은 실험 설계를 바꾼다 — **만든 모형이 실제 구조를 대표하는가**가
결과의 타당성을 좌우한다 (§6).

## 2. 검증 환경

`docker/docker-compose.bench.yml`의 **MySQL만** 기동했다. 7개 항목이 전부 DB 레벨이라
앱·LB·Redis가 필요 없다 (부수적으로 앱 이미지 빌드가 레지스트리 접근에 막혀 있기도 했다).

| 항목 | 값 |
|---|---|
| MySQL | 8.0.46 / 2 CPU / 3G / **버퍼풀 2G** / `binlog_format=ROW` |
| 장소 | 6,320 (벤치 6,000 + 마이그레이션 기본 320) |
| 유저 | 100,000 |
| 북마크 | 10,399,466 (1위 장소 69,784건) |
| **리뷰** | **198,191** — 이번에 신규 시드 |
| 배치 파라미터 | 반감기 90일 / 북마크 1.0 / 리뷰 3.0 (`PlaceStatsProperties` 기본값) |

**벤치 DB는 V21에 머물러 있어 V22·V23·V24를 직접 적용했다.** `flyway_schema_history`에
`installed_by='bench-manual'` · `checksum=NULL`로 기록해 나중에 앱을 붙여도 재적용으로 깨지지 않게 했다.
부수 실측: **V23의 1,039만 행 인덱스 재구축 21초** (in-place DDL, 버퍼풀 2G).

### 리뷰 시드 20만으로 확정

설계 문서가 §1.2 산정표는 20만, §2.6 과거 실측 행은 30만으로 갈려 있었다. **20만을 택했다.**

- §1.2가 유일하게 근거를 가진 숫자다 — 유저 10만 × 2건, 교차검증 DAU 2만 × 0.5%/일 → 3년 11만
- **리뷰/북마크 = 1/50 비대칭**이 설계 논거인데(북마크는 탭 1회, 리뷰는 방문+사진+500자)
  30만이면 1/35가 되어 그 논거와 어긋난다
- 30만은 맞춰야 할 기준이 **아니다** — 그 측정은 이미 폐기됐고, 폐기한 수치에 새 측정을
  종속시킬 이유가 없다

분포는 장소별 Zipf(북마크 실측 분포에서 유도) · rating J형(평균 3.87) · 최근 편향 + 트렌딩 20곳.
**장소의 10%는 저평점으로 뒤집었다** — 점수 공식이 `(rating − 3)`이라 음수 기여 경로가 있는데
그 경로를 걷는 데이터가 없으면 검증이 반쪽이 된다.

> **시드에서 한 번 밟은 함정.** 저평점 장소를 `i % 10 == 0`으로 골랐더니 장소 배치 주기와 맞물려
> **각 leaf의 Zipf 1위가 전부 저평점**이 됐다(리뷰 상위 4곳 평균 2.3). 인기순 검증용 시드가
> "인기 있을수록 평점이 낮다"는 없는 상관을 만든 것이다. id 해시로 흩어 해소했다
> (leaf 1위 60곳 중 저평점 10곳, 기대치 6).

## 3. 항목 1 — 배치 소요와 멱등성

같은 `calculatedAt`(`2026-07-31 02:00:00`)으로 4회 실행. 첫 회는 워밍업으로 버렸다.

| 라운드 | 소요 | 지문 |
|---|---:|---:|
| r1 (버림) | 6,159.3ms | 569239 |
| r2 | 6,036.7ms | 569239 |
| **r3 (중앙값)** | **6,049.5ms** | 569239 |
| r4 | 6,052.0ms | 569239 |

**소요 6,049ms, 편차 0.25%.** 하루 주기 대비 **0.007%** (6.05 / 86,400).
성공 조건(주기의 1% = 864초 미만)을 143배 여유로 통과했다.

**멱등성 확정.** 4회 전부 지문·합계(`sum=4041353.337640`)가 같다.
1회차는 INSERT 경로, 2회차부터는 UPDATE 경로이므로 이 일치는
**`ON DUPLICATE KEY UPDATE`가 어떤 컬럼도 빠뜨리지 않았다**는 뜻이기도 하다.

원인 지표: `created_tmp_disk_tables 0` · 버퍼풀 hit rate 100% (디스크 읽기 0블록).
설계 §2.6의 "파생 결과가 장소 수만큼뿐이라 디스크로 밀릴 여지가 없다"가 확인됐다.

> **주의: 이 값은 배치 *전체* 소요의 하한이다.** 앱을 거치지 않고 SQL로 직접 실행했으므로
> JPA·커넥션 획득·트랜잭션 경계 비용이 빠져 있다.

## 4. 항목 4 — 상한 조건 후에도 인덱스 전용 스캔인가

이 캠페인에서 **이론으로 못 푸는 두 항목 중 하나**였다. 옵티마이저의 인덱스 선택은 통계에 의존하고,
`created_at <= :calculatedAt` 상한(커밋 `b6a27e4`)이 붙었을 때 커버링이 유지될지는 확정이 아니었다.

| 쿼리 | key | Extra |
|---|---|---|
| 북마크 축 — 상한 **있음** (현행) | `idx_bookmark_target` | **`Using where; Using index`** |
| 북마크 축 — 상한 없음 (대조) | `idx_bookmark_target` | `Using index` |
| 리뷰 축 — 상한 있음 | `idx_place_reviews_place_created_rating` | **`Using where; Using index`** |

**커버링 유지.** 상한은 계획을 바꾸지 않았고 `Using where`만 더해졌다.
V23·V22 인덱스 정의는 재검토 대상이 아니다.

부수 소득 — **리뷰 축이 무시 수준이라는 설계 §2.6 주장도 실측됐다.**

| 축 | `EXPLAIN ANALYZE` 실측 | 읽은 행 |
|---|---:|---:|
| 북마크 | 6,051ms | 10.4M → 6,000 그룹 |
| 리뷰 | **117ms** (1.9%) | 198,191 → 5,975 그룹 |

## 5. 항목 2 — 실시간 집계를 왜 버렸는가

v0의 실제 경로는 `BookmarkRepository.countByPlaceIds` — 시 단위 후보 전체를 IN으로 넘긴 GROUP BY다.
서울(leaf 301~318) 1,800곳을 **리터럴 IN 리스트**로 넘겼다 (앱이 실제로 그렇게 보낸다).

| 경로 | 읽는 행 | 소요 |
|---|---:|---:|
| 단일 장소 실시간 COUNT (1위) | 69,784 | 12.3ms |
| **v0 실제 경로 — 서울 1,800곳** | **5,590,000** | **1,726ms** |
| **현행 — `place_stats` PK IN 1,800곳** | **1,800** | **1.2ms** |
| (참고) 전국 6,000곳 | 10,400,000 | 1,579ms |

**읽는 행 3,106배 · 소요 1,438배.** 성공 조건(100배 이상)을 압도적으로 통과했다.
요청 하나가 1.7초의 DB 작업을 요구하면 목표 120 req/s는커녕 예상 피크 22 req/s도 불가능하다 —
이것이 v0가 성공률 1.6%로 무너진 **원인**이다.

> **함정 기록.** 처음에 IN 리스트를 `GROUP_CONCAT`으로 만들었더니 `group_concat_max_len`
> 기본 1024바이트에 **조용히 잘려** 1,800곳이 171곳이 됐고, 마지막 항목이 `1017`이라는
> 잘린 쓰레기 id로 들어갔다. EXPLAIN은 정상 출력되므로 행 수를 세기 전엔 알 수 없다.

## 6. 항목 3 — 비정규화 카운터의 락 경합 (**결론이 뒤집힌 항목**)

### 이건 재현이 아니라 모형이다

카운터 컬럼은 채택된 적이 없어 구현체가 없다. 그래서 실험용 모형을 만들었다.

- **실험군** = `INSERT INTO bookmarks` + `UPDATE places SET cnt = cnt + 1` — **한 트랜잭션**
- **대조군** = `INSERT INTO bookmarks` (현행 채택안)

카운터만 때리는 모형은 쓰지 않았다 — 실제 구현이라면 둘이 같은 트랜잭션에 들어가므로
카운터만 재면 락 보유 시간이 실제보다 짧게 나와 **기각 근거를 실제보다 약하게** 만든다.

조건은 **HOT**(전 세션이 1위 장소 한 행에 집중, 최악)과 **SPREAD**(상위 10곳 분산).
세션 16 × 반복 50 = 800 트랜잭션. 3회 반복 전부 안정적이었다.

### 결과

| 구분 | 조건 | 처리량 (중앙값) | 락 대기 | 평균 대기 |
|---|---|---:|---:|---:|
| **현행** | HOT | **2,632 tx/s** | **0건** | — |
| 비정규화 | HOT | 903 tx/s | 799건 | 12.6ms |
| **현행** | SPREAD | **1,011 tx/s** | **0건** | — |
| 비정규화 | SPREAD | 903 tx/s | ~550건 | 1.8ms |

### 판정 — 락은 비정규화 기각의 근거가 될 수 없다

측정 전에 정해 둔 성공 조건은 이랬다:
*"자릿수 차이가 안 나오면 §2.3에 락 근거를 추가하지 않고, 오히려 '락 때문에 안 했다'를
앞으로 쓰지 않도록 기록에 못을 박는다."*

**락 경합은 실재한다** — 대기 0건 → 799건, 6개 라운드 전부 재현됐다.
**그러나 크기가 근거가 되기에 부족하다:**

- 최악 조건(HOT)에서 **2.9배** 저하. 자릿수가 아니다
- 그 최악 조건에서도 **903 tx/s** — 설계 §1.1의 예상 피크 **22 req/s의 41배**
- 현실적 조건(SPREAD)에서는 1.12배로, 로컬 노이즈와 구분하기 어려운 수준

→ **설계 §2.3에 락 근거를 추가하지 않는다.** 기각 근거는 여전히 셋뿐이다 —
축이 스키마에 샌다 / 2급 데이터 / 정확도 요구를 분리할 수 있다.
이것들은 성능 논거가 아니라 설계 논거이고, **실측은 그 셋을 보강하지도 반박하지도 않는다.**

> Task 8 브리프는 이 항목을 "`places`에 카운터 컬럼을 왜 안 넣었는가 (설계 §2.3)"로 연결했으나,
> §2.3을 다시 읽으면 락 이야기가 없다. 이 측정은 기존 근거의 뒷받침이 아니라
> **없던 네 번째 근거를 만들려던 시도**였고, 결과적으로 만들어지지 않았다.

부수 관찰: 현행 경로가 HOT(304ms)보다 SPREAD(791ms)에서 **느리다.** 락과 무관하며,
`idx_bookmark_target` B-트리 삽입이 HOT에서는 한 지점에 몰려 캐시 지역성이 좋기 때문이다.

## 7. 항목 5·6·7 — 배치가 무엇을 잠그는가

홀더 세션이 UPSERT 후 커밋하지 않고 붙잡은 상태에서 덤프했다.

| 대상 | RR | RC (현행) |
|---|---:|---:|
| `bookmarks` | 10,420,265 (S, next-key) | **0** |
| **`place_reviews`** | **198,766 (S, next-key)** | **0** |
| `places` (FK 부모) | 6,330 S + 6,320 S,REC_NOT_GAP | **6,320 S,REC_NOT_GAP** |
| `place_stats` | 6,320 X,REC_NOT_GAP | 6,320 X,REC_NOT_GAP |
| **합계 = `trx_rows_locked`** | **10,638,001 ✓** | **12,640 ✓** |
| UPSERT 소요 | 6,865ms | 5,317ms |
| History list length | 0 | 0 |

| 경합 세션 (`innodb_lock_wait_timeout=3s`) | RR | RC |
|---|---|---|
| 신규 북마크 삽입 | 차단 (타임아웃) | **즉시 성공 93ms** |
| **신규 리뷰 삽입** | **차단 (타임아웃)** | **즉시 성공 82ms** |
| 어드민 `UPDATE places` (동네 비활성화) | 차단 | **차단 (타임아웃)** |

### 항목 5 — `place_reviews`는 가설대로 거동한다 (최초 측정)

RR에서 **198,766건**의 shared next-key 락이 걸린다. 행 수 198,191을 넘는 것은
gap 몫이 더해지기 때문으로, 북마크 축과 **같은 성질**이다. RC에서는 0건.

→ **RC 전환이 리뷰 축까지 덮는다는 것이 확정됐다.** 설계 §2.7의 판정은 북마크 축에만
성립하는 것이 아니었다. 이 확인 전까지는 "구조가 같으니 같을 것"이라는 추정이었다.

### 항목 6 — FK 부모 S락은 벤치 규모에서 6,320건

기존 실측 320은 마이그레이션 기본 데이터만 있던 DB의 값이었다. 갱신 행 수만큼 걸린다는
성질이 규모를 키워도 그대로임을 확인했다 (장소 6,320 → S락 6,320).

**RC로 낮춰도 어드민 `UPDATE places`는 배치 커밋까지 막힌다.** 실측상 이것이
RC에서 유일하게 남는 차단이다. 배치가 6초대이므로 실피해는 어드민 액션 6초 지연이다.

### 항목 7 — History list length baseline = 0

배치 hold 중에도 0이었다. RC는 문장 단위 read view라 스캔 문장이 끝나면 purge를 막지 않는다는
설계 §2.7의 판정과 일치한다. 관측 수단이 0개이던 상태에서 **첫 기준값**을 확보했다.

> **폐기한 라운드 2건 (기록).** 첫 시도에서 "processlist에 `SELECT SLEEP`이 보이면 홀더"로
> 판정했는데, 앞선 실행이 남긴 홀더를 새 홀더로 오인했다. RC 덤프가 103초 전에 시작된 트랜잭션을
> 찍었고, RR 덤프는 `INNODB STATUS`(12,640건)와 `data_locks`(790,286건)가 서로 다른 트랜잭션을
> 가리키는 자기모순을 냈다. **락 합계 == `trx_rows_locked` 검증을 넣어** 재측정했고,
> 위 표는 두 라운드 모두 그 검증을 통과한 값이다. 검증이 없었다면 모순을 못 보고 인용했을 것이다.

## 9. 이 측정으로 말할 수 없는 것

- **v0 벤치 경로와 캐시 경로의 랭킹은 더 이상 같지 않다.** v0는 `COUNT(*)`, 서비스 경로는
  `popular_score`다. 지연·처리량 비교는 유효하지만 **모드 간 결과 diff 검증은 성립하지 않는다.**
- **배치 소요는 하한이다.** 앱을 거치지 않은 순수 DB 시간이다.
- **항목 3은 모형값이다.** 실제 애플리케이션 경로(JPA·커넥션 풀·트랜잭션 경계)를 거치지 않았으므로
  절대 수치가 아니라 **현행 구조와의 상대 비교로만** 읽어야 한다.
- **prod 절대 성능이 아니다.** 벤치는 버퍼풀 2G, prod는 기본값 128MB다 ([가이드 부록 A.4](load-test-guide.md)).
  버퍼풀 hit rate 100%는 2G 전제의 값이다.
- **레이턴시 지표를 쓰지 않았다.** 호스트 정리 없이 측정했고, 그래도 되는 항목만 골랐다.
  이 문서의 어떤 수치도 사용자 체감 응답시간이 아니다.
- **동시 실행·다중 인스턴스는 범위 밖**이다. 홀더는 항상 한 세션이었다.
