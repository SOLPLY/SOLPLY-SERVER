# 인증 MySQL 전환과 통계 스케줄 분리

2026-09-12 사용자와 Q1~Q9 합의 완료. 구현 후 별도 Claude Opus 작업자가 검증한다. 배포·PR 게시 금지.
사용자 요청으로 이슈 #404를 생성하고 develop 기반 `feat/#404-auth-mysql-stats-schedules` worktree에서 작업한다.

## 범위와 기존 계약

- 소셜 로그인과 관리자 OAuth state/nonce → 일회용 authCode 교환을 유지한다.
- 모바일 refresh 입력은 `Refresh-Token` 헤더, 로그인/재발급 결과는 기존 JSON DTO를 유지한다.
- Refresh 쿠키·익명 세션·Access 블랙리스트를 추가하지 않는다. 기존 oauth_nonce 쿠키만 유지한다.
- 인증 Redis 저장소 세 개(refresh, admin state, admin authCode)만 MySQL로 전환한다. 추천 캐시와 Redis 인프라는 유지한다.
- 기존 ADMIN 검사·자원 소유권 검사를 유지한다. 일반 토큰 인증에서는 DB·Redis를 조회하지 않는다.

## JWT와 전환

- Access TTL 30분, Refresh TTL 14일, 회전 유예 3초. 기존 설정 체계와 환경변수에 연결한다.
- Access/Refresh 서명 알고리즘과 각 키, issuer, audience, type, subject, 발급/만료 시각, 필수 클레임을 검증한다.
- Access는 현재 역할을 발급 시 넣고 요청 시 신뢰한다. 레거시 역할 DB 폴백을 제거한다.
- 로그인마다 독립 family ID를 생성하고 Access/Refresh에 넣는다. 다중 로그인 계열을 허용한다.
- 고정 키 설정을 유지한다. 온라인 키 교체는 구현하지 않으며 키·고정 클레임 설정 변경은 재로그인이 필요한 전환으로 취급한다.
- 기존 Access/Refresh는 새로운 필수 클레임이 없어 전환 후 거절한다. 기존 Redis refresh를 이관하지 않는다. 무중단 호환으로 표현하지 않는다.
- 새 Access는 로그아웃·Refresh 폐기·탈퇴·역할 변경 이후에도 만료까지 인증 단계에서 유효하다. 실제 도메인 로직의 상태/소유권 검사는 별개다.

## Refresh 데이터와 재구성

`refresh_token`: id, user_id, jwt_id UNIQUE, parent_jwt_id UNIQUE NULL 허용, issued_at, expires_at,
rotated_at, grace_expires_at, revoked_at. family_id, platform, token_format_version 및 재구성 고정값을 명시적으로 관리한다.
원문 JWT는 저장하지 않는다. 모든 고정 클레임과 헤더의 순서/내용 및 HS512 서명 선택을 재구성에서 동일하게 사용한다.
JWT NumericDate는 정수 초로 고정한다. issued_at/expires_at도 같은 정수 초를 저장하여 DB 왕복 후 문자열을 보존한다.
회전/유예 판정 시각은 UTC의 명시적 정밀도로 관리하고 테스트 Clock으로 경계를 재현할 수 있게 한다.

상태 우선순위: revoked_at 존재 → REVOKED; expires_at <= now → EXPIRED;
미회전 → ACTIVE; 회전됨 && now < grace_expires_at → GRACE; 나머지 → 유예 종료.
유예 시각 누락 등 불가능한 조합은 정합성 오류이며 재사용으로 단정하지 않는다.

## 트랜잭션과 경쟁

사용자 단위 DB 공통 잠금을 발급·회전·계열 로그아웃·전체 폐기·탈퇴에 적용한다.
외부 OAuth HTTP 호출은 가능한 한 잠금 밖에서 마치고 DB 변경과 토큰 발급 기록에 잠금을 집중한다.
잠금 순서는 사용자 → Refresh 행. 전체 폐기는 잠금 획득 이전에 완료된 발급을 포함하며,
전체 폐기 커밋 후 잠금을 얻어 성공하는 새 로그인은 허용한다. 이미 폐기된 토큰으로 재요청하면 정책에 따라 다시 전체 폐기할 수 있다.
탈퇴와 Refresh 폐기는 함께 커밋하여 같은 user 행 재가입으로 옛 계열이 살아나지 않게 한다.

회전 트랜잭션은 READ COMMITTED를 선택한다. 외부 서비스의 기존 트랜잭션에 조용히 참여해 격리 수준이 무시되지 않게 경계를 분리한다.
초기 조회는 분기용이며 다음 조건부 UPDATE가 회전 경쟁 판정이다.

```sql
UPDATE refresh_token SET rotated_at = :now, grace_expires_at = :graceExpiresAt
WHERE id = :id AND rotated_at IS NULL AND revoked_at IS NULL AND expires_at > :now;
```

- 1행 변경: 새 jti 자식 INSERT. 두 변경은 같은 트랜잭션이며 INSERT 실패 시 부모도 롤백한다.
- 0행 변경: 벌크 UPDATE 이전 영속성 컨텍스트 값을 재사용하지 않고 최신 부모/자식을 재조회해 재분류한다.
- 사용자 잠금으로 정상 진입 경로는 직렬화되더라도 CAS 실패 처리 자체를 생략하지 않는다. 실제 MySQL 테스트에서 이 분기도 별도 경쟁으로 검증한다.
- GRACE: parent_jwt_id로 자식을 찾아 ACTIVE일 때만 동일 Refresh 문자열을 재구성한다. Access는 사용자 상태·현재 역할을 확인해 새로 발급한다. 부모 유예와 자식 만료를 연장하지 않는다.
- 유예 부모의 자식이 이미 회전·폐기·만료됐으면 전용 401을 반환하고 이것만으로 전체 폐기하지 않는다. 자식 미존재·소유자/계열 불일치는 정합성 오류다.
- 유예가 끝난 회전 토큰 또는 이미 폐기된 토큰: 사용자의 모든 미만료·미폐기 Refresh를 폐기한다. 회전된 부모도 포함한다.
- 폐기 결과는 트랜잭션 안에서 값으로 반환하고 커밋 완료 후 바깥 계층에서 `401 REFRESH_TOKEN_REUSE_DETECTED`로 변환한다.
- 서명 검증을 통과했으나 DB 행이 없는 경우와 단순 만료를 구분한다. JWT 자체가 만료되면 DB 재사용 처리를 하지 않는다. DB 상태 분류에서는 폐기를 만료보다 우선한다.
- 재사용 관찰은 탈취 확정이 아니며 정상 지연도 포함할 수 있는 보안 정책이다.

## 로그아웃, 관리자, 정리

- 기존 DELETE /api/auth/logout은 유효 Access의 family ID로 그 계열의 Refresh를 폐기한다. 동일 Access 반복 호출은 200, 인증 누락/만료는 401이다.
- 관리자 state/nonce와 authCode는 만료를 검사하고 MySQL에서 원자적으로 일회 소비한다. 소비 실패와 만료의 오류 응답을 기존 흐름에 맞춘다.
- oauth_nonce 쿠키의 HttpOnly, Secure 설정, SameSite=Lax, 경로와 CORS 설정을 확인한다. Refresh 쿠키를 추가하지 않으므로 인증 방식 자체를 쿠키 기반으로 바꾸지 않는다.
- Refresh는 계열 내 모든 토큰 만료 이후 30일이 지나야 계열 단위로 삭제한다. 살아 있는 후속 토큰의 부모 이력을 지우지 않는다. 보존 기간은 설정값이다.
- 만료된 관리자 임시 데이터와 Refresh 이력을 매일 별도 ShedLock 정리 작업으로 삭제한다. 정리와 발급/회전의 경쟁에서도 살아 있는 계열을 삭제하지 않는다.
- Flyway 신규 마이그레이션, 환경별 설정 예시, 클라이언트 응답/오류 변경과 재로그인 전환 순서를 문서화한다. 구버전·신버전 혼합 서비스 기간을 호환 경로로 간주하지 않는다.
- 클라이언트는 Refresh 요청을 하나씩 실행하고 늦게 도착한 옛 응답으로 최신 토큰을 덮어쓰지 않아야 한다. 서버는 네트워크 응답 도착 순서를 보장할 수 없다.

> 서로 만나는 자리를 못 박은 것이다. 코드는 아래 해석대로 이미 동작한다.
>
> 1. **"그 계열의 Refresh를 폐기한다"는 로그아웃이라는 동작의 범위다.** 그 뒤에 오는 요청까지 다른
>    계열이 안전하다는 뜻이 아니다 — 로그아웃한 계열의 Refresh가 한 번이라도 더 도착하면 "이미
>    폐기된 토큰"이므로 위 "트랜잭션과 경쟁"의 전체 폐기 조항이 그대로 적용되어 그 사용자의 모든
>    계열이 끊긴다. 두 조항이 충돌하면 **전체 폐기 쪽이 이긴다.** 폐기 사유 컬럼이나 로그아웃
>    예외는 두지 않는다.
> 2. **"전체 폐기 커밋 후 잠금을 얻어 성공하는 새 로그인은 허용한다"는 발급이 막히지 않는다는
>    뜻이다.** 그렇게 만든 새 계열이 이후의 재사용 관찰에서 면제된다는 뜻이 아니다. 탈퇴 후
>    재가입으로 막 열린 계열도, 옛 계열의 폐기된 토큰이 한 번 도착하면 함께 끊긴다.
> 3. **클라이언트 계약이 하나 늘었다.** 로그아웃을 부르는 순간 대기 중인 Refresh 요청을 중단하고
>    재시도 큐를 비우고 저장된 토큰을 버린다. 이미 네트워크로 나간 요청은 서버가 회수하지 못하므로,
>    그 한 건이 남기는 전체 폐기는 이 정책이 감수하는 상한이다.
> 4. **재발급 경로의 실패는 전부 401이다.** 서명은 맞는 Refresh를 들고 왔는데 그 주인이 탈퇴했거나
>    행이 없는 경우를 위해 401 `AUTH-017`을 뒀다. 로그인·어드민 교환 경로의 "사용자 없음"은 그대로
>    404다. 비활성 사용자 판정은 사용자 잠금 단계에 있어 **행 상태 분류보다 앞선다.**
> 5. 따라서 아래 검증 기준 9의 **"다른 계열 보존"은 로그아웃 직후를 뜻한다.** 로그아웃한 계열의
>    Refresh를 한 번 더 보내는 경우는 같은 항목에서 **"다른 계열도 함께 폐기"**로 따로 확인한다.

## 통계 스케줄

- 리뷰 전량 재계산은 매시 30분, 북마크 아웃박스 델타 소비는 매시 15분, KST.
- 각각 별도 cron, ShedLock 이름, 재시도 설정, 시작/성공/실패/소요시간 로그를 둔다.
- 리뷰는 기존 count-cron/락 이름의 승계를 허용하여 설정 영향 최소화. 북마크용 키와 락은 신설한다. 문서에 정확한 실제 이름을 남긴다.
- 인기 점수 01:00, 안전망 01:45, 기존 집계 SQL과 스냅샷 리빌딩을 바꾸지 않는다.
- 파사드는 트랜잭션 밖, 리뷰 전량 집계와 북마크 델타의 기존 READ COMMITTED 경계를 유지한다.
- 북마크의 FOR UPDATE → 카운트 갱신 → 읽은 ID 삭제는 한 트랜잭션이다.
- PENDING/PROCESSING·worker 풀·추가 배치 UNIQUE·Idempotency Key·리뷰 아웃박스를 추가하지 않는다. 기존 비즈니스 UNIQUE는 유지한다.
- 스케줄러 풀은 확대하지 않는다. 같은 실행 스레드에서는 한 회차 지연이 다른 회차를 늦출 수 있고 ShedLock 시간 상한 초과도 무제한 상호배제를 보장하지 않는다.

## 검증 기준

구현 완료 후 테스트를 작성/수정하고 실행한다. H2로 동시성을 대체하지 않는다.
실제 MySQL Testcontainers, 독립 커넥션/트랜잭션, latch/barrier로 경쟁을 재현하고 환경변수 부재로 skip하지 않는다.

1. 동시 회전 자식 하나, 패자도 동일 Refresh, 정상 경쟁 전체 폐기 없음.
2. CAS 실패 최신 부모와 자식 조회; JPA stale/REPEATABLE READ 함정 방지.
3. JWT/DB 시각 정밀도 왕복 동일 문자열, 헤더·클레임 고정, 유예/만료 연장 없음.
4. 시각 경계와 REVOKED/EXPIRED/ACTIVE/GRACE 우선순위.
5. 연속 회전·자식 회전/폐기/만료·정합성 오류 정책.
6. 유예 종료 재사용과 이미 폐기된 토큰 재사용의 사용자 전체 폐기 실제 커밋.
7. 전체 폐기 대 회전/발급 경쟁과 직렬화 순서, 폐기 후 새 로그인 허용.
8. 자식 INSERT 실패 시 부모 UPDATE 롤백.
9. 계열 로그아웃 이후 재발급 차단·반복 로그아웃·다른 계열 보존·탈퇴 재가입 시 옛 계열 차단.
10. 관리자 임시 상태/코드 만료·동시 일회 소비.
11. 북마크 반영/삭제 실패 시 둘 다 롤백.
12. 두 cron/락/독립 재시도·로그·트랜잭션 경계, 새 스케줄이 기존 IT에서 예기치 않게 발화하지 않음.
13. Access 서명/만료/issuer/audience/type/필수 클레임 거절, 일반 인증 SQL/Redis 0회, ADMIN 보호 회귀.
14. 실제 MySQL 마이그레이션과 보존 정리, 관련 테스트 및 전체 빌드.
