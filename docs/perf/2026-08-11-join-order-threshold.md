# 2026-08-11 · 조인 순서 전환점 탐색 — 옵티마이저의 전환점은 스윕 밖에 있다

> 캠페인: [`load-test/campaigns/2026-08-11_join-order-threshold`](../../load-test/campaigns/2026-08-11_join-order-threshold/)
> **부하 테스트가 아니다.** 조인 순서 판정이라 `EXPLAIN ANALYZE`로 답한다 (가이드 §2).
> 처리량·백분위에 대해서는 **아무것도 주장하지 않는다.**
> 채취 2026-08-11, 96칸(규모 스윕 56 + 조합 16 + 실태그 앵커 16 + 실태그 3조각 8) 각 3회.
> 다섯 항목은 측정 전에 등록했다 — 캠페인 README에 있다.
> **제품 코드·마이그레이션은 건드리지 않았다.** 합성 태그를 깔고, 채취가 끝난 뒤 지웠다.

**사전 등록한 갈림길("두 전환점이 거의 일치하면 구현을 중단한다")은 발동하지 않았다.**
시 단위 전 구간에서 어긋나 있고, 어긋난 구간의 크기가 인기순 1,146에서 1.46배(1.32 → 0.905ms),
최신순 1,146에서 1.82배(1.58 → 0.869ms)다. 그래서 판단 규칙을 정하고 조건부 힌트를 구현했다(§6).

## 1. 무엇을 쟀는가

같은 문장을 두 형태로 잰다. **자연** = 힌트 없이 옵티마이저가 고른 계획, **강제** =
`JOIN_PREFIX(ps)`(인기순) 또는 `JOIN_PREFIX(p)`(최신순)로 지역 테이블을 드라이빙으로 못 박은 계획.
축은 넷이다 — 태그 규모 7단계(20 / 50 / 100 / 185 / 400 / 700 / 1,146곳) × 지역 2(동네 1곳 = 후보
100 / 시 단위 18곳 = 후보 1,800) × 정렬 2 × 형태 2.

규모 축은 합성 태그로 만들었다. 실태그는 연결 수 분포가 185와 1,146 사이에서 비어 있어
"규모만 다르고 나머지는 같은" 비교가 되지 않는다. 합성 태그는 활성 장소를 id 순으로 세우고
정확히 N개를 등간격으로 고른다 — 같은 데이터에 다시 돌리면 같은 행이 뽑힌다. **전국 균등 분포이고,
실태그의 지리 편중은 재현하지 않는다**(§7).

여기에 실태그 앵커 둘(`카페` 1,146곳 · `바/술집` 185곳)과 복수 태그 조합 다섯을 붙였다.

## 3. 주장 ① — 시 단위에서는 전환점이 스윕 안에 없다

### 3.1 시 단위 18곳 (지역 후보 1,800)

| 태그 규모 | 인기순 자연 | 인기순 강제 | | 최신순 자연 | 최신순 강제 | |
|---:|---:|---:|---|---:|---:|---|
| 20 | **0.0537** | 2.29 | 강제가 42.6배 손해 | **0.0814** | 2.39 | 29.4배 손해 |
| 50 | **0.106** | 1.71 | | **0.124** | 2.13 | |
| 100 | **0.191** | 1.37 | | **0.234** | 1.44 | |
| 185 | **0.295** | 1.17 | | **0.376** | 1.12 | |
| 400 | **0.432** | 0.916 | | **0.629** | 1.01 | |
| 700 | **0.678** | 0.902 | | 1.01 | **0.892** | ← 최신순 전환 |
| 1,146 | 1.32 | **0.905** | ← 인기순 전환 | 1.58 | **0.869** | |

**자연 형태의 드라이빙은 일곱 규모 모두 `place_tag`다.** 태그가 지역 후보의 64%까지 커져도
옵티마이저는 태그 주도를 놓지 않는다. 반면 실측으로는 인기순이 700과 1,146 사이에서,
최신순이 400과 700 사이에서 강제가 유리해진다. **두 전환점은 겹치지 않는다.**

강제 계획이 이기는 자리에서 무슨 일이 일어나는지는 트리가 보여준다.

```
자연  -> Sort: ps.popular_score DESC, ps.place_id, limit input to 11 row(s) per chunk
          -> Covering index lookup on pt using idx_place_tag_tag_place (tag_id=9007)  rows=1146
              -> Single-row index lookup on ps using PRIMARY   loops=1146   ← 326건만 살아남는다

강제  -> Limit: 11
          -> Sort: ps.popular_score DESC, ps.place_id           ← 1,800건 정렬 후 스트리밍
              -> Index range scan on ps using idx_place_stats_town_score   rows=1800
          -> Single-row covering index lookup on pt (place_id=ps.place_id, tag_id=9007)  loops=47
```

강제 계획은 지역 후보 1,800건을 정렬하지만 **정렬 결과를 스트리밍으로 흘리며 LIMIT에서
47회 만에 끊는다.** 자연 계획은 태그 1,146건을 전부 조인해 326건을 만든 다음 정렬한다.
옵티마이저는 강제 쪽을 더 비싸다고 본다(추정 비용 519 → 948, 1.83배). 실측은 1.46배 반대다 —
**LIMIT 조기 종료 이득이 비용 모델에 반영되지 않는다**는 등록 가설과 같은 방향이다.

### 3.2 동네 1곳 (지역 후보 100)

| 태그 규모 | 인기순 자연 (드라이빙) | 인기순 강제 | 최신순 자연 (드라이빙) | 최신순 강제 |
|---:|---:|---:|---:|---:|
| 20 | 0.0623 (`pt`) | 0.156 | 0.0617 (`pt`) | 0.143 |
| 50 | 0.0932 (`pt`) | 0.122 | 0.113 (`pt`) | 0.141 |
| 100 | 0.140 (**`ps`**) | 0.157 | 0.193 (`pt`) | 0.159 |
| 185 | 0.148 (`ps`) | 0.136 | 0.152 (**`p`**) | 0.158 |
| 400 | 0.143 (`ps`) | 0.137 | 0.123 (`p`) | 0.163 |
| 700 | 0.136 (`ps`) | 0.150 | 0.152 (`p`) | 0.167 |
| 1,146 | 0.0875 (`ps`) | 0.102 | 0.136 (`p`) | 0.106 |

**동네에서는 전환점이 스윕 안에 있다** — 인기순은 50과 100 사이, 최신순은 100과 185 사이에서
옵티마이저가 지역 주도로 돌아선다. 지역 후보가 100이므로 대략 "태그가 지역보다 커지는 자리"다.

그런데 **여기서는 어느 쪽을 골라도 시간이 거의 같다.** 차이가 가장 큰 칸이 태그 20곳으로
인기순 0.094ms · 최신순 0.081ms이고 둘 다 강제가 손해다. 태그 100 이상 열 칸은 차이가 0.04ms
안쪽이고 부호도 갈린다. 값 자체가 0.06~0.19ms 범위다. 동네 스코프는
지역 후보가 100건뿐이라 어느 쪽으로 돌든 훑는 양이 작다. **판단 규칙이 동네를 건드릴 이유가 없다**는
근거가 이 표다.

## 4. 주장 ② — 복수 태그의 드라이빙은 언제나 가장 작은 태그다

태그 조건은 AND로 묶인 `EXISTS` 블록 여러 개다. 태그 주도 계획이 선택될 때 어느 블록이
드라이빙이 되는지를 시 단위 자연 형태에서 봤다.

| 조합 | 각 그룹의 일치 행 수 | 드라이빙 | 인기순 | 최신순 |
|---|---|---|---:|---:|
| `카페` + 합성서브 20 | 1,146 / **20** | `tag_id=9101` (20) | 0.0872 | 0.0915 |
| `카페` + 합성서브 100 | 1,146 / **100** | `tag_id=9102` (100) | 0.302 | 0.425 |
| `카페` + 합성서브 400 | 1,146 / **400** | `tag_id=9103` (400) | 0.656 | 0.626 |
| `음식` + `바/술집` | 1,094 / **185** | `tag_id=21` (185) | 0.523 | 0.557 |
| `카페` + 옵션1군 + 옵션2군 | **1,146** / 1,756 / 1,803 | `tag_id=1` (1,146) | 2.02 | 2.63 |

**메인 태그 고정이 아니다.** 앞의 네 조합에서는 서브 태그가 드라이빙이 되고, 마지막 조합에서만
메인이 드라이빙인데 그건 메인이 마침 가장 작기 때문이다(옵션군은 `IN` 리스트라 그룹 합이 1,756·1,803).
드라이빙이 정해진 뒤 나머지 블록은 `uk_place_tag_place_tag`의 단건 커버링 조회로 붙는다.

이것이 판단 규칙의 형태를 정했다 — 유효한 태그 규모는 메인 태그의 연결 수가 아니라
**AND 그룹별 합의 최솟값**이다. 그 최솟값이 곧 교집합의 상한이고, 옵티마이저가 드라이빙으로 고를
후보이기도 하다.

## 5. 주장 ③ — 힌트는 조인 순서만 고정하고 세미 조인 전략은 고정하지 않는다

지점별 강제 실측값은 §3의 두 표가 전부다. 문제는 **실태그 3조각 조합**(`카페` + 옵션1군 4개 +
옵션2군 6개, 시 단위)에서 나왔다. 2026-08-07 A/B 시나리오가 가중치 40%로 치던 모양이고,
2026-08-10 재검증에서 강제가 3배 이득(2.45 → 0.809ms)이라고 기록된 바로 그 셀이다.

3회 중앙값의 산포가 커서 7회로 다시 쟀다.

| 형태 | 인기순 7회 중앙값 | 최신순 7회 중앙값 | 옵션군 EXISTS 처리 |
|---|---:|---:|---|
| 자연 | **1.99** | **2.43** | 세미 조인 (`pt` 주도) |
| `JOIN_PREFIX` 단독 | 2.12 | 2.04 | **구체화(Materialize with deduplication)** |

**`JOIN_PREFIX`만 걸면 이득이 없다.** 드라이빙은 지역으로 돌아오는데, 그 대가로 옵션군의
`IN` 리스트 `EXISTS` 두 개가 구체화로 바뀐다. 세미 조인 전략을 힌트로 지목해 보면 원인이 갈린다
(3회 중앙값).

| 힌트 | 인기순 | 최신순 | 옵션군 처리 |
|---|---:|---:|---|
| `JOIN_PREFIX` (기준) | 2.00 | 1.91 | 구체화 |
| `+ NO_SEMIJOIN(@qb1) NO_SEMIJOIN(@qb2)` | 3.52 | 3.55 | 종속 서브쿼리 |
| `+ SEMIJOIN(@qb1 FIRSTMATCH) SEMIJOIN(@qb2 FIRSTMATCH)` | **1.03** | **0.889** | FirstMatch 세미 조인 |

**구체화가 손해인 이유는 실행 위치다.** 구체화는 명단 두 벌을 미리 만든다 — 옵션1군 1,756엔트리를
훑어 1,145행으로, 옵션2군 1,803엔트리를 훑어 867행으로 중복을 지운다. 이 제작은 **LIMIT으로 멈추는
반복문 밖에서** 한 번 돌고, 트리에서 노드당 0.55~0.58ms를 먹는다. 반면 FirstMatch는 정렬 결과를
따라가며 첫 매치에서 끊는 프로브라 **반복문 안에서 15회만** 돈다(회당 1.2~1.3µs).

```
JOIN_PREFIX 단독
  -> Single-row index lookup on <subquery3> ...        loops=15
      -> Materialize with deduplication  rows=1756 → 1145   (actual 0.573ms, loops=1)   ← LIMIT 밖
  -> Single-row index lookup on <subquery4> ...        loops=15
      -> Materialize with deduplication  rows=1803 → 867    (actual 0.564ms, loops=1)   ← LIMIT 밖

JOIN_PREFIX + SEMIJOIN(FIRSTMATCH)
  -> Nested loop semijoin
      -> Filter: (pt.tag_id in (7,8,9,10))     loops=15   (회당 0.00122ms)   ← LIMIT 안
  -> Nested loop semijoin
      -> Filter: (pt.tag_id in (11,12,13,14,15,16))  loops=15               ← LIMIT 안
```

`NO_SEMIJOIN`이 더 나쁜 것도 같은 이유다. 세미 조인 변환을 막으면 `EXISTS`가 종속 서브쿼리로
내려가 정렬 **이전**의 필터에 붙는다. 옵션1군 블록이 지역 후보 1,800행 전부에서 평가되고
(`loops=1800`), 옵션2군 블록이 그것을 통과한 275행에서 다시 돈다.

**이것이 이 캠페인의 추가 발견이다.** `JOIN_PREFIX`는 조인 순서만 고정하고, 세미 조인 전략은
고정하지 않는다. 순서를 고정하면 옵티마이저가 남은 자유도에서 다른 선택을 하는데 그 선택이
이득을 도로 까먹을 수 있다. **두 힌트는 한 벌로 붙여야 한다.**

## 6. 후속 조치 — 판단 규칙과 게이트 판정

측정 뒤 판단 규칙을 정하고 조건부 힌트를 구현했다 (커밋 `f03c91b`).

**세 조건을 모두 만족할 때만 강제한다.**

| 조건 | 근거 |
|---|---|
| 동네가 2곳 이상 (시 단위) | §3.2 — 동네 1곳은 자연·강제 차이가 최대 0.094ms고, 값 자체가 0.06~0.19ms다 |
| 태그 필터가 있다 | 태그가 없으면 조인 자체가 없다 |
| **AND 그룹별 합의 최솟값 ≥ 1,000곳** | §4 — 유효 규모는 최솟값이다. 임계는 §3.1의 700(강제가 손해)과 1,146(강제가 이득) 사이의 보수적 경계 |

임계를 낮은 쪽이 아니라 높은 쪽에 붙인 이유는 손익이 비대칭이라서다. **흔한 태그에서 얻는 것은
1.46~1.82배인데 희귀 태그에서 잃는 것은 최대 42.6배다**(§3.1 태그 20곳). 어긋나도 손해가 작은 쪽으로
치우쳐야 한다. 캐시에 없는 태그 id는 0곳으로 본다 — 모르는 태그를 흔하다고 가정하지 않는다.

힌트는 `JOIN_PREFIX` + 옵션군이 있을 때 `SEMIJOIN(@qb FIRSTMATCH)`를 함께 붙인다(§5).

**게이트 판정**

| # | 등록한 게이트 | 결과 |
|---|---|---|

## 7. 이 채취로 말할 수 없는 것

- **커서 2페이지 이후를 재지 않았다.** 96칸 전부 첫 페이지다. 힌트가 발동하는 조합에 커서가 붙으면
  `WHERE`에 부등호가 하나 더 붙어 지역 쪽 추정이 달라지는데, 그 조합은 측정하지 않았다.
- **합성 태그가 전국 균등이라 실태그의 지리 편중을 재현하지 못한다.** 동네 스코프에서 바로 드러난다 —
  같은 185곳짜리인데 실태그 `바/술집`은 동네 301에 6곳, 합성 태그는 3곳이다(6,320분의 185를 균등하게
  깔면 100곳당 2.9곳). 시 단위 1,146에서도 갈린다 — 합성 태그는 인기순이 자연 1.32 / 강제 0.905로
  1.46배 이득인데, 같은 규모의 실태그 `카페`는 자연 1.21 / 강제 1.19로 **이득이 사라진다**
  (최신순은 실태그도 1.68 → 0.863으로 1.95배 이득이라 정렬에 따라 다르다).
  **임계 1,000은 합성 태그의 전환점 위에 얹은 값이다.**
- **700과 1,146 사이는 측정하지 않았다.** 전환점이 그 안에 있다는 것만 안다. 보수적 임계로 포기한
  구간이고, 실제 전환이 800이라면 800~1,000 구간의 이득을 버리고 있다.
- **부하 중 효과를 모른다.** 부하 0에서 단일 문장을 잰 CPU 시간이다. 동시성이 올라가면 지역 후보
  1,800건 정렬의 메모리·CPU 몫이 달라질 수 있는데, 그건 이 방법으로 안 보인다.
- **실트래픽의 태그 분포를 확보할 수 없는 환경이다.** 그래서 판단을 "어느 쪽이 자주 오는가"가 아니라
  절대값(최대 1.8배 이득 대 최대 42.6배 손해)과 DB 여유(2026-08-07 A/B에서 앱 스로틀 66.0% 대
  MySQL 1.0%)로 했다. 분포가 확보되면 임계를 다시 볼 것이다.
- **강제 형태의 문장은 채취 배치를 건너면 중앙값이 움직인다.** 조합 셀의 강제는 글자 하나 다르지 않은
  같은 문장인데 배치별로 인기순 2.00 / 2.12 / 2.76ms, 최신순 1.91 / 2.04 / 2.35ms다(0.4~0.8ms 폭).
  자연 형태는 인기순 1.99 / 2.02로 훨씬 좁다. **시간 판정이 아니라 플랜 형상 판정을 등록 계약으로
  걸어 둔 이유가 이것이다.**
- ~~힌트가 붙은 문장의 결과 집합 동일성을 IT가 덮지 않는다~~ — 문서 검토에서 발견해 같은 날
  보강했다(§6 게이트 ④). 발동/미발동 결과를 요소·순서 단위로 비교하는 IT 3건, 커서 페이지 포함.

**단발 이상치.** 3회 중 한 회가 중앙값의 2배를 넘은 칸이 다섯이다 —
`latest/town/size0050` 자연 10.5ms(중앙값 0.113), `popular/town/size0020` 강제 1.08(0.156),
`popular/town/real1146` 자연 0.541(0.215), `latest/city/cafe1146_sub0100` 자연 0.993(0.425),
`latest/city/real0185` 강제 1.96(0.951). 7회 배치에도 하나 있다(인기순 강제 4.9, 중앙값 2.12).
**전부 중앙값을 바꾸지 않는다.** 튀는 회차가 다섯 칸에 흩어져 있고 형태·정렬·규모에 몰려 있지 않아
계측 환경의 잡음으로 본다.

## 8. 남는 것

1. **700~1,146 구간의 실제 전환점.** 임계를 1,000에서 내릴 수 있는지는 이 구간을 재야 답이 나온다.
2. **실태그 분포에서의 재측정.** 합성 태그로 정한 임계라 지리 편중이 있는 실태그에서는 전환점이
   더 오른쪽에 있을 수 있다(§7의 `카페` 1,146 관측이 그 방향이다).
3. **커서 페이지 + 발동 조합의 플랜.** 결과 불변은 IT로 못 박았으나(§6 ④), 그 조합의 실행 계획과
   시간은 미측정이다.

8/10 값이 재현된다. **차이의 출처는 채취 조건이 아니라 인덱스 형상이다** — V33의 커버링 인덱스가
