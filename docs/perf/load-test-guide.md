# 기술적 선택을 검증하기 위한 부하 테스트 가이드라인

> **§1~11은 범용 방법론이다.** 이 프로젝트의 환경 스펙·지표 계약·과거 함정은 [부록 A](#부록-a-이-프로젝트에-적용)에,
> 디렉터리 구조와 실행 절차는 [`load-test/README.md`](../../load-test/README.md)에 있다.

## 1. 부하 테스트의 목적

부하 테스트의 목적은 좋은 숫자를 만드는 것이 아니라 다음 질문에 답하는 것이다.

1. 현재 구조에 실제 또는 예상 가능한 문제가 있는가?
2. 그 문제의 원인은 무엇인가?
3. 선택한 구조가 해당 원인을 해결하는가?
4. 요구되는 부하에서 정확성과 안정성을 유지하는가?
5. 개선으로 인해 새롭게 발생한 비용이나 한계는 무엇인가?

따라서 테스트 전에 먼저 **증명하려는 주장**을 정해야 한다.

예:

- 조회 시점의 집계 비용이 요청량에 비례해 DB 병목을 유발한다.
- 캐시를 적용하면 반복 조회로 발생하는 DB 부하를 줄일 수 있다.
- 동기 처리 구조는 예상 동시 요청에서 스레드 풀이 고갈된다.
- 구조 A는 예상 부하를 감당하지 못하지만 구조 B는 감당할 수 있다.
- 데이터가 증가하면 현재 쿼리의 응답시간이 급격히 나빠진다.

---

## 2. 부하 테스트가 필요한지 먼저 판단한다

모든 기술적 변경에 부하 테스트가 필요한 것은 아니다.

### 부하 테스트가 필요한 경우

- 트래픽 또는 데이터 증가가 설계 선택의 주요 근거인 경우
- 동시 요청에서만 문제가 발생하는 경우
- CPU, DB, 메모리, 커넥션 등 자원 한계를 확인해야 하는 경우
- 구조 A와 B의 처리 능력을 비교해야 하는 경우
- 예상 부하를 안정적으로 처리하는지 확인해야 하는 경우
- 캐시, 비동기 처리, 배치, 락처럼 부하에 따라 효과가 달라지는 경우

### 부하 테스트보다 다른 검증이 적합한 경우

- 쿼리 실행계획 비교 → 실행계획과 스캔 행 수 확인
- N+1 제거 → 요청당 쿼리 수 확인
- 단순 알고리즘 개선 → 마이크로벤치마크
- 데이터 정합성 → 동시성 테스트와 불변식 검증
- API 계약 변경 → 기능·통합 테스트
- 외부 장애 대응 → 지연·실패 주입 테스트
- 메모리 누수 → 장시간 안정성 테스트

먼저 작은 검증으로 가설을 확인하고, 실제 부하에서 효과를 확인할 필요가 있을 때 부하 테스트로 확장한다.

## 3. 테스트 전에 작성할 내용

부하 테스트를 실행하기 전에 아래 다섯 가지를 정의한다.

### 3.1 문제

현재 구조에서 무엇이 문제인가?

> 인기순 조회가 요청마다 여러 집계 쿼리를 실행한다. 요청량이 증가하면 DB 작업량이 요청량에 비례해 증가할 가능성이 있다.

### 3.2 원인 가설

왜 문제가 발생한다고 보는가?

> 한 요청이 평균 14개의 SQL statement를 실행하고 있으며, 동일한 집계 결과를 요청마다 반복 계산한다.

### 3.3 기술적 선택

어떤 변경으로 해결하려는가?

> 요청 시점에 집계하는 구조 A를 주기적으로 사전 집계한 결과를 조회하는 구조 B로 변경한다.

### 3.4 검증할 주장

테스트를 통해 무엇을 증명할 것인가?

> 구조 B는 요청당 DB 작업량을 줄이며, 동일한 환경에서 구조 A보다 높은 요청량을 안정적으로 처리한다.

### 3.5 성공 조건

어떤 결과가 나오면 선택이 타당하다고 판단할 것인가?

예:

- 요청당 statement 수가 의미 있게 감소한다.
- 예상 부하에서 오류와 타임아웃이 발생하지 않는다.
- 부하가 증가해도 p95가 급격히 상승하지 않는다.
- DB CPU와 커넥션 사용량이 포화되지 않는다.
- 결과의 정확성과 허용 가능한 최신성을 유지한다.

정확한 목표 수치를 정하기 어렵다면 A와 B를 비교하는 상대 조건을 사용할 수 있다.

## 4. 문제 유형에 따라 지표를 선택한다

모든 지표를 수집하지 않는다. 주장과 직접 연결되는 지표를 선택한다.

### 조회 및 쿼리 구조 개선

예:

- N+1 제거
- 인덱스 추가
- 쿼리 통합
- 실시간 집계를 사전 집계로 변경

핵심 지표:

- 요청당 SQL statement 수
- 쿼리 실행계획
- 스캔 행 수
- 쿼리 실행시간
- DB CPU
- DB 커넥션 사용량
- 처리량별 p95와 오류율

검증 논리:

> 코드 변경
> → 요청당 쿼리 또는 스캔량 감소
> → DB 작업량 감소
> → 동일 부하에서 응답시간과 자원 사용량 개선

---

### 캐시 적용

핵심 지표:

- 캐시 적중률
- 요청당 DB 접근 횟수
- DB QPS와 CPU
- 캐시 적중·미적중 응답시간
- 캐시 메모리 사용량
- 만료 직후의 순간 부하
- 데이터 최신성과 정합성
- 캐시 장애 시 동작

검증 논리:

> 캐시 적용
> → 반복 요청의 DB 접근 감소
> → DB 부하 감소
> → 동일 자원에서 더 많은 요청 처리

캐시의 효과뿐 아니라 TTL, 무효화, 장애 대응 비용도 함께 평가한다.

---

### 동기 처리와 비동기 처리 비교

핵심 지표:

- 사용자 요청 응답시간
- 초당 작업 유입량과 처리량
- 큐 적체량
- 작업 완료 지연
- 재시도와 실패 건수
- 중복·유실 여부
- 장애 후 적체 해소 시간

검증 논리:

> 비동기 전환
> → 요청 스레드 점유시간 감소
> → 사용자 응답 개선
> → 소비자가 예상 유입량 이상을 지속적으로 처리하는지 확인

사용자 응답이 빨라졌더라도 큐가 계속 쌓인다면 문제를 뒤로 미룬 것에 불과하다.

---

### 동시성 제어

예:

- 낙관적 락
- 비관적 락
- 원자적 갱신
- 분산 락
- 멱등성 처리

핵심 지표:

- 최종 데이터 정합성
- 유실·중복 건수
- 성공·실패 요청 수
- 충돌과 재시도 횟수
- 락 대기시간
- 데드락
- 동시 요청별 처리량과 p95

검증 순서:

1. 결과가 정확한지 확인한다.
2. 예상 동시 요청을 처리하는지 확인한다.
3. 정합성을 위해 발생한 성능 비용을 평가한다.

동시성 문제에서는 성능보다 정확성이 우선이다.

---

### CPU 사용량이 높은 로직

핵심 지표:

- 요청당 CPU 시간
- 프로세스 CPU 사용량
- 처리량
- p95와 p99
- CPU 포화 이후 오류율
- 프로파일링 결과
- 실행 횟수와 알고리즘 복잡도

검증 논리:

> 계산량 감소
> → 요청당 CPU 시간 감소
> → 같은 CPU에서 처리 가능한 요청량 증가

CPU 사용률만 비교하면 부하량의 영향을 받으므로, 가능하면 요청당 CPU 시간을 함께 본다.

---

### 메모리와 GC 문제

핵심 지표:

- 시간에 따른 힙 사용량
- 부하 종료 후 메모리 회수 여부
- 객체 할당량
- GC 횟수와 정지시간
- OOM 여부
- 처리량별 응답시간

짧은 최대 메모리보다 장시간 실행 시 계속 증가하는지가 중요하다.

---

### 외부 API 또는 네트워크 호출

핵심 지표:

- 외부 호출 횟수와 소요시간
- 전체 요청시간에서 외부 호출이 차지하는 비율
- 타임아웃과 재시도 수
- 연결 풀 사용량
- 외부 장애 시 내부 오류율
- 정상 기능으로 장애가 전파되는지
- 폴백과 서킷 브레이커 동작

이 경우에는 정상 상황뿐 아니라 지연과 실패를 인위적으로 발생시켜야 한다.

---

### 배치 작업

핵심 지표:

- 전체 완료시간
- 초당 처리 건수
- DB CPU와 I/O
- 읽기·쓰기 건수
- 트랜잭션 크기
- 락 대기시간
- 실패 후 재시작 가능 여부
- 온라인 요청에 미치는 영향

배치 자체의 완료시간뿐 아니라 실행 중 온라인 서비스가 안정적인지도 확인한다.

## 5. 지표는 세 단계로 연결한다

좋은 검증은 다음 세 종류의 지표를 연결한다.

### 결과 지표

사용자 또는 시스템이 체감하는 결과다.

- 처리량
- 응답시간
- 오류율
- 작업 완료시간
- 적체량

### 자원 지표

어디에서 한계가 발생하는지 보여준다.

- 앱 CPU
- DB CPU
- 메모리와 GC
- 커넥션
- 스레드
- 디스크·네트워크 I/O

### 원인 지표

기술적 선택이 왜 효과가 있었는지 설명한다.

- 요청당 쿼리 수
- 스캔 행 수
- 캐시 적중률
- 외부 호출 횟수
- 객체 할당량
- 락 충돌 수
- 요청당 CPU 시간

예:

> p95가 감소했다
> → DB CPU가 감소했기 때문이다
> → 요청당 쿼리와 스캔 행 수를 줄였기 때문이다.

응답시간 하나만으로는 개선 원인을 증명하기 어렵다.

### 원인 지표의 분모 — "요청당 평균"은 원인 지표가 아니다

전역 카운터를 요청 수로 나눈 값은 **워크로드 지표**(시스템이 얼마나 일했나)이지 원인
지표(동일 문장 한 번이 얼마나 일했나)가 아니다. 요청 믹스는 부하에 따라 변한다 — 포화로
타임아웃이 나면 후속 요청(스크롤 2페이지 등)이 미발화해 비싼 문장과 싼 문장의 비율이
달라지고, "요청당 평균"이 동일 쿼리가 비싸진 듯한 허상을 만든다.

2026-08-04 실측: 실행당 13.5배 비싼 커서 문장의 비중이 포화에서 16.6%→6.4%로 변해
"요청당 행 읽기 2배 증폭"으로 오독됐고, 플랜 플립 가설까지 세웠다가
`performance_schema` digest의 **실행당** 지표(ROWS_EXAMINED ÷ COUNT_STAR)로 기각됐다
(`load-test/campaigns/2026-08-04_saturation-amplification/`).

플랜 변경·쿼리 회귀 판정의 정본은 ① digest 실행당 값의 구간 비교, ② 동일 파라미터·동일
세션 설정의 EXPLAIN 시점 비교다. 분모에 클라이언트 관점 수치(성공 응답 수)를 쓰지 않는다 —
클라이언트가 포기해도 서버는 일을 계속한다.

## 6. 테스트 유형을 목적에 맞게 선택한다

### 기준 테스트

일정한 부하를 유지해 변경 전후를 비교한다.

용도:

- A/B 구조 비교
- 회귀 확인
- 자원 사용량 비교

### 단계 증가 테스트

부하를 단계적으로 올린다.

```text
50 RPS → 100 RPS → 150 RPS → 200 RPS
```

용도:

- 어느 시점부터 성능이 무너지는지 확인
- 병목 자원 확인
- A와 B의 수용 능력 비교

각 단계에서 확인한다.

- 응답시간이 완만하게 증가하는가
- 오류나 타임아웃이 발생하는가
- 어떤 자원이 먼저 포화되는가
- 부하 증가만큼 처리량도 증가하는가

### 순간 부하 테스트

짧은 시간에 요청이 급증하는 상황을 재현한다.

용도:

- 캐시 만료
- 이벤트 시작
- 알림 발송
- 트래픽 급증
- 오토스케일 반응

### 장시간 안정성 테스트

같은 부하를 오래 유지한다.

용도:

- 메모리 누수
- 커넥션 누수
- GC 악화
- 큐 적체
- 캐시 크기 증가
- 시간 경과에 따른 성능 저하

### 장애 상황 테스트

외부 API 지연, DB 연결 실패, 캐시 장애 등을 주입한다.

용도:

- 타임아웃
- 재시도
- 서킷 브레이커
- 폴백
- 장애 격리
- 복구 능력

---

## 7. A와 B를 공정하게 비교하는 방법

다음 조건을 동일하게 유지한다.

- 실행 환경과 자원 제한
- 애플리케이션 설정
- JVM 설정
- 데이터 크기와 분포
- 캐시 초기 상태
- 워밍업 시간
- 부하 패턴
- 테스트 시간
- 모니터링 방식

권장 순서:

1. 테스트 데이터를 고정한다.
2. 애플리케이션을 워밍업한다.
3. A를 여러 번 측정한다.
4. 같은 조건에서 B를 여러 번 측정한다.
5. 중앙값과 편차를 비교한다.
6. 결과 지표와 원인 지표가 같은 방향인지 확인한다.

한 번의 최고 결과보다 반복 측정의 일관성이 중요하다.

## 8. 구조 A는 실패하고 B는 통과했다는 것을 증명하는 방법

먼저 예상 부하를 정의한다.

> 예상 피크 요청량은 100 RPS이며, 불확실성과 순간 증가를 고려해 2배인 200 RPS를 검증 부하로 정한다.

통과 조건을 정의한다.

- 오류율이 허용 범위 이내다.
- 타임아웃이 발생하지 않는다.
- 응답시간이 테스트 동안 계속 악화되지 않는다.
- CPU, DB, 커넥션 등이 지속적으로 포화되지 않는다.
- 부하가 끝난 뒤 정상 상태로 회복한다.
- 결과의 정확성이 유지된다.

테스트 결과는 다음과 같이 판단한다.

> 구조 A는 150 RPS부터 DB CPU가 포화되고 p95가 급증했으며, 200 RPS에서 타임아웃이 발생했다. 구조 B는 200 RPS를 오류 없이 처리했고 자원 사용량과 응답시간도 안정적으로 유지됐다.

이 결과는 운영 서버의 절대 처리량을 보장하지 않는다. 그러나 동일한 조건에서 B가 요구 부하에 더 적합하다는 근거로 사용할 수 있다.

## 9. 결과를 해석할 때 주의할 점

### 응답시간만 보지 않는다

응답시간이 줄어도 다음 문제가 생겼을 수 있다.

- 오류가 증가했다.
- 작업을 큐로 넘겨 적체시켰다.
- 캐시로 인해 오래된 데이터를 반환한다.
- CPU 대신 메모리를 과도하게 사용한다.
- 평균은 좋아졌지만 일부 요청이 크게 느려졌다.

### 평균만 보지 않는다

최소한 다음을 함께 확인한다.

- p50: 일반적인 요청
- p95: 느린 요청의 경향
- p99: 꼬리 지연
- 오류율과 타임아웃

로컬 환경의 p99는 호스트 노이즈에 민감하므로 절대값보다 반복성, 원인 지표, A/B 차이를 함께 본다.

### 자원 사용률만으로 결론 내리지 않는다

CPU 80%가 반드시 문제인 것은 아니다. 반대로 CPU 30%라고 여유가 충분한 것도 아니다. 락, DB 커넥션, 외부 API 또는 단일 스레드가 병목일 수 있다.

### 오염된 구간을 임의로 제거하지 않는다

호스트 정지 등 명확한 환경 이상이 발생했다면 해당 테스트를 무효 처리하고 다시 실행한다. 결과가 좋아 보이도록 느린 구간만 제거해서는 안 된다.

### 개선의 비용도 기록한다

기술적 선택에는 대개 비용이 따른다.

- 캐시: 정합성과 무효화
- 사전 집계: 최신성 지연
- 비동기 처리: 운영 복잡성과 최종 일관성
- 락: 대기와 처리량 감소
- 인덱스: 쓰기 비용과 저장 공간
- 병렬 처리: CPU와 외부 시스템 부하 증가

개선 효과가 비용보다 큰지까지 판단해야 기술적 선택이 완성된다.

## 11. 핵심 체크리스트

### 테스트 전

- [ ] 해결하려는 문제나 요구사항이 명확하다.
- [ ] 병목 원인에 대한 가설이 있다.
- [ ] 비교할 대안이 있다.
- [ ] 테스트로 증명할 주장이 명확하다.
- [ ] 성공과 실패 조건을 정했다.
- [ ] 예상 부하의 산정 근거가 있다.
- [ ] 주장에 필요한 지표만 선택했다.

### 테스트 중

- [ ] 변경 전후 조건이 동일하다.
- [ ] 충분한 워밍업을 수행했다.
- [ ] 여러 번 반복했다.
- [ ] 오류율과 정확성을 함께 확인했다.
- [ ] 결과 지표와 원인 지표를 함께 수집했다.
- [ ] 부하를 발생시키는 장비가 병목이 아닌지 확인했다.
- [ ] 외부 프로그램이나 공유 환경의 간섭을 확인했다.

### 테스트 후

- [ ] 기술적 선택이 원인 지표를 실제로 변화시켰다.
- [ ] 그 변화가 사용자·시스템 결과로 이어졌다.
- [ ] 예상 부하에서 안정적으로 동작했다.
- [ ] 부하 종료 후 정상적으로 회복했다.
- [ ] 정합성이나 복잡성 같은 비용을 확인했다.
- [ ] 테스트 결과로 말할 수 있는 범위를 넘어서지 않았다.

## 결론

부하 테스트는 기술적 선택을 사후에 꾸미기 위한 도구가 아니라, 선택 과정의 가설을 검증하는 실험이다.

가장 중요한 흐름은 다음과 같다.

```text
요구사항 또는 문제
→ 병목 원인에 대한 가설
→ 해결 대안 비교
→ 성공 조건과 지표 선정
→ 동일 조건에서 검증
→ 결과와 원인 연결
→ 비용과 한계를 포함한 최종 판단
```

운영 환경이 없더라도 다음을 증명할 수 있다면 충분히 합리적인 기술적 근거가 된다.

- 같은 결과를 더 적은 작업량으로 만들었다.
- 동일한 자원에서 더 많은 요청을 안정적으로 처리했다.
- 구조 A가 실패한 요구 부하를 구조 B는 처리했다.
- 데이터나 트래픽 증가에 따른 성능 저하 폭을 줄였다.
- 정확성을 유지하면서 필요한 처리량을 달성했다.
- 장애가 다른 기능으로 전파되는 것을 막았다.

# 부록 A. 이 프로젝트에 적용

§1~11은 범용 지침이다. 아래는 SOLPLY 환경에서 그 지침을 어떻게 구체화했는지의 기록이다.

## A.1 필요한 정밀도는 효과 크기가 결정한다

§7의 "동일 조건 유지"를 어디까지 밀어붙일지는 **증명하려는 효과 크기**로 정한다.
효과가 크면 환경 통제에 시간을 쓸 필요가 없고, 효과가 작으면 로컬에서 주장하면 안 된다.

| 주장하려는 효과 | 대응 |
|---|---|
| **자릿수 차이** (10배 이상, 성공률 3% vs 100%) | 로컬 노이즈로 뒤집히지 않는다. 환경 통제에 시간 쓰지 않는다 |
| **2~5배** | 원인 지표(요청당 statements·CPU)로 교차 확인하면 충분하다 |
| **2배 미만** | 로컬 노이즈와 구분이 어렵다. 원인 지표로만 판정하고 응답시간으로는 주장하지 않는다 |
| **10~20% 개선** | **로컬에서 주장하지 않는다.** 전용 환경이 필요하다 (A.5) |

지금까지의 측정은 대부분 첫 두 행이었다 — v0 기각(성공률 1.6% vs 100%)도, 인덱스 S2b 채택
(성공률 3% vs 100%)도 자릿수 차이였다. 그래서 상태별 1회 측정으로 결론이 났다.

## A.2 세 계층의 지표를 어떤 도구로 얻는가

§5의 3단 구조는 이 프로젝트에서 세 도구에 대응한다.

| §5 분류 | 도구 | 시점 | 산출물 |
|---|---|---|---|
| **결과 지표** | `npx artillery` | 라운드 내내 | `results/reports/*.json` |
| **자원 지표** | `shared/sampler.sh` | 3초 간격 | `results/metrics/*.samples.csv` |
| **원인 지표** | `shared/metrics-snapshot.sh` | 라운드 전/후 1회 | `results/metrics/*.diff` |

Artillery만 돌리면 결과 지표만 남아 **개선의 원인을 증명할 수 없다.** 실행 절차는
[`load-test/README.md`](../../load-test/README.md)에 있다.

## A.3 지표 계약 — 1급 / 참고 / 폐기

로컬 벤치에서 어떤 숫자를 기준선으로 쓸지 미리 정해 둔다. 사후에 고르면 유리한 것만 남는다.

| 구분 | 지표 | 근거 |
|---|---|---|
| **1급 (기준선)** | 성공률·오류, 요청당 statements, 요청당 앱/DB CPU ms, 버퍼풀 hit rate·디스크 읽기, `created_tmp_disk_tables`, `select_scan`, p50, heap | baseline 5회에서 **전부 재현**됨 (요청당 statements 편차 0.1%) |
| **참고 (인용 금지)** | 정상 구간 10초 버킷 p99 중앙값, p95 | 호스트 상태에 흔들린다 |
| **폐기** | 라운드 전체 p99 · max | 5회에서 **16.1배** 흔들림. 호스트 스톨에 오염됨 |

호스트 스톨은 모든 요청을 동시에 지연시키지만 **총 자원 소비량은 바꾸지 않는다** — 그래서
요청당 CPU·statements는 오염된 라운드에서도 보존된다. 이것이 1급 지표를 고른 기준이다.

**실사용 p99는 부하 테스트가 아니라 프로덕션 모니터링에서 읽는다.**
Prometheus + Grafana가 붙어 있고 `application.yml`에
`management.metrics.distribution.percentiles-histogram.http.server.requests: true`가 켜져 있다.

## A.4 실환경 대표성 — prod가 벤치보다 열악하다

로컬을 "실서버보다 후한 환경"으로 착각하면 안 된다. 2026-07-30 기준 실측
(앱 인스턴스 행만 2026-08-05 토폴로지 변경을 반영했다):

| | 로컬 벤치 | 실제 prod |
|---|---|---|
| 앱 인스턴스 | **1대** + nginx edge (2026-08-05 이전에는 2대 + LB) | **1대** (`prod-app`) |
| 리소스 격리 | cgroup (앱 2vCPU/2G, DB 2vCPU/3G) | **제한 없음** — 전부 무제한 경쟁 |
| 한 호스트에 함께 사는 것 | 앱 + DB + Redis + edge | 앱 + DB + Redis + Prometheus + Grafana + **dev 스택 전체** + nginx + certbot |
| MySQL 버퍼풀 | `2G` 명시 | **기본값(128MB)** |
| 앱 ↔ DB 네트워크 | docker bridge | **docker bridge (동일)** |
| 배포 대상 | — | dev·prod가 **같은 EC2 한 대** (`CD.yml`의 `SERVER_PUBLIC_IP` 단일, 공용 `solply-net`) |

> ⚠️ **2026-08-05부로 벤치도 앱 1대다.** 가용성 요구를 철회해 인스턴스를 줄였고 nginx는
> 부하 분산이 아니라 edge로 남겼다(설계 `docs/design/2026-08-05-place-stats-version-rows.md` §6).
> 프로세스 수가 처리량의 직접 인자이므로 **이 시점 이후 수치는 단일 프로세스 재기준선이고,
> 기존 캠페인(2대 + LB)과 절대값을 비교하면 안 된다.** 역설적으로 이 변경은 벤치를 prod에
> 더 가깝게 만든다 — 위 표의 첫 행이 이제 양쪽 다 1대다.

두 가지 규칙이 따라 나온다.

1. **dev 서버에 부하를 쏘지 않는다.** dev와 prod가 같은 EC2에 있어 dev를 마비시키면 prod도 죽는다.
2. **"DB 분리 시 요청당 +6ms" 보정은 조건을 붙여 인용한다.** prod도 앱과 DB가 같은 호스트의
   docker bridge를 쓴다. 그 보정은 **나중에 DB를 분리하면** 필요해지는 계산이다.

반대로 **버퍼풀 128MB는 로컬 부하테스트로 절대 발견되지 않는다.** 이런 항목은 §2의 원칙대로
부하 테스트가 아니라 **설정 점검**으로 잡는다:

- [ ] prod MySQL 버퍼풀이 기본값(128MB)인가 → 데이터 규모 대비 상향 검토
- [ ] prod 컨테이너에 `mem_limit`이 없는가 → 앱이 DB 메모리를 밀어내 OOM 나는 경로
- [ ] Hikari 풀 크기 × 인스턴스 수 ≤ MySQL `max_connections`인가
- [ ] 운영 프로파일에서 쿼리 로깅(p6spy)이 꺼져 있는가

## A.5 전용 환경으로 승급하는 조건

아래 중 하나에 해당할 때만 별도 인스턴스를 띄운다. **dev/prod EC2는 건드리지 않는다.**

- SLO나 알람 임계값을 문서·모니터링에 확정해 넣어야 한다
- 인스턴스 체급·대수를 정해야 한다
- 쓰기·배치 경로 성능을 재야 한다 (fsync·IOPS가 로컬과 근본적으로 다르다)
- 장애·복구 시나리오를 검증해야 한다

운영 방식: **버스트 없는 인스턴스 타입**을 쓰고(t계열은 CPU 크레딧 때문에 측정값이 시간에 따라
변한다), 부하생성기는 **별도 인스턴스**에 두고, 상시 유지하지 않고 필요할 때 몇 시간만 띄우고,
스펙·설정을 prod와 동일하게 맞춘다(버퍼풀·커넥션 수 포함 — 기본값 차이가 결과를 뒤집는다).

## A.6 검토했으나 채택하지 않은 통제 수단

로컬 노이즈를 더 강하게 통제하는 방법들을 검토했고 비용 대비 이득이 없어 기각했다.
같은 논의를 반복하지 않기 위해 이유를 남긴다.

| 방안 | 기각 이유 |
|---|---|
| `cpuset`으로 컨테이너를 코어에 고정 | VM의 **vCPU에 고정될 뿐 물리 P/E 코어에는 고정되지 않는다.** Docker Desktop 하이퍼바이저 아래는 제어 밖이고, 오히려 스케줄러 선택지를 줄여 나빠질 수 있다. 실측 근거 없이 권장할 수준이 아니다. 또 `cpus: 2`(체급 재현)를 유지하는 한 **CFS 쿼터 판정이 남아 쓰로틀도 사라지지 않는다** |
| Docker Desktop VM vCPU 하향 | 호스트에 코어를 남겨 부하생성기와의 경합을 줄이는 효과는 있으나, 재부팅·프로세스 정리로 얻는 개선과 겹친다. 싼 방법을 먼저 쓴다 |
| 오염된 10초 버킷만 제외 | 낙관 편향 (§9). 라운드 전체를 무효 처리하고 재실행한다 |
| dev 서버 배포 후 측정 | dev와 prod가 같은 EC2에 산다 (A.4) |
| 매 커밋마다 정교한 환경 통제 | A·B 목적에는 과하다. **재부팅 + 무거운 프로세스 종료 후 변경 전후 연속 측정**이면 대개 충분하다 |

### 알고 있으나 해결하지 않은 한계

| 한계 | 영향 | 상태 |
|---|---|---|
| 부하생성기(Artillery)가 측정 대상과 같은 호스트에서 돈다 | §11의 "부하 발생 장비가 병목이 아닌지" 항목을 완전히 만족하지 못한다 | 미해결. 1급 지표로 판정하는 한 치명적이지 않아 보류 |
| `sampler.sh`가 3초마다 `docker exec mysql`을 2회 실행 | 계측이 DB 컨테이너 CPU를 소비한다 (200초 라운드 ≈ 130회) | 미해결. 경량화 예정 |
| 앱과 DB가 같은 커널·디스크를 공유 | 호스트가 스왑하면 둘이 동시에 멈춘다 | 구조적. **prod도 같은 구성이라 대표성 손실은 아니다** |
