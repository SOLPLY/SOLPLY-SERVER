## 0. 이 문서의 위치

원 과제는 `TODO.md`의 한 줄이다.

> 스캔 범위 개선 — 감쇠 특성상 기여가 0에 수렴하는 옛 행을 점수 집계에서 제외.
> (A) CASE 게이트(스캔 유지, 산술만 생략) / (B) 스캔 분리 + created_at 선두 인덱스.
> 옛 날짜 비중 증식 시드로 배치 소요 커브 + top-K 순위 동치 검증, **사전 등록 후**.
> 카운트는 전 기간 집계가 필요해 컷오프는 점수 축만

"사전 등록 후"가 이 문서다. 착수 승인은 §11의 게이트에서 받는다.

### 0.1 사전 탐침을 캠페인 결과와 구분한다

2026-08-06에 읽기 전용 조사를 한 번 돌렸고, 거기서 나온 수치가 이 설계를 크게 바꿨다.
그 조사는 **정식 캠페인이 아니다.** 구분해 두지 않으면 나중에 두 종류의 숫자가 섞인다.

| | 사전 탐침 (2026-08-06) | 이 문서가 등록하는 캠페인 |
|---|---|---|
| 성격 | 읽기 전용 조사. `EXPLAIN` / `EXPLAIN ANALYZE` / `SELECT`만 | 정식 A/B 측정 |
| 대상 | **북마크 파생 테이블 SELECT 단독** | `INSERT ... SELECT` 배치 전체 |
| 시드 | 현행 벤치 시드 1종 | 단계 시드 4~5종 (§4) |
| 반복 | 3회, 라운드 간 하향 드리프트 잔존 | 첫 회 폐기 후 3회 중앙값, 유효성 판정 선행 |
| 캠페인 디렉터리 | 없음 (원자료 미보존) | `load-test/campaigns/<날짜>_popular-score-scan-cutoff/` |
| 지위 | **가설의 출처. 판정 근거로 인용 금지** | 판정 근거 |

이 문서에서 **[사전 탐침]** 태그가 붙은 값은 전부 "그래서 이걸 재기로 했다"의 근거이지
"그래서 이렇게 결론 났다"의 근거가 아니다. 캠페인이 같은 값을 재현하지 못하면
**재현 실패 자체가 결과**이고, 사전 탐침 쪽을 버린다.

### 0.2 결론을 미리 정하지 않는다

사전 탐침의 방향은 컷오프에 우호적이지 않았다. 그래도 이 캠페인은 "컷오프가 안 된다"를
증명하러 가는 것이 **아니다**. 양쪽 모두 사전 등록된 성공 결론이다.

| 결론 | 성공인가 |
|---|---|
| 어떤 T·변형이 정확성·성능 게이트를 모두 통과 → 채택 | **성공** |
| 정확성은 통과하나 성능 이득이 게이트 미달 → **현행 전체 스캔 유지** | **성공** (근거 있는 유지) |
| 정확성 게이트를 통과하는 T가 아예 없음 → **현행 전체 스캔 유지** | **성공** (기각 근거 확보) |
| 게이트를 못 정하거나 시드·이식 검증이 깨져 판정 불가 | 실패 (§10.3) |

`docs/perf/2026-07-31-hybrid-score-formula.md`가 세운 규약을 계승한다 — **역방향 결론도
캠페인의 성공이다.** 지금 시점에서 가장 그럴듯한 결론이 "현행 유지"라는 사실은,
그 결론을 미리 적어 두는 이유이지 측정을 건너뛸 이유가 아니다.

## 1. 문제 · 원인 가설 · 기술적 선택 · 검증할 주장 · 성공 조건

가이드 §3의 다섯 항목이다.

### 1.1 문제

배치는 매시 북마크 원본을 **전량** 훑는다. 반감기 90일 감쇠 아래에서 1년 넘은 행의 기여는
사실상 0인데도 그 행을 매시 읽는다. 데이터가 쌓일수록 배치 비용이 같은 속도로 늘어난다.

블로그가 이 과제를 다음 질문으로 남겨 뒀다 —
`docs/blog/2026-08-03-popular-sort-aggregation.md:206-215`.

### 1.2 원인 가설

배치 소요의 지배 항이 북마크 축 파생 테이블이다.

- 배치 전체 **6,049ms** 중 리뷰 축은 **117ms(1.9%)**, 북마크 축이 **6,051ms** [실측,
  `docs/perf/2026-07-31-place-stats-batch.md:99-104`, `:133-136`]
- 북마크 축이 훑는 행 **10.4M → 6,000 그룹** [실측, 같은 문서]

즉 개선의 표적은 북마크 파생 테이블 하나로 좁혀진다.

### 1.3 기술적 선택 (후보)

점수 축(`decayed`)에만 시간 하한을 넣는다. 카운트 축(`cnt`)은 전 기간을 유지한다.
후보 셋과 조건부 보조 변형 둘은 §3에 정의한다.

### 1.4 검증할 주장

> 옛 행을 점수 집계에서 제외하면 **top-K 순위를 바꾸지 않으면서** 배치 소요를 줄일 수 있고,
> 그 절감분은 옛 행 비율이 커질수록 커진다.

이 문장은 셋으로 쪼개져 각각 게이트가 붙는다.

1. **순위 불변** — 정확성 게이트 G1·G2·G3 (§7)
2. **소요 절감** — 성능 게이트 P1·P2 (**§10.1**)
3. **성장 비용 억제** — 커브 게이트 P3 (**§10.1**). 여기가 이 과제의 진짜 주장이다

> 절 배치를 헷갈리지 말 것 — **§8은 무엇을 어떻게 재는가(측정 계약)이고, 게이트의 통과선은
> 전부 §10에 있다.** 두 절이 같은 지표를 다루지만 역할이 다르다.

### 1.5 성공 조건

지표 정의는 §8, 통과선은 §10에 절대 수치로 고정한다.
**효과 크기 사전 가늠**(가이드 부록 A.1)은 이렇다.

| 후보 | 예상 효과 크기 | 그래서 무엇으로 판정하나 |
|---|---|---|
| B (CASE 게이트) | **2배 미만** — 사전 탐침 −2.3~−28% | 응답시간·소요로 단독 주장 **금지**. 원인 지표(M2·M3) 동반 필수 |
| C (스캔 분리) | 현 인덱스에서는 **악화** [사전 탐침 +12.9~27.0%] | 같음 |
| 커브 기울기 (P3) | 단계 간 배수라 **2배 이상 가능** | 여기서만 소요 절대값이 1급 근거가 된다 |

가이드 A.1의 "2배 미만은 로컬 노이즈와 구분이 어렵다"가 이 캠페인의 대부분에 적용된다.
**그래서 판정의 무게중심을 커브(P3)에 두고, 단일 점의 소요는 원인 지표로만 뒷받침한다.**

## 2. 현재 구조 분석 — 쿼리 · 인덱스 · 트랜잭션

### 2.1 대상 쿼리

배치 전체가 단일 `INSERT ... SELECT`다 (`PlaceStatsRepository.java:105-152`).
논점은 그중 북마크 축 파생 테이블 하나다 — `PlaceStatsRepository.java:125-135`.

```sql
LEFT JOIN (
    SELECT bm.target_id AS place_id,
           COUNT(*) AS cnt,                                 -- 카운트 축: 전 기간 필수
           SUM(POW(0.5,
               TIMESTAMPDIFF(SECOND, bm.created_at, :calculatedAt)
                   / 86400.0 / :halfLifeDays)) AS decayed   -- 점수 축: 컷오프 대상
    FROM bookmarks bm
    WHERE bm.target_type = 'PLACE'
      AND bm.created_at <= :calculatedAt
    GROUP BY bm.target_id
) b ON b.place_id = p.id
```

**한 파생 테이블이 두 축을 동시에 낸다.** 이 사실이 후보를 가르는 축 전부다.
컷오프는 점수 축에만 걸 수 있는데
(설계서 `docs/design/2026-08-05-place-stats-version-rows.md:129-130`,
그리고 `cnt`가 `bookmark_count`로 나가 응답에 노출된다 — `PlaceStats.java:64-65`),
두 축이 한 `GROUP BY`에 묶여 있어 컷오프를 걸려면 **묶음을 푸는 것부터** 해야 한다.

점수 공식 전문:

```
score = W_B · LN(1 + Σ북마크 0.5^(경과일/H))
      + W_R · ((Σ평점 + m·C) / (리뷰수 + m) − C)
W_B = 1.0, W_R = 2.0, H = 90일, m = 5   (PlaceStatsProperties 기본값)
```

컷오프는 **첫 항의 Σ에만** 닿는다. 리뷰 항은 이 캠페인에서 변하지 않는다 — 그러나
G3의 분모(인접 순위 간격)를 만드는 데 참여하므로 값이 정확해야 한다(§12.1).

### 2.2 지우면 안 되는 계약 셋

| 계약 | 위치 | 컷오프 설계에 주는 제약 |
|---|---|---|
| `created_at <= :calculatedAt` **상한** | `PlaceStatsRepository.java:39-41` | 멱등성 계약이다. 없으면 미래 시각 행에서 `POW(0.5, 음수) > 1`이 되어 감쇠가 증폭이 된다. **컷오프는 하한 추가이지 상한 교체가 아니다** |
| `LN(1 + Σ)`의 정의역 | `:74-75` | `Σ ≥ 0`에 의존. 컷오프로 Σ가 줄어도 0 이상이라 안전은 유지된다 |
| 인덱스 전제 | `:81-84` | 북마크 축은 `idx_bookmark_target`(V23), 리뷰 축은 `idx_place_reviews_place_created_rating`(V22)로 각각 인덱스 전용 스캔이어야 한다 |

여기에 하나 더: **컷오프 날짜는 반드시 `:calculatedAt`에서 파생시킨다.** `NOW()`를 쓰면
같은 `calculatedAt` 재실행이 다른 결과를 내 멱등성이 깨진다 — 그 자체로 §10.3의 무효 조건이다.

### 2.3 인덱스 — 컷오프가 range 경계가 되지 못한다 ⚠️

현행 `idx_bookmark_target`은 **(target_type, target_id, created_at)**이다 (V23).
`created_at`이 세 번째, 즉 **`GROUP BY` 키인 `target_id`보다 뒤**에 있다.
전 장소 집계라 `target_id`에 등호 술어가 없으므로, `created_at`은 인덱스 탐색 경계가 될 수
없고 **`Filter`로만** 붙는다.

**[사전 탐침]** `EXPLAIN FORMAT=TREE`가 그대로 보여 줬다 — 컷오프를 넣어도
`Covering index lookup on bm using idx_bookmark_target (target_type='PLACE')`가 여전히
전체를 읽고, 컷오프는 그 **위에서** 행을 버린다. **읽는 행이 1행도 줄지 않는다.**
세 후보 전부 인덱스가 읽은 행이 **10.4M로 동일**했다.

> 옵티마이저 cost 수치는 137,377 vs 367,521로 개선처럼 읽히지만 이는 추정치이고
> 실측 rows는 같다. **cost를 근거로 인용하지 않는다.**

이것이 TODO 원문의 "(B) 스캔 분리 + **created_at 선두 인덱스**"가 왜 선두를 요구했는지의
답이자, 그 인덱스 없이 C를 재면 무엇을 재는지 모르게 되는 이유다.

부수 관찰 하나 — **[사전 탐침] 벤치 DB에 COURSE 북마크가 0건이다.**
`idx_bookmark_target` 선두 컬럼의 카디널리티가 1이고, `target_type='PLACE'` 등호의
선택도가 0이라 스캔 10.4M = 테이블 전체다. 운영에서 COURSE가 섞이면 그만큼 걷힌다.
**세 후보의 상대 비교는 셋 다 같은 등호를 쓰므로 영향받지 않지만, 절대값은 비관적이다.**
캠페인에서 이 상태를 그대로 둘지는 §11 게이트 항목 5.

### 2.4 트랜잭션 · 락

배치 한 회차는 **한 트랜잭션의 세 문장**이다 (`PlaceStatsBatchProcessor.java:98-112`):
① `upsertAll` → ② `shiftGeneration` → ③ `deleteVersionsOtherThan`.

| 성질 | 값 | 근거 |
|---|---|---|
| 격리 수준 | `READ_COMMITTED` **필수** | `PlaceStatsBatchProcessor.java:47` |
| RR이면 | 소스 테이블에 shared next-key 락 **10,638,001건** (RC는 12,640) | [실측] `docs/perf/2026-07-31-place-stats-batch.md:212-216` |
| RC에서 남는 차단 | `places` FK 부모 S락 **6,320건**, 커밋까지 유지 | [실측] 같은 문서 `:234-237` |
| 전제 | `binlog_format = ROW` (아니면 `ERROR 1665`) | `PlaceStatsRepository.java:56` |

**컷오프가 이 프로파일을 바꿀 수 있다.** 스캔 범위가 줄면 RC에서의 락 프로파일도 달라질 수
있는데 사전 탐침은 덤프하지 않았다. 캠페인 지표 M4에 락 카운터를 넣는 이유가 이것이다.

한 가지 주의 — **격리 수준은 프로세서가 트랜잭션을 새로 시작할 때만 적용된다.**
이미 열린 트랜잭션에 참여하면 스프링이 지정을 무시한다
(`PlaceStatsBatchProcessor.java:25-29`). 캠페인에서 배치를 SQL로 직접 돌리는 라운드는
세션 격리 수준을 명시적으로 `READ COMMITTED`로 맞춰야 앱 경로와 같은 조건이 된다.

### 2.5 컷오프가 스키마에 요구하는 것

**`place_stats`에는 아무것도 요구하지 않는다.** `bookmark_count`는 전 기간 집계를 유지하고
`popular_score`는 값만 달라진다. 컬럼 추가·인덱스 변경 불필요. 논점은 전적으로
`bookmarks` 읽기 쪽이다. (`PlaceStatsProperties`에 `score-cutoff-days` 프로퍼티를 더하는
것은 채택이 결정된 **후의** 일이며, 이 캠페인의 범위가 아니다.)

### 4.2 비율만으로는 부족하다 — 순위는 점수 손실의 **편차**에만 반응한다

#### 부호 규약 — 문서 전체에서 이 하나만 쓴다

컷오프는 점수를 **깎기만** 한다. 그래서 부호가 헷갈리지 않게 **양수인 손실 하나**로 통일한다.

```
손실  L_p = score_baseline,p − score_cutoff,p  ≥ 0
```

- **L은 항상 0 이상이다.** 클수록 많이 깎였다는 뜻이다.
- `Δscore`(= cutoff − baseline, 음수)라는 표기는 **이 문서에서 쓰지 않는다.**
- 표의 열 이름, 게이트 식, 지표 M5가 전부 `L` 기준이다.

#### 닫힌 형태

장소 p의 잘린 질량 비율을 `f_p`(= 컷오프로 사라진 감쇠 질량 ÷ 전체 감쇠 질량)라 하면

```
L_p = W_B · [ln(1 + S_p) − ln(1 + S_p(1 − f_p))] ≈ −W_B · ln(1 − f_p) ≥ 0   (S_p ≫ 1)
```

`−ln(1−f_p)`의 마이너스 부호는 **L을 양수로 만들기 위한 것**이지 손실이 음수라는 뜻이 아니다.
`0 < f_p < 1`이므로 `ln(1−f_p) < 0`이고, 따라서 `L_p > 0`이다.

**`f_p`가 모든 장소에서 같으면 L은 공통 상수 오프셋이고 순위는 한 칸도 안 바뀐다.**
로그가 컷오프의 손해를 거의 상수 이동으로 바꾸기 때문이다.

현행 시드가 정확히 그 상태다 — 장소 가중치가 시각과 무관해 유입률이 548일 내내 시간
불변이고, `docs/perf/2026-07-31-hybrid-score-formula.md` §6.3이 이를
`momentum/bookmark_count = 0.358 ± 0.020`으로 [실측]했다.

> **이 시드에서 top-K 동치를 확인해도 아무것도 증명하지 못한다.** hybrid가 α에 대해 겪은
> "판정 불가"(§7.1)와 같은 함정이고, 이번에는 방향이 반대라 더 위험하다 —
> **"컷오프해도 순위가 안 바뀐다"는 잘못된 안전 신호가 나온다.**

그래서 단계 시드는 **두 축**을 동시에 만든다.

- **축 1 — 전역 비율 R**: 배치 소요 커브의 x축. 성능 게이트(P3)용.
- **축 2 — 장소별 이질성 ρ**: `f_p`가 장소마다 갈려 `L_p`에 산포가 생기게 만든다. 정확성 게이트(G)용.
  `ρ = 최근 창 유입률 ÷ 평시 유입률`. ρ=1이 현행.

## 5. 컷오프가 제외하는 최대 기여도 — 산술 상한

게이트를 세우려면 "최악의 경우 얼마나 틀릴 수 있나"가 먼저 있어야 한다.
이 절은 **측정이 아니라 감쇠식에서 그냥 나오는 상한**이다. 시드나 환경과 무관하다.

### 5.1 단일 행의 상한

컷오프 T보다 오래된 행 하나가 감쇠 합 `S_p`에 넣을 수 있는 최대 기여는 **나이가 정확히 T일
때**이고, 그 값은 `0.5^(T/H)`다 (H = 90일). T보다 오래될수록 기여는 단조 감소한다.

| T (일) | T/H (반감기) | **단일 행 최대 기여** `0.5^(T/90)` |
|---:|---:|---:|
| 90 | 1.0 | 0.500000 |
| 180 | 2.0 | 0.250000 |
| 270 | 3.0 | 0.125000 |
| 360 | 4.0 | 0.062500 |
| 365 | 4.06 | 0.060140 |
| 450 | 5.0 | 0.031250 |
| 540 | 6.0 | 0.015625 |
| 630 | 7.0 | 0.007813 |
| 720 | 8.0 | 0.003906 |

### 5.2 장소별 상한

장소 p에서 T보다 오래된 행이 `n_p`개면, 잘려나가는 질량은

```
cut_p ≤ n_p × 0.5^(T/H)
```

이고, §4.2의 부호 규약대로 **손실 L_p(양수)**는

```
L_p = W_B · [ln(1 + S_p) − ln(1 + S_p − cut_p)] = −W_B · ln(1 − cut_p/(1 + S_p)) ≥ 0
```

**이 상한은 실무적으로 느슨하다** — `n_p`개가 전부 정확히 나이 T일 수는 없기 때문이다.
그래서 게이트에는 상한이 아니라 **§7의 실측 L 분포**를 쓴다. 상한의 쓸모는
"측정값이 이 선을 넘으면 계산이 틀린 것"이라는 **sanity check**다 — M5의 산출값이
`n_p × 0.5^(T/H)` 기반 상한을 넘으면 작업 테이블이 잘못됐다는 뜻이고 §10.3의 무효 조건이다.

### 5.3 T 후보별 전역 기여 손실

#### 기호 — §4.4의 `ρ`와 섞지 말 것

| 기호 | 뜻 | 범위 |
|---|---|---|
| `r_T` | T에서 **남는 행** 비율 | 0~1 |
| `g_T` | T에서 **남는 기여(감쇠 질량)** 비율 | 0~1 |
| `f_T` | T에서 **잘린 기여** 비율 `= 1 − g_T`. §4.2의 `f_p`를 전역으로 집계한 값 | 0~1 |
| `L_T` | 전역 점수 손실 `= −W_B · ln(g_T) ≥ 0` (§4.2 규약) | ≥ 0 |

**`ρ`는 §4.4의 장소별 유입률 이질성 전용이다.** 여기서는 쓰지 않는다.

#### **[사전 탐침] 현행 벤치 분포 기준** (§4.1 표에서 유도)

| T | 남는 행 `r_T` | 남는 기여 `g_T` | **잘린 기여 `f_T`** | **전역 손실 `L_T`** (양수) |
|---|---:|---:|---:|---:|
| 90일 | 0.319 | 0.689 | **31.1%** | **0.373** |
| 180일 | 0.495 | 0.872 | 12.8% | 0.137 |
| **270일** | 0.638 | 0.946 | **5.4%** | **0.0555** |
| 360일 | 0.764 | 0.978 | 2.2% | 0.0222 |
| 450일 | 0.878 | 0.9925 | 0.75% | 0.00753 |
| 540일 | 0.983 | 0.9993 | 0.07% | 0.0007 |

#### **[해석] 창을 1,095일(3년)로 늘렸을 때** (`k=1.6` 유지, 이질성 없는 균질 분포 기준)

| T | 옛 행 비율 `1 − r_T` | 잘린 기여 `f_T` | **전역 손실 `L_T`** (양수) |
|---|---:|---:|---:|
| 365일 | 49.7% | 2.57% | 0.0260 |
| 450일 | 42.6% | 1.25% | 0.0126 |
| 540일 | 35.7% | 0.59% | 0.0059 |
| 630일 | 29.2% | 0.28% | 0.0028 |
| 720일 | 23.1% | 0.13% | 0.0013 |

**창을 늘리면 "많은 행을 건너뛰면서 기여는 거의 안 버리는" 구간이 실제로 생긴다.**
T=540일에서 행의 35.7%를 건너뛰고 잘린 기여가 0.59%다. 컷오프가 성립할 여지가 있다면
여기다 — 그리고 §4.3의 단계 시드가 만드는 것이 정확히 이 구간이다.

> 위 표의 **전역** 손실 `L_T`는 순위를 판정하지 못한다(§4.2). 순위를 흔드는 것은 `L`의
> 평균이 아니라 **장소별 `L_p`의 산포**다. 그 산포는 §7이 잰다.

### 5.4 등록하는 T 후보

`T ∈ {270, 365, 450, 540, 630, 720}` (일). 여섯 점.

- 하단 270·365는 "이득은 크나 정확성이 의심스러운" 구간이다 — 기각될 가능성이 높지만
  **기각 근거를 남기기 위해** 재야 한다.
- 상단 630·720은 "정확하지만 아낄 게 있나" 구간이다.
- 90·180은 등록하지 않는다. 전역 손실 `L_T`가 0.137 이상이라 §7의 G3을 통과할 가능성이
  실질적으로 없고, 라운드 수를 늘릴 뿐이다. **사후에 추가하지 않는다** — 필요해지면
  그 사실 자체를 별도 기록으로 남기고 새 사전 등록을 쓴다.

## 6. 작업 테이블 — 원본을 한 번만 스캔한다

`docs/perf/2026-07-31-hybrid-score-formula.md` §4.1이 같은 문제(점수 공식 변경 → top-K 동치
판정)를 이미 풀었다. 그 절차를 그대로 가져온다.

### 6.1 절차

1. **원본 1회 스캔 → 작업 테이블.** `place_id × 나이 버킷(1일 단위)`으로 감쇠 합을 한 번
   만들면 **모든 컷오프 T가 접미 합**이 된다. 후보 T 여섯 개를 원본 재스캔 없이 평가한다.
2. **이식 검증.** 작업 테이블로 컷오프 없이(T=∞) 재계산한 `popular_score`가 실제
   `place_stats`와 일치해야 한다. hybrid 선례는 불일치 0건, 최대 오차 5.0e-7
   (`DECIMAL(18,6)` 반올림) [실측].
   **불일치하면 캠페인 전체 무효다** — 공식이 어긋나면 나머지 전부가 무의미하다.
   이 검증이 §3.1의 B·C 미확인 항목(NULL 전파, `LEFT JOIN` 조합 변화)도 함께 잡는다.
3. **감쇠 기준 시각을 상수로 고정.** `NOW()` 금지 — 재현성.
4. **카운트 축 불변 단언.** 전 장소에서 `cnt` 불일치 **0건**. 컷오프가 `bookmark_count`에
   닿지 않았음을 정확성 게이트와 별개로 확인한다.

### 6.2 이 절차가 있어야 하는 이유

정확성 게이트(§7)는 T 여섯 개 × 대상 네 개 × K 두 개 = 48조합을 평가한다.
매번 원본 10.4M~26.9M 행을 다시 훑으면 캠페인이 성립하지 않는다.
그리고 **이식 검증이 없으면 "재계산한 점수"와 "배치가 실제로 쓴 점수"가 같다는 보장이 없어
G1~G3의 판정 대상이 무엇인지 알 수 없다.**

## 7. 정확성 검증 — 점수 오차와 top-K

### 7.0 판정 순서 — 정확성이 성능보다 앞선다

가이드 §4 "동시성 제어" 절의 원칙("성능보다 정확성이 우선")을 그대로 적용한다.
**G를 통과한 T들 중에서만 P를 본다.** 반대로 하면 결과에 맞춰 T를 고르게 된다.

### 7.1 평가 대상과 K

hybrid §8.2가 스스로 지적한 결함(후보 100에 Top-50 기준은 절반이 통과라 지나치게 관대)을
고쳐, K를 후보 수의 10~20%로 잡는다.

| 대상 | 후보 수 | K |
|---|---:|---|
| 강남 (leaf 301) | ~100 | 10, 20 |
| 홍대·합정 (310) | ~100 | 10, 20 |
| 건대·성수 (306) | ~100 | 10, 20 |
| 서울 (leaf 301~318) | ~1,800 | 50, 100 |

### 7.2 게이트

| # | 조건 | 판정 |
|---|---|---|
| **G1** | 전 대상 × 전 K에서 컷오프 전후 **Top-K 집합이 완전 동일** (겹침 K/K) | 하나라도 미달 → 해당 T **기각** |
| **G2** | Top-K **내부 최대 순위 이동 ≤ 1칸** 그리고 **Kendall τ ≥ 0.99** | 미달 → 해당 T 기각 |
| **G3** | `2 × max_p abs(δ_p) < min_{1≤i≤K}(score_i − score_{i+1})` — `δ_p`는 **손실 `L_p`의 중심화 잔차**(§7.3), 우변은 기준선 랭크 1..K+1의 최소 인접 간격 | 미달 → 해당 T 기각 |

**G3이 G1·G2의 상위 개념이다.** G3이 성립하면 어떤 쌍도 순서가 뒤집힐 수 없으므로
집합·순서 보존이 **수학적으로 보장**된다. G1·G2는 그 보장의 경험적 확인이자, G3이 깨졌을 때
**실제 피해 크기**를 재는 장치다. 셋 다 등록하는 이유가 그것이다.

### 7.3 중심화가 필수다

§4.2의 손실 `L_p`(양수)를 중앙값으로 중심화한 **잔차**가 판정 대상이다.

```
δ_p = L_p − median_p(L_p)
```

`δ_p`는 부호가 양쪽으로 갈린다 — 중앙값보다 많이 깎인 장소가 양수, 덜 깎인 장소가 음수다.
그래서 게이트는 절댓값 `|δ_p|`를 쓴다.
(표 안에서는 마크다운 열 구분자와 겹치지 않도록 같은 값을 `abs(δ_p)`로 적는다.)

**공통 오프셋은 순위를 안 바꾼다**(§4.2). `max L_p`로 판정하면 통과 가능한 T를 부당하게
기각한다. 예를 들어 §5.3의 T=270일 전역 손실 `L_T = 0.0555`는 그 자체로는 순위와 무관하고,
문제가 되는 것은 그 값의 **장소 간 산포**뿐이다.

### 7.4 사전 등록 예상 — 측정 전에 박아 둔다

**[해석]** §4.4의 ρ 분포(창 1,095일, T=365, H=90)에서 나오는 **손실 `L_p`의 산포**
(전부 양수 — §4.2 규약):

| ρ (유입률 이질성) | 잘린 질량 `f_p` | **손실 `L_p = −ln(1−f_p)`** |
|---:|---:|---:|
| 0.3 (CHILLED) | 9.05% | **0.0949** |
| 0.5 | 5.63% | 0.0580 |
| 0.7 | 4.09% | 0.0418 |
| 1.0 (STEADY) | 2.90% | 0.0294 |
| 1.5 | 1.95% | 0.0197 |
| 2.5 (TRENDING) | 1.18% | **0.0119** |

**식은 옛 행에 치우친 장소(ρ 작음)가 더 많이 깎인다는 것을 그대로 보여 준다** —
`L`이 CHILLED에서 가장 크고 TRENDING에서 가장 작다.

산포 폭은 `0.0949 − 0.0119 = 0.083`이다. 그러나 **G3이 쓰는 값은 산포 폭이 아니라
§7.3이 정의한 중앙값 중심화 잔차**다. 장소 비중이 CHILLED 10 / SLOWING 15 / FADING 15 /
STEADY 40 / WARMING 15 / TRENDING 5(%)이므로 50번째 백분위는 STEADY 구간(누적 40~80%)에
떨어지고, `median(L_p) = 0.0294`다. 따라서

```
max_p |δ_p| = max(|0.0949 − 0.0294|, |0.0119 − 0.0294|) = 0.0655
```

> 중심을 **중앙값이 아니라 최소·최대의 중간(midrange)**으로 잡으면 0.042가 나온다.
> §7.3이 중앙값을 지정했으므로 **0.0655가 이 문서의 값이다.** 두 값이 1.6배 차이 나고
> 아래 예상의 방향까지 바꾸므로, 중심화 방식을 바꾸려면 §7.3부터 고쳐야 한다.

비교 대상은 **인접 순위 간격**이다. 동네 내 Zipf(0.9)에서 `decayed ∝ rank^-0.9`이므로
랭크 r과 r+1의 점수 차는 `0.9 · ln((r+1)/r)` **[해석]**:

| 경계 랭크 | 인접 간격 (leaf 100후보) |
|---:|---:|
| K=10 | 0.086 |
| K=20 | 0.044 |
| K=50 | **0.018** |

#### **[해석]** T별 G3 통과 예상

잔차는 꼬리 질량을 따라 `max|δ_p|(T) ≈ 0.0655 × 0.5^((T−365)/90)`로 줄어든다.
G3은 `2 × max|δ_p| < 인접 간격`이므로:

| T | `max abs(δ_p)` | `2 × max abs(δ_p)` | K=10 (0.086) | K=20 (0.044) | K=50 (0.018) |
|---:|---:|---:|:---:|:---:|:---:|
| 365일 | 0.0655 | 0.131 | ✗ | ✗ | ✗ |
| 450일 | 0.0341 | 0.068 | ✓ | ✗ | ✗ |
| 540일 | 0.0170 | 0.034 | ✓ | ✓ | ✗ |
| 630일 | 0.0085 | 0.017 | ✓ | ✓ | **✓ (아슬아슬)** |
| 720일 | 0.0043 | 0.0085 | ✓ | ✓ | ✓ |

> **[해석] 사전 등록 예상 1 — T=365일 컷오프는 K=10에서도 G3을 깬다.**
> (중앙값 중심화 기준 2×0.0655 = 0.131 > 0.086. midrange로 계산했다면 "K=10은 통과"로
> 잘못 읽혔을 자리다.)
>
> **[해석] 사전 등록 예상 2 — 서울(K=50)까지 안전한 컷오프는 T ≈ 620~630일
> (약 7 반감기)에서 시작한다.** 동네 단위(K=10)만 보면 T ≈ 420일부터다.
> T=630일에서 1,095일 창 기준 건너뛸 수 있는 행은 **29.2%**다(§5.3).

두 예상이 이 캠페인의 진짜 논점이다. **틀리면 틀린 대로 기록한다** — 이것이 예상을 측정
전에 적어 두는 이유다. 특히 예상 2가 맞으면 결론은 "컷오프는 유효하나 TODO가 암묵적으로
상정한 1년보다 훨씬 보수적인 지점에서만"이 되고, 그 경우 §9의 분리 판단이 다시 열린다.
반대로 **K=50이 끝까지 안 열리면 서울 단위 조회에서는 컷오프를 쓸 수 없다는 결론**이 되고,
그것도 §0.2의 "현행 유지"에 해당하는 성공적 결론이다.

| | M1-a (전체) | M1-b (점수 집계 SQL) |
|---|---|---|
| 답하는 질문 | **배치 창이 얼마나 길어졌나 / 짧아졌나** — 운영이 겪는 값 | **컷오프가 실제로 건드린 부분이 얼마나 줄었나** — 개선의 원인 |
| 컷오프가 닿나 | 일부만 | 전부 |
| 게이트 | P1 (§10.1) | P1의 하위 조건 + P2의 산술 일치 |

**둘을 하나로 합치면 컷오프의 효과가 불변 부분에 희석돼 판정이 흐려진다.**
배치 전체에는 컷오프가 닿지 않는 항이 여럿 붙어 있다 — 리뷰 축 **117ms** [실측,
`docs/perf/2026-07-31-place-stats-batch.md:133-136`], `places` 조인, `INSERT` 쓰기,
FK 부모 S락 6,320건, 그리고 V29가 더한 메타 시프트와 옛 버전 `DELETE`.
반대로 M1-b만 재면 "배치가 실제로 빨라졌다"를 말할 수 없다 — 사전 탐침이 정확히
그 상태였고(§0.1의 대상 행), §12.3이 값을 섞지 말라고 경고하는 이유가 그것이다.

**그래서 둘 다 잰다. 그리고 P2에서 두 값이 산술적으로 맞물리는지 확인한다** —
`M1-a 절감분 ≈ M1-b 절감분`이 성립해야 절감이 점수 집계에서 왔다는 말이 성립한다.
어긋나면 다른 데서 온 것이고, 그 자체가 조사할 사실이다.

#### M2 — digest만으로는 실제 스캔 행을 알 수 없다

`performance_schema` digest의 `ROWS_EXAMINED`는 **문장 단위 집계**다. 배치는
`INSERT ... SELECT` 한 문장이라 그 안의 파생 테이블 셋(북마크 축·리뷰 축·`places`)이
각각 몇 행을 읽었는지 **분해되지 않는다.** 컷오프가 건드리는 것은 그중 하나뿐이다.

세 가지가 더 있다.

1. **`loops`를 곱하지 않으면 틀린다.** D 후보(places 주도 재작성)는 장소 6,320건 각각에
   대해 range seek을 도는 형태라 `loops ≈ 6,320`이다. `actual rows` 문면만 읽으면
   **루프 한 번의 행 수**를 전체로 오해한다.
2. **사전 탐침이 "세 후보 전부 10.4M 동일"을 확인한 근거가 `EXPLAIN ANALYZE`였다**(§2.3).
   같은 방법으로 재야 그 관찰이 재현됐는지 아닌지를 말할 수 있다.
3. **P2의 "건너뛴 행 비율과 산술 일치"는 실제 읽은 행 수를 요구한다.** digest의 문장 단위
   합계로는 그 비율을 계산할 분자가 나오지 않는다.

**그래서 M2-a(`actual rows × loops`)가 정본이고, M2-b(digest 실행당)는 반복 라운드에서
"플랜이 흔들리지 않았다"를 싸게 확인하는 보조다.**

> ⚠️ **M2-a는 성능 라운드와 분리해 실행한다.** `EXPLAIN ANALYZE`는 문장을 실제로 돌리면서
> 계측을 얹기 때문에 소요가 부풀고(사전 탐침에서 A가 `EXPLAIN ANALYZE` 7,081ms vs
> 순수 실행 6,116ms), **그 시간을 M1에 쓰면 안 된다.**

### 8.2 나머지 지표에 대한 선택 근거

- **M3이 `sampler.sh`가 아닌 이유**: 배치는 약 5초(무부하 4,782ms [실측,
  minimal-stability 부록 C])이고 sampler는 3초 간격이라 2샘플밖에 안 잡힌다. 게다가
  `docker stats` 문면은 유효성 판정에 쓰지 않는 것이 이 저장소의 규칙이다
  (README §5, 2026-08-04 read-ceiling §9.1).
- **M2-b의 분모를 전역 카운터로 잡지 않는 이유**: 가이드 §5 "원인 지표의 분모".
  배치는 문장이 하나라 digest의 `COUNT_STAR`가 자연스러운 분모를 준다.
  **전역 카운터 ÷ 무언가로 판정하지 않는다.**
- **M4에 락 카운터를 넣은 이유**: §2.4. 컷오프가 스캔 범위를 줄이면 RC의 락 프로파일도
  달라질 수 있는데 사전 탐침은 이를 덤프하지 않았다.
- **HTTP 부하는 이 캠페인의 범위 밖이다.** 온라인 영향은 minimal-stability 라운드 C가
  **120 req/s에서만** 검증했으므로(300 겹침 미측정), 컷오프 채택이 결정된 **후에** 별도
  라운드로 확인한다. 범주를 일곱 개로 늘리지 않는다.
- **p95/p99를 쓰지 않는다.** 배치는 단발 실행이라 백분위의 의미가 없고, 가이드 부록 A.3의
  지표 계약상 꼬리는 참고치다.

### 8.3 기록 형식

성능 라운드 하나가 남기는 한 줄:

```
seed=S2  variant=B  T=540  round=r2
M1a=5104ms  M1b=4832ms  M2b=10400682  M3=4118ms
M4(handler_read_next=10400701, tmp_disk=0, sort_merge=0, bp_reads=0, lock_waits=0)
```

M2-a는 라운드가 아니라 **조합(후보 × 단계 × T)** 단위라 별도 파일이다:

```
seed=S2  variant=D  T=540
M2a: bookmarks 스캔 노드  actual rows=1,847  loops=6,320  → 읽은 행 11,673,040
     (기준선 A 동일 단계: actual rows=17,930,000  loops=1  → 17,930,000)
```

M5·M6도 T 단위 별도 파일이다 — 작업 테이블 기반이라 결정적이고 반복이 필요 없다.

M5·M6은 라운드가 아니라 T 단위라 별도 파일이다 — 작업 테이블 기반이라 결정적이고
반복이 필요 없다.

## 9. 전기간 카운트와 최근 점수를 분리할 실익 — 판단 규칙

### 9.1 왜 이 질문이 여기 있나

`TODO.md`의 별도 항목이 이 캠페인에 걸려 있다.

> 인기점수 배치·카운트 배치 분리 필요? — 검토 과제. 현재 결론: 카운트도 전량 스캔이
> 필요해 분리가 아끼는 건 행당 산술뿐이고 버전 의미론이 복잡해져 실익 없음.
> **스캔 범위 개선(컷오프) 도입 시 재검토** — 그때는 점수 스캔 < 카운트 스캔으로
> 역전되어 논점이 뒤집힌다

컷오프를 넣으면 점수 축이 카운트 축보다 싸지므로 논점이 뒤집힐 것이라는 예고다.
**사전 탐침은 그 예고와 어긋나는 방향의 신호를 냈다.**

### 9.2 사전 탐침이 드러낸 구조적 하한

**[사전 탐침]** 카운트 축 단독(전 기간)이 **2,127ms**(중앙값), 산술 바닥
`COUNT(*), SUM(1)`이 **3,074ms**(`EXPLAIN ANALYZE` 1회)였다.

`bookmark_count`는 전 기간 집계다(설계서 `:129-130`). 그러므로
**어떤 컷오프로도 이 하한을 내릴 수 없다.** 결과적으로 세 후보 중 무엇을 골라도 배치는
총 북마크 행 수에 **선형으로 남는다** — 컷오프는 기울기가 아니라 절편을 깎는다.

이것이 §1.4의 주장 3(성장 비용 억제)에 정면으로 걸린다. 그래서 P3이 이 캠페인의
가장 중요한 게이트다.

### 9.3 판단 규칙 — 측정 전에 고정한다

분리(C 계열)가 단일 스캔(A·B)보다 낫다고 말하려면 아래를 **전부** 만족해야 한다.

| # | 규칙 | 수치 |
|---|---|---|
| **D1** | 같은 시드·같은 라운드에서 **`M1-b(점수축) + M1-b(카운트축) < M1-b(A)`** | 여유 **≥ 10%** (라운드 간 편차 ±8% [사전 탐침] 위). **M1-b 기준인 이유**: 분리는 북마크 축 안에서 일어나는 일이라, M1-a로 재면 불변 항이 분모에 섞여 차이가 희석된다 |
| **D2** | 분리 이득이 단계 축에서 **커진다** — S0→S2의 이득 증가폭이 양수 | 부호만 본다 |
| **D3** | C-idx를 쓸 경우, 인덱스 비용(§3.3)이 이득보다 작다 | **M1-a** 절감 × 24회/일 > 인덱스 쓰기 증폭 + 21초 DDL의 상각. **정량화 불가하면 D3은 "판단 보류"로 기록하고 D1·D2만으로 채택하지 않는다** |
| **D4** | 카운트 축 하한이 실제로 하한임을 재확인 | `M1-b(카운트축 단독)`과 `M2-a(카운트축 읽은 행)`이 단계별로 총 행 수에 **선형**인지 |

**D1이 깨지면(= 분리가 더 비싸면) 카운트·점수 배치 분리 과제는 "컷오프를 넣어도 실익
없음"으로 결론 내고 TODO에서 닫는다.** 그것도 이 캠페인의 성공적 산출물이다.

반대로 D1~D4가 전부 성립하면 TODO의 예고가 맞은 것이고, **분리 자체는 별도 설계 세션의
주제로 넘긴다** — 버전 의미론(매시 버전의 점수 채움)이 복잡해지는 문제는 성능 측정으로
답할 수 있는 질문이 아니다.

| 감쇠 기준 시각이나 컷오프 날짜에 `NOW()`가 섞임 | 무효 — 재현 불가 |
| 변형 간 `place_stats` 지문(`rows_`·`sum_score`·`fingerprint`) 대조 누락 | 무효 — hybrid §6.5가 측정 후 현행 공식으로 복구하고 지문 일치를 확인한 절차를 계승 |
| 세션 격리 수준이 `READ COMMITTED`가 아님 | 무효 — 앱 경로와 조건이 다르다 (§2.4) |

두 번째도 무효면 **그 사실과 근거를 남기고 그대로 보고한다** (minimal-stability §6 규약).

## 11. 실행 순서 · 산출물 · 승인 게이트

### 11.1 착수 전 승인 게이트 — 여기를 통과해야 측정을 시작한다

아래 다섯 항목은 이 문서를 읽는 사람이 정해야 한다. **사전 등록 범위는 사후에 늘릴 수 없다.**

| # | 항목 | 이 문서의 제안 | 왜 물어야 하나 |
|---|---|---|---|
| 1 | **T 후보 목록** | `{270, 365, 450, 540, 630, 720}` | 90·180을 뺀 근거는 §5.4. 뺀 것을 나중에 되살릴 수 없다 |
| 2 | **단계 수** | S0·S1·S2·S2′ 필수, **S3 선택** | S3(2,690만 행)의 시드 생성·적재가 비용. **S2′는 뺄 수 없다** |
| 3 | **창 길이** | 548일 → **1,095일(3년) 확장** | §5.3·§7.4의 수치가 1,095일 전제. 창이 짧으면 큰 T를 시험할 수 없다 |
| 4 | **보조 변형 범위** | C-idx는 조건부, D는 등록만 | D를 등록해 두는 근거는 §3.2. 열지 않기로 해도 된다 |
| 5 | **벤치 DB 스냅샷 보존** | 결정 필요 | 이 시드로 덮으면 **기존 캠페인과 절대값 비교가 끊긴다**. COURSE 북마크 0건 상태(§2.3)를 고칠지도 여기서 함께 정한다 |

여기에 하나 더 — **§12.1의 설계서 정정을 측정 전에 끝낼지**도 함께 승인받아야 한다.

### 11.2 실행 순서

```
0. 설계서 리뷰 공식 정정 (§12.1)                    ← 측정 전에 끝낸다
1. 캠페인 디렉터리 생성 + README에 이 문서 요약 이식
2. 시드 생성기 개조 (§4.3 축1 + §4.4 축2 + §4.5 검증 출력)
3. S0 적재 → 시드 검증 → 작업 테이블 구축 → 이식 검증   ← 실패 시 캠페인 중단
4. S0에서 정확성 평가 (M5·M6, T 여섯 개)            ← G 통과 T 확정
5a. S0에서 EXPLAIN ANALYZE 채취 (A / B / C × G 통과 T)  ← M2-a. 성능 라운드와 분리
5b. S0에서 성능 라운드 (같은 조합)                   ← M1-a · M1-b · M2-b · M3 · M4
6. S1 → S2 → S2′ (→ S3) 반복: 3~5b를 단계마다
7. C-idx 판단 게이트 — 4에서 C가 G 통과 T를 가졌을 때만 인덱스 생성 후 재측정
8. D 판단 게이트 — 7이 임시테이블·정렬 신호로 기각됐을 때만
9. §9.3의 D1~D4 평가 (분리 실익 판단)
10. 결과 문서 작성 + README 색인 + TODO 갱신
```

**3번의 이식 검증이 첫 관문이다.** 여기서 깨지면 4번 이후가 전부 무의미하므로,
시드를 다 만들기 전에 S0 하나로 먼저 통과시킨다.

## 12. 실험 전 정정이 필요한 것 · 주의사항

### 12.1 ⚠️ 설계서의 리뷰 점수 공식이 구현과 다르다 — 측정 전에 정정할 것

`docs/design/2026-08-05-place-stats-version-rows.md`의 두 자리가 구현과 어긋나 있다.

| | 설계서 (`:13` §0 표, `:105-107` §3) | 실제 구현 (`PlaceStatsRepository.java:113-115`) |
|---|---|---|
| 리뷰 항 | `W_R × Σ리뷰(평점−3)` | `W_R × ((Σ평점 + m·C)/(리뷰수 + m) − C)` |
| 중심 | 상수 **3** | **전체 평균 C** (`COALESCE(AVG(rating), 3.0) + 0e0`) |
| 크기 | 리뷰 수에 비례해 무한정 증가 | **유계** — 베이지안 조정평점의 편차 |

설계서 전체에 "베이지안"이라는 단어가 한 번도 없다. 반면
`docs/blog/2026-08-03-popular-sort-aggregation.md:110-119`와
`PlaceStatsProperties.java:105-118`은 구현과 일치한다.
**뒤처진 것은 설계서 §3 한 곳이다.** IT `PlaceStatsBatchProcessorIT:452
평점은_전체_평균을_중심으로_가감된다`가 구현 쪽을 못 박고 있다.

**이 캠페인에 주는 구체적 위험은 두 가지다.**

1. **이식 검증이 깨진다.** §6의 작업 테이블을 설계서 공식으로 만들면 T=∞ 재계산이 실제
   `place_stats`와 일치하지 않고, §10.3에 따라 **캠페인 전체가 무효**가 된다.
   작업 테이블은 반드시 `PlaceStatsRepository.java:113-115`를 정본으로 삼는다.
2. **G3의 분모가 틀어진다.** 컷오프는 리뷰 항을 건드리지 않지만, 리뷰 항은
   **인접 순위 간격**을 만드는 데 참여한다. 리뷰 항이 유계(베이지안)인지 무계(합)인지에 따라
   상위권의 점수 간격이 달라지고, 그러면 G3의 통과선이 달라진다.

CLAUDE.md 규칙("구현이 이 문서와 달라지면 문서를 먼저 고친다")에 따라
**설계서 §0 표 13행과 §3 첫 불릿을 측정 착수 전에 정정한다.** §11.2의 0단계다.
(정정 자체는 이 문서의 범위가 아니라 별도 작업이다 — 여기서는 필요성만 등록한다.)

### 12.2 함께 정정 대상으로 올리는 문서 부채

캠페인의 유효성을 직접 위협하지는 않으나, 같은 세션에서 함께 처리하면 좋을 것들이다.

| 항목 | 위치 | 상태 |
|---|---|---|
| 설계서 §7의 블로그 경로가 `docs/superpowers/blog/`로 적혀 있다 | 설계서 `:190` | 실제는 `docs/blog/` |
| 증분 폐지 후에도 발행측 주석 5곳이 "준실시간 증분"을 주장한다 | `PlaceReviewServiceImpl.java:75`, 이벤트 레코드 4개, `PlaceService.java:329-333` | 소비자는 존재하지 않는다. 실제 계약은 배치 간격 ≤1h |

### 12.3 인용 시 주의 — 배치 소요의 네 값을 섞지 말 것

M1을 M1-a/M1-b로 쪼갠 실무적 이유가 이 표다. 기존 문서의 값들이 **서로 다른 것을 재고 있다.**

| 값 | 무엇을 잰 것인가 | 캠페인의 대응 지표 |
|---|---|---|
| **6,049ms** [실측, `2026-07-31-place-stats-batch.md:99-104`] | 배치 `INSERT ... SELECT` **전체** (리뷰 축·places 조인·INSERT 쓰기 포함), SQL 직접 실행. **V29 이전이라 메타 시프트·옛 버전 DELETE는 빠져 있다** | M1-a와 **부분만** 대응 |
| **6,116ms** [사전 탐침] | **북마크 파생 테이블 SELECT 단독** | **M1-b** |
| **4,782ms** [실측, minimal-stability 부록 C] | 무부하 상태의 배치 전체 (V29 이후, 앱 경로) | **M1-a** |
| **5,879ms** [실측, 같은 문서] | 120 req/s 부하 겹침 중 배치 전체 | M1-a (부하 조건이 달라 이 캠페인과 비교 불가) |

**측정 대상이 다르므로 직접 비교하면 안 된다.** 캠페인은 M1-a와 M1-b를 **같은 라운드에서
둘 다** 남기므로, 이후로는 어느 쪽과 비교하는지가 지표 이름으로 드러난다.

### 12.4 이 캠페인이 답하지 않는 것 (사전 명시)

1. **운영 데이터의 유입률 이질성은 여전히 미지수다.** §4.4의 ρ 분포는 합성 가정이다.
   hybrid §8이 남긴 "운영 환경에서 확인할 것"이 그대로 전제 조건으로 이월된다.
   **이질성이 벤치보다 좁으면 컷오프는 더 안전하고, 넓으면 더 위험하다** —
   방향은 예측 가능하나 크기는 아니다.
2. **온라인 조회 영향은 안 잰다.** 배치가 도는 중의 조회 지연은 minimal-stability가
   **120 req/s에서만** 확인했다. 채택이 결정된 후 별도 라운드.
3. **배치 소요는 하한이다** — SQL 직접 실행이면 JPA·커넥션 획득·트랜잭션 경계가 빠진다.
4. **카운트 축은 손대지 않는다.** 컷오프가 `bookmark_count`에 영향이 없음을 M5·M6과 별개로
   단언 검사한다(전 장소 `cnt` 불일치 0건 — §6.1-4).
5. **`target_type` 선택도가 운영과 다르다.** 벤치에 COURSE 북마크가 0건이라(§2.3)
   절대값이 비관적이다. 상대 비교는 영향받지 않는다.
6. **`place_stats` 단편화·크기 추이**(설계서 §9)는 범위 밖이나, 단계 시드로 북마크가
   2.6배가 되므로 **관찰값을 함께 기록해 둘 가치가 있다**(게이트 아님).
