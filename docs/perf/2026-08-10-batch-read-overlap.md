# 통계 배치와 읽기 트래픽이 겹치는 창 — 결합 vs 분리 저장 구조의 격리 실측

캠페인: [`load-test/campaigns/2026-08-10_batch-read-overlap/`](../../load-test/campaigns/2026-08-10_batch-read-overlap/)
(사전 등록 README · 실행 원장 `results/execution-log.md` · 원자료 `results/`)

## 문제

통계(북마크 수·리뷰 수·평점)를 `places`에 비정규화하지 않고 `place_stats`로 분리한 근거는
"배치가 전 행을 UPDATE하는 창 동안 정적 데이터(장소명·주소·좌표)가 담긴 16KB 페이지까지
영향권에 든다"는 우려였다. 서사의 다른 화살표(실시간 증분 기각 → 배치 채택)는 기존
캠페인이 검증했지만, 이 마지막 화살표는 이론으로만 있었다.

## 가설

1. 결합 구조: 전 행 배치 UPDATE가 `places` 클러스터드 페이지 전체를 더티로 만든다 —
   변경분은 통계 컬럼뿐이어도 더티는 페이지 단위다.
2. 분리 구조(현행): 같은 배치가 `place_stats` 페이지만 더티로 만들고 `places`는 클린이다.
3. 읽기끼리는 공유 래치라 경합이 없다 — 경합이 존재할 수 있는 창은 배치 겹침뿐이다.

## 비교 대상

서빙 경로(제품 코드)를 고정하고 배치 쓰기의 착지점만 바꿨다. 결합 구조는 벤치 DB에만
더미 통계 컬럼 5개 + 랭킹 커버링 인덱스를 미러링해 흉내 냈고(실험 후 제거), 두 팔의 집계
서브쿼리(북마크 10,400,682행 스캔)는 문장 그대로 같다.

| 팔 | 배치 착지점 | 라운드 |
|---|---|---|
| B-분리 (현행) | `place_stats` — 카운트 배치와 동일한 UPSERT+DELETE | r1, r3 |
| A-결합 (흉내) | `places` 더미 컬럼 — 같은 집계를 UPDATE | r2, r4 |
| P-양성 대조 | `place_stats` 인접 200행에 동시 20커넥션 증분 폭주 | 게이트 + r5b |

골격 스냅샷 캐시는 두 팔 모두 껐다(`skeleton-source=entity`). 캐시가 켜져 있으면 읽기가
`places`를 아예 읽지 않아 결합 팔의 충돌이 관측 불가능하고, 결합 가설의 세계에는 그런
캐시가 없다. 이 선택은 안정성 주장을 약화시키지 않는다 — ENTITY는 현행 서빙보다 DB
읽기가 엄격히 많은 경로이므로, 캐시 없이 안정이면 캐시 켠 운영 구성은 더 안정이다.

## 검증 환경

- 벤치 스택(2026-08-10, 형상 develop `ac8335e` + 캠페인 산출물): 앱 1대 2 vCPU/2 GiB
  (ENTITY 모드, 실배치 cron 비활성), MySQL 8.0.46 2 vCPU/3 GiB(버퍼풀 2 GiB), edge nginx.
- 데이터: 장소 6,320 · 북마크 약 1,040만 · 리뷰 198,191.
- 부하: **240 arrivals/s** (measure 구간 실측 360~384 HTTP req/s — 이 캠페인 실측
  1.60 요청/탐색). 원래 목표 300 arrivals로 시작했으나 캐시 OFF 상태의 앱 스로틀이
  24.2%로 사전 등록 게이트(5%)를 넘어 240으로 하향했다. 300에서도 100,702요청 전부
  200·실패 0이었다 — 하향은 실패 때문이 아니라 지연 판정의 오염 방지다.
- 라운드: 사다리 워밍업 150초(측정 제외) + measure 120초. measure 안에 대조 창(배치 전
  15초)과 배치 창(수동 발화, 3.3~5.2초)이 함께 들어가 같은 라운드 안에서 비교된다.
- 배치는 cron이 아니라 같은 문장의 수동 발화다(READ COMMITTED, 단일 트랜잭션) — 창
  경계를 초 단위로 통제하기 위함이고, DB 쪽 동작은 실배치와 같다.

계측: 배치 직후 `INNODB_BUFFER_PAGE` 테이블·인덱스별 더티 census(핵심 지표), 창 단위
digest(실행당 레이턴시 — DB 내부 측정이라 앱 스로틀과 독립), PFS synch 대기 창 diff,
1초 샘플러(히스토리 리스트·행 락). 검출력은 양성 대조로 먼저 증명했다: 무부하 폭주에서
synch 대기 1.25억 회/4.97초, 히스토리 리스트 0→1,166, 행 락 대기 0→10,985.

## 성공 조건 (사전 등록)

1. 격리: B팔에서 `places` 더티 ≈ 0이고 A팔에서 자릿수로 크다 — 2라운드 재현.
2. 검출력: 양성 대조에서 카운터가 움직인다(이 게이트 전의 0은 판정에 쓰지 않는다).
3. 안정성: B팔 measure 실패 0·도착 결손 ≤2%, 배치 창 실행당 레이턴시가 자릿수 악화 없음.
4. 읽기 영향 차이는 관측으로 기록하되 간극이 산포 안이면 "구분 불가"로 적는다.

## 결과

### 격리 — 배치 직후 테이블별 더티 페이지 (성공 조건 1: 성립)

배치 직전 더티는 전 라운드·전 인덱스 0이었다. 아래는 배치 커밋 직후 값이다.

| 라운드 (팔) | `places` 더티 | `place_stats` 더티 |
|---|---|---|
| r1 (B-분리) | **0** (전 인덱스) | 45 (PRIMARY만) |
| r3 (B-분리) | **0** (전 인덱스) | 12 (PRIMARY만) |
| r2 (A-결합) | **126** (PRIMARY 66/66 + 미러 인덱스 60) | 0 |
| r4 (A-결합) | **65** (PRIMARY 65/66) | 0 |

- 분리 구조에서 `places`는 배치 창에도 **클린 그대로**다. 결합 흉내에서는 정적 데이터가 담긴
  클러스터드 66페이지가 **사실상 전부**(65~66) 더티가 됐다 — 페이지에는 장소명·주소·좌표가
  같이 들어 있으므로, 통계 4컬럼을 갱신했을 뿐인데 정적 데이터 전체가 flush 대상이 된다.
- r2의 +126에는 미러 인덱스가 처음 실제 값으로 채워지며 일어난 페이지 분할(18→60) 몫이
  포함된다. 정착 후인 r4의 65가 정상 상태 값이다.
- 흥미로운 대칭: 두 팔 모두 **랭킹 커버링 인덱스의 더티는 0**이었다. 카운트 값이 변하지
  않으면(원본 북마크 불변) 인덱스 엔트리가 안 바뀌고, 매번 바뀌는 `count_calculated_at`은
  인덱스 말단에 없기 때문이다. 반대로 값이 실제로 바뀌는 양성 대조(r5b)에서는 더티가
  커버링 인덱스 쪽(61페이지)에 몰렸다 — "카운트가 실제로 움직이는 운영일수록 랭킹 인덱스
  재작성까지 배치 창에 얹힌다"는 관측이다.

### 안정성 — B팔 배치 겹침 (성공 조건 3: 성립, 240 arrivals 한정)

| 항목 | r1 (B) | r3 (B) |
|---|---|---|
| measure 요청/실패 | 43,162 / **0** | 44,286 / **0** |
| 도착 결손 | 0% | 0% |
| 배치 소요 (부하 중) | 3.349s | 3.356s |
| 배치 창 실행당 레이턴시 (대조 창 대비) | 1.32~1.52배 | 1.41~1.83배 |
| rows examined/실행 (플랜 안정) | 0.98~1.01배 | 0.98~1.42배* |

*r3의 1.42는 towns 문장 레이턴시 비율이고 rows는 전 문장 0.91~1.06배 — 실행계획 변화 없음.

배치가 도는 3.4초 동안 읽기 문장의 DB 내부 실행당 레이턴시는 최대 1.83배(0.145→0.265ms
수준) 상승에 그쳤고 자릿수 악화·오류·플랜 플립이 없었다. 무부하 배치 2.5초가 부하 중
3.3초가 된 것도 완만하다.

### 읽기 지연의 팔 간 차이 — 구분 불가 (성공 조건 4: 갈래 b)

A팔의 두 라운드가 서로 배 이상 달랐고(r2 1.31~1.59배, r4 1.05~1.20배), B팔(1.32~1.83배)이
A팔 r4보다 높은 구간도 있다. 창 내 상승분의 지배 항은 착지점이 아니라 **배치 집계 자체의
DB CPU 경쟁**(2 vCPU에서 북마크 1,040만 행 스캔이 1코어를 점유)으로 보이며, 착지점 차이가
읽기 레이턴시에 주는 몫은 이 환경의 산포 안에 있다. 사전 등록대로 "구분 불가"로 기록한다 —
분리의 실증 근거는 읽기 지연이 아니라 **페이지 오염 격리**다.

### 대기 이벤트 — 결합 배치만 락·트랜잭션 서브시스템을 두들긴다

배치 창의 초당 대기 횟수(대조 창 기준선 병기):

| 이벤트 | 대조 창 | B팔 배치 창 | A팔 배치 창 |
|---|---:|---:|---:|
| `lock_sys_page_mutex` | 0/s | 7.7~8.4k/s | **1.86M~2.16M/s** |
| `lock_sys_global_rw_lock` | 0/s | 7.7~8.3k/s | **1.85M~2.15M/s** |
| `trx_sys_mutex` | ~400/s | ~425/s | **1.85M~2.15M/s** |
| 창 합계 대기 시간 | 8.9~9.3ms/s | 13~15ms/s | **54~57ms/s** |

같은 집계·같은 행 수(6,320)의 배치인데 착지점이 `places`로 바뀌자 락 시스템·트랜잭션
시스템 뮤텍스 활동이 2~3자릿수 커졌다. 이 창에서 읽기 레이턴시 악화가 재현되지는
않았으므로(위 절) 이 수치로 사용자 영향을 주장하지는 않는다. 다만 결합 구조의 배치가
DB 내부 공유 자원을 훨씬 넓게 건드린다는 방향 증거이며, 기제 규명(파생 조인 UPDATE의
잠금 폭 등)은 후속 과제다.

### 계측 판명 — 이번 캠페인이 확정한 측정 한계 3건

1. 이 빌드(MySQL 8.0.46)에는 **페이지 래치 인스트루먼트(`buf_block_lock`)가 없다.**
   래치 증거는 PFS synch 창 diff로 근사했고, 검출력은 양성 대조로 증명했다.
2. `INNODB_METRICS`의 `innodb_rwlock_*` 전역 카운터는 초당 7.2만 UPDATE 폭주에서도
   전부 0 — 죽은 채널이라 판정에서 제외했다.
3. `buffer_page_read_undo_log`는 언두 "순회"가 아니라 언두 페이지 **디스크 읽기** 카운터다.
   전 데이터가 버퍼 풀에 상주하는 환경에서는 구조적으로 0이므로, 0을 "언두 순회 없음"의
   증거로 쓸 수 없다. MVCC 비용의 직접 계측은 이 환경에서 수단이 없었고, 간접 증거
   (히스토리 리스트·창 내 레이턴시)로만 남긴다.

## 해석

- 분리의 실증 근거가 확정됐다: **배치 창에 `places`(정적 데이터) 페이지가 결합이면 전부
  더티, 분리면 0.** 자릿수 차이라 호스트 노이즈와 무관하고 2/2 재현됐다.
- 현행(분리) 구조는 캐시를 끈 상태에서도 240 arrivals/s의 배치 겹침 창을 실패 0으로
  처리했고, 읽기 실행당 레이턴시 상승은 최대 1.83배에 그쳤다.
- 반면 "결합이면 읽기 응답이 느려진다"는 주장은 이 규모·이 환경에서 **하지 않는다** —
  측정이 그 차이를 구분하지 못했고, 창 내 상승의 지배 항은 배치의 CPU 경쟁이었다.
  분리를 정당화하는 것은 지연 수치가 아니라 오염 격리와 (별개 축인) 운영 근거
  (재계산 가능성·주기 분리·배치 실패 격리)다.

## 이 테스트로 말할 수 없는 것

- **결합 구조의 진짜 서빙 비용.** 서빙 경로가 고정이라 랭킹 스캔은 두 팔 모두
  `place_stats` 인덱스를 읽었다. 진짜 결합 설계라면 랭킹 커버링 인덱스도 `places`에 있어
  그 재작성 충돌(r5b가 보여준 커버링 인덱스 더티 61페이지 몫)까지 `places`로 옮겨온다 —
  A팔의 관측은 결합 비용의 **하한**이다.
- **300 arrivals(원 목표)에서의 지연 특성.** 캐시 OFF에서는 앱 스로틀 게이트에 걸려
  240으로 내렸다. 300에서 실패 0은 관측했지만 지연은 주장하지 않는다. 캐시 ON(운영
  구성)의 300 arrivals 배치 겹침은 2026-08-06 캠페인의 120 req/s C 라운드와 이번 하한
  논증으로 간접 커버될 뿐, 직접 측정은 없다.
- **MVCC 언두 순회의 직접 비용** (계측 판명 3).
- 꼬리 지연(p95/p99) — 이 호스트에서 재현성이 증명된 적 없다. 클라이언트 관점 수치는
  앱 스로틀(라운드 전체 3.5~5.8%)이 섞여 있어 p50 포함 판정에 쓰지 않았다.
- flush I/O 절대량·체크포인트 거동 — 로컬 Docker 디스크는 운영 스토리지를 대표하지 않는다.
- 실배치 스케줄(매시 30분)과 실트래픽 피크의 실제 겹침 빈도 — 운영 관측의 몫이다.

## 이력서 문장에 쓸 수 있는 것 / 없는 것

기존 초안의 "목표 피크(467 req/s)에서 배치 실행 순간에도 p99 59.7ms 검증"은 기록과
맞지 않는다 — p99 59.7ms는 배치 없는 4 vCPU 라운드(2026-08-06)의 수치이고, 배치 겹침
검증은 120 req/s(2026-08-06 C 라운드)와 이번 240 arrivals(≈360~384 req/s, 캐시 OFF)다.
정직하게 쓸 수 있는 문장:

> 통계 배치가 읽기 트래픽과 겹치는 창을 실측해, 통계 테이블 분리가 정적 장소 데이터
> 페이지를 배치 쓰기 영향권에서 완전히 격리함을 확인했다(결합 흉내 시 클러스터드 전
> 페이지 더티 vs 분리 시 0, 2회 재현). 분리 구조는 캐시 없이도 배치 창에서 240 arrivals/s
> (~370 req/s)를 실패 0·읽기 문장 지연 2배 이내로 처리했다.
