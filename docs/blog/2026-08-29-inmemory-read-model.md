# 문장을 싸게 만들 것인가, 없앨 것인가 — 조회 전용 인메모리 정렬 전환

작성일: 2026-08-29
연결: [여러 동네 목록 조회에서 실제 비용을 결정한 것은 무엇이었나](2026-08-21-multi-town-query-cost-structure.md)(DB 관점),
[DB 비용만 보고 고른 쿼리 형상이 앱에서 낸 청구서](2026-08-29-stmt-cache-hidden-app-cost.md)(첫 번째 해법의 상세)

장소 목록 조회의 DB 경로는 이미 두 번 다듬어져 있었다. 정렬이 6종(인기·최신·평점·
리뷰 수·북마크 수·거리)으로 늘 때 정렬별 커버링 인덱스를 갖췄고, 다중 동네 조회는
동네별 브랜치 UNION ALL로 바꿔 데이터가 늘어도 읽는 행이 늘지 않게 했다(전편). DB의
장부로는 할 수 있는 것을 다 한 구조다. 그런데 목표 부하를 걸자 아픈 곳은 DB가 아니라
앱이었고, 이 글은 그 앞에서 두 갈래 해법 — **문장을 싸게 만드는 설정**과 **문장 자체를
없애는 구조 전환** — 을 같은 자로 재서 후자를 채택한 기록이다.

측정 환경은 시리즈 공통이다. 앱 2 vCPU + MySQL 2 vCPU의 Docker cgroup quota, 부하는
평상시 60 arrivals/s에서 안착한 뒤 같은 실행에서 목표 피크 300 arrivals/s로 즉시
전환한다. 도착 하나가 1페이지와 커서 2페이지를 이어 부르므로 제공 부하는 약 571 req/s다.
믹스는 6종 정렬을 실사용 가정 비율(인기 40 / 거리 20 / 리뷰 15 / 북마크 10 / 평점 10 /
최신 5)로 섞고, 각 정렬을 단일 동네 40% / 시 단위(동네 18개) 60%로 다시 쪼갠다.

## 1. 목표 부하가 내민 청구서

DB 쪽 최적화를 끝낸 구조 — 엔티티 골격 + DB 정렬, 다중 동네는 UNION ALL — 에 목표
부하를 걸었다. 오류 0으로 완주는 한다. 그러나 피크 90초 동안 앱 CPU 스로틀이 **60.5초**
(발생 주기의 21.6%) 쌓였고, p95는 308ms까지 밀렸으며, 앱 CPU 평균 사용률은 쿼터의
75.5%였다. DB는 같은 시간 스로틀 0.57%로 멀쩡했다. 천장은 앱이다.

아픈 곳은 문장 텍스트였다. UNION ALL이 동네마다 완전한 SELECT를 복제하면서 다중 동네
문장이 최대 9,378자·바인드 127개가 됐고, 그 텍스트를 실행마다 앱이 문자 단위로 다시
읽고(드라이버 재파싱, 요청 CPU의 6.8%), 값을 끼운 전문을 통째로 실어 보내고(패킷
조립·전송 5.6%), 서버가 또 한 번 파싱한다. 이 문장을 쓰는 요청은 믹스의 48%(시 단위
60% × 비거리 80%)다. 프로파일로 이 몫들을 귀속한 해부는 별도 원고에 있다.

## 2. 첫 번째 해법 — 문장을 싸게 만든다

원인이 "텍스트 길이 × 반복"이니, 반복을 없애는 설정 네 줄(드라이버 문장 캐시 + 서버
prepared statement)이 첫 번째 해법이다. 같은 창에서 켜고 껐다.

| 목표 부하 (제공 ~571 req/s) | DB 정렬 (캐시 없음) | DB 정렬 + 문장 캐시 | 변화 |
|---|---:|---:|---:|
| 앱 스로틀 발생 주기 / 누적 | 21.6% / 60.5초 | 1.4% / 0.9초 | 1/15 |
| p95 | 308ms | 7ms | 1/44 |
| 요청당 앱 CPU | 2.536ms | 2.165ms | −15% |
| 요청당 DB CPU | 1.905ms | 1.539ms | −19% |
| 앱 CPU 사용률 (쿼터 대비) | 75.5% | 64.1% | −11%p |
| DB CPU 사용률 | 56.7% | 45.6% | −11%p |

효과는 실재한다 — 꼬리와 스로틀은 회복됐다. 그러나 이 해법이 손대지 못하는 것이 있다.
**요청당 일의 구조다.** 문장이 싸졌을 뿐 요청 하나는 여전히 SQL 10문장을 돌고, 결과
바이트를 엔티티로 조립하고, 커넥션을 오간다. 앱 사용률 64.1%는 운영 안전 기준(평균
~50%)을 여전히 넘고, 급증 전환 순간의 흔들림(전환 버킷 p95 63ms)도 남는다. 스로틀은
평균이 아니라 100ms 주기의 순간 수요로 발생하므로, 사용률이 상한에 가까울수록 벽을
치는 주기가 비선형으로 는다 — 64%는 그 가파른 구간의 문턱 바로 아래다. 데이터와
기능이 늘면 같은 자리로 돌아온다.

## 3. 문장을 싸게 만들어도 남는 것 — DB 정렬 경로의 유지 비용

인덱스를 더 다듬는 길은 후보가 되지 못했다. 정렬 6종 확장 때 이미 검증했기 때문이다.
정렬별 인덱스 다섯 개가 공존하는 상태에서 90개 요청 형상(정렬 × 지역 × 태그 ×
페이지)의 실행계획을 확인하니, 의도한 인덱스를 탄 것은 42칸이었다. 신규 정렬의 컬럼
집합이 기존 인기순 인덱스의 부분집합이라 다섯 인덱스가 전부 커버링이 되고, MySQL은
커버링 비용이 비슷하면 정렬 순서를 얻기 위해 인덱스를 바꾸지 않는다 — 근소하게 싼
쪽으로 몰리고 순서는 filesort로 만든다. 더 나쁜 발견은 커서 페이지였다. 커서에 실리는
정렬키 리터럴이 range 추정을 움직여, 같은 요청이 직전 페이지의 이력에 따라 다른 계획을
탔다. **실행계획이 요청의 순수 함수가 아니게 된다.**

이 변동성은 지금도 실재한다. 이번 측정에 쓴 벤치(자연 선택 상태)에서 단일 동네 실행계획을
다시 떠 보니, 평점순은 의도 인덱스를 타고 11행에서 멈추지만 리뷰순·북마크순은 여전히
평점 인덱스로 흘러 동네 100행을 읽고 filesort로 자르고 있었다. 손해 자체는 반사실
대조(FORCE INDEX)로 한정해 뒀다 — 이 규모에서 100행 대 11행이라 판정을 움직일 크기는
아니다. 문제는 크기가 아니라, **기준이 하나 늘 때마다 이 검증을 반복해야 하고 그 결과를
계획의 변덕에 맡겨야 하는 구조**라는 것이다.

## 4. 두 번째 해법 — 조회 전용 인메모리 정렬

두 번째 해법은 정렬·필터·페이징을 요청 시점의 DB에서 떼어내는 것이다.

```text
배치·어드민 커밋 후: place_stats 전체 조회 → (정렬 5종 × 동네) 사전 정렬 배열 생성 → volatile 참조 교체
요청: 해당 동네의 사전 정렬 배열에서 커서 위치 탐색(seek) → 다중 동네는 k-way merge → 페이지 확정
거리순: 동네 후보를 배열에서 받아 하버사인 + 최대 힙 top-k (DB 후보 조회도 사라짐)
```

골격 스냅샷과 같은 계약이다 — 새 배열을 완성한 뒤 참조를 한 번 교체하므로 요청은 이전
또는 새 세대 중 하나만 본다. 장소 6,320개 기준 전체 재생성은 90~184ms였다.

두 가지를 설계 시점에 고정했다.

**신선도는 DB 경로와 같아야 한다.** 어드민 수정은 커밋 직후 재생성으로 즉시 반영되고,
카운트·점수는 어차피 배치 주기로 갱신된다. 조회 축을 메모리로 옮겨도 **사용자가 보는
신선도는 그대로다.** 새로 잃는 것이 없다는 점이 전환 문턱을 낮췄다.

**두 경로의 응답은 바이트까지 같아야 한다.** `sort-source` 스위치로 두 경로를 같은
빌드에 공존시키고, 동점·같은 초 생성·리뷰 0건·좌표 없는 장소·다중 동네 병합 같은
함정을 심은 픽스처에서 두 모드를 나란히 돌려 응답과 커서 토큰이 완전히 같은지를
테스트가 문다. 기대값을 손으로 적지 않으므로 두 경로가 함께 틀리는 그린은 생기지
않는다. 다르면 캐시가 아니라 버그이고, 그 상태의 측정은 서로 다른 응답의 비용을 비교한
것이라 뜻이 없다.

## 5. 두 해법을 같은 자로 목표 피크까지 밀었다

세 구성을 같은 시나리오·같은 부하 지점(도착 300/s)으로 쟀다. **인메모리 열의 출처에는
설명이 필요하다** — DB 정렬 두 구성은 2026-08-29 한 창의 측정이고, 인메모리 구성은
같은 시나리오의 08-17 창 측정이다. 창(호스트 날짜)이 다르다는 한계가 있지만 차이의
방향은 한정된다: 두 창 모두에서 재진 동일한 대조 구성이 하나 있어 창의 눈금을 댈 수
있는데 나중 창이 더 후하게 나왔고(같은 구성의 요청당 앱 CPU 2.56 → 2.29ms), 인메모리
구성은 문장 캐시가 없던 시절의 측정이라 지금 형상에서는 이보다 좋다. 둘 다 **인메모리의 격차를 실제보다 작게 읽는 방향**이라,
표의 격차는 하한으로 읽으면 된다.

| 목표 피크 (전환 포함 90초) | DB 정렬 (캐시 없음) | DB 정렬 + 문장 캐시 | **인메모리 정렬** |
|---|---:|---:|---:|
| 앱 CPU 평균 (2 vCPU 쿼터 대비) | 75.5% | 64.1% | **43.2%** |
| DB CPU 평균 (쿼터 대비) | 56.7% | 45.6% | **19.2%** |
| 앱 스로틀 발생 주기 / 누적 | 21.6% / 60.5초 | 1.4% / 0.9초 | **0.46% / 0.3초** |
| DB 스로틀 | 0.57% / 0.1초 | 0% / 0초 | **0% / 0초** |
| 전환 버킷 p50 / p95 | 92.8 / 340ms* | 5.0 / 63.4ms | **3.0 / 4.0ms** |
| 피크 버킷 p50 | 5.0ms | 4.0ms | **3.0ms** |
| Hikari pending 최대 | (미수집) | (미수집) | **0** |
| 오류 | 0 | 0 | 0 |
| 운영 안전 기준 (스로틀·CPU·pending·DB) | 1/4 | 1/4 | **4/4 통과** |

\* 전환 다음 버킷은 p50 314ms·최대 879ms까지 밀렸고 복귀까지 약 20초가 걸렸다.

### 요청당 비용으로 환산하면

| 요청당 CPU (피크) | DB 정렬 (캐시 없음) | DB 정렬 + 문장 캐시 | **인메모리 정렬** |
|---|---:|---:|---:|
| 앱 | 2.54ms | 2.17ms (−15%) | **1.44ms (−43%)** |
| DB | 1.91ms | 1.54ms (−19%) | **0.64ms (−66%)** |
| 합 | 4.44ms | 3.70ms (−17%) | **2.08ms (−53%)** |
| 앱 축 처리 천장 (2,000ms/s ÷ 단가) | 789 req/s | 924 req/s (+17%) | **1,389 req/s (+76%)** |

괄호의 %는 캐시 없는 DB 정렬 구조 대비다. 요청당 단가는 부하량과 무관한 값이라 쿼터
환경 밖에서도 처리 여유의 산술적 기반이 된다. 인메모리 열의 −53%에는 골격 스냅샷(엔티티
조립 제거)의 몫이 함께 들어 있다 — 정렬 이관만의 몫은 아래 프로파일이 가른다.

### 원인 지표 — 산술이 먼저 갈렸다

요청당 SQL 문장 수가 10 → 10 → **7**이다. 문장 캐시는 문장을 싸게 만들 뿐 수를 줄이지
못하고, 인메모리 전환이 골격 조립 2문장과 정렬 쿼리 1문장을 지운다. 사라진 정렬 문장은
평균보다 훨씬 무거운 문장이었다 — 브랜치가 동네마다 11행에서 멈추도록 다듬은 UNION ALL
문장조차 다중 동네 1회 실행에 214행(태그 없는 1페이지 실측, 필터가 빡빡하면 1,800행대)을
읽는데, 인메모리 구조가 요청 전체에서 DB에 읽히는 행은 **16.8행**(행정구역 확장 12행 +
북마크 여부 5행)이다.

### "정렬을 앱으로 가져오면 앱 CPU를 내주는 것 아닌가"

이 직관은 JFR 프로파일로 검증했다. 정렬 이관의 몫만 떼기 위해 골격은 양쪽 다 스냅샷으로
같게 두고 정렬만 DB/메모리로 가른 두 구성을 피크에서 대조한 결과다.

| 정렬만 가른 프로파일 대조 (피크, 물리 코어 환산) | |
|---|---:|
| 사라진 것 — JDBC 드라이버·커넥션풀·Hibernate 결과 처리 | −32.4%코어 (감소분의 91%) |
| 새로 생긴 것 — 사전 정렬 배열 탐색·병합·거리 계산 | **+1.5%코어 (감소분의 4.3%)** |

쿼리를 던지고 결과 바이트를 객체로 조립하는 왕복 비용이, 이미 정렬돼 있는 배열을
탐색하는 비용보다 훨씬 컸다. 이 규모(6,320행)에서 정렬 이관은 앱을 내주고 DB를 사는
교환이 아니라 **양쪽에서 일을 지우는 선택**이다. 이 프로파일은 다중 동네 문장이 지금보다
훨씬 짧던 시절의 채집이라, 사라지는 왕복이 더 무거운 지금 문장 기준으로 4.3%라는 비중은
보수적인 값이다.

### JVM 할당과 GC 비용을 추가로 검증했다

위 비교에서는 관측자 효과를 줄이기 위해 GC 이벤트를 직접 기록하지 않았다. 그래서 다섯
질문이 남아 있었다.

1. 인메모리 구조에서 요청당 객체 할당은 실제로 얼마나 달라졌는가?
2. 정렬을 애플리케이션으로 옮기면서 어떤 객체가 새로 만들어졌는가?
3. GC가 CPU 여유 부족의 주요 원인이었는가?
4. 힙에 상주하는 스냅샷이 old 영역 부담을 키우는가?
5. 스냅샷을 통째로 교체할 때 지연이나 GC 정지가 발생하는가?

제품 코드를 바꾸지 않고 별도의 GC 분해 캠페인으로 답했다. 캐시 없는 DB 정렬 구조와
인메모리 구조를 **같은 부하·같은 90초 피크 창에서** 각 3라운드씩 재고, 커스텀 JFR
설정에는 GC 이벤트, 1초 주기의 ThreadAllocationStatistics, 빈도를 제한한
ObjectAllocationSample만 넣었다 — CPU 실행 샘플링은 계측 부하를 줄이기 위해 제외했다.
계측이 결과를 바꾸지 않았는지는 구조별 비계측 라운드 대조로 가뒀다: 요청당 앱 CPU
차이가 DB 정렬 +9.50%, 인메모리 −0.91%로 사전에 정한 ±15% 안이었고 p50 차이는 없었다.
관측자 효과가 0이라는 뜻이 아니라, 남은 차이가 판정을 뒤집을 크기가 아님을 확인한 것이다.

**요청당 할당은 절반이 됐다.** 피크 90초 구간의 중앙값이다.

| 지표 | DB 정렬 (캐시 없음) | 인메모리 정렬 | 변화 |
|---|---:|---:|---:|
| 요청당 힙 할당 | 1,537.6KB | 748.5KB | −51% |
| 할당 속도 | 845.9MB/s | 427.9MB/s | −49% |
| 요청당 앱 CPU (이 캠페인 창) | 2.582ms | 1.300ms | −50% |

요청당 할당의 라운드별 범위도 1,449.8~1,547.4KB vs 740.2~779.5KB로 겹치지 않았다.
(요청당 앱 CPU는 이 캠페인 창의 값이므로 §5 판정표와 절대값을 섞지 않는다 — 방향
확인용이다.) 이 감소를 한 가지 효과로 귀속하지는 않는다 — DB 목록 조회와 JDBC/Hibernate
처리 감소, 응답 조립과 정렬 방식 변화가 함께 든 구조 전체의 결과다.

**앱 정렬은 새 객체를 만들지만 전체 절감을 뒤집지 않았다.** 할당 표본에서 거리 계산
후보·정렬 후보·순위가 확정된 결과, 세 종류의 객체가 인메모리 구조에서만 관측됐고 전체
할당의 약 3.0~3.4%를 차지했다. ObjectAllocationSample은 가중치를 적용한 표본 기반
추정치라 요청당 할당량 계산에는 쓰지 않았다 — 크기는 ThreadAllocationStatistics로
판단하고, 표본은 새 할당의 종류와 대략적 비중 파악에만 썼다.

**GC 비용은 감소했지만 원래부터 주된 병목이 아니었다.** 같은 피크 창의 중앙값이다.

| 지표 | DB 정렬 (캐시 없음) | 인메모리 정렬 |
|---|---:|---:|
| GC 횟수 | 122회 (Young 102 · Old 20) | 68회 (Young 50 · Old 18) |
| GC 이벤트 시간 합 | 3,575.6ms (창의 3.97%) | 1,857.1ms (2.06%) |
| GC pause 합 | 395.1ms (창의 0.44%) | 224.9ms (0.25%) |
| 최대 GC pause | 29.8ms | 17.6ms |
| GC 스레드 CPU (2 vCPU 쿼터 대비) | 0.306% | 0.200% |
| 승격 속도 | 0.13MB/s | 0.09MB/s |
| GC 전 / 후 평균 힙 | 724 / 105MB | 644 / 89MB |

GC 횟수와 이벤트 시간은 라운드 간 변동이 컸고 구성별 3라운드는 신뢰구간을 만들 표본이
아니므로, 중앙값을 안정적인 점추정으로 읽지 않았다. 판정은 서비스가 멈춘 시간과 CPU에
직접 연결되는 두 지표로 했다 — GC pause 합 0.44% vs 0.25%, GC 스레드 CPU 0.306% vs
0.200%. 인메모리에서 둘 다 낮아졌지만, DB 정렬 쪽 값도 이미 피크 창과 쿼터에서 차지하는
비중이 작았다. **CPU 여유 개선의 주된 원인을 GC 감소로 해석하지 않는다** — 주요 변화는
매 요청 반복하던 DB/JDBC/Hibernate 처리 비용을 지운 데서 났다.

**상주 스냅샷이 old 영역 부담을 키운 흔적은 없었다.** 90초 피크 창에서 승격 속도
(0.13 → 0.09MB/s)와 GC 후 평균 힙(105 → 89MB) 모두 인메모리 쪽이 낮았다. 다만 90초
로컬 벤치이므로 장시간 운영에서의 힙 증가·메모리 누수·장기적 GC 악화까지 검증한 것은
아니다.

**스냅샷 통째 교체도 피크 부하에서 확인했다.** 교체 순간 두 세대의 스냅샷이 겹치며
힙과 GC에 부담을 줄 가능성을 보기 위해, 교체가 피크 90초 창의 한가운데 실행되도록 맞춘
유효 2라운드를 쟀다. 두 라운드 모두 교체 버킷의 서비스 지표는 p50 2ms·p95 4ms·오류
0이었고, 교체 이후 GC 후 힙 바닥은 3~6MB 높아진 채 유지됐다. 반면 교체 직후 young GC
pause는 한 라운드 4.2ms, 다른 라운드 41.6ms로 갈려 재현되지 않았으므로 **교체의 GC
정지가 항상 작다고 결론 내리지 않는다.** 또 이 실험은 교체만 격리하지 못했다 — 교체를
일으키는 배치 회차에 카운트 재계산과 DB 쓰기가 포함되므로, 측정값은 배치 회차 전체가
피크에 겹쳤을 때의 결과다.

정리하면, 인메모리 전환의 이득은 GC를 줄여서 난 것이 아니다 — 요청당 일 자체를 지웠고,
할당 감소는 그 노동이 사라진 증상이다.

## 6. 판정 — 서빙은 인메모리, 설정 네 줄은 폴백에

문장 캐시는 문장을 다루는 반복 비용을 지웠고, 그것만으로 스로틀과 꼬리를 회복시켰다.
그러나 앱 사용률 64%와 요청당 10문장이라는 구조는 그대로였다. 인메모리 전환은 문장
자체를 지워 사용률을 43%/19%로 내렸고, 급증 전환조차 안착 구간과 구분되지 않았다
(전환 버킷 3.0ms). 운영 안전 기준을 문면 그대로 통과한 것은 인메모리뿐이다.

그래서 구조는 이렇게 확정됐다. **서빙은 인메모리 정렬이 담당하고, DB 정렬 경로는
스냅샷이 없는 기동 직후와 운영 개입을 위한 폴백으로 남되, 문장 캐시 설정 네 줄을 켠
최선의 형태로 유지한다.** 폴백이라고 아무 때나 무너져도 되는 경로가 아니기 때문이다.
인덱스 다섯 개도 폴백과 함께 남는다 — 유지 비용은 합계 2.30MB로 사실상 0임을 재 뒀다.

종합하면, 처음 구조(캐시 없는 DB 정렬)에서 최종 구조(인메모리 서빙 + 캐시 폴백)까지
요청당 CPU 합계는 4.44 → 2.08ms(−53%), 앱·DB 사용률은 75.5%/56.7% → 43.2%/19.2%,
스로틀은 21.6% → 0.46%가 됐다. 이 감소에는 골격 스냅샷과 정렬 이관 두 몫이 함께 있고,
몫의 경계는 위 프로파일(감소분의 91%가 JDBC·ORM)과 문장 수 산술(10 → 7)이 긋는다.

## 7. 이름은 결말에서 — 이 구조가 CQRS가 된 이유

설계를 마치고 보니 구조에 이름이 붙어 있었다. 쓰기는 지금까지처럼 RDBMS가 정본이고,
조회 축(정렬·필터·페이징과 골격)만 미리 계산된 읽기 모델이 담당한다. 갱신은 배치와
어드민 커밋 훅이 밀어 넣고, 그 사이의 어긋남은 원래부터 배치 주기로 허용돼 있던 폭
그대로다. 조회와 명령의 책임 분리, 곧 CQRS다 — 다만 Redis 같은 외부 저장소 없이
인프로세스 배열과 참조 교체로 같은 계약을 얻었다. 목표가 패턴 적용이 아니라 "요청
시점의 반복 작업 제거"였기 때문에, 패턴은 결과로 따라왔다.

확장 방향도 같은 원칙을 따른다. 정렬 기준이 하나 더 늘면 인덱스와 실행계획 검증이
아니라 **사전 정렬 배열이 하나** 는다. "영업 중"처럼 시각에 따라 변하는 조건이 들어와도
검색 엔진을 들이는 것이 아니라 DB에서 후보를 자르고 앱에서 정렬하는 같은 틀이 받는다.

## 8. 측정 방법과 이 기록이 말할 수 없는 것

- 판정 라운드는 구성별 1회다. 스로틀 비율은 이 호스트에서 라운드 간 흔들림이 실측돼
  있으므로, 개별 수치는 "이 기준을 충족하는 라운드가 실재한다"의 증명으로 읽는다.
- 인메모리 열은 DB 정렬 두 구성과 다른 날의 측정이다(§5 서두의 방향 한정). 칸 사이
  1할 미만의 차이는 이 표로 판정하지 않는다.
- GC·할당 대조는 08-28 한 창, DB 정렬 두 구성의 대조는 08-29 한 창의 측정이라 서로
  절대값을 한 표에 섞지 않는다. 섞은 표는 위 판정표 하나이고 그 한계는 §5에 적었다.
- 캐시 없는 DB 정렬 구조는 호스트가 나쁜 날 같은 부하에서 응답 결손까지 간 관측이
  있으나, 호스트 압박과 겹친 창이라 서사와 판정 어디에도 쓰지 않았다.
- p99는 기록만 하고 판정에 쓰지 않았다. 세 구성 모두의 앱 CPU에는 요청마다 반복되는
  공통 고정비(JWT 파싱 등)가 깔려 있어, 이 바닥을 걷어내면 구조 간 상대 격차는 표의
  수치보다 크다.
- 검사 행 수치의 분모가 다르다 — DB 정렬 쪽 214행은 목록 문장 1회 실행의 폐루프 실측,
  인메모리 쪽 16.8행은 요청 전체의 부하 창 실측이다. 인메모리 요청의 문장은 각 1회씩
  돌므로 비교 방향은 보존된다.

근거 자료는 로컬의 `docs/perf/`와 `load-test/campaigns/`(2026-08-16·08-17·08-28·08-29
캠페인)에 보존했다.
