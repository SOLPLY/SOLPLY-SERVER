# 번호 둘로 맞추는 인스턴스별 인메모리 스냅샷 구조

작성일: 2026-09-10 · 구현 기준: 2026-09-15

솔플리의 장소 목록은 각 API 서버의 메모리에서 정렬·필터·페이지 탐색을 수행한다.
서버가 여러 대여도 스냅샷의 내용은 서버끼리 주고받지 않는다. 각 서버가 MySQL 원본을 직접
읽어 자기 스냅샷을 짓고, MySQL이 서버들에게 공유하는 것은 "무엇이 바뀌었나"를 말하는
번호 둘뿐이다.

이 글은 그 번호 둘의 뜻, 번호를 올리는 쓰기 경로, 각 서버가 번호를 보고 스냅샷을 다시 짓는
절차, 요청이 어느 회차로 답하는지를 설명한다. 로컬 자료구조와 관리자 수정의 반영,
Heap·GC 비용은 [메모리 조회 모델과 갱신·Heap·GC 설계](2026-09-09-admin-rebuild-tradeoff.md)에
정리한다.

## 1. 요청 처리와 데이터 갱신의 역할

```text
사용자 앱
  → Nginx
  → SOLPLY API 서버
      ├── 인증: Access JWT 검증
      ├── MySQL: 동네·태그 조건 검증, 사용자별 북마크 여부
      ├── MySQL: 공유 cursor_version 한 행 조회 (메모리 목록 요청마다)
      ├── 로컬 메모리: 이 서버의 스냅샷으로 장소 페이지 탐색
      └── 로컬이 공유 회차보다 뒤처졌으면
            → 이 서버의 리빌드에 합류해 기다렸다가 페이지 구성
  ← 목록·이미지 URL·커서

사용자 앱
  → CloudFront → S3 이미지 저장소

SOLPLY 서버의 스케줄 작업
  → 정기 집계 회차 넷: place_stats 갱신 + 번호 증가 [MySQL, 같은 트랜잭션]
  → 각 서버의 폴(1분): 번호가 커졌으면 원본을 읽어 자기 스냅샷을 다시 짓는다 [서버별 메모리]

관리자 수정
  → 원본 변경 + 번호 증가 [MySQL, 같은 트랜잭션]
  → 커밋 직후 그 서버의 표시값만 메모리에 바로 얹는다
```

목록의 정렬·필터·페이지 탐색은 메모리에서 처리하지만, 요청 전체가 DB 없이 실행되는 것은
아니다. 이미지 URL은 서버가 조합하고 실제 이미지는 앱이 요청한다. 소셜 로그인 제공자나
AI API는 목록 조회·집계·스냅샷 갱신 경로에 참여하지 않는다.

이 경로에 Redis는 없다. 서버 간 공유 기준이 MySQL의 한 행이고, 그 행을 고치는 쓰기가 원본을
고치는 트랜잭션 안에 있기 때문이다. 서버의 다른 기능이 Redis를 쓰는지와는 별개다.

## 2. MySQL에는 무엇을 저장하는가

| 테이블 | 역할 |
|---|---|
| 장소·동네·태그·북마크·리뷰 원본 | 도메인 데이터의 기준 |
| place_stats | 목록이 읽는 정렬 키·소속·태그 비트·표시값(이름·썸네일 키·대표 태그) |
| bookmark_count_events | 아직 소비하지 않은 북마크 증감 전표 |
| place_list_snapshot_metadata | 번호 둘(revision, cursor_version)을 담은 한 행 |
| shedlock | 같은 집계 회차의 인스턴스 간 실행 조율 |

스냅샷의 내용은 어디에도 저장되지 않는다. 정렬 배열도 표시값 맵도 각 서버가 원본을 읽어
만든다.

### 번호 둘은 다른 질문에 답한다

```text
place_list_snapshot_metadata (id = 1)
  revision        "다시 지을 것이 있나"   목록에 실리는 무엇이든 바뀌면 오르고,
                                        회차가 오를 때 0으로 돌아간다
  cursor_version  "지금 커서를 계속 써도 되나"   진행 중인 스크롤을 끊어야 할 때만 오른다
```

각 서버의 폴은 읽은 번호를 자기가 설치한 번호와 대조한다. 커서 토큰은 `cursor_version`을 싣고
다니며, 그 값이 공유 현재와 다르면 만료다.

하나로 합치면 둘 중 하나가 망가진다. `revision`만 두면 이름 한 칸 고친 관리자 수정이 모든
스크롤 세션을 끊는다. `cursor_version`만 두면 "스크롤을 유지한다"를 고른 수정이 어느 서버에도
반영되지 않는다.

번호를 올리는 문장은 하나다. `cursor_version`이 오르는 쓰기에서는 `revision`이 0으로 돌아간다.

```text
SET revision       = IF(? = 1, 0, revision + 1),
    cursor_version = cursor_version + ?
```

물음표 둘에는 같은 값이 들어간다. 커서를 끊는 쓰기면 1, 아니면 0이다. DB가 현재 값을 읽어
더하므로 두 트랜잭션이 같은 값을 읽어 같은 값을 쓰는 유실이 없다. 자바로 읽어 더해서 다시 쓰는
방식은 쓰지 않는다.

| 쓰기 | revision | cursor_version |
|---|---|---|
| 정기 집계 회차(리뷰 카운트·북마크 델타·인기 점수·안전망) | 0으로 리셋 | +1 |
| 관리자 장소 생성·수정·삭제·동네 활성화, 기본값 | +1 | 유지 |
| 관리자가 "목록 새로 시작"을 명시한 경우 | 0으로 리셋 | +1 |
| 관리자 태그 이름·활성 상태, 이미지 후처리(썸네일 키) | +1 | 유지 |

리셋을 두는 이유는 로그를 읽기 위해서다. `(13, 3)`은 "13회차의 3번째 변경"이다. 대가는
`revision` 하나만으로는 새것인지 알 수 없다는 것이다. 두 번호의 전순서는
`(cursor_version, revision)` 사전식이다. 회차가 다르면 회차로 갈리고, 같을 때만 그 안의 몇
번째 변경인지를 본다.

그래서 번호 비교는 `SnapshotMetadata.isNewerThan` 한 메서드에 모으고, 코드 어디에서도
`revision`을 직접 대소 비교하지 않는다. 한 곳이라도 남으면 집계 회차 직후가 조용히 무너진다.
그 회차가 지은 새 스냅샷은 `revision`이 0이라, `revision`만 비교하는 자리에서 방금 만든 최신이
"낡았다"로 판정돼 버려진다.

집계 회차가 커서를 끊는 이유는 인기 점수·북마크 수·리뷰 수가 전 장소에 걸쳐 바뀌어 정렬
순서가 통째로 갈리기 때문이다. 그 위에서 옛 커서로 이어 가면 항목이 겹치거나 빠지는데, 200
응답이라 클라이언트가 알 방법이 없다. 그래서 명시 만료로 끊는다.

관리자 수정은 기본이 "스크롤 유지"다. 장소 추가·삭제·동네 이동도 자동으로 커서를 끊지 않는다.
운영 시간대에 장소 하나를 고칠 때마다 스크롤 중이던 사용자를 첫 페이지로 되돌리지 않기
위해서다. 대신 이어 보는 사용자에게 항목 하나가 겹치거나 빠져 보일 수 있고, 대량 정리처럼
그 어긋남이 눈에 띌 작업에서는 요청의 `restartPlaceList`를 `true`로 보내 목록을 새로
시작시킨다.

## 3. 쓰기 경로는 번호를 같은 트랜잭션에서 올린다

번호를 올리는 UPDATE는 데이터를 고친 그 트랜잭션의 마지막 문장이다. 롤백되면 번호도 없던 일이
되고, 커밋되면 반드시 올라 있다. "데이터는 바뀌었는데 번호는 그대로"인 상태가 없으므로
어느 서버도 변경을 놓치지 않는다.

```text
관리자 쓰기 트랜잭션
  → 장소·관계·표시값 변경
  → place_stats upsert
  → JPA 변경 flush
  → 번호 UPDATE (revision + 1, cursor_version + 0 또는 1)   ← 마지막 문장
  → 커밋

커밋 직후 (같은 서버)
  → 손댄 장소의 표시값을 DB에서 다시 읽어 이 서버의 메모리에 바로 얹는다
  → 실패해도 던지지 않는다 — 다음 리빌드가 원본에서 가져온다
```

마지막에 두는 이유는 그 UPDATE가 모든 쓰기 경로가 만나는 한 행을 잠그기 때문이다. 트랜잭션의
앞에서 잠그면 남은 작업(태그 재삽입·이미지 정리·통계 수천 행 UPDATE)이 도는 내내 다른 쓰기가
기다린다. JPA의 지연 쓰기를 먼저 내보내는 것도 잠금 구간을 실제로 꼬리에 붙이기 위해서다.

번호는 "모든 서버가 순서·소속까지 다시 읽어라"는 신호이고, 커밋 직후의 표시값 패치는 관리자가
방금 고친 이름·썸네일을 그 서버에서 바로 보이게 하는 것이다. 둘은 서로를 대신하지 않는다.
패치가 실패해도 번호는 이미 올라 있으므로 손실이 아니라 지연이다.

### 북마크 델타는 전표를 삼키는 트랜잭션에서 올린다

북마크 원본 변경과 아웃박스 전표 생성은 하나의 트랜잭션이다. 등록은 +1, 해제는 -1을 기록한다.

```text
북마크 델타 회차 트랜잭션 (READ COMMITTED)
  → 지금 있는 전표에 이번 회차 표식(UUID)을 찍는다        ← claim
  → 표식 찍힌 PLACE 전표를 장소별 SUM(delta)로 합산
  → place_stats.bookmark_count에 더한다
  → 표식 찍힌 전표만 삭제
  → 번호 UPDATE (둘 다 +1)
  → 커밋
```

표식은 "세기 전에 있던 전표만 지운다"를 SQL 한 문장으로 하기 위한 이름표다. 재계산 중 들어온
새 전표는 표식이 없어 남고, 다음 회차가 처리한다. 확인된 성질은 둘이다. 중간에 실패하면
표식까지 함께 롤백돼 전표가 처음 상태로 남는다는 원자성, 그리고 조건 없는 claim UPDATE가 그
시점에 보이는 전표 행마다 잠금을 잡는다는 것. "UUID가 중복을 막는다"거나 "정확히 한 번"
같은 표현은 쓰지 않는다. 근거는 잠금과 원자성이다.

전표가 하나도 없는 회차는 번호를 올리지 않는다.

## 4. 정기 집계 회차

`place_stats`를 고치는 정기 회차는 넷이고, 회차를 여는 길은 cron 발화 하나뿐이다.

```text
cron 발화 (KST)
  → ShedLock 획득 시도 → 못 잡으면 블록 없이 건너뛴다
  → 잡으면 프로세서가 자기 READ COMMITTED 트랜잭션을 연다
      → 집계 문장 → 번호 UPDATE → 커밋
  → 실패하면 회차별 시도 횟수까지 재시도 (시도마다 새 트랜잭션)
  → 끝까지 실패하면 이번 회차를 포기한다
```

| 회차 | 기본 발화 | 하는 일 | 락 이름 / lockAtMostFor |
|---|---|---|---|
| 북마크 델타 소비 | 매시 :00 :15 :30 :45 | 전표를 삼켜 `bookmark_count`에 더한다 | place-stats-bookmark-delta / 10분 |
| 리뷰 카운트 | 매시 :05 :20 :35 :50 | `review_count`·`avg_rating` 전량 재계산 | place-stats-count / 10분 |
| 인기 점수 | 매시 :10 | 인기 점수 채점 | place-stats-score / 30분 |
| 카운트 안전망 | 매일 01:25 | `bookmark_count`를 원본에서 다시 세고 전표를 비운다 | place-stats-count-safety / 10분 |

발화를 DB에 남기지 않으므로 놓친 회차를 되짚는 장치가 없다. 값이 낡는 상한은 곧 회차
간격이다. 네 회차가 모두 그 시점의 원본에서 값을 다시 만드는 재계산(델타는 그때까지 쌓인
전표 전부)이라, 놓친 발화를 소급해 돌려도 다음 발화 한 번의 결과와 같다. 인스턴스가 발화
순간에 죽거나 스케줄러 스레드가 앞 회차에 묶여 발화가 밀려도 마찬가지다.

안전망만 하루 1회인 이유는 그 회차가 북마크 전량 스캔이기 때문이다. 북마크 축은 델타로
바뀌면서 정확성이 전표 발행·소비 규칙 위에 서게 됐고, 규칙에 버그가 생기면 카운트가 조용히
어긋난다. 안전망은 그 표류의 상한을 하루로 자른다. 15분 격자로 올리면 델타 설계가 걷어낸
전량 스캔이 그대로 되돌아온다. 리뷰 수·평균 평점은 리뷰 회차가 매번 전량 재계산하므로
안전망이 다시 세지 않는다.

ShedLock이 지키는 것은 "정시에 한 인스턴스만 돈다"이고, `lockAtMostFor`는 임대다. 회차가
그 상한을 넘겨 돌면 락이 풀린 채 계속 돌고 그 창에서 다른 인스턴스가 같은 회차를 시작할 수
있다. 그 겹침을 막는 장치는 없다. 겹쳤을 때 값이 어떻게 되는지는 확인하지 않았다. 두 회차는
각자 기준 시각을 잡으므로 읽기 뷰가 다르고 나중에 커밋한 쪽이 이긴다.

네 회차는 같은 분에 겹치지 않고 최소 5분씩 떨어져 있다. 5분이 충분하다는 보장은 없다.
회차 소요는 데이터 양과 그때의 DB 상태에 달렸고, 실제 소요는 회차 종료 로그에만 남는다.
가장 좁은 자리는 전표를 두고 만나는 안전망(01:25)과 델타(01:30)다.

신선도의 대가가 있다. 집계가 값을 고칠 때마다 `cursor_version`이 오르므로, 델타가 전표를
삼킬 때마다 진행 중인 스크롤이 만료될 수 있다. 15분마다 그럴 수 있다는 뜻이다.

배포 환경의 cron은 저장소에 없다. `application.yml`은 `.gitignore`에 걸려 있고 CI/CD가
시크릿 본문으로 덮어쓴다. 그 본문에 옛 cron이 남아 있으면 코드 기본값을 이긴다.

## 5. 각 서버는 번호를 보고 자기 스냅샷을 다시 짓는다

모든 서버에 기본 1분 간격의 폴이 있다. 폴이 하는 일은 번호 한 행을 읽는 것뿐이다.

```text
폴 (1분마다)
  → place_list_snapshot_metadata 한 행 조회
  ├── 읽은 번호가 설치한 번호보다 새것이 아니다 → 끝. 원본 테이블을 건드리지 않는다
  └── 새것이다 → 이 번호를 목표로 리빌드를 부른다

리빌드
  → 새 트랜잭션 (REQUIRES_NEW · REPEATABLE READ 명시 · readOnly)
      → 첫 문장: 번호 한 행 읽기
      → 읽은 번호를 알린다 (원본을 읽기 전에)
      → place_stats 전량 읽기
      → tags 전량 읽기
  → 트랜잭션 종료
  → 행을 PlaceEntry·PlaceView·TagView로 조립
  → 정렬 배열 구성
  → 로컬 갱신 잠금 안에서
      ├── 읽어 온 번호가 설치한 것보다 새것이 아니면 버린다
      ├── 새 표시값 맵 위에 그 시점 뒤에 커밋된 표시값 패치를 먼저 합친다
      └── 표시값 맵 교체 → 스냅샷(번호 쌍, 정렬 배열) 채택
```

번호와 데이터가 같은 시점인 근거는 read view 하나다. InnoDB의 REPEATABLE READ는 트랜잭션의
첫 일반 SELECT에서 read view를 만들고 그 뒤 모든 문장이 같은 시점을 본다. 그래서 번호를 먼저
읽든 나중에 읽든 값은 같다. 번호를 첫 문장으로 두는 것은 read view가 열리는 자리를 코드에서
드러내는 규칙이지 정합성의 조건이 아니다. 정합성이 실제로 걸린 곳은 쓰기 쪽이다. 목록을 바꾸는
트랜잭션이 같은 트랜잭션에서 번호를 올리므로, 이 read view가 어떤 변경을 보았다면 그 변경의
번호도 함께 본다.

설치하는 것은 실제로 읽은 번호다. 폴에서 본 번호나 완료 시점의 최신 번호를 붙이지 않는다.
읽은 뒤에 더 많은 변경이 커밋됐다면 그것은 다음 폴이 번호 차이로 알아본다.

### 겹치는 리빌드는 붙는다

리빌드를 부르는 곳은 셋이다. 기동, 폴, 목록 요청. 셋 다 같은 문을 지나고, 그 문 뒤에는 지금
도는 리빌드들의 목록이 있다. 부르는 쪽은 자기가 방금 DB에서 읽은 번호를 목표로 들고 온다.

```text
리빌드를 부른다 (목표 = 방금 읽은 번호)
  → 도는 리빌드를 훑는다
  ├── 읽은 번호가 아직 비어 있는 것이 있다      → 거기 붙는다
  ├── 읽은 번호가 내 목표보다 낡지 않은 것이 있다 → 거기 붙는다
  └── 둘 다 없다                              → 하나 더 띄운다
```

읽은 번호가 비어 있는데도 붙어도 되는 근거는 read view 하나다. 그 리빌드의 첫 SELECT는 내가
DB를 읽은 뒤에 도니, 내가 본 최신을 반드시 담는다. 그래서 하나 더 띄우는 경우는 도는 것들이
전부 내 목표보다 앞선 시점을 읽고 있을 때뿐이다.

이 규칙이 막는 것은 캐시 미스 스탬피드다. 같은 회차를 필요로 하는 요청이 한꺼번에 몰려도 전량
읽기는 첫 하나뿐이고 나머지는 거기 붙는다. 동시에 도는 리빌드 수의 상한은 "리빌드 한 번 도는
동안 커밋된 서로 다른 버전의 수"이고, 요청 수와는 무관하다.

리빌드가 도는 실행기는 스레드 둘 고정이다. 셋 이상이 겹치는 일은 드물지만 겹치면 힙 압박은
확실하다. 무부하 x10 측정에서 리빌드 한 번이 250.3~253.2 MB를 할당했다
(`docs/perf/2026-09-10-current-snapshot-rebuild-x10.md`). 셋째는 대기열에서 앞의 것을 기다리고,
그동안 오는 쪽은 읽은 번호가 비어 있는 그 셋째에 전부 붙는다. 그래서 대기열 길이는 규칙상 최대
1이다.

폴 간격 안에 변경이 여러 건 쌓이면 리빌드 한 번이 최신 상태를 통째로 읽는다. 중간 번호마다
짓지 않는다. 폴 간격이 정하는 것은 커서가 오르지 않는 변경, 즉 관리자의 표시값 수정이 다른
서버에 닿는 상한이다. 커서가 오르는 변경은 그 회차를 필요로 하는 첫 요청이 폴과 무관하게
리빌드를 띄운다(6절).

실패하면 기존 스냅샷을 그대로 두고 경고를 남긴다. 그것으로 끝이다. 따로 쉬는 시간도 재시도
횟수도 없고, 다음 폴이나 다음 요청이 다시 띄운다. 폴이 띄우는 리빌드는 간격마다 하나이므로,
실패가 연달아 나도 폴이 내는 전량 읽기는 간격당 한 번을 넘지 않는다.

## 6. 요청은 어느 회차로 답하는가

메모리 목록을 쓰는 요청은 예외 없이 `cursor_version` 한 행을 DB에서 읽는다. 로컬 회차와 커서가
맞으면 그 조회를 건너뛰고 싶어지지만, 그 최적화는 정확히 틀린 경우를 놓친다. 이 서버가 뒤처져
있고 커서도 그만큼 낡은 경우 둘이 서로 맞으므로, 아무 문제 없어 보이는 채로 옛 회차를
최신이라 말하며 서빙한다.

```text
목록 요청
  → 동네·태그·정렬·필터·커서 형식 검증 (페이지는 만들지 않는다)   ← 대기보다 먼저
  → 북마크 검색이면 DB 경로로 바로 응답
  → 공유 cursor_version 읽기 = shared, 이 서버의 설치 회차 = mine

첫 페이지
  ├── mine >= shared → 지금 스냅샷으로 응답
  └── mine <  shared → shared 설치를 기다렸다가 로컬 스냅샷으로 응답

커서가 있는 요청 (커서의 회차 = wanted)
  ├── wanted != shared → PLACE-006 만료. 뒤처졌으면 리빌드는 띄워 두되 기다리지 않는다
  ├── mine == shared   → 지금 스냅샷으로 응답
  ├── mine >  shared   → PLACE-006 만료. 번호를 읽은 뒤 이 서버가 더 나아갔다
  └── mine <  shared   → shared 설치를 기다렸다가 로컬 스냅샷으로 응답
```

검증이 대기보다 먼저인 이유는, 대기 뒤에 있으면 애초에 잘못된 요청이 400 대신 예산을 다 쓰고
503으로 나가 클라이언트가 고칠 곳을 잘못 짚기 때문이다.

공유 회차와 로컬 회차가 같으면 `revision`이 달라도 기다리지 않는다. 표시값이나 소속이 조금
낡았을 수 있지만, 그것을 요청이 기다려서 메우는 순간 모든 첫 페이지가 리빌드를 기다리게 된다.
반영은 폴이 맡는다.

기다리는 요청은 대기표를 하나 등록하고, 읽은 번호를 목표로 리빌드를 부른다(5절의 규칙대로
붙거나 띄운다). 대기표는 설치된 `cursor_version`이 목표 이상일 때만 깨어난다. 목표에 못 미치는
설치, 즉 대기표가 붙은 시점에 이미 더 앞선 시점을 읽고 있던 리빌드가 끝난 경우는 그냥 지나간다.
깨워 봐야 요청이 다시 판정하고 다시 기다릴 뿐이다.

깨어난 요청은 번호를 다시 읽지 않는다. 목표가 설치됐다는 것이 깨어난 조건 자체라 다시 읽어
확인할 것이 없고, 그대로 로컬 스냅샷으로 응답한다. 요청 하나가 내는 번호 조회는 언제나 한
번이다. 그래서 요청 쪽 규칙이 둘로 준다. 목표가 설치되면 답하고, 예산을 넘기면 503이다.
재판정 루프도 그 횟수 상한도 없다.

기본 예산은 `solply.place-list-snapshot.request-wait-timeout-ms=3000`이다. 서블릿 비동기
응답을 쓰므로 기다리는 동안 요청 스레드도 DB 커넥션도 잡지 않는다. 예산 안에 설치되지 않으면
`PLACE-007`(503)로 답한다. 클라이언트는 보고 있던 목록을 그대로 두고 같은 커서로 다시 시도하면
된다. 리빌드가 실패해도 대기표를 즉시 깨우지 않는다. 다음 폴이나 다음 요청이 다시 띄우고,
예산은 요청 쪽 시계가 끊는다. 한 요청의 시간 초과는 공용 리빌드를 취소하지 않으므로 다른 요청과
다음 폴은 계속 그 결과를 쓴다.

보장의 범위는 번호를 읽은 그 시점까지다. 한 번의 기다림이 겨누는 목표는 그때 관측한 값으로
고정되고, 기다리는 사이 공유 회차가 또 올라도 그 기다림이 늘어나지 않는다. 기다리는 사이 이
서버가 목표를 지나쳐 설치했다면, 재개한 커서 요청은 페이지를 만들 때 커서 회차 대조에 걸려
`PLACE-006` 만료로 끊긴다. 이미 교체된 커서를 옛 회차로 되살리는 일은 하지 않는다.

## 7. 기동과 수렴

```text
기동
  → 포트를 열기 전에, 부르는 스레드에서 동기로 첫 리빌드
  ├── 성공 → 준비 완료
  └── 실패 → 폴 간격만큼 쉬고 다시 시도
        → 기본 60초 안에 성공하지 못하면 컨텍스트 기동 실패
```

빈 목록은 "장소가 없다"와 구분되지 않는 정상 응답이라, 데이터가 있는데 못 읽은 서버가 그것을
내보내면 클라이언트는 오류인 줄도 모른다. 그래서 짓지 못한 서버는 트래픽을 한 건도 받지 않는다.
60초는 "다시 시도하지 않기로 하는 기한"이지 한 번의 DB 읽기를 끊는 상한이 아니다. 개별 DB
호출의 상한은 커넥션·쿼리 타임아웃이 정한다.

신규 서버는 남을 기다리지 않는다. 기다릴 대상은 DB가 응답하는 것뿐이다. 서버마다 폴 시점과
리빌드 시점이 다르므로 같은 순간에 모든 서버가 같은 회차를 들고 있지는 않다. 정상 갱신이
이어지는 한 모든 서버가 최신 번호로 수렴한다는 것이 이 구조의 보장이고, 동시에 같아진다는
것은 아니다. 그 차이를 요청이 메우는 자리가 6절이다.

## 8. 실패와 복구

| 실패 지점 | 남는 상태와 후속 처리 |
|---|---|
| 관리자 트랜잭션 실패 | 원본과 번호 함께 롤백. 아무 서버도 변경을 보지 않는다 |
| 관리자 커밋 뒤 표시값 패치 실패 | 번호는 올라 있음. 다음 리빌드가 원본에서 가져온다 |
| 집계 트랜잭션 실패 | 통계·전표 소비·번호 함께 롤백. 회차 내 재시도, 끝까지 실패하면 다음 정시 발화 |
| 발화 순간 인스턴스 종료·발화 밀림 | 그 회차는 없던 일. 다음 정시 발화가 최신 원본으로 다시 만든다 |
| 서버의 리빌드 실패 | 기존 스냅샷 유지. 다음 폴이나 다음 요청이 다시 띄운다, 대기 중인 요청은 예산까지 기다린다 |
| 번호 조회 실패(요청 경로) | 로컬 회차를 최신이라 말하지 않고 PLACE-007. 로컬 폴백 없음 |
| 기동 리빌드 실패 | 60초 안에 재시도, 실패하면 그 서버는 뜨지 않는다 |

스냅샷 폴은 집계 회차와 스레드를 나눠 쓰지 않는다. 집계 회차는 스레드 넷짜리 배치 스케줄러에서
돌고, 폴은 전용 스레드 하나에서 돌며 리빌드를 스레드 둘짜리 전용 실행기에 맡기고 바로 돌아온다. 폴
간격이 목록 요청의 대기 예산 안에 들어가는 값이라, 몇 분짜리 집계 회차 뒤에 줄을 세우지 않은
것이다. 그래도 폴 간격은 반영 지연의 보장 상한이 아니다. 실제 지연은 폴 간격 + 원본 읽기·정렬
시간이다.

## 9. 비용의 범위와 측정 한계

서버마다 원본을 전량 읽고 정렬한다. 서버가 n대면 같은 읽기와 정렬이 n번 일어난다. 그 대신
payload 저장·전송·복원, 발행 포인터 경쟁, 소비자 소유권 같은 공유 기준이 없다.

기본 설정의 근거는 실측 하나와 예산 하나다. 옛 커밋(`f2d7724`) 기준 x10 데이터셋 63,200
장소를 2 vCPU / Xmx1280MiB에서 무부하로 전량 다시 지었을 때 리빌드 한 회차의 중앙값이
185ms였고(`docs/perf/2026-09-10-current-snapshot-rebuild-x10.md`, 15회 발화), 그 창에서
CPU 스로틀링과 자연 Full GC는 0이었다. 185ms는 원본 읽기·조립·정렬·설치를 합친 값이지 DB
읽기만의 시간이 아니다. 무부하 측정이라 사용자 부하 중의 요청 지연이나 여러 서버가 동시에
리빌드할 때의 DB 부하는 이 숫자로 말할 수 없다. 현재 코드로 다시 잰 값도 아니다. 1분·3초·
60초는 이 근거 위의 초기값이지 검증된 상한이 아니다.

| 측정 대상 | 함께 확인할 값 |
|---|---|
| 리빌드 한 회차 | 원본 읽기·조립·정렬·설치 시간, CPU, 할당량 |
| 갱신 중 메모리 | 옛 스냅샷과 새 스냅샷이 공존하는 구간의 최대 점유, 자연 GC 횟수·정지 |
| 사용자 영향 | 리빌드 중 조회 지연 분포, 대기표의 실제 완료 시간, 503 비율 |
| 여러 서버 | 같은 번호 변경에 서버들이 몰려 읽을 때의 DB 부하, 서버별 수렴 시차 |
| 집계 회차 | 15분 격자에서 회차별 소요, 회차 겹침 여부, 스크롤 만료 빈도 |

## 10. 확장 후보와 그것이 줄이는 것

각 후보는 다른 비용을 줄인다. 비용이 측정으로 확인될 때만 선택지가 된다.

| 후보 | 줄이는 것 | 남는 것 |
|---|---|---|
| 원시 자료구조(객체 배열 대신 열 배열) | 객체 할당과 힙 점유 | 읽기와 정렬 자체 |
| 동네 단위 재생성 | 재생성 대상 범위와 연산량 | 어느 동네를 다시 지을지 관리하는 기준 |
| 정렬 결과까지 직렬화하는 공유 빌더 | 서버마다 반복되는 DB 전량 조회와 정렬 | 다운로드·역직렬화·메모리 할당, 발행 기준 관리 |

Redis를 두는 것 자체가 정렬 비용을 없애지는 않는다. 정렬 결과를 재사용할 수 있는 저장 형식이
핵심이고, 그것은 저장소가 MySQL이든 Redis든 같은 질문이다.
