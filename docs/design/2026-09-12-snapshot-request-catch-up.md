# 장소 목록 요청의 스냅샷 적재 대기

## 요청 계약

- 일반 첫 페이지는 요청을 검증하고 MySQL 현재 발행 ID를 확인한다. 로컬이 뒤처졌다면 현재 발행물을 적재한 뒤 응답을 다시 구성한다. 표시값만 바뀐 발행도 비교 대상이다.
- 커서 요청은 로컬 버전이 일치하면 추가 발행 조회 없이 처리한다. 불일치할 때만 DB 현재 커서 버전을 확인한다.
- 공유 현재 커서와도 다르면 기존 `PLACE-006`(400)이다. 공유 현재와 같고 로컬이 뒤처졌다면 적재를 기다려 동일 커서로 다시 조회한다.
- 북마크 검색은 기존 DB 경로를 유지한다.
- 적재 실패·대기 시간 초과·발행 정보 조회 실패·실행기 거절은 `PLACE-007`(503)이다. 클라이언트는 목록을 유지하고 같은 커서로 재시도한다. 첫 페이지도 동일 조건에서 503을 받는다.
- 과거 발행물 복원이나 커서 이력 보관은 추가하지 않는다. 기다리는 사이 구조 발행이 바뀌면 커서가 실제로 만료될 수 있다.

## 인스턴스 내부 조정

```text
요청 또는 설치 폴
  → AtomicReference의 진행 중 Future 확인
      ├── 있음 → 같은 결과 공유
      └── 없음 → CAS로 등록한 한 호출만 적재 제출
                    → 전용 스레드에서 다운로드·검증·디코딩
                    → 설치 잠금 안에서 최신 발행 ID 재확인
                    → 채택 후 Future 완료
```

전용 적재 실행기는 스레드 1개, 큐 길이 1, 초과 시 거절 정책이다. 기본 스케줄러 풀은 확대하지 않는다. 설치 폴은 기다리지 않고 반환한다. 관리자 훅과 기동 복원은 직접 설치하며, 관리자 훅이 잡은 잠금을 다른 적재 스레드가 기다리는 교착을 피한다. 늦은 설치가 최신 상태를 덮지 않도록 설치 ID를 잠금 안에서 재검사한다.

## 대기 시간과 스레드

`solply.place-list-snapshot.request-wait-timeout-ms`의 기본값은 2000ms다. 한 요청에서 같은 절대 deadline을 사용하며 적재 대기와 재개 실행기의 큐 대기를 제한한다. 최대 적재 대기 횟수는 2회다. 첫 페이지는 처음 관측한 발행을 기준으로 판단해 계속 새로운 발행을 쫓지 않는다.

컨트롤러는 CompletableFuture를 반환한다. 완료 뒤 응답 재구성과 DB 조회는 기존 applicationTaskExecutor에서 수행하며, 적재 스레드와 타이머 스레드에서는 수행하지 않는다. 큐에서 실행되기 전에 시간 초과된 요청은 재조회를 건너뛴다. 요청의 시간 초과는 공유 적재를 취소하지 않는다.

초기 동기 검증·응답 구성·DB 조회와 이미 시작한 재개의 수행 시간은 강제로 중단하지 않는다. 따라서 이 설정은 전체 HTTP 응답의 2초 상한이 아니다. 공용 재개 실행기의 큐 크기 자체도 제한하는 변경이 아니며 부하에 따른 큐 점유는 별도 관측이 필요하다.

## 비용과 검증 범위

첫 페이지마다 작은 발행 메타데이터 조회가 추가된다. 로컬이 뒤처진 경우 초기 응답 구성을 버리고 다시 구성하므로 동네·북마크 조회 등이 반복될 수 있다. 공유 적재는 중복 payload 다운로드를 줄이지만 관리자 직접 설치와 겹치는 다운로드까지 하나로 묶지는 않는다.

검증에서는 요청과 폴의 중복 적재 방지, 늦은 인스턴스의 동일 커서 복구, 첫 페이지 발행 ID 비교, 실제 커서 만료, 실패·시간 초과의 503 JSON, 사용자 식별자 유지, 큐가 막힌 경우의 시간 초과, 공유 적재의 지속을 확인한다. 신규 테스트 결과는 검증 완료 후 별도 기록한다.
