## 1. 무엇을 바꿨는가

`PlaceListDbQueryRepository.appendTagFilters`의 문자열 세 개다. 인기순과 최신순이 이 메서드를
공유하므로 한 번 고쳐 두 경로가 함께 바뀐다.

```sql
-- before
EXISTS (SELECT 1 FROM place_tag pt JOIN tags t ON t.id = pt.tag_id
         WHERE pt.place_id = ? AND t.id = :tagId AND t.active = 1)
-- after
EXISTS (SELECT 1 FROM place_tag pt WHERE pt.place_id = ? AND pt.tag_id = :tagId)
```

스키마 변경도, 인덱스 추가도, 힌트도 없다.

## 3. 케이스가 무엇을 조회하는가

**조회 범위**는 둘이다. 동네 1곳(`town_id = 301`, 활성 장소 **100개**)과 그 시의 동네 18곳
(`301~318`, 활성 장소 **1,800개**). 사용자가 동네를 하나 고르면 앞쪽, 시를 고르면 뒤쪽이다.

**태그 조합**은 넷이다.

| 이름 | 사용자가 고른 것 | 그 태그가 붙은 장소(전국) |
|---|---|---|
| `카페` | 메인 태그 하나 | 1,146곳 |
| **`카페` + 옵션 2종** | 메인 `카페` + 옵션1 `커피/디저트·작업·독서·힐링` 중 하나 + 옵션2 `시그니처메뉴·감성인테리어·채광좋음·콘센트많음·시간제한없음·바테이블` 중 하나 | 옵션1 각 424~455곳 · 옵션2 각 287~312곳 |
| `음식`+`바/술집` (희귀) | 메인 `음식` + 옵션1 `바/술집` | `음식` 1,094곳 · **`바/술집` 185곳** |
| `맛집 · 디저트` (0건) | 메인 태그 하나 | **0곳** |

서브 태그는 **타입 내 OR, 타입 간 AND**다. 그래서 두 번째 줄은 "카페이면서, 옵션1 넷 중 하나이면서,
옵션2 여섯 중 하나"를 뜻한다 — 화면에서 칩을 여러 개 눌렀을 때 나가는 가장 무거운 요청이다.

`맛집 · 디저트`는 억지로 만든 입력이 아니다. 활성 MAIN 태그라 `TagValidator`를 통과하고 사용자가
고를 수 있는 선택지인데, 아직 그 태그가 붙은 장소가 없을 뿐이다. **태그를 새로 추가한 직후가 정확히
이 상태다.**

모든 요청은 `LIMIT 11`로 나간다 — 첫 페이지 10건 + 다음 페이지가 있는지 판정할 1건
(`PlaceService.DEFAULT_PAGE_SIZE`).

### 4.3 "차이 없음"으로 읽은 근거

결과 0건 태그(인기순)는 0.011 → 0.016으로 숫자만 보면 1.5배 느리다. 그러나 **트리가 노드 단위로
같다.**

```
-> Sort: ... limit input to 11 row(s) per chunk
    -> Stream results
        -> Nested loop inner join
            -> Index lookup on pt using idx_place_tag_tag_id (tag_id=31)  rows=0
            -> Single-row index lookup on ps using PRIMARY  (never executed)
```

before에서도 `tags`는 트리에 없다 — `t.id = 31`이 PK 등호라 상수로 접혀 사라진다. 즉 두 형상이
**같은 일을 하고** 절대값이 10~20µs라 그 크기의 흔들림은 노이즈다. 희귀 서브태그도 마찬가지로
트리가 같다 — 그쪽은 after가 더 빠른 칸(인기순 동네 18곳 0.842 → 0.655)과 더 느린 칸(최신순 동네
18곳 0.718 → 0.899)이 섞여 있는데, 트리가 같으니 방향에 의미를 두지 않는다.

**이것이 주장 ②의 핵심이다.** 오추정이 판단을 좌우하지 않던 입력에서는 아무것도 바뀌지 않는다.

### 4.4 V31 이전 회차와의 차이

이 캠페인은 두 번 돌았다. 처음(`baseline.txt`)은 최신순 정렬 인덱스가 없던 상태였고, 본문 수치는
V31을 적용한 두 번째 회차(`with-v31.txt`)다. **`tags` 조인 제거의 A/B로는 두 회차 모두 유효하다**
— 각 회차 안에서 before/after의 인덱스 조건이 같기 때문이다. 다만 최신순의 절대값이 달라진다.

| 최신순 · after | V31 이전 | V31 적용 |
|---|---:|---:|
| 동네 1곳 · `카페` + 옵션 2종 | 0.253ms | **0.184ms** |
| 동네 1곳 · `카페` | 0.214ms | **0.099ms** |
| 동네 18곳 · `카페` | 2.370ms | **1.800ms** |
| 동네 18곳 · `카페` + 옵션 2종 | 2.800ms | 2.770ms |

마지막 줄이 거의 같은 이유는 그 조합만 주도 테이블이 `place_tag`라 `places` 인덱스를 쓰지 않기
때문이다. 인기순은 `place_stats` 단독이라 두 회차가 전부 오차 범위 안이다(예: 동네 1곳 태그 3개
0.180 → 0.170) — **V31과 무관한 경로가 안 움직였다는 것이 이 재측정의 대조군 역할을 한다.**

**정정 하나.** V31 이전 회차에서 "동네 1곳 · `카페` 하나"를 인기순 5.6배 · 최신순 2.3배 개선으로
읽었는데 **그것은 노이즈였다.** 그 회차의 before 3회가 각각 0.445 / 3.27 / 0.0622ms로 50배 넘게
흔들렸다. 재측정에서는 0.089 / 0.070 / 0.076으로 안정적이고, before와 after가 사실상 같다
(0.076 vs 0.082).

**개선이 없는 것이 오히려 설명과 맞는다.** 단일 태그는 `t.id = :mainTagId`가 PK 등호라 `tags`가
상수로 접히고(트리에 나타나지도 않는다) 다른 태그 집합과 결합되지 않는다. 10% 과소평가가 한 번만
적용되므로 태그 후보 추정이 1,146개에서 100여 개로 줄어들 뿐, 지역 후보 100개보다 작아지지 않는다.
그래서 before·after의 트리가 노드 단위로 같다 — 둘 다 `Covering index lookup on ps` 주도에
`uk_place_tag_place_tag` 단건 확인이다.

복수 태그에서 무너지는 이유는 다르다. 서브 태그의 `IN (7,8,9,10)`·`IN (11..16)`은 범위라 상수로
접히지 않고, 각각 4개·6개인 후보 집합이 **조건 없는 해시 조인으로 카테시안 결합**된다. 두 집합에
10% 과소평가가 각각 적용된 뒤 곱해지면서 실제 24행이 0.024행으로 예상됐다.

## 5. 왜 이렇게 되는가

### 5.1 뒤집힘이 사라진 자리 — 동네 1개 + 태그 3개

before는 태그 두 축의 해시 조인 결과를 `rows=0.024`로 보고 `place_tag`에서 시작했다. 그 결과
`place_tag` 엔트리 **10,536건**을 훑고 장소를 10,536번 PK 조회한 뒤 weedout까지 돌았다(11.3ms).

after는 추측할 조건이 없어 태그 쪽 추정이 정직해지고, 그러면 **100 < 1,146**이라 지역에서 시작하는
것이 싸다는 판단이 나온다. 인기순은 랭킹 인덱스를 그대로 타고 17행만에 11건을 채웠다(0.170ms).

### 5.2 뒤집힘이 남은 자리 — 시 단위 + 태그 3개

시 단위는 after에서도 주도 테이블이 `place_tag`다. 정직해진 숫자로도 **1,146 < 1,800**이기 때문이다.
그래도 5.1~7.5배 좋아진 것은 판단이 바뀌어서가 아니라 **훑는 양이 줄어서**다 — 10,536 엔트리 +
weedout이 1,146 엔트리로 내려앉았다.

**남은 이 선택은 결함이 아니다.** 태그 쪽이 실제로 더 작으면 거기서 시작하는 게 맞다.

### 5.3 그래서 힌트를 쓰지 않았다

`JOIN_PREFIX(ps)`로 지역 주도를 강제하면 시 단위 + 흔한 태그 3개가 3.76 → 0.90ms로 4.2배 빨라진다.
그러나 같은 힌트가 다른 입력에서는 손해다.

| 시 단위 · 인기순 (`tags` 제거 상태) | 힌트 없음 | `JOIN_PREFIX(ps)` |
|---|---:|---:|
| 흔한 태그 3개 | 3.76ms | **0.90ms** |
| 희귀 서브태그(185건) | **0.58ms** | 1.10ms |
| 결과 0건 태그 | **0.034ms** | 2.56ms |

결과 0건 태그는 옵티마이저가 태그부터 뒤져 **0건을 확인하고 즉시 끝낸다.** 힌트를 박으면 1,800건을
정렬해 놓고 하나씩 확인하다 아무것도 못 건진다 — **75배 손해**다.

즉 힌트는 특정 입력만 개선하고 **데이터 분포에 따라 계획을 바꿀 여지를 없앤다.** 빠른 계획 하나를
못 박는 대신, 잘못된 선택을 유발하던 정보를 바로잡는 쪽을 택했다.

(이 표는 위 32건 채취와 별개로 잰 즉석 비교다. 캠페인 원자료에는 없다.)

### 5.4 히스토그램은 왜 아닌가

`ANALYZE TABLE tags UPDATE HISTOGRAM ON active`도 같은 곳에 도착한다(최신순 시 단위 22.6 → 2.62ms).
코드를 한 글자도 안 바꾸고 되니 매력적이지만 택하지 않았다.

MySQL 히스토그램은 **자동 갱신되지 않고 `mysqldump`에도 실리지 않는다.** 새 환경을 세우거나 DB를
복원했는데 `ANALYZE`를 빠뜨리면 **아무 에러 없이 22ms로 되돌아간다.** 조인 제거는 성능이 코드에
담기므로 어느 환경에 배포하든 같은 문장이 나간다.

두 처방을 겹쳐도 추가 이득이 없다는 것(2.47 vs 2.73/2.62, 오차 범위)이 **같은 원인을 두 방법으로
고치는 것**임을 보여 준다.

## 6. 이 채취로 말할 수 없는 것

- **처리량·레이턴시에 대해 아무 주장도 하지 않는다.** 부하 0에서 단일 문장을 잰 CPU 시간이고,
  요청 하나는 이 문장 말고도 SQL을 여러 개 쓴다. 66배는 **이 문장의** 배수다.
- **실트래픽에서 태그 필터 요청의 비중을 모른다.** 어떤 조합이 얼마나 오는지 모르는 채로 잰
  값이라, 전체 응답시간에 미치는 몫은 별도 관측이 필요하다.
- **비활성 태그가 있는 환경에서 같은 배수가 나오는지 모른다.** 이 시드는 `tags` 34행이 전부
  활성이라 `filtered 10.00`의 오차가 최대인 조건이다.
- **오추정의 원인을 `t.active = 1`로 특정한 근거는 "그것을 지우니 사라졌다"까지다.**
  `optimizer_trace`로 계수 연쇄를 확인하지는 않았다. 실제로 트리의 `rows=0.024`가 `0.4 × 0.6`과
  맞지 않아 계수 하나가 더 곱해진 자리가 있는데, 그것이 어디서 왔는지는 못 짚었다.
- **`JOIN_PREFIX`·히스토그램 수치(§5.3·§5.4)는 캠페인 밖의 즉석 측정이다.** 워밍업 후 3회 중앙값이긴
  하나 원자료가 캠페인에 남아 있지 않다.

## 7. 다음에 볼 것

1. **동네 18곳 + 흔한 태그 3개의 4.34ms(인기순)** — 조기 종료를 살리면 0.90ms까지 갈 여지가 있으나,
   힌트로는 다른 입력을 망가뜨린다. 태그 분포를 보고 힌트를 **동적으로** 붙이는 방법이 있지만
   그건 옵티마이저가 이미 하는 일을 애플리케이션에서 다시 하는 것이라 신중해야 한다.
2. **실트래픽의 태그 필터 비중 관측** — 위 1번을 할 가치가 있는지는 이것이 먼저 답한다.
3. **`PlaceTagMatcher`(북마크 검색)와의 비대칭** — 그쪽은 여전히 엔티티에서 타입·활성을 본다.
   갈리는 입력은 상위 검증이 튕겨내므로 관측되지 않지만, 두 경로가 다른 규칙을 들고 있다는 사실은
   남는다.
