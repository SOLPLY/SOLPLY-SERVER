# 어드민 수정은 언제 스냅샷을 다시 만들고, 언제 표시값만 바꾸는가

작성일: 2026-09-09 · 측정 반영 2026-09-10
배경 글: [조회 전용 인메모리 정렬 전환](2026-08-29-inmemory-read-model.md)
설계·판단 기록 전문: `docs/design/2026-09-09-admin-display-view-split.md`,
`docs/design/2026-09-10-inmemory-snapshot-decision.md`

## 1. 이 서비스에서 가장 중요한 것

솔플리에서 가장 많이 불리는 API는 장소 목록 조회다. 앱 서버 2 vCPU에서 평상시 초당 60명,
피크 초당 300명이 들어와도 느려지지 않아야 한다. 이 요구를 맞추기 위해 목록 조회는 요청
시점에 DB를 정렬하지 않는다.

- 장소 전체를 미리 읽어서 동네별로 나누고, 정렬 5종(인기·최신·평점·리뷰 수·북마크 수)마다
  정렬된 배열을 만들어 메모리에 둔다. 이 배열 묶음을 **스냅샷**이라 부른다.
- 요청은 스냅샷 배열에서 커서 위치를 이진 탐색으로 찾고, 태그로 걸러서 10건을 돌려준다.
  DB를 전혀 안 친다.
- 스냅샷은 통째로 새로 만든 뒤 참조를 한 번 바꿔 끼운다. 요청은 옛 스냅샷이나 새 스냅샷 중
  하나만 본다.

어드민 기능은 이 반대편에 있다. 하루에 수십 번 쓰이고, 장소 이름을 고치거나 동네를 옮기거나
새 장소를 등록한다. 어드민이 고친 내용은 사용자에게 바로 보여야 한다.

## 2. 문제 — 어드민 반영 방법이 사용자 조회에 영향을 준다

어드민이 고친 내용을 바로 보이게 하는 방법은 하나였다. **무엇을 고치든 스냅샷을 통째로 다시
만든다.** 장소 이름 한 글자를 고쳐도 장소 6,320개를 DB에서 다시 읽고 다섯 번 정렬한다.

지금은 0.1초 안팎이라 문제가 없다. 그런데 이 비용은 장소 수에 비례한다. 장소가 10배가 되면
그 시간도 늘고(실측은 9장), 재빌드가 도는 동안 앱 서버의 CPU를 사용자 조회와 나눠 써야 한다.

목표는 이것이었다. **어드민이 실서비스 데이터를 즉시 반영하되, 그 과정이 사용자 조회의 속도와
사용성에 영향을 주지 않게 만든다.**

## 3. 판단 기준 — "이 수정이 사용자가 보는 순서나 필터 결과를 바꾸는가"

어드민 수정을 전부 같은 방법으로 처리할 이유가 없었다. 수정 항목을 하나씩 놓고 질문 하나를
던졌다.

> 이 값을 바꾸면, 사용자 목록의 **정렬 순서**나 **태그 필터 결과**가 바뀌는가?

- **바뀐다** → 스냅샷 배열의 내용이 달라져야 한다. 스냅샷을 다시 만든다.
- **바뀌지 않는다** → 화면에 찍히는 글자나 그림만 달라진다. 스냅샷은 그대로 두고, 표시값만
  갈아끼운다.

이 기준으로 어드민 수정 항목을 나누면 다음과 같다.

| 어드민이 바꾼 것 | 순서·필터에 영향 | 처리 |
|---|---|---|
| 장소 이름, 썸네일 | 없음 | 그 장소 하나만 DB에서 다시 읽어 **표시 맵**에 넣는다 |
| 태그 이름, 태그 활성/비활성 | 없음 | **태그 맵**을 통째로 다시 읽어 교체한다(태그는 수십 개라 하나씩 고를 필요가 없다) |
| 장소 생성, 삭제 | 있음(목록에 들어오거나 빠짐) | 스냅샷 전량 재빌드 |
| 장소의 동네 이동, 좌표 변경 | 있음(어느 동네 배열에 속하는지, 거리순 결과가 바뀜) | 스냅샷 전량 재빌드 |
| 장소의 태그 집합 변경 | 있음(태그 필터 결과가 바뀜) | 스냅샷 전량 재빌드 |
| 인기 점수, 리뷰 수, 북마크 수 | 있음(정렬 키) | 배치가 채우는 값이라 배치 후 타이머 재빌드(기존과 같음) |
| 태그 타입(MAIN ↔ OPTION) | 있음(장소마다 대표 태그가 바뀜) | **수정 자체를 막았다.** 쓰이지 않는 기능이고, 열어 두면 재빌드 분기가 하나 더 생긴다 |

수정 API는 하나라서 이름부터 태그까지 한 번에 받는다. 그래서 서비스가 저장 전과 후의
동네·좌표·태그 집합을 비교한다. 하나라도 다르면 재빌드, 모두 같으면 표시 맵 갱신이다.

## 4. 표시값을 어디에 두느냐 — 스냅샷 안이 아니라 밖

표시값만 갈아끼우려면 표시값이 스냅샷 배열 안에 있으면 안 된다. 배열 원소 안에 이름이 들어
있으면 이름을 바꾸기 위해 배열 다섯 개를 건드려야 한다. 그래서 스냅샷 안팎을 이렇게 나눴다.

```
스냅샷 (버전 있음, 최근 3장 보존)
  └ 동네 × 정렬 5종 → 불변 배열
      원소에 든 것: 정렬 키, 좌표, 태그 비트   ← 조회가 비교·필터에서 읽는 값

스냅샷 밖 (버전 없음, 한 벌)
  장소 표시 맵   placeId → 이름, 썸네일, 메인 태그 id
  태그 맵        tagId   → 이름, 활성 여부

응답 한 건 = 배열 원소 + 장소 표시 맵 조회 + 태그 맵 조회
```

배열 원소에 무엇을 남기는지도 기준이 있다. **조회 요청이 비교하거나 필터링하면서 읽는 값만
원소에 둔다.** 정렬 키는 이진 탐색이 읽고, 태그 비트는 순차 스캔이 원소마다 읽고, 좌표는
거리순이 후보 전부의 값을 읽는다. 이 값들이 맵에 있으면 원소마다 맵 조회가 붙어 조회가
느려진다. 반대로 이름과 썸네일은 최종 10건에만 필요하니 맵에서 10번만 꺼내면 된다.

## 5. 데이터는 어떤 구조에 담겨 있고, 왜 그 구조인가

앱 서버 하나에 스프링 싱글톤 빈 셋이 있고, 그 안에 모든 것이 들어 있다.

```
SnapshotBox (싱글톤 빈)                                 ← 조회는 여기서 시작한다
  └ volatile List<Snapshot> snapshots                   최신이 0번, 최근 3장까지 보존
       ├ Snapshot(version = 1207, sortedPlaces)         ← 현재. 커서 없는 요청이 본다
       ├ Snapshot(version = 1206, sortedPlaces)         ← 스크롤 중인 사용자가 커서 버전으로 찾아 본다
       └ Snapshot(version = 1205, sortedPlaces)
            └ SortedPlaces                              불변
                 ├ 장소 값: PlaceEntry 객체 N개 (placeId, townId, tagMask,
                 │          popularScore, createdAt, 카운트 둘, ratingToInt, 좌표)
                 └ 정렬 순서: EnumMap<정렬 5종, HashMap<동네, PlaceEntry[]>>
                              — 같은 객체를 다섯 배열이 다른 순서로 참조

PlaceViewHolder (싱글톤 빈, 스냅샷 밖 한 벌)
  └ volatile ConcurrentHashMap<placeId, PlaceView(이름, 썸네일 파일 키, 메인 태그 id)>
                                        — URL은 응답에 실리는 10건에서만 조립한다

TagViewHolder (싱글톤 빈, 스냅샷 밖 한 벌)
  └ volatile ConcurrentHashMap<tagId, TagView(이름, 활성)>
```

읽는 쪽은 커서가 없으면 0번 사진, 있으면 커서에 실린 버전의 사진을 골라 그 인덱스에 페이지를
묻고, 돌아온 객체 10개와 두 홀더에서 응답 값을 읽는다. 쓰는 쪽(로더)은 락 안에서
새 인덱스를 만들어 사진으로 감싼 뒤 리스트를 새 사진이 앞에 붙은 것으로 바꿔 끼운다. 어드민의
표시값 수정은 스냅샷을 건드리지 않고 홀더 맵에 그 장소 하나만 put 한다.

자료구조 선택이 결과를 가른 데이터는 다섯이다. 기호는 n = 한 동네의 장소 수(현재 100~300),
k = 요청의 동네 수(최대 18), p = 페이지 크기(10).

**1. 정렬 순서 — 동네별로 미리 정렬해 둔 `PlaceEntry[]`**

- 구조: 그 동네·그 정렬 순서로 늘어선 장소 객체의 참조 배열. 정렬 5종 × 동네마다 하나. 장소
  객체는 하나뿐이고 다섯 배열이 참조를 공유한다.
- 조회:
  - 커서 위치를 이진 탐색 → O(log n), 동네당 비교 8~9회.
  - 거기서부터 순차로 p개를 채운다.
  - 여러 동네면 동네마다 이진 탐색한 뒤 크기 k인 최소 힙으로 병합 → 원소당 log k, 페이지가 찰 때까지만 전진.
- 비교한 대안과 안 택한 이유:
  - 요청마다 정렬(1세대): 후보 전량(시 단위 약 1,800개)에 n log n. 부하 측정에서 밀렸다.
  - TreeMap 같은 정렬 컬렉션: 삽입·삭제를 지원하는 대신 원소마다 노드 객체. 여기는 재빌드 때만 통째로 바뀌므로 그 지원이 필요 없다.
- 메모리: 참조 하나 4B × 5종 = 장소당 20B.

**2. 장소 값 — 장소당 객체 하나, 정렬 배열은 참조만 공유**

- 구조: `PlaceEntry` record 하나에 정렬 키 다섯·좌표·태그 비트가 들어 있다. 정렬 배열 다섯이 같은 객체를 가리키므로 "정렬 종류 × 장소 전체"를 복제하지는 않는다.
- 조회: 비교는 `sorted[mid]`로 참조를 따라가 객체의 필드를 읽는다. 순차 스캔은 원소마다 참조 한 번 + `tagBitmask` 읽기다.
- 검토하고 택하지 않은 대안 — **열별 원시 배열(SoA)**. 실제로 구현해 게이트까지 통과시킨 뒤 되돌렸다(설계 문서 §11).
  - SoA가 얻는 것: 필요한 필드만 연속으로 읽어 캐시 라인 하나로 여러 행을 처리한다. 장소 객체가 0개가 되어 Old GC 표시 대상과 재빌드 때 객체 할당이 사라진다. 63만 개 × 3장 규모면 매력적이다.
  - 기각의 핵심은 **조기 종료**다. 조회는 커서 위치부터 시작해 필요한 10건을 확보하면 즉시 중단하기 때문에 전체 후보를 순회하지 않는다. 여러 동네의 k-way merge도 동네마다 현재 원소 하나만 힙에 올린다. 그래서 후보 상한(18개 동네 × 300 = 5,400)과 요청이 실제로 읽는 수는 다르다. 실제 검사 수는 대략 결과 10 ÷ 필터 통과율이다. 통과율 50%면 20개 안팎이고, 1%로 떨어져야 1,000개다.
  - 따라서 현재 조회 경로에서 실제로 접근하는 Entry 수가 충분히 작다면, SoA의 cache locality 개선 효과 역시 제한적일 가능성이 있다. 실제 검사 건수나 cache miss가 병목이라는 관측이 없는 상태에서는 이를 위해 데이터 표현을 복잡하게 바꿀 근거가 부족하다. "배열이 작아서 캐시에 다 들어간다"는 논거는 쓰지 않는다. 문제는 배열 크기가 아니라 검사 건수이고, 객체판의 캐시 상주는 애초에 보장되지 않는다.
  - 끝까지 가는 요청은 둘이다. 희귀 태그 조합으로 거의 다 걸러지는 경우는 트래픽의 주류가 되기 어렵다고 본다(가정이다, 측정 안 함). 거리순은 커서와 무관하게 후보 전량의 좌표를 매번 읽지만, 그쪽은 메모리 읽기보다 후보당 거리 계산이 비용을 정한다.
  - 순서가 거꾸로였다. 단순한 구조 → 부하에서 병목 확인 → 프로파일러로 원인 좁힘 → 대안 구현 → 재측정이 맞는 순서인데, "객체가 많으면 GC가 힘들 수 있으니 미리 SoA"는 앞 세 단계를 건너뛴 과최적화다. 모든 판단을 숫자로 증명할 필요는 없다. "SoA는 복잡도와 버그 표면을 늘린다"는 벤치마크 없이도 확실한 설계 비용이고, "SoA가 CPU를 얼마나 줄인다"는 환경 의존이 커서 측정 없이 단정하면 안 된다.
  - 대가는 컸다. 장소 하나가 배열 열 개로 찢어져 값 하나에 첨자를 두 번 타고, 필드 하나 추가가 생성·재빌드·복사·접근자·테스트를 전부 건드리며, 이진 탐색·k-way merge·Top-K·커서까지 행 번호가 전파되어 다른 열에 잘못 적용해도 컴파일러가 못 잡는다.
  - 다시 꺼낼 신호: CPU가 이미 높은데 scan이 hot path의 큰 비중을 차지함, JFR·async-profiler에서 특정 반복문이나 객체 접근이 두드러짐, allocation rate·GC가 실제 병목으로 보임, 데이터가 수십만~수백만으로 커질 예정, p95/p99 목표가 빡빡해 몇 % CPU 절감도 의미 있음. 그때 요청당 검사한 Entry 수(무필터·흔한 태그·희귀 태그)를 재고, 두 구조를 A/B 부하 테스트나 프로파일링으로 비교한다.
  - 정렬마다 키·id·마스크만 원시 배열로 복사하고 최종 10건만 객체를 찾는 중간안도 검토했다. 객체 N개가 그대로 남아 GC 이점이 없고, 남는 locality는 이 규모에서 가장 덜 중요한 이점이라 택하지 않았다.
- 남긴 것 하나: 평점을 `BigDecimal` + `double` 두 벌에서 `int` 하나(4.50 → 450)로 줄였다. 장소마다 객체 하나가 줄고 비교가 정수끼리가 되며, 응답 시점에 스케일 2를 되씌워 DB 경로와 바이트가 같다.
- 메모리: 10배(63,200개)에서 한 장 8.9 MB 실측(장소당 약 140B — 객체 80B, 정렬 참조 20B, 좌표 `Double` 박싱 48B). 현재 규모면 한 장 1 MB 미만.

**3. 태그 필터 — 장소당 `long` 비트마스크**

- 구조: 장소의 태그 집합을 비트 하나씩으로 접은 `long` 하나. 요청의 태그도 그룹(메인·서브 둘)마다 마스크 하나로 접는다.
- 조회: 장소 하나의 판정 = `entry.tagBitmask() & mask` AND 3번. 원소당 O(1). 걸러진 원소를 거의 공짜로 지나간다.
- 비교한 대안과 안 택한 이유: 장소마다 태그 id `Set`. 원소당 해시 조회와 객체 접근이 붙는다.
- 한계: 태그 63개. 현재 34개.

**4. 표시값 — 스냅샷 밖 `ConcurrentHashMap` 한 벌**

- 구조: `placeId → (이름, 썸네일 파일 키, 메인 태그 id)`, `tagId → (이름, 활성)`. 스냅샷과 별개 객체이고 버전이 없다. 썸네일 URL은 미리 만들지 않고 응답에 실리는 10건에서만 조립한다 — 재빌드마다 N개의 문자열을 만들 이유가 없다.
- 조회: 확정된 10건에 대해서만 맵 get 10 + 10회. 정렬·필터에는 쓰이지 않는다.
- 갱신: 어드민이 이름을 고치면 그 장소 하나만 put. 스냅샷 3장이 모두 그 값을 본다.
- 비교한 대안과 안 택한 이유:
  - 배열 원소 안에 포함: 이름 하나 바꾸는 데 배열 5개를 건드린다.
  - 스냅샷마다 맵 한 벌: 어드민 수정 때 보존 3장의 맵을 모두 고쳐야 한다.
- 허용 근거: "표시값은 최신이어도 된다"는 계약(6장). 옛 스냅샷을 보는 사용자가 최신 이름을 봐도 문제가 아니다.
- 메모리: 10배에서 한 벌 8.2 MB 실측(문자 내용 제외, 장소당 약 130B). 스냅샷 한 장과 비슷한 크기이고, 한 벌이라 보존 장수만큼 곱해지지 않는다(9-2).

**5. 스냅샷 보관 — 불변 인덱스를 `volatile List`에 3장, 참조 교체**

- 구조: 새 인덱스를 다 만든 뒤 리스트 앞에 붙이고 참조를 한 번 바꾼다. 3장을 넘긴 꼬리는 버린다.
- 조회: volatile 읽기 한 번. 옛것 아니면 새것만 본다. 락 없음.
- 3장인 이유: 커서에 버전이 실려 있어 스크롤 중에 재빌드가 일어나도 그 사용자는 자기가 보던 사진을 계속 본다.
- 비교한 대안과 안 택한 이유:
  - 배열 제자리 수정: 조회가 락을 잡거나 수정 중인 배열을 본다.
  - 캐시 라이브러리(Caffeine): 갓 만든 사진을 접근 빈도가 낮다고 축출할 수 있고 청소 시점이 비결정적이다. 3장은 리스트 하나로 충분하다.

**예외 — 거리순**

- 사전 정렬이 없다. 기준점이 요청마다 달라 미리 세울 순서가 없다.
- 조회: 동네의 후보 전량(최대 k × n)에 거리 계산 → 크기 p인 최대 힙으로 가까운 p개만 유지 → O(k·n log p). 힙이 찬 뒤에는 "가장 먼 것보다 가까운가"를 원시 비교로 먼저 걸러 대부분의 후보가 객체를 만들지 않고 탈락한다.
- 비교한 대안과 안 택한 이유: 후보 전량 정렬 O(n log n).
- 요청당 비용이 후보 수에 비례하는 유일한 정렬이라 측정 믹스에서 20% 비중으로 따로 본다.

**요청 하나의 일**: DB 0회, 락 0회, 이진 탐색 k번, 페이지 크기만큼의 스캔, 맵 조회 20회.
동네 장소 수가 10배가 되면 이진 탐색 비교가 3~4회 늘어나는 것이 전부다.


## 6. 이 방식이 사용자에게 영향을 주지 않는 이유

**조회는 락을 잡지 않는다.** 재빌드도 표시 맵 갱신도 조회 경로를 막지 않는다. 재빌드는 새
배열을 다 만든 뒤 참조를 한 번 바꾸고, 표시 맵 갱신은 맵에 값을 하나 넣는 것이다.

**스크롤 중에 순서가 흔들리지 않는다.** 스냅샷은 버전을 달고 최근 3장을 보존한다. 커서에 버전이
실려 있어서, 스크롤 중에 재빌드가 일어나도 그 사용자는 자기가 보던 스냅샷을 계속 본다.

**표시값은 최신이어도 된다.** 스냅샷 밖 표시 맵은 한 벌이라, 옛 스냅샷을 보는 사용자도 최신
이름을 본다. 이것은 문제가 아니다. 사용자에게 필요한 약속은 "같은 장소가 두 번 나오거나, 봤던
장소가 다시 나오지 않는다"이고, 그것은 배열이 불변이라 지켜진다. 이름이 스크롤 도중 바뀌는
것은 오히려 어드민이 원하는 동작이다. 이 약속을 한 문장으로 적어 두었다.

> 커서는 정렬 순서의 일관성을 보장한다. 표시값과 소속(생성·삭제)은 최신 값일 수 있다.

**재빌드와 표시 맵 갱신이 겹쳐도 수정이 사라지지 않는다.** 재빌드가 DB를 읽은 뒤에 어드민이
이름을 고쳐 맵에 넣으면, 이어서 재빌드가 옛 이름이 든 맵으로 갈아끼울 수 있다. 그러면 수정이
다음 재빌드까지 10분간 사라진다. 이를 막기 위해 재빌드와 맵 갱신을 락 하나로 줄 세우고, 맵
갱신은 락을 잡은 뒤 DB를 다시 읽어 넣는다. 락을 기다리는 쪽은 어드민 훅이고 커밋 뒤에
실행되므로 어드민 화면에도 사용자 화면에도 보이지 않는다.

## 7. 왜 "장소 하나만 배열에서 고치기"까지는 가지 않았나

처음에는 여기서 더 나갔다. 동네 이동이나 생성·삭제도 스냅샷 전체를 다시 만들지 말고, 그
동네의 배열 다섯 개에서 장소 하나만 넣거나 빼자는 설계였다. 외부 리뷰 두 번을 거쳐 접었다.
이유는 두 가지다.

**아끼는 양이 작다.** 이 방식이 아끼는 것은 "DB 전량 읽기와 전 배열 재정렬"이다. 배열 하나에
원소를 끼우는 것 자체는 여전히 그 동네 크기에 비례한다. 그리고 아끼는 총량은 (재빌드 한 번의
비용 × 어드민 빈도)다. 하루 수십 회 × 0.1~0.3초면 하루 몇 초의 CPU 시간이다.

**사는 복잡도가 크다.** 장소가 배열의 어느 자리에 있는지 찾기, 동네 둘(옛 동네·새 동네)을
고치는 순서, 재빌드와 패치가 동시에 일어날 때의 처리, 중간에 실패했을 때의 복구. 그리고
정합성 규칙이 "DB대로 다시 만든다" 하나에서 둘로 늘어난다. 지금 규칙은 하나라서, 어떤 종류의
수정이든 중간에 실패해도 다음 재빌드가 고친다.

하루 몇 초를 아끼기 위해 살 물건이 아니었다. 표시값 분리만으로 어드민 수정의 대부분(이름·
썸네일·태그 이름)이 재빌드 없이 반영되므로, 재빌드가 남는 것은 소속이 바뀌는 드문 수정이다.


## 8. 통째로, 기한 없이 힙에 두는 것이 사용자 API에 해가 되지 않는가

이 구조에는 걱정이 둘 따라붙는다. 하나는 **상주 객체**다. 스냅샷은 만들어지면 교체될 때까지
살아 있으니 Old 영역에 눌러앉고, 장소 수만큼의 객체가 GC 마킹 대상이 된다. 다른 하나는
**재빌드 순간**이다. 새 스냅샷을 짓는 동안 DB 행이 객체로 바뀌며 힙이 출렁이고, 그 스레드가
CPU를 쓰며, 옛 스냅샷은 죽어도 Old에 남아 Young GC로는 걷히지 않는다.

이 둘이 사용자 조회에 해가 되는지는 순서를 지켜 봤다. 먼저 **GC 성능이 괜찮은가**를 네 축
(Throughput·Latency·Footprint·Promptness)으로 읽고, 나쁜 데가 있으면 **왜인가**를 GC 빈도·
할당률·GC 전후 힙·Old 증가·Full GC로 내려가 본다. 원인 지표부터 늘어놓으면 "그래서 사용자에게
무엇이 문제였나"가 빠진 글이 된다.

두 열을 나란히 놓는다. 왼쪽은 부하 아래 serving 정상 상태(현재 규모 6,320곳, 초당 600 요청,
2026-08-28 측정), 오른쪽은 현실적 최대 규모인 10배(63,200곳)에서 보존 스냅샷 3장이 찬 뒤 재빌드를
다섯 번씩 태운 창(무부하, 2026-09-10 측정)이다. 다른 창·다른 규모라 나란히 놓되 빼지 않는다.

| 축 | serving 정상 상태 (현재 규모, 부하 중) | 재빌드 창 (10배, 보존 3장이 찬 뒤) |
|---|---|---|
| **Throughput** — GC에 뺏기는 시간 | 정지 합이 90초 창의 0.25%, GC 스레드 CPU가 2 vCPU의 0.20% | 재빌드 한 번(0.27~0.39초)에 Young 정지 합 중앙값 0~95 ms, 최대 245 ms |
| **Latency** — 단일 정지 최대 | 재빌드를 피크 한가운데서 발화했을 때 직후 Young 정지 4.2 / 41.6 ms | Young 단일 최대 204 ms. **Full GC 0회** |
| **Footprint** — 붙드는 힙 | GC 후 바닥 89 MB | Full GC 직후 live **112 MB(힙 1,280 MB의 8.8%)**, 그중 스냅샷 3장 26.8 MB(2.1%). 재빌드 한 번의 할당 240 MB |
| **Promptness** — 죽은 것을 얼마나 빨리 걷나 | 재지 않음 | 보존이 3장으로 찬 뒤에도 GC 후 바닥이 147 → 204 → 257 MB로 오르다 Full GC에서 112 MB로 돌아옴 |
| **CPU** — 재빌드가 도는 동안 | 요청당 앱 CPU 1.8~1.9 ms, 앱 코어 0.85 | 재빌드가 도는 200~400 ms 동안 JVM이 **1.0~1.65 core**(중앙 1.33). 100 ms 쿼터를 다 채운 구간은 20회 중 3회에서 각 1회 |
| **부하 중 재빌드 시 p50** | 발화 버킷 p50 2 ms · p95 4 ms · 에러 0 (이웃 버킷과 같음) | **미측정** — 10배에서 부하 한가운데 발화는 하지 않았다 |

**serving 정상 상태에서 GC는 주항이 아니다.** 등록한 문턱(10%)의 40분의 1이고, 재빌드를 피크에
끼워 넣어도 그 버킷의 지연이 움직이지 않았다. 상주 객체가 Old에 있다는 것 자체는 비용이 아니었다.

**재빌드 창은 다르다.** 300 ms 남짓 동안 JVM이 코어 하나 반을 쓰고, Young GC가 0~2번 와서 최대
200 ms를 멈춘다. 그 순간 serving에 남는 것은 코어 0.35~1개와 힙 1,100 MB 이상이다. 힙은 넉넉하고
CPU는 짧게 좁아진다.

이제 "왜 그런가"를 원인 지표로 본다.

- **GC 빈도.** 재빌드 한 번이 240 MB를 할당한다. G1의 young 영역 크기에서 이것은 Eden을 0~2번
  채우는 양이라 Young GC가 0~2회다. 창 안에 GC가 오느냐는 그 순간 Eden이 얼마나 차 있었냐의
  우연이라 "0회"를 보장으로 읽지 않는다.
- **할당률.** 240 MB ÷ 0.27초 ≈ 0.9 GB/s. serving이 초당 600 요청에서 428 MB/s를 할당하는 것과 같은
  자릿수이고, 지속 시간이 1초 미만이다.
- **GC 전후 힙.** Young GC 직전 값은 641~962 MB까지 올라가지만 그것은 재빌드가 만든 정점이 아니라
  그때까지 쌓인 쓰레기의 높이다. 판정에 쓸 값은 Full GC 직후 112 MB다.
- **Old 증가.** 스냅샷 객체는 만들어지는 동안 전부 살아 있어 Survivor에 담기지 않고 Young GC 한두 번
  만에 Old로 조기 승격된다. 교체돼 죽은 뒤에도 Old에 남아 동시 마킹 뒤 mixed GC나 Full GC가 와야
  걷힌다. 위 표의 Promptness 행이 그 자국이고, 10배에서는 그 누적이 Full GC를 부르기 전에 라운드가
  끝났다(15회 동안 0회).
- **Full GC.** 10배에서는 없다. 100배에서는 있었고, 그것이 9-5다.

그래서 "해가 되지 않는가"의 답은 이렇다. 상주는 해가 아니고, 재빌드는 300 ms짜리 CPU 목을 만든다.
그 목이 부하 중 사용자 지연으로 드러나는지는 10배에서 직접 재지 않았고, 현재 규모에서 "무영향"
이었다는 것이 유일한 간접 증거다. 어드민 수정은 빈도가 불규칙한 소수의 사건이라 이 목을 지금 구조
변경으로 없애지 않고, 드러나는 날의 답을 10장에 적어 둔다.

## 9. 규모가 커지면 어디가 먼저 아픈가 — 추정을 측정으로 바꿔 쓴다

초안은 이 절을 추정으로 썼다. 10배와 100배를 재고 나서 다시 쓴다. 빗나간 추정은 지우지 않고
옆에 둔다.

### 9-1. 현실적인 규모

현재 장소는 6,320곳이다. 장소는 어드민이 큐레이션해 넣는 데이터라 사용자 생성 데이터처럼
폭증하지 않는다. 현실적 최대를 10배(63,200곳)로 두고 판단했고, 100배(632,000곳)는 어디서
깨지는지 보려는 극단 조건이다.

### 9-2. 힙 — 한 장 8.9 MB, 상주 전체가 힙의 8.8%

| 힙에 상주하는 것 | 10배 실측 (Full GC 직후 히스토그램) | 초안의 추정 |
|---|---|---|
| 스냅샷 한 장 (`PlaceEntry` 4.82 + 정렬 배열 1.21 + 좌표 `Double` 박싱 2.89 MB) | **8.9 MB** | 약 6 MB |
| 보존 3장 | **26.8 MB** (`PlaceEntry` 63,200 × 3개가 그대로 보인다) | 25 MB |
| 표시 홀더 한 벌 (`PlaceView` + 키 + 맵 노드, 문자 내용 제외) | **8.2 MB** (`PlaceView` 63,200 × 1개 — 복제되지 않는다) | 20 MB |
| 상주 프레임워크(스프링·하이버네이트 등) | 약 77 MB | — |
| **live 합계** | **112 MB** = 힙의 8.8% | 약 40 MB |

두 가지가 초안과 다르다. "표시 맵이 스냅샷보다 먼저 커진다"는 추정은 10배에서 맞지 않았다 —
URL을 미리 완성해 두지 않고 파일 키만 들고 응답 시점에 조립하도록 바꾼 뒤라 문자열이 가벼워졌다.
반대로 스냅샷 한 장의 셋 중 하나가 좌표 박싱이라는 것은 몰랐다. `Double` 둘이 장소마다 붙고
보존 장수만큼 곱해진다. 원시 `double`로 바꾸면 한 장에서 32%가 빠지지만, 10배에서 8.7 MB를 아끼려고
결측 표식을 코드에 들일 이유는 없어 손잡이로만 적어 둔다.

100배는 옛 로더 형상(JOIN이 있는 문장과 썸네일 전량 문장)의 값이다. Full GC 직후 생존이 720 MB로
힙의 56%였다. 10배 실측을 열 배 하면 스냅샷 3장 268 MB + 홀더 + 프레임워크로 430 MB 안팎이어야
하는데 실측은 그보다 컸고, 그 차이는 가르지 않았다.

### 9-3. 시간 — 10배 0.3초, 100배 4~5초

| 규모 | 재빌드 소요 실측 (중앙값) | 초안의 추정 |
|---|---|---|
| 현재 6,320 | 0.06~0.1초 | 0.1~0.3초 |
| 10배 63,200 | **0.27~0.39초** | 1~3초 |
| 100배 632,000 (옛 로더) | 4.4~5.2초 | 10~30초 |

추정보다 빨랐다. 문장 하나가 `place_stats` 한 테이블만 읽도록 바꾼 것(JOIN과 썸네일 전량 문장
제거)이 컸다. 재빌드 시간이 길어질 때 먼저 영향받는 것은 사용자 조회가 아니라 어드민 응답
(소속을 바꾸는 수정은 커밋 뒤 재빌드를 기다린다)과 앱 기동(첫 스냅샷이 서야 목록이 열린다)이다.

### 9-4. CPU — 총량이 아니라 재빌드가 도는 300 ms의 경합

재빌드는 스레드 하나로 돈다. 그래서 총량은 "한 코어 × 재빌드 시간"으로 작고, 문제는 그 시간
동안의 경합이다. 10배 실측은 이렇다.

- 발화 전후 1.3초 구간의 평균은 0.3~0.5 core다. 이것만 보면 코어 하나 반이 남는다.
- 그 CPU는 재빌드가 실제로 도는 200~400 ms에 몰려 있고, 그 구간의 JVM 사용은 1.0~1.65 core다.
  로더 스레드 1 core에 같은 순간의 Young GC 워커와 JIT가 얹힌 값이다.
- 100 ms 쿼터를 다 채워 컨테이너가 멈춘 구간은 20회 중 3회에서 각 1회, 1~1.5 ms였다.

피크 초당 600 요청에 앱 코어 0.85가 필요하다는 실측을 그대로 대면, 그 300 ms는 처리량이 모자라
적체가 생길 수 있는 구간이다. 이것이 8장의 "미측정" 칸이 중요한 이유다.

### 9-5. 100배에서 본 한계 — 로더만 고쳐서는 늘어나지 않는다

100배에서는 재빌드 동안 힙이 상한에 붙어 Full GC(정지 약 380 ms)와 스로틀이 났다. 원인은 둘이
겹친 것이었다.

- **중간 결과의 동시 보유.** 결과 전량을 `List<Object[]>`로 받는 방식은 "드라이버 버퍼 + 행 배열
  전량 + 만들어지는 스냅샷"을 한 순간에 힙에 둔다. Hibernate의 행 단위 streaming으로 바꾸자 할당이
  21% 줄고, 보존 3장이 찬 정상 상태의 Full GC가 2회 → 1회, Full GC 직후 생존이 815~929 → 720 MB가
  됐다.
- **스냅샷 자체 × 보존 장수.** streaming 뒤에도 Full GC가 남았다. 남은 정점은 중간 결과가 아니라
  살아 있는 스냅샷 4장(보존 3 + 건설 중 1)이었다.

streaming은 10배에서 다시 재 보니 갈리는 것이 할당 5.9%뿐이고 시간·CPU·힙·GC는 구분 불가였다.
대가는 드라이버 전용 fetch size 약속과 "스트림을 닫기 전 같은 커넥션에 다른 문장 금지"라는
순서 제약, 서버 prepared statement 모드에서 그 계약을 어기면 예외 대신 소켓 읽기가 멈추는 함정이다.
현실적 규모에서 이득이 측정되지 않으므로 되돌렸고, 구현과 검증 기록은 설계 문서에 남겨 재빌드
할당이 부담이 되는 날 첫 손잡이로 꺼낸다.

### 9-6. 인메모리 조회를 버릴 시점

이 구조의 전제는 둘이다. **전체 데이터가 한 인스턴스의 힙에 넉넉히 들어가고, 전량을 다시 만드는 데
1초 안팎이면 된다.** 규모가 이 전제를 깨는 방향으로 가면 재빌드를 더 잘게 쪼개는 것이 아니라
구조를 바꿀 때다.

| 신호 | 뜻 |
|---|---|
| 재빌드 소요가 초 단위를 넘어 어드민 응답에 붙는다 | 전량 재빌드가 싸다는 전제가 깨진다 |
| 재빌드 중 GC 정지가 사용자 조회에 나타난다 | 힙이 일시 사용량을 흡수하지 못한다 (10장이 먼저다) |
| 장소가 수십만이거나, 태그가 비트마스크 예산(62개)을 넘거나, 검색어·임의 반경 검색 요구가 생긴다 | 동네 단위 정렬 배열과 비트마스크로는 못 담는 규모·기능이다 |

앞의 둘은 규모, 마지막은 기능이다. 최종 답은 **외부 조회 인프라**다. 검색 엔진(Elasticsearch·
OpenSearch 계열)이 정렬·필터·페이징을 맡고 어드민 수정은 문서 하나의 upsert가 되며, 지금 고민한
"재빌드냐 표시값 갱신이냐"는 그 구조에서는 문제 자체가 없다. 커서 계약(회차 고정·명시 만료)은
검색 엔진의 point-in-time reader에 같은 모양으로 대응되므로 클라이언트 계약은 살아남는다.

## 10. 재빌드가 GC로 지연에 나타나기 시작하면 — 원인은 "같은 서버", 답은 빌더 분리

8장과 9장을 한 줄로 줄이면 이렇다. **재빌드의 할당·CPU·Old 승격이 전부 사용자 요청을 처리하는
JVM 안에서 일어난다.** 로더를 아무리 깎아도 같은 힙, 같은 두 코어를 나눠 쓴다. 근본 원인은 어드민
기능(쓰기와 재빌드)과 사용자 API(읽기)가 한 서버에서 처리된다는 점이고, 그렇다면 답도 로더가
아니라 배치에 있다.

### 10-1. 빌더를 어드민 서버로 떼어낸다

스냅샷을 **짓는 곳**과 **서빙하는 곳**을 나눈다. 어드민 요청을 받는 서버가 DB에서 스냅샷을 짓고
공유 저장소에 올리며, 사용자 API 인스턴스는 그것을 받아 로컬 힙에 두고 서빙만 한다. 10분 타이머
재빌드도 어드민 서버가 돈다.

```
[어드민 서버 — 빌더]                [Redis — 공유 저장소]              [API 인스턴스 N대 — 서빙]
 어드민 수정 커밋 / 10분 타이머      snapshot:s{스키마}:{버전}          NEW_VERSION 수신
   → DB에서 스냅샷 생성        ──▶   (TTL 60분, 통짜 blob)       ──▶   GET → 역직렬화 → 정렬 배열 재조립
   → 버전 발급 (DB 발급 번호)          └─ PUBLISH NEW_VERSION(v)         → 로컬 최신보다 새면 채택
```

API 인스턴스에서 무엇이 사라지고 무엇이 남는지가 핵심이다.

| 항목 | 지금 (같은 JVM) | 빌더 분리 뒤 (API JVM) |
|---|---|---|
| 재빌드 CPU (10배 기준 200~400 ms 동안 1.0~1.65 core) | serving과 나눠 씀 | **사라진다.** 어드민 서버가 쓴다 |
| 재빌드 할당 (10배 240 MB) | serving 힙에서 일어남 | **사라진다.** 남는 것은 blob 역직렬화와 정렬 배열 재조립의 할당(미실측) |
| DB 전량 읽기 | API 인스턴스마다 | 어드민 서버 한 곳, 회차당 1회 |
| 옛 스냅샷의 Old 잔류 | 교체마다 한 장 | 같다. 교체는 여전히 참조 해제 한 번이고 한 장 8.9 MB다 |
| 어드민 응답 | 재빌드 완료까지 기다림 | 같다. 어드민 서버 안의 일이라 사용자와 무관 |
| 기동 | DB에서 직접 지음 | Redis에서 받아 뜸. 없으면 DB에서 직접 짓는 경로로 후퇴 |

빌더 JVM은 성격이 달라진다. 지연 목표가 없고 처리량이 전부인 배치형 워크로드라, 정지를 허용하는
대신 처리량이 높은 Parallel GC를 쓰는 선택이 열린다. API JVM은 G1을 유지한다. 이것은 제안이고
측정하지 않았다.

### 10-2. 다중 인스턴스와 같은 그림이다

빌더 분리는 인스턴스를 여러 대로 늘릴 때 필요한 설계와 같은 것이다. 설계는 이미 있고
(`docs/design/2026-09-01-multi-instance-snapshot-pipeline.md`), 빌더의 위치만 "어드민 요청을 받은
API 인스턴스 + 타이머 리더"에서 "어드민 서버"로 옮기면 된다. 요지 넷을 그 위에서 다시 적는다.

| 다중 인스턴스에서 생기는 문제 | 처리 |
|---|---|
| 서버마다 스냅샷이 달라진다 | 빌더 하나(어드민 서버)가 만든 스냅샷을 Redis에 통짜 blob으로 올리고(TTL 60분), 각 API 인스턴스는 로컬 힙을 1차 캐시로 써 조회는 Redis I/O 없이 처리한다 |
| 다음 스크롤이 다른 서버로 간다 | 커서에 실린 버전이 로컬에 없으면 Redis에서 한 번 받아 이어받는다. 첫 페이지 핫패스에는 Redis가 없다 |
| 어드민 수정이 다른 서버에 늦게 보인다 | 새 버전을 Pub/Sub으로 알리고 각 인스턴스가 받아 채택한다. 알림이 유실돼도 10분 타이머 회차가 흡수한다 |
| 어드민 수정과 타이머가 겹친다 | 버전 번호는 DB 발급 테이블에서 단조로 나오고 빌더만 발급한다. 각 인스턴스는 자기 최신보다 큰 번호만 채택한다 |

**Redis는 조회 가속기이지 정본이 아니다.** 정본은 MySQL이고, Redis가 죽으면 각 API 인스턴스는
로컬 스냅샷으로 정속 서빙을 계속하면서 자기 타이머로 DB에서 직접 짓는 경로로 후퇴한다. 내주는
것은 둘이다. 어드민 수정이 다른 서버에 10분까지 늦게 보이고, 서버를 넘어간 옛 커서는 만료돼
1페이지로 돌아간다.

### 10-3. 로더 최적화는 어디로 가나

이 그림에서 재빌드 CPU가 serving JVM에 들어오는 순간은 하나뿐이다. **Redis가 죽어 API 인스턴스가
직접 짓는 강등 경로**다. 그래서 Hibernate streaming이나 JDBC `ResultSet`의 primitive getter로
행별 할당을 없애는 손잡이는 평시 성능이 아니라 그 강등 경로를 가볍게 하는 안전장치, 그리고
어드민 서버 자체가 100배 같은 규모에서 버티게 하는 수단으로 자리가 옮겨진다. Hibernate가 대신
해 주던 타입 변환·null 처리·커넥션과 ResultSet 수명 관리를 직접 지는 비용이 따라오므로, 그때도
프로파일로 병목을 확인한 뒤에 든다.

### 10-4. 언제 시작하나

둘 중 하나가 켜지면 착수한다. **인스턴스를 2대 이상으로 늘리기로 하는 날**, 또는 **부하 중
재빌드 버킷의 p50이 이웃 버킷의 2배를 넘는 관측이 나오는 날**이다. 지금은 둘 다 아니다. 착수 순서는
직렬화 스키마와 왕복 등가 테스트 → 아카이브 적재 → 커서 해석에 Redis 단계 추가 → 발행·수신·채택
→ 강등 시나리오 테스트이고, 그 전에 정할 것이 셋 남아 있다. 표시 홀더(이름·썸네일·대표 태그)를
blob에 같이 실을지 장소 id 이벤트로 전파할지, 정렬 배열까지 실어 재조립 비용을 없앨지, 역직렬화와
재조립이 API JVM에 얹는 할당과 시간의 실측이다.

그리고 이 전환은 규모의 답이 아니다. 빌더 분리와 공유 저장소는 "재빌드가 serving을 건드린다"와
"인스턴스가 여러 대다"를 푼다. 데이터 규모 자체가 단일 JVM 힙의 범위를 넘어가면 9-6대로 외부 조회
인프라로 나간다.

## 11. 세 문장으로

**어떤 자료구조에, 어떤 근거로.** 조회가 비교·필터에서 읽는 값(정렬 키 다섯, 좌표, 태그 비트)만
장소당 객체 하나에 담고, 동네 × 정렬 5종의 참조 배열을 미리 정렬해 둔다. 요청은 이진 탐색으로
시작점을 찾아 10건이 차면 멈추고, 표시값은 스냅샷 밖 홀더 한 벌에서 마지막 10건만 꺼낸다. 전량
스캔이 아니라서 열별 원시 배열(SoA)은 구현까지 했다가 되돌렸다.

**왜 괜찮다고 봤나.** 부하 아래 serving에서 GC는 정지 합 0.25%·GC CPU 0.20%로 주항이 아니고,
현실적 최대인 10배에서 보존 3장이 찬 뒤 재빌드를 태워도 live 힙 112 MB(8.8%), Full GC 0회, 재빌드
300 ms 동안 코어 1.3개였다. 원인 쪽으로 내려가면 재빌드 할당 240 MB가 Eden 0~2번 분량이고 죽은
스냅샷이 Old에 남지만 Full GC를 부르기 전이다. 재지 않은 것은 10배 부하 중 발화의 p50 하나다.

**아프기 시작하면.** 원인은 어드민과 API가 같은 JVM이라는 것이므로, 빌더를 어드민 서버로 떼어
Redis를 공유 저장소로 두고 API 인스턴스는 받아서 서빙만 한다. 다중 인스턴스 설계와 같은 그림이고,
로더 최적화는 그 뒤 강등 경로의 안전장치로 남는다. 데이터가 단일 JVM 힙을 넘어가면 외부 조회
인프라로 나간다.
