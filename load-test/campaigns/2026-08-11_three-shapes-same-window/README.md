# 2026-08-11 · 세 구조를 한 창에서 — 기반 고정, 쿼리 구조만 셋

> **부하 테스트가 아니다.** 조인 구조가 만든 문제를 각 해법이 얼마나 걷어냈는지를 묻는 질문이라
> `EXPLAIN ANALYZE`로 답한다 ([가이드](../../../docs/perf/load-test-guide.md) 게이트 ①).
> 처리량·백분위에 대해서는 **아무것도 주장하지 않는다.**
>
> 채취 2026-08-11, 세 열 × (지역 3 × 태그 7 × 정렬 2) + 핫콤보 커서 2페이지.

## 1. 무엇을 묻는가

태그 필터 목록 조회의 실행 계획이 입력에 따라 흔들리는 문제가 있었고, 두 번의 해법이 있었다 —
EXISTS에서 `tags` 조인을 걷어낸 것(A), 그리고 태그 소속을 `place_stats`의 비트마스크로
비정규화해 조인 자체를 없앤 것(B). **각 해법이 그 문제를 얼마나 해결했는가**가 이 캠페인의
질문이다.

## 2. 설계 — 기반을 고정하고 쿼리 구조만 바꾼다

세 열 모두 **통계 테이블 형태와 커버링 인덱스가 V32+V33으로 같다**(B만 그 위에 V34의 컬럼·
인덱스를 더한다). 조인 구조 말고는 다 같아야 조인 구조의 몫만 남기 때문이다.

| 열 | 기반 | 태그 필터 술어 |
|---|---|---|
| **JOIN** | V32+V33 | 그룹당 EXISTS, 안에 `place_tag JOIN tags` + `t.active = 1`, 그룹 안은 `IN` 리스트 |
| **A** | V32+V33 | 그룹당 EXISTS, `place_tag`만 본다 |
| **B** | V34 | EXISTS 없음. `(ps.tag_bitmask & :그룹마스크) != 0` 세 개 |

**JOIN 열과 A 열은 EXISTS 안의 문자열 말고는 바이트 동일한 SQL이다.** 그 차이만 남기는 것이
이 캠페인의 전부다. B는 EXISTS가 사라지므로 문장이 달라지지만 FROM·정렬·LIMIT은 현행 구현
그대로다.

술어의 의미는 셋 다 같다 — **그룹 안 OR, 그룹 사이 AND**(확정 스펙).

### 2.1 처음 구조를 V29 형상까지 되돌리지 않는 이유

되돌릴 수는 있었고 실제로 재현도 됐다(버전당 행 집합 + `place_stats_meta`, 08-06 앵커 4칸 중
3칸이 노드 단위로 일치). 그런데 그 형상에는 조인 구조 말고도 **테이블 2배 · PK의 `version` ·
인덱스 선두의 `version` · 비커버링 태그 인덱스**가 함께 얹혀 있다. 그것까지 되돌리면 각 칸이
"조인을 없앤 몫"이 아니라 **"그동안 쌓인 기반 개선분 전체"**를 재게 된다. 두 질문은 다르고,
지금 묻는 것은 앞쪽이다.

### 2.2 창을 통일하는 이유

세 구조의 수치가 세 캠페인에 흩어져 있는데, 그 사이에 **창 드리프트**가 있다. 같은 컨테이너·
같은 데이터인데도 시점이 다르면 옵티마이저가 다른 계획을 고르거나 같은 계획이 다른 시간을 낸다.
실측으로 확인된 것 둘:

- `place_tag` 프로브의 비용 계수가 시간이 지나며 싸졌다 (단건 커버링 조회 0.622 → 0.266).
  그것만으로 작은 지역 + 인기순의 주도 테이블이 태그에서 지역으로 넘어간다.
- 형상 전환이 `idx_place_stats_town_score`를 재생성한다(`tag_bitmask`가 말단에 실려 있어
  피할 수 없다). 갓 만든 인덱스는 통계가 정확하고 버퍼풀에 완전히 상주해 지역 주도가 싸 보인다.

그래서 캠페인 사이의 절대값을 그대로 빼거나 나누면 구조의 차이가 아니라 창의 차이를 읽게 된다.
이 캠페인은 그 축을 통일한다.

## 3. 검증 환경

| 항목 | 값 |
|---|---|
| 토폴로지 | `docker/docker-compose.bench.yml` — MySQL 8.0.46(2 CPU / 3G, 버퍼풀 2G) 단독. **앱 정지** |
| 데이터 | 활성 장소 **6,320** · `place_tag` **15,481**(합성 2종 포함) · `tags` **36행(비활성 0)** |
| 부하 | **0** |
| 측정 | `EXPLAIN ANALYZE` 워밍업 1회 + 3회 중앙값. JOIN 열의 무거운 칸(카페·핫콤보·이색공간)과 핫콤보 커서는 **7회** |
| 형상 전환 | V34 되돌림 → JOIN·A 채취 → V34 복원 → B 채취. `place_stats`의 행은 건드리지 않는다 |

## 4. 그리드

```text
지역 3   동네 1곳 town_id 301(후보 100) · 동네 4곳 301~304(400) · 시 18곳 301~318(1,800)
태그 7   무태그 · 카페(1,146) · 핫콤보(카페 + OPTION1 4종 + OPTION2 6종) ·
         이색공간(985) · 음식+바술집(1,094 & 185) · 합성 규모 20(id 40) · 0건(id 41)
정렬 2   인기순 · 최신순
커서     1페이지 전 칸 + 2페이지는 핫콤보 칸만
         (동네 1곳 핫콤보는 매치가 10건이라 2페이지가 존재하지 않는다 — 측정 시 확인)
```

합성 태그(id 40·41)는 채취 전 시드, 채취 후 롤백한다. 비트 자리 = tag id라 62 이하여야 하고,
세 열이 같은 태그를 써야 비교가 성립한다.

## 5. 게이트 — 과거 재현이 아니라 A 열의 재현성

이 캠페인의 목적이 **같은 창 안의 열 간 비교**라, 과거 수치 재현을 통과 조건으로 걸지 않는다.
대신 A 열 3칸을 어제 기록(`2026-08-11_tag-bitmask-read-model/results/summary-a.csv`)과 대조해
**드리프트의 크기를 기록만 하고 진행한다.** 어긋나도 막지 않는다 — 그것이 §2.2를 뒷받침하는
정보이기 때문이다.

결과: 주도 노드는 3칸 모두 일치. 시간은 한 칸이 2배 밖이었다.

| 칸 | 어제 | 오늘 |
|---|---|---|
| city18 · 무태그 · 인기순 | 0.803ms `ps` | 1.08ms `ps` |
| city18 · 핫콤보 · 인기순 | 2.05ms `pt` | **6.44ms** `pt` |
| city18 · 음식+바술집 · 최신순 | 0.84ms `pt` | 0.606ms `pt` |

## 6. 해석 규칙

- **세 열은 서로 비교하라고 만든 것이다.** 같은 컨테이너·같은 데이터·같은 그리드·같은 시간대·
  같은 술어에서 나왔다.
- **원 캠페인 기록과 절대값으로 대조하지 않는다.** `2026-08-06_tag-filter-join-order`와
  `2026-08-11_tag-bitmask-read-model`의 수치는 각자의 창에서 유효하고 그대로 보존한다.
- JOIN 열에서 오추정 구조가 재현됐는지는 CSV의 `tags_nodes`·`cartesian` 열로 읽는다.
  - `tags_nodes > 0` — `t.id`가 `IN` 리스트라 조인이 상수로 접히지 않고 트리에 남았다
  - `cartesian > 0` — 두 태그 축이 조건 없는 해시 조인으로 곱해졌다(추정이 무너지는 자리)
  - 단일 태그 그룹만 있는 칸은 `t.id`가 PK 등호라 조인이 접혀 `tags_nodes = 0`이 정상이다
