# 2026-08-05_improved-recheck — 개선 형상의 목표 부하 재확인과 이전 붕괴점 재판정

> **사전 등록 문서다** (2026-08-05, 측정 전 고정 — 사용자 확인 완료).
> 개선 2건(커서 쿼리 조인 순서 고정 `82cec34`, 요청당 SQL 18→11 `22358cb`+`2a50575`)이
> 반영된 형상이 목표 부하를 어떤 여유로 받는지, 이전 붕괴점(도착 500/s)이 어떻게 되는지 잰다.

## 1. 문제

목표 피크(도착 300/s = 실처리 361 req/s)는 개선 **전** 형상으로만 통과가 확인됐고
(2026-08-04_read-ceiling), 개선 후 형상의 부하 실측은 없다. 개별 검증은 끝났지만 —
SQL 개수는 StatementInspector 통합 테스트, 실행계획은 EXPLAIN — **그 합이 부하에서
어떤 여유·상한으로 나타나는지는 부하만이 답한다.**

## 2. 예측 (측정 전 기록)

- 요청당 SQL 18.16 → ≈11.2 (−39%), 커서 쿼리 실행당 행 읽기 12,66x → ≈1,822.
- 병목이던 MySQL CPU의 요청당 비용이 줄어 **300에서 여유 확대**, **500에서 산술상 통과권**
  (554 req/s × 11 SQL × ~200µs ≈ 1.2 vCPU < 배정 2 vCPU).
- 위험 요인: 직전 A/B(500B)에서 앱 스로틀이 45.7~48.2%까지 올라 MySQL(49.6%)에 근접 —
  **DB를 풀면 앱이 다음 천장**일 수 있다는 예고가 이미 있다.

## 3. 기술적 선택

이 캠페인에는 선택이 없다 — **이미 커밋된 선택의 사후 검증**이다.
근거 기록: `PlaceListDbQueryRepository.findPopularRows` javadoc(STRAIGHT_JOIN),
`UserRepository.findForAuthentication` javadoc(role 클레임), 캠페인
`2026-08-04_saturation-amplification`(표적 확정 + FORCE INDEX A/B 효과 2.7배).

## 4. 검증할 주장

**목표의 가치 서술은 "CPU 절감"이 아니라 "같은 DB 자원으로 받는 피크 상향 + 목표
부하에서의 여유 확보"다.** CPU·SQL 개수·행 읽기는 그것을 증명하는 원인 지표로 쓴다.

1. 도착 300/s: 통과 유지 + 개선이 원인 지표로 실재 (SQL/요청, 커서 행 읽기, DB CPU 하락)
2. 도착 500/s: 이전 붕괴점(성공 155 req/s·실패 67.6%, LB 8192 재기준선)의 재판정

## 5. 성공 조건 (측정 전 고정)

**비교 기준선은 LB 조건이 같은 `2026-08-04_saturation-amplification`의 amp300-r2 /
amp500A-r2다** (read-ceiling 수치는 LB 1024라 절대값 비교 금지).

| 지점 | 조건 | 기준 |
|---|---|---|
| 300 (판정) | ⓐ 도착률 ≥98% · 실패 0 | 통과 유지 |
| 300 (판정) | ⓑ digest: 인기순 요청당 SQL 11.2±0.2, `users` SELECT digest **부재**, 커서 쿼리 실행당 rows ≤2,000 | 개선의 원인 지표 실재 |
| 300 (판정) | ⓒ MySQL cgroup 사용률·스로틀이 기준선(사용률 ~43%·스로틀 9.9%) 대비 하락 | 자원 여유 확대 |
| 500 (판정) | 도착률 ≥98% + 실패 <0.5% + 성공 처리량이 시도(≈554)의 ≥98% + p50이 300 지점의 3배 이내 | **통과** 정의 |
| 650 (관찰) | 500 통과 시에만. 판정 없음 — 새 상한의 어림값 기록 | — |
| 참고 | p50·p95 기록만 — 판정·주장 금지 (재현성 미증명 + 효과 크기 원칙) | — |

**500 결과의 해석 분기 (사전 등록):**

- (a) 통과 → 새 상한은 554 req/s 초과 — 650 관찰로 어림
- (b) 실패 + MySQL 스로틀 지배 → DB 천장 잔존 → 다음 수는 ②b 로컬 캐시
- (c) 실패 + 앱 스로틀 지배 → **병목이 앱으로 이동** → 다음 수는 앱 쪽 조사
- (d) 도착률 미달 + artillery 프로세스 CPU 포화 → 생성기 한계 — 서버 판정 불가, 지점 재설계

## 6. 프로토콜

- 형상: HEAD `82cec34` + 벤치 인프라(LB `worker_connections` 8192 — amp 캠페인과 동일,
  미커밋) + BookmarkService 중복 가드(읽기 전용 믹스에서 미사용 경로, 단일 형상이라 무해).
- **토큰: role 클레임(`USER`) 포함으로 재생성** — 배포 1시간 후의 정상 상태(클레임 경로,
  SQL 11개)를 재현한다. 레거시 토큰이면 폴백(+1 SQL)을 재게 된다.
- 측정 전 검증: p6spy off 로그 확인, 시드 불변(장소 6,320·towns 84), **클레임 경로 확인**
  (digest TRUNCATE → 단건 요청 → `users` SELECT 부재 확인).
- 라운드: 지점당 3회(각 워밍업 30s + 램프 30s + 지속 120s), **r1은 워밍업으로 폐기**,
  라운드 간 60초 휴식. 부하는 LB(8082)로만.
- 계측: digest TRUNCATE/덤프 + cgroup `cpu.stat` 전후 + sampler 3초 + metrics-snapshot
  + artillery 프로세스 CPU. CPU 판정은 cgroup 정본(docker stats 문면 금지).
- 배치 발화가 매시 :00 부근이라는 관찰(amp §9-1)이 있어, 라운드가 정각과 겹치면 기록하고
  겹친 라운드는 무효 후보로 별도 표기.

## 7. 이 테스트로 말할 수 없는 것

- p50·p95의 개선 폭 (비포화 지연은 효과 크기 밴드상 주장 불가, 꼬리는 재현성 미증명)
- 쓰기 혼합 믹스에서의 거동 — 읽기 전용 한정
- 650 관찰값의 판정력 (라운드 수 부족, 어림값)
- 개별 개선의 기여 분해 (STRAIGHT_JOIN vs SQL 다이어트 — 단일 형상 측정이라 합산 효과만)

## 결과 (2026-08-05 실행 — 판정 전문은 [결과 문서](../../../docs/perf/2026-08-05-improved-recheck.md))

- **300 통과 (ⓐⓑⓒ 전부 충족):** 실패 0 · SQL/요청 **11.17**(예측 적중) · `users` SELECT
  digest 소멸 · 커서 쿼리 실행당 **1,822행**(FORCE INDEX 실험값과 일치) · MySQL 사용률
  46.9→**28.6%**, 스로틀 9.9→**~1%** · 요청당 DB CPU 3.51→**2.13ms (−39% = SQL 감소율과 산술 일치)**
- **500 통과 — 분기 (a):** 시도 ≈600 req/s(등록서의 "554"는 과소 산정 — 믹스 계수 1.2 누락)를
  도착률 100%·실패 0·성공 597~604 req/s로 처리. 기준선(155 req/s·실패 63.5%) 대비 **3.9배**.
  p50 하위 조건은 유효 2라운드 중 1라운드 충족 — 미충족 라운드(r3)는 동일 작업량에 요청당
  CPU만 +7~9% 오른 호스트 경합 서명이라 코드 귀속 불가, p50은 등록대로 기록만.
- **650 관찰 — 붕괴, 병목 앱 이동:** 앱 스로틀 52~59% vs MySQL 23%. MySQL은 500 지점과
  동일한 여유를 남긴 채 앱이 무너졌다(등록서 §2 위험 예고 실현). 실패의 상당수는 LB
  서킷브레이커(`no live upstreams` 502) 산물로 순수 적체보다 급격해 보임. 새 천장은
  시도 600~700 사이 — 협착하지 않음.
- 부수 확정: 배치 cron `0 30 * * * *`(**:30**), 실측 발화 01:30:04. 직전 캠페인의 ":00 발화"
  관찰은 `calculated_at`(집계 컷오프)을 발화 시각으로 읽은 오독으로 추정(가설).
