# 장소 목록을 메모리에 보관할 때의 갱신·Heap·GC 설계

작성일: 2026-09-09 · 설계 기준: 2026-09-10

솔플리의 장소 목록은 동네와 태그로 후보를 좁히고, 선택한 순서로 한 페이지를 반환한다.
여러 사용자가 공유하는 정렬 순서를 미리 만들어 메모리에 두면 요청은 필요한 위치부터
목록을 찾을 수 있다. 대신 서버는 전체 조회 데이터를 계속 보관하고, 변경될 때 새 상태를
만드는 비용을 감당해야 한다.

이 구조에서 확인할 질문은 세 가지다. **어드민 변경을 조회 중인 요청과 충돌 없이 어떻게
반영할 것인가. 전체 데이터를 만료 시간 없이 힙에 두어도 되는가. 갱신과 GC가 사용자
응답을 늦추기 시작하면 어느 작업을 어디로 옮길 것인가.**

## 1. 어떤 요구사항을 고려했나

목록을 넘기는 동안 정렬·필터 기준이 바뀌면 페이지 경계가 흔들릴 수 있다. 커서에 Snapshot
version을 넣고, 다음 페이지도 같은 version일 때만 이어간다. current가 바뀌면 커서를
만료시키고 첫 페이지 재요청을 요구한다. 어드민 변경을 빠르게 반영하는 서비스 정책에 따라
과거 커서를 위해 별도의 Snapshot을 보존하지 않는다.

반영 시점은 값의 역할에 따라 나눈다.

| 데이터 | 반영 시점과 방식 |
|---|---|
| 장소 생성·삭제·공개 상태, 동네·태그 집합·좌표 | DB 커밋 후 해당 장소를 재조회해 Snapshot 부분 갱신 |
| 기존 장소의 인기 점수·평점·리뷰 수·북마크 수 등 정적 정렬 키 | 주기적 전체 재빌드에서 일괄 반영 |
| 장소 이름·썸네일·대표 태그 ID | Snapshot 밖 `PlaceViewHolder`에 반영 |
| 태그 이름·활성 상태 | Snapshot 밖 `TagViewHolder`를 갱신 |

장소에 부착된 태그 집합은 필터 기준이고, 태그 이름·활성 상태는 대표 태그의 표시 기준이다.
두 변경은 서로 다른 데이터를 갱신한다. 표시값만 바뀌면 Snapshot version은 유지한다.

정합성의 기준은 DB다. 커밋 이후 메모리에 반영되기까지 지연을 허용하되, 롤백한 변경을
공개하지 않는다. 반영에 실패하면 current로 조회를 유지하고 다음 성공한 전체 재빌드에서
조회 모델을 다시 맞춘다.

## 2. 어드민 변경은 어떻게 반영하나

어드민이 바꾼 내용은 빠르게 보여야 하지만, 아직 커밋되지 않은 값이나 반쯤 수정된 목록이
노출돼서는 안 된다. 그래서 변경을 저장하는 단계와 조회용 상태를 공개하는 단계를 나눈다.

```text
원본 변경 저장                 ← 장소·태그 관계·조회 원천을 같은 트랜잭션에 반영
  │
  ▼
변경 장소 ID 수집              ← 같은 ID는 중복 없이 모음
  │
  ▼
DB 커밋 성공                  ← 롤백하면 조회 모델 갱신도 실행하지 않음
  │
  ▼
갱신 차례 확보                ← 다른 갱신이 끝난 뒤 최신 DB 상태를 재조회
  │
  ▼
현재 조회 모델과 비교
  ├─ 표시값만 변경            → 별도 표시 저장소 갱신 · Snapshot/version 유지
  │
  └─ 조회 기준 변경
       │
       ▼
     영향 동네만 준비         ← 태그·좌표: 배열 복사 후 같은 위치의 참조 교체
       │                        생성·삭제·이동: 해당 동네 구성·정렬 다시 준비
       ▼
     새 version 발급
       │
       ▼
     필요한 표시값 준비       ← 새 장소가 조회될 때 표시값도 사용할 수 있게 함
       │
       ▼
     current 참조 교체        ← 완성된 Snapshot을 한 번에 공개
       │
       ▼
     이후 요청부터 새 상태 사용
```

### 변경 내용을 전달하기보다 최신 상태를 다시 읽는다

알리는 것은 “어느 장소가 변경됐다”는 사실이다. 이름 변경·태그 변경·동네 이동을 각각의
이벤트로 모델링하고, 이벤트에 담긴 값을 순서대로 재생하지 않는다. 변경 ID로 DB를 다시
읽으면 현재 존재하는지, 어느 동네에 속하는지, 어떤 태그가 붙었는지를 한곳에서 판단할 수
있다. 삭제한 장소도 ID를 넘기며, 최신 조회 결과에 행이 없으면 목록에서 제거한다.

같은 트랜잭션에서 같은 장소를 여러 번 수정해도 한 번의 갱신에 모아 처리한다. 현재 구현은
커밋 이후 콜백에서 같은 요청 스레드가 이 작업을 수행한다. 따라서 갱신 대기는 어드민
응답 시간에 포함된다. 여러 API 서버로 변경을 전파하는 경로는 별도의 분산 설계에 해당한다.

### 이미 조회 중인 목록을 직접 고치지 않는다

요청이 보고 있는 배열에 장소를 끼워 넣거나 빼면 탐색 도중 순서와 길이가 달라질 수 있다.
갱신은 새 배열을 준비해서 공개하고, 기존 배열은 그대로 둔다. 영향받지 않은 동네의 배열과
바뀌지 않은 장소 객체는 새 Snapshot에서도 공유한다.

태그·좌표만 달라진 기존 장소는 정적 정렬 키를 유지하므로 같은 위치의 참조만 바꿀 수 있다.
생성·삭제·이동은 원소 구성이 바뀌므로 해당 동네의 배열을 다시 만든다. 점수·리뷰 수처럼
계속 변하는 정렬 키는 전체 재빌드에서 일괄 반영한다. 어드민이 수정한 장소만 새 통계로
정렬되는 일을 피하기 위해서다. 신규 장소는 보존할 기존 정렬 키가 없어 DB 값을 사용한다.

이름과 썸네일은 순서·필터·후보 집합을 바꾸지 않으므로 Snapshot 밖에서 갱신한다.
일반 장소 수정에서는 최신 값 비교까지 수행하지만, 표시값만 바뀌었다면 배열 복사와
version 발급 없이 끝난다. 이미지 이동 후 최종 파일 키 반영, 태그 이름 변경도 표시값만
갱신한다.

### 늦게 끝난 재빌드가 최신 수정을 덮지 않게 한다

참조를 한 번에 교체하면 조회는 완성된 Snapshot만 보지만, 여러 갱신이 서로의 결과를
덮어쓰는 문제까지 해결되지는 않는다. 부분 갱신 둘이 같은 current에서 출발하면 한쪽의
수정이 빠진 결과를 다른 쪽이 공개할 수 있다. 전체 재빌드도 오래전에 읽은 DB 상태로
늦게 완성되면 그 사이 반영된 부분 갱신을 덮을 수 있다.

**version이 더 크다는 것만으로 내용도 더 최신이라고 보장할 수는 없다.** 현재는 모델을
준비한 뒤 version을 발급하므로, 오래된 데이터를 읽은 작업이 늦게 끝나 더 큰 번호를 받을
수 있다. 번호 비교는 이미 발급된 작은 버전의 재채택을 막지만, 생성 과정의 충돌은 막지 못한다.

```text
갱신을 직렬화하지 않았다고 가정하면

재빌드 B: 변경 전 DB 조회      ← 이 상태로 모델 생성 시작
  │
  ▼
어드민 변경 커밋
  │
  ▼
부분 갱신 A: v11 공개         ← 어드민 변경이 목록에 반영됨
  │
  ▼
재빌드 B: 뒤늦게 모델 완성    ← 내용은 여전히 변경 전 상태
  │
  ▼
v12 발급 후 공개             ← 번호가 더 크므로 version 비교를 통과
  │
  ▼
어드민 변경이 덮어써짐        ← 발급 순서가 내용의 최신성을 보장하지는 않음
```

그래서 **write lock은 Snapshot 변경 경로 전체를 직렬화하는 락**이다. 부분 갱신은 current
확보 전부터, 전체 재빌드는 DB 조회 전부터 락을 잡고 새 상태 공개까지 유지한다. 표시값
갱신도 같은 락을 사용해, 재빌드의 표시 맵 교체와 장소별 표시값 수정이 서로 덮이지 않게 한다.
사용자 조회는 이 락을 잡지 않고 확보한 Snapshot을 그대로 읽는다.

```text
Thread A — 어드민 부분 갱신     Thread B — 주기적 전체 재빌드

write lock 획득                write lock 획득 시도
  │                              │
  ▼                              │
current Snapshot 확보            │ 대기
  │                              │
  ▼                              │
변경 장소 DB 조회                │  ← 읽기 트랜잭션은 락 안에서 시작·종료
  │                              │
  ▼                              │
영향 동네 반영 · 새 모델 준비     │  ← 확보한 current를 기반으로 구성
  │                              │
  ▼                              │
version 발급 · 표시값 갱신        │  ← 조회 기준이 변경된 경우
  │                              │
  ▼                              │
Snapshot 공개                    │
  │                              │
  ▼                              │
write lock 해제 ────────────────▶ lock 획득
                                 │
                                 ▼
                               DB 전체 조회      ← 락 획득 후 새로 읽음
                                 │
                                 ▼
                               전체 모델 구성    ← DB 조회 결과로 생성
                                 │
                                 ▼
                               version 발급 · 표시 맵 교체
                                 │
                                 ▼
                               Snapshot 공개 · lock 해제

사용자 조회 스레드              ← 위 write lock에 참여하지 않음
  │
  ▼
current 참조 확보
  │
  ▼
같은 Snapshot으로 요청 완료     ← 중간에 current가 교체돼도 확보한 참조 유지
```

전체 재빌드는 current를 수정하는 작업이 아니라 DB에서 전체 모델을 새로 만드는 작업이다.
반대로 재빌드가 먼저 락을 잡았다면, 어드민 변경은 DB에 커밋되더라도 부분 갱신은 재빌드
공개까지 기다린다. 이후 최신 current와 DB 상태를 읽어 반영하므로 재빌드 뒤에 수정이 적용된다.
이 락은 한 JVM 안의 캐시 갱신을 제어하며, 원본 DB 쓰기 자체를 막거나 여러 서버의 갱신을
함께 직렬화하는 락은 아니다.

부분 갱신은 최신 상태를 읽은 뒤 준비하므로 오래된 변경 내용을 뒤늦게 적용하지 않는다.
갱신에 실패하면 예외를 기록하고 현재 Snapshot으로 조회를 유지한다. 다음 성공한 전체
재빌드는 DB 기준으로 조회 모델을 다시 맞춘다. 주기적 재빌드가 정렬 키 반영뿐 아니라
누락된 변경의 복구, 즉 reconciliation도 담당하는 이유다.

### 교체 중인 요청과 다음 페이지를 구분한다

진행 중인 요청은 시작할 때 확보한 Snapshot을 끝까지 사용한다. 이후 들어오는 요청은 새
current를 사용하며, 커서 version이 current와 다르면 첫 페이지부터 다시 요청하도록 한다.
표시값은 별도로 최신 값을 읽기 때문에 페이지 전체의 표시 시점까지 고정되지는 않는다.

```text
요청 A가 v10 확보
  │
  ▼
current를 v11로 교체          ← 요청 A가 확보한 v10의 내용은 그대로
  │
  ├─ 진행 중인 요청 A        → v10으로 응답 완료
  │
  ├─ 교체 후 들어온 요청 B   → v11을 확보해 조회
  │
  └─ v10 커서의 후속 요청    → version 불일치 · 커서 만료 · 첫 페이지 재요청
```

## 3. 전체 데이터를 기한 없이 캐싱하면 Heap이나 GC 문제가 없나

**만료 시간이 없다는 것과 데이터가 끝없이 누적된다는 것은 다르다.** 이 캐시는 요청마다
결과를 추가하는 저장소가 아니라, 현재 장소 집합을 표현하는 조회 모델이다. 보관량은 요청
횟수보다 장소 수·저장 필드·정렬 배열 수에 의해 정해진다. current 한 벌을 보관하고,
교체한 Snapshot을 과거 커서용으로 따로 붙잡지 않는다.

그렇다고 current 한 벌이 힙에 들어간다는 사실만으로 충분하지는 않다. 요청 처리에 필요한
임시 객체와 다음 모델을 만드는 공간까지 같은 힙에서 사용하기 때문이다.

```text
평상시                       ← current · 표시값 · 프레임워크 객체 상주
  │                            요청용 후보·결과·응답 객체는 계속 생성·회수
  ▼
전체 재빌드 시작             ← 현재 모델을 유지한 채 새 모델 생성
  │                            DB 결과·그룹화 리스트·정렬 임시 공간도 함께 사용
  ▼
새 모델 완성 · current 교체  ← 이후 요청은 새 모델 사용
  │
  ▼
기존 모델을 잡은 요청 종료   ← 마지막 참조가 사라져야 GC 대상이 됨
  │
  ▼
GC가 회수                   ← 참조 교체 직후 곧바로 메모리가 줄지는 않음
```

현재 로더는 DB 결과를 전량 받아 모델을 만든다. 따라서 재빌드의 할당량과 순간 점유는
완성된 Snapshot 크기보다 크다. 부분 갱신은 영향 동네의 배열만 복사하고 나머지를 공유하지만,
이 역시 임시 할당이 없는 것은 아니다.

### 상주량과 교체 과정의 비용을 따로 본다

오래 살아남은 객체는 Old 영역에 있을 수 있다. 여전히 참조되는 데이터는 필요한 상태이므로
GC가 제거할 수 없고, 그만큼 새 할당과 GC 작업에 쓸 공간이 줄어든다. 상주 데이터가 크면
살아 있는 객체를 추적하는 비용도 고려해야 한다. 다만 Old에 객체가 있다는 사실만으로
모든 Young GC가 그 전체를 순회하거나 긴 정지를 만든다고 단정할 수는 없다.

교체 시에는 새 객체를 빠르게 할당하는 동안 GC가 발생할 수 있다. 기존 모델의 참조가 끊겨도
메모리는 즉시 회수되지 않는다. G1에서는 Old 영역 회수가 마킹과 이후 회수 단계에 걸쳐
진행될 수 있고, 동시 GC 작업도 애플리케이션과 CPU를 나눠 쓴다.
[Java 21 G1 동작](https://docs.oracle.com/en/java/javase/21/gctuning/garbage-first-g1-garbage-collector1.html)

따라서 **안정 상태의 상주량이 예산에 맞는지**, **재빌드와 회수가 겹칠 여유가 있는지**를
각각 확인해야 한다. 느린 요청이 교체된 Snapshot을 계속 참조하면 회수가 늦어지고, 여러
교체에 걸쳐 요청이 남으면 순간적으로 살아 있는 버전도 두 개를 넘을 수 있다.

TTL을 붙여도 다음 조회를 위해 전체 모델이 필요하다면 생성과 할당은 다시 발생한다.
이 구조의 적합성은 만료 시간 자체보다 실제 데이터 규모에서 상주량·갱신 비용·회수 속도가
사용자 요청과 함께 감당 가능한지로 판단한다.

## 4. 재빌드와 GC가 사용자 latency에 영향을 주기 시작하면

먼저 응답 지연이 늘어난 시점에 무엇이 실행됐는지 확인한다. 재빌드 중 지연이 늘었다고 해서
원인이 모두 GC인 것은 아니다. DB 결과 변환·정렬이 CPU를 사용해 요청이 기다릴 수도 있고,
GC pause가 요청 스레드를 멈추거나 동시 GC가 CPU 경쟁을 더할 수도 있다.

```text
사용자 지연 증가 관측
  │
  ▼
재빌드·CPU·GC 시간축 대조    ← 지연이 어느 작업과 겹치는지 확인
  │
  ▼
비용이 집중된 곳 구분
  │
  ├─ DB 결과·중간 객체 생성
  │    │
  │    ▼
  │  전량 물질화·중복 복사를 줄일 여지 확인
  │
  ├─ 생성·정렬·GC와 요청의 지속적인 자원 경쟁
  │    │
  │    ▼
  │  모델 생성을 별도 빌더 프로세스로 분리
  │
  └─ 안정 상태의 전체 모델이 힙 예산을 압박
       │
       ▼
     저장 표현·캐시 범위 재검토
       │
       ▼
     필요하면 데이터 분할 또는 외부 조회 저장소 검토
```

### 빌더를 분리하는 목적은 생성 작업의 자원을 격리하는 것이다

같은 JVM의 다른 스레드에서 재빌드하더라도 힙과 GC는 공유한다. 생성 작업이 사용자 요청에
영향을 준다면 어드민 측의 별도 프로세스에서 조회 모델을 만들고, API는 완성된 모델을
받아 조회하도록 구성한다. CPU도 격리하려면 프로세스뿐 아니라 실행 자원 배치와 한도까지
함께 설계해야 한다.

```text
빌더 프로세스
  DB 읽기                    ← 조회 결과와 생성용 임시 객체는 빌더 힙에 할당
    │
    ▼
  장소 값 생성 · 동네별 정렬  ← 생성·정렬 CPU도 빌더에서 사용
    │
    ▼
  배포용 직렬화
    │
    ▼
공유 배포 저장소
  완성된 최신 모델 보관      ← Snapshot과 별도의 최신 표시값 제공
    │
    ▼
API 프로세스
  다운로드                   ← 수신 버퍼는 API 힙 사용
    │
    ▼
  검증 · 객체와 배열 복원     ← 최종 모델의 할당은 API에도 남음
    │
    ▼
  current 참조 교체
    │
    ▼
  로컬 조회                  ← 교체된 모델은 기존 요청 종료 후 GC 대상
```

**빌더 분리는 API의 GC를 없애는 설계가 아니다.** DB 조회 결과와 정렬용 임시 객체는
빌더에서 만들지만, API가 사용할 최종 장소 객체·배열은 API에도 필요하다. 수신 버퍼와
역직렬화, 교체된 모델의 회수 비용도 남는다. 따라서 분리 후에는 모델 생성 시간이 아니라
API의 적재 구간이 사용자 latency에 미치는 영향을 확인해야 한다.

적재의 객체 생성·참조 추적이 실제 병목이라면 정렬 순서를 포함한 배포 형식, 더 간결한
필드 표현이나 원시 배열을 검토할 수 있다. 이 선택도 복원 비용과 조회 코드 복잡도를 함께
평가한다. 최종 모델 자체가 가용 힙을 넘어서는 문제는 빌더 위치만 바꿔 해결할 수 없다.

이 책임 분리와 최신 상태의 전파·복구를 구체화한 것이
[Current Snapshot 분산 배포 설계](2026-09-10-distributed-inmemory-snapshot-architecture.md)다.

## 5. 재빌드 자체의 자원 여유를 먼저 확인한다

실험은 **현재 장소 수 6,320곳의 10배인 63,200곳**에서 수행했다. 지금 데이터가 힙에
들어가는지만 보는 것이 아니라, 데이터가 늘어났을 때 전체 모델을 유지하고 교체할 여유까지
확인하기 위해서다. 앱 자원은 **2 vCPU·메모리 2 GiB·최대 힙 1,280 MiB**로 고정했다.

이번에는 **사용자 조회 부하를 넣지 않았다.** current 한 벌이 올라온 상태에서 full rebuild
한 번이 CPU·Heap·GC 여유를 얼마나 사용하는지 먼저 분리해 보았다. 사용자 응답 지연은
직접 측정하지 않았으며, 그 영향은 자원 압박이 관측되거나 서비스 지연 검증이 필요한 시점에
부하를 함께 넣어 확인할 대상으로 남겼다.

```text
서버 기동 · current Snapshot 한 벌 로드
  │
  ▼
안정화 대기 · 재빌드 워밍업 2회       ← 기동 직후 비용과 정본 표본 구분
  │
  ▼
full rebuild 1회 실행                ← 기존 current를 유지한 채 새 모델 생성
  │
  ▼
새 Snapshot 완성 · atomic swap       ← elapsed와 CPU·Heap·자연 GC 기록
  │
  ▼
완료 후 10초까지 자연 GC 관측
  │
  ▼
간격을 두고 반복                     ← 라운드당 정본 5회, 실행 간격 약 30초
  │
  ▼
측정 종료 후 진단 GC · 히스토그램    ← 회수 후 live heap 확인, 자연 GC 통계와 분리
```

기동·스모크 확인을 마친 뒤 20초 안정화 대기를 두고 실행했다. 벤치 전용 트리거가 운영과
같은 재빌드 메서드를 호출했으며, 주기 스케줄러를 기다리는 대신 반복 실행으로 표본을 모았다.
따라서 실행 간격 자체가 운영의 10분 주기를 재현하는 실험은 아니다.

| 관점 | 확인한 것 | 측정 방법 |
|---|---|---|
| CPU 여유 | 소요 시간·총 CPU 시간·평균 core·quota 제한 | 재빌드 로그, 전후 `cpu.stat`, JFR CPU 시계열 |
| Latency 위험 요인 | 재빌드 주변 자연 GC와 pause | JFR의 GC 종류·횟수·정지 시간, 완료 후 관측 구간 |
| Heap 여유 | 교체 주변 점유와 회수 뒤 상주량 | Actuator 200 ms 폴링, JFR, 측정 종료 후 진단 GC |

GC·Heap의 관측 창은 실행 트리거 시각부터 완료 로그 후 1초까지로 잡았다. 완료 시점부터
10초까지의 GC도 별도로 확인했다. 이 관측 창은 재빌드 메서드의 실행 시간보다 넓다.

CPU 시간은 앱 컨테이너 전체의 소비량이다. 사용자 조회 부하가 없어도 JIT·계측·트리거
처리 등의 비용은 포함된다. 평균 core는 **CPU 차분과 같은 시간 구간**으로 나눠야 하며,
재빌드 메서드의 elapsed와 측정 구간이 다르면 두 값을 그대로 나누지 않는다.

Heap도 두 값을 함께 본다. 관측 최대값은 중간 객체와 회수 전 쓰레기까지 포함한 점유이고,
진단 GC 후 live heap은 그때 실제로 참조되는 데이터의 크기다. 전자는 교체 구간의 여유를,
후자는 지속적으로 보관하는 비용을 보여 준다. 200 ms 폴링은 짧은 정점을 놓칠 수 있고,
진단 GC는 자연 회수의 시점이나 속도를 증명하지 않는다.

미리 정한 SLO나 합격선은 없었다. CPU quota의 지속적인 소진, 반복되는 긴 GC 정지,
메모리 한계 접근 여부를 관측해 **지금 빌더 분리가 필요한 자원상 근거가 있는지** 판단했다.

## 6. 조회 자료구조와 비용의 핵심

조회 모델은 `정렬 종류 → 동네 ID → 정렬된 장소 참조 배열`이다. 장소 객체 하나를 다섯
정렬 축이 공유하며, 표시값은 ID로 찾는 별도 맵에 둔다.

```text
SnapshotBox                              ← 목록 조회가 Snapshot을 확보하는 곳
  └ volatile Snapshot current            ← 보관하는 Snapshot은 한 벌
       ├ version
       └ SortedPlaces
            └ EnumMap<정렬 종류, HashMap<동네 ID, PlaceEntry[]>>
                 └ 정렬 5종 × 동네별 PlaceEntry[]
                      └ 각 원소는 PlaceEntry 객체를 참조

장소 값: PlaceEntry 객체 N개
  → 정렬 키 다섯 · 동네 ID · 좌표 · 태그 비트마스크 · 장소 ID
정렬 순서: 위 객체들을 동네별 다섯 배열이 서로 다른 순서로 참조
  → 같은 Snapshot 안에서 장소 하나의 객체는 다섯 정렬 축이 공유

PlaceViewHolder  (Snapshot 밖, 한 벌)
  └ placeId → 이름 · 썸네일 파일 키 · 대표 태그 ID
TagViewHolder    (Snapshot 밖, 한 벌)
  └ tagId → 이름 · 활성 상태
```

장소 값과 정렬 순서는 역할을 나누어 표시한 것이다. 전체 장소 객체를 별도 목록에 한 벌 더
저장한다는 뜻은 아니며, 정렬 배열들이 해당 객체를 참조한다. 부분 갱신으로 만든 새 Snapshot은
변경하지 않은 동네의 배열과 장소 객체를 기존 Snapshot과도 공유한다.

### 배열에서 한 페이지를 꺼내는 흐름

정적 정렬은 이미 정렬된 배열을 읽는다. 커서가 지정한 장소를 ID로 찾는 것이 아니라,
**커서의 정렬 값과 placeId보다 뒤에 오는 첫 위치**를 같은 비교 규칙으로 찾는다.
첫 페이지는 배열의 처음에서 시작한다.

```text
목록 요청                    ← 대상 동네·태그·정렬 조건과 커서 검증
  │
  ▼
current Snapshot 참조 확보   ← 커서 version이 다르면 만료
  │
  ▼
정렬 축 선택                 ← 최신순·인기순 등 요청에 맞는 동네별 배열 선택
  │
  ▼
동네별 시작 위치 결정        ← 커서가 있으면 이진 탐색, 없으면 처음
  │
  ├─ 한 동네   → 그 배열을 순서대로 읽으며 태그 필터 적용
  │
  └─ 여러 동네 → 아래의 힙 병합으로 순서를 맞추며 태그 필터 적용
  │
  ▼
필터를 통과한 L개 확보       ← L = 페이지 크기 + 1, 후보가 소진돼도 종료
  │
  ▼
hasNext 판단 · 페이지 절단  ← 10건 페이지라면 11번째 항목으로 다음 페이지 판단
  │
  ▼
표시값·사용자별 북마크 조립  ← 표시값이 사라진 장소는 제외될 수 있음
  │
  ▼
응답 · 다음 커서 생성        ← 조회한 Snapshot의 version과 소비한 경계 사용
```

### 여러 동네의 후보는 어떻게 하나의 순서로 모이나

동네마다 페이지를 완성한 뒤 합치는 방식이 아니다. 각 동네의 **다음 후보 하나**를 비교해
전체에서 가장 앞선 장소를 하나씩 꺼낸다. 힙에는 각 동네의 배열과 현재 위치를 담고,
그 위치의 장소를 기준으로 우선순위를 정한다.

```text
동네 A의 정렬 배열      동네 B의 정렬 배열      동네 C의 정렬 배열
       │                      │                      │
       ▼                      ▼                      ▼
커서 다음 위치 탐색     커서 다음 위치 탐색     커서 다음 위치 탐색
       │                      │                      │
       └──────────────────────┼──────────────────────┘
                              ▼
                    요청 전용 PriorityQueue   ← 동네마다 다음 후보 하나, 최대 k개
                              │
                              ▼
                    전체에서 가장 앞선 후보 꺼냄
                              │
                              ▼
                    꺼낸 동네의 위치를 한 칸 전진
                              │
                              ▼
                    다음 후보가 있으면 힙에 다시 넣음
                              │
                              ▼
                    꺼냈던 후보의 태그 필터 확인
                              ├─ 통과 → 페이지 결과에 추가
                              └─ 탈락 → 결과에 넣지 않음
                              │
                              ▼
                    L개 확보 또는 힙이 비었는가?
                              ├─ 아니오 → 힙에서 다음 후보를 꺼내는 단계 반복
                              └─ 예     → 페이지 선택 종료
```

필터에서 탈락해도 해당 동네의 다음 후보는 계속 비교에 참여한다. 각 동네가 이미 정렬돼
있으므로 다음 후보들만 비교해도 전체 순서를 유지할 수 있다. 필터를 통과하는 장소가 적으면
그만큼 더 많은 후보를 꺼내야 하며, 힙과 탐색 위치는 요청마다 따로 만들어 공유 배열을 바꾸지 않는다.

거리순은 기준 좌표가 요청마다 달라 위 정적 배열의 커서 탐색·병합을 사용할 수 없다.

```text
대상 동네의 전체 장소 확인
  │
  ▼
태그·좌표 조건으로 후보 수집
  │
  ▼
요청 기준점에서 후보별 거리 계산
  │
  ▼
거리 커서 뒤의 후보만 검토
  │
  ▼
크기 L의 최대 힙에 가까운 후보 유지  ← 힙의 가장 먼 후보보다 가까우면 교체
  │
  ▼
남은 후보를 가까운 순으로 정렬
  │
  ▼
hasNext 판단 · 표시값 조립 · 응답
```

### 이 흐름에 필요한 자료구조와 비용

| 자료구조 | 선택 근거 |
|---|---|
| `EnumMap` | 고정된 정렬 종류를 내부 배열로 연결해 기본 접근 `O(1)` |
| 동네별 `HashMap` | 연속적이지 않은 동네 ID로 배열 탐색, 적절한 해시 분산에서 평균 `O(1)` |
| 장소 참조 배열 | 인덱스 접근·이진 탐색·이어지는 순차 스캔에 적합 |
| 태그 비트마스크 | 고정 폭 정수의 비트 연산으로 후보당 `O(1)` 판정 |
| `PriorityQueue` | 배열 기반 힙으로 다음 후보 유지, 삽입·제거 `O(log h)`, 머리 확인 `O(1)` |
| 표시값 맵 | 장소는 동시 조회·항목 교체가 가능한 `ConcurrentHashMap`, 태그는 불변 맵을 통째로 교체 |

`N`은 전체 장소 수, `A`는 정렬 축 수(5), `T`는 동네 수, `n_t`는 동네별 장소 수다.
조회에서 `k`는 대상 동네 수, `S`는 검사한 원소 수, `L`은 페이지 크기+1이다.

| 흐름 | 주요 비용 |
|---|---|
| 전체 생성 | 읽은 행을 그룹화 `O(N)` → 축별 배열 생성·정렬 `O(A × Σ[n_t log(n_t+1)])` |
| 상주 저장 | 장소 객체 `O(N)` + 정렬 참조 `O(AN)` + 동네 맵 `O(AT)` |
| 한 동네 조회 | 커서 이진 탐색 → 필터 스캔, `O(log(n_t+1) + S)` |
| 여러 동네 조회 | 동네별 이진 탐색 → 크기 k의 힙으로 병합, `O(Σ log(n_t+1) + (k+S) log(k+1))` |
| 거리순 조회 | 대상 `N_q`개 스캔 → 후보 `C`개 거리 계산·상위 L개 유지 → 결과 정렬, `O(N_q + C log(L+1) + L log(L+1))` |

필터 통과율이 낮으면 검사량 `S`가 커진다. 거리순은 후보 리스트와 ID 맵을 만들므로 추가
공간도 `O(C+L)`이다. 부분 갱신은 기존 장소를 찾는 스캔이 최악 `O(N)`이고, 실제 변경 시
동네 맵을 얕게 복사한 뒤 영향 동네의 배열만 복사하거나 정렬한다. 단건 수정 전체가 상수
시간에 끝난다는 의미는 아니다. 동네 해석·태그 검증·사용자 북마크 등 DB 경로는 별도로 남는다.

자료구조 계약: [EnumMap](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/EnumMap.html),
[HashMap](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/HashMap.html),
[PriorityQueue](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/PriorityQueue.html).
구현 근거: [SortedPlaces](../../src/main/java/org/sopt/solply_server/domain/place/cache/SortedPlaces.java),
[SnapshotLoader](../../src/main/java/org/sopt/solply_server/domain/place/cache/SnapshotLoader.java),
[DistanceSort](../../src/main/java/org/sopt/solply_server/domain/place/sort/DistanceSort.java).

## 7. 측정 결과와 설계 판단

실험 형상과 원자료는 [무부하 재빌드 비용 실측](../perf/2026-09-10-current-snapshot-rebuild-x10.md)에
정리돼 있다. 아래는 같은 호스트 조건의 유효 라운드 3개, **워밍업을 제외한 재빌드 15회**의
결과다. 메모리 수치는 원자료의 바이트 값을 MiB로 환산했다.

호스트 스왑이 발생한 라운드는 통째로 제외했고, 호스트 상태가 다른 라운드는 별도로 기록했다.
실험 진행 이력은 정본에 남기고, 여기서는 자원 여유와 설계 판단에 필요한 값만 다룬다.

### 10배 데이터에서도 재빌드가 자원 한계를 드러냈는가

| 항목 | 관측 결과 | 의미 |
|---|---|---|
| 재빌드 wall-clock | 중앙 **185 ms**, 범위 **173~215 ms** | 워밍업 후 한 번의 전체 생성·교체 시간 |
| 전후 구간 앱 CPU time | 중앙 **0.246초**, 범위 **0.199~0.336초** | 재빌드를 포함한 컨테이너 CPU 소비 |
| 같은 CPU 차분 구간의 평균 core | 중앙 **0.51 core**, 범위 **0.42~0.71 core** | 약 0.45~0.51초의 전후 측정 구간 기준 |
| CPU throttling | **15회 모두 0**, `throttled_usec` 증가도 0 | 정본 실행의 전후 구간에서 quota 제한 미관측 |
| 자연 발생 Young GC | **15개 관측 창 중 3개에서 각 1회** | pause **30.1 / 35.2 / 37.3 ms** |
| 자연 발생 Full GC | **유효 라운드 전체에서 0회** | 진단용 강제 GC는 제외 |
| 완료 후 10초의 GC | **15회 모두 0회** | 이 구간에 추가 자연 GC 미관측 |
| 재빌드 관측 창 안의 최대 Heap | **867.5 MiB**, 힙 상한의 **67.8%** | 해당 표본에서 약 **412.5 MiB**의 여유 |
| 진단 GC 후 전체 live heap | **96.5~97.8 MiB**, 힙 상한의 **7.5~7.6%** | current·표시값·프레임워크 등을 포함 |
| 재빌드 실행 스레드의 할당 | 라운드별 중앙 **250.3~253.2 MiB** | 최종 모델보다 큰 생성 과정의 할당 비용 |

CPU 차분은 재빌드 전후에 수집한 시각으로 계산했다. 이 구간에는 트리거 처리 등이 포함돼
재빌드 elapsed보다 길다. 따라서 `0.246초 ÷ 185 ms`를 재빌드의 평균 core라고 쓰지 않는다.
JFR의 200 ms 표본에서는 재빌드 주변에 약 1.2 core까지 관측됐지만, 이것 역시 해당 표본
구간의 평균이므로 순간 최대값이나 사용자 요청에 보장되는 남은 core로 해석하지 않는다.

**CPU와 GC에서 확인한 것은 워밍업 후 반복 재빌드가 이 조건에서 지속적인 자원 포화를
일으키지 않았다는 점**이다. 37.3 ms의 pause가 사용자에게 허용 가능한지는 응답 지연 목표와
함께 판단해야 한다. Full GC가 없다는 사실만으로 Old 영역에 압박이 전혀 없다고 단정하지도 않는다.

### 상주 모델은 작지만, 교체 과정에는 별도의 공간이 필요하다

진단 GC 후 전체 live heap은 약 **97 MiB**였고, 그중 Snapshot의 주요 객체는 다음과 같다.

| 구성 | 개수 | 크기 |
|---|---:|---:|
| `PlaceEntry` | 63,200개 | 4.82 MiB |
| `PlaceEntry[]` | 정렬 배열 330개 + 공용 빈 배열 1개 | 1.21 MiB |
| 좌표 `Double` | 장소당 2개, 총 126,400개로 산정 | 2.89 MiB |
| **위 주요 객체 합계** | | **약 8.93 MiB** |

정렬 배열 330개는 **동네 66개 × 정렬 축 5개**다. 331개의 동네나 별도의 전체 장소 배열을
뜻하지 않는다. 약 8.93 MiB는 주요 객체의 합이며, Snapshot의 맵·키 등 모든 메타데이터를
합산한 정밀 retained size는 아니다.

히스토그램에서 `PlaceEntry`와 `PlaceView`는 각각 63,200개로 확인됐다. **측정 종료 후
진단 GC를 거쳤을 때 current 한 벌에 해당하는 객체만 남았다**는 증거다. 과거 Snapshot을
계속 보관하지 않는 설계와 맞는다. 다만 반복 중 자연 GC의 바닥 표본이 충분하지 않아,
교체된 모델이 매번 언제 회수되는지나 장시간의 누적 추세까지 확인한 것은 아니다.

반면 재빌드 실행 스레드는 한 번에 약 **250 MiB**를 할당했다. 여기에는 새 Snapshot뿐
아니라 새 표시값과 DB 조회 결과, 그룹화·정렬용 임시 객체 등이 들어간다. 따라서 약 9 MiB의
Snapshot 주요 객체만 보고 재빌드의 Heap 비용도 그 정도라고 볼 수는 없다.

재빌드 관측 창 안의 폴링 최대 867.5 MiB에는 앞선 할당 중 아직 회수되지 않은 객체도 포함된다. 이를 재빌드
한 번의 순수 증가량이나 신구 Snapshot만의 공존 비용으로 분리할 수는 없다. 그래도 실제
힙 점유이므로 예산 판단에서 버릴 값은 아니다. **회수 뒤 상주량과 교체 주변 점유를 함께
봤을 때 여유가 관측됐으며, 순간 최대 점유를 완전히 포착했다고 보장하지는 않는다.**

### 높은 Heap 점유는 얼마나 유지됐고, 어떻게 회수됐나

**약 250 MiB는 재빌드 한 번의 실행 스레드 할당량이고, 800 MiB대는 그 시점의 JVM 전체
점유다.** 재빌드 직전부터 있던 상주 객체·작업 중인 객체·미회수 객체 위에 새 할당이 더해진다.
`current-g`의 한 실행은 다음과 같았다.

```text
재빌드 직전 약 551 MiB       ← 기존 상주량과 아직 회수되지 않은 할당 포함
  │
  ▼
재빌드 직후 약 807 MiB       ← 새 모델과 중간 객체 등이 추가됨
  │
  ▼
GC 직전 약 883 MiB           ← 이후 계측 등의 할당도 계속됨
  │
  ▼ Young GC · pause 39.9 ms
GC 직후 약 171 MiB           ← 높은 점유의 상당 부분이 자연 GC로 회수됨
```

200 ms 간격 Heap 시계열과 JFR을 대조하면, 같은 라운드에서 다음 두 구간을 확인할 수 있다.

| 구간 | 800 MiB 이상 연속 유지 | 자연 Young GC 전 → 후 | pause |
|---|---:|---:|---:|
| 첫 번째 | 약 20초 | 883 → 171 MiB | 39.9 ms |
| 두 번째 | 약 12초 | 887 → 201.5 MiB | 56.2 ms |

지속 시간은 여러 구간의 합이 아니라 **연속된 폴링 표본이 모두 800 MiB 이상이었던 시간**이다.
그동안 GC로 조금씩 낮춰 점유를 유지한 것이 아니라, 추가 할당이 이어지다가 마지막 Young GC에서
크게 내려갔다. 800 MiB는 지속 시간을 비교하기 위한 기준이며 JVM의 GC 임계값은 아니다.

이 사례는 높은 점유가 모두 상주 데이터는 아니었음을 보여 준다. 다만 어떤 이전 Snapshot이
언제 회수됐는지까지 구분해 주지는 않는다. 또한 **앞 표의 37.3 ms는 재빌드 직후 관측 창 안의
최대 pause다.** 이후 회수 구간에는 더 긴 pause와 더 높은 Heap 점유가 있으므로, 이를 전체
실험의 최대값으로 해석하지 않는다.

근거: [Heap 시계열](../../load-test/campaigns/2026-09-10_current-snapshot-rebuild-x10/results/metrics/current-g.heap.csv),
[JFR 원본](../../load-test/campaigns/2026-09-10_current-snapshot-rebuild-x10/results/jfr/current-g.jfr).

### 30초 반복 실험과 운영의 10분 주기는 구분한다

실험은 표본을 모으기 위해 약 30초마다 재빌드했고, 실행 사이에 강제 GC를 하지 않았다.
짧은 반복 주기와 계측 할당 때문에 앞선 작업의 미회수 객체가 남아 있는 상태에서 다음
재빌드가 실행될 수 있다. 따라서 **이번 800 MiB대 점유를 운영에서 재빌드 한 번마다 추가로
필요한 공간이라고 해석하지 않는다.**

운영에서는 10분 사이에 요청 처리와 자연 GC가 계속된다면, 이전 재빌드의 임시 객체가 다음
재빌드 전에 회수될 것으로 기대할 수 있다. 하지만 시간만 지나면 반드시 회수되는 것은 아니다.
할당이 적고 공간이 충분하면 미회수 객체가 오래 남을 수도 있다. 또 이전 객체가 회수돼도
새로운 요청 객체가 공간을 사용하므로, 다음 재빌드 직전 전체 점유가 반드시 낮아지는 것도 아니다.

따라서 운영에서는 최대 점유 하나보다 **자연 GC 후 점유가 계속 증가하는지, 회수 후 충분한
여유가 생기는지, GC 빈도·CPU 비용·pause가 응답 지연과 처리량에 부담을 주는지**를 함께 본다.
Young GC로 충분히 회수되고 그 비용을 감당할 수 있다면, 잠시 높은 Heap 점유 자체를 문제로
보지는 않는다.

### 결과를 적용할 범위

실험은 사용자 조회 부하가 없는 상태에서 수행했다. 계측도 비용을 쓰므로 수치를 순수한
재빌드 스레드의 비용으로만 해석하지 않는다. 비계측 대조 5회에서도 throttling은 없었지만,
그 라운드의 elapsed 중앙값은 228 ms로 더 길었다. 원인은 분리하지 못했으므로 185 ms를
항상 재현되는 시간으로 제시하지 않는다.

또한 정본은 워밍업 이후다. 기동 후 첫 워밍업에서는 CPU 소비가 더 컸고, 일부 throttling도
관측됐다. 정본 15회의 결과를 기동 직후부터 모든 상황에 확대하지 않는다.

### API JVM 안에서 주기적 재빌드를 유지한다

**조회가 재빌드를 기다리지 않는 구조와 10배 데이터에서 측정한 자원 비용을 고려하면,
평상시 요청 처리에 CPU·Heap 여유가 있는 조건에서는 재빌드가 서비스 성능을 크게 훼손할
가능성이 낮다고 판단했다. 따라서 주기적 전체 재빌드는 API JVM 안에서 수행하는 구성을 유지한다.**

이 판단은 구조와 측정 결과를 함께 근거로 한다.

- **재빌드 시간이 곧 요청의 대기 시간은 아니다.** write lock은 갱신 작업끼리만 직렬화한다.
  사용자 요청은 이미 확보한 immutable Snapshot으로 조회를 계속하므로, 새 모델의 생성과
  교체가 끝날 때까지 기다리지 않는다.
- **추가 CPU 작업은 짧고 드물다.** 10분 주기의 재빌드는 현재의 10배인 63,200곳에서도
  워밍업 후 중앙 185 ms에 완료됐다. 정본 15회에서 throttling이 관측되지 않았다는 결과와
  함께 보면, 지속적으로 요청 처리 여유를 잠식할 가능성은 낮다.
- **모델 보관과 교체에 쓸 Heap 여유가 관측됐다.** 1,280 MiB 힙에서 진단 GC 후 전체
  live heap은 약 97 MiB였고, 재빌드 직후 관측 창 안의 최대 점유는 약 868 MiB였다. 상주 모델뿐 아니라
  재빌드 중 임시 할당까지 고려해도, 무부하 측정에서는 메모리 한계에 접근하지 않았다.

남는 영향은 같은 JVM의 CPU와 GC를 공유하면서 생길 수 있는 일부 요청의 지연이다.
재빌드 직후뿐 아니라 이후 회수 구간의 GC pause도 요청을 멈출 수 있다. 위 사례에서는
39.9~56.2 ms의 pause가 확인됐다. 평소 CPU가
포화에 가깝다면 짧은 재빌드도 대기를 늘릴 수 있다. **따라서 이는 구조와 무부하 실측에
근거한 설계 판단이며, 피크 부하에서 응답 지연 목표를 충족한다고 검증한 결과는 아니다.**

현재는 이 구성을 유지하면서 운영에서 재빌드 시점의 CPU·Heap·GC와 응답 지연을 함께
관찰한다. 자원 압박이나 지연 증가가 나타나면 사용자 부하와 재빌드를 함께 실행해 경합을
확인하고, 생성 작업이 원인으로 확인되면 Snapshot Builder 분리를 검토한다. 여러 API에
공통 모델을 배포해야 하는 요구 역시 분리를 검토할 별도의 계기다.
