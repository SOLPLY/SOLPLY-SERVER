# 2026-08-01 · 캐시(A) vs DB 직행(B) — 캐시 존치 판정 (플랜 C Q1)

> **부하 테스트가 맞다** (게이트 ①): 구조 A/B의 처리 능력·자원 사용 비교. Artillery + 3단 지표 전부 사용.
> 아래 다섯 항목은 **측정 전 사용자 확정 완료 (2026-07-31).** 결과에 맞춰 수정하지 않는다.
>
> **선행 조건**: B 경로 구현 완료 (플랜: docs/superpowers/plans/2026-07-31-db-direct-path.md).
> 미구현 상태면 측정 불가 — 구현 세션부터.

## 1. 문제

#381 캐시의 존재 이유는 "캐시 미스마다 324만 엔트리 실시간 집계"를 피하는 것이었다.
사전 집계(place_stats) + 점수-캐시 분리를 거치며 **그 비용 자체가 소멸**했고, 지금 캐시가
담는 것은 장소 정보·태그뿐이다. 존재 이유였던 비용은 사라졌는데 캐시의 비용(코드 복잡도,
커서 세대 갈림 창, 인스턴스 간 불일치, town_id/active stale 계약, 플랜 C 숙제 전부)은 남아 있다.

## 2. 원인 가설

캐시가 현재 절약하는 것은 "장소 ~100행(시 단위 1,800행)+태그의 반복 조회"뿐이다.
B의 추가 비용은 요청당 인덱스 쿼리 2~3회(정렬된 페이지 id + 장소 fetch + 북마크 여부)로,
사전 집계 테이블이 있는 지금은 **동급 수준일 것**으로 추정한다.
단 baseline의 "요청당 14.2 statements"는 리팩터링 전 수치다 — **A부터 재측정**한다.

## 3. 기술적 선택

**B = 캐시 미사용 + DB 정렬 직행**: `idx_place_stats_town_score`로 인기순 커서 페이징을 DB에서
처리하고 페이지 20건만 places+태그 조회. LATEST·태그 필터도 DB로. `popular-read-mode` 토글로
같은 빌드에서 A/B 전환. 분산 캐시(Redis)는 Q1 제외 — Q2 소재.

**두 모드의 랭킹 소스가 같으므로(place_stats) 응답이 동일해야 한다** — 결과 diff 검증이
정합성 체크로 성립한다 (v0 시절엔 불가능했던 것).

## 4. 검증할 주장

목표 부하 **120 req/s**(DAU 11만 헤드룸, 산정 근거는 설계 §1.1)에서 B가 A와
1급 지표로 동급인가, 아니면 어느 한쪽이 명확히 우위인가.

## 5. 성공 조건 (사전 등록 — 2026-07-31 사용자 확정)

**효과 크기 예상: 2배 미만(동급)** → 가이드 A.1에 따라 응답시간이 아니라 **원인 지표 중심** 판정.

| 판정 | 조건 |
|---|---|
| **B 채택 (캐시 제거)** | 120 req/s에서 B: 성공률 100% · DB CPU 비포화(지속 80% 미만) · 요청당 statements가 **A+3 이내** · p50이 **A의 2배 이내** → 동급이면 단순화 이득이 승자 |
| **A 유지 (캐시 존치)** | B에서 성공률 저하·타임아웃, DB CPU 포화, 또는 p50 자릿수 열화 |
| **보류** | 그 사이 애매 구간 → 단계 증가 테스트(50→100→150→200)로 수용 한계 비교 후 사용자 결정 |

- 정합성 게이트 (판정 이전의 전제): 동일 요청 3종(무필터 1페이지 / 태그 필터 / 커서 2페이지)의
  **두 모드 응답 body가 동일**해야 한다. 다르면 측정 중단 — B 구현 버그다
- 라운드: 모드별 워밍업 1 + 본 3회, 같은 세션 연속 (가이드 §7), 중앙값 비교
- 시나리오: baseline `place-list-popular.yml` 재사용 (비교 가능성)

## 이 측정으로 말할 수 없는 것 (미리 명시)

- **LATEST 정렬의 부하 특성** — 시나리오가 인기순 중심이다. 근거로만 말한다: 정렬 대상 ≤1,800행
  filesort는 캐시 경로의 메모리 정렬과 같은 규모
- **캐시 제거가 없애는 정성 이득**(커서 세대 갈림 창, 인스턴스 간 불일치, 워밍 비용)은 지표에
  안 잡힌다 — 판정문에 정성 항목으로 기록
- **배치 실행 순간(02:00±6초)의 B 순간 부하** — 별도 라운드 없이는 말 못 함
- 로컬 절대치는 운영 SLO가 아니다 (지표 계약 A.3)

## 결과

**판정: B 채택 — 캐시를 제거한다.** 전문: [`docs/perf/2026-08-01-cache-vs-db-direct.md`](../../../docs/perf/2026-08-01-cache-vs-db-direct.md)

사전 등록한 성공 조건 4개를 모두 충족했고, 예상했던 "동급"이 아니라 **B가 모든 1급 지표에서
A와 같거나 나았다.** 모드별 3라운드 중앙값:

| 지표 | A (cache) | B (db) | 조건 | 판정 |
|---|---:|---:|---|---|
| 성공률 | 100% | 100% | 100% | ✅ |
| 요청당 statements | 15.18 | 17.18 (+2.00) | A+3 이내 | ✅ |
| p50 | 8.9 ms | 6.0 ms (−33%) | A의 2배 이내 | ✅ |
| DB CPU 평균/최대 | 26.9% / 76.7% | 25.7% / 56.3% | 지속 80% 미만 | ✅ |
| 요청당 앱 CPU | 6.19 ms | 4.57 ms (−26%) | — | (주장의 근거) |

정합성 게이트 3종 + 발급 커서 토큰까지 전부 동일. 6라운드 전부 유효(앱 CPU 200% 초과 샘플 0).

**가설이 과소평가한 것은 A의 비용이었다.** 캐시가 아끼는 것(인덱스 조회 2~3회)만 셈에 넣고,
캐시가 매 요청 치르는 비용(후보 1,800건을 flatMap해 메모리 정렬하는 앱 CPU)은 넣지 않았다.
요청당 힙 할당이 A 3,044 KB vs B 1,146 KB로 2.66배 차이 난다 — 후보 집합 캐시는 히트해도
정렬 비용이 매 요청 그대로 남는다.

**말할 수 없는 것 4건은 그대로 유효하고, 측정 중 3건이 추가됐다** (결과 문서 §9). 그중
운영에 직접 걸리는 것: db 모드는 `ps.active`가 낡은 장소를 누락하므로 동네 재활성화 시
최대 24시간 인기순에서 사라질 수 있다 — **B 채택은 Q3(동기 갱신 훅)를 필수로 만든다.**
