# 사전 조사: 메인 검토를 반영한 인계 요약

기준 형상: `develop@64a97e08274303199b33244ba579adde22e4437d`.
정본: [최종 설계](../design/2026-09-21-place-list-town-cache.md).
Opus5 읽기 전용 조사와 메인의 코드 확인을 취합했다. 구현/테스트/신규 측정 결과가 아니다.

## 확인한 출발점

- `SortedPlaces`는 이미 동네별/정렬축별 배열이다. 동네별로 바꿀 것은 적재, 소유, 버전, 교체 범위다.
- `SnapshotLoader`는 전체 `place_stats`와 tags를 읽는다. metadata와 source를 RR read view로 묶는 현행 규칙은 보존해야 한다.
- `SnapshotBox`는 최신 전역 스냅샷 한 장. 과거 버전 저장소가 아니다.
- `PlaceListRequestOrchestrator`의 요청 catch-up은 cursorVersion 기준이며 revision 차이는 차단하지 않는다. 새 정책에서는 정렬/필터/대상 변경을 자동 분류해 동네 버전을 올려야 한다.
- `PlaceService.listPlaces`는 전역 표시 holder에서 값이 없으면 항목을 제외한다. 동네 캐시 객체에 표시값을 함께 소유하여 일부 적재/삭제로 대상이 조용히 빠지지 않도록 해야 한다.
- `SortedPlaces.patch()`는 main 호출부가 확인되지 않았다. 현행 부분 적재 구현으로 간주하지 않는다.
- `PlaceListDbQueryRepository`는 기존 비교 SQL을 제공하지만 현재 일반 목록 요청 경로에 연결되어 있지 않다. 설정만 바꿔 DB 비교가 가능하다고 가정하지 않는다.
- Caffeine 의존성은 `build.gradle`에 이미 있다. 현 main cache에서 사용 중이라고 해석하지 않는다.
- 실제 `PlaceListCursor.FORMAT_VERSION`은 **v7**이다. 주석에 v6 설명이 남아 있으므로 상수를 기준으로 새 포맷 전환을 검토한다.

## 구현 전 유의점

- 동네 버전은 한 번호로 충분한 후보다. 기존 `(revision, cursorVersion)`을 동네별 두 번호로 그대로 복제하지 않는다. 표시값은 다음 전체 배치까지 지연 허용한다.
- 관련 버전들을 `IN` 한 문장으로 읽는 방식은 좋은 후보지만, 사용자 계약은 **하나의 일관된 read view**이지 특정 SQL 문장 수 자체가 아니다. 불필요한 N+1은 비용으로 검증한다.
- 정기 전체 배치 후 모든 동네 캐시는 최신 버전과 달라질 수 있다. 실제 적재량은 이후 조회되는 동네 수/요청 분포에 달렸다. 전 동네가 즉시 적재된다고 단정하지 않는다.
- 여러 동네 중 하나가 변경되면 해당 탐색은 만료한다. 이것이 기존 전역 버전 방식보다 만료 범위를 넓힌다고 단정할 근거는 없다. 전역 방식은 무관한 동네 변경도 영향을 준다.
- 동등성은 동일한 사용자 결과/정렬/필터/페이지 계약이다. 기준선과 새 방식의 커서 문자열이 바이트 단위로 동일해야 한다는 조건을 임의 추가하지 않는다.
- 거리순은 사용자 명시 제외 사항이다. 이를 별도 최적화/벤치/설계 질문으로 재도입하지 않는다. 공통 코드 변경이 기존 경로에 주는 영향은 최소화한다.
- Flyway 번호는 구현 직전에 디렉터리 최신 번호를 확인해 배정한다. 사전 보고서의 예시 번호를 그대로 쓰지 않는다.

## 실패와 경쟁 검증 포인트

- 동네별 버전과 원본 변경의 원자성, 롤백, 동네 이동 양쪽 버전.
- 적재 도중 버전 변화, metadata/source 다른 시점 혼합 금지.
- 하나의 요청에 관련된 모든 동네 대기를 합쳐 1초 예산 적용. 동네마다 1초씩 늘어나는 구현 금지.
- 한 요청의 timeout/cancel이 공용 적재를 취소하지 않는지, 실패가 다른 동네 대기까지 전파되지 않는지.
- 새 캐시 게시 후 오래된 적재가 도착해 덮어쓰는 경쟁.
- 표시값만 바뀐 동네도 성공한 정기 전체 배치 후 재적재 대상에 포함되는지.
- 현행 SQL 실패 시 waiter가 바로 실패하지 않고 요청 timeout까지 남을 수 있다. 새 실패전파 정책은 이 동작을 무비판적으로 복제하지 않는다.

## 로컬 환경과 과거 자료

- 조사 워커는 Docker daemon 연결 실패를 보고했다. 재개 시 상태를 다시 확인해야 한다. 이것은 새 벤치의 불가능 판정이나 운영 상태가 아니다.
- `docker/docker-compose.bench.yml`은 앱 1대 + nginx edge + MySQL + Redis 형태다. 이번 캐시 설계에 Redis를 도입한다는 뜻이 아니다. 실제 실험 topology/resource는 실행 전에 확인하고 별도 캠페인에 고정한다.
- local ignored `application.yml`의 count/score/safety cron은 annotation 기본값과 다르다. 이 차이는 메인과 워커가 각각 확인했다. 현재 로컬값 또는 코드 기본값을 운영 실제 주기라고 부르지 않는다.
- 이전 63,200 장소 리빌드 비용(185ms 중앙값 등)은 과거 형상에서 얻은 무부하 측정이다. 현재 전체 스냅샷이나 동네별 경로의 검증 결과가 아니다.
- 기존 `load-test` 도구, seed, JVM/JFR 기록을 재사용할 수 있으나 거리순을 뺀 새 요청 믹스는 과거 믹스와 다른 워크로드다. 과거 절대값과 직접 우열 비교하지 않는다.

## 새 메인이 정리할 실행 계획

1. 최종 요구사항에 맞는 최소 공통 버전/커서 계약과 세 후보의 구현 인터페이스를 정한다.
2. 같은 동네 집중/여러 동네 분산, hit/cold miss, 부분 변경/전체 배치 후 조회를 구분한 실험 조건을 수치로 사전 기록한다.
3. 정합성 검증 후 단일 적재 비용부터 측정하고, 필요한 경우 서빙 부하 비교로 확장한다.

작업자의 초안에 있던 `10배 이상 개선 필수`, 관측 후 유리한 성공선 결정, 3초를 새 기본 예산으로 확장, 이슈/이미 합의한 정책 재승인은 **채택하지 않는다**. 가설을 기각할 수 있는 비교여야 하며, 수치를 본 뒤 성공 조건을 만들지 않는다. 현재 사용자 대기 예산은 1초다.
