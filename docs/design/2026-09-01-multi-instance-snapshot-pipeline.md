# 2026-09-01 · 다중 인스턴스 스냅샷 파이프라인 — 버전·커서 정합의 확장 설계

> **지위: 스케일아웃 안건의 확정 설계다. 지금 짓지 않는다.**
> 발동 조건은 "앱 인스턴스를 2대 이상으로 늘리기로 결정하는 날"이며, 그 전까지 운영 코드는
> #397의 단일 인스턴스판(로컬 보존 3장 + 인스턴스 로컬 버전)으로 충분하다. 단일 인스턴스판은
> 이 설계의 부분집합이라, 착수하는 날 이 문서의 파이프라인으로 확장하면 된다.
> 설계 합의는 2026-09-01 그릴링 세션. 구현이 이 문서와 달라지면 문서를 먼저 고친다.

## 1. 무엇이 문제인가

#397의 목록 스냅샷은 두 가지가 **인스턴스 로컬**이다.

- **회차 버전이 로컬이다.** 버전이 그 JVM이 찍은 시각이라, 인스턴스 A가 발급한 커서를 B가
  받으면 B의 보존 목록에 그 버전이 없다 — 내용이 사실상 같은 사진을 들고서도 커서를 만료시킨다.
  라운드로빈 N대면 2페이지 이후 요청의 약 (N−1)/N이 만료된다.
- **어드민 훅이 로컬이다.** 커밋 뒤 재생성은 그 요청을 받은 JVM에서만 돌아, 나머지 인스턴스는
  자기 타이머(10분)까지 낡은 사진을 서빙한다. "어드민 변경은 즉시 보인다"는 1순위 요구가
  다중 인스턴스에서 깨진다.

두 로컬성 모두 해당 코드 javadoc에 "스케일아웃할 때 이 기능부터 되짚을 것"으로 박혀 있고,
이 문서가 그 되짚음의 결과다.

## 2. 요구사항 — 그릴링에서 확정된 순서대로

1. **어드민 변경은 전 인스턴스에서 즉시 보인다.** (기존 1순위 요구의 클러스터 확장)
2. **클러스터는 같은 사진으로 수렴한다.** 인스턴스마다 첫 페이지가 제각각인 상태를 평시
   상태로 두지 않는다. 다만 "전원 동시 전환"은 분산 환경에서 물리적으로 불가능하므로,
   보장하는 것은 전파 지연(수십 ms) 안의 수렴이다.
3. **커서는 인스턴스를 넘어도 이어진다.** 버전이 가리키는 사진을 어느 인스턴스에서든 찾을 수
   있어야 하고, 찾지 못하면 조용히 다른 회차로 갈아타는 대신 명시적으로 만료시킨다.
4. **Redis 장애는 서비스 장애로 번지지 않는다.** 데이터의 정본은 어디까지나 MySQL이다.

## 3. 파이프라인 — 흐름은 하나다

트리거가 무엇이든(어드민 수정이든 10분 타이머든) 같은 흐름을 탄다. 경로가 하나면 고장도
한 곳에서 난다는 것이 이 구도의 유지보수성 근거다.

```
[빌더 하나]                    [Redis]                      [전 인스턴스]
 어드민: 그 요청의 인스턴스     snapshot:s{스키마}:{버전}      NEW_VERSION 수신
 타이머: ShedLock 리더    ──▶   (TTL 60분, 통짜 blob)   ──▶   아카이브에서 fetch
                                    │                        역직렬화 → 인덱스 재조립
 DB에서 사진 생성                    └─ PUBLISH ────────────▶  로컬 보관소 put
 버전 발급 (epoch ms)                  NEW_VERSION(v)          로컬 최신보다 새면 채택
```

### 3-1. 빌드 — 이벤트당 빌더는 하나다

**의도: 버전 발급 주체를 하나로 좁혀 "버전↔내용 1:1" 불변식을 구조로 보장한다.**
버전 번호는 빌더가, 사진을 완성한 순간에, 한 번만 발급한다. 남의 버전에 내 내용을 붙이는
경로가 존재하지 않으므로 "버전은 같은데 스냅샷이 다른" 사고가 원천 봉쇄된다.

- 어드민 수정 → 그 요청을 받은 인스턴스가 빌더다 (afterCommit 재생성, #397 그대로).
- 10분 타이머 → ShedLock 리더 하나만 빌더다. 클러스터 전체 DB 부하가 회차당 1회로 준다.
  (#397의 "인스턴스마다 각자 타이머"는 이 지점에서 리더 방식으로 바뀐다 — 각자 빌드는
  강등 경로로만 남는다, §3-6.)
- 빌드 자체는 #397과 동일: 읽기 트랜잭션 하나에 쿼리 2문장, 완결된 사진만 만든다.

체크할 것
- [ ] 버전 발급이 빌드 완료 시점 한 곳뿐인지 (수신·채택 경로 어디에도 발급이 없는지)
- [ ] 어드민 훅의 트랜잭션당 1회 접기, 실패 격리(직전 사진 유지)가 승계됐는지
- [ ] 타이머 리더 잠금이 기존 배치의 ShedLock 관례와 같은 방식인지

### 3-2. 아카이브 적재 — 통짜 blob, TTL 60분

**의도: 사진의 저장 형태를 사진의 계약과 일치시킨다 — 불변·원자·회차 단위.**
`SET snapshot:s{스키마버전}:{버전}` (TTL 60분). 값은 Entry 목록의 직렬화 바이트 전체다.

- **직렬화 대상은 Entry 목록까지다.** 정렬 배열은 참조 구조라 직렬화가 무의미하고, 수신 측이
  `PlaceListIndex.of(entries)`로 재조립한다. 포맷 = "Entry 목록의 스키마"이며 그 이상이 아니다.
- **포맷은 스키마 있는 바이너리(Protobuf/MessagePack 계열) 또는 커스텀 Jackson.** 타입과
  null 유무를 스키마 수준에서 못 박기 위해서다. BigDecimal은 원생 타입이 없으므로 **스케일을
  보존하는 표현(문자열 또는 unscaled+scale 쌍)을 스키마에 명시**한다 — 흐려지면 4.50이
  4.5가 되어 응답 바이트 등가가 깨진다. 좌표의 null은 "좌표 없음"이라는 의미값이다 —
  0.0으로 접히면 거리순 후보가 오염된다.
- **키에 스키마 버전을 넣는다.** 롤링 배포 중 구코드는 자기 스키마 키만 읽으므로 신포맷을
  역직렬화하다 넘어질 일이 없다. 어긋난 커서는 아카이브 미스 = 만료 = 1페이지 리셋으로
  떨어지고, 옛 사진의 물리 폐기는 TTL이 한다 — 별도 청소 작업이 없다.

체크할 것
- [ ] **왕복 등가 테스트가 첫 삽이다**: 직렬화 → 역직렬화 → 재조립한 사진의 응답·커서가
      원본과 바이트째 같은지. #397의 "스냅샷 vs DB 경로" 등가 게이트와 같은 계보의 안전망.
- [ ] 직렬화 사진 크기 실측 (산수 추정 1~3MB — 실측으로 대체할 것)
- [ ] 배포 창을 걸친 스크롤의 만료는 수용 항목으로 기록

### 3-3. 전파 — 페이로드 없는 발행

**의도: 전파가 나르는 것은 "새 회차가 있다"는 사실뿐이다. 사진은 아카이브에서 가져온다.**
`PUBLISH snapshot-events NEW_VERSION(v)`. Pub/Sub는 유실될 수 있는 채널이지만 정확성에
닿지 않는다 — 유실된 인스턴스는 다음 10분 회차 발행이 흡수하고, 그 사이 낡은(그러나 그
자체로 완결된) 사진을 서빙할 뿐이다.

체크할 것
- [ ] 수신 처리 래치: 발행이 몰릴 때 "진행 중 1 + 대기 1"로 접는지 (발신 측 트랜잭션당
      1회 접기와 같은 계보)
- [ ] 유실 시 낡음 상한이 타이머 주기(10분)로 닫히는지

### 3-4. 채택 — 전원이 같은 사진을 받아 든다

**의도: 클러스터 수렴. 아카이브에 이미 있는 사진을 각자 DB에서 다시 짓는 중복을 없앤다.**
수신 인스턴스는 `snapshot:s{n}:{v}`를 GET → 역직렬화 → 인덱스 재조립 → 로컬 보관소 put →
**받은 버전이 로컬 최신보다 새면** current로 채택한다. 버전이 epoch ms 단조라 이 로컬 비교가
곧 순서 가드이고, 원안의 `snapshot:current` 포인터·CAS·리더 선출은 전부 불필요해진다.

체크할 것
- [ ] 채택 가드가 로컬 비교 하나뿐인지 (전역 포인터를 들이지 않았는지)
- [ ] 역직렬화 실패 시 그 사진을 버리고 자가 빌드로 후퇴하는지 (오답 채택 금지)
- [ ] 인덱스 재조립 비용 실측 (미실측 — 외부에서 돌던 1.44ms 류 수치는 출처가 없어 기각,
      짓는 날 왕복 등가 테스트와 함께 잰다)

### 3-5. 서빙과 커서 해석 — #397 그대로, 한 단계만 추가

**의도: 커서 계약(v6, 회차 고정, 명시 만료)은 이미 구현된 것을 그대로 쓴다.**
커서 해석이 로컬 보관소 → **Redis 아카이브** → 만료의 3단이 될 뿐이다.

```
커서 없음        → 로컬 current로 서빙, 커서에 그 버전
커서 버전 v 있음 → 로컬 byVersion(v) 적중 → 그 사진으로 서빙 (회차 고정)
                → 미스 → Redis GET → 적재 후 서빙   ← 이 단계만 신설
                → 그것도 미스 → EXPIRED_PLACE_CURSOR (1페이지 리셋)
```

체크할 것
- [ ] Redis fetch가 커서 미스 경로에만 있는지 (첫 페이지 핫패스에 Redis가 없는지)
- [ ] 만료 응답의 클라이언트 처리(1페이지 재요청)가 이미 v6 계약에 있으므로 추가 계약 없음

### 3-6. 강등 — Redis가 죽으면 #397 단일 인스턴스판으로 후퇴한다

**의도: Redis는 회차 사진의 아카이브이자 신호 버스이지, 데이터의 정본이 아니다. 정본은 MySQL이다.**

| Redis 다운 시 | 동작 |
|---|---|
| 서빙 | 로컬 보관소의 사진으로 정속 지속 — 서비스는 멈추지 않는다 |
| 신선도 | 각 인스턴스가 자가 빌드 타이머로 후퇴 (이 경로는 코드에서 사라지지 않는다) |
| 클러스터 수렴 | 한시 포기 — 인스턴스별 사진이 갈라진다 (문서화된 강등) |
| 교차 인스턴스 커서 | 아카이브 조회 불가 → 그 경우에 한해 만료로 강등 |

체크할 것
- [ ] 자가 빌드 경로가 살아 있고 강등 시 자동 발동하는지 (별도 스위치 없이)
- [ ] Redis 복구 후 다음 발행부터 수렴이 재개되는지 (복구 절차가 무개입인지)

## 4. 계약 요약

| 계약 | 값 | 성격 |
|---|---|---|
| 커서 보장 수명 | **Redis TTL 60분** | 사용자에게 하는 약속의 정본. #397의 20~30분(로컬 3장)에서 확장 |
| 로컬 보관소 상한 | 8개 (ConcurrentSkipListMap, 나이순 동기 축출) | **계약이 아니라 힙 예산** (~한 자릿수 십 MB). 어드민 편집이 몰려 로컬 창이 줄어도 보장은 TTL이 지므로 #397의 "회차 기준 보존 창 축소" 약점이 소멸 |
| 타이머 주기 | 10분 유지 | 조절하는 것은 카운트·점수 낡음 상한 하나. 리더 단일 빌드라 늘려서 아끼는 비용이 사실상 0이라 신선도를 내주지 않는다 |
| 어드민 반영 | 커밋 직후 빌드 + 발행 → 전 인스턴스 수십 ms 수렴 | 1순위 요구 |
| 버전 | epoch ms, 빌더만 발급 | 버전↔내용 1:1 불변식의 근거 |

로컬 보관소는 캐시 라이브러리 없이 짓는다 — Caffeine의 W-TinyLFU가 갓 만든 회차를 "접근
빈도 낮음"으로 축출하는 입장 심사 함정, 비동기 청소의 비결정성, 설정 표면을 근거로 기각.
옛 골격 스냅샷이 같은 근거로 캐시 라이브러리를 기각했던 선례와 같은 계보다.

## 5. 기각한 대안들 — 왜 이 모양이 아닌가

**DB 버전 행 (V29 계보).** 회차마다 전 행을 새 버전으로 적재하면 10분 주기 기준 하루 약 91만
행의 쓰기 증폭, 증분 리스너의 표적 버전 문제, 청소 배치가 따라온다. 이 저장소가 실제로 지었다가
V32에서 되돌린 실물이다 — [2026-08-05 설계서](2026-08-05-place-stats-version-rows.md)의
철거 사유가 그대로 유효하고, 사진의 보관은 DB의 일이 아니라 캐시의 일이다.

**Redis ZSET 등으로 정렬을 분해 저장.** 정렬별 ZSET에 (점수, placeId)를 싣는 모양은 세 가지에서
진다. 사진의 소비 단위가 "회차 전체"라 부분 조회·부분 갱신의 소비자가 없고(통짜 GET 한 번이
정확히 필요량이다), 정렬 5종 × 동네 × 회차의 키 폭발에 태그 비트마스크 필터는 Redis에서 돌릴
수도 없으며, 무엇보다 "언제나 완결된 한 회차"라는 핵심 계약이 키 수십 개에 흩어져 원자 교체가
소멸한다. **저장 형태는 계약의 모양을 따라간다 — 불변·원자 단위면 통짜 blob이다.**

**신호만 전파하고 각자 DB에서 재빌드.** 그릴링에서 한 차례 추천됐다가 기각됐다. 수신 사진이
더 신선해지는 장점은 있으나, 클러스터가 서로 다른 사진을 드는 상태가 평시가 되고, 아카이브에
이미 있는 사진을 두고 DB 읽기를 반복한다. 요구 2(수렴)가 확정되며 채택 방식으로 정리됐고,
자가 재빌드는 강등 경로로 생존한다.

**전파 없이 lazy fetch만.** 커서 정합은 성립하지만 어드민 즉시성(요구 1)이 다른 인스턴스에서
최대 10분 깨져 기각.

**세션 고정(sticky session).** 설계 무변경으로 로컬 버전이 성립하는 가장 싼 대안. LB 의존이
생기고 수렴 요구는 못 채우므로 채택하지 않되, "인프라 사정으로 Redis를 들일 수 없는 날"의
차선으로 기록해 둔다.

## 6. 외부 검색 엔진은 언제인가

이 파이프라인은 "정렬 5종 + 동네 + 태그 비트마스크"라는 **닫힌 질의 집합**을 인메모리 전량
사진으로 푸는 구조다. 검색 엔진(Elasticsearch 계열)을 들이는 시점은 이 구조의 전제 중 하나가
깨질 때이고, 그 전에는 운영물만 하나 늘 뿐이다.

| 깨지는 전제 | 신호 |
|---|---|
| 질의 집합이 닫혀 있다 | 형태소·오타 허용 전문 검색, 반경/폴리곤 지리 질의, 태그 64비트를 넘는 필터 조합 요구 |
| 전량이 메모리에 든다 | 장소 수가 현재의 수십 배(수십만)로 늘어 사진 크기·재생성 시간이 힙 예산과 어드민 응답 지연을 압박 |
| 전량 재생성이 싸다 | 재생성이 수 초대로 올라 afterCommit 훅이 어드민 응답을 눈에 띄게 붙잡음 |

그날이 와도 이 문서의 계약은 이식된다 — 회차 고정·명시 만료는 검색 엔진의 point-in-time
reader + 커서 API에 같은 모양으로 대응되므로, 클라이언트 계약(v6·만료 시 1페이지 리셋)은
저장 기술과 독립적으로 살아남는다.

## 7. 착수하는 날의 순서

1. 직렬화 스키마 + **왕복 등가 테스트** (여기가 첫 삽 — 급소부터 잠근다)
2. 아카이브 적재 (빌드 완료 지점에 SET 한 줄)
3. 커서 해석에 Redis fetch 단계 추가 (로컬 미스 → GET → 만료)
4. 발행·수신·채택 경로 (+ 수신 래치, 역직렬화 실패 시 후퇴)
5. 타이머의 ShedLock 리더 전환
6. 강등 시나리오 테스트 (Redis 차단 상태에서 서빙 지속·수렴 포기·커서 만료 확인)

1~3까지만으로도 "교차 인스턴스 커서"는 성립한다(수렴 없이). 4~5가 요구 1·2를 마저 채운다.
단계마다 배포 가능한 중간 상태다.

## 8. 이 문서로 말할 수 없는 것

- **비용 수치는 전부 산수 추정이다.** 직렬화 사진 크기(1~3MB), 재조립 CPU, Redis 왕복,
  채택 지연(수십 ms) — 실측 전이다. 그릴링 중 외부에서 돌던 "1.44ms" 류 수치는 출처가 없어
  기록에서 배제했다.
- **Redis 자체의 구성(단일/센티널/클러스터)은 다루지 않았다.** 착수 시점의 인프라 사정에 따른다.
- **몇 대까지 버티는가를 말하지 않는다.** 이 설계의 스케일 한계(발행 폭주, 아카이브 대역)는
  인스턴스 수십 대 규모의 질문이고, 그 전에 §6의 전제들이 먼저 깨질 가능성이 크다.
