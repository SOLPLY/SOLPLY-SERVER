# 반복 DB 조회 비용을 줄이면서 사용자가 보던 장소 목록을 유지하기

장소 목록을 요청할 때마다 DB를 조회하던 구조에서, **동네별 데이터를 불변 버전으로 보관하고 정렬 결과를 재사용하는 구조**로 변경한다. 목적은 [반복되는 JDBC 처리·Hibernate 객체 매핑](../perf/2026-08-06-jfr-saturation-short.md)을 줄여 요청 처리에 필요한 애플리케이션 CPU 여유를 확보하는 것이다. 캐시를 빠르게 읽는 것뿐 아니라, 사용자가 스크롤하는 동안 같은 장소 집합과 순서를 유지해야 한다.

## 1. 요구사항 — 최신 목록으로 시작하고, 선택한 목록으로 이어 본다

사용자는 여러 동네와 태그·정렬 조건을 선택한다. 서울 전체 조회와 상세보기를 다녀온 뒤의 스크롤도 고려한다. 현재 자원 기준은 API 서버 1대·2 CPU·메모리 2GiB·JVM 힙 1,280MiB다. 관리자 수정은 드물 것으로 예상하며, 통계는 주로 배치로 바뀐다. 리뷰 통계는 매시간, 북마크 델타는 기본 15분 간격으로 갱신하도록 설정되어 있다.

목록을 보는 도중 변경 사항을 늦게 보여주는 것은 허용한다. 대신 **정상 응답에서는 페이지 사이의 데이터 변경 때문에 장소가 중복되거나 누락되지 않아야 한다.** 약 5분 안의 이어보기를 중요하게 보되 무기한 보관은 요구하지 않는다.

| 상황 | 사용자에게 제공할 동작 |
|---|---|
| 첫 페이지·명시적 새로고침 | DB에서 확인한 최신 동네별 버전으로 시작 |
| 다음 페이지의 버전 확보 가능 | 첫 페이지와 같은 집합·필터 값·정렬 기준으로 이어보기 |
| 로컬에 없지만 여전히 최신 버전 | 같은 버전을 재적재해 이어보기. 추가 지연 발생 가능 |
| 일시적인 조회·적재 실패 | 같은 커서로 재시도 |
| 필요한 과거 버전의 부재가 확인되고 복구 불가 | 첫 페이지부터 다시 조회하도록 안내 |

따라서 사용자 영향을 나타내는 지표는 캐시 미스율보다 **다음 페이지를 요청한 탐색 중 처음부터 다시 시작해야 했던 탐색의 비율**이다. 재시도와 재적재 지연은 별도로 본다. 실제 운영의 탐색 지속시간·재시작 비율은 아직 측정하지 않았다.

## 2. 설계의 중심 — 읽던 버전을 일정 기간 유지한다

**MVCC처럼 새 버전이 생겨도 기존 읽기는 선택한 버전을 계속 보는 방식이다.** DB의 트랜잭션 격리 전체를 구현하는 것은 아니며, 목록 조회에 필요한 동네별 스냅샷을 보관한다.

```text
첫 페이지: A동네 v10 + B동네 v20 선택
다음 페이지: 같은 버전 조합 + 같은 필터·정렬 조건
데이터 변경: 새 버전을 별도 생성하고 기존 객체는 유지
```

버전이 고정하는 대상은 장소 집합과 필터·정렬에 쓰는 값이다. 표시값만 바꾸는 모든 수정이 버전을 올리지는 않는다. 커서에는 동네별 버전 조합과 조회 조건을 연결하며, 원하는 과거 버전이 없을 때 최신 데이터를 이어 붙이지 않는다.

DB에서는 목록 데이터 변경과 동네 버전 증가를 같은 쓰기 트랜잭션으로 커밋한다. 적재할 때는 [`TownSourceLoader`](../../src/main/java/org/sopt/solply_server/domain/place/cache/town/TownSourceLoader.java)가 **같은 읽기 전용 REPEATABLE READ 트랜잭션에서 버전과 장소 데이터를 읽는다.** 번호만 먼저 읽고 별도 시점의 데이터를 그 번호로 저장하지 않는다. 여러 동네의 전역 단일 시점까지 보장하는 구조는 아니다.

## 3. 첫 번째 트레이드오프 — 해당 동네 전체 재조회 vs 변경분으로 새 버전 구성

**필요한 해당 동네의 모든 장소를 다시 읽어 새 버전을 만든다.** 변경되지 않은 행도 읽는 대신 삭제·변경 이력을 추적하고 적용하는 절차를 줄인다.

부분 반영을 하더라도 기존 사용자가 읽는 버전을 수정할 수는 없다. 새 버전을 구성하려면 기준 버전 이후의 변경과 삭제를 빠짐없이 알아야 한다. 변경되지 않은 객체를 공유할 수는 있지만, 현재 배열·맵 구조에서는 새 버전의 장소 참조 모음을 구성하는 비용까지 사라지지 않는다.

현재 변경 경로는 버전 구간별 변경 이력을 보관하지 않으며 전체 통계 배치도 실제 변경 장소 목록을 만들지 않는다. **결정을 가른 것은 적재 비용을 없애는 것보다 변경 추적의 복잡도를 줄이는 편이 현재 구조에 적합하다는 점이다.** 부분 반영보다 실행 비용이 작다고 입증한 것은 아니다. 큰 동네에서 소수 장소가 자주 바뀌어 전체 재적재가 부담이 된다면 변경분 구성 쪽이 유리해질 수 있다.

## 4. 두 번째 트레이드오프 — 정렬 순서대로 태그 검사 vs 역색인으로 후보부터 추출

같은 버전의 정렬 결과는 재사용한다. 장소 객체 한 벌을 여러 정렬의 참조 배열이 공유하며, 필요한 배열은 처음 요청될 때 생성한다. 핵심 판단은 생성 시점보다 **정렬된 배열에서 조건을 검사할지, 태그로 후보를 먼저 추린 뒤 정렬할지**다. 대상은 인기순 등 정적 정렬 5종이며, 사용자 좌표에 따라 달라지는 거리순은 별도 경로다.

### 선택: 커서 다음부터 검사하고, 다음 한 페이지를 찾으면 멈춘다

정렬 배열을 읽으며 태그 비트마스크를 검사하고 페이지 크기 L에 다음 페이지 확인용 1건을 더 찾으면 멈춘다. 여러 동네는 정렬 배열을 병합한다. 불일치 장소도 검사하므로 희소 조건이나 일치 장소가 뒤에 몰린 조건에서는 비효율적일 수 있다.

그럼에도 유지한 근거는 다음과 같다.

- 필요한 결과는 태그 일치 장소 전체가 아니라 **정렬된 다음 L+1건**이다. 일치 장소가 충분하면 후보 전체 수집·정렬 없이 조기 종료한다.
- 다음 요청은 커서 이전 범위를 건너뛴다. 첫 페이지에서 지나간 불일치 범위를 매번 처음부터 검사하지 않는다. 다만 다음 페이지 확인을 위해 미리 읽었던 일부 범위는 다시 검사할 수 있다.
- 일치 장소가 적으면 이어지는 페이지 수도 적다. 한 페이지의 긴 검사를 모든 후속 페이지에서 반복한다고 계산하지 않는다. 이것이 해당 조건의 요청 빈도가 낮다는 뜻은 아니다.

### 측정: 두 방식 모두 유리한 조건이 있었다

합성 데이터 24조건을 독립 JVM 3회로 비교했다. 역색인은 **후보 추출 → 커서 조건 적용 → 정렬 → L+1건 반환**까지 측정했다. 아래는 인기순 페이지당 실행 스레드 CPU이며 HTTP 응답시간이 아니다.

| 동네당 장소 × 선택 동네 / 조건 | 정렬 배열 검사 | 역색인 + 후보 정렬 |
|---|---:|---:|
| 100 × 3 / 흔한 태그 | 0.342µs | 5.348µs |
| 100 × 3 / 희귀 조합 | 4.547µs | 0.214µs |
| 1,000 × 3 / 뒤쪽 집중 | 72.832µs | 5.391µs |

1,000곳은 성장 민감도를 보기 위한 조건이며 실제 동네 규모가 아니다. 5개 정적 정렬의 결과 동등성을 확인했으며 성능 측정은 인기순에 한정했다. [상세 조건과 결과](../perf/2026-09-23-tag-scan-vs-index.md)

**모든 조건에서 빠르기 때문에 선택한 것이 아니다.** 커서 진행과 조기 종료를 활용하면서 희소 조건의 추가 검사 비용을 감수한다. 큰 동네·여러 동네에서 희소 조건의 반복 요청이 실제 CPU 부담을 차지하면 역색인을 검토한다. 그때는 동네·버전별 태그 후보 집합을 만들고, 태그 그룹 안의 합집합·그룹 사이의 교집합으로 후보를 추린 뒤 커서 이후 후보를 정렬하거나 상위 L+1건을 선택한다. 인덱스도 같은 불변 버전에 묶어 보관해야 한다.

## 5. 세 번째 트레이드오프 — 이전 버전으로 이어보기 vs 누적 보관의 메모리·GC 비용

**버전이 바뀌어도 이전 데이터를 바로 제거하지 않는다.** 새로고침을 줄이는 대신 최신 데이터 한 벌보다 많은 객체를 보관하고, 요청과 새 버전 적재가 겹치는 비용을 부담한다.

판단에 필요한 실험은 특정 시간 동안 기다리는 것이 아니라, **여러 버전을 쌓아 둔 상태에서 요청과 버전 갱신·재적재가 겹쳐도 무리가 없는지** 확인하는 것이었다. 합성 데이터 6,320곳·66동네를 사용했고 API 자원은 1절의 조건이다.

| 확인 항목 | 결과 |
|---|---|
| 전 동네 한 벌의 객체 그래프 크기 | 정적 5개 정렬 배열 포함 약 2.11MiB |
| 부하 중 마지막 누적량 | 전체 데이터 17.5벌에 해당하는 장소 객체 |
| 마지막 부하 구간 | 목표 120요청/초, 서울 전체 조회 약 83%, 9,639건 모두 정상 |
| GC 후 앱 전체 힙 | 약 121MiB |
| 부하 중 자연 Young GC | 10회, 정지 시간 합계 0.239초 |
| 적재 실패·용량 제거 | 0건 |

전 동네 10버전을 미리 보관하고 두 부하 구간에서 버전을 8회 더 갱신했다. 모든 동네가 같은 수의 버전을 가진 것은 아니다. 객체 그래프 크기와 GC 후 앱 전체 힙도 서로 다른 측정값이다. 측정 범위는 로컬 다중 버전 캐시이며 Redis 발행 작업은 포함하지 않았다. [측정 조건과 원본](../perf/2026-09-24-town-retention-memory.md)

**이 데이터 규모와 부하에서는 여러 버전의 보관·재적재가 요청 처리를 압박하는 현상이 관측되지 않았다.** 이전 버전을 빨리 버려 메모리를 아끼기보다 보관해 이어보기를 지원한다. 초기 로컬 설정은 TTL 65분·추정 용량 64MiB이며 정적 정렬 배열 공간도 가중치에 포함한다. 최신·과거 버전 모두 적재 시점부터 만료 시간을 적용하고 조회로 연장하지 않는다. TTL과 용량은 상한이며, 특정 사용자의 5분 보관이나 65분간 발생할 모든 변경량을 보장하는 수치는 아니다.

## 6. 네 번째 트레이드오프 — 즉시 병렬 처리 vs 동시 작업 제한으로 자원 보호

**같은 동네·버전의 적재와 같은 정렬 배열 생성은 공유하되, 서로 다른 작업에는 별도 실행 상한·대기열을 추가하지 않는다.** 짧은 작업을 줄 세우는 대기를 피하는 대신 동시에 필요한 CPU·임시 객체·DB 연결이 늘어날 수 있다.

앞의 서울 전체 약 83% 구간에서 p95 12.1ms·p99 40.9ms, 적재 235건 완료, 적재 실패·요청 예산 초과 0건을 확인했다. 이 규모에서 추가 제한이 필요하다는 근거는 관측하지 못했다. 제한을 둔 구조보다 빠르다고 비교한 결과는 아니다.

별도 대기열이 없어도 Tomcat 스레드·Hikari 연결 풀·CPU 경쟁에 의한 대기는 남는다. 요청 적재 예산 1초도 유지하며, 한 요청의 시간 초과나 취소가 다른 요청의 공유 적재를 취소하지 않는다. 목표 부하에서 적체·GC 부담·재시도가 반복되면 실행 제한을 검토한다.

## 7. 단계적 개선 — Redis로 과거 버전을 복구하고 반복 적재 비용을 줄인다

### 로컬 캐시만으로 해결되지 않는 경우

로컬에 버전이 남아 있으면 계속 읽고, 없어도 아직 DB 최신이면 재적재할 수 있다. 그러나 **로컬에 없는 과거 버전은 현재 DB 테이블로 재구성할 수 없다.** 배포·재시작으로 잃었거나, 여러 서버로 확장했을 때 요청받은 서버가 그 버전을 가진 적 없다면 처음부터 다시 조회해야 한다.

용량과 TTL을 늘리면 이미 적재한 버전의 제거 위험은 줄지만, 가진 적 없는 버전을 제공할 수는 없다. 스티키 세션은 후속 요청을 같은 서버로 보내 이 위험을 줄일 수 있으나 부하 편중을 감수해야 하고 서버 교체는 해결하지 못한다. 현재는 미적용 보완책이다.

운영 관측 없이 이러한 탐색 중단이 자주 발생한다고 단정하지 않았다. Redis 도입 근거는 분산 환경이라는 이유만이 아니라, **보관된 과거 버전을 복구할 범위를 넓히면서 로컬 미스의 DB 적재 비용도 줄일 수 있는지**였다.

### 측정: 같은 로컬 객체를 완성하는 데 필요한 비용 비교

제품 DB 로더와 Redis JSON 복원 양쪽에서 같은 동네·버전의 장소 객체와 인기순 배열이 완성되는 지점까지 비교했다. 준비 구간을 제외한 3블록이며 버전·전체 필드·정렬 결과의 동등성을 확인했다. API 앱은 2 CPU·2GiB, MySQL과 Redis는 별도 컨테이너였다.

| 적재 범위 | DB 앱 CPU/적재 | Redis 앱 CPU/적재 | 힙 할당 DB → Redis |
|---|---:|---:|---:|
| 1동네·101곳 | 0.467~0.614ms | 0.206~0.324ms | 455 → 144KiB |
| 서울 18동네·1,800곳 | 25.177~27.508ms | 9.330~9.942ms | 8,096 → 2,541KiB |

CPU는 통신 스레드까지 포함한 앱 전체 사용량의 블록별 범위다. 서울의 적재 지연 p50 중앙값은 9.21ms에서 3.13ms로 줄었다. **힙 할당은 약 69% 감소했다.** 이는 적재 중 임시 객체 생성 부담이 작아졌다는 근거이며, 캐시 보유 메모리나 서비스 전체 GC가 같은 비율로 줄었다는 뜻은 아니다.

발행 비용도 있다. 이미 확보한 서울 스냅샷을 직렬화해 Redis에 저장하는 데 앱 CPU 약 8~9ms가 들었으며, 원본 DB 조회는 이 값에 포함하지 않았다. JSON 전송량은 DB 응답보다 약 2배였다. 재사용되지 않는 버전은 발행 비용만 추가되므로 실제 이득은 재적재 빈도에 달린다. [측정 조건·결과·발행 비용](../perf/2026-09-24-redis-town-load.md)

**선택은 로컬 캐시를 유지한 채 Redis를 추가하는 것이다.** 일반 요청은 로컬 객체·정렬 배열을 계속 재사용한다. Redis는 로컬에 없는 버전의 공유 원본 역할을 맡아, 반복 적재 CPU·할당을 줄이고 배포·서버 이동 이후의 과거 버전 복구를 보완한다. 대신 공유 메모리·발행 작업·장애 대응·저장 형식 호환 관리가 추가된다.

### 조회와 발행 구조

```text
첫 페이지: DB 최신 버전 확인 / 다음 페이지: 커서 버전 유지
  → 로컬 조회
  → 없으면 Redis의 같은 동네·버전 조회
  → 없거나 접근 실패하면 여전히 최신인 버전만 DB로 복구
  → DB로 확보한 스냅샷은 Redis에 비동기 발행

관리자·배치 변경: 데이터와 버전을 함께 DB 커밋
  → 비동기로 버전·데이터를 같은 읽기 트랜잭션에서 확보
  → Redis에 발행
```

발행할 때는 읽어 온 번호와 데이터를 함께 전달한다. 비동기 작업이 데이터를 다시 읽어 다른 시점의 값을 원래 번호로 저장하지 않는다. 커밋 후 적재 전에 다음 변경이 커밋되면 실제로 읽은 새 번호를 사용하므로 모든 중간 버전의 보관을 보장하지는 않는다.

동일 서버의 적재·발행은 공유하고 서버 간 중복은 허용한다. 같은 Redis 키는 최초 저장을 유지하며 반복 발행으로 내용·TTL을 덮어쓰지 않는다. 발행 실패 시 최신 조회는 DB로 처리할 수 있고, 로컬 객체가 남아 있으면 그 객체로 공유 보관을 다시 시도한다. Redis 장애는 과거 버전의 부재가 확인된 것이 아니므로 곧바로 새로고침을 요구하지 않는다.

## 8. 최종 결과 — 요청마다 조회하던 장소 데이터를 버전별로 재사용한다

기존에는 페이지를 요청할 때마다 DB에서 장소 데이터를 읽고 객체로 변환했다. 현재는 **첫 페이지에서 목록의 버전을 선택하고, 이후 페이지는 그 버전의 데이터와 정렬 배열을 재사용**한다.

```text
기존: 매 페이지 요청 → DB에서 장소 조회·정렬·필터 → 객체 매핑 → 응답

현재: 첫 페이지는 DB 최신 버전 확인 / 다음 페이지는 커서 버전 유지
       → 해당 버전의 로컬 객체 확보
          └ 없으면 Redis에서 복원, 복구 가능한 최신 버전만 DB에서 적재
       → 재사용하는 정렬 배열에서 커서 다음부터 태그 검사
       → 다음 한 페이지를 찾아 응답
```

**달라진 비용:** 로컬에 데이터와 정렬 배열이 있으면 장소 행을 다시 조회·매핑하거나 같은 정렬을 반복하지 않는다. 대신 페이지에 필요한 필터 검사와 여러 동네의 정렬 결과 병합을 수행한다. 로컬에 없는 데이터도 Redis에서 복원하면 DB 적재보다 적은 CPU와 임시 객체 할당으로 확보할 수 있었다. 서울 18동네·1,800곳의 적재 비교에서 앱 CPU는 약 25~28ms에서 9~10ms로, 힙 할당은 약 7.9MiB에서 2.5MiB로 줄었다. 이는 적재 경로의 측정값이며 전체 API의 DB 전용 대비 CPU 개선율은 아니다.

**사용자에게 제공하는 보장:**

- 첫 페이지는 요청 처리 중 DB에서 확인한 최신 동네별 버전으로 시작한다.
- 이후 페이지는 같은 장소 집합·필터 값·정렬 기준을 유지한다. 새 버전이 생겨도 정상 응답 사이에 데이터 변경 때문에 장소가 중복되거나 누락되지 않는다.
- 로컬에서 사라진 과거 버전도 Redis에 남아 있으면 복원해 이어 본다. 배포·서버 이동으로 로컬 데이터가 없어졌다는 이유만으로 처음부터 조회할 필요는 줄어든다.
- 필요한 버전을 일시적으로 확보하지 못하면 같은 커서로 재시도한다. 과거 버전의 부재가 확인되어 복구할 수 없을 때만 첫 페이지부터 다시 조회하도록 안내하며, 다른 버전을 섞어 성공 응답하지 않는다.

이 구조는 **이전 버전과 정렬 배열의 메모리, 새 버전 생성·Redis 발행 비용을 부담하는 대신 반복 조회 비용을 줄이고 읽던 목록을 유지하는 선택**이다. 무기한 보관이나 모든 변경 버전의 발행을 보장하지는 않는다. 그 범위 안에서 최신 목록으로 시작하는 동작과 기존 목록을 안정적으로 이어 보는 동작을 분리했다.
