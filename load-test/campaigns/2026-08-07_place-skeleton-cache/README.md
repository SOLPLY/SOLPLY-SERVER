# 장소 골격 스냅샷 캐시 A/B — 사전 등록

> **이 문서는 첫 요청 이전에 작성됐다.** 결과를 보고 고치지 않는다.
> 이슈 [#383](https://github.com/SOLPLY/SOLPLY-SERVER/issues/383) · 브랜치 `perf/#383-place-skeleton-cache`

## 1. 문제

목표 부하 **300 arrivals/s(≈464 HTTP req/s)**에서 앱 CPU 스로틀이 **13.5%**이고,
knee가 바로 위 **360 arrivals**에 있다. 헤드룸이 1.2배뿐이다.

병목은 DB가 아니라 앱 CPU다 — 같은 계단에서 앱 스로틀 **66.0%** vs MySQL **1.0%**,
디스크 읽기·락 대기·tmp disk 전부 0, 버퍼풀 hit 100%
([계단 진단](../../../docs/perf/2026-08-06-app-saturation-diagnosis.md)).
앱 CPU 상한만 4 vCPU로 올린 대조 라운드에서 스로틀 18.2%→0.8%, p99 391.6→59.7ms로 떨어진 것이
같은 결론을 다른 방향에서 확인한다([최소 안정성 부록 D](../../../docs/perf/2026-08-06-minimal-stability-final.md)).

## 2. 원인 가설

요청당 앱 CPU **3.05ms**(부하 5.9배 구간에서 2.64~3.42ms로 거의 불변) 중 일부를
`findPlacesWithTagsByIds` + `place_images` 지연로딩과 그 **JPA 엔티티 하이드레이션**이 쓴다.

- 이 두 쿼리가 읽는 것은 **장소마다 변하지 않는 값**이다 — 이름·썸네일·대표 태그명·동네
- 하이드레이션은 행을 객체로 바꾸는 것에 그치지 않는다. 영속성 컨텍스트 등록, LAZY 프록시,
  컬렉션 래퍼가 함께 만들어진다. 페이지 10건이면 `Place` 10개 + `PlaceTag` 30개 안팎이
  매 요청 생성·폐기된다
- JFR에서 Hibernate inclusive **20.8~22.3%**, MySQL Connector/J **12.7~13.0%**
  ([JFR 프로파일](../../../docs/perf/2026-08-06-jfr-saturation-short.md))

**정렬 쿼리(`findPopularRows`/`findLatestRows`)는 원인이 아니다.** `createNativeQuery`로
`Object[]`를 받아 하이드레이션이 없고, 커버링 인덱스로 카운트·평점까지 함께 실어온다.

## 3. 기술적 선택

**장소 단위 `volatile Map` 스냅샷 캐시.** 장소당 불변 5필드(`id`·`name`·`imageUrl`·
`mainTagName`·`townId`)만 담고, 매시 카운트 배치 직후 통째로 교체한다.

기각한 대안과 근거:

| 대안 | 기각 사유 |
|---|---|
| 페이지(요청) 단위 캐시 | 키가 동네 19 × 태그조합 1,025 × 정렬 2 ≈ **39,000**으로 폭발하는데, 그렇게 더 아끼는 것은 **가장 싼 쿼리 하나**(native 커버링 정렬)뿐 |
| (동네+태그)→id 리스트 캐시 | 커버링 인덱스가 카운트·평점을 이미 실어오므로, id만 캐시하면 `place_stats`를 PK로 **다시** 읽어야 해서 **순 절감 0** |
| Caffeine 등 캐시 라이브러리 | 크기가 장소 수(6,320)로 고정, 만료 주체가 카운트 배치 하나, 미스 비용이 현행과 동일 → eviction·TTL·single-flight가 **전부 불필요**. `Map.copyOf` + 참조 교체가 원자적이고 락이 없다 |

## 4. 검증할 주장

> **요청당 앱 CPU가 줄어 목표 부하의 스로틀이 내려가고 knee가 360보다 위로 이동한다.**

부수 주장: 요청당 쿼리 수가 페이지당 2 감소한다. DB 지표는 무변이거나 개선된다
(**DB 부하를 줄이는 것이 목적이 아니다** — 가이드 §4의 "캐시 적용" 템플릿이 상정하는
*캐시 → DB 접근 감소 → DB 부하 감소* 사슬과 이 캠페인의 주장은 다르다. DB 지표는 판정이 아니라
**부작용 확인용**으로 쓴다).

## 5. 성공 조건

### 5.0 전제 — 판정 이전에 먼저 통과해야 한다

**정합성 게이트.** 캐시 on/off 두 모드의 **응답 body와 커서 토큰이 동일**해야 한다.
`PlaceSkeletonCacheIT.캐시를_켜고_끈_응답과_커서가_완전히_같다`가 두 정렬 × 두 페이지로
이미 덮지만, **벤치 데이터(장소 6,320 · 북마크 1,040만)에서 한 번 더 확인**한다.
diff가 비면 통과가 아니라 "아무것도 보지 않은 것"일 수 있으므로, 게이트 실행 전에
스냅샷 크기가 0이 아님을 로그로 확인한다.

### 5.1 지표 계약 — 무엇을 근거로 쓰는가

측정에서 나오는 숫자마다 **믿을 수 있는 정도가 다르다.** 사후에 고르면 유리한 것만 남으므로
미리 나눈다.

| 구분 | 지표 | 근거 |
|---|---|---|
| **1급 (판정)** | 목표 부하(S4-300)의 **앱 스로틀 비율**, **knee 위치** | 천장 근처의 비선형성이 신호를 증폭한다 — S4에서 앱이 2.0코어 중 **1.501코어(75%)**를 쓰므로, 요청당 CPU가 12% 줄면 66%가 되고 스로틀은 그보다 크게 떨어진다 |
| **보조 (원인)** | 요청당 앱 CPU ms, 요청당 statements | 가이드 A.3의 1급 기준선. statements는 세면 나오는 결정론적 값이라 **전환 확인**으로도 쓴다 |
| **참고 (인용 주의)** | p95, 정상 구간 p99 | 호스트 상태에 흔들린다 |
| **주장하지 않음** | p50·처리량 | 목표 부하에서 이미 p50 6ms다. 캐시를 켜도 사용자가 느낄 변화가 없다 |

**요청당 앱 CPU를 1급으로 올리지 않은 이유.** 예상 효과가 10~15%인데, 가이드 A.1은
"10~20% 개선은 로컬에서 주장하지 않는다"고 못 박는다. 이 지표의 **라운드 간 산포를 이 저장소가
잰 적이 없으므로**, 워밍업 라운드에서 산포를 먼저 재고 그 폭을 이 문서에 추가 기록한다.
산포보다 확실히 큰 차이일 때만 원인 근거로 인용한다. **결과를 보고 정하는 것이 아니라
노이즈 크기를 보고 정하는 것이며, 확정 시점은 워밍업 직후·본 라운드 시작 전이다.**

### 5.2 판정

| 판정 | 조건 |
|---|---|
| **채택** | 정합성 게이트 통과 **그리고** S4 스로틀이 눈에 띄게 감소 **그리고** knee가 360보다 위로 이동 |
| **기각** | knee가 그대로 S4→S5 |
| **보류** | 스로틀은 내렸는데 knee는 안 움직임 → 원인 지표로 재해석 후 사용자 결정 |

### 5.3 히트율 — 코드 추가 없이 잰다

`performance_schema` digest에서 `findPlacesWithTagsByIds` 문장의 `COUNT_STAR`가
**그대로 미스가 발생한 페이지 수**다. 0이면 히트율 100%. 카운터를 넣었다 빼는 것보다 정확하고,
가이드 §5의 "원인 판정은 digest 실행당 값으로" 규칙과도 맞는다.

## 6. 무효 조건 (라운드 유효성 — 결과를 읽기 전에 먼저 판정한다)

기존 캠페인 규칙을 그대로 재사용하고 하나를 더한다.

| 조건 | 판정 |
|---|---|
| 구간 평균 절대 코어가 배정 상한(2.0)을 초과 (**cgroup `cpu.stat` 기준**, docker stats 문면 금지) | 라운드 무효 |
| 낮은 계단(S1·S2)에서 도착률 결손 2% 초과 또는 p50 급등 | 라운드 무효 |
| 컨테이너 재시작·OOM | 라운드 무효 |
| 앱과 DB가 같은 샘플에서 동시 급등 (호스트 스톨 서명) | 라운드 무효 |
| **스냅샷 빌드가 라운드 창과 겹침** (카운트 배치 `cron 0 30 * * * *`) | 라운드 무효 |

**오염 구간만 잘라내지 않는다.** 라운드 전체를 폐기하고 재실행한다.

## 7. 형상과 전환

- 브랜치 `perf/#383-place-skeleton-cache`. 커밋 해시는 실행 시각에 기록한다
- **같은 빌드에서 설정 하나로 전환한다** — `solply.place-list.skeleton-cache-enabled`
  ```bash
  # off (기준선)
  BENCH_APP_JSON='{"solply.place-list.skeleton-cache-enabled":"false"}' \
    docker compose -f docker/docker-compose.bench.yml up -d --force-recreate bench-app
  ```
  ⚠️ `docker restart`로는 환경변수가 반영되지 않는다
- **전환 검증을 설정값이 아니라 실행된 SQL로 한다.** 매 전환마다
  `performance_schema.events_statements_summary_by_digest`를 비우고 요청 1건을 보내
  `findPlacesWithTagsByIds` 문장의 유무를 확인한다. 설정이 읽혔더라도 코드가 그것을
  쓰지 않을 수 있다
- 라운드: 모드당 **워밍업 1회(폐기) + 본 3회**, 라운드 사이 60초, 중앙값 판정
- 부하 진입점은 edge(`localhost:8082`) 고정. 앱 포트에 직접 쏘지 않는다

## 8. 이 측정으로 말할 수 없는 것

(결과 문서에 그대로 옮긴다)

- **단일 호스트에서 Artillery가 측정 대상과 자원을 공유한다.** 절대 처리량은 운영 용량이 아니다
- **응답시간 개선을 주장하지 않는다** (§5.1)
- **장시간 안정성을 말하지 않는다.** 계단당 30초다
- 기존 캠페인(앱 2대 + LB) 수치와 **절대값을 비교하지 않는다** — 단일 프로세스 재기준선이다
