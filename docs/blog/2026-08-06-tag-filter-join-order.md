## 기대한 실행 순서와 실제

인기점수는 배치가 `place_stats`에 미리 계산해 둔다. 인기순 조회는 다음 인덱스를 타도록 설계했다.

```text
(version, town_id, popular_score DESC, place_id, ...)
```

기대한 동작은 명확했다. 현재 버전과 요청 지역으로 범위를 좁히고, 인기점수 순서대로 읽다가 한
페이지에 필요한 11건을 찾으면 멈춘다. 조회에 필요한 값도 인덱스에 담았으므로 테이블 본문을 다시
읽지 않고 끝나기를 기대했다.

태그 필터가 붙어도 이 순서는 유지될 것이라고 봤다. 태그 조건은 인기순으로 읽어 내려가면서 장소마다
"이 태그가 붙었나"를 확인하는 일이고, 후보를 좁히는 조건이 하나 더 붙었을 뿐이다. **옵티마이저도
당연히 인기순 인덱스에서 시작하는 쪽이 싸다고 계산할 것이라고 생각했다.**

하지만 인덱스를 만들었다고 MySQL이 반드시 그렇게 쓰는 것은 아니다. 그래서 실제 API가 만드는 SQL에
`EXPLAIN ANALYZE`를 실행했다. 쿼리를 실제로 수행하면서 MySQL이 선택한 실행 순서와 각 단계의 실제
행 수, 반복 횟수, 소요 시간을 보여주는 명령이다. 부하를 재려는 것이 아니라 다음 세 가지를 확인하려는
목적이었다.

```text
단일 동네: 인기순 인덱스를 따라 읽고 별도 정렬 없이 11건에서 멈추는가?
여러 동네: 정렬이 필요하더라도 커버링 인덱스 안에서 처리되는가?
태그 필터: 태그 조건이 붙어도 place_stats에서 시작하는가?
```

앞의 둘은 예상대로였다. 단일 동네에서는 인덱스에서 11건만 읽고 멈췄고, 여러 동네도 테이블 본문을
조회하지 않은 채 인덱스 엔트리만 정렬했다.

**어긋난 것은 세 번째다.** 같은 인기순 조회인데 MySQL이 `place_stats`가 아닌 `place_tag`에서 조회를
시작했다. 그 결과 인기순으로 정렬된 인덱스도, 11건을 찾으면 멈추는 방식도 쓰지 못했다. 먼저 태그에
연결된 장소 후보를 모으고, 중복을 제거한 다음 인기점수로 다시 정렬하는 실행계획이 선택됐다.

기대와 실제가 갈린 자리는 여기다. 옵티마이저는 왜 더 비싼 쪽을 싸다고 계산했나.

## 태그 필터는 어떻게 생겼나

장소 목록은 메인·서브 태그 조건을 지원한다. 장소와 태그는 다대다 관계이므로 `place_tag`에서 해당
장소에 요청한 태그가 연결되어 있는지 `EXISTS`로 확인했다.

기존 쿼리는 연결된 태그가 활성 상태인지 확인하기 위해 `tags`까지 조인했다.

```sql
EXISTS (
    SELECT 1
    FROM place_tag pt
    JOIN tags t ON t.id = pt.tag_id
    WHERE pt.place_id = p.id
      AND t.id = :tagId
      AND t.active = 1
)
```

## 문제 상황

사용자가 태그를 하나 고르면, 조회는 인기순으로 읽어 내려가면서 장소마다 그 태그가 붙었는지
확인한다. 동네 하나(활성 장소 100곳)를 조회하면 57곳을 확인해 11건을 채우고 멈춘다. 0.076ms이고
정렬도 따로 필요 없다.

```text
place_stats에서 지역 장소를 인기순으로 조회
→ 장소별 태그 연결 여부 단건 확인
→ 11개를 찾으면 조기 종료
```

최신순도 `places`에서 지역 후보를 먼저 만든 뒤 태그를 확인하고 `created_at` 기준 결과를 구성했다.

태그를 세 개 고르면 같은 동네 조회가 `place_tag` 엔트리 10,536건을 읽는다. 100곳 중 10곳을 고르는
요청이다. 조건을 더 걸었으니 후보는 같거나 줄어야 하는데 읽는 양은 57건에서 185배로 늘었다. 조건이
늘어난 만큼 비용이 붙은 것이 아니라 조회하는 방식 자체가 달라진 것이다.

바뀐 방식은 이렇다.

```text
tags 조건 평가
→ place_tag에서 태그 연결을 대량 탐색
→ 장소 테이블을 PK로 반복 조회
→ 지역 조건으로 대부분 제거
→ 복수 태그로 발생한 중복 제거
→ 인기 점수 또는 생성 시각으로 정렬
→ 상위 11개 반환
```

지역으로 좁힌 다음 태그를 확인하던 순서가, 태그로 후보를 모은 다음 지역으로 걸러내는 순서로
뒤집혔다. 인기순은 랭킹 인덱스와 조기 종료를 함께 잃었고, 최신순도 지역 필터보다 태그 연결 탐색이
먼저 수행됐다. 시 단위(장소 1,800곳)에서는 10,536행을 뽑아 나머지 태그 조건을 확인해 2,874행으로
줄이고, 그 2,874건을 장소별로 조회해 지역 조건을 통과한 615건을 남긴 뒤, 복수 태그로 생긴 중복을
걷어내 211건을 정렬했다.

주목할 곳은 그 10,536이라는 숫자가 **동네 1곳과 시 18곳에서 똑같다**는 점이다. 조회 범위를 18배로
넓혀도 읽는 양이 그대로다. 사용자가 지역을 좁혀도 DB가 하는 일은 줄지 않는다. 비용이 사용자가 고른
지역이 아니라 그 태그가 전국에 몇 곳이나 붙어 있는지를 따라가고 있었다.

## 원인 분석

MySQL은 쿼리를 실행하기 전에 각 단계가 몇 행을 남길지 미리 계산한다. 조인 순서는 그 예상 행 수를
견줘서 정해진다. 작아 보이는 쪽에서 시작해야 뒤따르는 단계가 적게 돌기 때문이다. 그래서 "이 조건을
걸면 후보가 몇 분의 몇으로 줄어드는가"가 조인 순서를 결정하는 재료가 된다.

이 값은 인덱스가 있는 컬럼이라면 실제로 세어볼 수 있다. `pt.tag_id = 7`이면 인덱스를 들춰 "7번
태그에 붙은 엔트리가 1,146건"이라고 답할 수 있다. 반면 `t.active`처럼 인덱스도 별도 통계도 없는
컬럼은 셀 방법이 없다. 이때 MySQL은 데이터를 보지 않고 **고정 기본값 10%를 쓴다.** 실제 분포가
어떻든 "이 조건을 걸면 후보가 1/10로 줄어든다"고 가정하는 것이다.

당시 `tags`의 34개 행은 모두 활성이었다. `active = 1`의 실제 통과율은 100%인데 10%로 봤으니, 이
조건이 한 번 적용될 때마다 예상치가 실제의 1/10로 깎였다.

단일 태그는 PK로 조회한 태그 한 행이 상수로 처리돼 다른 태그 집합과 결합되지 않는다. 반면 복수
태그에서는 각각 4개와 6개인 후보 집합이 카테시안 곱으로 결합된다. 집합마다 10% 과소평가가 적용된 뒤
서로 곱해지면서 오차도 함께 곱해졌고, 최종 결과를 실제 24행이 아닌 0.024행으로 예상했다.

```text
지역 후보:      100개 또는 1,800개
태그 후보 예상: 0.024개
```

이 정보를 기준으로 보면 태그부터 시작하는 것이 압도적으로 저렴해 보인다. 옵티마이저가 비합리적으로
동작한 것이 아니라, 부정확한 예상치를 근거로 합리적인 선택을 한 것이다.

따라서 문제의 본질은 다대다 관계 자체가 아니라 다음과 같았다.

```text
분포를 셀 수 없는 active 조건
→ 통과율을 실제 100%가 아닌 10%로 고정 가정
→ 태그 후보 규모를 실제의 1/1,000로 예상
→ 태그부터 읽는 것이 압도적으로 싸다고 판단
→ 대량 연결 탐색, PK 반복 조회, 중복 제거 및 재정렬
```

조건 하나가 느리게 만든 것이 아니다. 그 조건이 **옵티마이저의 판단 재료를 흐려서** 실행 방식 자체를
바꿔 놓았다.

## 고칠 방법은 셋이었다

원인이 "옵티마이저가 셀 수 없는 조건"이라면 쿼리에서 손댈 자리는 셋뿐이다. 조건을 다른 문법으로
쓰거나, 실행계획을 강제하거나, 조건을 쿼리에서 빼거나. (셀 수 있게 통계를 만들어 주는 네 번째
방법도 있는데, 그건 코드 밖에 남는 일이라 맨 뒤에서 따로 다룬다.)

### 하나 — 쿼리를 다시 쓴다

조인이 말썽이니 서브쿼리로 바꾸면 되지 않을까. 가장 먼저 떠오르는 방법이고, 통하지 않는다.
`pt.tag_id IN (SELECT t.id FROM tags t WHERE ... AND t.active = 1)` 형태와 `tags`를 중첩 `EXISTS`로
확인하는 형태를 각각 만들어 실행계획을 떠 보면, 조인 형태까지 셋이 노드 단위로 같다. 태그 후보를
0.024개로 보는 추정도 그대로다. MySQL이 서브쿼리를 세미조인으로 평탄화해 결국 조인으로 되돌리기
때문이다. (캠페인 밖의 즉석 확인이다.)

돌아보면 당연하다. 문법을 바꿔도 옵티마이저가 답해야 할 질문은 "`t.active = 1`을 통과하는 행이 몇
개인가"로 똑같이 남는다. 그 질문에 답할 재료가 없다는 것이 원인이었으므로, 쓰는 방식을 바꾸는
것으로는 원인에 닿지 않는다.

### 둘 — 실행계획을 강제한다

그렇다면 계획을 직접 못 박는 방법이 남는다. `place_stats` 또는 `places`를 항상 주도 테이블로
고정하는 방안을 검토했다. 그러나 최적의 시작점은 태그 분포에 따라 달랐다.

```text
흔한 태그
→ 태그 연결 장소가 많음
→ 지역 장소부터 읽고 조기에 종료하는 것이 유리

희귀 태그
→ 태그 연결 장소가 적음
→ place_tag부터 읽는 것이 유리

결과가 없는 태그
→ place_tag부터 읽으면 즉시 종료 가능
```

실제로 장소 주도로 고정했을 때 흔한 태그는 4.2배 빨라졌지만, 희귀 태그(연결 장소 185개)는 약 2배,
결과가 없는 태그는 약 75배 느려졌다. 결과가 없는 태그는 `place_tag`부터 읽으면 0건을 확인하고 즉시
끝나는데, 힌트를 박으면 1,800건을 정렬해 놓고 하나씩 확인하다 아무것도 건지지 못한다.

즉 조인 순서 힌트는 특정 입력만 개선하고, 옵티마이저가 데이터 분포에 따라 계획을 바꿀 가능성을
제거한다. 어떤 태그 조합이 얼마나 들어올지 모르는 상태에서 계획 하나를 못 박는 셈이라 택하지 않았다.

### 셋 — 질문을 분리한다 (택한 것)

남은 방법은 조건을 쿼리에서 빼는 것이다. 뺄 수 있는지 따져 보다가, 이 조건이 애초에 목록 쿼리가
답할 질문이 아니었다는 데까지 갔다. 한 쿼리 안에 성격이 다른 두 질문이 들어 있었다.

```text
"이 장소에 이 태그가 붙었나"   → 장소마다 답이 다르다. 목록 쿼리가 답할 질문이다.
"이 태그가 유효한가"           → 요청 하나당 한 번이면 되고, 어느 장소를 보든 답이 같다.
```

뒤의 질문은 `tags` 34행만 보면 끝나고, 조회 결과와 아무 상관이 없다. 그리고 이미 다른 곳에서 답하고
있었다 — `TagValidator`가 저장소를 호출하기 전에 태그 id의 존재·활성·타입을 확인하고, 비활성 태그
id는 `NOT_FOUND_TAG`로 막는다. 그래서 목록 쿼리에서 떼어내는 데 드는 추가 비용이 0이었다.

떼어내야 하는 이유는 성능만이 아니었다. **잘못된 태그 id의 올바른 답은 빈 목록이 아니라 404다.**
SQL 조건으로 두면 사용자는 결과가 왜 비었는지 알 수 없다. 반대로 목록 쿼리 쪽에는 이득이 있다.
남는 조건이 전부 인덱스로 실제 건수를 셀 수 있는 것이 되어, 옵티마이저가 추측할 자리가 사라진다.

다대다 연결을 확인하는 `place_tag`는 유지하되, `tags` 조인만 제거했다. `place_tag.tag_id`는
`tags.id`를 참조하는 외래키이므로 연결된 태그의 존재는 이미 보장되고, `pt.tag_id`가 곧 태그
id이므로 `t.id = :tagId`는 `pt.tag_id = :tagId`와 같은 조건이다. 조인이 보태던 정보는 `active`
하나뿐이었다.

```sql
EXISTS (
    SELECT 1
    FROM place_tag pt
    WHERE pt.place_id = p.id
      AND pt.tag_id = :tagId
)
```

이를 통해 다음 효과를 얻었다.

```text
tags 조인 제거
→ 남은 조건은 pt.tag_id = :tagId 하나, 인덱스로 실제 건수를 셀 수 있다
→ 태그 후보를 0.024개가 아니라 1,146개로 예상
→ 지역 후보와 크기를 제대로 견줘 조인 순서 선택
```

## 결과

전후를 같은 DB·같은 파라미터로 채취했다. 값은 `EXPLAIN ANALYZE` 최상위 노드 시간의 3회 중앙값이다.
최신순 정렬 인덱스까지 정리한 현재 스키마 기준이다.

측정한 요청은 이렇다. 조회 범위는 **동네 1곳**(장소 100개)과 **그 시의 동네 18곳**(장소 1,800개)이고,
태그는 실제 서비스 태그를 그대로 썼다.

| 태그 조합 | 사용자가 고른 것 | 그 태그가 붙은 장소(전국) |
|---|---|---|
| `카페` | 메인 태그 하나 | 1,146곳 |
| `카페` + 옵션 2종 | `카페` + `커피/디저트·작업·독서·힐링` 중 하나 + `시그니처메뉴·감성인테리어·채광좋음·콘센트많음·시간제한없음·바테이블` 중 하나 | 옵션1 각 424~455곳 · 옵션2 각 287~312곳 |
| `음식` + `바/술집` | 희귀한 서브 태그가 붙은 조합 | `바/술집` **185곳** |
| `맛집 · 디저트` | 활성 태그지만 붙은 장소가 없다 | **0곳** |

서브 태그는 타입 내 OR, 타입 간 AND다. 두 번째 줄이 화면에서 칩을 여러 개 눌렀을 때 나가는 가장
무거운 요청이다. 모든 요청은 `LIMIT 11`(첫 페이지 10건 + 다음 페이지 판정용 1건)로 나간다.

| 정렬 | 조회 범위 | 태그 조합 | 후보 → 통과 | before | after | |
|---|---|---|---:|---:|---:|---|
| 인기순 | 동네 1곳 | `카페` + 옵션 2종 | 100 → 10 | 11.30ms | **0.17ms** | **66.5배** |
| 최신순 | 동네 1곳 | `카페` + 옵션 2종 | 100 → 10 | 12.40ms | **0.18ms** | **67.4배** |
| 인기순 | 동네 18곳 | `카페` + 옵션 2종 | 1,800 → 211 | 22.30ms | **4.34ms** | **5.1배** |
| 최신순 | 동네 18곳 | `카페` + 옵션 2종 | 1,800 → 211 | 20.90ms | **2.77ms** | **7.5배** |

| 인기순 | 동네 18곳 | `맛집 · 디저트` | 1,800 → 0 | 0.011ms | 0.016ms | 계획 동일 |

"후보 → 통과"는 조회 범위의 활성 장소 수와 태그 조건을 통과한 장소 수다. 응답은 그중 앞의 10건이다.
100개 중 10개를 고르는 요청이 11~12ms였다는 뜻이고, 그 10개를 찾으려고 `place_tag` 엔트리를
10,536건 훑고 있었다.

**태그가 하나뿐인 조회는 거의 바뀌지 않았다.** 단일 태그에서는 10% 과소평가가 한 번만 적용되므로
태그 후보 추정이 1,146개에서 100여 개 수준으로 줄어들 뿐, 지역 후보 100개보다 작아지지 않는다.
그래서 실행계획이 원래부터 지역 주도였고, 실제로 변경 전후의 실행계획이 노드 단위로 동일하다.
개선은 태그를 여러 개 걸어 오차가 곱해질 때만 나타나며, 이는 원인 분석과 일치한다.

동네 단위 복수 태그 조회에서는 주도 테이블이 지역으로 돌아왔다. 여러 동네를 묶어 조회할 때는 지역
후보 1,800개가 태그 후보 1,146개보다 많으므로 **여전히 태그 주도가 선택된다.** 그런데도 5~7.5배
좋아졌다. 주도 테이블이 같은데 무엇이 달라졌나 — 태그 쪽에서 하는 일의 모양이 바뀌었다.

인기순을 예로 들면 이렇다. before는 태그 두 축을 곱한 조합 24가지를 각각 인덱스로 찍어 10,536행을
뽑아 놓고, **그 10,536행 전부에** 나머지 조건을 하나씩 되물었다. 트리에 찍힌 단건 조회 횟수가 약
24,000번이다. after는 인덱스를 한 번 훑어 후보를 1,145곳으로 접은 다음 거기에만 물으므로 1,631번으로
내려간다. 판단이 바뀌어서가 아니라 **되묻는 횟수가 열몇 분의 일이 되어** 빨라진 것이다.

이 선택은 정확한 추정치에 근거한 것이므로 되돌릴 이유가 없다.

**희귀 태그와 결과가 없는 태그에서는 실행계획이 노드 단위로 동일했다.** 두 조합의 시간 차이는
10~20µs 수준으로 측정 노이즈다. 오추정이 판단을 좌우하지 않던 입력에서는 아무것도 바뀌지 않는다는
뜻이고, 이것이 힌트를 사용하는 방식과 갈리는 지점이다.

결과 집합이 바뀌지 않는다는 것은 `PlaceListDbQueryRepositoryIT`와 `PlaceListFlowIT`의 32개 테스트로
확인했다.

## 이 수치로 말할 수 없는 것

- 부하 0에서 단일 쿼리를 잰 값이다. 요청 하나는 이 쿼리 외에도 SQL을 여러 개 사용하므로, 66배는
  전체 응답시간의 배수가 아니라 이 쿼리의 배수다.
- 실제 트래픽에서 태그 필터 조회의 비중을 아직 모른다. 어떤 조합이 얼마나 들어오는지 모르는 상태에서
  잰 값이다.
- 검증 데이터의 `tags` 34개 행이 모두 활성이라 `filtered 10.00`의 오차가 최대인 조건이었다. 비활성
  태그가 섞인 환경에서는 격차가 이보다 작을 수 있다.

## 남는 것

미뤄 둔 네 번째 방법이 이것이다. `ANALYZE TABLE tags UPDATE HISTOGRAM ON active`로 통계를 만들어
주면, 셀 수 없던 조건이 셀 수 있게 되면서 같은 결과에 도달한다. 코드를 바꾸지 않아도 되지만 택하지
않았다. MySQL 히스토그램은 자동 갱신되지 않고 `mysqldump`에도 실리지
않아서, 환경을 새로 구성하거나 백업을 복원할 때 누락되면 아무 오류 없이 원래 성능으로 되돌아간다.
조인 제거는 성능이 코드에 담기므로 배포 환경과 무관하게 동일하게 동작한다.

이 개선의 핵심은 빠른 조인 순서 하나를 못 박은 것이 아니다. 옵티마이저가 추측에 기대게 만들던 조건을
걷어내 판단 재료를 정확하게 만들고, 데이터 분포에 따라 계획을 바꿀 여지는 그대로 남겨 둔 것이다.

처음에 어긋난 지점도 결국 같은 자리였다. 인덱스를 만들어 두었으니 옵티마이저가 당연히 그것을 고를
것이라고 봤는데, 옵티마이저는 인덱스를 보고 고르는 것이 아니라 자기가 가진 숫자를 보고 고른다.
쿼리가 옳게 쓰였다는 것과 옳게 실행된다는 것은 다른 이야기였다.
