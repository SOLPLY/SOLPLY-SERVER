# 2026-09-09 · 어드민 수정을 재빌드 없이 반영 — 표시값 분리와 전량 재빌드 유지의 기록

> **지위: #400의 확정 설계이자 판단 기록이다.**
> 시작은 "어드민이 장소 하나를 고칠 때 스냅샷 전체를 다시 짓는 것은 확장성이 나쁘다"였고,
> 장소 단위 패치 설계까지 갔다가 외부 리뷰 2건과 그릴링을 거쳐 되돌아왔다. 결과물보다
> **왜 되돌아왔는지**가 이 문서의 본체다. 구현이 이 문서와 달라지면 문서를 먼저 고친다.
> 측정 수치는 구현 뒤 캠페인에서 채운다(§9). 빈칸은 빈칸으로 둔다.

## 1. 어디서 시작했나

목록 스냅샷(#397)은 어드민이 장소를 만들거나 고치거나 지우면 커밋 직후 전량을 다시 짓는다.
6,320개를 DB에서 다시 읽고, 동네별로 나누고, 정렬 5종을 다시 만든다. 이름 하나를 고쳐도 같다.

문제로 본 것은 지금의 비용이 아니라 **기울기**였다. 어드민 한 번의 비용이 장소 수 N에
비례하면, N이 자라는 만큼 어드민 작업이 서비스 자원을 먹는다. 사용자 요청은 N과 무관하게
값싸게 만들어 놓고 어드민 쪽만 N에 매달려 있는 모양이 걸렸다. 그래서 "장소 하나만 고치면
비용이 N과 무관해지지 않나"에서 논의가 시작됐다.

## 2. 처음 설계 — 장소 단위 패치

배열이 참조 배열이고 원소가 불변 record라, 장소 하나를 고치는 방법은 셋이었다.

- **끼우기·빼기·동네 이동**: 그 동네의 정렬 배열 5개를 하나 더하거나 뺀 새 배열로 만들어 교체.
- **갈아끼우기**: 정렬 키가 안 바뀐 수정은 자리가 같으니 새 원소를 만들어 칸의 참조만 교체.
- **전량 재빌드**: 배치 타이머(10분)만.

여기에 다중 인스턴스 대비로 DB 버전 발급 테이블, 태그 63개 한계 대비로 비트 자리 회수까지
한 이슈에 넣으려 했다. 이 시점에 외부 리뷰를 받았다.

되돌아온 지점은 마지막에서 두 번째 행이다. "N에 비례하면 안 된다"는 좋은 목표처럼 들리지만
요구사항은 아니었다. 아끼는 양은 (재빌드 비용 × 어드민 빈도)이고, 어드민 수정이 하루
수십 회면 그 양은 하루 몇 초의 코어 시간이다. 그것을 위해 정합성 모델을 다시 정의하고
패치·재빌드 겹침·부분 실패 복구를 관리하는 것은 좋은 거래가 아니었다.

## 4. 확정 설계

### 4-1. 계약

> 커서는 정렬 순서의 일관성을 보장한다. 표시값과 소속(생성·삭제)은 최신 값일 수 있다.

스크롤 중에 보이는 것: 이름이 바뀔 수 있고, 새 장소가 나타날 수 있고, 지워진 장소가
사라질 수 있다. 보이지 않는 것: 같은 장소가 두 번 나오거나, 봤던 장소가 밀려 다시 나오는
일. 커서가 값 기반(정렬 키 튜플 + placeId)이라 배열에 장소가 더해지거나 빠져도 "이 값
다음부터"는 흔들리지 않는다.

### 4-2. 구조

```
사진(PlaceListPhoto, 버전 있음, 최근 3장 보존)
  └ 동네 × 정렬 5종 → PlaceListEntry[]  (불변. 정렬 키·좌표·태그비트만.
                                        장소 객체는 하나, 배열 다섯이 참조를 공유)
     ← 열별 원시 배열로 바꿨다가 되돌린 기록은 §11

사진 밖 (버전 없음, 한 벌)
  PlaceViewHolder  placeId → (이름, 썸네일 URL, 메인 태그 id)
  TagViewHolder    tagId   → (이름, 활성)

응답 = Entry + PlaceViewHolder.get(placeId) + TagViewHolder.get(mainTagId)
```

표시 맵이 사진 밖에 한 벌인 이유: 사진마다 두면 어드민 수정 때 보존 사진 3장의 맵을 모두
고쳐야 한다. 한 벌이면 put 한 번이고, 약한 계약이라 옛 사진이 최신 이름을 보여 줘도 된다.

좌표와 태그비트가 배열에 남는 이유: 순차 스캔이 원소마다 태그비트를 읽어 거르고, 거리순은
후보 전량의 좌표를 읽는다. 맵으로 빼면 스캔하는 원소마다 맵 조회가 붙는다. 이름·썸네일은
페이지에 실리는 10건에만 필요하다.

### 4-3. 어드민 수정별 처리

| 바뀐 것 | 처리 | 이유 |
|---|---|---|
| 이름·썸네일 | 그 장소만 다시 읽어 표시 맵 put | 정렬·필터에 안 닿음 |
| 태그 이름·의미·활성(캐스케이드 포함) | 태그 맵을 통째로 다시 읽어 교체 | 태그는 수십 행이라 어느 것이 바뀌었는지 모을 필요가 없다. 태그 활성은 표시에만 쓰인다(비트마스크·필터에 활성 조건 없음) |
| 태그 타입 | 수정 불가로 막음 | 타입이 바뀌면 그 태그를 대표로 쓰던 장소가 전부 낡는다. 필요 없는 기능이라 막는 게 재빌드 분기보다 낫다 |
| 생성·삭제·동네 재활성화 | 전량 재빌드 (지금과 같음) | 소속이 바뀜 |
| 동네 이동·좌표·장소의 태그 집합 | 전량 재빌드 | 배열 원소가 바뀜 |
| 정렬 키(점수·카운트) | 타이머 전량 재빌드 (지금과 같음) | 배치가 채움 |

수정 API 하나가 이름부터 태그까지 받으므로, 서비스가 저장 전후의 동네·좌표·태그 id 집합을
비교해 하나라도 달라졌으면 재빌드, 모두 같으면 표시 put으로 가른다. API를 둘로 쪼개는 것은
프론트 변경이 따라와서 하지 않았다.

표시 경로는 place_stats의 파생 컬럼 upsert도 건너뛴다(바뀐 게 없으니). 그 결과 예전에는 어떤
수정이든 파생 컬럼을 원본에서 다시 써서 다른 경로로 어긋난 행이 우연히 고쳐지는 효과가
있었는데 그게 사라졌다. 파생 컬럼의 정본은 여전히 기동·복구의 전량 재작성이라 계약상 문제는
없지만, 우연한 자가 치유를 기대하던 곳이 있다면 이제 없다.

태그를 비활성화하면 자식 태그도 함께 내려간다(캐스케이드). 처음 배선은 진입 태그만 맵에
반영해 자식이 10분간 낡았다. 리뷰로 잡은 뒤 자식마다 put을 걸었고, 마지막에는 "태그 쓰기가
있었으면 태그 맵을 통째로 다시 읽는다"로 바꿔 세는 일 자체를 없앴다. 비활성 태그는 목록에서
이름만 숨고 비트마스크와 필터에는 영향이 없다. 이 브랜치 이전부터 그랬다.

### 4-4. 락 하나 — 유실을 막는다

타이머 재빌드가 DB를 읽은 뒤 어드민이 이름을 고치고 put 하면, 그 뒤 재빌드가 옛 이름의 맵으로
갈아끼운다. 다음 재빌드(10분 안)까지 수정이 사라진다. 사진 교체에도 오늘 같은 성질의 창이
있다(재빌드 둘이 겹치면 늦게 끝난 쪽이 큰 버전을 달고 낡은 데이터를 채택할 수 있다).

```
재빌드:  락 → [읽기 트랜잭션: SELECT 3문장] → 사진 만들기 → 버전 발급 → 맵 교체 → 사진 채택 → 락 해제
put:     락 → 그 장소(태그)를 DB에서 다시 읽기 → 맵에 넣기 → 락 해제
조회:    락 없음
```

put은 진행 중인 재빌드가 교체를 끝낸 뒤에 들어가고, 재빌드 둘은 겹치지 않는다. 비용은
어드민 훅이 재빌드 하나(현재 0.1~0.3초)만큼 기다리는 것뿐이고 커밋 뒤라 사용자 조회에는
영향이 없다.

순서에서 두 가지가 중요하다. **락이 트랜잭션보다 앞이다.** 반대로 하면 락을 기다리는 동안
DB 커넥션을 쥐고 있어서 어드민 둘이 겹치면 발급 커넥션이 굶는다(리뷰 지적, §3-1). **put도
값을 들고 오지 않고 락 안에서 다시 읽는다.** 커밋 전에 만든 값을 들고 오면 늦게 깨어난
옛 콜백이 최신 값을 덮을 수 있다. 락은 put을 줄 세울 뿐 커밋 순서를 모른다. 번호로 새 것을 가리는 방식(재빌드 읽기 시작 번호 < put 번호면 안 덮기)은
기다림이 없지만 설명할 게 많고 지금 빈도에서 얻는 게 없어 하지 않았다.

### 4-5. 버전 발급 테이블

빌드가 끝나면 테이블에 한 줄 insert 해서 받은 번호가 사진 버전이다. 밀리초 시각은 더 쓰지 않는다.

지금은 빌더가 하나라 필요 없다. 미리 까는 이유는 09-01 설계에서 빌더가 둘 이상이 되기
때문이다(어드민 요청을 받은 인스턴스 + 타이머 리더). 그때 시계가 느린 인스턴스가 더 새
데이터로 지은 사진이 작은 번호를 달고 "낡은 버전"으로 거절되는 일을 막는다. Redis INCR도
되지만 Redis가 비워지면 번호가 1부터 다시 시작해 같은 거절이 난다.

### 4-6. 옛 사진에서 삭제된 장소를 만나면

표시 맵에 없으니 그 행을 건너뛴다. 계약상 정상이다(소속은 최신일 수 있다). 페이지가 한 건
짧아질 수 있는데, 옛 커서로 스크롤 중 그 장소가 삭제된 경우뿐이라 드물다. 다음 커서는
건너뛴 행을 포함해 소비한 마지막 원소 기준으로 만든다.

## 5. 왜 전량 재빌드를 유지하나 — 내준 것과 얻은 것

**선택.** 소속·정렬·필터에 닿는 어드민 수정은 장소 하나라도 스냅샷 전체를 다시 만든다.

**내준 것 하나.** 어드민 한 번의 비용이 장소 수에 비례한다. 장소 하나를 고치려고 전부를
다시 읽고 다시 정렬한다.

| 규모 | 장소 수 | 재빌드 소요 | 출처 |
|---|---|---|---|
| 현재 | 6,320 | 94~302ms | 08-07 캠페인(콜드/웜) |
| 현재 (이번 형상) | 6,320 | __ | §9 측정 |
| 10배 | 63,200 | __ | §9 측정 |
| 100배 | 632,000 | __ | §9 측정 |

**얻은 것 셋.**

1. **정합성 규칙이 하나다.** "DB대로 다시 만든다." 생성인지 삭제인지 동네 이동인지 구분할
   필요가 없고, 중간에 실패해도 다음 회차가 고친다.
2. **배열이 끝까지 불변이다.** 요청이 잡은 배열은 어떤 경우에도 바뀌지 않는다. 커서의 순서
   보장이 코드 한 줄이 아니라 구조에서 나온다.
3. **패치 경로가 없다.** 장소의 자리 찾기, 동네 두 개를 고치는 순서, 재빌드와 패치가 겹칠 때,
   부분 실패 복구. 이 코드와 테스트가 통째로 없다.

**패치를 택하지 않은 이유.** 패치가 아끼는 것은 "전량 읽기와 전 배열 정렬"이고, 배열에
하나를 끼우는 것 자체는 여전히 동네 크기에 비례한다. 아끼는 양은 (재빌드 비용 × 어드민
빈도)인데, 어드민 수정이 하루 수십 회면 하루 몇 초의 코어 시간이다. 복잡도를 사서 얻을 게 없다.

## 6. 요구와 선택의 기록

| 요구 | 선택 | 안 한 것 |
|---|---|---|
| 요청마다 정렬하지 않는다 | 동네별 사전 정렬 배열 5종 | 요청 시 정렬 (1세대, 실측 패배) |
| 스크롤 중 순서가 바뀌지 않는다 | 사진 버전 + 최근 3장 보존, 배열 불변 | 배열 제자리 수정 |
| 어드민 표시 수정이 즉시 보인다 | 표시 맵·태그 맵을 사진 밖에 두고 put | 표시값을 배열 원소에 |
| 어드민 한 번에 전량 재빌드를 안 한다 | 표시값만 분리. 소속 변경은 전량 유지 | 배열 단위 패치 |
| 재빌드와 put이 겹쳐도 유실이 없다 | 둘을 한 락으로 줄 세움 | 번호로 새 것 가리기 |
| 다중 인스턴스에서 버전이 안 겹친다 | DB 발급 테이블(버전 발급소) | 밀리초 시각, Redis INCR |
| 태그가 63개를 넘는다 | 이번엔 안 함 | bit_index 회수 |

## 7. 하지 않은 것과 그 이유

- **배열 단위 패치.** §3, §5.
- **비트 자리 회수.** 옛 사진의 마스크는 옛 매핑으로 읽어야 하는데 태그 맵은 한 벌이다.
  매핑을 사진에 묶거나, 보존 사진이 다 사라질 때까지 자리를 안 쓰는 정책이 필요하다. 태그가
  34개인 지금 필요가 없다. 필요해지면 정답은 "long으로 바꾸기"가 아니라 컬럼 추가나 검색
  엔진 이관이다.
- **사진마다 표시 맵.** §4-2.
- **수정 API 분리.** §4-3.
- **번호로 새 것 가리기.** §4-4.

## 8. 이 선택이 바뀌는 시점

- 재빌드 소요가 __초(§9 측정으로 정함)를 넘을 때. 어드민 훅이 락으로 그만큼 기다리고,
  한 코어가 그 시간 동안 재빌드에 쓰인다.
- 어드민 수정이 분 단위로 잦아질 때. 아끼는 양이 (비용 × 빈도)라 빈도가 먼저 움직인다.
- 그때 꺼낼 설계는 §2의 패치다. 표시 맵은 이미 분리돼 있으니 남는 것은 배열 끼우기·빼기와
  갈아끼우기뿐이고, 계약(§4-1)은 그대로 쓸 수 있다.

## 9. 측정 — 게이트 확정 (2026-09-09, 구현 뒤 실행)

1. **문제.** 전량 재빌드 비용이 규모에 비례하는데 어디서 문제가 되는지 모른다.
2. **가설.** 비용은 DB 읽기(행 수) + 객체 생성 + 동네별 정렬 5종(N log N)이라 규모에 거의
   선형. 현재 94~302ms → 10배 1~3초 → 100배 10~30초 자릿수. 서비스 영향은 2 vCPU 중 한
   코어를 그 시간 쓰는 것과 사진 두 벌이 겹치는 힙(현재 사진 약 1.75MiB).
3. **선택.** 소속 변경은 전량 재빌드 유지, 표시값만 분리.
4. **주장.** 현재·10배에서 재빌드는 어드민 응답 지연으로만 나타나고 서비스 지표·GC·힙에
   흔적이 없다. 100배는 깨지는 지점 기록용(성공 조건 없음).
5. **성공 조건(10배).** 재빌드 5회 중앙값 2초 이하 / 발화 버킷 p50이 이웃의 2배 이하·에러 0 /
   힙 바닥 상승 사진 크기 2배 이하·Old GC 대조와 같은 수준 / 앱 cgroup 스로틀 대조와 같은 수준.

판정은 원인·자원 지표(재빌드 소요, 스레드 할당, GC 정지, 힙 바닥, 스로틀)로 하고 응답시간은
"2배 안 넘음"의 안전판이다. 규모 점은 현재·10배·100배. 08-20 캠페인에서 성장 상한을 동네당
300곳(3배)으로 정했으므로 3배는 제품 판단, 10배는 설계 여유다. 발화는 count-cron이 아니라
어드민 장소 수정 API로 걸어 스냅샷 재빌드만 격리한다. 어드민 빈도는 측정할 수 없어 "하루
수십 회"를 가정으로 적는다.

09-01 파이프라인은 사진만 나른다. 이제 사진 밖에 홀더 두 벌이 생겼으므로 그때는 둘 중

발행"과 같은 결이다. 착수하는 날 정한다.

## 11. 정렬 배열을 객체 배열에서 원시 배열로 — 시도했다가 되돌린 기록 (같은 이슈 #400, 2026-09-09)

> **결말부터.** 아래 §11-1~11-5의 결정대로 구현해 게이트를 전부 통과했고(커밋 584c0df~a0e6994),
> 같은 날 객체 배열로 되돌렸다(0342fbc). 남긴 것은 평점을 `int` 하나로 둔 것뿐이다. 되돌린
> 이유는 §11-6. 이 절의 나머지는 그때의 결정 그대로 두어, 다시 검토할 때 처음부터 설계하지
> 않게 한다.

사용자 결정(2026-09-09). 측정 없이 착수하는 이유는 성능 주장이 아니라 **구조 선택**이기 때문이다.
사진이 불변이라 정확성에는 영향이 없고, 얻는 것은 "장소당 객체 1개 → 0개"(GC 마킹 대상 소멸)와
스캔·거리순이 연속 배열을 읽는 것이다. 지금 규모에서 빠르다고 주장하지 않는다. 100배 측정(§9)은
이 형상으로 한 번만 한다.

### 11-1. 모양 — 정렬마다 순서 배열 하나, 값은 장소 표 한 벌

```
PlaceListIndex
  장소 표 (전체 장소, 열별 원시 배열, 행 번호 = slot)
    long[]   placeId, townId, tagMask, createdAtEpochSecond
    int[]    reviewCount, bookmarkCount, ratingToInt
    double[] popularScore, latitude, longitude   (좌표 없음은 NaN 같은 표지값 — 0.0 금지, §Entry javadoc)
  orders: EnumMap<정렬 종류, HashMap<동네 id, int[] order>>
    order[i] = 그 동네·그 정렬에서 i번째 장소의 slot

seek:  key[order[mid]], placeId[order[mid]]    연속 배열에 한 번 접근
scan:  tagMask[order[i]]
응답:  slot으로 장소 표에서 10건의 나머지 값
```

정렬마다 키·id·마스크를 복사하는 모양(점프 0)은 100배에서 사진당 약 140MB라 기각. 이 모양은 약 60MB.

### 11-2. 열 타입 — 범위가 확실한 열만 int

| 열 | 타입 | 이유 |
|---|---|---|
| reviewCount, bookmarkCount, ratingToInt | int | 21억을 넘을 일이 없다 |
| placeId, townId | long | DB 컬럼이 BIGINT. 좁히면 컬럼과 어긋나는 날 조용히 틀린다 |
| tagMask | long | 63비트 |
| createdAtEpochSecond | long | 2038년에 int를 넘는다 |
| popularScore, latitude, longitude | double | |
| order | int | 장소 표 행 번호 |

### 11-3. 평점 — BigDecimal을 버리고 int 하나

`avg_rating`은 `DECIMAL(3,2)`라 소수점 자리가 2로 고정이다. BigDecimal이 내부에 드는 것(정수 450 +
자리 2) 중 자리는 상수이므로 **정수 450만** `ratingToInt`에 든다. 비교는 정수끼리. 커서는 지금처럼
double을 싣되 안에서 `Math.round(v × 100)`으로 정수로 바꿔 비교한다(원값이 백분의 일 단위라 오차
없음). 응답에 실을 때만 `BigDecimal.valueOf(ratingToInt, 2)`로 `4.50`을 만든다 — 등가 IT의 바이트
동일이 이걸로 유지된다. 정렬용 double 열(`avgRatingValue`)은 없앤다.

### 11-4. 열 분리(필드마다 배열)를 택한 이유

한 배열에 장소당 N칸씩 몰아넣는 모양과 비교했다. 무거운 경로(스캔·거리순 후보 수집)가 "많은 행 ×
적은 필드"라 열 분리가 캐시 라인을 덜 낭비하고, 응답 조립(한 행 × 전 필드)은 페이지당 10행이라
비용이 안 된다. 다만 동네당 100~300개 규모에서는 어느 배치든 캐시에 다 들어가 차이가 측정에
안 잡힌다. 그래서 기준은 성능이 아니라 단순성이고, `mask[i]`가 `packed[i*12+2]`보다 읽기 쉽다.

### 11-5. 바뀌는 곳과 지켜야 할 것

- **로더**: 세 문장 결과를 장소 표 열에 채우고, 동네·정렬마다 `int[] order`를 정렬한다. 자바 표준에
  "인덱스 배열을 비교자로 정렬"이 없어 박싱(`Integer[]`)하거나 정렬을 직접 짠다. 재빌드 비용은
  §9 측정에 그대로 잡힌다.
- **PlaceListIndex**: seek·scan·병합 Leg·거리순 후보가 `order`와 열을 읽는다. 커서 비교는 축별로
  열 타입이 다르다(인기순 double, 최신순 long, 평점 int, 카운트 int).
- **PlaceService**: `PlaceListEntry` 대신 slot으로 열을 읽어 응답·커서를 만든다. `PlaceListEntry`
  record는 사라지거나 로더 내부 조립용으로만 남는다.
- **`DistanceSort.topK`**: 후보를 Entry 리스트가 아니라 slot 배열(또는 lat/lng 열 + slot)로 받는다.
- **지켜야 할 게이트**: `PlaceListSnapshotEquivalenceIT`(메모리 경로 = DB 경로 응답 바이트 동일),
  `PlaceListViewPatchEquivalenceIT`, 커서 v6 포맷 무변경, 표시 홀더·락·발급 구조 무변경(§4).
- **기준선(§4-2)은 그대로**: 비교·스캔이 읽는 값만 장소 표에, 표시값은 홀더에.

### 11-6. 구현했다가 되돌린 이유 (2026-09-09)

구현은 커밋 셋으로 했다: 평점을 int 하나로(584c0df) → `DistanceSort`가 열 배열을 받게(2a05747) →
인덱스를 표와 자리 배열로(618e6e7). 단계마다 등가 IT 둘이 통과했고 테스트 363개였다. 그 뒤
코드를 다시 읽으며 사용자가 판단을 뒤집었고, 0342fbc로 객체 배열에 되돌렸다.

**되돌린 논리.** 열 배열이 얻는 것은 셋이고 전부 사실이다 — 사진 안의 장소 객체가 0개가 되어
Old GC 표시 대상이 사라지고, 재빌드 때 장소 수만큼의 객체 할당이 사라지고, 필요한 열만 연속으로
읽어 캐시 라인 하나로 여러 행을 처리한다. 63만 개 × 사진 3장 규모면 매력적이다. 그러나:

- 현재 scan 단위는 동네별 정렬 배열 100~300개라 한 번의 scan이 다루는 working set이 작다.
  열 배열의 연속 접근이 구조적으로 유리하더라도, 이 규모에서는 객체 배열의 cache miss가 실제
  병목으로 커질 가능성이 낮다. ("캐시에 다 들어간다"고 말하지 않는다 — 객체판도 참조를 따라
  뛰고, 캐시 상주는 CPU·객체 배치·GC 압축·다른 스레드에 따라 보장되지 않는다.) 감으로는 태그
  필터만 볼 때 300 × 8B = 2.4KB 대 300 × 80B = 24KB. 구조적 차이는 분명하지만 24KB도 작다.
- 객체 수·GC·재빌드 할당이 문제라는 관측이 없다. 관측 없는 병목에 미리 지불한 것이다.
- 지불한 것은 컸다. 장소 하나가 배열 열 개로 찢어져 `table.popularScore(order[i])`처럼 첨자를
  두 번 타고, 필드 하나 추가가 생성·재빌드·복사·접근자·테스트를 전부 건드리며, seek·k-way
  merge·Top-K·커서까지 행 번호(맨 `int`)가 전파되어 다른 열에 잘못 적용해도 컴파일러가 못 잡는다.
- 100배 규모는 서버 하드웨어 자체가 한계인 영역이라 요구사항으로 두지 않는다.
- 중간 선택지(정렬마다 id·마스크·정렬 키만 원시화하고 최종 K건은 객체 조회)는 검토했으나
  택하지 않았다. 객체 N개가 그대로 남아 GC 이점이 없고, 남는 것은 locality뿐인데 그것이 이
  규모에서 가장 덜 중요한 이점이다. 정렬 키가 축마다 타입·개수가 달라 배열 묶음도 축마다 갈린다.

**남긴 것.** 평점을 `int ratingToInt` 하나로 두는 것(§11-3). 객체 배열에서도 장소마다 `BigDecimal`
객체 하나와 `double` 중복을 없애고 가독성 손실이 없다. 커서 복원은 반드시 `Math.round(v × 100)`
이어야 한다 — 0.00~9.99 중 69개 값(4.35 등)이 double에서 정수 바로 아래에 떨어져 버림이면 1
작다. 테스트가 4.35 커서로 그 경계를 고정한다. 두 경로의 경계 판정이 같은 근거(k → k/100.0의
순서 보존)는 `PlaceListIndex`의 커서 복원 헬퍼 javadoc에 있다.

**다시 검토할 신호.** 재빌드 할당량이 커짐, Old GC 표시 시간·빈도 증가, 힙 때문에 컨테이너
메모리가 부담, scan CPU에서 cache miss가 의미 있게 관측. 이 중 하나가 JFR·프로파일러에 보이면
§11-1~11-5가 설계 그대로 쓰인다.

## 12. 이 문서로 말할 수 없는 것

- **어드민 빈도.** 측정 수단이 없다. "하루 수십 회"는 가정이고 이 가정이 §5의 산수를 떠받친다.
- **표시 맵 조회가 요청 경로에 더한 비용.** 페이지당 맵 조회 20번(장소 10 + 태그 10)이다.
  자릿수로 무시할 만하지만 재지 않았다.
- **"한 시점 데이터"를 원하는 화면이 있는가.** 제품 판단으로 없다고 봤다. 생기면 계약을 다시
  정해야 하고 그때는 사진마다 표시 맵(§4-2의 안 한 것)이 첫 후보다.
- **MAIN 태그가 둘인 장소.** 비정상 데이터다. 캐시의 두 경로(전량·단건)는 `place_tag.id` 순으로
  같은 답을 내지만, 엔티티 경로는 정렬 없는 fetch join이라 태그 id 순이 된다. 등가 테스트는 이
  경우를 제외한다. 스펙을 정하지 않았다.
