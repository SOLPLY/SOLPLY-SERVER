# 2026-08-04_read-ceiling — 읽기 전용 목표 부하 300 req/s 검증 (캠페인 ①)

> **사전 등록 문서다.** 아래 다섯 항목과 성공 조건은 측정 전에 사용자와 합의해 고정했다
> (2026-08-04). 결과에 맞춰 수정하지 않는다.

## 0. 목표 부하 산정표 — 300은 어디서 온 숫자인가

임의 숫자가 아니라 규모 가정의 결과다. 실무 관례(DAU × 인당 요청 ÷ 86,400 × 피크 계수)를
그대로 따랐다.

| 단계 | 값 | 근거 |
|---|---|---|
| 규모 가정 | DAU 200,000 | 성공 시나리오. 1인 가구 타깃 지역 서비스에서 방어 가능한 상한급 |
| 인당 인기순 요청 | 30건/일 | 인기순이 홈 기본 정렬이라 진입마다 발생 + 무한 스크롤 |
| 평균 부하 | ≈ 70 req/s | 200,000 × 30 ÷ 86,400 |
| 피크 계수 | ×5 | 여가 서비스 — 저녁·주말 집중형 |
| **목표 피크** | **300 req/s** | 인기순 조회 경로 **단독** |

참고 교차 검증: 같은 공식에 대형 서비스(DAU 1,000만 × 인당 200건)를 넣으면 피크 7만~10만
req/s가 나온다 — 발표에서 오가는 "10만 TPS"급과 일치. 즉 단일 경로 300은 규모 가정에 비례하는
정직한 숫자다.

**시드는 불변** (장소 6,320 · 동네 350). 장소 수는 서비스 특성상 유저 수에 비례하지 않고,
읽기 경로(place_stats 기준 조회)는 bookmarks 행 수와 무관하다.

## 1. 문제

목표 부하를 300 req/s로 올렸을 때 현 구조(place_stats 사전 집계 + DB 직접 정렬, 형상은
커서 v3 포함)가 받아낼 수 있는지 불명확하다. 직전 캠페인의 "300 붕괴"는 쓰기 10% 믹스
+ 북마크 중복 등록 500 변환의 예외 로깅 오버헤드가 섞인 수치라서, **읽기 경로 자체의
한계로 귀속할 수 없다.**

## 2. 원인 가설

읽기 전용에서도 병목은 앱이 아니라 **MySQL CPU**이고, 지배 비용은 시 단위 계열
(다중 range + filesort, 요청 수 기준 ~40%)일 것이다.

근거: 동네 단위 0.324ms vs 시 단위 0.806ms(V26 커버링 후) EXPLAIN 실측, 직전 래더에서
읽기 포화가 DB 단독이었던 관찰 (`docs/perf/2026-08-02-post-removal-regression.md`).

## 3. 기술적 선택

**이 캠페인에는 없다 — 선택을 위한 진단이 목적이다.** 개선안(parentTownId 인덱스 등)은
이 캠페인의 자원·원인 지표를 보고 캠페인 ②에서 별도 사전 등록한다. 선택을 먼저 확정하면
원인을 끼워 맞추게 되기 때문에 순서를 강제한다.

## 4. 검증할 주장

읽기 전용 믹스에서도 현 구조는 300 req/s를 받지 못하며, 붕괴 시점의 병목은 앱이 아닌
DB CPU다.

- 이번 서사에서 중요한 것은 무릎의 정확한 위치가 아니라 **"300에서 실패했고, 개선 후
  어디까지 받게 됐는가"** 이므로, 붕괴 전 지점 협착(270 등)은 하지 않는다.
- 300이 **통과**하면 그것도 유효한 결과다 — 직전 붕괴가 쓰기·예외 로깅 오염 몫이었다는
  뜻이고, 목표 상향(330/360)을 다시 논의한다.

## 5. 성공 조건 (측정 전 고정)

| # | 조건 | 판정 |
|---|---|---|
| ⓐ | 생성기 달성률 ≥ 목표의 98% (지속 구간 평균) | 미달 라운드는 지연이 다른 부하를 잰 것 → **무효** |
| ⓑ | 붕괴 판정: 달성률 정체 + p50이 정상 기대(≈11ms)의 3배 이상 + 실패(타임아웃·5xx) 상승 | 셋이 함께 나타나면 붕괴 확정 (처리량×지연 교차 해석) |
| ⓒ | 붕괴 라운드에서 DB CPU 상한(200%) 도달 + 앱 CPU 상한 미달 | 안 나오면 "병목은 DB" 주장 불성립 → 캠페인 ②로 진행하지 않음 |

- 판정 지표: **p50 + 자원 지표(sampler) + 원인 지표(metrics-snapshot diff)**.
- **p95/p99는 기록한다** (판정에는 쓰지 않음). 유효 라운드 간 재현성이 확인되면 "이 스펙
  기준"을 달아 승급 후보 — 읽기 전용 + 예외 로깅 제거라 직전보다 안정적일 것으로 기대.

## 6. 믹스 — 직전 캠페인과 무엇이 다른가

읽기 4종의 상대 비율은 유지하고 재정규화, **쓰기(bookmark-toggle 10%)는 제외**했다.

| 시나리오 | 직전 | 이번 | 근거 |
|---|---|---|---|
| popular-town (동네 첫 페이지) | 36 | **40** | 홈 기본 진입 — 가장 흔한 요청 |
| popular-city (시 단위, leaf 18) | 18 | **20** | filesort가 남는 비싼 경로 |
| popular-tag-filter (EXISTS 필터) | 18 | **20** | 필터 부하 대표 |
| popular-scroll (시 단위 2페이지) | 18 | **20** | 커서 술어 + 무한 스크롤 |
| bookmark-toggle | 10 | **0** | 산정표상 피크 쓰기 ≈ 0.5%라 10%는 30배 과대 대표. 중복 가드 결함(수정 전) 예외 로깅이 앱 CPU를 오염시키는 문제도 차단 |

⚠️ **직전 캠페인 수치와 직접 비교 불가** (믹스가 다름). 개선 전/후 비교는 이 믹스를
기준으로 캠페인 ② 안에서 수행한다.

## 등록 추가 (2026-08-04, 300 통과 판정 직후 · 측정 전 고정) — 상한 탐색: 도착 500/s

300 통과로 §4의 "통과 시 목표 상향 재논의" 분기를 탄다. 사용자 결정: 중간 지점 없이
**도착 500/s(실처리 ≈600 req/s) 단일 지점**으로 상한을 탐색한다 — 서사상 필요한 것은
무릎의 정밀 위치가 아니라 "어디까지 받는가"이므로.

- **검증할 주장:** 읽기 전용 믹스에서 현 구조가 실처리 ≈600 req/s를 받는지 확인한다.
  통과 → "읽기 한계 ≥ 600 실처리 확인". 붕괴 → "한계 ∈ (361, 600) 실처리"로 기록.
- **성공 조건:** ⓐ 달성률 ≥ 98% — 단 미달 시 **생성기 포화와 서버 붕괴를 구분**한다
  (artillery 프로세스 CPU 기록 필수. 같은 호스트에서 돌므로 500부터는 생성기가 먼저 걸릴
  수 있다). 생성기 몫이면 상한은 "≥ 달성치" 하한 서술로만 남긴다. ⓑ 붕괴 판정 기준 동일
  (달성률 정체 + p50 3배 + 실패 상승). ⓒ 붕괴 시 병목 귀속: 앱/DB 어느 CPU가 상한
  도달인지 자원 지표로 특정.
- 프로토콜 동일: 3라운드(r1 폐기), 60초 휴식, 매시 :30 배치 회피, 지표·유효성 규칙 동일.

### 결과 (2026-08-04 측정, 판정: 붕괴 — 병목은 MySQL CPU)

3라운드 실행(01:34~01:46), r1 워밍업 폐기, r2·r3 유효. 도착률은 100.0%(vusers.created
68,550 = 이론값 정확 일치) — 서버가 받은 부하는 시도 기준 **554~555 req/s**였다.

| 지표 | r2 | r3 | (300 지점 r3) |
|---|---|---|---|
| 성공 응답 처리량 (지속) | 308 req/s | 313 req/s | 361 req/s |
| p50 (지속 구간) | 9,417 ms | 9,048 ms | 6 ms |
| 실패 (타임아웃 중심) | 43.8% | 39.1% | 0% |

| 앱 cgroup 스로틀 비율 | 12.5~13.7% | 8.5~9.1% | — |

**판정.**

- **ⓑ 붕괴 확정 — 적체형이다.** 도착을 500/s로 올리자 성공 처리량이 361 → 308~313 req/s로
  **하락**하며 p50이 1,500배 뛰었다(처리량 하락 + 지연 상승 = 적체). 서버는 받은 요청의
  98.8%를 실제로 처리했다(Com_select ÷ 7.17 교차 검산) — 일을 버린 게 아니라 10초(클라이언트
  타임아웃)를 넘겨 끝냈다.
- **ⓒ 병목은 DB다.** MySQL이 100ms period의 68%에서 2 vCPU 쿼터에 스로틀(앱의 17~27배,
  스로틀 누적 578~623초). 커넥션 풀(Hikari 10×2)은 threads_running 15~21로 사실상 전량
  동시 실행. 디스크 I/O·정렬 디스크 폴백·락 대기는 전부 0 — 순수 CPU 병목.
- **읽기 전용 한계: 실처리 361 req/s 통과 / 시도 554 req/s 붕괴.** 한계는 그 사이이며
  이 캠페인에서는 더 협착하지 않는다 (서사에 필요한 것은 "목표 300/실처리 361을 절반
  여유로 통과, 1.5배 지점에서 DB CPU로 붕괴"까지다).

**판정에 딸린 결정 3건 (워커가 유보한 것).**

1. **유효성 규칙 해석 — r2·r3 유효.** sampler(docker stats)가 배정 상한 200%를 넘는 값을
   보고했으나, cgroup `cpu.max`(200000/100000 강제 적용)·`cpu.stat` 실측으로 상한 초과가
   물리적으로 없었음을 확인했다. 규칙의 의도는 "호스트 경합으로 컨테이너가 배정 이상을
   먹었는가"이고 cgroup이 그 일이 없었음을 보인다. **교훈: 고동시성에서 docker stats CPU는
   과대 보고한다 — cgroup cpu.stat이 정본** (함정 목록 등재 대상).
2. **LB가 제3의 천장으로 등장 — 단 주 병목 아님.** HTTP 500 전량(160건)이 nginx
   `worker_connections 1024` 고갈 몫으로 확인됐다(에러 로그 건수와 정확 일치, 앱 예외 0건).
   실패의 0.24%라 이번 귀속을 바꾸지 않지만, **향후 361 req/s 초과 측정 전에는 LB 설정
   상향이 선행 조건**이다.
3. **원인 지표 이상 1건 — 미규명으로 남긴다.** 요청당 Innodb_rows_read 1,101→2,253,
   Handler_read_key 227→930(4배), Select_scan 0.003→0.115로 증가했고 믹스 변화(스크롤 p2
   미발화로 실현 배수 1.199→1.13)로는 설명되지 않는다. 정렬 계열은 불변인데 인덱스 탐색·행
   읽기만 늘었다 — 포화 상태의 플랜 플립 가설(기존 §9-2와 같은 계열)이 후보이나 EXPLAIN
   없이는 주장하지 않는다. **후속: 포화 부하 중 EXPLAIN/옵티마이저 trace 확보.**
