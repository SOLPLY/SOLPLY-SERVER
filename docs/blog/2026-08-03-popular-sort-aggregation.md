이 문서는 최종 구조로 이어진 판단 과정만 담는다. 중간에 채택했다가 되돌린 구성(이벤트 증분, 조인 순서 힌트, 다중 인스턴스 전제)은 최종 선택을 이해하는 데 필요한 만큼만 선택지 표에 남기고, 도입과 철회의 왕복 서사는 싣지 않는다.

## 판단 줄기

인기순 정렬을 위한 장소 통계를 언제, 어디서 계산해 어디에 둘 것인가. 그리고 그 구조가 목표 부하와 무한 스크롤 일관성 앞에서 어떻게 부서지고, 무엇으로 다시 세웠는가.

## 0. 독자에게 먼저 줄 맥락

- 어떤 기능인가: SOLPLY(1인 가구 여가 장소 큐레이션)의 장소 리스트 인기순 정렬. 홈 화면의 기본 정렬이라 진입과 무한 스크롤마다 조회가 발생한다.
- 사용자 흐름: 동네 또는 시 단위로 목록을 열고, 태그로 거르고, 커서 기반 무한 스크롤로 내려간다.
- 구조: edge 프록시 뒤에 애플리케이션 프로세스 1개와 MySQL 1개. 결제가 없는 서비스라 잠깐의 중단을 수용하고, 이중화가 요구하는 복잡도(무중단 배포, DB 복제, 인스턴스 간 정합성)를 사지 않기로 했다. (근거: docs/design/...-version-rows.md §0, 커밋 `5fc8f55`)
- 목표 부하: 인기순 경로 단독 피크 도착 300 req/s. DAU 20만 × 하루 30회 ÷ 86,400 × 피크 계수 5 ≈ 300. 같은 공식에 대형 서비스 규모(DAU 1,000만, 인당 200건)를 넣으면 7만~10만 req/s가 나와 업계에서 오가는 "10만 TPS"급과 자릿수가 맞는다. 임의의 숫자가 아니라 규모 가정에 비례하는 숫자다. (근거: load-test/campaigns/2026-08-04_read-ceiling/README.md)
- 벤치 환경: 앱 2vCPU/2GB, MySQL 2vCPU/3GB, 북마크 약 1,040만 행 시드. (근거: docker/docker-compose.bench.yml)

## 1. 요청 시점 계산을 기각하고 사전 집계로 갔다

문제. 인기순이 들어오기 전까지 북마크는 세어질 일이 없는 데이터였다. 정렬이 생기면서 처음으로 장소별 집계가 필요해졌다.

알게 된 것. 조회 쿼리 안에서 매번 집계하는 비용을 InnoDB 핸들러 카운터로 실측하니, 서울 단위 조회 한 번이 장소 435곳 × 장소당 평균 북마크 7,466개로 인덱스 엔트리 3,247,626개를 읽었다. EXPLAIN 추정(약 24만 행)의 13.5배다. 옵티마이저 추정만 보고 판단했다면 규모를 한 자릿수 이상 얕봤을 것이다. (근거: docs/perf/2026-08-02-post-removal-regression.md)

선택지와 근거. 요청 시점 계산은 비용이 북마크 수에 비례해 자라고, 그 비용을 지불할 이유가 없었다. 인기는 집단 행동의 누적이라 하루 안의 유입으로 상위권이 거의 바뀌지 않고(시드 기준 강남 1위 장소 북마크 65,730개, 최하위 5,016개로 13배 격차), 사용자도 순위가 몇 시간 늦는 것을 인식하지 못한다. 주기 배치로 미리 계산해 두고 조회는 읽기만 하는 사전 집계를 택했다.

## 2. 계산은 데이터가 있는 곳에서 한다

문제. 사전 집계 배치가 북마크 1,040만 행을 장소 단위로 집계해야 한다. DB에서 SQL로 집계할지, 애플리케이션으로 가져와 계산할지.

선택과 근거. 어디서 계산하든 그 1,040만 행은 DB가 스캔해야 한다. 이미 스캔한 행을 애플리케이션으로 가져와 계산할 이유가 없다. 옮기는 순간 네트워크 전송과 JDBC 객체 변환 비용이 추가되고, 그 부담은 하필 DB보다 먼저 포화되는 앱 CPU에 얹힌다(§8의 실측). 행별 연산(감쇠 × 가중치)은 단순해서 DB 산술을 아껴 얻는 것도 없다. 집계와 점수 계산은 SQL 한 문장(INSERT ... SELECT)으로 DB에서 끝내고, 애플리케이션은 배치 흐름만 관리한다. (근거: docs/design/...-version-rows.md §3.1)

재검토 조건. 행당 연산이 수 µs급으로 복잡해지거나 DB CPU가 병목으로 전환되면 계산 위치를 다시 따진다. 배치가 무거워지면 계산 위치보다, 감쇠 특성상 기여가 0에 수렴하는 오래된 행을 스캔에서 빼는 쪽이 먼저다.

## 3. 계산한 점수를 별도 통계 테이블에 뒀다

| 선택지 | 문제를 어떻게 푸는가 | 판정과 이유 |
|---|---|---|
| 인스턴스 로컬 메모리 | 배치 결과를 프로세스 안에 들고 정렬 | 기각. 재시작마다 소실되고 재구축 경로가 결국 DB 재계산이라 영속 계층이 따로 필요해진다 |
| 원본(places) 컬럼 비정규화 | 원본 행에 점수 컬럼을 붙임 | 기각. 정렬 축이 늘 때마다 원본에 컬럼이 붙고, 파생 데이터는 원본과 정확도 요구가 달라 분리가 자연스럽다 |
| 분산 캐시(Redis sorted set) | 점수를 정렬 자료구조에 적재 | 기각. 아래 부연 |
| 별도 통계 테이블(place_stats) | 계산 결과가 곧 영속 저장소 | 채택. 사본 계층이 생기지 않는다 |

Redis 기각 부연. 어느 쪽이든 전량 재계산 배치는 사라지지 않는다. 시간 감쇠 점수는 저장된 값이 시간이 지나면 스스로 낡아서 주기적으로 원본에서 다시 계산해야 하는데, 원본은 DB에 있다. Redis에 두는 순간 "DB에서 계산해 Redis에 얹는" 사본 계층이 생기고, DB 테이블에 두면 계산 결과가 곧 영속 저장소다. sorted set의 정렬 흡수가 이기려면 DB 정렬이 병목이어야 하는데, 정렬 축을 인덱스 선두에 두면 동네 단위 조회는 수백 행 수준의 인덱스 스캔이라 병목이 아니었다(§8 실측). 프로젝트가 직전 작업에서 Redis 조회 캐시를 걷어내며 의존을 줄이는 중이었다는 운영 방향도 있었다. 다시 올라올 조건도 적어뒀다. 단일 DB가 읽기를 감당하지 못하는 규모가 되면 읽기 리플리카와 캐시 계층 중 무엇이 먼저인지부터 다시 따진다.

## 4. 점수 공식, 두 항의 감쇠가 다르다

```
점수 = Σ 북마크 [ 1.0 × 0.5^(경과일 / 90) ]      ← 시간 감쇠
     + 3.0 × Σ 리뷰 (평점 − 3)                    ← 감쇠 없음
```

인기(북마크)는 최근 활동이라 감쇠하고, 평판(리뷰)은 누적 판단이라 감쇠하지 않는다. 리뷰에 감쇠를 걸면 최근 리뷰가 과대 가중되는데, 리뷰의 가치는 다수 의견의 평균화에 있으므로 소수의 최근 저평점이 순위를 흔드는 것은 오답이다. 시점과 무관하게 1표씩이 맞다. (근거: 커밋 `d898d38`, 테스트 "리뷰_기여는_작성_시점과_무관하다")

평점에서 3을 빼는 것은 낮은 평점이 순위를 실제로 끌어내리게 하기 위해서다. 원점수를 그대로 합산하면 1점 리뷰도 점수를 올려, 평점 낮은 장소가 리뷰 수만으로 상위에 오른다. 북마크 반감기 90일은 "역대 인기"와 "이번 주 트렌딩" 사이에서 앞쪽을 유지하는 선택이다.

## 5. 쓰기 경로는 배치 하나로 통일했다

문제. 사전 집계로 가면 통계값에 지연이 생긴다. 얼마나 신선해야 하는가.

알게 된 것. 즉시성이 정말 필요한 것은 남의 행동이 아니라 내 행동의 반영인데, 그것은 집계 숫자가 아니라 북마크 여부 표시(체크 상태)가 담당한다. 숫자는 조회수처럼 주기 갱신되는 값으로 읽힌다.

선택지와 근거. 회차 사이를 메우는 이벤트 기반 증분(커밋 후 비동기 +1/-1)을 검토했지만, 그 경로를 두는 순간 허용 오차의 정의, 배치와의 착지 경합, 음수 방지, 교착 시 재시도, 수렴 시점이라는 질문 목록이 따라온다. 원자성을 보장하지 못하는 경로에 그 비용을 지불할 이유가 없어 순위·북마크 수·평점 모두 배치 주기(1시간 이내) 지연을 수용하고 쓰기 경로를 배치 하나로 통일했다. 배치는 원본에서 전량을 다시 계산하므로 어떤 오차도 다음 회차에 소멸하고, 같은 기준 시각으로 몇 번을 돌려도 결과가 같아(멱등) 실패하면 다시 돌리면 된다. (근거: docs/design/...-version-rows.md §5, 커밋 `d4626dc`)

배치 주기. 하루 1회에서 매시 1회로 당겼다. 감쇠 신선도 때문이 아니다(반감기 90일 점수는 한 시간에 0.032%만 변한다, 산술). 신규 장소가 목록에 반영되는 지연과 관리자 조치(장소 비활성화)가 사라지는 지연에 1시간 상한을 두기 위해서다. 전량 재계산이 약 6초로 싸다는 실측이 있어 가능한 결정이었다.

격리 수준. 기본 REPEATABLE READ에서는 배치의 집계 SELECT가 갱신 쿼리 안에 있어 잠금 읽기로 동작했고, 북마크 테이블에 넥스트 키 락 약 1,073만 개를 잡았다(실측). READ COMMITTED로 전환하고 집계 기준 시각에 상한을 걸어 서비스 쓰기와 잠금으로 부딪히지 않게 했다. (근거: PlaceStatsRepository.upsertAll javadoc의 실측 기록, 커밋 `82cec34` 시점 판)

## 6. 스크롤 일관성, 배치 전과 후를 버전으로 관리한다

문제. 매시 배치가 점수를 통째로 갱신하면, 스크롤 도중 배치가 지나갈 때 커서가 서 있던 좌표계(점수 순서)가 재배열된다. 다음 페이지에서 이미 본 장소가 다시 나오거나 안 본 장소가 건너뛰어진다.

| 선택지 | 원리 | 판정과 이유 |
|---|---|---|
| 버전 행 스냅샷 | 배치 1회차 = 버전 하나의 불변 행 묶음, 커서가 버전을 고정 | 채택 |
| 테이블 이중화(블루-그린) | 두 테이블을 번갈아 쓰고 포인터 전환 | 기각. 같은 보장을 테이블 두 개와 전환 장치로 사는 셈 |
| Redis 스냅샷 + TTL | 회차별 키로 sorted set 적재, 옛 키를 TTL로 유지 | 기각. §3의 Redis 기각 근거가 그대로 적용 |
| 세대 컬럼 쌍(현재/직전 점수 컬럼) | 같은 행에 두 세대 점수를 나란히 보관 | 기각. 갱신 순서가 계약이 되고, 정렬 컬럼을 동적으로 갈아 끼우는 SQL과 인덱스 2벌이 필요 |

채택 구조. 통계 테이블 기본 키가 (장소, 버전)이고, 배치는 기존 행을 덮어쓰는 대신 새 버전의 행 묶음을 쓴 뒤 보관 범위(현재 + 직전, 2버전) 밖을 지운다. 쓰기 경로가 배치 하나뿐이라 버전 행은 쓰고 나면 아무도 만지지 않는다.

```
배치 회차       13:30        14:30        15:30
                v1 생성  →   v2 생성   →  v3 생성 + v1 삭제
스크롤 세션            └── v1로 시작한 스크롤은 v2가 생겨도 v1을 계속 읽는다
```

커서는 자기가 태어난 버전을 싣고 다니고, 조회는 `WHERE version = ?` 하나로 그 스냅샷만 읽는다. 스크롤 일관성이 "코드가 컬럼을 잘 고른다"는 계약이 아니라 "보던 행들이 거기 그대로 있다"는 구조에서 나온다. (근거: docs/design/...-version-rows.md §1~§4, 커밋 `d4626dc`, 테스트 "전환 전 발급 커서가 전환 후 직전 버전으로 서빙")

만료 정책. 두 버전보다 오래된 커서(스크롤 2시간 이상 방치)는 좌표계가 이미 없다. 낡은 좌표를 새 좌표계에 이어 붙이면 이음새에서 누락과 중복이 생기므로, 만료 오류를 돌려주고 첫 페이지부터 다시 시작하게 했다. 보관 2버전의 근거는 스크롤 세션 수명이다. 배치 간격을 두 번 넘기는 세션은 드물고, N버전 보관은 저장량과 청소 비용만 늘린다.

인덱스. (버전, 동네, 점수, 장소 id, 표시값들) 한 벌. 버전이 항상 등호로 걸려 자기 스냅샷만 잘라내고, 그 안에서 필터와 정렬을 인덱스가 흡수하며, 말단에 표시값까지 실려 조회가 인덱스 안에서 끝난다(커버링). 여러 동네를 묶는 시 단위 조회는 동네별로는 점수순이어도 전체로는 점수순이 아니라 정렬(filesort)이 남는데, 정렬 대상이 인덱스 엔트리 수백~1,800건 수준이라 수용했다. 저장·쓰기 비용은 늘어난다. 행이 2배(전 컬럼이 버전마다 중복)이고 매시 INSERT + DELETE가 페이지 분할과 단편화를 만들 수 있어 관찰 항목으로 등재했다.

말단의 표시값은 처음에 북마크 수 하나였고, 목록에 평점·리뷰 수를 실으면서 셋이 됐다(V30). 이때 "인덱스를 늘릴 것인가"를 재서 정하지 않고 그냥 늘린 것이 이 대목의 판단이다. 측정으로 답이 나오지 않는 크기이기 때문이다. 덮지 못한 컬럼이 하나라도 있으면 페이지 행마다 기본 키로 되짚는 룩업이 붙는데, 기본 페이지 크기가 10이고 통계 테이블은 장소 약 6,000 × 보관 2버전 ≈ 12,000행이라 통째로 버퍼풀에 상주한다. 요청 하나가 이미 SQL 11개 × 문장당 고정비 약 200µs를 쓰는 마당에 룩업 10회의 몫은 그 아래로 묻혀, 로컬 벤치에서는 노이즈와 구분되지 않는다. 반대로 대가 쪽은 산술로 확정된다. 엔트리당 약 6바이트 × 12,000 ≈ 72KB, 그리고 쓰기 주체가 시간당 배치 하나뿐이라 인덱스 유지비를 물 경로 자체가 없다. 이득이 측정 불가능하게 작고 비용도 확정적으로 작을 때는, 재서 정하는 것보다 구조가 가진 성질("이 쿼리는 인덱스 안에서 끝난다")을 깨지 않는 쪽이 낫다는 판단이다. 정렬 인덱스에 표시 컬럼을 얹는 선택은 표시 항목이 늘 때마다 인덱스도 함께 늘어난다는 뜻이므로, 그 연동은 쿼리 쪽 주석에 못 박아 뒀다.

## 7. 설계가 맞는지 부하로 확인했다

판정 기준을 측정 전에 등록하고 쟀다. 측정 후에 기준을 세우면 나온 숫자에 맞춰 판단이 휘기 때문이다. (측정 조건 주의: §7~§9의 부하 수치는 앱 2대 + 로드밸런서 시절의 것이다. 이후 단일 프로세스로 정리되어 절대값은 새 기준선이 필요하다. 근거: load-test/README.md)

배치 무해 확인. 부하가 걸린 한가운데서 실제 스케줄러 경로로 배치를 발화시켰다. 소요는 5.7초에서 6.2초(1.08배)로 늘었을 뿐, 같은 구간의 조회 지연과 행 락 대기는 배치 없는 라운드와 구분되지 않았다. (근거: docs/perf/2026-08-02-post-removal-regression.md)

한계 측정. 조회 90% + 쓰기 10% 혼합에서 약 240 req/s에 멈췄지만, 붕괴 라운드에 쓰기 결함(중복 등록 서버 오류)과 예외 스택 로깅 오염이 섞여 있어 구조의 한계로 판정할 수 없었다. 쓰기와 예외 로깅을 뺀 읽기 전용 구성으로 다시 쟀다. (근거: docs/perf/2026-08-04-read-ceiling.md)

| | 도착 300/s (목표 지점) | 도착 500/s (상한 탐색) |
|---|---|---|
| 처리 요청 | 실처리 361 req/s | 시도 554 → 성공 308~313 req/s로 하락 |
| p50 | 6~7ms | 9초 이상 |
| 실패 | 0 | 39~44% (10초 타임아웃) |
| MySQL CPU | 배정량의 43% | 스케줄 주기의 68%에서 강제 정지(스로틀) |
| 판정 | 통과 | 붕괴, 병목은 MySQL CPU |

"240 붕괴"는 읽기 구조가 아니라 쓰기 결함과 로깅의 몫으로 재귀속됐다. 붕괴의 모양도 읽어뒀다. 처리량 하락 + 지연 상승 조합은 요청을 거절하는 상태가 아니라 밀린 일을 안고 허덕이는 상태이고, 서버 쪽 카운터 검산으로 받은 요청의 98.8%를 처리하고 있었다. 일을 버린 게 아니라 늦게 끝냈고, 클라이언트가 먼저 포기했다.

## 8. 원인을 쫓다가 측정 방법부터 고쳤다

문제. 포화 라운드에서 요청당 행 읽기(전역 누적 카운터 ÷ 요청 수)가 정상 구간의 2배로 보였다. 사실이라면 부하가 실행계획 자체를 바꾸는 악순환이라 용량 증설로도 못 푼다.

알게 된 것. 이 지표는 판정에 쓸 수 없는 값이었다. 전역 카운터는 서버가 한 모든 일의 합이라 어떤 SQL이 비싸졌는지 지목하지 못하고, "요청 수" 분모는 부하에 따라 구성이 변한다. performance_schema의 쿼리 모양별 집계로 "읽은 행 ÷ 실행 횟수"를 재고, 동일 파라미터 EXPLAIN을 부하 전·중·후 네 시점에 떠서 확인했다. 결과는 가설 기각이다. 가장 비싼 쿼리의 실행당 행 읽기는 정상 12,669 vs 포화 12,664로 불변, 실행계획도 네 시점 동일. "2배"의 정체는 요청 구성의 이동이었다. 1페이지가 타임아웃된 사용자는 2페이지를 요청하지 못하므로 유독 비싼 2페이지 쿼리의 비중이 16.6% → 6.4%로 줄었고, 평균은 "같은 쿼리가 비싸짐"과 "비싼 쿼리가 덜 섞임"을 구분하지 못한다. (근거: docs/perf/2026-08-04-saturation-amplification.md)

기각된 가설이 진범을 데려왔다. 2페이지 쿼리는 부하와 무관하게 항상 13.5배 비쌌다. 당시 인기순 쿼리는 통계 테이블을 읽은 뒤 원본(places)을 조인하고 있었는데(역할은 내린 장소 즉시 숨김 하나), 커서 조건이 조인과 만나며 옵티마이저가 정반대 계획을 골랐다.

| | 1페이지 (정상 계획) | 2페이지 (뒤집힌 계획) |
|---|---|---|
| 먼저 읽는 테이블 | 통계 테이블, 점수 인덱스로 해당 지역만 | 원본 테이블, 인덱스 전체 스캔 |
| 실행당 행 읽기 | 약 940 | 6,342 + 행마다 통계 테이블 되짚기 ≈ 12,700 |
| 정렬 | 인덱스가 대부분 흡수 | 임시 테이블 + 정렬 |
| 옵티마이저 비용 추정 | 약 990 | 880, 이 추정이 이겼다 |

겹친 원인은 둘이다. 조인 조건(p.id = ps.place_id)은 두 컬럼이 같다는 선언이라 옵티마이저가 통계 테이블 쪽 커서 조건을 원본의 id 조건으로 옮겨 적을 수 있고, 그 순간 원본부터 읽는 계획이 후보로 생긴다. 그리고 그 후보의 비용 계산에 필요한 active = 1의 통과율을 MySQL 기본 통계가 모른다(인덱스 통계는 값 종류 수만 담고 분포는 없다). 통계가 없으면 내장 기본값을 쓰는데 등호 조건은 10%만 남긴다고 가정한다. 실제는 거의 100%다. "원본 전체를 훑어도 10%만 살아남으니 싸다"는 계산이 이겼고 실행은 정반대였다. 옵티마이저가 멍청한 게 아니라 틀린 입력으로 정확한 계산을 했다.

효과 크기는 실험으로 확인했다. 인덱스를 강제 지정한 실험군에서 실행당 행 읽기 12,664 → 1,822, 포화 지점 성공 처리량 2.7배(155 → 421 req/s). (근거: 같은 문서, 캠페인 results/explain)

## 9. 처방, 조인을 없애고 불변식을 배치로 옮겼다

| 선택지 | 원리 | 판정과 이유 |
|---|---|---|
| FORCE INDEX 상시화 | 인덱스를 코드로 못박음 | 기각. 인덱스 이름에 코드가 결합되고, 미래의 더 나은 인덱스도 배제 |
| 파생 테이블 재구성 | 통계 테이블 선별을 서브쿼리로 먼저 완료 | 기각. "다음 페이지 있음" 판정(페이지 크기 + 1건 읽기)이 바깥 노출 필터에 깎여 스크롤 조기 종료 |
| 조인 순서 힌트 | 먼저 읽을 테이블만 고정 | 기각. 증상의 봉합. 옵티마이저가 뒤집을 자유도가 남아 있는 한 힌트는 그것을 코드로 틀어막는 것 |
| 조인 제거 | 노출 필터의 책임을 배치로 이동 | 채택 |

채택 근거. 걸러낼 정보(지역 조건, 정렬 축, 정렬을 흡수하는 인덱스)가 전부 통계 테이블 쪽에 있는데, 노출 필터 하나 때문에 매 요청 원본을 되짚고 있었다. 조인을 지우고 "통계 테이블(버전 스냅샷)에는 노출 중인 장소만 있다"는 불변식을 배치가 보장하게 옮겼다. 배치가 새 버전을 쓸 때 노출 중인 장소만 담고, 내려간 장소는 다음 배치부터 새 버전에 실리지 않는다. 단일 테이블 쿼리에는 조인 순서라는 자유도가 없으므로 계획이 뒤집히는 문제가 구조적으로 불가능해졌다. (근거: 커밋 `d46ac44`, `d4626dc`, 설계서 §3~§4)

대가. 관리자가 장소를 내려도 다음 배치까지(1시간 이내) 목록에 남는다. 관리자 조치는 드문 사건이고, 그 한 시간을 0으로 만들자고 어드민 쓰기 경로를 통계 테이블에 결합(동기 삭제 훅)하는 것은 수지가 맞지 않아 수용했다.

## 10. 요청 한 건의 원가, SQL 18개를 11개로

계획을 고쳐도 붕괴는 남는다는 산술이 있었다. SQL 한 건의 MySQL CPU가 부하와 무관하게 약 200µs로 일정한데 요청당 SQL이 18개라, 500 req/s급에서는 SQL 처리 고정비만으로 CPU 예산이 소진된다. 남은 천장은 계획이 아니라 SQL 개수였다. (근거: docs/perf/2026-08-04-saturation-amplification.md)

```
개선 전  SQL 18개 = 데이터 SELECT 8  +  트랜잭션 제어 명령 10  (트랜잭션 2개 × 5개)
개선 후  SQL 11개 = 데이터 SELECT 6  +  트랜잭션 제어 명령 5   (트랜잭션 1개)
```

트랜잭션 하나가 제어 명령 5개(autocommit 전환 2, 읽기 전용 설정·원복 2, COMMIT 1)를 만들고, 요청마다 트랜잭션이 둘 열리고 있었다. 하나는 목록 조회 서비스의 것이라 당연한데, 다른 하나는 인증 필터가 매 요청 유저 1행을 읽으며 여는 것이었다. 단건 조회는 그 자체로 원자적이라 그 다섯 개는 아무것도 보호하지 않는다. 조회의 유일한 목적이 권한 판정이었으므로 토큰 발급 때 권한을 실어 서명 검증만으로 인증이 끝나게 했다. 대가는 탈퇴나 권한 변경이 토큰 수명(1시간) 동안 반영되지 않는 것인데, 목록은 로그인 없이도 쓰는 기능이라 수용했다. (근거: 커밋 `22358cb`, `2a50575`)

이 변경에는 부하를 걸지 않았다. SQL 개수 감소는 결정론적 산술이라 부하가 답할 질문이 없고, 검증의 정본은 실행된 SQL 개수를 값으로 단언하는 통합 테스트다. 균형을 위해 적어두면 제어 명령 10개는 개수로는 절반이 넘지만 DB가 거기 쓰는 시간은 전체의 15%다. 이 개선의 이득은 CPU의 대세가 아니라 요청당 왕복 수와 커넥션 점유 시간의 감소다.

## 11. 개선 형상의 재측정 결과

계획 교정(당시는 조인 순서 힌트 형태) + SQL 다이어트가 반영된 형상으로 같은 지점을 다시 쟀다. (근거: docs/perf/2026-08-05-improved-recheck.md. 조건 주의: 앱 2대 + LB 토폴로지, 조인 제거·버전 행 반영 전)

- 도착 300/s: 통과 유지에 여유 확대. MySQL 사용률 46.9 → 28.6%, 요청당 DB CPU 3.51 → 2.13ms. 감소율 39%가 SQL 개수 감소율 39%와 일치해, "요청당 비용 = SQL 개수 × 건당 고정비" 모델이 재확인됐다.
- 도착 500/s(시도 600 req/s): 실패 0, 성공 597~604 req/s. 개선 전 붕괴 지점(성공 155)의 3.9배.
- 시도 700: 붕괴. 이때 병목은 MySQL이 아니라 앱 CPU였다(스로틀 앱 52~59% vs MySQL 23%). DB 병목을 풀면 다음 병목이 앱으로 이동한다는 것까지 확인됐다.

## 12. 남은 한계

- 최종 형상(조인 제거 + 버전 행 + 단일 프로세스)의 부하 재측정이 없다. 개별 변경은 각자의 정본(통합 테스트, EXPLAIN)으로 검증했지만, 부하에서의 합은 새 기준선 측정이 필요하다.
- 버전 행 전환의 실행계획 확인(EXPLAIN ANALYZE, examined rows와 filesort 기록)이 미채취다. 벤치 스택 다음 기동 때 뜬다.
- 버전 행의 저장·쓰기 비용(행 2배, 매시 INSERT + DELETE의 단편화)은 예상이지 측정이 아니다. 배치 소요와 테이블 크기를 관찰 항목으로 등재했다.
- 표시 북마크 수·평점·리뷰 수의 신선도가 1시간 이내로 낮아졌다. 사용자 체감은 관찰 대상이다. 특히 리뷰는 자기가 방금 쓴 것이 목록 숫자에 바로 안 잡히는데, 북마크와 달리 체크 상태 같은 즉시 신호가 없어 관찰 우선순위가 높다.
- 표시 컬럼이 정렬 인덱스에 실려 있어 표시 항목이 늘 때마다 인덱스가 함께 넓어진다. 지금 규모에서는 무시할 만하나, 표시 항목이 계속 늘면 "정렬용 인덱스"와 "표시용 커버링"을 분리할지 다시 따져야 한다.
- 요청당 SQL 개수 × 고정비 천장을 더 낮추는 다음 수는 사용자와 무관한 부분(목록 골격·장소·태그)의 로컬 캐시다. 버전 체계가 있어 캐시 키에 버전을 실으면 배치마다 자연 무효화된다. 별도 작업으로 미뤄뒀다.
- 시 단위 조회의 filesort는 남아 있다. 문제가 되면 조회 축(시)을 통계 테이블에 비정규화해 등호 하나로 만들 수 있다는 것까지 확인해뒀다.
