# 2026-08-06 · 앱 CPU 포화 징후 진단 (계단형 단일 라운드)

> **사전 등록 문서다. 부하를 걸기 전에 썼다.** 아래 §5의 판정 규칙과 §6의 무효 조건은
> 첫 요청을 보내기 전 시각에 확정된 것이고, 측정 후 고치지 않는다.
> 작성 시각 **2026-08-06 16:14 KST**.

## 0. 이 캠페인이 답하려는 것 / 답하지 않는 것

직전 캠페인([`2026-08-06_minimal-stability-final`](../2026-08-06_minimal-stability-final/))은
안정성 게이트였다. 거기서 나온 관찰 — 300 req/s에서 앱 스로틀 18.2%, 상한을 4 vCPU로 올리면
꼬리가 무너진 것이 회복 — 은 "앱 CPU 상한이 병목"을 **지지**했지만, 그 캠페인은 부하 두
점(120·300)만 봤고 자원 지표를 **라운드 시작/종료 누계 차분**으로만 남겼다. 그래서
*어디서부터* 처리량이 안 늘고 지연이 꺾이는지, 그 순간 큐·컨텍스트 스위치·GC가 무엇을 했는지는
알 수 없다.

이 캠페인은 그 빈칸을 **계단형 라운드 하나**로 채운다. 개선을 하지 않고, A/B도 하지 않는다.
**징후를 재고 판정만 한다.**

**답하지 않는 것:** 운영 절대 용량(부하생성기가 같은 호스트에 산다 — §7),
개선 방안의 효과, 장시간 성질(계단이 30초다).

## 1. 문제

앱이 2 vCPU 쿼터 안에서 **어느 지점부터 포화되는지가 미확정**이다. 포화점을 모르면
"지금 형상이 목표 부하 대비 얼마나 남았는가"도, "다음에 무엇을 고쳐야 하는가"도 말할 수 없다.

## 2. 원인 가설 (= 이번에 확인하려는 5가지 징후)

| # | 가설 | 참이면 보일 것 |
|---|---|---|
| Q1 | 앱 CPU가 쿼터(2 vCPU = 절대 2.0코어)에 접근하면서 **실제 HTTP 처리량이 더는 안 는다** | 도착률을 올려도 실제 req/s가 평탄해지고, 같은 구간에서 절대 코어가 2.0에 붙는다 |
| Q2 | 요청량 증가에 대해 응답시간이 **비선형으로 급증하는 knee**가 있다 | 계단 간 처리량 증가율 대비 지연 증가율이 특정 계단에서 급격히 커진다 |
| Q3 | 그 순간 **run queue / CPU pressure / context switch / JVM live threads / GC 시간**이 함께 오른다 | cgroup `cpu.pressure`·`/proc/stat ctxt`·`jvm_threads_live`·`jvm_gc_pause_seconds_sum`의 구간 증가량이 같은 계단에서 꺾인다 |
| Q4 | **DB는 여유로운데 앱만 포화된다** | 같은 계단에서 앱 스로틀은 오르는데 MySQL 절대 코어·스로틀·락·커넥션은 평탄하다 |
| Q5 | 특정 작업이 CPU를 과도하게 차지한다 | (프로파일이 필요하다 — §8 참조) |

## 3. 기술적 선택

**없다. 이 캠페인은 제품 코드를 한 줄도 바꾸지 않는다.** 형상은 `93f0851` 그대로이고,
앱 2 vCPU / MySQL 2 vCPU·3 GiB도 그대로다. 계측만 추가한다.

## 4. 검증할 주장

> 이 환경에서 앱은 도착 120~360 req/s 구간 안 어딘가에서 **CPU 쿼터 포화로** 처리량이
> 평탄해지고 지연이 비선형으로 꺾이며, 그 순간 DB는 포화되지 않는다.

## 5. 판정 규칙 (사전 등록 — 임계를 미리 못 박는다)

**게이트가 아니라 판정 규칙이다.** 합격/불합격이 아니라 "징후가 있다/없다"를 가른다.

| # | 징후 | 성립 조건 |
|---|---|---|
| P1 (Q1) | 처리량 평탄화 | 인접 계단에서 **도착률은 ≥ 1.2배 오르는데 실제 HTTP req/s는 < 1.05배** |
| P2 (Q1) | CPU 상한 도달 | 그 계단의 앱 **절대 평균 코어 ≥ 1.8** (쿼터 2.0의 90%) 또는 **throttled period 비율 ≥ 10%** |
| P3 (Q2) | knee | 인접 계단에서 (p95 증가율) ÷ (실제 req/s 증가율) 이 **≥ 3배**로 튀는 지점이 존재 |
| P4 (Q3) | 큐·스위치·GC 동반 | knee 계단에서 앱 `cpu.pressure some`의 초당 증가량, `/proc/stat ctxt`의 초당 증가량, JVM live threads 중 **2개 이상이 직전 계단 대비 ≥ 1.3배** |
| P5 (Q4) | 앱만 포화 | knee 계단에서 MySQL 절대 평균 코어 **< 1.0** 이고 MySQL throttled 비율 **< 5%** 이며 `Innodb_row_lock_waits` 증가 **0** |

**CPU에 합격/불합격 임계를 두지 않는다** — 앱·DB 각각의 cgroup 사용량과 스로틀을 정량 보고하고
headroom을 해석한다(직전 캠페인과 같은 원칙, 가이드 §9).

**꼬리 백분위(p95/p99)는 이 저장소의 지표 계약에서 "참고·인용 금지"다**([가이드 A.3](../../../docs/perf/load-test-guide.md)).
그럼에도 P3에 쓰는 이유는 knee 판정이 **절대값이 아니라 같은 라운드 안 계단 간 기울기 변화**이기
때문이다. 그래서 **SLO로 승격하지 않고**, p50 기울기와 함께 읽으며, 단일 라운드임을 명시한다.

## 6. 무효 조건 (사전 등록 — 해당하면 라운드 폐기, 재시도 1회)

| 신호 | 판정 |
|---|---|
| 앱·DB cgroup 절대 코어가 **배정 상한(2.0)을 초과** | 무효 → 재실행 |
| **낮은 계단(120·180)에서 이미** 도착률 결손 > 2% 또는 p50 급등 | 생성기·호스트 경합 서명 → 무효 |
| 라운드 중 컨테이너 재시작·OOM | 무효 → 재실행 |
| 라운드 창에 **인기 점수 배치(`cron 0 30 * * * *`)가 겹침** | 무효 → 재실행 (겹침 여부는 앱 로그로 사후 확인) |

오염된 계단만 잘라내지 않는다. **라운드 전체를 폐기한다.**

## 7. 정확한 시나리오

요청 믹스는 [`2026-08-06_minimal-stability-final/scenarios/stability-300.yml`](../2026-08-06_minimal-stability-final/scenarios/stability-300.yml)과
**완전히 같다** — 바뀌는 축은 도착률 하나뿐이다.

| 계단 | 도착률 (arrivals/s) | 지속 | Artillery 10초 버킷 |
|---|---:|---:|---|
| Warm up | 60 | 30s | 3 |
| S1 | 120 | 30s | 3 |
| S2 | 180 | 30s | 3 |
| S3 | 240 | 30s | 3 |
| S4 | 300 | 30s | 3 |
| S5 | 360 | 30s | 3 |

- **한 도착 = 평균 1.6 HTTP 요청**(커서 2페이지가 붙는 시나리오가 60%). 따라서 **실제 HTTP
  req/s를 도착률과 별도로 반드시 기록한다** — 도착 360이면 HTTP는 약 576/s가 기대값이다.
- 계단을 30초로 잡은 이유는 10초 버킷이 계단 경계를 걸치지 않게 하기 위함이다.
- 라운드 전 워밍업 라운드 1회(120/s·60초)를 돌리고 **판정에 쓰지 않는다**.

## 8. 수집 지표

| 계층 | 도구 | 해상도 | 산출물 |
|---|---|---|---|
| 결과 | `npx artillery` | 10초 버킷 | `results/reports/*.json` |
| 자원(앱) | `tools/collect-app.sh` | **1초** | `*.app1s.tsv` — cgroup `cpu.stat` 전 항목·`memory.current`·`cpu.pressure`, VM `loadavg`/`stat ctxt`/`pressure/cpu` |
| 자원(DB) | `tools/collect-db.sh` | **1초** | `*.db1s.tsv` — 앱과 동일 항목 |
| 자원(JVM) | `tools/collect-jvm.sh` | **1초** | `*.jvm1s.tsv` — live/daemon/peak threads, GC count·sum·max, heap, Hikari |
| 자원(DB 상태) | `tools/collect-mysql-status.sh` | **1초** | `*.dbstat1s.tsv` — threads, 락, tmp disk, buffer pool reads |
| 원인 | `shared/metrics-snapshot.sh` + `tools/digest-snapshot.sh` | 라운드 전/후 | `*.diff` · `digests/*.tsv` |

**1초 수집기는 전부 누계를 그대로 적고, 구간 값은 분석에서 차분으로 만든다.**
시작/종료 누계만으로 계단을 추정하지 않는다.

> `/proc/loadavg`·`/proc/stat`·`/proc/pressure`는 컨테이너가 아니라 **Docker VM 전체**를 본다.
> 앱만의 run queue가 아니므로 **호스트(VM) 경합 프록시**로만 읽는다. 앱만의 CPU 압력은
> 컨테이너 cgroup의 `cpu.pressure`(PSI)로 본다.

### 프로파일(Q5) — 가능성 조사 결과와 처리

앱 이미지가 **JRE 형상**이라 `jcmd`가 없고, `jdk.attach` 모듈도 없으며, BusyBox `nc`는
유닉스 소켓(`-U`)을 지원하지 않아 HotSpot attach 프로토콜을 셸로 구현할 수도 없다.
남는 경로는 `-XX:StartFlightRecording`(= JVM 기동 인자)뿐인데 **컨테이너 재생성이 필요**하고,
그러면 측정 대상인 "지금 워밍업된 앱"이 사라진다. 원자료:
[`results/profile/jfr-capability.txt`](results/profile/jfr-capability.txt).

따라서 **Q5는 미측정으로 보고한다.** actuator/JVM 지표로 특정 작업의 CPU 비중을 추정해
꾸며내지 않는다.

## 9. 알려진 한계 (사전 명시)

- **부하생성기(Artillery)가 측정 대상과 같은 호스트에서 돈다.** Docker VM 11 vCPU 중 컨테이너에
  4가 배정돼 있고 나머지를 생성기·OS가 나눠 쓴다. 그래서 이 캠페인의 수치를 **운영 절대 용량으로
  일반화하지 않는다.** 생성기 자체 포화는 도착률 결손과 VM run queue로 감시한다(§6).
- **단일 라운드다.** 계단 간 비교는 같은 라운드 안이라 조건이 같지만, 라운드 간 재현성은
  증명하지 않았다. 꼬리 백분위를 SLO로 승격하지 않는 이유다.
- **계측 자체가 비용이다.** 초당 actuator 스크레이프 1회(앱 tomcat 스레드 1개 점유)와
  MySQL 상태 질의 1회(커넥션 1개 상주)가 측정 대상 안에서 돈다.
- **Q5(프로파일)는 위 사유로 미측정이다.**

## 9-1. 실행 기록 (측정 후 추가 — §5·§6의 기준은 고치지 않았다)

| 라운드 | 라벨 | 시각 | 상태 |
|---|---|---|---|
| 워밍업 | `warmup` | 16:09:12 | 판정에 쓰지 않음 (JIT·커넥션 예열) |
| **계단** | `sat-step-1` | 16:12:01 ~ 16:15:12 | **유효** — §6의 네 무효 조건 전부 해당 없음 |

**분석 중 정렬 버그를 하나 잡았다.** 처음 만든 창(window)은 Artillery의 **첫 버킷 경계**를
부하 개시 시각으로 썼는데, 실제 첫 요청은 그보다 **9.0초 늦게** 나갔다(Artillery가 프로세스
기동과 함께 첫 버킷을 연다). 그래서 계단 창이 통째로 9초 앞으로 밀려 낮은 계단이 섞였고,
도착률이 69~95%로 **결손난 것처럼** 보였다. 도착 **총계가 계획과 정확히 일치**(37,800 = 37,800)한
것이 단서였다. 정렬 기준을 `firstCounterAt`으로 바꾸고 **계단에 완전히 포함되는 10초 버킷
2개(20초)** 를 대표 구간으로 삼자 전 계단 도착률이 100.0%가 됐다.
결과·자원 지표를 **같은 구간**에서 자른다는 원칙도 이때 확정했다.
