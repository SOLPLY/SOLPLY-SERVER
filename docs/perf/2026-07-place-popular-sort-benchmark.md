## 0. 실험 목적
- "캐시가 정말 필요한가"를 선험이 아닌 실측으로 판단한다.
- v0: 요청마다 DB 집계 (popular-read-mode=db) / v1: 스냅샷 로드 시 1회 집계 (기본값 cache)

## 2. 실행 계획 (EXPLAIN)

`load-test/bench/explain-popular.sql` 결과. V21로 재생성한 `idx_bookmark_target`이 두 경로 모두에서 커버링으로 동작한다.

**v0 직행 쿼리 (상관 서브쿼리)**

| id | select_type | table | type | key | ref | rows | Extra |
|---|---|---|---|---|---|---|---|
| 1 | PRIMARY | \<derived2\> | ALL | NULL | NULL | 435 | Using filesort |
| 2 | DERIVED | p | range | idx_places_town_active | NULL | 435 | Using where; Using index |
| 3 | DEPENDENT SUBQUERY | b | ref | **idx_bookmark_target** | const, p.id | 547 | **Using index** |

→ 기대대로 장소당 인덱스 range scan 1회(커버링). 다만 `DEPENDENT SUBQUERY`는 **바깥 행마다 다시 실행**된다.

**실측: 요청 1건이 훑는 인덱스 엔트리 수**

EXPLAIN의 `rows: 547`은 옵티마이저가 인덱스 통계로 뽑은 **1회 실행당 추정치**이지 실제 개수가 아니다.
`COUNT(*)`는 값별 개수를 저장해두지 않으므로 해당 `(target_type, target_id)` 엔트리를 **하나씩 밟아가며 세야 한다**.
실제로 세어보면:

| 조회 범위 | 장소 수 | 실제 순회 엔트리 | 장소당 평균 |
|---|---|---|---|
| 동네 (102 강남) | 42 | **550,598** | 13,110 |
| 시 단위 (101 서울 = leaf 10개) | 435 | **3,247,626** | 7,466 |

추정치 기반 계산(435 × 547 ≈ 24만)보다 **13.5배** 많다.

부하 믹스를 반영한 목표 부하(100 arrival/s)의 총 요구량:

| 시나리오 | 요청/s | 요청당 엔트리 | 소계 |
|---|---|---|---|
| 동네 (weight 40) | 40 | ~324,763 (동네 평균) | 13.0M |
| 시 단위 (20) | 20 | 3,247,626 | 65.0M |
| 태그 필터 (20) | 20 | ~54,127 (메인 태그 6종 중 1) | 1.1M |
| 스크롤 (20 × 2요청) | 40 | 3,247,626 | 129.9M |
| **합계** | **120** | | **약 2.09억/초** |

> 스크롤 2페이지가 1페이지와 같은 비용인 이유: 커서 조건은 파생 테이블 **바깥**에 적용되므로
> (`WHERE x.cnt < :cursorCount ...`), 안쪽에서는 여전히 모든 장소의 카운트를 계산한다.
> 즉 스크롤 시나리오 하나가 시 단위 요청 2건과 같고, 이 20%가 전체 비용의 62%를 차지한다.

초당 2억 건의 인덱스 엔트리 순회는 4 vCPU로 불가능하다. 이것이 §3 붕괴의 직접 원인이다.

`Using index`(커버링)가 없앤 것은 "엔트리마다 PK로 원본 테이블 행까지 찾아가는 랜덤 접근"이며,
**엔트리를 하나씩 밟는 비용 자체는 남는다**. V21 인덱스는 비용을 크게 낮추지만 0으로 만들지는 못한다.

**스냅샷 로더 집계 쿼리 (IN + GROUP BY)**

| id | select_type | table | type | key | rows | Extra |
|---|---|---|---|---|---|---|
| 1 | SIMPLE | b | range | **idx_bookmark_target** | 373,888 | Using where; **Using index** |

→ 커버링 range scan 1회. 이 비용은 캐시 미스/리프레시 때만 발생(동네당 10분에 1회).

### 3.1 한계점 탐색 — "CPU를 더 주면 되는가"

목표 부하에서 붕괴한 것만으로는 "얼마나 모자란가"를 알 수 없어, 유입률을 낮은 쪽부터 올리며
포화 지점을 찾았다. 각 45초, MySQL 4 vCPU 고정.

> 주의: 이 사다리는 애드혹 측정이라 §3·§4와 달리 Artillery 리포트를 저장하지 않았다.
> 수치는 콘솔 요약에서 옮긴 것이며, 재현하려면 부록의 절차를 유입률만 바꿔 실행하면 된다.

| 유입 | 200 응답 | p99 | MySQL CPU 피크 |
|---|---|---|---|
| 5/s | 268 / 268 (100%) | 518ms | **200%** (4코어 중 2개) |
| 10/s | 546 / 546 (100%) | 1,901ms | **413%** (포화) |
| 20/s | 222 / 940 (24%) | 9,999ms | 428% |
| 30/s | **0** / 1,350 (0%) | — | 408% |

**필요 CPU 추정**: 포화 전 유일한 지점(5 req/s에 2코어)에서 **req/s당 0.4코어**.
선형 외삽하면 목표 100 req/s에는 **약 40코어**가 필요하다. 완벽한 선형 확장을 가정한 **하한**이며,
실제로는 락·컨텍스트 스위칭 오버헤드로 더 든다. 같은 부하를 v1은 **0.57코어**(4코어의 14.2%)로 처리했다 — **약 70배 차이**.

**코어를 늘려도 해결되지 않는 부분**: v0는 CPU가 절반 남는 5 req/s에서조차 p99가 518ms로
v1(19ms)보다 27배 느리다. 요청 1건이 325만 엔트리를 밟는 **절대 시간**은 코어를 늘려도 줄지 않는다.
즉 CPU 증설은 처리량은 사줘도 지연은 사주지 못한다.

**더 중요한 것 — 비용의 증가 방향**:
v0의 요청당 비용은 **북마크 수에 비례**한다. 북마크가 400만 → 800만이면 순회 엔트리도 2배,
필요 코어도 40 → 80개다. 북마크는 DAU × 시간으로 계속 쌓이므로 CPU를 사도 주기적으로 또 사야 한다.
반면 v1의 요청당 비용은 **북마크 수와 무관**하다(스냅샷을 읽을 뿐). 북마크가 10배가 돼도
늘어나는 것은 10분에 한 번 도는 집계 쿼리 시간뿐이다.

→ 결론: 인덱스가 부족했던 것이 아니라(§2에서 보듯 이미 최적 커버링 인덱스),
**매 요청 실시간 집계라는 접근 자체가 이 데이터 규모에서 성립하지 않는다.**

### 4.1 실제 운영 시 필요 CPU 산정

v1 라운드의 시계열(`popular-v1-r1.samples.csv`)에서 뽑은 **순수 소요량**. 컨테이너 100% = 1코어 기준.

| | 평균 | 피크 | 100 req/s 기준 소요 |
|---|---|---|---|
| 앱 | 27.5% | 88.4% | **0.88 코어** (피크 기준) |
| MySQL | 10.5% | 14.2% | **0.14 코어** |
| **합계** | | | **약 1 코어** |

> 앱이 DB보다 6배 더 쓴다. 캐시 도입 후 병목은 DB가 아니라 **앱 쪽 작업**
> (leaf 스냅샷 병합 → 태그 필터 → 정렬 → DTO 변환 → JSON 직렬화)으로 넘어왔다. §6의 할당 지적과 같은 맥락.

**이 수치의 한계 — 그대로 용량 산정에 쓰면 안 된다:**
- 측정 대상은 **장소 리스트 API 하나뿐**이다. 실제 서비스는 북마크·코스·추천·인증 등이 같은 인스턴스에서 돈다.
- 부하 모델의 피크는 120 req/s인데 측정은 100 req/s까지만 했다.
- 피크 88.4%는 **순간값**이라, 실제로는 GC·배포·트래픽 스파이크를 위한 여유율이 더 필요하다.

**여유율·이중화를 반영한 참고치** (이 API 기준, 실제 확정은 전체 엔드포인트 측정 후):

| 항목 | 근거 |
|---|---|
| 앱 인스턴스당 2 vCPU | 피크 0.88코어에 여유율 ~50% → 현재 벤치 스펙(2 vCPU)이 이 API 하나에는 적정 |
| 앱 인스턴스 2대 | 가용성(무중단 배포·장애 격리)상 최소. 단, **v2 다중 인스턴스 이슈 선행 필요** — 인스턴스별 캐시가 독립이라 인기순 순위가 서로 다르게 보일 수 있다 |
| DB 2 vCPU | 이 API는 0.14코어. 나머지 엔드포인트(쓰기 포함)를 고려해도 4 vCPU는 과다 |

→ **이 API만 놓고 보면 총 4~6 vCPU 규모**(앱 2×2 + DB 2)면 목표 부하를 감당한다.
v0였다면 §3.1대로 DB에만 40코어 이상이 필요했다.

## 5. v1' 참고 (배치 비정규화, SQL 수준)

`load-test/bench/denorm-compare.sql` — `places.bookmark_count` 컬럼 + 주기 재계산

| 항목 | 값 |
|---|---|
| 배치 UPDATE 소요 (3회) | 1,090ms / 1,058ms / 1,083ms (평균 ≈ **1.08초**, 1,039행 갱신) |
| 읽기 쿼리 소요 (10회 평균) | **0.81ms** |
| 읽기 EXPLAIN | `type: ALL`, `Using where; Using filesort` — `idx_places_town_bookmark` **미사용** |

해석:
- 배치 비용 1.08초/회는 충분히 저렴하다 (전체 북마크 500만 GROUP BY 1회).
- 다만 `(town_id, bookmark_count DESC)` 인덱스는 **시 단위 조회(town_id IN 10개)에서 정렬에 쓰이지 못한다** —
  여러 town 파티션에 걸친 ORDER BY라 filesort로 흐른다. 장소 수가 1,039개라 지금은 무시할 수준(0.81ms)이지만,
  장소가 수만 개로 늘면 이 인덱스는 시 단위 조회를 도와주지 못한다.
- 즉 v1'은 v0의 병목(상관 서브쿼리 반복)은 확실히 제거하지만, v1이 이미 p99 19ms를 내는 상황에서
  스키마 변경 + 배치 스케줄러 + 신선도 관리 비용을 추가로 지불할 근거는 약하다.

### v1' 채택 시 filesort 회피법 (참고)

복합 인덱스가 정렬에 쓰이려면 선행 컬럼이 **단일값**이어야 한다. `town_id IN (10개)`는 정렬된 구간을
10개 주는 것일 뿐, 이들을 가로지르는 전역 내림차순 경로가 없어 filesort로 흐른다.

회피법은 **동네별 top-K를 각각 뽑아 합친 뒤 다시 정렬**하는 것이다:

```sql
(SELECT id, bookmark_count FROM places WHERE town_id=102 AND active=1
   ORDER BY bookmark_count DESC, id ASC LIMIT 20)
UNION ALL
(SELECT id, bookmark_count FROM places WHERE town_id=103 AND active=1
   ORDER BY bookmark_count DESC, id ASC LIMIT 20)
-- ... leaf 10개
ORDER BY bookmark_count DESC, id ASC LIMIT 20;
```

각 서브쿼리는 `town_id` 단일값이라 인덱스가 정렬에 그대로 쓰이고 20개에서 멈춘다.
최종 정렬 대상은 전체 장소가 아니라 `동네 수 × 페이지 크기` = 200행으로 고정된다.

정당성: 전역 top-20에 드는 장소는 반드시 **자기 동네의 top-20 안에** 있으므로 누락이 없다.
커서 페이징도 각 서브쿼리에 `AND (bookmark_count, id) < 커서` 조건을 더하면 같은 논리로 성립한다.

(대안: `places`에 root town을 `city_id`로 비정규화하고 `(city_id, bookmark_count DESC)` 인덱스를 만들면
단일값 조회가 되어 더 단순하다. 다만 비정규화 컬럼이 하나 더 늘어난다.)

## 6. 후속 확장 시 주의점 (장소 수가 늘어날 때)

이번 측정은 장소 719개(시 단위 조회 시 435개) 기준이다. 장소가 크게 늘 때 **어디가 먼저 꺾이는지**를
미리 정리해둔다. 아래는 실측이 아니라 코드·측정 구조에서 도출한 판단이므로, 실제 임계점은 재측정이 필요하다.

**먼저 걸릴 곳은 정렬이 아니라 요청당 리스트 할당이다.**
정렬 자체는 수백~수만 개 모두 Java 메모리에서 서브 밀리초다. 반면 시 단위 요청은 매번 시 전체 목록을
새로 만든다 — `PlaceService.getPlaces`에서 leaf 스냅샷 병합(①)과 태그 필터 결과(②), 그리고
`PlaceListPaginator.paginate`의 방어적 복사(③)로 **요청 1건당 N 크기 리스트를 3번** 생성한다.

```java
// PlaceService.getPlaces
List<CachedPlace> filtered = CachedPlaceFilter.filter(
    leafTownIds.stream()
        .flatMap(id -> townPlacesCache.getPlaces(id).stream())
        .toList(),          // ① 시 전체 N개
    ...);                   // ② 필터 결과
// PlaceListPaginator.paginate
List<CachedPlace> ordered = new ArrayList<>(places);  // ③ 복사
```

N=435에서는 무시할 수준이지만(§4에서 시 단위 p99 18ms), N이 커지면 정렬 비용보다 이 할당·GC 압력이
먼저 나타난다. v1 라운드에서 앱 CPU가 88%까지 오른 것도 DB가 아니라 앱 쪽 일(병합·필터·정렬·DTO 변환)이
실제로 돌고 있다는 뜻이다.

**수정 방향**: 스냅샷은 이미 정렬된 상태로 캐시에 있으므로, ①에서 leaf별 **상위 K개만 뽑아 병합**하면
§5의 UNION ALL과 같은 원리로 비용이 `O(전체 장소 수)` → `O(동네 수 × 페이지 크기)`가 된다.
단, POPULAR 정렬 기준으로 미리 정렬된 뷰가 스냅샷에 필요하다(현재 스냅샷은 createdAt desc 정렬).

## 7. 판단

**① 사전 집계는 선택이 아니라 필수 — v0(매 요청 실시간 집계) 기각.**
v0의 실용 한계는 약 5 req/s로 목표(100 req/s)의 1/20이다(§3.1). CPU 증설로 메꿀 수 있는 문제도
아니다: 100 req/s에 최소 40코어가 필요하고(선형 가정 하한), CPU가 남는 구간에서도 p99 518ms로
지연은 그대로이며, 비용이 북마크 수에 비례해 계속 자란다. 인덱스는 이미 최적 커버링이었으므로(§2)
남은 개선축이 없다 — **매 요청 실시간 집계라는 접근 자체가 이 데이터 규모에서 성립하지 않는다.**

**② v1(스냅샷 로드 시 집계 내장) 채택 — 프로덕션 기본값 유지.**
목표 부하에서 p99 19.1ms·에러 0·DB CPU 14.2%(§4). 요청당 비용이 북마크 수와 무관해 데이터가
쌓여도 늘어나는 건 10분 주기 집계 1회의 시간뿐이다. 이 API 기준 앱 2대(각 2 vCPU) + DB 2 vCPU면
목표 부하를 감당한다(§4.1).

**③ v1'(배치 비정규화 컬럼) 기각.**
배치 자체는 저렴하지만(1.08초/회), v1이 이미 충분한 상황에서 스키마 변경 + 배치 스케줄러 +
신선도 관리라는 상시 운영 비용을 추가할 근거가 없다(§5). 시 단위 조회에서 정렬 인덱스를 못 타는
한계도 실측으로 확인했다. **단, 캐시 계층 없이 DB 단독으로 서빙해야 하는 제약이 생기면 1순위 대안**
— 그 경우 §5의 UNION ALL 패턴으로 filesort를 회피한다.

**④ 인기순 순위의 최대 10분(soft TTL) stale 수용.**
누적 북마크 랭킹은 집단 행동의 누적값이라 개인이 즉시 반영을 기대하는 데이터가 아니다.
개인 체감이 필요한 read-your-writes 경로(내 북마크 여부·목록)는 캐시를 타지 않고 DB 직행이므로
영향 없다. 실시간 반영이 필요한 "최근 급상승" 기능은 별도 설계로 분리한다(후속 소재).

**⑤ 확장 임계점은 기록만, 선제 대응은 하지 않는다 (YAGNI).**
장소 수가 수만 단위로 늘면 병목은 정렬이 아니라 요청당 리스트 할당·GC 압력이며(§6),
그때의 수정 방향(leaf별 top-K 병합, POPULAR 사전 정렬 뷰)을 §6에 남겨뒀다.
현 규모(시 단위 435개)에서는 실측상 문제가 없어 지금 손대지 않는다.

**후속(별도 플랜):**
- v2 다중 인스턴스 — 인스턴스별 캐시 독립으로 인한 순위 불일치·중복 집계·무효화 전파를 실측하고
  L1+pub/sub vs L1+L2 계층화를 결정 (②의 "앱 2대" 구성의 선행 과제)
- 최근 급상승 Top N (트렌딩) — 시드에 심어둔 시간 축 편향 데이터 활용
