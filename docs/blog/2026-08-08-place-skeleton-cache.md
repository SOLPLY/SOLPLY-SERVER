## 1. 피크 부하보다 20%만 더 오면 서버가 버티지 못했다

먼저 "얼마나 버텨야 하는가"를 정했다. 임의로 고른 숫자가 아니라 규모 가정에서 나온 값이다.

```
  DAU 200,000        성공 시나리오. 1인 가구 타깃 지역 서비스에서 잡을 수 있는 상한급
× 인당 30건/일        인기순이 홈 기본 정렬이라 진입마다 발생 + 무한 스크롤
÷ 86,400초           = 평균 70 req/s
× 피크 계수 5         여가 서비스라 저녁·주말에 몰린다
──────────────────────────────────────────────
= 목표 300 req/s      인기순 조회 경로 단독
```

가정 넷 중 **DAU와 피크 계수는 근거가 약하다.** 운영 데이터가 없어 업계에서 통용되는
범위를 따랐을 뿐이다. 그래서 이 숫자는 "반드시 맞는 목표"가 아니라 **"어디까지 버티는지
재기 위한 기준선"**으로 쓴다. 뒤에 나오는 절감 수치는 전부 실측이라, 이 가정이 흔들려도
같이 흔들리지 않는다.

**부하 도구에는 req/s가 아니라 "초당 유입 사용자" 수로 설정한다.** 사용자 한 명이
시나리오를 타며 평균 1.6개를 요청하므로 이렇게 대응된다.

```
초당 유입 사용자 300명  →  전체 480 req/s  →  그중 인기순 345 req/s  (목표 300보다 15% 위)
```

부하를 req/s 단위로 올리지 않는 이유가 있다. **서버가 한계를 넘으면 처리량이 오히려
줄기 때문**이다. 실제로 뒤에서 같은 부하(480명)에 캐시 없음은 720.1 req/s, 캐시는
767.3 req/s가 나온다. **거는 값**과 **나온 값**을 같은 단위로 부르면 둘을 구분할 수
없다. 그래서 부하는 유입 사용자 수로 올리고, req/s는 결과 지표로만 쓴다.

이 설정으로 부하를 올려 보니 이렇게 나왔다.

```
초당 유입 사용자 300명   ← 여기까지는 버텨야 한다. 버텼다 (p50 6ms)
초당 유입 사용자 360명   ← p50이 156ms로 꺾인다

한계까지 남은 여유 = 1.2배
```

**실제 트래픽은 평균으로 오지 않는다.** 점심시간에 몰리고, 푸시 알림 한 번 보내면 순간
몇 배가 뜬다. 20% 여유는 사실상 여유가 없는 것이고, 하필 사람이 가장 많은 순간에 장애가 난다.

왜 360명에서 못 버티는지부터 찾아야 했다.

## 2. 원인을 어떻게 좁혔나

**부하와 함께 치솟은 지표는 앱 컨테이너의 CPU 스로틀 비율이었다.** 응답시간이 꺾인
유입 360명 구간에서 66.0%. 이 지표가 무엇인지가 이 글의 절반이라 먼저 설명한다.

앱은 도커 컨테이너로 띄우고 CPU를 2코어로 제한해 뒀다. "2 vCPU급 스펙에서 어디까지
버티나"에 답하려면 스펙이 고정돼야 하고, 같은 호스트에 MySQL이 있어 앱이 코어를 다
가져가면 병목이 어디인지 가릴 수 없기 때문이다. 그런데 도커의 CPU 한도는 "코어 2개짜리
기계"를 만들어 주는 것이 아니다. 리눅스 CFS 스케줄러가 집행하는 **배급**이다.

```
cpu.max = 200000 100000
  주기 100ms  ← 배급 단위 시간. 1초에 10개
  쿼터 200ms  ← 창 하나에서 쓸 수 있는 CPU 시간 (코어 2개 × 100ms)
```

CFS는 CPU를 **100ms짜리 창으로 끊어서 배급한다.** 창 안에서 쿼터 200ms를 다 쓰면 남은
시간 동안 그 컨테이너의 스레드가 전부 멈춘다. 그리고 **안 쓰고 남긴 쿼터는 다음 창으로
넘어가지 않는다.** 스로틀 비율은 이렇게 잘린 창의 비율이다. 66.0%면 1초에 오는 창 10개
중 6~7개에서 스레드 전체가 멈춰 섰다는 뜻이다.

**(1) 평균 CPU부터 확인했다. 여유가 있어 보였다.** 같은 부하를 건 다른 라운드에서
20초 평균은 1.73코어, 쿼터의 87%였다. 평균만 보면 13%가 남는데 **창의 35.4%가 잘렸다.**
1초 단위로 펼치면 이유가 보인다(둘째 줄은 그 1초의 창 10개 중 잘린 개수).

```
초당 앱코어 : 1.96 1.93 1.85 1.82 1.77 1.53 1.52 1.48 1.59 1.59 1.61 1.63 1.70 1.68 2.05 1.99 1.84 1.65 1.72
잘린 창     :   10   11    6    5    4    0    0    0    0    0    1    0    2    0    9   10    8    0    2
```

앞 5초와 15~17초에 몰려 있고 그 사이 9초는 거의 안 잘린다. 한가한 순간이 남긴 쿼터는
몰리는 순간을 메워 주지 못하므로, **20초 평균이 말하는 "13% 여유"는 실제로는 어느
순간에도 없었던 상태다.**

**(2) 한도가 문제인가, 수요가 문제인가.** 스로틀이 높을 때 가능한 해석은 둘이고,
처방이 정반대라 여기서 갈라야 했다.

- **순간 편중이 문제인 경우.** 평균 수요는 쿼터에 한참 못 미치는데, 요청이 몰리는
  순간에만 창이 잘리는 상태다. CPU가 모자란 것이 아니라 100ms 단위 배급이 순간
  수요를 못 따라가는 것이므로, **한도를 올리거나 아예 푸는 것이 정답이고 코드는
  고칠 것이 없다.** 전용 인스턴스에 컨테이너 하나를 올릴 때 한도를 걸지 않고 기계의
  코어를 그대로 쓰게 두는 실무 관행이 이 판단이다. 지킬 이웃이 없는데 한도를 걸면
  이 낭비만 생긴다.
- **수요 초과가 문제인 경우.** 요청들이 쓰는 CPU 총량 자체가 쿼터에 닿는 상태다.
  수용량은 결국 "코어 수 ÷ 요청당 CPU"인데, 한도를 풀어도 분자가 물리 코어로 커질
  뿐이다. 근본적으로는 코어를 더 사거나(증설), 요청당 CPU를 줄여야(설계) 한다.

둘은 **평균 수요가 쿼터 대비 어디에 있는지**로 가른다. 실측은 이랬다.

| 초당 유입 사용자 | 평균 CPU 수요 | 잘린 창 |
|---:|---:|---:|
| 300 (목표) | 쿼터의 75% | 13.5% |
| 360 (목표의 1.2배) | **쿼터의 95%** | 66.0% |

목표 부하만 보면 편중이 실재한다. 평균으로 25%가 남는데도 창의 13.5%가 잘렸다.
하지만 응답시간이 꺾이는 360명에서는 **평균 수요 자체가 쿼터의 95%에 닿는다.**
편중은 잘리는 시점을 앞당기는 부차 요인이고, 못 버티는 지점의 주범은 수요다.
한도를 올리거나 푸는 것은 이 수요를 그대로 둔 채 그릇만 키우는 일이라, 여기서는
증설과 같은 선택이 된다. 그래서 다음 질문은 "그 수요는 어디서 오는가"가 됐다.

**(3) DB인가? 아니다.** 같은 부하에서 앱 스로틀 66.0% 대 MySQL 1.0%다.
디스크 읽기·락 대기·임시 테이블 전부 0, 버퍼풀 적중 100%였다.

**(4) 병목이 CPU라는 교차 확인.** 코드는 그대로 두고 CPU 쿼터만 2에서 4 vCPU로 올린
대조 라운드를 돌렸더니 스로틀 18.2% → 0.8%, p99 391.6ms → 59.7ms로 떨어졌다.
CPU만 늘려도 낫는다면 병목은 CPU가 맞다. 동시에 이 라운드는 (2)의 결론을 다시
보여준다. 코어를 두 배로 사면 낫는다. 문제는 그것을 사지 않고 얻는 것이 이 작업의
목표라는 점이다.

**(5) 그 CPU는 무슨 일에 쓰이나? JFR로 프로파일링했다.** 병목의 위치는 확정됐으니
이제 내용물이 필요하다. API 요청 하나를 처리하는 동안 앱 CPU가 쓰이는 일은 대략
정해져 있다. HTTP를 파싱하고, 인증 필터를 지나고, 쿼리를 만들어 보내고, DB가 일하는
동안은 기다리다가(이때 CPU는 거의 안 쓴다), 돌아온 행들을 파싱해 객체로 조립하고,
로직을 돌린 뒤 JSON으로 직렬화해 내보낸다. 이 중 어느 단계가 비싼지는 코드를
읽어서는 알 수 없고, 재야 안다.

JFR(Java Flight Recorder)은 JVM에 내장된 프로파일러다. 10ms마다 "지금 CPU에서 돌고
있는 스레드가 어느 코드 위에 있나"를 호출 스택째로 찍는다. 스택이 통째로 남기 때문에
그 순간 실행되던 메서드 하나가 아니라 "컨트롤러 → 서비스 → Hibernate → 드라이버"처럼
어느 경로를 타다가 잡혔는지까지 알 수 있고, 수백 장을 모으면 경로별 등장 비율이 CPU
시간의 배분에 가까워진다. DB 응답을 기다리며 잠든 스레드는 표본에서 제외했으므로
아래 비율은 대기가 아니라 실제로 CPU를 태운 일이다. 목표 부하(300명)와 응답시간이
꺾인 360명에서 한 번씩 떴다.

| 스택에 그 경로가 포함된 샘플 비율 | 300명 | 360명 |
|---|---:|---:|
| Hibernate (쿼리 실행과 엔티티 조립) | 20.8% | 22.3% |
| MySQL 드라이버 (행 수신·파싱, 위 몫과 겹침) | 13.0% | 12.7% |

가장 큰 묶음이 "DB에서 읽어 엔티티로 만드는 경로"였고, 부하가 달라도 비율이 비슷하니
우연한 스냅샷이 아니다. 그다음은 Spring Data 5% 안팎, Spring Security 3% 안팎,
JSON 직렬화(Jackson) 2% 안팎으로 뚝 떨어진다. 그런데 가장 큰 묶음 안의 단일 메서드는
어느 것도 6.1%를 넘지 않았다. 핫스팟 하나를 고쳐서 될 일이 아니라 비용이 경로 전체에
얇게 발려 있어서, 줄이려면 **그 경로를 아예 타지 않게 만들어야 하는** 모양이었다.

나머지 CPU가 개선 불가능한 것은 아니다. 표적이 못 됐을 뿐이다. 프레임워크 고정비는
개별 몫이 5% 이하라 걷어내는 공사에 비해 얻는 것이 작다. 후보가 하나 더 있긴 했다.
실행 JAR의 리소스 URL 처리가 CPU 샘플의 10% 안팎을 차지했고, 그 조회 캐시의 락 앞에서
스레드가 20ms 이상 기다린 사건도 반복해서 잡혔다. 하지만 이 녹화는 스택을 5프레임에서
잘라 어떤 요청 코드가 리소스 조회를 촉발하는지 가려낼 수 없었고, 그래서 후속 프로파일
표적으로만 남겼다. 지금 없앨 것은 가장 크면서 없앨 방법이 분명한 덩어리다.

**(6) 그 경로를 코드에서 특정했다.** 목록 한 페이지에 SELECT 6개가 나가는데,
그중 둘이 **장소마다 변하지 않는 값**(이름·썸네일·대표 태그명·동네)을 읽고 있었다.
매 요청 같은 답이 나오는 쿼리다.

문제는 쿼리 2회의 왕복이 아니라 **그 결과를 객체로 조립하는 일**이었다.
태그를 페치 조인하면 장소 1건이 태그 수만큼 행으로 펼쳐져, 27컬럼짜리 결과가
실행당 35.6행으로 늘어난다.

```
27컬럼 × 35.6행  →  요청 하나가 컬럼을 약 960번 꺼낸다
그중 문자열 컬럼은 꺼낼 때마다 새 String이 만들어진다  →  요청당 약 280개
응답이 실제로 쓰는 문자열은 name 하나다.

여기에 Place 10개 + PlaceTag 35.6개 + PlaceImageInfo 9.88개 + 컬렉션 래퍼 40개,
그리고 영속성 컨텍스트 등록과 프록시가 매 요청 만들어졌다 버려진다.
```

**객체를 만드는 것 자체는 비싸지 않다.** JVM에서 객체 하나는 TLAB 포인터를 옮기는 일이라
나노초 단위다. 비싼 것은 **그 객체를 채우는 과정**, 즉 컬럼을 꺼내고, 타입을 바꾸고,
영속성 컨텍스트에 등록하고, 프록시와 컬렉션 래퍼를 엮는 일이다.
객체 개수는 그 일이 얼마나 많은지 보여주는 숫자일 뿐 그 자체가 원인은 아니다.

> **정리: 매 요청 같은 답이 나오는 값을 매번 DB에서 읽어 객체로 조립하고 있었다.
> 그 조립이 요청당 CPU를 키우고, 커진 요청당 CPU가 창을 자르고, 잘린 창이 대기를 만든다.**

그래서 증명할 주장을 **"요청당 앱 CPU를 줄인다"**로 잡았다. 응답시간은 목표 부하에서
이미 p50이 한 자릿수 ms라 판정 지표에서 뺐다.

## 3. 해결안을 고른 과정

고르기 전에, 이미 쓰고 있던 것 하나를 구분해 둔다. `@Transactional(readOnly = true)`는
조회 서비스에 진작부터 붙어 있었다. readOnly는 하이버네이트가 변경 감지용 스냅샷을 만들지
않게 해 주는데, 위의 요청당 CPU는 전부 그 상태에서 잰 값이다. 남아 있던 비용은 readOnly가
건드리지 못하는 컬럼 추출·영속성 컨텍스트 등록·프록시 쪽이다.

후보는 싼 수단부터 검토했다. 설정만 바꾸는 방법, 코드를 고치는 방법, 상태(캐시)를
들이는 방법 순이다.

| 안 | 없앨 수 있는 것 | 판단 |
|---|---|---|
| CPU 한도 상향·제거 | 스로틀 (조립 작업은 그대로) | **보류.** 2장 (2)에서 가른 대로 평균 수요가 쿼터에 닿는 상태라, 한도 조정은 수요를 둔 채 그릇을 키우는 증설이다. 효과 자체는 (4)의 대조 라운드로 확인됐으니 마지막 수단으로 남겼다 |
| DTO 직접 프로젝션 | 조립 작업 대부분 (쿼리 2개는 남는다) | 장소 단위 캐시와 3.1에서 직접 비교했다 |
| 요청 결과 캐시 (요청 파라미터를 키로 그 페이지의 장소 id 목록을 저장) | 정렬 쿼리 1개 | **기각.** 키가 동네 19 × 태그조합 1,025 × 정렬 2 ≈ 39,000이고 커서 축이 무한히 붙는다 |
| **장소 단위 캐시** | **조립 작업 전체 + 쿼리 2개** | **채택.** 키가 장소 수 6,320에서 멈춘다 |

요청 결과 캐시가 응답을 통째로 담지 못하고 id 목록에 그치는 이유가 있다. 응답에는
사용자마다 다른 북마크 여부와 매시 바뀌는 카운트가 섞여 있다. 그렇게 남는 정렬 쿼리
1개는 `place_stats` 커버링 인덱스 하나로 끝나는 **가장 싼 쿼리**라 없애서 얻을 것이
적고, 키는 요청 파라미터를 따라가느라 조합만큼 는다. 반대로 키가 데이터(장소)를
따라가면 장소 수에서 멈추고, 원인으로 지목한 조립 작업을 정확히 없앤다.

### 3.1 프로젝션이면 충분한가, 캐시까지 가야 하나

프로젝션은 캐시보다 싼 수단이다. 상태를 만들지 않으니 stale해질 일도, 워밍업할 것도
없다. 그래서 이 둘은 말로 가르지 않고 직접 쟀다. 같은 빌드에 세 방식(기존 엔티티 경로,
프로젝션, 장소 단위 캐시)을 넣고 설정으로 갈아 끼우며, 목표 부하에서 방식을 교대해
3라운드씩 돌렸다. 프로젝션은 캐시 스냅샷을 만들 때와 같은 SQL과 조립 코드를 페이지
id로만 돌리므로, 엔티티와의 차이는 하이드레이션 몫, 캐시와의 차이는 쿼리 왕복 몫으로
읽을 수 있다.

| 요청당 | 엔티티 | 프로젝션 | 캐시 | 비고 |
|---|---:|---:|---:|---|
| 힙 할당 | 1,005 KB | 761 KB | 696 KB | 라운드 산포 2.0%, 확정 |
| 앱 CPU | 2.40 ms | 1.92 ms | 1.88 ms | 산포 11~22%, 점추정 |
| DB CPU | 1.75 ms | 1.65 ms | 1.37 ms | |
| 커넥션 점유 | 3.36 ms | 2.36 ms | 1.88 ms | |

앱 CPU만 보면 절감의 대부분을 프로젝션이 가져간다. 원인으로 지목한 조립 작업을 없애는
것이 전부라면 프로젝션으로 충분하다는 뜻이고, 프로젝션과 캐시의 앱 CPU 차이(1.92 대
1.88ms)는 산포 안이라 이 둘을 앱 CPU로 가를 수는 없다.

캐시를 고른 근거는 그 옆 두 줄이다. 남은 쿼리 2개까지 없애면 **DB CPU가 17%, 커넥션
점유가 20% 더 줄어든다.** 커넥션 점유는 서버가 못 버티는 구간에서 상황을 키우던
항목이다. CFS가 창을 자르면 커넥션을 쥔 스레드도 함께 멈춰 반납이 늦어지고, 풀에서
기다리는 요청이 늘어난다(4장). 그리고 캐시는 5필드를 만드는 일 자체를 요청에서 떼어내
배치 주기당 1회로 줄인다. 프로젝션은 그 일이 싸졌을 뿐 여전히 요청마다 한다.

캐시 대상은 **장소마다 변하지 않는 5개 필드**로 정했다.

```
id, name, imageUrl, mainTagName, townId
```

북마크 수·리뷰 수·평점은 넣지 않았다. 정렬 쿼리가 커버링 인덱스로 이미 함께 실어오기
때문이다. `isBookmarked`도 넣지 않았다. 사용자마다 다른 값이기 때문이다.

### 3.2 캐시 라이브러리를 쓰지 않았다

Caffeine이 이미 `build.gradle`에 있었지만 쓰지 않고 스프링 빈 하나로 만들었다.

```java
private volatile Map<Long, PlaceSkeleton> map = Map.of();
```

라이브러리가 푸는 문제가 이 데이터에는 없었기 때문이다.

| Caffeine 기능 | 이 캐시에 필요한가 |
|---|---|
| `maximumSize`, eviction | 크기가 장소 수 6,320으로 고정이라 트래픽이 늘어도 자라지 않는다 |
| TTL, `refreshAfterWrite` | 갱신 주체가 배치 하나다. 배치가 교체하는 것이 곧 만료다 |
| `LoadingCache` | 미스해도 기존 경로 그대로다. 최악이 캐시 없는 상태와 같다 |

반대로 **불변 Map을 통째로 갈아 끼워야만 얻는 것**이 둘 있다. 참조 대입 한 줄이라 교체하는 동안
미스가 생길 틈이 없고, 새 Map을 만드니 사라진 장소가 자동으로 빠진다. Caffeine이라면
`invalidateAll()`과 `putAll()` 사이에 6,320개짜리 미스가 몰리고, `putAll()`만 하면
삭제된 장소가 남는다.

**전량을 들고 있기로 했으니 메모리를 따져야 했다.** compressed oops 기준으로
객체 레이아웃을 계산하면 엔트리 1건이 290 B다. `PlaceSkeleton` 40 B(헤더 12 + `long` 2개
+ 참조 3개), `Long` 키와 Map 슬롯 40 B, 문자열 3개 210 B를 더한 값이다.
**6,320개에 1.75 MiB, 힙 상한 1.25 GiB의 0.14%.** 나중에 힙덤프로 실측했더니 계산과 맞았다.

### 3.3 무효화 코드를 쓰지 않고 배치에 태웠다

갱신 시점 후보는 둘이었다.

- 장소·태그를 고치는 관리자 경로 6곳에 무효화를 건다
- 매시 카운트 배치가 끝난 직후 스냅샷을 통째로 바꾼다

두 번째를 골랐다. 이 시스템은 **장소 메타데이터가 최대 1시간 stale인 것을 이미 허용하고**
있었기 때문이다. 인기순의 기준 테이블이 `place_stats`이고 그 행 집합을 만드는 주체가
같은 배치다. 캐시가 stale 구간을 새로 만드는 것이 아니라 이미 허용된 구간에 올라타는 것이다.

무효화 지점을 6곳 두면 하나를 빠뜨렸을 때 그 장소는 조용히 영원히 stale로 남는다.
배치 교체는 최악이 "1시간 늦게 반영"이고 무효화 코드가 0줄이 된다.
서버가 뜰 때는 트래픽을 받기 전에 미리 만들어 둔다(6,320개에 302ms, 버퍼풀이 따뜻하면 94ms).

### 3.4 미스로 읽은 값을 캐시에 넣지 않는다

전 엔트리가 같은 배치 회차에서 나와야 **"지금 캐시는 몇 시 사진"**이라고 한 문장으로
말할 수 있다. 개별 값을 끼워 넣으면 엔트리마다 시점이 달라져 그 말이 성립하지 않는다.

넣지 않아도 손해가 없다. 다음 배치가 어차피 채우고, 그전까지 미스 비용은 캐시 도입 이전과
똑같은 **쿼리 2회**다(장소 조회 + 이미지 지연로딩). `@BatchSize(50)`가 최대 페이지 크기와
맞춰져 있어 지연로딩이 페이지당 1회로 고정되므로, 미스가 몇 건이든 이 값은 변하지 않는다.

## 4. 결과

같은 빌드에서 설정 하나로 캐시를 켜고 끄며 초당 유입 사용자를 120명에서 480명까지
30초씩 올렸다. 두 방식 각각 3라운드를 돌려 중앙값을 썼다. 페이지 크기는 앱 기본값 10이다.

**먼저 응답이 같은지부터 확인했다.** 요청 5종의 응답 body와 커서 토큰이 두 방식에서 동일했다.
이게 깨지면 나머지 수치는 의미가 없다.

**① 원인으로 지목한 것이 실제로 사라졌나** (`performance_schema` digest)

| | 캐시 없음 | 캐시 |
|---|---|---|
| 장소 엔티티 조회(태그 페치조인) | 103,566회 | **0회** |
| 이미지 지연로딩 | 103,492회 | **0회** |
| 요청당 SELECT | 5.99 | **4.00** |
| 요청당 힙 할당 | 1,036 KiB | **721 KiB** |

0회는 미스가 한 건도 없었다는 뜻이다. 할당이 30% 줄어든 것이 조립 작업이 사라진 몫이다.

**② 증명하려던 주장, 요청당 앱 CPU** (각 칸은 **캐시 없음 → 캐시** 순이다)

부하는 세 지점으로 읽는다. 평상 수준, 버텨야 하는 목표 피크, 그리고 목표를 넘는 여유
구간이다. 전체 계단 수치는 근거 문서에 있다.

| 초당 유입 사용자 | 요청당 앱 CPU | 앱 스로틀 | p50 |
|---:|---|---|---|
| 120 (평상 수준) | 2.374 → 2.095 ms | 0.0% → 0.0% | 4 → 3 ms |
| **300 (목표 피크)** | **2.576 → 1.920 ms (−25.5%)** | 4.2% → 3.1% | 5 → 4 ms |
| 480 (목표의 1.6배) | 2.776 → 2.218 ms | **100% → 13.8%** | **5,827 → 5 ms** |

라운드 전체 실패가 캐시 없음 9,395 / 1,574 / 0건에서 캐시 **0 / 0 / 0건**이 됐고,
최대 처리량은 720.1에서 **767.3 req/s**로 늘었다.
DB 부하는 줄이려던 대상이 아니었는데 함께 줄었다(목표 부하에서 DB 코어 0.895 → 0.720).

평상과 목표에서는 사용자가 겪는 차이가 거의 없다. 애초에 거기까지는 버티고 있었다.
갈리는 곳은 셋째 줄이다. 캐시 없는 쪽은 창이 전부 잘리며 p50이 초 단위로 늘어졌고,
캐시 쪽은 스로틀 13.8%에 p50 5ms를 지켰다. 요청당 0.65ms를 줄인 효과는 평균을 조금
낮추는 것이 아니라, 2장의 메커니즘 그대로 **창 하나가 쿼터를 다 써서 잘릴 확률을
낮추는 것**이다. 창이 잘리지 않으면 그 뒤에 줄줄이 딸려오던 대기가 통째로 사라진다.

**③ 혹시 다른 원인은 아니었을까**

- **GC가 준 것 아닌가.** 목표 부하에서 아낀 CPU가 6,249ms인데 GC 멈춤 시간 차이는 14ms,
  **0.22%**다. 자릿수가 두 자리 어긋난다. 아낀 것은 GC가 아니라 조립 작업 그 자체다.
- **커넥션 풀이 작았던 것 아닌가.** 서버가 버티지 못하던 구간에서 HikariCP `pending`이 38까지 올라
  풀(10개)이 작아 보인다. 아니다. 커넥션 점유 시간이 2.26ms에서 9.4ms로 늘었는데
  **SQL은 그대로였고 그 시각 DB는 스로틀 0%·락 대기 0**이었다. CFS가 창을 자를 때
  커넥션을 쥔 스레드도 함께 멈춰 반납이 늦어진 것이다. 커넥션 타임아웃은 전 라운드 0건이었다.
  **모자란 게 아니라 늦게 돌아온 것**이다. 풀을 키웠다면 코어 2개를 더 잘게 나눠 쓰게 되어
  오히려 나빠졌을 것이다.

## 5. 남은 것

- **캐시를 켠 쪽의 천장을 모른다.** 초당 유입 사용자 480명(767.3 req/s)까지 걸어도 버텼다.
  다만 거기서도 스로틀이 0은 아니다(13.8%). 판정 기준은 목표 부하에서의 여유(3.1%)이고,
  목표 위 구간의 수치는 여유 확인이지 보장이 아니다.
- **요청당 SELECT 4개가 남았다.** `towns`와 `tags`는 작고 거의 변하지 않는 참조 데이터라
  Caffeine `LoadingCache`로 없앨 수 있고, `place_stats`는 목록의 내용을 결정하므로 어렵고,
  북마크 여부는 사용자별이라 못 없앤다.
- **전량 상주는 장소 수가 고정에 가깝다는 전제 위에 있다.** 엔트리당 290 B라 10만 장소면
  29 MB로 아직 들어가고, 그 위로 가면 `maximumSize`와 `refreshAfterWrite`로 자주 찾는
  장소만 남기는 쪽이 맞다.
- **3.1의 앱 CPU 두 몫은 점추정이다.** 호스트 상시 부하로 라운드 산포가 11~22%까지 벌어져,
  방향은 힙 할당(산포 2.0%)과 쿼리 수로 확정했고 ms 단위 몫은 자릿수만 읽어야 한다.
- **A/B의 세 라운드는 독립 반복이 아니었다.** 커넥션을 얻기까지 기다린 시간이 캐시 없음
  29.3 → 27.7 → 24.1ms, 캐시 14.8 → 2.8 → 0.4ms로 두 방식 모두 라운드를 거듭할수록
  예외 없이 줄었다. 무엇이 계속 데워지는지는 규명하지 못했다. 3.1의 세 방식 비교에서는
  방식을 교대하고 라운드마다 JVM을 새로 띄워 이 순서 효과를 상쇄했다.
