# 장소 목록의 메모리 조회 모델과 갱신·Heap·GC 설계

작성일: 2026-09-09 · 구현 기준: 2026-09-13

솔플리의 장소 목록은 동네와 태그로 후보를 좁히고, 선택한 순서로 한 페이지를 반환한다.
여러 사용자가 공유하는 정렬·필터 데이터를 메모리에 두면 요청마다 전체 장소를 읽고 정렬할
필요가 없다. 대신 서버는 조회 데이터를 상주시켜야 하고, 원본이 바뀔 때마다 그것을 다시 짓는
과정에서 CPU·메모리·DB 비용을 부담한다.

이 글은 현재 조회 자료구조와 관리자 수정이 반영되는 경로, 객체 수명과 측정 범위를 다룬다.
여러 서버가 같은 상태로 수렴하는 절차와 요청이 어느 회차로 답하는지는
[번호 둘로 맞추는 인스턴스별 스냅샷 구조](2026-09-10-distributed-inmemory-snapshot-architecture.md)에
정리한다.

## 1. 한 요청이 어떤 상태를 읽는가

장소 목록에는 모든 사용자가 공유하는 값과 요청마다 달라지는 값이 함께 있다.

| 값 | 조회 위치 |
|---|---|
| 장소의 소속 동네·좌표·태그 비트마스크·정렬 키 | 이 서버의 Snapshot |
| 장소 이름·썸네일 파일 키·대표 태그 ID | PlaceViewHolder |
| 태그 이름·활성 상태 | TagViewHolder |
| 동네 범위와 전달된 태그 조건의 유효성 | MySQL |
| 공유 cursor_version | MySQL, 메모리 목록 요청마다 한 행 |
| 해당 사용자가 이번 페이지의 장소를 북마크했는지 | MySQL |

따라서 메모리 조회 모델을 쓴다고 요청 전체에서 DB 접근이 없어지는 것은 아니다. 일반 장소
목록은 조건 검증 뒤 메모리에서 페이지를 고르고, 사용자별 북마크 여부를 붙인다. 내 북마크만
조회하는 요청은 별도의 DB 조회 분기를 쓴다.

다음은 `PlaceService`가 페이지를 한 번 구성하는 흐름이다. 이 서버가 공유 회차에 뒤처졌는지
판정하고 기다리는 일은 이 바깥의 요청 조정 단계가 맡는다.

```text
요청 조정 단계
  → 동네 범위·태그 조건·정렬·필터·커서 형식 검증 (페이지는 만들지 않는다)
  → 공유 cursor_version 조회, 이 서버의 설치 회차와 비교
  → 답할 수 있으면 아래로, 뒤처졌으면 리빌드에 합류해 기다렸다가 아래로

페이지 구성
  → 이 서버의 Snapshot 참조를 한 번 확보
  → 커서의 회차가 그 Snapshot의 회차와 다르면 만료
  → 같은 참조로 후보 탐색·필터링·페이지 추출
  → 표시 홀더에서 이름·이미지 키·태그 이름 조회
  → MySQL에서 페이지 내 사용자 북마크 여부 조회
  → 목록·이미지 URL·다음 커서 반환
```

각 페이지 구성은 확보한 Snapshot으로 끝까지 정렬·필터·커서 경계를 계산한다. 갱신 도중 다시
최신을 읽어 한 페이지에 서로 다른 정렬 상태가 섞이지 않게 한다. 썸네일은 파일 키로 CloudFront
URL을 조합해 반환하고, 이미지 다운로드는 클라이언트가 별도로 수행한다.

표시값은 Snapshot 밖에서 읽는다. 따라서 **정렬·필터 기준은 요청이 확보한 상태로 고정되지만,
표시값까지 같은 시점으로 고정되는 것은 아니다.** 표시 홀더와 Snapshot은 서로 다른 참조이며,
세 참조의 교체가 모든 독자에게 하나의 원자적 교체로 보인다는 보장은 없다. 커서의 계약도
그대로다. 커서는 정렬 순서의 일관성을 보장하고, 표시값과 소속은 최신 값일 수 있다.

## 2. 상주 자료구조와 페이지 탐색

```text
SnapshotBox
  └── 최신 Snapshot 한 벌 (volatile 참조 하나)
        ├── revision:      이 스냅샷이 읽은 원본 시점
        ├── cursorVersion: 이 스냅샷이 발급하는 커서의 회차
        └── SortedPlaces
              └── 정렬 종류 → 동네 ID → PlaceEntry 참조 배열

PlaceEntry
  └── 장소 ID·동네·태그 비트마스크·좌표·정렬 키와 표시 통계

PlaceViewHolder
  └── 장소 ID → 이름·썸네일 파일 키·대표 태그 ID

TagViewHolder
  └── 태그 ID → 이름·활성 상태
```

스냅샷은 한 장만 든다. 옛 회차를 몇 장 보존해 만료 창을 늘리는 장치는 없고, 커서가 지금 회차의
것이 아니면 만료로 끊어 클라이언트가 최신 목록에서 다시 시작한다. 이미 스냅샷을 잡은 요청은
그 참조로 끝까지 간다.

장소 하나의 `PlaceEntry`를 여러 정렬 배열이 참조한다. 같은 장소의 값 객체를 정렬 축마다
복제하는 방식이 아니다. 배열은 정렬 순서를, 엔트리는 장소의 값을 표현한다. 배열 원소에는
비교와 스캔이 읽는 값(정렬 키·좌표·태그 비트)만 두고, 표시값은 홀더에 둔다.

정적 정렬은 동네별로 미리 정렬한 배열을 사용한다. 커서가 있으면 정렬 키와 장소 ID를 비교해
다음 위치를 이진 탐색하고, 그 위치부터 태그 조건을 적용한다.

```text
한 동네
  → 커서 다음 위치 탐색
  → 배열을 순서대로 읽으며 태그 필터 적용
  → 페이지 크기 + 1개 확보 또는 후보 소진

여러 동네
  → 각 동네에서 커서 다음 위치 탐색
  → 동네별 다음 후보 하나씩 우선순위 큐에 넣기
  → 전체에서 가장 앞선 후보를 꺼내 필터 검사
  → 그 후보가 나온 동네의 위치를 전진시켜 다음 후보 추가
  → 페이지 크기 + 1개 확보 또는 후보 소진
```

여러 동네의 페이지를 각각 완성한 뒤 합치지 않는다. 이미 정렬된 배열의 다음 후보들을 비교해
하나의 순서로 읽는다. 필터에서 탈락한 후보도 탐색 위치는 전진한다. 태그 조건을 통과하는 장소가
적으면 페이지 하나를 위해 검사하는 후보 수가 늘어난다.

거리순은 기준 좌표가 요청마다 달라 정적 배열의 순서만으로 해결할 수 없다. 대상 동네의 후보를
확인하고 거리를 계산한 뒤, 필요한 개수의 가까운 후보를 힙에 유지해 결과를 만든다.

| 작업 | 비용을 결정하는 값 |
|---|---|
| 정적 목록 조회 | 대상 동네 수, 커서 탐색 비용, 필터 통과 전 검사한 후보 수 |
| 거리순 조회 | 대상 후보 수, 거리 계산 수, 유지할 결과 개수 |
| 전체 배열 구성 | 장소 수, 동네별 장소 분포, 정렬 축 수 |
| 상주 메모리 | 장소 객체 수, 정렬 배열의 참조 수, 표시값 크기 |

태그 비트마스크는 후보 하나의 판정을 고정 폭 비트 연산으로 처리한다. 후보 탐색 자체를 없애는
장치는 아니다. 요청별 힙과 탐색 위치는 공유 배열을 변경하지 않는다.

## 3. 변경의 종류와 반영 경로

원본이 바뀌면 그 트랜잭션이 MySQL의 번호 한 행을 올리고, 각 서버의 폴이 번호 차이를 보고
원본 전량을 읽어 자기 스냅샷을 다시 짓는다. 부분 갱신 경로는 하나뿐이고, 그것은 표시값이다.

| 변경 | revision | cursor_version | 정렬 배열 | 표시값 |
|---|---|---|---|---|
| 통계 회차(인기 점수·리뷰 수·평점·북마크 수) | +1 | +1 | 각 서버가 전량 리빌드 | 리빌드가 함께 읽는다 |
| 장소 생성·삭제·동네 이동·태그 집합·좌표 수정 | +1 | 유지(기본) 또는 +1(명시) | 각 서버가 전량 리빌드 | 커밋 직후 그 서버에 즉시 + 리빌드 |
| 장소 이름·썸네일·대표 태그 | +1 | 유지 | 리빌드가 다시 짓지만 순서는 같다 | 커밋 직후 그 서버에 즉시 + 리빌드 |
| 태그 이름·활성 상태 | +1 | 유지 | 위와 같다 | 태그 맵 한 벌을 커밋 직후 즉시 + 리빌드 |

정렬 배열을 메모리에서 부분 수정하는 경로는 두지 않는다. 그 순간 "스냅샷은 어느 한 시점의
완결된 것"이라는 계약이 깨지고, 얹을 기준 배열이 어느 시점의 것인지를 따로 관리해야 한다.
순서에 영향을 주는 변경은 리빌드가 통째로 다시 읽는다. 전량 읽기 한 번의 비용이 그 관리의
복잡도를 살 이유가 없다는 것이 근거다(7절).

리빌드는 폴 간격(기본 1분) 안의 변경을 묶는다. 관리자가 장소 열 건을 연달아 고쳐도 서버마다
리빌드는 한 번이다. 폴은 번호만 보고, 커졌으면 그 시점의 최신 원본을 읽는다. 그래서 다른
서버에 관리자 수정이 닿는 상한이 곧 폴 간격이다.

## 4. 관리자 수정과 표시값 즉시 반영

관리자 트랜잭션에서 스냅샷을 짓는 일은 없다. 요청 스레드가 하는 일은 원본을 고치고 번호를
올리는 UPDATE 하나까지다.

```text
관리자 쓰기 트랜잭션
  → 장소·관계·표시값 변경
  → place_stats upsert (파생 칸: 동네·태그 비트·좌표·이름·썸네일 키·대표 태그)
  → JPA 변경 flush
  → 번호 UPDATE            ← 같은 트랜잭션의 마지막 문장
  → 커밋

커밋 직후 (afterCommit, 같은 서버)
  → 새 REPEATABLE READ 트랜잭션에서
      첫 문장으로 번호를 읽고, 손댄 장소의 표시값을 place_stats에서 다시 읽는다
  → 로컬 갱신 잠금 안에서
      ├── 읽은 번호 <= 설치한 revision      → 얹지 않는다 (리빌드가 이미 실었다)
      ├── 같은 장소에 더 새 패치가 밀려 있다 → 얹지 않는다
      └── 홀더에 얹고, (번호, 값)을 밀린 패치로 보관
```

패치에 붙는 번호는 부르는 쪽의 쓰기 번호가 아니라 **값을 읽은 트랜잭션이 관측한 번호**다.
값을 다시 읽는 것은 커밋 뒤라 그 사이 남의 커밋이 끼면 "번호는 내 것인데 데이터는 그 뒤의 것"인
어긋난 쌍이 되는데, 읽은 트랜잭션의 번호를 그대로 붙이면 번호와 데이터가 언제나 같은 시점이다.
설치자의 비교가 전부 관측값끼리 이뤄지는 근거가 이것이다.

### 리빌드와 패치가 겹칠 때 옛 값으로 되돌아가지 않는다

리빌드는 관리자 커밋보다 앞선 시점의 원본을 읽고 있었을 수 있다. 그 결과를 통째로 대입하면
방금 얹은 표시값이 옛 값으로 되돌아간다. 그래서 얹은 패치는 관측한 번호와 함께 보관했다가,
리빌드가 새 표시값 맵을 **홀더에 걸기 전에** 그 맵 위에 미리 얹는다. 리빌드가 읽은 시점보다
앞선 패치는 그때 버린다.

```text
리빌드 (revision R을 읽음)
  → 새 표시값 맵 후보 구성
  → 로컬 갱신 잠금 안에서
      ├── 밀린 패치 중 번호 > R 인 것을 후보 맵 위에 얹는다 (번호 <= R 은 버린다)
      ├── 표시값 맵 교체 (한 번)
      └── Snapshot 채택 (revision R)
```

홀더를 먼저 갈고 나중에 패치를 다시 얹는 순서는 안 된다. 조회는 락을 잡지 않으므로 그 사이에
옛 표시값이 그대로 보인다. 패치끼리도 번호를 비교한다. 느리게 도착한 옛 패치가 새 패치를
덮지 않게 하기 위해서다.

패치는 설치한 revision을 올리지 않는다. 올리면 그 번호까지의 리빌드가 전부 "이미 설치했다"로
막히는데, 그 사이 번호에는 표시값이 아닌 변경(통계 회차의 정렬 키, 다른 관리자의 소속 변경)이
섞여 있다. 패치는 자기가 아는 한 칸만 고치고 번호는 건드리지 않는다.

패치가 실패해도 던지지 않는다. 던지면 이미 커밋된 관리자 요청이 500으로 나간다. 못 얹은 값은
번호 차이를 본 다음 리빌드가 원본에서 가져오므로 손실이 아니라 지연이다. 다른 서버는 애초에
이 패치를 받지 않고 리빌드로만 따라온다.

### 스크롤을 끊을지는 관리자가 고른다

장소 수정·삭제·동네 활성화 요청에는 `restartPlaceList` 필드가 있다. 생략하면 `false`이고, 지금
스크롤을 내리고 있는 사용자는 하던 페이지를 계속 받는다. 이번 수정이 순서나 소속을 건드렸다면
이어 보는 사용자에게 항목 하나가 겹치거나 빠져 보일 수 있다. 동네 하나를 켜면 장소 수백 건이
한꺼번에 들어와 순서가 크게 갈리지만, 그것이 트래픽 시간대인지 새벽인지는 코드가 알 수 없으므로
자동으로 끊지 않고 작업하는 관리자가 정한다.

## 5. 로컬 잠금과 조회 중인 객체의 수명

`CacheWriteLock`은 한 JVM의 갱신 작업끼리 순서를 맞춘다. 잡는 자리는 둘이다. 리빌드의 설치
단계와 표시값 패치. 사용자 조회는 이 잠금을 잡지 않고 불변 데이터를 읽는다.

리빌드의 읽기·조립·정렬은 전부 잠금 밖에서 끝내고, 잠금 안에서는 이미 완성된 것을 대입만
한다. 그래서 중간에 터지면 아무것도 바뀌지 않은 채로 끝나고 지금 회차가 그대로 서빙된다.
관리자 경로가 잠금 안에서 하는 일은 방금 읽은 표시값을 맵에 넣는 것뿐이라, 갱신 잠금이 오래
잡히는 경로는 없다.

이 서버에서 실제로 도는 리빌드는 언제나 하나다. 리빌드를 부르는 곳은 셋(기동·폴·목록 요청)인데
전부 같은 문을 지나고, 겹치는 요청은 돌고 있는 그 작업에 붙는다. 둘이 겹치면 읽기 부하도 힙도
두 배인데 얻는 것은 없다. 나중에 끝난 쪽만 설치되고 앞선 쪽은 단조 가드에 걸려 버려진다.
실제 리빌드는 전용 스레드 하나에서 돌고, 폴은 그 스레드에 맡기고 바로 돌아온다. 기다리는
요청은 비동기 대기표를 등록할 뿐 요청 스레드도 DB 커넥션도 잡지 않는다.

조회가 잠금을 기다리지 않는다는 사실과 조회 지연에 영향이 없다는 주장은 다르다. 리빌드도 같은
JVM에서 CPU·힙을 쓰므로 자원 경쟁과 GC를 통해 응답에 영향을 줄 수 있다. 별도의 빌더 서버나
스케줄러 풀 확대는 이 구조에 없다.

```text
교체 전
  최신 → Snapshot A
  진행 중인 요청 → Snapshot A

교체 후
  최신 → Snapshot B
  이미 시작한 요청 → Snapshot A로 처리 계속

기존 요청 종료
  Snapshot A를 붙잡는 참조가 없어지면 GC 회수 대상
```

한 벌만 보관해도 교체 순간 힙에 스냅샷 한 벌만 존재하는 것은 아니다. 진행 중인 요청과 리빌드
작업이 기존 객체를 참조할 수 있다. 참조가 끊겼다고 즉시 메모리가 회수되는 것도 아니다. 실제
회수 시점은 GC 실행에 달려 있다.

## 6. Heap·GC 비용은 어디에서 생기는가

상주량과 갱신 중 최대 점유를 나누어 봐야 한다. 상주량은 현재 엔트리·정렬 배열·표시값에 주로
붙고, 갱신 중에는 원본 조회 결과와 새 스냅샷의 재료가 추가된다.

```text
리빌드 중인 서버
  기존 Snapshot·표시값과 진행 중인 요청의 참조
  + place_stats 전량 조회 결과 (행 배열)
  + tags 전량 조회 결과
  + 새 PlaceEntry·표시 맵·정렬 배열
  → 설치 뒤 옛 스냅샷과 행 배열은 참조가 끊기면 회수 대상
```

이 항목들이 항상 전부 같은 시점에 최대 크기로 존재하는 것은 아니다. 하지만 상주 스냅샷 한 장의
크기만 보고 리빌드에 필요한 힙을 추정해서는 안 된다. 행 배열과 조립 중인 객체가 함께 살아 있는
구간이 있고, 정렬은 새 배열을 만든다.

TTL 없이 최신 스냅샷을 보관하는 이유는 다음 요청이 즉시 조회할 완성본이 필요하기 때문이다.
일정 시간이 지났다고 모델을 비우기보다 새 스냅샷을 준비한 뒤 교체한다. 메모리 안전성은 TTL
유무가 아니라 데이터 크기, 갱신 중 동시 점유, 요청이 참조를 유지하는 시간, JVM 여유와 GC
동작으로 확인해야 한다.

## 7. 확인한 것과 추가로 측정할 것

같은 로더 형상(원본 전량을 행 배열로 읽어 조립·정렬)을 가진 옛 커밋(`f2d7724`)에서 x10
데이터셋 63,200 장소를 2 vCPU / Xmx1280MiB로 무부하 리빌드했을 때, 15회 발화의 중앙값은
185ms였고 그 창에서 CPU 스로틀링과 자연 Full GC는 0회였다
(`docs/perf/2026-09-10-current-snapshot-rebuild-x10.md`). 185ms는 읽기·조립·정렬·설치를 합친
값이다. DB 읽기만의 시간이 아니고, 현재 코드로 다시 잰 값도 아니며, 사용자 부하가 섞인 상황의
응답 지연을 말하지 않는다.

실제 구조의 비용 판단에는 다음 관측이 더 필요하다.

| 측정 대상 | 함께 확인할 값 |
|---|---|
| 리빌드 한 회차 | 원본 읽기·조립·정렬·설치 시간, CPU, 할당량 |
| 갱신 중 메모리 | 옛·새 스냅샷과 행 배열이 공존하는 구간의 최대 점유, 자연 GC 횟수·정지 시간 |
| 사용자 영향 | 리빌드 중 조회와 북마크 쓰기의 지연 분포, 대기표의 완료 시간 |
| 반복 실행 | 관리자·집계 변경이 쌓이는 속도, 폴 간격 묶음이 실제로 리빌드 수를 줄이는지 |
| 여러 서버 | 같은 번호 변경에 서버들이 몰려 읽을 때의 DB 부하 |

진단을 위해 강제 실행한 GC는 자연 GC 결과와 분리해야 한다. 무부하에서 갱신이 끝난 시간만으로
사용자 요청이 섞인 상황의 지연을 판단할 수도 없다. 현재 구조의 운영 비용은 이 측정으로 확인할
대상이며, 갱신 빈도나 스냅샷 한 장의 크기 하나만으로 충분히 작다고 단정하지 않는다.

기능 검증은 Testcontainers MySQL 8.0 위의 통합 테스트와 결정적 단위 테스트로 한다. 표시값
패치와 리빌드 설치의 순서 역전, 패치 둘의 완료 순서 역전, 실패 뒤 폴링 복구, 관리자 옵션의
생략·false·true, 생성·삭제·동네 활성화·태그·이미지 후처리 경로를 각각 문는다. 운영 부하에서의
지연·메모리 여유를 측정한 결과는 아니다.
