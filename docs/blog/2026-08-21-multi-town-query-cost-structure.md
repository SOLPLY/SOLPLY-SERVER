# 여러 동네 목록 조회에서 실제 비용을 결정한 것은 무엇이었나

작성일: 2026-08-21
측정 정본: [4개 형상 부하 격자와 실행 계획 분석](../perf/2026-08-20-in-union-mask-load-grid.md),
[성장·분포 축 측정 캠페인](../../load-test/campaigns/2026-08-20_growth-300-per-town/README.md)

단순한 조회 구조에서 시작해, 데이터 증가를 대비해 실행 계획을 분석하고, 여러 최적화
가설을 부하로 검증하면서 실제 비용을 결정하는 요인이 무엇인지 찾아간 기록이다.
중간에 한 번 기각한 선택지가 마지막에 되살아난다.

---

## 시작은 단순한 쿼리 하나였다

이 서비스의 메인 기능은 장소 목록 조회다. 사용자가 동네 여러 곳을 고르고(시 단위를
고르면 18개 동네), 태그 필터를 걸고(같은 그룹 안은 OR, 그룹 사이는 AND), 인기순으로
한 페이지 11건(10건 + 다음 페이지 판정 1건)을 받는다. 정렬의 원천은 배치가 주기적으로
갈아 끼우는 읽기 전용 통계 테이블 `place_stats`이고, 여기에
`(version, town_id, popular_score DESC, ...)` 커버링 인덱스가 있다. InnoDB의 세컨더리
인덱스는 엔트리에 인덱스 컬럼과 PK만 담기 때문에, 응답에 필요한 컬럼이 인덱스에
없으면 행마다 PK로 테이블(클러스터드 인덱스)을 다시 찾아가야 한다. 이 인덱스는
응답 컬럼까지 전부 담고 있어 그 왕복 없이 인덱스만 읽고 끝난다. 커버링이라 부르는
이유이고, 뒤에 나올 이야기의 바닥이 되는 성질이다.

처음 구현은 가장 단순한 형태였다.

```sql
SELECT ps.place_id, ps.popular_score, ...
FROM place_stats ps
WHERE ps.version = :v
  AND ps.town_id IN (:동네 18곳)
  AND EXISTS (SELECT 1 FROM place_tag pt
               WHERE pt.place_id = ps.place_id AND pt.tag_id IN (:그룹1))
  AND EXISTS (... :그룹2 ...)
ORDER BY ps.popular_score DESC
LIMIT 11
```

동네당 장소가 100곳 안팎, 시 단위 요청이면 후보 1,800행. 이 규모에서는 아무 문제가
없었다.

## 데이터가 늘면 어디부터 무거워질까

성장을 대비해 실행 계획을 열어봤다. 이 쿼리가 빠른 이유는 일찍 멈추기 때문이다.
단일 동네 조회는 정렬 인덱스를 점수순으로 읽으며 조건을 확인하다 11건이 차면 멈춘다.
그런데 동네를 IN으로 여러 개 묶는 순간 이 이점이 사라진다.

```
단일 동네                              다중 동네 IN
[동네 구간을 점수순으로 읽는다]          [동네A 구간][동네B 구간]...[동네R 구간]
조건 확인하며 11건 차면 멈춘다           구간 안에서만 점수순이고,
                                       구간을 건너면 전체 순서가 없다
                                       → 전 구간 1,812행을 다 읽고
                                       → 정렬을 마쳐야 상위 11건을 안다
```

인덱스로 18개 구간을 짚어 읽는 것 자체는 그대로다. 사라지는 것은 점수 순서다. 동네 경계를
넘는 순간 "지금까지 본 것보다 높은 점수는 더 없다"는 보장이 사라지므로, 후보 전량을
읽고 filesort(우선순위 큐 11행)를 거쳐야 한다. digest로 확인하면 이 쿼리는 조건과
무관하게 실행마다 1,812행을 읽는다. 데이터가 자라면 이 전량 스캔이 정비례로 자란다.

이때의 가정은 이랬다. 읽는 행 수와 filesort가 문제다. 그렇다면 동네별로 쪼개서 각
동네의 조기 종료를 살리면 되지 않을까.

## 쿼리를 동네별로 쪼개면 될까

두 가지 분할을 검토했다. 하나는 SQL 안에서 쪼개는 UNION ALL이다.

```sql
(SELECT ... WHERE town_id = :동네A ... ORDER BY popular_score DESC LIMIT 11)
UNION ALL
(... 동네 18곳 반복 ...)
ORDER BY popular_score DESC LIMIT 11
```

다른 하나는 애플리케이션에서 동네별 쿼리 18개를 CompletableFuture로 병렬 실행하고
우선순위 큐로 병합하는 방식이다.

부하를 걸어 보니 예상과 반대였다. 시나리오는 태그 선택도 3점으로 잡았다.
무태그(S1), 흔한 태그 1개(S2, 전국 1,105곳, 동네 통과율 약 17%), 희귀
조합(S3, 3그룹 태그 5개, 통과율 약 9%).

| 처리량(QPS), 동네당 100곳 | S1 무태그 | S2 흔한 태그 | S3 희귀 조합 |
|---|---|---|---|
| IN + EXISTS (초기 구조) | 3,386 | 2,898 | 1,115 |
| UNION ALL + EXISTS | 3,682 | **1,378** | **565** |

무태그에서는 읽는 행이 1,812에서 407로 4.5배 줄었는데 처리량은 9%밖에 안 올랐고,
태그가 붙자 초기 구조의 절반으로 떨어졌다. 실행 계획을 나란히 놓고 원인을 찾았다.

첫째, 태그를 EXISTS로 확인하는 구조에서는 브랜치가 일찍 멈추는 것도 공짜가 아니었다.
S2 기준으로 두 실행 흐름을 나란히 놓으면 이렇다.

```
초기 구조 (IN + EXISTS)                  분할 (UNION ALL + EXISTS)
───────────────────────────            ───────────────────────────
1. 18개 동네 구간 스캔 (1,800행)         브랜치 × 18 (동네마다):
2. 전량을 우선순위 큐로 정렬              1. 동네 구간을 점수순으로 읽는다
3. 정렬 순서대로 place_tag 확인           2. 행마다 place_tag를 되짚어 확인
4. 11건 차는 순간 전체 종료               3. 11건 차면 그 브랜치만 종료
   → 확인 57회에서 끝                       → 브랜치마다 27~92행
                                        4. 18개 결과 198행을 임시 테이블에 모음
                                        5. 최종 정렬 후 11건

place_tag 확인: 57회                    place_tag 확인: 합계 1,185회 (21배)
```

초기 구조는 정렬을 먼저 끝내고 전체 LIMIT 11의 보호 아래 57회만 확인하는데, 분할하면
브랜치마다 각자 11건을 채워야 하므로 확인이 21배로 늘고, 정렬 대상도 11행이 아니라
18×11 = 198행이 된다.

둘째, 같은 분할이라도 두 방식은 비용을 내는 자리가 다르다.

```
UNION ALL: 요청당 문장 1개              병렬 실행: 요청당 문장 18개
───────────────────────────           ───────────────────────────
앱 ── 왕복 1번 ── DB                   앱 ── 왕복 18번 ── DB
     파싱·플랜 수립 1회                     파싱·플랜 수립 ×18
     브랜치 18개 실행                       단일 동네 쿼리 ×18
     임시 테이블에 모아 최종 정렬             (DB에는 정렬·임시 테이블 없음)
     11건 응답                             11건씩 18묶음 응답
                                          → 병합·최종 정렬은 앱 메모리에서
```

UNION ALL은 병합과 정렬까지 DB가 마치는 대신 파싱·플랜 수립·네트워크 왕복을 한 번만
치른다. 병렬 실행은 각 문장이 단일 동네 조회라 인덱스 순서로 11건 읽으면 끝이라
DB에는 정렬도 임시 테이블도 아예 없지만(문장당 0.05ms), 파싱·플랜·왕복 같은 문장
단위 고정비를 18번 낸다. 실제로 재 보니 이 고정비 반복이 지배적이어서, 병렬 실행의
DB 몫은 포화 상한으로도 요청 환산 1,047~1,318에 머물렀다. 198행을 병합하는 일과 왕복
18번은 앱이 따로 부담하는데, 그 몫은 이 값에 포함되지도 않았다(이 측정은 뒤에 나올
비트마스크를 얹은 형상으로 했다. 문장 고정비는 태그 판정 방식과 무관하므로 EXISTS였다면
더 나빴을 것이다).

이 시점의 교훈은 이것이다. **읽는 행 수는 원인을 가리키는 지표였지 병목 그 자체가
아니었다.** 이 규모에서 병목은 행당 단가(행마다 place_tag를 되짚는 비용)와, 쪼갠
단위마다 반복되는 고정비(UNION이면 브랜치 실행과 임시 테이블, 병렬 실행이면 문장마다
붙는 파싱·플랜·왕복)였다. 그래서 분할을 접고 IN 하나를 유지하기로 했다.

## 남은 문제, 태그에 따라 실행 계획이 흔들린다

분할을 접고 나니 다른 문제가 남았다. 조인이 있으면 옵티마이저는 어느 테이블을 먼저
읽을지 고른다. 이 첫 자리가 드라이빙 테이블이고, 바깥 반복문이 되어 전체 읽기 규모를
결정한다. 이 쿼리에는 드라이빙 테이블 후보가 둘 있어서 계획이 두 갈래로 갈린다.

```
A. place_stats가 드라이빙 테이블 (동네 주도)
1. 18개 동네 구간을 전량 스캔 (1,800행) — IN이라 일찍 멈출 수 없다
2. 후보 전량을 filesort — 태그를 아직 안 걸렀으니 정렬 입력이 후보 전체다
3. 정렬된 순서대로, 행마다 place_tag를 랜덤 lookup해 태그를 확인한다
4. 통과 11건이 차면 종료 — 정렬을 먼저 한 덕에 확인 작업이 LIMIT의
   보호를 받는다 (S2 실측: 57회 확인에서 멈춤)

비용이 따라가는 축: 요청한 동네들의 후보 수

B. place_tag가 드라이빙 테이블 (태그 주도)
1. 태그 인덱스에서 그 태그가 붙은 행을 전국 단위로 스캔한다
   — 태그 인덱스에는 동네 조건이 없어 지역으로 좁혀 읽을 수 없다
2. 행마다 place_stats를 PK로 랜덤 lookup해 동네·버전 조건을 거른다
3. 같은 장소가 태그마다 중복 등장하므로 weedout 임시 테이블로 중복을 걸러낸다
4. 남은 후보를 정렬한 뒤 LIMIT 11 — 정렬이 맨 뒤라 LIMIT이 어떤 읽기도
   줄여주지 못한다

비용이 따라가는 축: 그 태그가 붙은 전국 장소 수
```

각 계획의 문제 지점이 흐름에 그대로 있다. A는 전량 스캔에 더해 **거르기 전에 후보
전체를 정렬**해야 하고(마스크 구조가 걸러낸 뒤 11행 큐만 유지하는 것과 대비된다),
행 확인마다 lookup 단가를 낸다. 이 정렬-먼저 순서는 사실 비싼 확인에 대한 적응이다.
스캔 중에 EXISTS를 확인하면 1,800행 전부에 lookup이 필요하지만, 정렬부터 하면
상위부터 확인하다 11건에서 멈출 수 있다. B는 읽기가 조회 지역이 아니라 태그의 전국
규모를 따라가고, 랜덤 lookup이 그 규모만큼 반복되고, weedout 임시 테이블 유지비가
행마다 붙고, LIMIT은 끝까지 아무 일도 줄여주지 못한다.

옵티마이저는 요청마다 두 계획의 비용을 추정해 작은 쪽을 고른다.

```
드라이빙 테이블 선택 과정
1. A의 비용 추정 ← "요청한 18개 동네의 후보 수"를 따라간다
2. B의 비용 추정 ← "그 태그가 붙은 전국 장소 수"를 따라간다
3. 둘을 비교해 작은 쪽을 드라이빙 테이블로 채택
```

선택이 두 숫자의 비율에 걸려 있는데, 두 숫자는 서로 다른 이유로 자란다. 후보 수는
요청한 지역의 데이터 성장을, 태그 행 수는 전국의 태그 부착량을 따라가기 때문이다.

어느 쪽이 싼지는 태그 분포가 정한다. 문제는 옵티마이저의 비용 추정이 정확하지 않다는
것이다. 희귀 조합(S3)에서 옵티마이저는 place_tag를 드라이빙 테이블로 골랐는데,
힌트로 반대 계획(A)을 강제해 재 보니 그쪽이 1.85배 빨랐다(1,115 vs 2,058 QPS). 비용 모델이 랜덤 lookup
수천 회와 중복 제거용 임시 테이블의 실비를 과소평가했고, LIMIT의 조기 종료 이득은
조인 비용 계산에 반영하지 않기 때문이다.

더 곤란한 것은 이 선택이 데이터 성장의 방향에 따라서도 뒤집힌다는 점이다. 이
서비스의 데이터가 고르게 자랄 것이라는 보장이 없다. 1인 가구가 밀집한 서울 쪽에
장소 등록이 먼저 몰릴 수 있고, 태그는 장소마다 몇 개를 붙이느냐는 운영 방식에 달려
있어 장소 수에 비례해 자란다는 보장도 없다. 그래서 같은 규모(동네당 200곳)로 키우되
성장 분포만 다른 두 벤치 스키마를 만들어 비교했다. 전국이 고르게 2배가 된 스키마와,
서울 18개 동네만 2배가 된 스키마다.

| S2 기준 | 동네 후보 | 태그 전국 행 수 | A 비용 추정 | B 비용 추정 | 선택 |
|---|---|---|---|---|---|
| 전국이 고르게 2배 | 3,600 | 2,210 | 1,987.70 | 2,172.25 | A 유지 |
| 서울만 2배 | 3,600 | 1,407 | 1,987.70 | 1,409.40 | **B로 전환** |

옵티마이저 트레이스를 떠 보면 A의 비용은 두 스키마에서 소수점까지 같다. 움직인 것은
B의 비용 하나뿐이고, 그것만으로 계획이 넘어갔다. 그리고 넘어간 쪽이 실제로는
느렸다(처리량 1,650 vs 1,020). 반대로 희귀 조합(S3)에서는 서울만 자란 쪽이 1.7배
빨랐다(866 vs 501). 같은 분포 변화가 시나리오에 따라 유리하게도 불리하게도 작용한다.

장소가 어느 지역에 몰려 등록될지, 태그가 장소 증가에 비례해 붙을지는 서비스가
예측하거나 통제할 수 있는 값이 아니다. 계획 선택이 남아 있는 한, 이 쿼리의 성능은
통제 불가능한 변수에 걸려 있는 셈이다.

## 힌트로 잡을 수 있을까

계획을 고정하는 고전적인 수단은 힌트다. 태그 조합별로 일치 행 수를 추정해 조건부로
힌트를 넣는 방안을 검토하고 기각했다. 이유는 셋이다.

1. 조건부 힌트가 제대로 동작하려면 "옵티마이저가 틀리는 지점"을 애플리케이션이
   알아야 한다. 그 판단의 입력이 바로 옵티마이저가 틀리는 그 추정치라, 사실상 비용
   모델을 애플리케이션에 다시 구현하는 일이 된다.
2. 임계값을 실측으로 맞춰 놓아도 데이터가 자라면 소리 없이 어긋난다. 어긋났다는
   신호도 없다.
3. 상한이 낮다. 힌트로 얻을 수 있는 최선이 2,058인데, 다음 절의 구조 변경은 같은
   시나리오에서 3,869를 낸다. 잘못된 선택지 중 나은 쪽을 고르는 문제였다.

## 계획 선택이라는 문제 자체를 없앴다

관점을 바꿨다. 계획이 흔들리는 근본 원인은 태그 확인이 다른 테이블(place_tag)에
있다는 것이다. 행마다 다른 테이블에 물어봐야 하는 조건이니 조인이 필요하고, 조인이
있으니 순서 선택이 생기고, 순서 선택이 있으니 오판의 여지가 생긴다.

place_tag가 조인에서 빠지면 드라이빙 테이블 후보가 place_stats 하나만 남고, 계획
선택이라는 문제 자체가 사라진다.

그래서 place_stats에 태그를 비트마스크로 비정규화했다. 장소마다 붙은 태그를 BIGINT
한 컬럼(`tag_mask`)에 비트로 담고, 이 컬럼을 정렬 커버링 인덱스의 끝에 포함시켰다.
태그 판정은 그룹마다 비트 AND 한 번이다. 그룹 안 OR는 그룹 마스크와의 AND가 0이
아닌지로, 그룹 사이 AND는 판정을 나란히 거는 것으로 그대로 표현된다.

```sql
WHERE ps.version = :v AND ps.town_id IN (:동네들)
  AND (ps.tag_mask & :그룹1마스크) != 0
  AND (ps.tag_mask & :그룹2마스크) != 0
ORDER BY ps.popular_score DESC LIMIT 11
```

중요한 것은 이것이 컬럼 추가가 아니라 인덱스 재설계라는 점이다. 세컨더리 인덱스
엔트리에는 인덱스에 넣은 컬럼만 존재하므로, tag_mask를 테이블 컬럼으로만 두면 스캔
중인 인덱스에서는 마스크가 보이지 않아 판정 때마다 PK로 클러스터드 인덱스를 되짚어야
한다. 그러면 후보마다 행을 되짚는 비용이 place_tag 대신 place_stats 자신을 상대로
부활한다. 마스크가 정렬 인덱스 엔트리 안에 있어야 스캔·판정·SELECT가 전부 인덱스
안에서 끝난다.

후보 행 하나를 판정하는 흐름이 이렇게 바뀐다.

```
EXISTS: 행마다 다른 테이블에 묻는다      마스크: 행이 스스로 답한다
───────────────────────────           ───────────────────────────
[후보 행을 인덱스에서 읽는다]           [후보 행을 인덱스에서 읽는다]
→ place_tag를 랜덤 lookup             → 같은 엔트리 안의 tag_mask와 비트 AND
  (그룹 수만큼 반복)                     (그룹 수만큼 반복, 읽기 추가 없음)
→ 통과 여부 판정                       → 통과 여부 판정

행당 비용 = 인덱스 lookup × 그룹 수     행당 비용 = CPU 비트 연산 몇 번
```

효과는 두 겹이다. 되짚기가 사라지고(place_tag 확인 0회), place_tag가 조인 그래프에서
빠지면서 **계획 후보가 하나로 줄었다.** 드라이빙 테이블로 삼을 테이블이 하나뿐이니
옵티마이저가 고를 것이 없다. 동네당 100곳 측정에서 처리량은 3,415 / 3,763 / 3,869(S1/S2/S3)로,
읽는 행은 세 시나리오 모두 1,812행으로 소수점까지 같았다. 그런데 태그가 늘수록
오히려 빨라진다. 실행 순서를 펼치면 이유가 보인다.

```
IN + 마스크의 실행 순서 (쿼리 1개)
1. 18개 동네 구간의 인덱스 엔트리를 전량 읽는다 (1,812행, 태그와 무관하게 동일)
   — 구간 안에서만 점수순이고 구간 사이엔 순서가 없어, "남은 행은 전부 지금
     11등보다 낮다"는 확신을 어느 시점에도 가질 수 없다. 그래서 못 멈춘다.
2. 엔트리마다 tag_mask 비트 AND로 통과/탈락을 판정한다
3. 탈락한 행은 그 자리에서 버린다 → 정렬로 넘어가지 않음
4. 통과한 행만 11칸짜리 우선순위 큐와 비교한다
   — 지금의 11등보다 점수가 높으면 교체, 아니면 그 자리에서 버림
5. 스캔이 끝나면 큐에 남은 11건이 결과
```

EXPLAIN에는 filesort로 찍히지만 임시 테이블은 만들지 않는다(digest 실측 임시 테이블
0.00개/실행). LIMIT이 작으면 정렬이 위처럼 우선순위 큐로 돌아서, 보관 공간은 딱
11행이고 행당 일은 "현재 11등과 비교 한 번"이다. 그래서 읽는 양(1단계)은 태그가 뭐든
전량으로 같지만, 큐(4단계)가 처리할 행은 마스크를 통과한 만큼만이다. 무태그면
1,812행 전부가 큐의 비교를 거치고, 희귀 조합이면 160행 정도만 거친다. 조건이
깐깐할수록 정렬 일감이 줄어서, 같은 스캔량으로도 처리량이 올라가는 것이다.

## 성장 범위를 실제로 재봤다

여기서 멈추지 않은 이유가 있다. 마스크를 얹은 IN 구조의 읽기는 여전히 후보 전량이다.
동네당 장소가 자라면 정비례로 무거워진다. 반면 앞에서 기각한 분할은 브랜치 조기
종료 덕에 규모에 둔감할 수 있다.

성장 범위를 정하는 것부터가 엔지니어링 판단이었다. 이 서비스는 동네 단위로 장소를
선별해 보여주는 큐레이션 구조라, 동네당 장소 수가 등록형 플랫폼처럼 자릿수 단위로
자라지 않는다. 지금 동네당 100곳 안팎에서 현실적으로 계획할 수 있는 상한을
2배(200곳)로 잡았다. 그 너머의 규모라면 이 쿼리의 형상을 고르는 문제가 아니라 캐싱
같은 다른 구조를 먼저 논의할 문제가 된다. 그 상한을 실제로 시딩해 쟀다(태그 분포
비율을 유지한 채 장소를 복제).

| 처리량(QPS) | 형상 | 동네당 100곳 | 동네당 200곳 |
|---|---|---|---|
| S1 무태그 | IN + 마스크 | 3,415 | 1,904 |
| | UNION ALL + 마스크 | **3,836** | **3,586** |
| S2 흔한 태그 | IN + 마스크 | **3,763** | 2,198 |
| | UNION ALL + 마스크 | 3,353 | **2,941** |
| S3 희귀 조합 | IN + 마스크 | **3,869** | **2,239** |
| | UNION ALL + 마스크 | 2,742 | 2,023 |

규모를 2배로 키우자 순위가 실제로 뒤집혔다. 현재 규모에서 IN이 앞서던 흔한
태그(S2)는 200곳에서 UNION이 34% 앞서는 쪽으로 역전됐다(2,198 vs 2,941). 무태그(S1)는
IN이 3,415에서 1,904로 떨어지는 동안 UNION이 3,836에서 3,586으로 거의 그대로여서,
격차가 12%에서 88%로 벌어졌다. 데이터 성장이 IN에는 그대로 비용이 됐고, UNION에는
거의 비용이 되지 않은 것이다.

차이의 출처를 보려면 UNION + 마스크의 내부 동작을 IN(앞 절의 실행 순서)과 나란히
놓으면 된다.

```
UNION ALL + 마스크의 실행 순서 (쿼리 1개, 브랜치 18개)
브랜치마다 (동네마다):
1. 그 동네의 인덱스 구간을 점수순으로 읽는다 — 구간 안은 순서가 보장된다
2. 엔트리마다 tag_mask 판정, 통과 11건이 차는 순간 그 브랜치는 종료
   — "남은 행은 전부 이 11건보다 낮다"가 동네 안에서는 성립하기 때문
3. 브랜치 결과(최대 11건)를 union 임시 테이블에 쌓는다
전체:
4. 임시 테이블의 최대 198행(18×11)을 정렬해 상위 11건을 응답
```

IN이 잃어버린 "일찍 멈출 수 있는 순서"를 동네 단위로 되살린 구조다. 대가는 union
임시 테이블 한 개(digest 실측 1.00개/실행)와 브랜치 18개의 실행 준비인데, 둘 다
규모와 무관한 상수다. 파싱·플랜·왕복은 여전히 문장 하나 몫만 낸다.

읽는 행이 이 구조 차이를 그대로 보여준다. IN + 마스크는 1,812에서 3,615로 규모에
정비례해 늘었다. UNION + 마스크는 S1에서 407 그대로, S2에서 1,395에서 1,401로
사실상 그대로다. 브랜치는 점수순으로 읽다 마스크 통과 11건이 차면 멈추므로, 통과율이
높으면 동네가 얼마나 커지든 읽는 깊이가 변하지 않는다.

```
브랜치 하나가 읽는 깊이 (동네당 200행, 통과 11건이 차면 멈춤)
S1 무태그     ██ 23행                모든 행이 통과, 바로 멈춤
S2 흔한 태그  ███████ 78행           통과율 17%, 조금 더 읽고 멈춤
S3 희귀 조합  ██████████████████ 189행  통과율 9%, 동네를 거의 다 읽음

(비교: IN + 마스크는 어떤 시나리오든 동네 전량 200행을 읽는다)
```

희귀 조합(S3)만 다르다. 그림처럼 11건을 채우기 위해 동네의 거의 전부를 읽어야
하니, 일찍 멈추는 이득이 사실상 없어져 읽는 양이 IN의 전량 스캔과 비슷해지고, 남는
차이는 브랜치 18개를 각각 실행하고 임시 테이블로 모으는 비용(UNION 쪽, 이 창 실측으로
실행당 약 0.4ms)이냐 큰 정렬 한 번(IN 쪽)이냐 정도라 처리량도 10% 안쪽으로 붙는다. **정리하면, 분할이 IN보다 나을 수 있는
이유는 브랜치가 일찍 멈춘다는 것 하나인데, 얼마나 일찍 멈추는지는 태그 통과율이
정한다.** 그래서 두 형상의 우열이 뒤바뀌는 규모도 태그마다 다르다. 무태그는 처음부터
분할이 우세했고, 흔한 태그는 100~200곳 사이에서 역전됐고, 희귀 조합은 200곳에서도
IN이 근소하게 앞선다.

분포 실험의 결론도 여기서 확인됐다. 성장 분포가 다른 두 200곳 스키마에서 마스크
형상들은 읽는 행이 소수점 첫 자리까지 같고 처리량 차이도 측정 오차 안이었다. 조회한
동네 구간만 읽는 구조라, 서울 밖의 데이터가 얼마나 자랐든 이 쿼리가 읽는 양에는 아무
영향이 없다. 계획이 하나뿐이니 분포 변화가 계획을 바꿀 여지도 없다.

태그 분포의 영향이 통째로 사라진 것은 아니라는 점은 구분해 둘 필요가 있다. 통과율이
낮아지면 브랜치가 더 깊이 읽고, IN이라면 정렬 입력이 줄어드는 식으로, **일의 양은
마스크 구조에서도 여전히 분포를 따라간다.** 사라진 것은 분포가 **일하는 방식을
바꾸는 통로**다. 조인이 있던 초기 구조에서는 분포가 어느 문턱을 넘으면 드라이빙
테이블이 바뀌면서 비용이 따라가는 축 자체가 달라졌고(동네 후보 수 → 태그 전국 규모),
그래서 성능이 절벽처럼 변했다(같은 규모에서 1,650 vs 1,020). 마스크 구조에서 분포는
일의 양을 연속적으로만 바꾼다. 통과율이 절반이 되면 그만큼 더 읽을 뿐, 실행 방식이
통째로 바뀌는 지점이 없다.

## 기각했던 분할을 다시 꺼냈다

최종 형상은 UNION ALL + 마스크다. 앞에서 분할을 기각했을 때 진 이유를 다시 보면,
분할 자체가 아니라 태그 판정 방식이 문제였다. 행마다 place_tag를 되짚는 비용이,
브랜치가 일찍 멈춰서 아끼는 것보다 컸던 것이다. 마스크가 되짚기를 없애자 그 비용은
사라지고 일찍 멈추는 이득만 남았다. 그리고 이 비교에 등장한 형상 가운데 데이터가
늘어도 처리량이 거의 떨어지지 않는 것은 이 구조뿐이다(S1 3,836 → 3,586,
S2 3,353 → 2,941).

### 왜 UNION ALL + tag_mask가 확장성에 유리했는가

UNION ALL + tag_mask를 선택한 이유는 현재 QPS가 가장 높아서가 아니라, 서비스의
데이터 증가가 쿼리 작업량 증가로 직접 이어지지 않는 구조였기 때문이다.

**Top-N 크기가 고정되어 있다.** 페이지 크기가 11건으로 고정되어 있으므로 데이터가
늘어도 각 동네 브랜치가 찾아야 할 결과 수는 늘지 않는다. 따라서 LIMIT을 충분히 일찍
채울 수 있는 조건에서는 브랜치의 탐색량을 데이터 전체 규모와 분리할 수 있다.

**태그 판정이 현재 읽고 있는 인덱스 엔트리에서 끝난다.** tag_mask를 정렬 인덱스에
포함해 후보마다 place_tag를 다시 탐색하지 않는다. 덕분에 브랜치에서 탈락 후보를
확인하는 비용이 충분히 작아져, early-stop으로 줄인 탐색량이 실제 처리량 이점으로
이어진다. 같은 분할 구조가 EXISTS에서는 반복 index probe 때문에 오히려 느렸다는
실측이 이 조건의 중요성을 보여준다.

**분할 단위마다 정렬 순서가 이미 보장된다.** 각 동네는 popular_score 순서의 인덱스
구간을 가지므로 브랜치는 별도 정렬 없이 순서대로 읽다가 LIMIT을 채우면 종료할 수
있다. 즉 UNION은 정렬을 없애는 방식이 아니라, 정렬 순서를 활용할 수 있는 단위로
문제를 분해하는 방식이다.

**주요 요청에서는 필터 통과율이 early-stop을 살릴 만큼 높다.** 무태그와 일반적인
태그 조건에서는 11건을 채우는 깊이가 데이터 규모보다 훨씬 작아, 장소 수가 증가해도
브랜치당 읽는 행 수가 거의 증가하지 않았다. 반대로 희귀 조합에서는 거의 전량을
읽어야 해 UNION의 이점이 사라졌다. 따라서 이 선택의 이점은 UNION 자체가 아니라
Top-N 구조와 실제 요청 선택도의 결합에서 나온다.

**분할 수와 쿼리 실행 횟수가 고정되어 있다.** 브랜치 수는 시 단위 동네 수인 18개로
제한되고, UNION ALL 하나의 SQL 안에서 실행되므로 네트워크 왕복과 애플리케이션→DB
쿼리 횟수는 한 번이다. 동네별 쿼리를 애플리케이션에서 병렬 실행했을 때처럼 문장 단위
고정비와 connection 사용량이 브랜치 수만큼 증폭되지 않는다.

이 조건에서는 데이터 증가가 두 구조에 다르게 작용한다.

```
IN + mask                          UNION ALL + mask
동네당 데이터 증가                   동네당 데이터 증가
→ 조회 대상 전체 후보 증가           → 브랜치는 여전히 Top 11만 필요
→ scan/sort 작업량도 비례 증가       → 통과율이 유지되면 early-stop 깊이는 거의 고정
                                   → 전체 작업량 증가 억제
```

실측에서도 이 차이가 확인됐다. 동네당 100→200곳으로 늘렸을 때 IN + mask는 읽는
행이 1,812→3,615로 거의 2배 증가한 반면, UNION + mask는 S1에서 407행, S2에서 약
1,400행 수준을 유지했다. 그 결과 S2는 100곳에서는 IN이 앞섰지만 200곳에서는 UNION이
34% 앞서는 쪽으로 역전됐고, S1은 격차가 더 크게 벌어졌다.

내주는 것도 명확히 적어 둔다. 희귀 조합은 현재 규모에서 IN 쪽이 41% 빠르다(3,869
vs 2,742). 이것을 수용한 근거는 세 가지다. 여러 그룹의 희귀 태그를 동시에 거는
요청은 트래픽에서 차지하는 비중이 작고, 내준 뒤의 절대 처리량(2,742 QPS)도 여유가
크며, 데이터가 늘면 이 격차 자체가 사라진다(200곳에서 이미 10% 안쪽).

## 이 여정에서 얻은 판단 기준

정리하면 다음 네 가지다.

1. **rows examined는 진단 지표지 병목이 아니다.** 행을 4.5배 줄이고 처리량이 9%
   오른 측정이 있었다. 병목은 행당 단가(순차 읽기냐 랜덤 되짚기냐)와 쪼갠 단위마다
   반복되는 고정비에 있었고, 규모가 커진 뒤에야 행 수가 병목으로 올라왔다.
2. **일찍 멈추는 구조를 만들었다고 일찍 멈추는 것이 아니다.** 실제로 어디서 멈추는지는
   조건을 통과하는 행이 얼마나 흔한지가 정한다. 같은 분할 구조가 무태그에서는 브랜치당
   23행을 읽고 멈췄고, 희귀 조합에서는 189행, 동네의 거의 전부를 읽었다.
3. **쿼리를 쪼갤수록 문장 고정비(파싱, 플랜 수립, 네트워크 왕복)가 실행 횟수만큼
   붙는다.** 이 비용은 문장이 읽는 데이터 양과 무관하게 문장마다 붙는다. 쿼리 하나가
   0.05ms여도 18개로 쪼개면 이 비용을 요청마다 18번 낸다. 데이터가 작을수록 이
   비용이 전체를 지배한다.
4. **계획 선택이 남아 있는 구조는 통제할 수 없는 변수에 성능이 걸린다.** 규모를
   고정하고 성장 분포만 바꿔도 계획이 뒤집혔고, 뒤집힌 방향이 시나리오마다 반대였다.
   비정규화의 실질 효과는 판정 단가를 줄인 것만이 아니라, 태그 분포가 실행 계획에
   영향을 줄 길 자체를 없앤 것이다.

최적화는 JOIN을 없애는 일도, filesort를 없애는 일도 아니었다. 이 서비스의 데이터
규모와 분포에서 가장 싼 비용 구조를 고르는 일이었고, 같은 선택지라도 어떤 조건과
결합하느냐에 따라 답이 바뀌었다. 동네별 분할이 그랬다. 태그를 EXISTS로 확인할 때는
초기 구조의 절반밖에 못 내는 안이었지만, 태그 판정을 마스크로 바꾸자 데이터가 늘어도
처리량이 유지되는 유일한 구조가 됐다.

## 측정 방법과 이 기록이 말할 수 없는 것

측정은 벤치 스키마(서울 18개 동네, 동네당 100곳 기준. 성장 측정은 태그 분포 비율을
유지한 복제 시딩)에서 했다. 부하는 워커 4개가 지속 커넥션으로 쉼 없이 반복 실행하는
폐루프 방식으로 셀당 약 30초, DB 컨테이너의 cgroup CPU가 상한 2코어에 붙었는지로
포화를 확인했고, 읽는 행 수는 performance_schema digest의 실행당 값으로 판정했다.

- 동네당 100~200곳 범위의 측정이다. 그 밖의 규모로 외삽할 수 없다.
- DB 쿼리 단위 측정이다. 병렬 실행 방식의 애플리케이션 몫(스레드, 병합, 왕복)은
  포함하지 않았다.
- 단독 워크로드다. 다른 쿼리와 경합하는 상황은 재지 않았다.
- 셀 대부분이 1회 채취라, 같은 문장 재측정에서 확인한 드리프트(1~10%)보다 작은
  차이는 판정에 쓰지 않았다.
