# 장소 목록 조회의 DB 비용을 단계적으로 줄인 과정

여러 동네에서 태그 조건에 맞는 장소를 인기순으로 조회하는 기능을 최적화했다. 출발점은 통계 값과 동네 ID를 한 테이블에 두고, 동네 안의 정렬 순서를 인덱스로 제공하는 것이었다. 이후 태그 주도 계획과 동네 주도 계획의 비용을 비교하고 동적 힌트를 검토한 뒤, 태그 판정을 비트마스크로 옮겼다. 동네별 Top-K와 Prepared Statement 재사용은 각각 탐색량과 반복 문장 처리 비용을 줄이는 후속 단계였다.

```text
동네 ID 비정규화 + 동네별 정렬 인덱스
  → IN + EXISTS: 태그 주도 / 동네 주도 계획 비교, 동적 힌트 검토
  → IN + 비트마스크: 태그 조인과 후보별 태그 조회 제거
  → UNION ALL + 비트마스크: 동네별 Top-K로 조기 종료
  → Prepared Statement 재사용: 반복 문장 처리 비용 절감
```

이 문서는 DB 조회 경로의 개선만 다룬다. 인메모리 설계는 [별도 문서](2026-09-21-place-list-design-evidence.md)의 범위다. 성능 수치는 **2026년 8월의 기존 벤치 결과**이며, 9월 21일에는 자료와 대상 브랜치의 코드를 대조하고 판단 근거를 보완했다. 현재 운영 성능이나 진행 중인 인메모리 구현의 검증 결과가 아니다. **2026-09-23에는 메인 태그 동등 조건과 복합 인덱스를 추가했다. 기존 측정은 이 추가 전 결과이며, 새 구조의 성능은 재측정하지 않았다.**

## 1. 기능과 상황

한 페이지에 장소 10곳과 다음 페이지 존재 여부를 판단할 1곳, 총 **11건(K=11)**을 조회한다. 요청은 동네 하나 또는 여러 동네를 포함하고, 태그 조건은 그룹 안에서는 OR, 그룹 사이에서는 AND로 적용한다.

장소별 동네·인기 점수 등 조회용 값은 `place_stats`에 한 행씩, 태그 관계는 `place_tag`에 여러 행으로 저장했다. 초기 구조는 동네를 `IN`으로 좁히고 `EXISTS`로 태그를 확인했다. 인기순 인덱스는 `(town_id, popular_score DESC, place_id ASC, …)` 형태다. 마지막 장소 ID는 동점 순서를 확정하는 기준이다.

비교 데이터는 서울 18개 동네, 동네당 약 100곳으로 요청 지역의 후보가 약 1,800곳인 규모였다. 성장 실험에서는 동네당 200곳으로 늘렸다. 관리형 태그는 당시 자료상 34개였고, 흔한 단일 태그(동네 내 통과율 약 17%)와 다중 태그 조합(약 9%)을 따로 측정했다. 전국 후보 수와 요청 지역 안의 통과율은 다른 값이며, 전국에서 흔한 태그도 지역·다른 태그와의 조합에서는 드물 수 있다. 읽기가 쓰기보다 잦다는 서비스 특성을 설계 전제로 삼았지만, 정확한 운영 읽기/쓰기 비율이나 희귀 조건의 요청 비중을 측정한 근거로 쓰지는 않는다.

목표는 단건 지연 몇 ms를 줄이는 것에 그치지 않았다. **같은 DB 자원에서 더 많은 요청을 처리하고, 데이터 증가에 따라 요청당 작업이 늘어나는 정도를 줄이는 것**이었다.

### 출발점: 정렬에 필요한 동네 정보를 함께 저장했다

통계 테이블에 정렬 값만 있으면 요청 지역을 알기 위해 장소 원본을 조회해야 한다. 동네 ID를 통계 테이블에 함께 두면 `(town_id, 정렬 키, place_id)` 인덱스로 동네 구간을 찾고 그 안의 정렬 순서대로 읽을 수 있다. 실제 V24부터 동네 정보와 인기순 인덱스가 함께 도입돼 있다. 여기서 “정렬 값을 먼저 두고 동네를 추가한다”는 것은 설계의 논리적 순서이며 별도 배포 이력을 뜻하지 않는다.

동네가 별도 테이블에 있든 TOWN 타입 태그로 표현되든, 이 조회 인덱스에 동네 ID를 싣는 목적은 같다. **동네별로 정렬된 후보를 제공하는 것**이다. 다만 여러 동네를 `IN`으로 합치면 전역 순서는 별도 정렬이 필요하므로, 동네별 인덱스만으로 모든 정렬을 제거한 것은 아니다.

## 2. 첫 번째 판단: 태그 후보부터 찾을 것인가, 동네의 장소를 읽으며 판정할 것인가

### 확인한 문제

태그를 별도 테이블에서 확인하면 Optimizer는 어디부터 읽을지 선택해야 한다.

```text
태그 주도: 전국 태그 후보 → 장소별 PK 조회 → 요청 동네 확인 → 중복 처리·정렬
동네 주도: 요청 동네 후보 → 정렬 → 순서대로 태그 확인 → 11건 확보 시 확인 종료
```

`place_tag`에는 동네 정보가 없었다. 태그 주도 계획은 태그로 후보를 줄여도 전국에서 찾은 후보를 장소별로 다시 조회해야 요청 동네에 속하는지 알 수 있었다. 반면 동네 주도 계획은 여러 동네의 후보를 먼저 읽고 정렬하는 대가로, 이후의 태그 확인을 전역 11건을 확보한 시점에 멈출 수 있었다.

동일한 2 vCPU MySQL의 희귀 조합 요청에서 자연 선택과 힌트 강제 계획을 비교했다.

| 계획 | 실행당 rows examined | 평균 실행시간 | 달성 QPS |
|---|---:|---:|---:|
| 자연 선택: 태그 주도 | 4,579 | 2.87ms | 1,115 |
| 강제: 동네 주도 | 2,658 | 1.44ms | 2,058 |

선택된 계획의 처리량이 약 46% 낮았다. 여기서 행 수는 **전체 문장의 digest 지표**로, 서로 다른 장소 수나 한 인덱스의 스캔 행 수와 같지 않다. 이 결과는 단건 지연보다 반복 조회가 소모하는 DB 자원에 개선 여지가 있음을 보여줬다. [측정 정본 §3.2](../perf/2026-08-20-in-union-mask-load-grid.md)

### 비교한 대안과 선택 근거

**Histogram으로 추정을 보완할 수 있는가?** 초기에는 `tags.active`의 통과율 오추정이 있었고, Histogram으로 개선된 사례도 있었다. 이 조건은 요청 단계에서 이미 검증하므로 불필요한 `tags` 조인을 제거했다. 그 뒤 남은 `place_tag` 조인의 비용 순위 문제를 앞선 통계 오류와 구분했다. [초기 조사](2026-08-11-tag-filter-join-order.md)

별도의 단일 태그 규모 실험에서는 핵심 후보 수인 태그 1,146건과 지역 1,800건의 예상·실제가 맞았는데도, 예상 비용은 태그 주도 519 / 동네 주도 948, 실제 시간은 1.32 / 0.905ms로 순위가 반대였다. 이는 **위 QPS 표와 다른 실험**이다. 주요 후보 수가 맞는 상황에서 Histogram만으로 비용 순위까지 바로잡힌다고 기대할 근거는 약했다. 모든 중간 단계의 추정이 정확했다거나 특정 비용 항목의 오차를 분리 규명했다는 뜻은 아니다. [규모별 대조 §3](../perf/2026-08-11-join-order-threshold.md)

**동적 Hint로 유리한 계획을 고를 수 있는가?** 조인 순서와 FirstMatch를 함께 강제한 실제 요청에서는 1.99→1.03ms로 개선됐다. 그러나 조인 순서만 강제하면 세미 조인 전략이 바뀌어 개선되지 않는 경우도 있었다. 동적 힌트는 과거에 구현·검토된 뒤 철회된 대안이다. [힌트 조합 실험 §5](../perf/2026-08-11-join-order-threshold.md), [철회 근거](2026-08-18-tag-filter-join-order-digest.md)

계획을 나누는 기준은 전국 태그 후보 수 하나로 정할 수 없었다. 요청 동네의 후보 수, 태그 그룹의 결합 통과율, 정렬 기준도 영향을 줬다. 서울 후보를 3,600건으로 동일하게 두고 서울 밖의 증가량만 달리한 실험에서도, 흔한 태그의 전국 행 수가 2,210 / 1,407로 달라지자 선택이 동네 주도 / 태그 주도로 바뀌었고 처리량은 각각 1,650 / 1,020 QPS였다. 이 실험은 **전체 DB 크기를 같게 통제한 비교가 아니라 조회 범위 밖의 분포에 대한 의존성 확인**이다. [성장 분포 기록](2026-08-21-multi-town-query-cost-structure.md)

따라서 약 1ms의 이득이 작다는 이유만으로 힌트를 포기한 것은 아니다. 그 이득을 유지하려면 조건별 성능 경계, 통계 공급, 분포 변화 후 재측정과 힌트 적용 여부 확인을 계속 관리해야 했다. 고정 힌트는 판단 규칙을 줄이지만 후보별 태그 조회는 남기고, 태그 주도가 더 적합한 조건도 포기한다.

### 해결과 추가 부담

**태그 관계를 `place_stats.tag_bitmask`에 함께 저장했다.** 그룹별 태그 집합을 마스크로 만들고 읽고 있는 인덱스 엔트리에서 판정한다.

```sql
AND (ps.tag_bitmask & :group1Mask) != 0
AND (ps.tag_bitmask & :group2Mask) != 0
```

마스크를 정렬용 커버링 인덱스에도 넣어 태그 확인을 위한 `place_tag` 조회와 테이블 본문 재조회를 피했다. 그룹 내부 OR와 그룹 사이 AND는 유지한다. 태그 조인 순서와 세미 조인 전략 선택은 사라지지만, **인덱스 선택 등 모든 실행계획 선택이 고정되는 것은 아니다.**

### 왜 현재 조회에서는 동네 후보를 읽으며 비트 연산으로 판정하는 것이 합리적인가

**첫째, 동네 조건만으로 읽을 범위가 작아진다.** 서비스의 조회는 전국의 태그 매칭 장소를 모두 찾는 기능이 아니라, 사용자가 고른 지역 안에서 정렬된 11건을 찾는 기능이다. 당시 동네당 약 100곳, 서울 18개 동네를 합쳐도 후보는 약 1,800곳이었다. 마스크 방식이 감수하는 것은 전국 장소의 전량 스캔이 아니라 **이미 지역으로 한정된 인덱스 구간의 스캔**이다. 동네가 추가되어 전국 데이터가 늘어도 요청 지역이 같다면 읽을 후보 범위가 함께 늘지는 않는다.

**둘째, 후보 수만큼 중요한 것은 후보 한 건을 확인하는 비용이다.** `(tag_id, place_id)` 인덱스는 태그가 붙은 장소 ID를 찾지만 그 장소의 동네·점수까지 알려 주지 않는다. 태그 주도 계획은 후보마다 `place_stats`를 별도로 탐색해 지역을 확인하고 정렬 값을 얻는다. 반면 동네 주도 마스크 방식은 각 동네의 인덱스 구간 시작을 찾은 뒤 엔트리를 순서대로 읽고, 그 안에 있는 마스크를 검사한다. 고정된 최대 세 그룹의 비트 AND와 비교로 판정하므로 태그 확인을 위한 추가 B+Tree 탐색이 없다. 버퍼 풀에 데이터가 있어도 별도 인덱스를 반복 탐색하는 CPU 작업과 이미 읽은 값에 연산하는 작업의 차이는 남는다.

따라서 비교할 것은 단순히 “태그 후보가 지역 후보보다 적은가”가 아니다.

```text
태그로 먼저 좁히기
  전국 태그 후보 읽기 + 후보별 장소 조회 + 나머지 태그 확인 + 중복 처리·정렬

지역으로 먼저 좁히고 마스크 판정
  요청 동네의 인덱스 구간 읽기 + 엔트리 안에서 그룹별 비트 판정 + 통과 결과 정렬
```

예를 들어 별도 규모 실험의 태그 후보는 1,146건으로 지역 후보 1,800건보다 적었다. 그러나 이 계획은 장소 PK 조회를 1,146회 수행했고, 요청 지역에 남은 것은 326건이었다. **처음 후보가 더 적다는 사실만으로, 작은 지역 구간을 읽는 것보다 총비용이 작다고 볼 수 없었던 이유**다. 이 수치는 두 접근 방식의 차이를 설명하는 근거이며 비트 연산 한 번의 속도를 측정한 값은 아니다. [실행 트리](../perf/2026-08-11-join-order-threshold.md)

**셋째, 태그로 찾은 순서는 서비스가 반환할 순서가 아니다.** 태그 인덱스에서 11개를 찾았다고 인기순 상위 11개가 정해지지 않는다. 지역·다른 태그를 만족하는 후보의 점수를 확인한 뒤 비교해야 한다. 동네 중심의 정렬 인덱스는 동네 안에서는 반환할 점수 순서로 읽을 수 있고, 마스크는 그 순서를 유지한 채 판정할 수 있다. 이 성질이 다음 단계의 동네별 Top-K와 결합하면 11건 확보 후 탐색을 멈추는 근거가 된다. 다만 **이 단계의 여러 동네 `IN` 조회에는 여전히 전역 정렬이 필요하다.** 비정규화만으로 조기 종료까지 얻었다고 설명하지 않는다.

이 구조적 판단은 같은 `IN` 형상을 유지한 비교로도 확인했다. 희귀 조합에서 `IN + EXISTS`는 1,115 QPS, `IN + 비트마스크`는 3,869 QPS였다. 마스크 방식은 지역 후보를 모두 읽었는데도 태그 조인과 반복 Lookup을 없앤 쪽의 처리량이 높았다. 즉 당시 규모에서는 **태그로 후보를 더 줄이기 위해 조인하는 비용보다, 작은 지역 후보 집합을 읽으며 싸게 판정하는 비용이 낮았다.** 이는 해당 조건의 전체 쿼리 비교이지, 태그 조인·중복 제거·정렬 각각의 기여를 분리한 수치는 아니다. [같은 형상 비교](../perf/2026-08-20-in-union-mask-load-grid.md)

선택의 근거는 비트 연산 자체가 빠르다는 사실만이 아니다. **지역으로 한정된 작은 후보 집합, 동네별 정렬 인덱스, 그 엔트리에서 끝나는 태그 판정**을 함께 이용할 수 있었기 때문이다. 태그를 먼저 찾는 경로를 유지하기보다 요청의 지역·정렬 조건에 맞춘 읽기 경로를 단순하게 만드는 편이 합리적이었다.

### 비정규화로 추가된 갱신 책임

읽는 시점의 태그 관계 조회를 없애는 대신, 태그가 바뀔 때 조회용 표현을 미리 맞추는 책임을 부담한다. 당시 관리형 태그 34개는 정수 마스크로 표현할 수 있었고, 장소마다 하나의 마스크를 갱신하면 여러 조회가 이를 재사용한다. 다음은 그 책임을 구현한 내용이다.

- `place_tag`를 원본으로 유지하고, 장소 태그 변경과 마스크 재계산을 같은 트랜잭션에서 처리한다. 현재 코드의 `AdminPlaceService`는 변경 후 `upsertRowsForActivePlaces`를 호출하고, 저장소는 flush 후 `BIT_OR(1 << tag_id)`로 마스크를 만든다. 전체 재생성 경로도 원본에서 계산한다.
- 원본만 바꾸는 별도 SQL·이관 경로가 생기면 마스크도 갱신해야 한다. 누락은 느린 조회가 아니라 **잘못된 필터 결과**를 만든다. 재생성 수단이 있다는 것과 자동 불일치 탐지·복구가 있다는 것은 다르다.
- 마스크를 담은 인덱스가 넓어지고, 태그 변경 시 해당 인덱스 엔트리도 갱신한다. 추가 저장 공간·쓰기 비용은 이번 자료에서 별도로 정량화하지 않았다.
- 현재 구현은 태그 ID를 비트 위치로 쓰며 최대 ID 62를 허용한다. 태그 개수뿐 아니라 ID 소진도 제약이다. 상한을 넘는 생성은 거부하고 표현 방식을 재검토해야 한다.

구현 근거: [마스크와 정렬 인덱스 도입](../../src/main/resources/db/migration/V34__place_stats_read_model.sql), [태그 마스크 변환](../../src/main/java/org/sopt/solply_server/domain/place/util/TagBitmask.java), [쓰기 저장소](../../src/main/java/org/sopt/solply_server/domain/place/repository/PlaceStatsRepository.java).

### 이 판단에서 남는 한계

비트 AND는 태그 조건을 B+Tree의 탐색 범위로 바꾸지 않는다. 필터 통과율이 낮으면 지역 후보 대부분을 읽는 한계는 그대로다. 이번 선택은 그 작업을 없앤 것이 아니라 **당시 지역 후보 규모에서 감당할 읽기 비용을 낮춘 것**이다. 태그 후보가 극히 적을 때 태그 주도가 더 빨랐던 기존 실험도 있으므로 모든 태그 조합에서 최저 비용이라고 주장하지 않는다.

**단계 기록 — 결정과 근거:** 작은 지역 인덱스 구간을 읽고 엔트리 안에서 판정하는 비용이 전국 태그 후보의 반복 장소 조회보다 낮았고, 같은 IN 형상의 부하 비교가 이를 뒷받침해 비정규화를 선택했다. **구현 변경:** 과거에 마스크 컬럼·커버링 인덱스·쓰기 갱신을 도입했으며 이번에는 코드 대조와 설명 보완만 했다. **검증 결과:** 기존 자연/강제 계획의 QPS와 결과 해시 대조 기록, 현재 갱신 코드 확인. **해석의 한계:** 희귀 태그에서 역색인의 이점을 포기했고, 갱신 비용·운영 요청 비중·현재 쓰기 경로의 실행 테스트는 새로 측정하지 않았다.

### 메인 태그는 인덱스로 좁히고 추가 태그만 검사한다 — 2026-09-23 구현

앞선 판단을 더 구체화하면 모든 태그를 같은 방법으로 처리할 필요는 없다. 요청의 메인 태그는 단일 선택이고, 현재 어드민 쓰기 경로도 장소에 메인 태그 하나를 연결한다. 이미 비정규화된 `main_tag_id`를 동네 다음에 배치하면 두 동등 조건으로 범위를 제한하면서 정렬 순서를 유지할 수 있다.

```text
메인 태그 미선택: (town_id, 정렬 키, place_id, …)
메인 태그 선택:   (town_id, main_tag_id, 정렬 키, place_id, …)
                  → 추가 태그 그룹만 비트마스크로 판정
```

추가 태그는 여러 그룹과 OR 조합이 있으므로, 이번에는 그 조합마다 탐색 인덱스를 만들지 않고 정렬된 후보를 읽는 중에 판정한다. 선택의 부담은 이제 **동네·메인 태그로 줄인 후보를 추가 태그 때문에 끝까지 읽을 수 있다는 것**이다. 작은 후보 집합을 저렴하게 검사하는 방향은 유지하되, 단일 동등 조건으로 줄일 수 있는 범위는 인덱스로 먼저 줄인다.

메인 태그 선택 시 SQL은 `ps.main_tag_id = :mainTagId`를 사용하고, 나머지 그룹은 기존 비트 AND를 유지한다. 메인 태그 비트도 마스크에 그대로 저장한다. 이 비트를 빼도 BIGINT 저장 크기가 줄지 않고, 전체 태그 집합을 쓰는 다른 조회 경로와 표현이 달라지기 때문이다. 두 값은 기존 원본 갱신 트랜잭션에서 함께 재계산한다.

[신규 V49 마이그레이션](../../src/main/resources/db/migration/V49__place_stats_main_tag_sort_indexes.sql)은 기존 동네별 인덱스를 유지하고 정적 정렬 5종의 메인 태그 인덱스를 추가한다. 최신순의 동점 ID 방향, 평점순의 리뷰 수 보조 정렬, 표시값·마스크 커버링을 그대로 유지했다. 기존 강제 인덱스 옵션도 메인 태그 유무에 맞는 인덱스를 지목한다. 기본 설정에서 실제 인덱스 선택은 Optimizer가 수행한다.

기존 `main_tag_id`는 첫 MAIN 태그를 고르는 표시값이었으므로, 목록 대상 장소에 서로 다른 MAIN 태그가 둘 이상 있으면 마이그레이션을 중단한다. 임의로 하나만 골라 기존 필터 결과를 누락시키지 않으며, 원본 정리가 끝난 뒤 적용해야 한다. 정상 데이터는 원본에서 `main_tag_id`를 갱신하고, MAIN이 없는 장소는 NULL로 유지한다.

**얻는 것:** 메인 태그로 후보를 제한하면서 동네 안의 정렬 순서를 활용할 수 있는 접근 경로. **추가 부담:** 정렬 인덱스 5개의 저장·갱신 비용. **확인 범위:** 쿼리 결과·커서와 마이그레이션 정합성은 테스트 대상으로 두고, 추가 성능 측정은 하지 않았다. 기존 QPS 수치는 메인 태그 인덱스 도입 전 결과이므로 이 구조의 실측값으로 옮기지 않는다.

## 3. 두 번째 판단: 여러 동네를 한 번에 읽을 것인가, 동네별 Top-K를 합칠 것인가

### 확인한 문제

태그 판정 비용을 줄인 뒤에도 여러 동네를 `IN`으로 읽는 구조는 남았다. 인덱스는 동네별 점수순이므로 서로 다른 동네를 합친 전역 점수순을 바로 제공하지 못한다. 확인한 계획에서는 요청 동네의 후보를 모두 읽고 마스크로 거른 뒤 전역 Top-K를 구했다.

여기서 **전체 후보를 읽는 것과 전체 후보를 완전히 정렬하는 것은 다르다.** 마스크에서 탈락한 행은 정렬에 들어가지 않고, MySQL의 Top-N 정렬은 상위 K개만 유지할 수도 있다. 다만 더 높은 점수의 후보가 남았는지 확인하기 위해 해당 동네 구간들을 끝까지 읽는 작업은 남는다.

### 비교한 대안

- **`IN + 비트마스크`:** SQL 구조가 짧고 단순하다. 후보가 적으면 전량 읽기의 비용보다 분할·병합 비용을 피하는 이점이 컸다.
- **동네별 SQL을 앱에서 병렬 실행:** 개별 동네의 정렬 인덱스를 쓸 수 있지만 문장 실행·왕복이 동네 수만큼 늘고, 앱의 병합과 커넥션 동시 점유 관리가 추가된다. 기존 실험은 단일 동네 문장들의 DB 처리량을 측정한 것이며, 완성된 병렬 API의 성능 비교는 아니다. DB 작업 효율을 우선해 채택하지 않았다.
- **한 SQL 안의 `UNION ALL`:** 각 동네에서 조건에 맞는 상위 11건을 구하고, 그 결과만 합쳐 전역 상위 11건을 반환한다. 여러 브랜치가 있어도 앱이 보내는 SQL은 하나다. 병렬 실행을 보장하는 구조라는 뜻은 아니다.

분할만 먼저 적용한 `UNION ALL + EXISTS`도 측정했다. 흔한 태그에서는 통합 조회가 정렬 후 태그 확인을 57회에 끝낸 반면, 분할 조회는 동네마다 11건을 채우느라 1,185회 확인했다. **분할하면 태그 Lookup도 줄어든다는 예상은 성립하지 않았다.** `EXISTS`를 비트마스크로 바꿔 후보 판정 단가를 낮춘 뒤에야 분할의 이점이 살아났다. [네 구조 및 개별 문장 비교 §3](../perf/2026-08-20-in-union-mask-load-grid.md)

### 해결: 동네 안의 정렬 순서를 살렸다

```text
각 동네의 정렬 인덱스 구간
  → 커서 이후 후보의 태그 판정
  → 통과 11건을 찾으면 해당 동네 탐색 종료
  → UNION ALL로 최대 동네 수 × 11건 병합
  → 같은 기준으로 최종 정렬 → 전역 11건
```

결과가 정확한 이유는 간단하다. 어떤 장소보다 앞선 결과가 자기 동네에 이미 11개 있다면, 그 장소는 전역 상위 11개에도 들어갈 수 없다. 따라서 **같은 필터와 커서 조건을 먼저 적용한 동네별 Top-11**의 합집합에 전역 Top-11이 반드시 포함된다.

성립 조건은 동네 집합이 중복되지 않고 장소가 하나의 동네에 속하며, 브랜치와 바깥 정렬이 장소 ID 동점 처리까지 같은 순서를 쓰는 것이다. 인기순은 `점수 DESC, 장소 ID ASC`다. 커서 조건도 브랜치 안에 넣어 다음 페이지 후보 중 Top-K를 구한다. 이 증명은 한 번의 조회 결과에 관한 것이며, 서로 다른 페이지 요청 사이의 데이터 변경까지 막아 주지는 않는다.

현재 [DB 조회 저장소](../../src/main/java/org/sopt/solply_server/domain/place/repository/querydsl/PlaceListDbQueryRepository.java)의 `townBranchedSql`이 브랜치별 정렬·LIMIT과 바깥 정렬·LIMIT을 생성한다. 단일 동네는 병합 없이 조회한다. 여기서의 인덱스 조기 종료 근거는 인기순 등 인덱스 순서와 맞는 정렬에 해당하며, 요청 좌표에 따라 순서가 달라지는 거리순으로 일반화하지 않는다.

### 현재 규모와 성장 규모에서 달랐던 결과

태그 분포 비율을 유지하고 동네당 장소를 약 100→200곳으로 늘린 **DB 단독 부하 실험**이다. 앞 절의 전국/서울 성장 분포 비교와 목적이 다르다.

| 조건 | 구조 | 동네당 100곳 QPS | 동네당 200곳 QPS |
|---|---|---:|---:|
| 흔한 태그 | IN + 비트마스크 | 3,763 | 2,198 |
| 흔한 태그 | UNION ALL + 비트마스크 | 3,353 | 2,941 |
| 희귀 조합 | IN + 비트마스크 | 3,869 | 2,239 |
| 희귀 조합 | UNION ALL + 비트마스크 | 2,742 | 2,023 |

흔한 태그에서 `IN`의 QPS는 약 42%, `UNION ALL`은 약 12% 감소했다. 성장 규모에서는 `UNION ALL`이 약 34% 높았다. 현재 규모의 최고 QPS를 포기하는 대신, **태그 통과율과 동네 수가 유지되는 성장 조건에서 읽기 증가를 완화하는 구조**를 선택했다. 이 42%/12%는 비트마스크 적용 후 두 구조의 성장 민감도 비교이며, 최초 `EXISTS`부터의 전체 개선율이나 비트마스크 단독 효과가 아니다. [성장 실험 기록](2026-08-21-multi-town-query-cost-structure.md)

### 추가 부담과 반대 선택의 조건

브랜치마다 인덱스 탐색을 시작하고 결과를 병합해야 한다. 확인한 실행계획에는 내부 임시 테이블 기록·읽기와 최종 filesort가 있었다. `UNION ALL`은 중복 제거를 하지 않지만, 이 병합 작업까지 없애지는 않는다. 고정 비용이라는 표현도 **동네 수를 고정했을 때**만 맞는다. 동네가 늘면 브랜치·SQL 길이·최대 병합 행 수가 함께 증가한다.

필터를 통과하는 비율이 낮으면 각 동네에서 11건을 채우지 못해 거의 끝까지 읽는다. 직관적으로는 동네당 후보 수 N, 통과율 p일 때 `min(N, K/p)` 정도를 생각할 수 있지만, 이는 매치가 정렬 순서에 고르게 섞였다는 근사다. 매치가 낮은 점수대에 몰리면 전체 통과율이 같아도 더 깊이 읽는다. **K개를 반환한다고 K개만 읽는 것은 아니다.**

희귀 조합의 표가 이 한계를 보여준다. 100곳에서는 `UNION ALL`의 QPS가 `IN`보다 약 29% 낮았고, 200곳에서도 수치상 우위를 얻지 못했다. 후자의 약 10% 격차는 당시 측정 변동과 가까워 작은 순위 차이를 확정하지 않는다. 희귀 조합이 실제 요청에서 드물다는 운영 근거도 없으므로 가중 평균 성능이 개선됐다고 주장하지 않는다.

따라서 후보가 작거나, 통과율이 낮거나, 동네 수가 많아 분할 비용이 커진다면 `IN`이 더 적합할 수 있다. 지역 자체가 매우 크고 태그 매치가 극히 적다면 앞 절의 태그 역색인부터 다시 비교할 조건이다. 이러한 요청별 동적 전환을 새로 구현한 것은 아니다.

**단계 기록 — 결정과 근거:** 동네별 정렬 인덱스의 조기 종료를 활용해 성장 시 작업량 증가를 완화했다. **구현 변경:** 과거의 브랜치별 필터·커서·Top-K 및 전역 Top-K 구현을 확인했으며 이번에는 설명만 보완했다. **검증 결과:** 기존 SQL 결과 해시 대조, 실행계획, 100/200곳의 조건별 QPS를 대조했다. **해석의 한계:** 흔한 태그의 이득을 희귀 조건·임의 규모·모든 정렬에 확대하지 않는다. 태그 통과율이 낮을 때 전량에 가까운 스캔은 해결하지 못했다.

## 4. 세 번째 판단: 길어진 SQL을 줄일 것인가, 준비한 문장을 재사용할 것인가

### 확인한 문제

동네별 쿼리 본문을 복제한 `UNION ALL`은 DB 탐색량을 줄였지만 SQL을 길게 만들었다. 당시 18개 동네의 평점순 커서 요청은 최대 9,378자, 바인드 127개였다. DB에 SQL을 직접 보내는 앞선 부하 실험으로는 앱·드라이버에서 이 문장을 처리하는 비용을 볼 수 없었다.

앱을 포함한 CPU 프로파일에서는 SQL 문자열 조립 비중이 0.07%였고, 드라이버의 문장 분석이 6.8%, 패킷 조립·송신이 5.6%로 관측됐다. 긴 문장을 생성하는 것보다 만들어진 문장을 실행마다 분석하고 값과 합쳐 보내는 경로가 조사 대상이 됐다. 이 비율은 **당시 프로파일의 표본 비중**이며, 모두 `UNION ALL` 전환 때문에 새로 생긴 비용이라고 분해한 수치는 아니다. [프로파일 원자료](../../load-test/campaigns/2026-08-28_gc-decomposition/results/diagnosis-app-cost.md)

### 비교한 대안과 선택 근거

기존 `IN` 형상, `UNION ALL` 기본 설정, 드라이버 캐시만 켠 설정, 서버 Prepared Statement까지 켠 설정을 비교했다. 문장을 짧게 만드는 `JSON_TABLE + LATERAL`도 구현해 검사했지만, **측정한 MySQL 8.0의 해당 형상**에서는 동네별 구간을 전량 읽고 정렬했다. 데이터 2배 조건에서 QPS가 `UNION ALL`보다 약 24% 낮아 되돌렸다. 모든 LATERAL 쿼리나 다른 MySQL 버전에서도 불가능하다는 결론은 아니다. [대안 구현·기각 및 설정 비교](../perf/2026-08-29-394-stmt-shape.md)

따라서 동네별 조기 종료 구조를 유지하면서 이미 준비한 문장을 재사용하는 쪽을 택했다. 두 설정의 역할은 다르다.

| 설정 | 재사용하는 것 | 여전히 반복하는 것 |
|---|---|---|
| `cachePrepStmts=true`만 적용 | 물리 커넥션별 드라이버의 문장 분석 정보 등 | 클라이언트 방식에서는 값이 반영된 SQL 텍스트 전송과 서버 처리 |
| 위 설정 + `useServerPrepStmts=true` | 해당 DB 세션에 준비한 문장과 드라이버 측 문장 재사용 | 문장 ID·파라미터 전송, DB 조회 실행, 결과 반환 |

JDBC의 `PreparedStatement` API를 쓴다는 사실만으로 서버 문장 재사용까지 켜지는 것은 아니다. Connector/J의 `cachePrepStmts`는 클라이언트 문장 분석뿐 아니라 서버 준비 가능 여부와 서버 Prepared Statement 자체의 캐시도 제어한다. 서버 측 준비는 최초 `COM_STMT_PREPARE` 후 ID를 받아 `COM_STMT_EXECUTE`로 실행하는 방식이다. [Connector/J 설정](https://dev.mysql.com/doc/connector-j/en/connector-j-connp-props-performance-extensions.html), [서버 준비 사용 설정](https://dev.mysql.com/doc/connector-j/en/connector-j-connp-props-prepared-statements.html)

서버가 보관하는 것은 반복 파싱·분석을 줄이기 위한 문장 내부 구조다. **조회 결과 캐시나 모든 세션이 공유하는 고정 실행계획 캐시로 설명하지 않는다.** 메타데이터 변경 등으로 재준비가 발생할 수 있으므로 파싱이 영구히 한 번뿐이라는 보장도 아니다. [MySQL 문장 캐싱](https://dev.mysql.com/doc/refman/8.0/en/statement-caching.html)

### 해결과 검증 결과

동네 ID·마스크·커서·LIMIT 값을 바인딩하는 기존 쿼리에 다음 설정을 적용했다.

```properties
cachePrepStmts=true
prepStmtCacheSqlLimit=16384
prepStmtCacheSize=512
useServerPrepStmts=true
```

캐시를 켜도 SQL 길이 제한이 작으면 긴 문장이 제외된다. 물리 커넥션별로 재사용하므로 커넥션 워밍업도 필요하다. 값만 달라지면 같은 SQL을 재사용할 수 있지만, 동네 수·정렬·커서 유무·태그 그룹 유무가 바뀌면 SQL 형상은 달라진다.

같은 측정 창에서 DB 경로로 조회하도록 고정하고 JDBC 설정을 바꾼 결과다. 목표 부하는 약 571 req/s였으며 앱과 MySQL에 각각 2 vCPU를 배정했다. 요청당 CPU는 cgroup 누적 CPU 사용량을 응답 수로 나눈 값으로, 요청 응답시간과 다르다.

| 설정 | 앱 CPU / 요청 | DB CPU / 요청 | 앱 스로틀 발생 주기 비율 |
|---|---:|---:|---:|
| 재사용 설정 없음 | 2.536ms | 1.905ms | 21.6% |
| 드라이버 캐시만 | 2.424ms | 1.895ms | 17.0% |
| 드라이버 캐시 + 서버 준비 | 2.165ms | 1.539ms | 1.4% |

결합 설정에서 요청당 앱 CPU는 약 15%, DB CPU는 약 19% 낮았다. 드라이버 캐시만으로는 남아 있던 문장 전송·서버 파싱 경로까지 줄이는 선택을 지지한다. 다만 절감분을 각 내부 작업에 정확히 배분한 실험은 아니다. JDBC 설정은 목록 SQL 외 다른 DB 문장에도 적용되므로 이 전체 차이를 장소 Top-K SQL 하나의 효과로 귀속하지 않는다.

재사용은 CPU 수치 외에도 카운터로 확인했다. 안정 구간 60초에 문장 실행 36,030회 동안 `Com_stmt_prepare` 증가가 0이었고, 서버에 상주한 문장은 합계 114개였다. 낮은 부하의 3회 교차 측정에서는 앱 CPU 차이가 산포 안이었지만 서버 준비 구성의 DB CPU가 더 낮았다. 목표 부하는 구성당 1회였고 p95 308→7ms도 관측됐으나, 절대 꼬리 지연의 재현성은 입증하지 않았다. [설정 비교 정본 §3·§6](../perf/2026-08-29-394-stmt-shape.md)

### 추가 부담과 반대 선택의 조건

재사용은 커넥션별 캐시와 DB 세션별 준비 문장을 보관하는 메모리를 요구한다. 벤치에서는 전체 커넥션 합계 114문장의 서버 메모리가 약 58MB로 기록됐다. 이때의 캐시 크기 512가 운영에서도 적절하다는 뜻은 아니다. 커넥션 수와 사용 SQL 형상이 늘면 상주 메모리, 축출과 재준비 빈도도 확인해야 한다.

문장이 짧고 거의 반복되지 않거나 커넥션 수명이 짧아 재사용이 적다면 준비·보관 비용의 이득이 작아진다. 실제 트래픽에서 형상이 지나치게 다양해 캐시가 순환한다면 크기를 무조건 키우기보다 형상 수와 재사용률부터 다시 확인한다. 짧은 단일 형상으로 바꾸면서 인덱스 조기 종료까지 유지할 수 있는 실행계획이 확인된다면 쿼리 재작성도 다시 비교할 수 있다.

줄이지 못한 작업도 분명하다. 문장 실행 횟수, 요청마다 인덱스를 읽고 태그를 판정하는 일, 브랜치 결과 병합·정렬, 결과 전송과 JDBC/Hibernate 결과 매핑·객체 생성은 남는다. Prepared Statement는 **같은 결과의 반복 조회를 없애지 않는다.**

**단계 기록 — 결정과 근거:** 동네별 조기 종료를 유지하면서 반복 문장 처리 비용을 줄이기 위해 드라이버 캐시와 서버 준비를 함께 선택했다. **구현 변경:** 과거 JDBC 설정 채택을 확인했으며 현재 저장소의 [벤치 Compose](../../docker/docker-compose.bench.yml)에 네 설정이 있다. 이번 설정 변경은 없고 운영 환경의 실제 JDBC URL 적용 여부는 확인하지 않았다. **검증 결과:** 기존 같은 창 구성 비교·프로파일·서버 카운터 기록을 대조했다. **해석의 한계:** 설정은 API의 여러 SQL에 영향을 주며, 목표 부하 1회 결과·현재 운영 재사용률을 일반화하지 않는다.

## 5. 결과와 해결하지 않은 범위

세 단계는 서로 다른 비용을 줄였다.

1. **비트마스크:** 후보마다 태그 관계를 조회하던 일을 인덱스 엔트리의 비트 판정으로 바꿨다. 태그 조인 선택 문제를 없앤 대신 파생 데이터 갱신 책임을 추가했다.
2. **동네별 Top-K:** 인덱스 순서를 활용해 충분한 결과를 찾은 동네의 탐색을 멈췄다. 흔한 태그의 2배 규모 실험에서 QPS 감소 폭은 42%에서 12%로 완화됐지만, 통과율이 낮으면 거의 전량을 읽고 병합 비용까지 부담한다.
3. **문장 재사용:** 반복 문장 분석·SQL 전문 전송·서버 파싱 부담을 줄였다. 별도 API 부하 비교에서는 결합 설정의 요청당 앱/DB CPU가 약 15%/19% 낮았지만, DB 조회와 결과 처리 자체는 계속 반복됐다.

첫 두 단계의 DB QPS와 세 번째 단계의 API CPU는 **서로 다른 측정**이므로 하나의 전후 개선율로 합치지 않는다. DB 실험은 4개 워커·지속 커넥션의 폐쇄형 부하, 셀당 약 30초, 워밍된 버퍼 풀과 2 vCPU 포화 상태의 SQL 비교다. 실제 요청 도착률, 다른 쿼리·쓰기와의 경합, 운영 최대 API 처리량을 재현한 결과가 아니다. 일부 셀은 1회 측정이며 재측정 변동보다 작은 차이는 선택 근거로 삼지 않는다.

남은 핵심은 **필터 통과율이 낮을 때의 넓은 탐색과, 같은 요청이 와도 되풀이하는 조회·전송·매핑 작업**이다. 전량에 가까운 탐색이 남는다는 사실은 반복 작업을 줄이는 다음 설계를 검토할 근거가 된다. 다만 캐싱만 도입하면 희귀 조건의 스캔 복잡도까지 자동으로 사라진다는 뜻은 아니다. 그 해결 범위는 후속 문서에서 별도로 판단한다.

## 인메모리 설계 문서에서 인용할 배경 요약

> 장소 목록 조회에서는 먼저 태그를 통계 테이블의 비트마스크로 비정규화해 태그 조인과 후보별 태그 조회를 제거했다. 이후 동네별 Top-K를 `UNION ALL`로 합쳐 조기 종료를 활용했고, 흔한 태그의 동네당 100→200곳 DB 실험에서 QPS 감소 폭을 약 42%에서 12%로 완화했다. 길어진 SQL은 Prepared Statement 재사용으로 반복 준비·전송 비용을 줄였다. 그러나 필터 통과율이 낮으면 여전히 대부분의 후보를 읽었고, 같은 요청마다 DB 탐색·필터·병합·결과 전송과 매핑은 반복됐다.

- 사용자 첨부 수치를 기존 성능 문서와 비교했고, 수치의 변화율·문서 내 로컬 링크를 점검했다. 성장 실험 수치는 기존 성장 기록을 인용하며 이번 DB에서 재현하지 않았다.
- 새 구현 변경·부하 측정·애플리케이션 테스트는 하지 않았다. 기존 비교와 코드로 문서의 선택 근거를 구성할 수 있고, 진행 중인 다른 구현에서 성능을 다시 재면 과거 선택을 검증하는 비교 조건이 달라지기 때문이다.
- 새 측정이 필요한 조건은 운영의 희귀 필터 비중·동네 규모·SQL 재사용률 변화로 선택을 다시 해야 할 때다. 그때 비교할 주장과 바뀔 결정을 먼저 정한다. 이번 문서의 기존 수치를 운영 보장으로 바꾸지는 않는다.
