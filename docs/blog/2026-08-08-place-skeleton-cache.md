# 반복적인 DB 조회와 Hibernate 하이드레이션을 스냅샷 캐시로 제거한 과정

이 작업은 평상시 응답시간 몇 ms를 줄이기 위한 캐시 도입이 아니었다. 앱 2 vCPU와 DB 2 vCPU로
구성한 서버에서 가장 많이 호출되는 장소 목록 API가, 평상시 60 arrivals/s에서 피크
300 arrivals/s로 갑자기 증가해도 안정적으로 동작하는지 검증하는 것이 출발점이었다.

기존 엔티티 경로는 요청을 모두 처리했지만 CPU 평균 61.8%, CFS 스로틀링 8.12%, Hikari
pending 12와 함께 p99가 96ms까지 상승했다. 오류율 0%만으로 안정적이라고 판단할 수 없었다.
요청당 CPU 비용을 낮춰 같은 2 vCPU 안에서 피크와 JVM의 순간적인 추가 작업을 흡수할 여유를
확보하는 것을 목표로 삼았다.

## 1. 왜 Docker에 2 vCPU limit을 걸었나

실제 2 vCPU 서버 두 대를 준비한 것은 아니다. 먼저 앱 2 vCPU 서버와 DB 2 vCPU 서버에 각각
배포한다는 모델을 정하고, 로컬의 Docker cgroup CPU quota를 각각 2 vCPU로 고정해 자원 예산을
근사했다.

앱과 MySQL이 호스트 CPU를 제한 없이 나눠 쓰면 매 라운드가 사용할 수 있는 자원이 달라진다.
CPU limit은 지연을 발견한 뒤 문제를 만들려고 추가한 조건이 아니라, 동일한 서버 사양에서
Entity·Projection·Snapshot을 비교하기 위해 테스트 전에 고정한 조건이었다.

다만 Docker의 2 vCPU quota가 실제 2코어 서버와 완전히 같지는 않다.

```text
cpu.max = 200000 100000

100ms마다 사용할 수 있는 CPU 시간 = 200ms
                              = 2코어 × 100ms
```

Docker에서는 한 주기의 quota를 소진하면 다음 주기까지 스레드 실행이 제한되고, 이것이 CFS
스로틀링으로 기록된다. 실제 2코어 전용 서버에 quota가 없다면 같은 수요 초과가 스로틀링 대신
run queue 대기로 나타날 수 있다. 따라서 이 글에서 스로틀링은 운영 서버를 그대로 복제한
지표가 아니라, **가정한 2 vCPU의 처리 여유가 사라졌다는 경고 신호**로 사용한다.

## 2. SLO 충족과 운영 안전은 다르게 판정했다

먼저 목표 피크의 합격 기준을 정했다. 운영 데이터가 없는 프로젝트이므로 실제 SLA라고 부르지
않고, 비교 실험을 위한 내부 SLO와 운영 안전 기준으로 구분했다.

| 구분 | 기준 | 확인하려는 것 |
|---|---|---|
| 사용자 성능 SLO | 오류 0%, p99 100ms 이하 | 사용자가 요청을 정상적인 시간 안에 완료하는가 |
| 운영 안전 기준 | Hikari pending 0, 앱 CPU 평균 50% 안팎 | 트래픽·JVM 변동을 흡수할 처리 여유가 남는가 |
| 포화 경고 지표 | CFS 스로틀링이 극소량이며 p99·pending에 영향을 주지 않음 | 2 vCPU의 순간 처리 한계에 반복적으로 닿지 않는가 |

CPU 50%는 단 한 번이라도 넘으면 실패하는 절대선이 아니다. 1초 최대 이용률은 짧은 burst에
민감하므로 참고값으로 두고, 피크 구간 평균과 CFS 스로틀링의 빈도·누적시간, p99와 pending을
함께 판단했다. 스로틀링 역시 0%만 통과로 정하지 않았다. 일부 주기에서 발생하더라도 짧게
끝나고 사용자 지연이나 커넥션 대기열로 전파되지 않으면 통제된 상태로 봤다.

이 구분이 필요한 이유는 **현재 요청을 성공시킨 것과 다음 변동까지 감당할 수 있는 것은 다른
문제**이기 때문이다. p99 SLO를 간신히 지켜도 CPU 여유가 없고 대기열이 생겼다면, 트래픽이
조금 늘거나 JIT 같은 JVM 작업이 겹칠 때 바로 SLO를 위반할 수 있다.

## 3. 목표 피크에서 무엇이 문제였나

새 JVM에 평상시 부하 60 arrivals/s를 주어 실제 요청 경로를 워밍업한 뒤, 같은 실행에서
300 arrivals/s로 즉시 전환했다. 완전히 워밍업된 가장 우호적인 상태만 재지 않은 이유는 실제
운영에서도 피크 전환 중 JIT 컴파일 같은 JVM 작업이 추가로 발생할 수 있기 때문이다.

기존 엔티티 경로의 결과는 다음과 같았다.

| 지표 | Entity |
|---|---:|
| p99 | 96ms |
| 최대 응답시간 | 399ms |
| 앱 CPU 평균 | 61.8% |
| CFS 스로틀 발생 주기 | 8.12% |
| 스로틀링 누적 스레드 시간 | 8,185ms |
| Hikari pending 최대 | 12 |
| 오류 | 0 |

Entity는 오류 0%, p99 96ms로 사용자 성능 SLO의 경계 안에는 들어왔다. 하지만 CPU 평균이
목표 운영선을 넘고, 스로틀링이 8.12% 발생했으며 Hikari pending도 12까지 쌓였다. 따라서
**SLO는 충족했지만 운영 안전 기준은 충족하지 못한 상태**로 판정했다.

피크 중 JIT 컴파일 시간이 2,707ms 증가했고, CPU 포화·CFS 스로틀링·pending·p99가 같은
구간에서 함께 상승했다. 별도의 JFR 진단 라운드에서도 피크 60초 동안 100ms 이상 걸린 C2
컴파일 5건(합계 1.063초), deoptimization 31건, 컴파일러 스레드 CPU 약 1.845
CPU-seconds가 관측됐다. JIT가 요청 처리와 같은 2 vCPU를 실제로 나눠 쓰고 있었던 것이다.

하지만 1.845 CPU-seconds는 피크 60초 평균으로 환산하면 약 0.031코어다. JIT가 포화를
촉발할 수는 있어도, 요청 경로의 기본 CPU 수요를 모두 설명하는 유일한 원인은 아니었다.

JIT는 자주 실행되는 코드를 실행 중 네이티브 코드로 최적화하며 CPU를 사용한다. 요청 처리만으로
CPU 여유가 부족한 상태에서는 이 일시적인 작업이 포화를 촉발할 수 있다. 해결해야 할 것은
JIT가 아니라, JIT와 경쟁하던 **요청 경로의 높은 기본 CPU 수요**였다.

### JIT 컴파일을 줄이면 해결되지 않을까

이 가능성도 실험했다. Java 21은 일반적인 C1+C2 계층형 컴파일을 유지한 채
`CICompilerCount=1`로 기동할 수 없었다. 따라서 실험군에는 C2를 중단하는
`TieredStopAtLevel=1`과 `CICompilerCount=1`을 함께 적용했다. 이는 컴파일러 스레드 수만
바꾼 A/B가 아니라 **C1-only 컴파일 정책 전체를 바꾼 진단 실험**이다.

| 피크 300 arrivals/s | 기본 C1+C2 | C1-only, Compiler 1개 |
|---|---:|---:|
| JVM 컴파일 누적 증가 | 3,635ms | 348ms |
| 컴파일러 CPU 추정 | 1.845 CPU-seconds | 0.057 CPU-seconds |
| 앱 CPU 평균 | 1.323코어 | 1.955코어 |
| CFS 스로틀 발생 주기 | 8.25% | 96.96% |
| p99 | 53ms | 9,923ms |
| 성공 / 실패 VU | 23,400 / 0 | 9,877 / 13,523 |

JIT 작업은 의도대로 줄었지만 C2가 만들어 주는 최적화된 코드를 포기하면서, 매 요청 반복되는
Hibernate·JDBC·응답 조립 코드의 실행 비용이 더 크게 증가했다.

```text
줄어든 일시적 JIT 비용
< C2를 포기해 증가한 지속적인 요청 처리 비용
```

따라서 컴파일러 스레드를 억제하는 방식은 채택하지 않았다. JIT 자체를 없애는 대신 요청당
CPU 비용을 낮춰, 요청 처리와 정상적인 JVM 작업이 함께 실행될 여유를 만드는 방향이 더
타당했다.

CFS 스로틀링도 원인이 아니라 증상이었다. CPU quota를 2 vCPU에서 4 vCPU로 높인 대조
실험에서 스로틀링과 p99가 함께 감소해 CPU 병목임을 확인했다. 하지만 이 방법은 요청당 비용을
그대로 둔 채 서버 자원을 늘리는 증설이다. 처음 가정한 2 vCPU 안에서 해결하려면 요청이 쓰는
CPU 자체를 줄여야 했다.

## 4. 요청 CPU는 어디에 쓰이고 있었나

이제 줄여야 할 요청 비용이 무엇인지 찾아야 했다. 캐시 이전 Entity 구조에 같은
`60 → 300 arrivals/s`를 적용하고, 피크 구간의 HTTP 요청 스레드만 JFR로 CPU 프로파일링했다.
5ms 주기로 수집한 3,489개 표본을 전체 호출 스택까지 확인한 뒤, 실제 CPU가 관측된 지점과
가장 가까운 소유 컴포넌트 하나에만 배정했다.

| 캐시 이전 Entity 요청 경로 | 요청 스레드 CPU 표본 비중 |
|---|---:|
| JDBC·MySQL Driver | 13.33% |
| Hibernate 하이드레이션·결과 조립 | 4.84% |
| Hibernate 쿼리·기타 ORM | 13.64% |
| 애플리케이션 응답 조립 | 0.49% |
| Jackson JSON 직렬화 | 1.98% |
| 애플리케이션 기타 | 4.87% |
| Spring·Tomcat·보안·메트릭 공통 경로 | 60.85% |

Hibernate 전체는 18.48%였고, JDBC까지 합치면 31.81%, 응답 조립까지 포함하면
**32.30%**였다. 즉 요청마다 반복하던 DB 결과 처리, ORM 엔티티 구성과 응답 조립 경로가
요청 스레드 CPU 표본의 약 3분의 1을 차지했다.

이 비율은 메서드별 정확한 CPU 시간이 아니라 샘플링 기반 추정치다. 또한 5ms 프로파일링은
포화 상태에 오버헤드를 더하므로 이 진단 라운드의 latency는 성능 결과로 사용하지 않고,
CPU가 소비되는 **구성비와 호출 경로를 찾는 용도**로만 사용했다.

코드에서 해당 경로를 따라가 보니 장소 목록을 조회할 때 애플리케이션은 매 요청 다음 작업을
반복했다.

```text
DB 조인 결과 수신
→ Hibernate 엔티티 생성
→ 연관 컬렉션 구성
→ 영속성 컨텍스트 등록
→ 응답 DTO 변환
→ JSON 직렬화
```

목록 응답에 필요한 값은 장소 이름, 대표 이미지, 메인 태그처럼 대부분 변하지 않지만, 요청마다
같은 데이터를 DB에서 읽고 객체 그래프로 다시 구성하고 있었다. 이 작업이 요청당 CPU를 키웠고,
피크에서 추가 JVM 작업과 겹치자 2 vCPU의 여유가 소진됐다.

여기서 해결 지점이 정해졌다. JSON 직렬화나 Spring MVC처럼 모든 응답에 필요한 공통 비용을
미세 조정하는 것보다, 결과가 거의 변하지 않는데도 매 요청 반복되는 약 32%의 DB·ORM·조립
경로를 줄이는 편이 효과와 변경 범위가 명확했다.

```text
반복 DB·ORM·조립 비용                 일시적 JVM 비용
        │                                  │
        └──── 요청당 기본 CPU 수요 ────────┘
                         ↓
                 2 vCPU 처리 여유 소진
                         ↓
             CFS 스로틀링 → p99·pending 증가
```

## 5. Projection과 Snapshot을 비교했다

곧바로 캐시를 도입하지 않고 두 가지 해결 후보를 같은 `60 → 300 arrivals/s` 조건에서 비교했다.

### DTO Projection

Entity와 연관 컬렉션을 만들지 않고 필요한 필드만 직접 조회한다. ORM 하이드레이션 비용은
줄지만 다음 작업은 요청마다 남는다.

```text
DB 조회 → JDBC 결과 처리 → Projection 객체 생성 → 값 변환
```

### Snapshot Cache

변경이 드문 장소 골격을 미리 조립해 메모리에 보관한다. 요청은 메모리의 골격을 사용하므로
골격 DB 조회와 결과 변환이 요청 경로에서 사라진다.

```text
배치: DB 조회 → 전체 Snapshot 생성 → 참조 교체
요청: Snapshot 조회 → 사용자별·실시간 값 결합 → 응답
```

동일한 목표 피크의 결과는 다음과 같았다.

| 지표 | Entity | DTO Projection | Snapshot Cache |
|---|---:|---:|---:|
| p99 | **96ms** | **8ms** | **8ms** |
| 최대 응답시간 | 399ms | 18ms | 40ms |
| 앱 CPU 평균 | **61.8%** | **45.0%** | **42.3%** |
| CFS 스로틀 발생 주기 | **8.12%** | **0.40%** | **0.17%** |
| 스로틀링 누적 스레드 시간 | 8,185ms | 46ms | 9ms |
| Hikari pending 최대 | **12** | **0** | **0** |
| 오류 | 0 | 0 | 0 |
| 사용자 성능 SLO | 경계 내 통과 | 통과 | 통과 |
| 운영 안전 기준 | **실패** | **통과** | **통과** |

Projection과 Snapshot 모두 목표 피크를 통과했다. Entity 대비 Snapshot은 앱 CPU 평균을
31.6%, p99를 91.7% 줄였고, 스로틀 발생 주기 비율을 8.12%에서 0.17%로 낮췄다.

동일한 JFR 설정으로 Snapshot의 요청 경로도 교차 확인했다. 두 라운드의 전체 응답 수 차이는
0.16%였고, DB·Hibernate·응답 조립에 배정된 CPU 표본은 Entity 1,127개에서 Snapshot
663개로 **41.2% 감소**했다. 그중 Hibernate 하이드레이션·결과 조립 표본은 169개에서
42개로 **75.1% 감소**했다.

Snapshot에서도 해당 경로가 0이 되지는 않았다. 목록 정렬·필터링과 사용자별 북마크처럼
요청마다 필요한 DB 작업은 남겨 두고, 변경이 드문 장소 이름·이미지·메인 태그 골격만 캐시로
대체했기 때문이다. 따라서 “모든 DB 접근을 없앴다”가 아니라 **제거하려던 반복 골격 조립
경로가 실제로 크게 감소했다**는 것이 이 프로파일의 결론이다.

Snapshot의 별도 독립 라운드에서도 p99 14ms, pending 0으로 처리했다. JIT 실행량과 CPU
순간값은 라운드마다 달랐지만, 두 번 모두 목표 피크에서 사용자 지연으로 전파되지 않았다.

## 6. Projection도 통과했는데 Snapshot을 선택한 이유

앱 CPU 차이만으로 Snapshot을 선택하지는 않았다. 독립 JVM마다 JIT 실행 시점이 달라 CPU
수치는 흔들릴 수 있고, 별도의 요청당 CPU 측정에서도 Projection과 Snapshot의 차이는 산포
안이었다.

선택을 가른 것은 **트래픽과 DB 부하를 분리할 수 있는가**였다.

Projection은 Entity 조립을 싸게 만들지만 골격 조회 쿼리 두 번과 결과 변환을 매 요청 반복한다.
Snapshot은 해당 조회를 요청 경로에서 0회로 만든다. 트래픽이 증가해도 골격 조회 수와 DB
커넥션 점유가 함께 증가하지 않는다.

구조적으로 Projection의 커넥션 점유시간은 공통 쿼리와 골격 쿼리 두 건의 점유시간을 합친
값이지만, Snapshot에는 공통 쿼리의 점유시간만 남는다. 별도의 300 arrivals/s 요청당 비용
비교 실험에서도 골격 쿼리가 요청당 2회에서 0회로 줄었고, DB CPU는 요청당 1.650ms에서
1.368ms로 17.1%, 커넥션 점유시간은 중앙값 기준 2.36ms에서 1.88ms로 약 20% 감소했다.
정확한 커넥션 절감률은 실행 환경에 따라 달라질 수 있지만, 쿼리 두 건을 제거한 만큼 점유시간이
줄어드는 방향은 구현 구조와 측정 결과가 일치한다.

따라서 최종 판단은 다음과 같았다.

> Projection만으로도 목표 응답 성능은 달성할 수 있었다. 그러나 변경이 드문 공통 데이터를
> 매 요청 DB에서 다시 읽고 변환할 이유가 남아 있었다. Snapshot으로 그 작업을 요청 경로에서
> 제거해 앱 CPU 여유뿐 아니라 다른 쿼리가 사용할 DB·커넥션 여유까지 확보했다.

## 7. Snapshot은 어떻게 구성했나

캐시에는 장소 목록의 공통 골격만 저장했다.

```text
id, name, imageUrl, mainTagName, townId
```

북마크 여부처럼 사용자마다 다른 값과 리뷰 수·평점처럼 변경되는 값은 요청 시점에 결합했다.
전체 장소가 6,320개이고 변경 빈도가 낮아 개별 키 캐시보다 불변 Map 전체를 한 번에 교체하는
방식을 선택했다.

```java
private volatile Map<Long, PlaceSkeleton> map = Map.of();
```

새 Map을 완성한 뒤 `volatile` 참조를 한 번 교체하므로 요청 스레드는 이전 또는 새 Snapshot
중 하나만 본다. 부분 갱신 상태가 노출되지 않고, 삭제된 장소도 새 Map에서 자연스럽게 빠진다.

스냅샷은 서버 시작 시 한 번 만들고, 매시 통계 배치가 끝난 뒤 전체를 다시 생성한다. 장소
6,320개의 전체 생성 시간은 94~302ms였고, 메모리는 약 1.75MiB로 힙 상한 1.25GiB의
0.14%였다. 작은 고정 메모리를 사용해 요청마다 반복되던 DB 조회와 객체 생성을 제거했다.

관리자가 즉시 수정해야 하는 요구사항이 생기면 수정 트랜잭션 커밋 후 전체 Snapshot을 다시
생성할 수 있다. 장소 수나 수정 빈도가 커져 전체 재생성 비용을 무시하기 어려워지면 개별 키
갱신 방식으로 전환할 수 있다.

## 8. CPU limit이 없는 환경에서도 의미가 있을까

CFS 스로틀링은 CPU limit이 있을 때만 발생한다. 그래서 앱·MySQL·edge의 quota를 제거하고
같은 4개 CPU에서 경쟁하게 하는 별도 실험으로, 개선 효과가 인위적인 limit에만 의존하는지
확인했다.

limit이 없으므로 컨테이너의 CFS 스로틀링은 0이었다. 대신 전체 CPU가 포화되자 PSI CPU
대기와 run queue, 응답 지연이 증가했다. 캐시 적용 후에는 요청당 전체 CPU와 SQL 문장 수,
힙 할당이 같은 방향으로 감소했다.

즉 바뀐 것은 포화가 드러나는 방식이었다.

```text
CPU limit 있음  → quota 소진 → CFS 스로틀링
CPU limit 없음  → 물리 코어 소진 → run queue 대기
```

두 환경 모두 근본 조건은 같다.

```text
요청당 CPU × 초당 요청 수 ≥ 가용 CPU
```

Kubernetes에서도 limit 없는 Pod는 노드에 여유 CPU가 있으면 request를 넘어 사용할 수 있다.
하지만 여러 Pod의 수요가 노드 용량에 닿으면 스로틀링 대신 CPU 경합과 run queue 대기가
발생한다. HPA가 Pod를 늘리더라도 메트릭 수집, 새 Pod 기동과 JVM 워밍업에는 시간이 필요하고,
모든 Pod가 공유하는 DB 부하는 합산된다.

따라서 요청당 CPU와 DB 조회를 줄이는 일은 단일 인스턴스의 응답시간뿐 아니라, 스케일아웃이
개입하기 전의 CPU 여유와 공유 DB의 처리 여유를 함께 확보하는 작업이다.

다만 이번 실험은 Kubernetes에서 수행하지 않았다. Docker의 quota와 cpuset으로 제한된 서버
자원을 근사했을 뿐이며, HPA가 실제 피크를 방어하는 시간이나 필요한 Pod 수까지 검증한 것은
아니다.

## 9. 결론

목표 피크에서 기존 Entity 구조는 오류 0%, p99 96ms로 사용자 성능 SLO의 경계는 지켰다.
그러나 CPU 평균 61.8%, CFS 스로틀링 8.12%, Hikari pending 12를 기록해 운영 안전 기준에는
실패했다. JFR로 캐시 이전 요청 스레드 CPU의 약 32%가 DB 결과 처리·Hibernate 엔티티 구성과
응답 조립 경로에 쓰이는 것을 확인했다. 피크 중에는 C2 컴파일과 deoptimization도 실제로
발생해, 이미 부족하던 처리 여유를 추가로 사용했다.

DTO Projection은 ORM 조립 비용을 줄여 목표 성능을 달성했다. 여기서 한 단계 더 나아가 변경이
드문 장소 골격을 Snapshot으로 캐싱해 DB 조회까지 요청 경로에서 제거했다. 그 결과 같은 목표
피크에서 CPU 평균 42.3%, 스로틀링 0.17%, pending 0, p99 8ms를 기록했다.

이 작업의 핵심은 캐시가 항상 가장 빠르다는 것이 아니다. **사용자 성능 SLO를 지키는 데서
그치지 않고, 비결정적으로 발생하는 JVM 작업과 트래픽 변동에도 SLO를 계속 지킬 CPU·DB
안전 여유를 확보했다는 것**이다.

근거 자료와 원시 JFR 프로파일은 로컬의 `docs/perf/`와 `load-test/campaigns/`에 보존했다.
