## 측정 1 — 캐시 제거 후 회귀 확인

### 1. 문제

08-01 판정은 "토글 위의 B"를 쟀다. 실제 배포될 코드는 다르다 — 캐시 철거, **커버링 인덱스(V26)**,
`ps.active` 제거(조인 가드 일원화), 북마크 검색 DB 전환, 배치 매시 30분. 판정이 실코드에서도
성립하는지 확인하지 않으면 "측정한 것과 배포하는 것이 다른" 상태가 된다.

### 2. 원인 가설

요청당 statements는 구조 변화가 없어 **~17.2 유지**. p50은 커버링 인덱스로 시 단위 쿼리
(트래픽 40%)가 6.46→0.806ms(단건 프로브 실측)로 줄어 **동급 이상**을 예상한다.

### 3. 기술적 선택

단일 경로 코드 + V26 위에서 08-01과 같은 시나리오·시드·부하로 재측정, 08-01 B 중앙값과 직접 비교.

### 4. 검증할 주장

**리팩터링이 성능 회귀를 만들지 않았다.** (개선은 덤이지 주장이 아니다)

### 5. 성공 조건 (사전 등록 — 2026-08-02 사용자 확정)

| 지표 | 기준 | 08-01 B 참조값 |
|---|---|---|
| 성공률 | 100% | 100% |
| 요청당 statements | **18.2 이하** (17.18 + 여유 1) | 17.18 |
| p50 | **7.2ms 이하** (6.0 × 1.2) | 6.0ms |
| DB CPU | 지속 80% 미만 | 최대 56.3% |

하나라도 어긋나면 **원인 지표로 귀속 조사 후 보고** (판정을 늘리지 말 것).
p99는 폐기 지표 — 판정에 쓰지 않되, 08-01 B에서 재현성(1.15배)이 확인됐으므로
**"참고" 딱지를 달아 기록만** 한다 (참조값 19.9ms).

## 측정 2 — 부하 중 배치 실행

### 1. 문제

배치가 매시 30분으로 바뀌어 피크 트래픽과 상시로 겹친다. 캐시 시절엔 배치 순간의 읽기가
캐시로 흡수됐지만, 지금은 **6,320행 UPSERT와 초당 수백 건의 정렬 읽기가 place_stats 한
테이블에서 만난다.** 08-01 문서 "말할 수 없는 것" 3번의 해소.

### 2. 원인 가설

무해할 것 — SELECT는 잠그지 않는 일관 읽기라 UPSERT 행 락과 대기 관계가 없고, 배치 창은
무부하 실측 ~6.0초다.

### 3. 기술적 선택

코드 변경 없이 **라운드를 xx:30에 걸치게 배치** — 120초 정속 구간 한가운데에 실제 스케줄
배치가 자연 발화하게 한다. 수동 SQL 실행은 앱 경로가 아니라서 기각 (스케줄러 → Facade →
Processor의 실제 트랜잭션 경계를 그대로 겪어야 한다).

> **방법 수정 (2026-08-03, 측정 전 사용자 지시).** xx:30 자연 발화 대기를 **벤치 한정 크론
> 오버라이드**(`BENCH_APP_JSON`으로 `solply.place-stats.cron`만 변경)로 대체한다. 수동 SQL
> 기각 사유는 "앱 경로 이탈"이었는데, 크론 오버라이드는 발화 시각만 바꾸고 스케줄러 →
> ShedLock → Facade → Processor 경로를 그대로 태우므로 그 사유에 걸리지 않는다. 대신
> "말할 수 없는 것"이 하나 늘어난다: 이 측정이 검증하는 것은 **"피크 부하 중 배치 1회
> 실행"의 영향**이지, 매시 30분이라는 발화 시각 자체가 아니다 (시각은 어차피 판정과 무관).

### 4. 검증할 주장

**매시 배치는 피크 부하 중에 돌아도 사용자 체감 영향이 없다.**

### 5. 성공 조건 (사전 등록 — 2026-08-02 사용자 확정)

| 지표 | 기준 |
|---|---|
| 배치 포함 라운드 성공률 | 100% |
| 배치 포함 라운드 p50 | 무배치 라운드 중앙값의 **1.2배 이내** |
| `Innodb_row_lock_waits` 증가분 | 무배치 라운드와 구분 불가 수준 |
| 배치 소요 (앱 로그 실측) | 무부하 6.0초의 **2배 이내** |

실패 시 → **새벽 고정 복귀** 또는 **UPSERT 청크 분할**을 숫자와 함께 들고 사용자 결정 요청.

## 측정 3 — 한계 부하 탐색 (2026-08-03 추가)

### 1. 문제

캐시 계층 없는 DB 직행 구조가 **어느 규모까지** 유효한지 실측 근거가 없다. 분산 캐시 기각(설계
문서 §3.2~3.4)은 현 규모 기준의 판단인데, 재검토 임계 규모가 숫자로 없으면 그 판단의 적용
한계가 공중에 뜬다.

### 2. 원인 가설

08-01 실측(120 req/s: 요청당 앱 CPU 4.4ms ≈ 앱 2대 용량의 13%, DB CPU 최대 56%, p50 6.0ms)을
선형 외삽하면 한계는 **240 req/s(목표의 2배) 이상**. 먼저 포화하는 자원은 **DB CPU**로 예상한다
(집계는 없어졌지만 정렬·조회가 전부 DB에 있다).

포화 자원의 정체가 곧 결론이다: **DB가 먼저면** "이 지점부터 리플리카/캐시 재검토"라는 조건이
서고, **앱이 먼저면** "읽기 저장소를 Redis로 바꿔도 한계 동일"이라는 더 강한 기각 근거가 선다.

### 3. 기술적 선택

캐시 계층 없는 `place_stats` 직조회 구조 유지 + **분산 캐시 재도입 조건을 부하 임계값으로 정의**.

### 4. 검증할 주장

현 구조가 **읽기·쓰기 혼합 부하**에서 목표의 2배(240 req/s)까지 성공률·지연 열화 없이 동작하고,
한계 지점에서 먼저 포화하는 자원이 무엇인지 식별된다. 쓰기를 섞는 이유(2026-08-03 사용자 지시):
분산 캐시와의 실질 차이는 **증분 UPDATE와 인기순 SELECT(조인)가 같은 place_stats에서 만난다**는
것이므로, 조회 전용 부하로는 이 주장을 검증할 수 없다.

### 5. 성공 조건 (사전 등록 — 2026-08-03 사용자 확정)

| 항목 | 기준 |
|---|---|
| 240 req/s 라운드 성공률 (5xx 기준) | **≥ 99.9%** — 5xx만 실패. 북마크 토글의 4xx는 도메인 충돌(이미 북마크됨 등)로 **별도 집계·비율 보고** |
| 240 req/s 라운드 **조회 계열 p50** (엔드포인트별 지표) | **≤ 18ms** (120 req/s 기준 6.0ms × 3). 토글 p50은 기록만 |
| `Innodb_row_lock_waits` | 라운드별 증가분 기록 — 락 대기 타임아웃(`1205`) 0건 |
| 한계 라운드(실패 발생 시) | 포화 자원이 지표로 특정될 것 — DB CPU ≥180% / 앱 CPU ≥180%(어느 한 대) / 커넥션 풀 대기 중 무엇인지 |
| 전 라운드 | 커서 중복·누락 0건 |

### 라운드·판정 규칙 (측정 1·2와 다른 부분)

- 단계: **180 → 240 → 300** req/s, 여유 있으면 360 추가. 시나리오는 이 캠페인
  `scenarios/place-list-popular-<rate>.yml` — **혼합 믹스**: 조회 90%(baseline 내부 비율
  36:18:18:18 유지) + 북마크 토글 10%(같은 placeId POST→DELETE, `limit-processor.js`)
- **측정 3은 반드시 측정 1 이후에 실행** — 토글이 시드를 소폭 변형한다 (성공 경로는 넷 제로,
  POST 4xx 후 DELETE만 시드 북마크를 실제 감소시킨다. 원본·통계가 함께 움직여 정합성은 유지)
- **유효성 규칙 조정**: 한계 탐색 라운드에는 "앱 CPU 200% 초과 = 무효" 규칙을 적용하지 않는다
  (포화가 관찰 대상이다). 단 **벤치 외 프로세스에 의한 호스트 오염은 여전히 무효**
- **중단 조건**: 성공률 <99% 라운드가 나오면 다음 단계는 돌지 않는다
- **측정 불가 판정**: artillery 생성기 자체가 호스트 CPU를 포화시키면 그 라운드는 구조의
  한계가 아니라 **측정 환경의 한계**로 기록한다 (라운드 중 artillery 프로세스 CPU 기록 필수)
- 커넥션 풀 대기로 한계가 나오면 **설정 한계이지 구조 한계가 아니다** — HikariCP 풀 크기를
  기록하고 구분해서 판정한다

## 이 측정으로 말할 수 없는 것 (미리 명시)

1. **LATEST 정렬의 부하 특성** — 시나리오가 인기순 중심 (08-01과 동일한 한계)
2. **북마크 검색의 부하 특성** — 시나리오에 없음. 근거로만 말한다: 페이징 없는 소량 조립이고
   IT가 기능 등가를 보장한다
3. **배치 무해성의 재현성** — 배치 포함 라운드는 1~2회다. "N회 재현"이 아니라
   "실측 1~2회 + 락 이론 근거"의 결합 주장임을 결과 문서에 명시. 경계선이면 라운드 추가
4. **로컬 절대치는 운영 SLO가 아니다** (지표 계약 A.3)
5. **한계 부하의 절대값은 이 벤치 사양(컨테이너 2vCPU)의 것이다** — 운영에서 유효한 것은
   "목표의 몇 배" 라는 비율과 "무엇이 먼저 포화하는가"라는 구조 특성뿐이다
6. **한계 탐색은 단계당 1라운드다** — 재현성 주장이 아니라 1회 관찰이다. 판정이 경계선에
   걸리면 해당 단계만 1회 반복한다
7. **쓰기 분산은 균등(placeId 1~6000 uniform)이다** — 핫 플레이스 집중 시의 증분 경합은
   이 측정이 아니라 2026-07-31 Task 8 실측(최악 집중 903 tx/s)이 말한다. 두 실측의 결합이
   전체 주장이다
