## 1. 실험 목적

앞선 세 캠페인은 전부 **실행계획 채취**였다. 태그 EXISTS에서 `tags` 조인을 뺀 변경(`b24185a`)과
최신순 정렬 인덱스 복원(`77669b4`, V31)은 단일 쿼리에서만 검증됐고, **동시 요청이 붙었을 때
이 형상이 안정적인지는 재본 적이 없다.** 이 캠페인은 그 빈칸 하나만 채운다.

**개선의 크기는 주장하지 않는다** — 개선 전 형상을 같은 부하로 재지 않았으므로 A/B 대조군이 없다.
묻는 것은 하나다: *개선이 들어간 최종 형상이 목표 부하를 안정적으로 처리하는가.*

## 6. 배치 겹침 라운드 — **완료 · C1~C5 전부 충족**

### 6-1. 첫 시도는 버렸다 (생성기 정지)

사전 등록한 방식은 운영 스케줄(`@Scheduled(cron = "0 30 * * * *")` → `PlaceStatsFacade`
→ ShedLock → `PlaceStatsBatchProcessor`)의 자연 발화에 정상 구간을 겹치는 것이었다.
시각을 맞추려고 대기 루프를 **백그라운드 프로세스**로 띄운 것이 실패 원인이다 — 그 프로세스가
세션 하네스에 정지당해 04:28:50이 아니라 **04:43:23에 시작했고 실행 중에도 멈췄다.**

| 폐기 증거 | 값 |
|---|---|
| 도착 | 9,300 계획 중 **4,839** (52%) |
| 응답시간 | median **2,725ms** (같은 부하의 유효 라운드는 5ms) |
| 같은 구간 서버 자원 | 앱 CPU **40%대**, MySQL 30%대 — **서버는 놀고 있었다** |
| 샘플러 | 140초 예약인데 04:44:21에 멈춤 |

서버가 느렸다면 자원 지표가 올라갔어야 한다. 올라가지 않았으므로 **부하 생성기 쪽 정지**이고,
가이드 §6에 따라 구간을 잘라내지 않고 라운드 전체를 폐기했다
(원자료는 `results/discarded/`에 사유와 함께 남겼다 — 사전 등록의 "1회 재시도" 한도를 여기서 썼다).

### 6-2. 재시도 방식과 사전 등록으로부터의 이탈 — 발화 **시각**만 바꿨다

자연 발화(05:30)를 기다리는 대신, 제품이 스스로 노출한 조절 나사를 임시로 돌렸다.
`PlaceStatsFacade`의 스케줄 표현식은 `@Scheduled(cron = "${solply.place-stats.cron:0 30 * * * *}")`라
프로퍼티 하나로 주기를 바꿀 수 있다. 벤치 compose에 이미 뚫려 있는 `BENCH_APP_JSON` 통로로
그 프로퍼티만 주입하고 bench-app만 재기동했다.

```bash
BENCH_APP_JSON='{"solply.place-stats.cron":"0 0/2 * * * *"}' \
  docker compose -f docker/docker-compose.bench.yml up -d --force-recreate bench-app
```

**바뀐 것은 발화 시각뿐이고 경로는 사전 등록 그대로다** —
`@Scheduled` → `PlaceStatsFacade.recalculatePlaceStats()` → `@SchedulerLock`(ShedLock)
→ `PlaceStatsBatchProcessor`. 수동 SQL도, 테스트 전용 훅도, 프로세서 직접 호출도 쓰지 않았다.
**제품 코드와 추적 중인 `docker/docker-compose.bench.yml`은 한 줄도 고치지 않았고**, 라운드
종료 직후 기본 설정으로 원복해 `SPRING_APPLICATION_JSON={}`과 정상 응답(200)을 확인했다.

**주기를 1분이 아니라 2분으로 고른 이유**는 무효 조건 회피다. 라운드는 100초(20+20+60)인데
1분 주기면 라운드 안에서 **두 번 발화**하거나(사전 등록 §6의 "배치 2회 = 무효"), 종료 직후의
발화가 사후 스냅샷과 원복을 오염시킨다. 2분 주기는 라운드 안 **정확히 1회**를 보장하면서
종료 후 ~80초의 원복 여유를 남긴다.

**시각 정렬은 백그라운드 예약을 쓰지 않았다.** 첫 시도를 죽인 것이 바로 그 방식이라,
`tools/run-round.sh`의 `npx artillery` 직전에 **포그라운드 가드**(`BENCH_ALIGN_*`, 기본 off)를
넣어 발화 경계 50~56초 전에서만 출발하게 했다. PRE 스냅샷이 몇 초를 먹으므로 스크립트 시작이
아니라 생성기 기동 직전에 정렬해야 한다.

### 6-3. 발화가 정상 구간 안에 들어갔다는 증거

| 시각 | 사건 |
|---|---|
| 05:14:50 | `batch-watch before` — 라운드 직전 DB 상태 확정 |
| 05:15:04 | 정렬 완료 (다음 배치 경계까지 56초) |
| ~05:15:05 | artillery 첫 요청 = 라운드 t=0 |
| 05:15:45 | 정상 구간 시작 (t+40) |
| **05:16:00.011** | **배치 시작** — t≈55s, 정상 구간 안 |
| **05:16:05.890** | **배치 완료** — `elapsed=5879ms`, `affectedRows=6320` |
| 05:16:45 | 정상 구간 종료 (t+100) |
| 05:17:13 | `batch-watch after` |

**배치가 정확히 1회 돌았다는 것을 세 갈래 독립 증거로 확인했다.**

1. **앱 로그** — PRE(05:14:51)와 POST(05:16:50) 사이의 `인기순 점수 배치` 줄이 05:16:00 한 쌍뿐이다.
2. **p6spy digest** — 라운드 창에서 리셋·덤프한 digest에 `INSERT INTO place_stats …`가
   **호출 1회 · 5,792ms/실행**. (배치 전체 5,879ms의 98.5%가 이 문장 하나다.)
3. **actuator `logback_events_total`** — `info` 11 → 13으로 **정확히 +2**(시작·완료 한 쌍).
   2회 발화였다면 +4였어야 한다.

### 6-4. C1~C5 판정

| # | 조건 | 결과 | 근거 |
|---|---|---|---|
| **C1** | 배치가 성공 로그로 완료 | **충족** | `인기순 점수 배치 완료 - affectedRows=6320, elapsed=5879ms` |
| **C2** | 새 `version` 생성 + `current_generation`이 그것을 가리킴 | **충족** | before `current=1785993240 / prev=1785993120` → after `current=1785993360 / prev=1785993240` — **정확히 한 세대 이동** |

| **C4** | 배치 소요시간 기록 (게이트 아님) | **5,879ms** | 같은 형상 무부하 기준선 **4,782ms**(05:12) · **4,773ms**(05:14) → **+1,100ms / +23%** |

두 회차(05:12·05:14)가 **같은 형상·같은 데이터·부하만 없는** 대조군이 됐다.

### 6-5. 공통 게이트(S1~S6)도 전부 충족했다

| # | 값 |
|---|---|
| S1 도착률 | 계획 9,300 / 생성 **9,300 = 100.00%** |
| S2 성공률 | `http.codes.200` 14,437 / 요청 14,437 = **100%**, 에러 0 |
| S3 앱 예외·5xx | `logback_events_total{level="error"}` 0 → **0**, `warn` 0 → **0**. 응답이 전부 200이라 edge 통과 5xx 0 |
| S4 정상 구간 지연 | 버킷 중앙값 **p50 5ms · p95 7.9ms · p99 13.9ms** (게이트 100/200ms) |
| S5 OOM·재시작·GC | `restart_count` 0, `memory.peak` 538MiB/2,048MiB, GC +132회 **+580ms**, 구간 max **44ms** |
| S6 커넥션·락·디스크 정렬 | Hikari active 0 · pending 0, `Innodb_row_lock_waits` **0**, `Innodb_row_lock_time` **0**, `Created_tmp_disk_tables` **0**, `Connection_errors_max_connections` **0** |

**무효 조건(§6)에 걸린 신호는 없다.** 앱 cgroup CPU는 쿼터의 31.9%로 상한(2 vCPU) 미초과,

p50도 A와 같은 5ms로 **꼬리만이 아니라 전체가 밀리는 서명이 없다.** 재시작·OOM 0.

### 6-6. 배치에 귀속되는 비용 — 그리고 반증된 두 가설

같은 부하·같은 믹스의 A 라운드가 대조군이다. 차이는 배치 하나다.

| 지표 | A (`r-a-120`) | **C (`r-c-120-batch`)** | 차이 |
|---|---:|---:|---|
| 정상 구간 p95 (버킷 중앙값) | 7.9ms | **7.9ms** | 동일 |
| 정상 구간 p99 (버킷 중앙값) | 16.0ms | **13.9ms** | 오히려 낮음 |
| 정상 구간 처리율 (중앙값) | 188 req/s | **186 req/s** | −1% |
| 앱 CPU (쿼터 대비) | 24.1% | **31.9%** | **+7.8%p** |
| 앱 throttled 주기 | 0.7% (0.66s) | **2.6% (9.32s)** | **+1.9%p** |
| MySQL CPU (쿼터 대비) | 13.3% | **13.8%** | +0.5%p |

**비용은 앱 CPU에 나타나고 지연에는 나타나지 않았다.** 배치는 앱 프로세스 안에서 도니까
앱 CPU가 오르는 것이 정상이고, 그 상승분이 스로틀을 0.7%→2.6%로 밀어 올렸다. 그런데 120 req/s는
쿼터의 3분의 1만 쓰는 부하라 남은 여유가 그 상승을 흡수했다 — 사용자가 보는 지연은 A와 동등하다.
**300 req/s처럼 스로틀이 이미 18%인 부하에서도 같을 것이라고 말할 수는 없다. 재지 않았다.**

사전 등록 §2가 이론상 가능하다고 적어 둔 **두 경로는 실측으로 부정됐다.**

- **"버퍼풀 오염 → 조회 디스크 읽기 상승"** — `Innodb_buffer_pool_reads` **0**,
  `Innodb_data_reads` **0**, hit rate **100.000000%**. 배치가 `places`·`bookmarks`·`reviews`를
  전량 훑었는데도 조회가 디스크로 내려간 적이 **한 번도 없다.** 워킹셋이 2G 버퍼풀에
  이미 상주해 있었기 때문이다.
- **"UPSERT 행 락 → 조회 지연"** — `Innodb_row_lock_waits` **0**, `Innodb_row_lock_time` **0**.
  `PlaceStatsRepository#upsertAll`의 READ COMMITTED + 시각 상한 설계가 의도대로 동작했다.
  조회는 `place_stats`의 **다른 version**을 읽으므로 UPSERT 대상 행과 애초에 겹치지 않는다.

> 참고: "피크 중 배치 1회는 무해하다"는 2026-08-02 캠페인에서도 측정됐다
> (성공률 100% · p50 0.76배 · 락 대기 +1건 · 배치 6.195초). 그 뒤 인기 점수 공식이
> 바뀌었고(`5e0fe94`) V31 인덱스가 생겼으므로 그 숫자를 그대로 옮겨 쓸 수 없어 다시 쟀고,
> **같은 방향의 결론이 현 형상에서 재확인됐다** (배치 5.879초, 락 대기 0).

### 6-7. 이 라운드의 한계

- **라운드 당시 앱 컨테이너의 전체 로그는 남지 않았다.** 원복이 `--force-recreate`라 컨테이너가
  교체됐다. S3의 근거는 원복 **전에** 채취한 actuator `logback_events_total`(error·warn 0)과
  `batch-watch after`의 로그 발췌다 — 카운터는 전 구간 누적이라 누락된 예외를 숨기지 못한다.
- **배치 1회만 봤다.** 연속 발화나 배치와 300 req/s의 조합은 재지 않았다.
- 무부하 기준선 2회(4,782·4,773ms)는 **재현성을 주장할 표본이 아니다.** C4의 +23%는
  단일 관측이고 게이트가 아니라 보고 항목이다.

## 7. 자원 병목 판정과 headroom

**병목은 앱 컨테이너의 CPU 쿼터다.** MySQL이 아니다.

| 부하 | 앱 쿼터 사용률 | 앱 throttled | MySQL 쿼터 사용률 | MySQL throttled |
|---|---:|---:|---:|---:|
| 도착 120 (실처리 ~188 req/s) | 20.6~24.1% | 0.3~0.7% | 12.5~13.3% | **0%** |
| 도착 300 (실처리 ~465 req/s) | 50.2~56.5% | **7.5~18.2%** | 35.3~37.6% | 0.2~0.8% |

읽는 법:

1. **120에서는 여유가 크다.** 앱이 쿼터의 4분의 1, DB가 8분의 1이다. throttled 주기가 1% 미만이라
   요청이 CPU를 기다린 적이 사실상 없다. 이 부하에서 자원 병목은 **없다**.
2. **300에서는 평균 사용률이 절반인데 throttling이 18.2%까지 뛴다.** 이 조합이 핵심이다 —
   평균으로 보면 절반이 남는데 **100ms 주기 단위로는 쿼터를 자주 다 쓴다**는 뜻이고,
   도착이 균일하지 않기 때문이다. 평균 CPU 사용률로 headroom을 읽으면 여기서 틀린다.
3. **앱:DB 소비 비율이 1.5:1로 일정하다** (118:80, 105:75). 부하가 올라도 비율이 유지되므로
   **앱이 먼저 벽에 닿는다.** 이는 2026-08-05 캠페인의 결론("다음 병목은 앱 CPU")과 같은 방향이다.
4. **DB 쪽은 아직 한참 남았다** — 디스크 읽기 0, 락 대기 0, 임시 디스크 테이블 0, 커넥션 11/200.

**headroom 해석:** 목표 부하 120 req/s(실처리 ~188 req/s)에서 앱 CPU 쿼터의 약 4분의 1을 쓴다.
단순 비례로 보면 여유는 4배 안팎이지만, 300에서 이미 throttling이 7.5~18.2%로 나타나므로
**실용 여유는 그보다 작다.** 이 캠페인은 붕괴점을 찾지 않았으므로 상한을 숫자로 말하지 않는다.

## 8. 사전 등록 조건 판정

| # | 조건 | A | B | C |
|---|---|---|---|---|
| S1 | 도착률 ≥ 99% | **충족** (100.00%) | **충족** (100.00%) | **충족** (100.00%) |
| S2 | 성공률 ≥ 99.9% | **충족** (100%) | **충족** (100%) | **충족** (100%) |
| S3 | 앱 예외 0 · NGINX 5xx 0 | **충족** | **충족** | **충족** (logback error·warn 0) |
| S4 | 정상 구간 p95 ≤ 100 · p99 ≤ 200 | **충족으로 볼 수 있으나 근거는 참고치** | **미증명 — 보수적으로 미달로 본다** | **충족** (버킷 중앙값 p95 7.9 · p99 13.9) |
| S5 | OOM 0 · 재시작 0 · GC 장기정지 없음 | **충족** | **충족** (GC max 30ms) | **충족** (GC max 44ms) |
| S6 | 커넥션 고갈 0 · 락 대기 0 · 디스크 정렬 0 | **충족** | **충족** | **충족** |
| C1~C5 | 배치 겹침 | — | — | **전부 충족** (배치 5,879ms · 2버전 12,640행 · 실패 0) |

**S4를 이렇게 판정하는 이유.** Artillery 리포트는 정상 구간만의 **원자료 합산 백분위**를 주지
않는다. 가진 것은 10초 버킷별 백분위뿐이고, **백분위는 재집계가 불가능**하므로 버킷 값들의
중앙값은 "정상 구간 p95"가 아니다. 따라서:

- **A**: 라운드 전체 p95 8.9ms · p99 18ms로 게이트의 **11분의 1 수준**이다. 버킷 최댓값
  (p95 16.9 · p99 43.4)조차 게이트 아래라 결론이 바뀔 여지가 없다 — 실질 충족으로 읽는다.
- **B**: 라운드 전체 p95 194.4ms · p99 391.6ms로 게이트를 **넘는다.** 버킷 값들이 게이트 위아래로
  걸쳐 있고 두 라운드 간 산포가 16~37배라 "정상 구간만 보면 통과"라고 말할 근거가 없다.
  **미증명이므로 미달로 보수 판정한다.**

**B에서 무엇이 통과하고 무엇이 안 되는지는 분리해서 읽어야 한다.**

| B에서 통과한 것 | B에서 통과 못 한 것 |
|---|---|
| 오류 게이트 — 실패 0건, 5xx 0건, 도착률 100%, 커넥션·락·디스크 전부 깨끗 | 지연 게이트 — 라운드 전체 p95/p99가 사전 등록 임계를 넘음 |
| 구조 안정성 — 요청당 statements·행/실행이 불변, 플랜 변화 없음 | headroom — 앱 CPU throttling 18.2% (A의 26배) |

즉 **300 req/s에서 서비스는 깨지지 않지만 여유는 경계에 있다.**
꼬리 상승의 서버측 동반 지표는 앱 CPU throttling이고, throttled 시간(56.1s)이 B반복(20.9s)의
2.7배인 것이 두 라운드의 꼬리 차이와 같은 방향이다. 다만 **호스트에서 부하생성기가 함께 도는
환경이라 두 요인을 완전히 분리하지는 못했다**(§10).

무효 조건은 어느 라운드에도 해당하지 않았다 — cgroup 상한 초과 없음, 앱·DB 동시 급등 없음
(B는 부하 수준에 맞게 함께 오르되 상한 아래에서 유지), **p50이 5→6ms로 사실상 불변**(호스트
스톨이면 p50까지 밀린다), 재시작·OOM 0. 그래서 B를 폐기하지 않고 그대로 보고한다.

## 9. 태그 개선의 운영 부하 영향

**개선된 SQL이 부하 중에도 `tags` 조인 없이 실행된다** — digest 원문으로 확인했다.

```sql
-- r-b-300 digest, 태그3 인기순 1페이지 (COUNT_STAR 5,657 · 행/실행 680.9 · 1.025ms/실행)
SELECT `ps`.`place_id`, ... FROM `place_stats` `ps`
WHERE `ps`.`version` = ? AND `ps`.`town_id` IN (...)
  AND EXISTS (SELECT ? FROM `place_tag` `pt` WHERE `pt`.`place_id` = `ps`.`place_id` AND `pt`.`tag_id` = ?)
  AND EXISTS (SELECT ? FROM `place_tag` `pt` WHERE ...)
```

`tags` 테이블이 **어느 digest에도 나타나지 않는다** (인기순·최신순 태그 문장 4종 전부 확인).
같은 파라미터의 `EXPLAIN ANALYZE`(무부하, `results/explain/pre-round-c.txt`)도 일치한다:

```
-> Limit: 21 row(s) (actual time=1.17..1.17 rows=21 loops=1)
    -> Sort: ps.popular_score DESC, ps.place_id, limit input to 21 row(s) per chunk
        -> Nested loop inner join
            -> Index lookup on pt using idx_place_tag_tag_id (tag_id=12) (rows=287)
            -> Single-row covering index lookup on pt using uk_place_tag_place_tag (tag_id=7)
            -> Single-row covering index lookup on pt using uk_place_tag_place_tag (tag_id=1)
            -> Single-row index lookup on ps using PRIMARY (place_id=..., version=...)
```

운영 부하 관점에서 말할 수 있는 것:

1. **태그 경로가 무태그 경로보다 비싸지 않다.** A에서 시 단위 태그 3개 인기순은 p50 6ms /
   실행당 0.858ms · 659.7행이고, 같은 범위의 **무태그**는 실행당 0.450ms · **1,089.2행**이다.
   태그가 붙으면 훑는 행이 오히려 **40% 줄어든다** — 필터가 선택도로 작동하고 있다는 뜻이다.
   (개선 전에는 같은 조합에서 `place_tag` 10,536 엔트리를 훑었다.)
2. **부하가 올라가도 플랜이 흔들리지 않는다.** 행/실행이 659.7 → 659.4로 0.05% 이내 불변이고
   `SUM_NO_INDEX_USED`·`SUM_SORT_MERGE_PASSES`·`SUM_CREATED_TMP_DISK_TABLES`가 전부 0이다.
   조인 순서가 부하나 버퍼 상태에 따라 뒤집힐 위험은 이 부하 범위에서 관측되지 않았다.
3. **커서 2페이지가 1페이지보다 싸다.** 태그 인기순 p2는 p95 8.9ms로 p1(10.9ms)보다 낮다 —
   커서 술어가 범위를 좁히기 때문이다. 무한 스크롤이 뒤로 갈수록 무거워지는 형태가 아니다.
4. **최신순 태그 경로도 같은 모양이다** (679행/실행, 플랜에 `tags` 없음, filesort는 남지만
   입력이 29행이라 비용이 되지 않는다).

**말하지 않는 것:** 이 캠페인은 개선 **전** 형상을 같은 부하로 재지 않았다. 위 1번의 "40% 적게
훑는다"는 무태그와의 비교이지 개선 전 태그 경로와의 비교가 아니다. 개선 폭의 근거는 여전히
[2026-08-06 태그 조인 순서 캠페인](2026-08-06-tag-filter-join-order.md)의 실행계획 A/B다.

## 10. 이 테스트로 말할 수 없는 것

1. **배치 겹침의 무해성 — 120 req/s에서만 확인했다.** 라운드 C는 배치 1회를 정상 구간 안에
   포착해 C1~C5를 전부 충족했지만(§6), 그 부하는 앱 CPU 쿼터의 3분의 1만 쓰는 지점이다.
   **스로틀이 이미 18%인 300 req/s에서 배치가 겹치면 어떻게 되는지는 재지 않았다.**
   연속 발화도 보지 않았다.
2. **개선의 크기.** A/B 대조군이 없다. "태그 개선으로 처리량이 몇 배 늘었다"를 이 숫자로
   말할 수 없다.
3. **꼬리 지연(p95/p99)의 절대값.** 유효 라운드 간 16~37배 산포가 났다. 이 환경에서 꼬리는
   판정에도 SLO에도 쓸 수 없다. 실사용 p99는 프로덕션 모니터링에서 읽는다.
4. **한계 처리량.** 붕괴점을 찾지 않았다. 300 통과와 그 위 어딘가의 천장 사이는 미탐색이다.
5. **장시간 성질.** 정상 구간 60초짜리 라운드다. 메모리·커넥션 누수, GC 악화, 캐시 증가는
   검증 대상이 아니다. (참고로 `memory.peak`은 컨테이너 기동 이후 누적값이라 라운드별
   증가분으로 읽으면 안 된다.)
6. **운영 절대 성능.** 로컬 벤치이고, 오히려 prod가 더 열악하다(버퍼풀 기본값 128MB, 자원 격리
   없음 — [가이드 A.4](load-test-guide.md)).

### 명시할 환경 한계 — 부하생성기가 같은 호스트에서 돈다

Artillery가 측정 대상과 같은 macOS 호스트에서 실행됐다. 호스트는 11 vCPU이고 컨테이너에 4가
배정돼 있다. 라운드 중 호스트 load average는 A에서 4.5~6.1, B에서 5.0~**13.9**까지 올라갔다.

- **도착률이 100%였다**는 것은 생성기가 계획한 요청을 전부 쏘아냈다는 뜻이므로, 생성기가
  병목이 되어 부하를 못 만든 상황은 아니다.
- 그러나 **B의 꼬리에 호스트 경합이 얼마나 기여했는지는 분리하지 못한다.** 앱 cgroup
  throttling(18.2%)은 서버측에서 직접 측정된 값이라 실재하지만, 호스트 스케줄링 지연이
  그 위에 얼마나 얹혔는지는 이 구성으로 알 수 없다.
- 실제로 **라운드 C의 첫 시도는 이 한계가 최악으로 발현된 경우**였다 — 생성기 프로세스 자체가
  정지당해 라운드를 통째로 버렸다(§6).

이 한계는 [가이드 A.6](load-test-guide.md)에 "인지된 미해결 항목"으로 이미 등록돼 있다.

## 부록 D. 앱 CPU 상한만 4 vCPU로 올린 대조 라운드 (`r-d-300-app4`)

§5·§7의 판정은 **300 req/s의 꼬리가 앱 CPU 쿼터에서 온다**고 봤다. 그 근거는 앱 cgroup
스로틀(18.2% / 56.10s)이었지만, 스로틀과 꼬리가 **같은 라운드에서 동시에 관찰됐다**는 것은
상관이지 인과가 아니다. 이 부록은 **다른 것을 전부 고정하고 앱 CPU 상한만 2→4 vCPU로 올려**
그 상관이 인과인지 한 번 확인한 기록이다.

**이것은 사후 추가 관찰이다.** §5·§6의 사전 등록 기준을 고치지 않았고, 이 라운드의 값을
캠페인의 게이트 판정에 되먹이지 않았다.

### D-1. 무엇만 바꿨나

| 축 | 값 |
|---|---|
| 바꾼 것 | 앱 컨테이너 CPU 상한 **2 → 4 vCPU** (`docker update --cpus 4 solply-bench-app`) |
| 고정한 것 | 제품 코드(무변경) · 시나리오 `stability-300.yml` · 도착 프로파일(20s@60 + 20s 60→300 + 60s@300) · 엔드포인트 · 호스트 · 앱 메모리 2 GiB · `-Xmx1280m` · Tomcat 50 · Hikari 10 · **MySQL 2 vCPU / 3 GiB 무변경** · DB 데이터 |
| 방식 | **컨테이너를 재기동하지 않았다** — `docker update`가 cgroup `cpu.max`를 살아 있는 채로 바꾼다. JIT·버퍼풀·커넥션 상태가 그대로 유지되므로 "재기동으로 딸려 들어오는 변수"가 없다 |
| 검증 | 부하 전 컨테이너 안에서 `cpu.max` = `400000 100000` (=4 vCPU), `docker inspect` `NanoCpus=4000000000`, `RestartCount=0`, MySQL `cpu.max`는 `200000 100000` 그대로 |
| 원복 | 라운드 직후 `docker update --cpus 2` → `cpu.max` `200000 100000`, `NanoCpus=2000000000`, `SPRING_APPLICATION_JSON={}`, 두 경로 **HTTP 200** 재확인 |
| 원자료 | `results/metrics/r-d-300-app4.cpulimit.{before,applied,restored}` |

**추적 중인 `docker/docker-compose.bench.yml`은 한 줄도 고치지 않았다** (`cpus: 2` 그대로).
`docker update`는 컨테이너 런타임 설정만 바꾸므로 다음 `docker compose up`이면 자동으로 2로 돌아간다.

JVM은 `system_cpu_count`를 **4.0으로 즉시 보고**했다 — JDK 21의 컨테이너 지원이
`availableProcessors()`를 cgroup에서 다시 읽기 때문이다. 다만 **GC 스레드 수처럼 기동 시점에
고정되는 값은 2 vCPU 기준 그대로**다. 이 라운드가 재는 것은 "4 vCPU로 기동한 앱"이 아니라
**"쿼터만 풀린 앱"**이다.

### D-2. 실행 기록

### D-4. 분모 함정을 먼저 치운다

4 vCPU 라운드의 "쿼터 대비 29.9%"는 **분모가 두 배가 됐으니 자동으로 절반이 되는 값**이다.
이 숫자만 보고 "여유가 생겼다"고 말하면 아무것도 증명하지 못한다. 그래서 분모에 의존하지 않는
**절대 코어 사용량**(`usage_usec ÷ 관측 창`)으로 다시 본다.

| | B | B반복 | D |
|---|---:|---:|---:|
| 절대 평균 코어 | 1.130 | 1.004 | **1.198** |
| 요청당 앱 CPU | 3.34ms | 2.97ms | **3.55ms** |

**절대 사용량은 줄지 않고 늘었다.** 같은 일(요청 35.3천 건, 요청당 statements 11.69)을 하면서
CPU를 6~19% 더 썼다. 이것이 이 부록의 핵심 관찰이다 — 상한이 풀리자 앱이 **더 많은 CPU를
실제로 가져갔다**. 2 vCPU 라운드에서 앱은 원하는 만큼 못 쓰고 있었던 것이고, 56.10초의
throttled 시간이 바로 그 "못 쓴 대가"다.

요청당 CPU가 되레 늘어난 것(3.34 → 3.55ms)은 병렬도가 오르며 생기는 비용(컨텍스트 스위치,
GC 스레드 활동 +287회)으로 보이지만, **이 라운드 하나로는 그 귀속을 확정하지 못한다.**
여기서 쓰는 결론은 방향뿐이다 — 절대 사용량이 **줄지 않았으므로** 스로틀 감소가 분모 착시가 아니다.

### D-5. 판정 — 앱 CPU 상한 병목 가설을 **지지한다**

사전에 정한 지지 조건은 **스로틀 감소와 p95/p99 개선이 함께 나타날 때**였다. 둘 다 나타났다.

| 조건 | 결과 |
|---|---|
| 앱 스로틀 감소 | 18.2% → **0.8%** (주기), 56.10s → **0.58s** (시간) — **23배·97배** |
| 꼬리 개선 | p95 194.4 → **13.9ms**, p99 391.6 → **59.7ms**, max 953 → **246ms** |
| 분모 착시 아님 | 절대 코어 1.130 → **1.198** (줄지 않음) |
| 다른 축이 원인이 아님 | 요청당 statements 11.69 불변 · 락 대기 0 · tmp disk 0 · buffer pool reads 0 / hit 100% · 커넥션 11 고정 · Hikari pending 0 — **DB 쪽 지표가 하나도 안 움직였다** |

즉 300 req/s의 꼬리는 DB 경합·플랜 흔들림·커넥션 고갈·GC가 아니라 **앱 컨테이너가 CPU 쿼터에
막혀 실행 대기하던 시간**이었다. §7의 "병목은 앱 CPU"라는 결론이 대조 실험으로 한 번 재현됐다.

**보수적으로 읽어야 할 값이 하나 있다.** B의 꼬리는 두 반복 사이에서 이미 16~37배로 흔들렸고
(p95 194.4 vs 45.2), D는 그 흔들리는 분포와 **단 한 번** 비교한 것이다. D의 13.9ms가 B반복의
45.2ms보다 3.3배 좋다는 것은 관찰이지만, **개선 배수를 수치로 주장할 근거는 아니다.**
안전하게 말할 수 있는 것은 **방향**이다 — D의 최악값(p99 59.7ms)이 B 두 라운드의 최선값
(p99 247.2ms)보다도 4배 낫고, 스로틀은 두 자릿수 배로 줄었다.

### D-6. 곁다리 관찰 — MySQL 스로틀이 늘었다 (후속 확인 필요)

앱 스로틀이 사라진 라운드에서 **MySQL 스로틀이 0.8% / 0.33s → 2.9% / 4.78s로 올랐다.**
MySQL의 절대 사용량은 거의 그대로다(0.753 → 0.766 코어).

이것을 "다음 벽은 DB의 2 vCPU"로 읽지 않는다. **단일 관측 한 번의 2.9%로 단정할 수 없다** —
B 두 라운드 사이에서도 MySQL 스로틀은 0.8%와 0.2%로 4배 흔들렸고, 이 값이 B의 산포를 넘어선
신호인지 그 안의 요동인지 구분할 반복이 없다. 응답시간·처리율·요청당 statements 어디에도
DB 쪽 악화가 나타나지 않았다는 점도 함께 봐야 한다.

말할 수 있는 것은 **관측 사실과 그럴듯한 기전**까지다: 앱이 더 이상 억제되지 않아 요청이 DB에
더 촘촘한 버스트로 도달했을 수 있다. **후속 확인이 필요한 항목**으로 남긴다 — 확인하려면
DB 스로틀을 1급 지표로 놓고 같은 조건을 여러 번 반복해야 하고, 이 부록은 그것을 재지 않았다.

### D-7. 이 부록의 한계

- **단일 실행이다.** 반복이 없으므로 재현성을 주장하지 않는다. 비교 대상인 B는 두 번 돌렸고
  그 둘조차 꼬리가 16~37배 달랐다 — 이 산포 위에 한 번 얹은 관찰이다.
- **부하생성기가 같은 호스트에서 돈다** (§10과 같은 한계). 라운드 중 호스트 load average가
  4.55 → 12.43으로 올랐고, 앱 스로틀 감소분에 호스트 스케줄링이 얼마나 섞였는지는 분리하지 못한다.
  다만 도착률 100%·p50 불변은 생성기가 병목이 아니었다는 방증이다.
- **라운드 사이 휴식이 20초였다** (원 캠페인 규약은 60초). 워밍업 종료 15:31:10 → 측정 시작
  15:31:30. 앱 CPU가 완전히 idle로 내려간 뒤 시작하지 않았다.
- **"4 vCPU로 기동한 앱"이 아니다.** GC 스레드 수 등 기동 시 고정되는 값은 2 vCPU 기준이다
  (D-1). 재기동해서 재면 다른 숫자가 나올 수 있다.
- **운영 스펙 권고가 아니다.** 이 캠페인의 형상(2 vCPU)은 비용 현실성에 맞춘 의도적 선택이고
  (`docker-compose.bench.yml` 주석), 목표 부하 120 req/s에서는 스로틀이 0.7%다. 4 vCPU가
  필요하다는 결론이 아니라, **300 req/s의 꼬리 원인이 앱 CPU 쿼터였다**는 진단이다.
