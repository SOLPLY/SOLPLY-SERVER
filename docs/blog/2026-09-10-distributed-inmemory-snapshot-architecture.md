# 어드민 서버와 다중 API 인스턴스의 Current Snapshot 배포 설계

작성일: 2026-09-10

> 이 글은 현재 로컬 Snapshot의 계약을 분산 환경에 적용하는 **아키텍처 제안**이다.
> 어드민 빌더 분리와 Redis 배포·복원 경로는 아직 구현되지 않았다.
> 로컬 자료구조와 갱신 알고리즘은 [장소 목록 Snapshot 설계](2026-09-09-admin-rebuild-tradeoff.md)에 정리한다.

장소 목록을 로컬 메모리에서 조회하면 API는 빠르게 후보를 찾을 수 있지만, 전체 모델을
만드는 DB 조회·객체 생성·정렬도 같은 JVM에서 실행하면 사용자 요청과 CPU·힙을 나눠 쓴다.
그 과정의 할당과 GC가 요청 latency에 영향을 주는 경우, 모델 생성은 별도 빌더에 맡기고
API는 완성된 모델을 받아 조회하는 역할로 나눌 수 있다. 여러 API가 같은 조회 상태로
수렴해야 한다는 요구도 이 배포 경로에서 함께 다룬다.

이 설계의 목적은 **생성 비용을 사용자 요청에서 격리하면서, 각 API가 완성된 최신 상태를
안전하게 받아 쓰게 하는 것**이다. Redis는 최신 모델의 배포 저장소이고, 실제 목록 조회는
API의 로컬 메모리에서 수행한다. current는 한 벌만 유지하며, 오래된 커서는 만료시킨다.
커서가 Redis의 최신 version인데 로컬에만 없다면 그 모델을 복원해 이어간다.

본문 1~8절은 **최신 모델의 생성·배포·로컬 조회·복구 계약**을 다룬다. 그 뒤의
**확장성 고려**는 병목이나 검색 요구가 달라졌을 때 선택할 대안으로 분리한다.
기본 배포 설계가 SoA나 역색인, Elasticsearch 도입을 전제로 하지는 않는다.

## 1. 설계를 결정하는 요구사항

- 어드민 변경을 빠르게 반영한다. 과거 커서를 유지하기 위해 과거 Snapshot을 보존하지 않는다.
- 한 요청의 정렬·필터·후보 집합은 요청이 확보한 Snapshot으로 고정한다.
- 이름·썸네일·태그 이름은 Snapshot 밖의 최신 표시값으로 조립한다.
- 어드민 변경은 변경된 장소 ID로 DB를 다시 읽어 부분 반영한다.
- 주기적 전체 재빌드는 정렬 키를 일괄 반영하고, 놓친 변경을 DB 기준으로 다시 맞춘다.
- 알림이 유실되거나 API가 재시작해도 저장된 최신 상태로 복구할 수 있어야 한다.
- 늦게 끝난 작업이나 역순 알림이 최신 상태를 덮어쓰지 못해야 한다.

여기서 최신 반영은 전파 지연을 허용하는 최종적 일관성이다. 모든 요청마다 Redis와 DB의
최신 상태를 확인하는 계약은 아니다. 전파 지연과 실패 중의 지연을 구분해 관측한다.

## 2. 저장소와 실행 주체의 역할

| 구성 요소 | 책임과 수명 |
|---|---|
| RDB | 장소·통계·태그의 기준 데이터. 조회 모델을 다시 만드는 원천 |
| 어드민 측 빌더 | 변경 ID 재조회, 부분 갱신, 주기적 전체 재빌드, 버전 발급·배포 |
| Redis | 최신 Snapshot 한 벌, 최신 표시값, 버전·표시값 갱신 번호 |
| API의 `SnapshotBox` | 조회에 쓰는 immutable current Snapshot 한 벌 |
| API의 표시 홀더 | 장소 ID·태그 ID로 찾는 최신 표시값 |

완성된 모델을 배포하는 흐름과, 그 모델로 사용자 요청을 처리하는 흐름은 다음과 같이 연결된다.
아래 구성은 분산 환경의 제안이며, 빌더는 하나의 갱신 실행권 아래에서 동작한다.

```text
어드민 변경 요청
  │
  ▼
DB 트랜잭션 커밋              ← 원본 장소와 조회 원천 데이터 저장
  │
  │ 변경 장소 ID                         주기 실행
  │                                        │
  └─────────────────┬──────────────────────┘
                    ▼
             어드민 측 빌더
             갱신 실행권 확보             ← 부분 갱신·전체 재빌드 직렬화
                    │
                    ▼
             DB 최신 상태 읽기            ← 변경 ID만 조회 / 전체 조회
                    │
                    ▼
             조회 모델·표시값 준비         ← 부분 반영 / 정렬 키 일괄 반영·복구
                    │
                    ▼
             완성된 최신 상태 공개         ← 표시값만 바뀌면 Snapshot 버전 유지
                    │
                    ▼
                  Redis
             최신 Snapshot 한 벌
             + 별도의 최신 표시 상태
                    │
                    │ 공개 후 Pub/Sub 알림
                    │ API는 기동·재접속·주기 확인으로도 동기화 시작
                    ▼
             각 API의 동기화 작업
             Redis 최신 상태 확인
                    │
                    ▼
             다운로드 · 검증 · 복원       ← 알림에 모델을 싣는 대신 저장된 상태 조회
                    │
          ┌─────────┼─────────┐
          ▼         ▼         ▼
        API A     API B     API C         ← 각자 준비 완료 후 current 교체
        current   current   current
        표시값    표시값    표시값        ← 서버 사이 전파 지연은 존재

사용자 목록 요청
  │
  ▼
로드밸런서
  │
  ▼
위 API 중 한 곳으로 전달
  │
  ▼
로컬 current 참조 확보        ← 일반 조회는 Redis를 매번 왕복하지 않음
  │
  ├─ 첫 페이지 / 커서 버전 일치
  │    │
  │    ▼
  │  로컬 정렬·필터·페이지 선택
  │    │
  │    ▼
  │  표시값·사용자별 값 조립 → 응답
  │
  └─ 커서 버전이 로컬에 없음
       │
       ▼
     Redis 최신 version 확인
       ├─ 커서와 같음 → 최신 모델 복원·검증 후 같은 커서로 조회
       └─ 커서와 다름 → 커서 만료 · 첫 페이지 재요청
```

동기화는 API마다 수행한다. 사용자 요청은 그 API가 이미 준비한 로컬 모델을 읽으며,
커서의 로컬 미스에서만 위 복원 경로를 추가로 거친다. 복원 중 최신 버전이 바뀌거나 Redis를
사용할 수 없는 경우의 처리는 5절에서 다룬다.

사용자별 북마크 조회, 요청의 동네 해석·태그 검증 등은 별도의 DB 경로를 사용할 수 있다.
로컬 정렬·필터링이 전체 요청의 외부 저장소 독립성을 뜻하지는 않는다.

## 3. 변경을 만들고 공개하는 순서

### 변경 ID로 최신 상태를 읽고, 영향받은 부분을 준비한다

빌더가 전달받는 것은 변경된 장소 ID다. 변경 당시의 값을 이벤트에 담아 재생하면 지연된
이벤트가 최신 값을 덮을 수 있으므로, 갱신 차례에 DB에서 현재 상태를 다시 읽는다. 존재하지
않으면 제거하고, 새 장소라면 추가하며, 기존 장소라면 현재 조회 모델과 비교한다.

```text
DB 커밋 후 변경 ID 전달
  → 갱신 차례 확보 → 해당 장소의 최신 상태 재조회
  → 표시값만 변경: 표시 상태만 갱신
  → 조회 기준 변경: 영향 동네만 반영한 새 Snapshot 준비
  → 필요한 표시값과 새 version의 모델을 완성한 뒤 공개
```

조회 중인 배열은 직접 바꾸지 않는다. 같은 동네의 태그·좌표 수정은 배열을 복사해 장소
참조를 교체하고, 생성·삭제·이동은 해당 동네의 구성을 다시 만든다. 다른 동네는 기존 구조를
공유한다. 기존 장소의 정렬 키는 유지하고 주기적 전체 재빌드에서 일괄 반영한다.

전체 재빌드는 정렬 키 반영과 함께 부분 갱신에서 놓친 상태를 DB 기준으로 다시 맞춘다.
이 작업이 복구하는 범위는 조회 모델이며, 조회 원천인 DB 데이터 자체의 오류를 수리하는
작업까지 포함하지는 않는다.

### DB 조회부터 배포까지 갱신 작업을 직렬화한다

```text
갱신 실행권 확보 → DB 조회 → 읽기 트랜잭션 종료 → 모델 생성
                → 버전 발급 → 배포 데이터 준비 → Redis 공개 → 실행권 해제
```

부분 갱신·전체 재빌드·표시값 갱신을 같은 순서 제어에 포함한다. 현재 JVM 내부의
`CacheWriteLock`은 로컬 갱신을 직렬화한다. 분산 빌더에서도 활성 발행자는 하나로 두며,
여러 어드민 프로세스를 운영한다면 리더 교체 후 이전 발행자의 쓰기를 거부할 실행권 번호
(fencing token)을 공개 단계에서 검사해야 한다. DB의 `AUTO_INCREMENT`는 버전의 유일성을
제공하지만, 그 번호만으로 DB 조회 내용의 최신성을 판정할 수는 없다.

### 완성된 최신 상태만 공개한다

Redis에는 version과 payload를 함께 읽을 수 있는 최신 Snapshot 레코드를 둔다.
큰 데이터는 임시 키에 먼저 준비할 수 있지만, 검증이 끝난 뒤 최신 레코드로 원자적으로
교체한다. 여러 키를 함께 공개한다면 Redis transaction 또는 Lua로 공개 경계를 묶는다.
Redis Cluster를 사용한다면 원자적으로 처리할 키의 동일 hash slot 배치도 필요하다.
이 경계는 공개 명령의 사전 검증을 포함한다. Redis transaction은 실행 중 오류에 대한
롤백을 제공하지 않으므로 명령을 묶는 것만으로 실패 처리가 끝나지는 않는다.
[Redis Transactions](https://redis.io/docs/latest/develop/using-commands/transactions/),
[Cluster specification](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)
키 구성은 아래 기본안으로 구체화한다. binary의 세부 스키마와 최대 payload 크기는 구현 시 확정한다.

현재 Snapshot을 공개하기 전에 그 모델을 서빙하는 데 필요한 표시값도 준비한다.
배포 중 임시 데이터는 작업 종료 후 정리한다. 과거 version을 조회하는 저장소나 보관 기간은
두지 않는다. API는 다운로드가 끝난 모델만 채택하며, 실패하면 현재 참조를 유지한다.

### Redis에는 어떤 키로 무엇을 저장하나

다음은 **분산 배포 구현을 위한 키 설계안**이다. 현재 애플리케이션에 이미 존재하는 키라는
뜻은 아니다. 예시는 `prod` 환경이며, 모든 키의 `{place-list}`는 Redis Cluster에서 함께
공개할 키를 같은 hash slot에 배치하기 위한 hash tag다.

| 키 | Redis 타입 | 저장 내용 |
|---|---|---|
| `prod:{place-list}:meta` | Hash | `snapshotVersion`, `displayRevision`, `writerToken` |
| `prod:{place-list}:snapshot:current` | Hash | `version`, `schemaVersion`, `encoding`, `checksum`, `payload` |
| `prod:{place-list}:views:current` | Hash | field는 장소 ID, value는 이름·썸네일 파일 키·대표 태그 ID의 인코딩 값 |
| `prod:{place-list}:tags:current` | Hash | field는 태그 ID, value는 이름·활성 상태의 인코딩 값 |
| `prod:{place-list}:staging:<buildId>:snapshot` | Hash | 공개 전 Snapshot 레코드. `buildId`는 실행마다 고유한 ID |
| `prod:{place-list}:staging:<buildId>:views` | Hash | 전량 교체를 준비할 때의 새 표시 맵 |
| `prod:{place-list}:staging:<buildId>:tags` | Hash | 전량 교체를 준비할 때의 새 태그 맵 |

각 표시 맵에는 예약 field `__schemaVersion`도 둔다. 장소·태그가 0개여도 빈 모델을 나타내는
키가 존재하게 하고, ID 조회·순회에서는 이 field를 제외한다. `snapshot:current`의 payload는
장소 값과 정렬 순서이며, 이름·썸네일은 포함하지 않는다. checksum은 payload 전송·저장
손상을 검증하는 값이고, schemaVersion은 읽을 수 있는 형식인지 판단하는 값이다.

`meta`를 먼저 읽으면 큰 payload를 받지 않고 갱신 필요성을 확인할 수 있다. Snapshot을
복원할 때는 `snapshot:current`의 version과 payload를 한 번의 `HMGET`으로 읽고, 로컬
모델을 준비한 뒤 `meta`를 다시 확인한다. 서로 다른 공개 시점의 데이터를 섞어 채택하지
않도록 실제 레코드 version·최신 version을 모두 대조한다.

```text
빌더가 새 모델 완성
  │
  ▼
staging 키에 payload와 필요한 전량 표시 맵 저장
  │                                      ← 임시 키만 만료 시간 설정
  ▼
공개 실행권·키 타입·필수 필드·목표 version 사전 검사
  │
  ▼
짧은 원자적 공개 구간                     ← 같은 hash slot에서 Lua 등으로 처리
  ├─ staging Snapshot을 snapshot:current로 RENAME
  ├─ 표시값: 변경 ID만 HSET / 전량 교체라면 staging 맵을 RENAME
  ├─ 공개된 current 키의 임시 TTL 제거(PERSIST)
  └─ meta의 snapshotVersion·displayRevision 갱신
  │
  ▼
Pub/Sub으로 공개 사실 알림               ← 저장 키와 별개의 채널
  │
  ▼
각 API가 meta와 current 데이터를 읽어 검증·채택
```

발행 채널은 `prod:place-list:updated`로 두고, 메시지에는 `snapshotVersion`,
`displayRevision`, `changedPlaceIds`, `fullDisplaySync`를 넣는다. 예를 들어 장소 42의
이름만 바꾸면 `views:current`의 field `42`와 displayRevision만 갱신한다.
Snapshot payload와 snapshotVersion은 그대로이며, 알림은 해당 ID를 다시 읽게 하는 신호다.
전량 표시 상태를 교체했거나 변경 ID가 많으면 전체 동기화 신호만 보낸다.

최신 키에는 TTL을 두지 않고, 준비 중 실패한 staging 키만 TTL과 작업 종료 정리로 제거한다.
`RENAME`은 목적지 키를 대체하므로 공개 후 과거 버전 키를 보관하지 않는다. 이력용
`snapshot:<version>` 목록은 만들지 않는다. 삭제된 장소의 표시값은 진행 중 요청을 위해
부분 갱신 시 남기고, 다음 전량 표시 맵 교체에서 제외하는 정책을 적용할 수 있다.
[Redis HSET](https://redis.io/docs/latest/commands/hset/),
[Redis RENAME](https://redis.io/docs/latest/commands/rename/)

단, 공개 명령의 원자성과 영속성·실패 복구는 별개다. Lua도 실행 중 오류를 자동 롤백하지
않으므로 쓰기 전에 검증하고, 공개 결과가 불완전하면 version·필수 데이터 검증에서 거부해
재배포한다. 큰 Hash를 대체할 때의 메모리 해제 비용과 staging/current의 동시 점유도
예산에 포함한다. 같은 hash slot에 모은 모델은 여러 Redis 노드에 자동 분산되는 구조가
아니므로, 단일 모델의 크기 한계는 별도로 판단해야 한다.

## 4. 빌더를 분리하면 API의 Heap·GC 부담은 어디까지 줄일 수 있나

생성 과정에서 잠시 필요한 객체와 API가 조회를 위해 계속 보관할 객체를 구분해야 한다.
DB 결과·그룹화·정렬 작업을 빌더가 맡아도, API에 최종 모델을 올리는 비용은 남는다.

```text
빌더 JVM에서 발생
  DB 결과 수신·변환 → 장소 객체 생성 → 동네별 정렬 → 직렬화
  → 조회 결과와 생성용 임시 객체 회수

API JVM에서 발생
  배포 데이터 수신 → 버퍼에서 장소 객체·정렬 배열 복원
  → current 참조 교체 → 교체된 모델을 참조하던 요청 종료
  → 수신 버퍼와 더 이상 참조되지 않는 객체 회수
```

빌더의 GC pause는 별도 JVM인 API의 요청 스레드를 직접 멈추지 않는다. 다만 같은 머신의
CPU를 경쟁하거나 DB·네트워크를 과도하게 사용하면 간접 영향은 남으므로 실행 자원 배치도
함께 고려한다.

### 정렬 결과까지 전달해 API의 재정렬을 피한다

배포 형식은 장소 데이터를 한 번씩 기록한 목록과 동네·정렬 축별 인덱스 배열로 구성하는
안이다. API는 장소 객체를 만들고 그 순서대로 참조 배열을 연결한다. 빌더가 만든 순서를
전달하므로 API에서 다시 정렬할 필요가 없다. 좌표의 결측값, 정렬 키 정밀도, 동률 순서까지
보존하고 검증해야 동일 version의 커서가 동일한 위치를 가리킨다.

장소 수가 `N`, 정렬 축이 `A`개라면 복원 작업과 최종 객체·배열의 규모는 `O(N+AN)`이다.
이 비용은 분리 후에도 각 API에서 발생한다. 빌더의 부분 갱신이 동네 일부만 복사하더라도
기본 배포 단위는 완성된 전체 Snapshot이므로 직렬화·전송·API 복원은 전체 크기에 비례한다.

### 적재 중의 메모리 여유까지 확보한다

API에는 current와 생성 중인 새 모델뿐 아니라 수신·압축 해제 등의 버퍼도 함께 존재할 수
있다. 교체 뒤에도 진행 중인 요청이 참조한 모델은 살아 있고, 참조가 끊어진 뒤에야 GC 대상이
된다. current를 한 벌만 보관해도 순간 점유가 한 벌로 제한되는 것은 아니다.

따라서 분리의 효과는 **API의 적재 구간을 포함한 사용자 latency**로 검증한다. 빌더의
처리 시간만 줄었거나 DB 조회가 API에서 빠졌다는 사실만으로 충분하지 않다.

복원 비용이나 최종 모델 크기가 실제 한계가 될 때 검토할 저장 표현·역직렬화 대안은
뒤의 **확장성 고려**에서 다룬다. 기본 배포 설계에서는 수신·복원·교체까지 포함한 API의
지연과 메모리 여유를 검증한다.

## 5. 커서 버전과 최신 Snapshot 복원

먼저 커서의 정렬·필터 지문을 검증한다. 지문이 맞지 않으면 `INVALID_PLACE_CURSOR`다.
버전 확인은 다음과 같이 처리한다.

```text
커서 없음
  └─ 로컬 current 확보 → 첫 페이지 조회

커서 있음
  ├─ 확보한 local current.version == cursor.version → 같은 참조로 조회
  └─ 로컬에 해당 version 없음
       └─ Redis primary에서 최신 version 확인
            ├─ cursor.version != latest.version → EXPIRED_PLACE_CURSOR
            └─ cursor.version == latest.version
                 → 최신 payload와 필요한 표시 상태 가져오기
                 → 내용·스키마·version 검증 및 최신 여부 재확인
                 → current 채택 후 해당 참조로 조회
```

로컬 적중 요청은 Redis를 왕복하지 않는다. 따라서 로컬이 아직 전파를 받지 못했다면
Redis보다 늦은 current로 요청을 처리할 수 있다. 로컬 적중에도 전역 최신성을 강제하려면
매 요청의 확인 비용이 필요하며, 이 설계는 빠른 전파와 주기적 동기화를 사용한다.

복원 중 Redis의 최신 버전이 바뀌면 읽던 버전을 과거 Snapshot으로 채택해 이어가지 않는다.
커서를 만료시키고 최신 목록 재요청을 요구한다. API의 백그라운드 동기화와 요청 복원은
하나의 실행 경로로 합쳐 중복 적재를 막는다. 채택 전에 local current도 다시 확인해
이미 더 최신인 로컬 모델을 덮거나, 채택이 거절된 모델을 요청에 넘기지 않는다.

최신 여부를 확인한 직후에도 다음 배포는 일어날 수 있다. 확인·채택 시 확보한 참조를
요청 끝까지 사용하는 것이 경계이며, 응답 종료까지 전역 최신 상태를 잠그지는 않는다.

| 상황 | 처리 |
|---|---|
| 커서가 Redis 최신 버전이며 로컬에만 없음 | 제한된 대기 시간 안에 복원하여 같은 커서로 계속 조회 |
| 커서가 Redis 최신 버전과 다름 | `EXPIRED_PLACE_CURSOR`, 커서를 버리고 첫 페이지 재요청 |
| Redis 장애 또는 최신 payload 자체 유실 | 최신 모델 복원 불가에 대한 일시적 오류; 빌더 재배포·재시도 |
| 초기 Snapshot이 전혀 없는 API | 초기 적재 완료 전 readiness를 열지 않음 |

Redis 오류를 오래된 커서라고 단정하지 않는다. 클라이언트는 만료 시 기존 목록을 첫 페이지로
교체하며, 자동 재시작 횟수를 제한한다. 새 첫 페이지를 기존 목록 뒤에 붙이지 않는다.

## 6. 표시값과 알림 유실 복구

표시값은 Redis에도 Snapshot과 별도로 저장한다. 장소 ID별 최신 표시값과 태그 맵을 두고,
표시 상태의 갱신 번호인 `displayRevision`을 별도로 증가시킨다. 값과 revision은 같은
원자적 공개 단위로 갱신하고, 전체 상태 교체도 완성된 맵을 준비한 뒤 공개한다. 표시값만 수정하는 작업은
Snapshot payload를 생성하거나 교체하지 않는다.

장소별 갱신 알림에는 변경 ID와 revision을 넣는다. API는 알림의 오래된 값을 직접 적용하는
대신 Redis에서 해당 ID의 최신 값을 읽는다. 연속된 revision의 갱신은 ID 단위로 처리하고,
번호가 건너뛰거나 기동·재접속한 경우에는 최신 표시 상태 전체를 읽어 따라잡는다.
전체 읽기는 읽기 전후 revision을 비교해 일관된 상태를 확보하고, 경합 시 제한적으로 재시도한다.
표시값 동기화도 API의 같은 갱신 실행 경로에서 처리해 전량 교체가 최신 ID 패치를 되돌리지 않는다.

Pub/Sub은 빠른 동기화를 시작하는 신호다. 유실 메시지를 다시 보내지 않으므로 API는
기동·재접속·주기 실행 시 저장된 `snapshotVersion`과 `displayRevision`을 직접 비교한다.
중간 알림을 모두 재생할 필요 없이 최신 상태로 수렴한다.
[Redis 공식 문서: Pub/Sub 전달 보장](https://redis.io/docs/latest/develop/pubsub/)

DB 전체 재빌드 주기와 API의 Redis 상태 확인 주기는 별도로 둔다. 전자는 DB에서 조회 모델을
맞추고, 후자는 이미 배포된 모델을 놓친 API를 복구한다. 반영 지연은 대기·생성·전송·적재
시간을 포함하며, 실패가 반복되는 동안에는 늘어난다.

표시 홀더는 Snapshot과 수명이 다르다. 요청이 Snapshot을 고정해도 표시값 전체가 같은 시점에
고정되지는 않으며, 현재 표시 맵에 없는 장소는 응답 조립 시 제외될 수 있다.

## 7. Redis 장애와 배포 복구

Redis의 읽기·쓰기는 현재 primary로 모은다. replica는 복제와 장애 전환을 담당한다.
Redis는 기본적으로 비동기 복제이므로 replica 읽기는 최신 version 판정에 지연을 추가할 수
있고, 장애 전환에서는 최근 쓰기가 유실될 수 있다. primary 읽기가 장애 전환까지 포함한
무손실을 보장하지는 않는다.
[Redis 공식 문서: Replication](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)

완성된 로컬 모델이 있는 API는 가능한 조회를 유지한다. 공유 모델이 유실되면 권한을 가진
빌더가 DB에서 새 version의 모델을 만들어 배포한다. API별 독립 버전 발급은 두지 않는다.
아무 데이터도 없는 API는 복구가 끝날 때까지 준비되지 않은 상태로 남는다.

API는 이미 채택한 version보다 낮은 공유 version으로 되돌아가지 않는다. 장애 전환으로
공유 상태가 후퇴했다면 빌더가 새 version을 배포해 수렴시킨다. 이 동안 로컬 버전 차이에
따른 커서 만료가 발생할 수 있다. 연결·명령·복원 대기를 제한하고 재연결 후 최신 상태를
다시 확인한다.

| 실패 지점 | 복구 경로 |
|---|---|
| DB 커밋 후 갱신 알림·실행 유실 | 다음 성공한 전체 재빌드에서 DB 기준으로 재조정 |
| 모델 준비 또는 Redis 공개 실패 | 현재 모델 유지, 갱신 작업 재시도 |
| 공개 성공 후 Pub/Sub 알림 유실 | API의 주기적 최신 상태 비교 |
| API 적재·검증 실패 | current 유지, 적재 재시도 |
| Redis 최신 데이터 유실 | 빌더의 새 version 배포 후 API 재동기화 |

## 8. 기본 배포 설계의 검증 범위

- 최신 커서의 로컬 미스는 복원하고, 오래된 커서는 명시적으로 만료시키는가.
- 적재 도중 추가 배포, 알림 중복·역순·유실에도 최신 상태로 수렴하는가.
- Redis의 meta·payload·표시 상태가 맞는지 검사하고 미완성 공개를 거부하는가.
- staging TTL이 current에 남지 않고, 초기 적재·장애 전환 후 복구가 가능한가.
- 직렬화 왕복 후 정렬·필터·거리순·커서 결과가 같은가.

현재 로컬 구조의 10배 데이터 검증과 성능 결과는 [로컬 Snapshot 문서](2026-09-09-admin-rebuild-tradeoff.md)에 기록한다.

## 확장성 고려: 병목과 요구가 달라질 때의 선택지

**여기부터는 기본 배포 파이프라인의 필수 구성이나 이번 구현 대상이 아니다.** 데이터 규모·
API 수·검색 요구가 커질 때 어떤 부분을 다시 검토할지 정리한다. SoA, 버퍼 직접 접근,
태그 역색인, 외부 검색 인프라는 모두 도입 조건이 확인됐을 때 선택할 대안이다.

### 현재 모델이 잘 맞는 범위와 세 가지 확장 문제

현재 목록 조회는 지역·한정된 태그·정해진 정렬 다섯 종류·거리순·페이지 조회로 범위가
정해져 있다. 공통 정렬은 미리 배열로 준비하고 태그는 비트마스크로 검사할 수 있다.
거리순은 요청 좌표에 따라 계산하되, 대상 동네와 태그로 후보를 한정한다. 어떤 형태의 조회를
지원해야 하는지 미리 알 수 있다는 점이 이 모델을 단순하게 유지하는 근거다.

확장 시에는 저장 표현, 여러 서버의 갱신, 후보 탐색을 구분한다. 하나의 해결책이 세 문제를
모두 해결하지는 않는다.

```text
현재: 객체 기반 Local Snapshot
  │
  ├─ 객체 수·Heap·GC 부담 증가
  │    ↓
  │  SoA로 저장 표현 검토
  │
  ├─ 여러 API의 동기화 / 모델 생성 비용 격리 필요
  │    ↓
  │  본문의 Builder + Redis 배포 설계
  │    ↓
  │  API 복원이 병목이면 배열 친화 binary·버퍼 접근 검토
  │
  └─ 태그 탐색량·검색 조건 복잡도 증가
       ↓
     가변 비트 집합 / 태그 역색인 검토

전체 모델의 복제 비용 또는 직접 구현할 검색 기능이 감당 범위를 넘어섬
  ↓
Elasticsearch 등 외부 조회 인프라 검토
```

이는 순서대로 밟는 단계가 아니다. 객체 수에 문제가 없어도 다중 API 운영을 위해 빌더를
분리할 수 있고, 단일 JVM에서도 태그 탐색량이 커지면 역색인을 검토할 수 있다.

### SoA: 장소별 객체 대신 필드별 primitive array에 저장한다

장소마다 `PlaceEntry` 객체를 만들고 여러 배열에서 참조하면, API 적재 때 장소 수만큼
객체를 생성해야 한다. 이 객체 수와 좌표 박싱 등이 할당·GC 부담의 주요 원인으로 확인되면
SoA(Structure of Arrays)를 후보로 둔다. **조회에 사용할 최종 표현 자체를 필드별 원시
배열로 두는 방식**이며, 전송 형식만 바꾸는 것과 구분한다.

```text
동네별 SoA 블록                         ← 부분 갱신의 복사 범위도 동네로 유지
  ├─ long[]   placeIds
  ├─ long[]   tagMasks
  ├─ double[] popularScores
  ├─ long[]   createdAtEpochSeconds
  ├─ long[]   bookmarkCounts / reviewCounts
  ├─ int[]    ratings
  ├─ double[] latitudes / longitudes
  ├─ 좌표 유효성 비트맵                  ← null을 0도 좌표로 바꾸지 않음
  └─ 정렬 축별 int[] order              ← 장소 객체 참조 대신 같은 블록의 행 번호

인기순 배열의 다음 위치
  │
  ▼
행 번호 i 읽기
  │
  ▼
tagMasks[i]로 필터 · placeIds[i]로 표시값 조회
```

원시 배열의 원소는 객체 참조가 아니므로 장소별 객체 헤더·박싱·원소별 참조 추적을 줄일
수 있다. GC가 추적할 배열 객체와 동네 블록은 남지만, 장소마다 별도 객체를 만들 필요는
없다. 다만 배열의 전체 바이트 수, 수신 버퍼, 교체 중 신구 모델의 동시 점유는 사라지지 않는다.
큰 배열은 G1의 humongous object 취급을 받을 수 있어 객체 수 감소만으로 pause 개선을
보장할 수도 없다. [Java 21 G1의 큰 객체 처리](https://docs.oracle.com/en/java/javase/21/gctuning/garbage-first-g1-garbage-collector1.html)

SoA에서도 공개된 배열은 수정하지 않는다. 태그·좌표 수정은 해당 동네 블록의 필요한 배열을
복사하고, 원소 구성이 바뀌면 행 번호와 정렬 인덱스를 함께 재구성한다. 필드 추가·결측값·
스키마 호환·간접 인덱스 접근을 관리하는 비용이 생기므로, 현재 객체 기반 구현에 바로
적용된 구조로 설명하지 않는다.

### Redis 수신 후 역직렬화는 어떻게 줄이나

Redis는 여기서 저장된 bytes를 전달한다. 줄이려는 것은 **API가 받은 bytes를 조회용
객체로 다시 풀어내는 과정**이다. binary를 쓴다고 그 과정이 자동으로 없어지지는 않는다.

| 선택 | 줄이려는 비용 | 남는 비용과 조건 |
|---|---|---|
| 정렬 순서까지 binary에 포함 | API의 재정렬·텍스트 숫자 파싱 | 객체 모델로 복원하면 장소별 객체 생성은 남음 |
| SoA에 맞춘 binary를 primitive array로 복원 | 객체별 역직렬화·박싱·중간 DTO | 배열 할당·디코딩·복사는 필요 |
| FlatBuffers 같은 버퍼 직접 접근 형식 | 전체를 별도 객체 그래프로 풀어내는 작업 | 버퍼를 조회 중 유지하고 접근 코드·스키마 검증을 관리 |
| 동일 version의 동시 적재를 하나로 합침 | 알림·타이머·커서 복원 경합의 중복 다운로드·할당 | 새 version을 한 번 적재하는 비용은 남음 |

```text
빌더에서 조회용 필드와 정렬 순서 완성
  │
  ▼
조회 표현에 맞는 binary로 인코딩
  │
  ▼
Redis 저장 · API 수신
  │
  ├─ 배열 복원 방식 → primitive array 생성 → 불변 모델 공개
  │
  └─ 버퍼 접근 방식 → 형식·범위 검증 → 버퍼를 가진 불변 모델 공개
                         ↑ 조회할 때 필요한 값에 직접 접근
```

FlatBuffers는 직렬화된 버퍼에서 별도 전체 unpack 없이 접근할 수 있는 형식을 제공한다.
그러나 네트워크 수신, 압축 해제, 접근용 객체나 문자열 처리까지 모두 무할당·무복사라는
뜻은 아니다. [FlatBuffers 공식 설명](https://flatbuffers.dev/)

압축은 전송량을 줄이는 대신 압축 해제 CPU와 버퍼를 요구한다. off-heap이나 memory-mapped
방식도 후속 후보지만, 메모리 수명과 해제를 직접 관리하고 요청이 참조하는 동안 저장 영역을
유지해야 한다. heap 점유만 줄이고 프로세스 전체 메모리를 놓치지 않아야 한다.

API 수가 늘면 한 번의 전량 배포도 API 수만큼 다운로드·복원이 발생한다. 모델 크기 `B`,
API 수 `I`, 초당 배포 횟수 `f`라면 단순 전량 배포의 전송량은 대략 `B × I × f`다.
이 비용이 허용 범위를 넘으면 최신 결과로 갱신을 합치거나 동네 블록 단위 배포를 검토한다.
변경분 전송을 택한다면 기준 version이 맞을 때만 적용하고, 빠진 변경이 있으면 최신 전량
모델로 복구해야 한다. 현재의 전량 배포 기본안에 이 복잡도를 필수로 넣지는 않는다.

### 태그가 복잡해지면 역색인으로 후보부터 좁힐 수 있다

현재 비트마스크는 “장소가 어떤 태그를 갖는가”를 작게 표현하고 후보 하나를 빠르게 검사한다.
태그 수가 표현 범위를 넘거나 희귀한 태그 조합 때문에 페이지를 채우기까지 지나치게 많이
스캔한다면, “태그에 해당하는 장소는 무엇인가”를 저장하는 역색인을 검토한다.
태그 수 증가만의 문제라면 가변 비트 집합도 대안이며, 곧바로 외부 검색 서버가 필요한 것은 아니다.

`long` 한 개의 표현 범위가 부족한 경우에는 여러 word로 늘리는 방법부터 검토할 수 있다.
반면 복합 AND/OR/NOT 조건이나 facet count(조건별 결과 수)가 필요해지면 후보 집합 연산의
가치가 커진다. NOT은 전체 장소에 대한 무제한 여집합이 아니라 대상 동네·공개 장소 같은
유효 후보 범위 안에서 제외 집합을 계산해야 한다. facet count는 현재 페이지의 10건만
세어서는 구할 수 없으므로 어떤 필터 범위의 전체 후보를 집계할지도 정해야 한다.

```text
태그 → 정렬된 장소 ID 목록 또는 장소 비트맵
  조용함    → {11, 25, 42}
  작업하기  → {11, 42, 70}
  주차가능  → {25, 42}
             │
             ▼
요청 조건: (조용함 OR 작업하기) AND 주차가능
             │
             ▼
그룹 내 합집합 → 그룹 간 교집합 → 대상 동네와 교집합
             │
             ▼
후보 {25, 42} 확보
             │
             ▼
선택한 정렬·커서 조건 적용 → 페이지 구성
```

정렬된 posting list는 두 목록을 포인터로 병합해 합집합·교집합을 구할 수 있다. 길이가
각각 `a`, `b`라면 단순 병합은 `O(a+b)`다. 밀집 비트맵은 기계어 단위 AND/OR로 처리하고,
희소한 경우에는 압축 비트맵을 후보로 둘 수 있다. 비용은 후보 밀도와 실제 표현에 따라 달라진다.

역색인은 필터 후보를 찾는 구조이므로 인기순 같은 결과 순서를 자동으로 제공하지 않는다.
후보가 적으면 후보만 정렬·top-K 처리하고, 후보가 많으면 사전 정렬 배열을 훑으며 후보
집합 포함 여부를 검사하는 방법을 비교한다. 거리순도 좁혀진 후보에 대해서 거리를 계산한다.

대신 태그별 목록의 저장 공간, 생성·삭제·태그 변경 시 색인 갱신이 추가된다. Snapshot과
역색인은 같은 version으로 함께 공개해야 후보 집합과 정렬 기준이 어긋나지 않는다.
인덱스에 SoA 행 번호를 저장한다면 블록 재구성 시 번호 변경도 함께 반영해야 한다.

### 어느 시점에 Elasticsearch 같은 외부 조회 인프라를 도입하나

기준은 장소 수 한 가지가 아니다. **API마다 전체 모델을 보관·갱신하는 비용과 직접 구현할
검색 기능의 범위가 서비스의 자원·지연·운영 예산 안에 있는가**로 판단한다. 현재의
6,320곳에서 10배인 63,200곳을 대상으로 하는 검증은 데이터 성장 여유를 확인하는 기준점이며,
그 수가 곧 Elasticsearch 도입 임계값이라는 뜻은 아니다.

| 도입 검토를 시작할 조건 | 현재 모델에서 부담이 되는 이유 |
|---|---|
| 최종 모델 + 교체 여유 + 요청 처리 공간이 API 메모리 예산을 초과 | 생성 위치를 옮겨도 전체 복제 모델은 각 API에 남음 |
| API 수·변경 빈도 증가로 배포와 적재가 허용 반영 지연을 넘음 | 조회 서버를 늘릴수록 동일 모델의 복제·전송 비용도 증가 |
| 현실적 부하에서 필터·거리 계산이 latency 목표를 지속적으로 초과 | 고정 정렬 배열과 후보 스캔만으로는 필요한 탐색 범위를 줄이기 어려움 |
| 전문 검색·형태소 분석·관련도·복잡한 지리 조건이 핵심 요구가 됨 | 범용 검색 기능과 색인을 애플리케이션에서 직접 유지해야 함 |

예를 들어 자유 텍스트·형태소 분석·오타 허용 검색·관련도 점수와 함께 가격 범위,
영업시간, 복합 속성 필터, facet까지 요구되면 장소 정렬 배열만으로 해결할 수 있는 범위를
벗어난다. 태그 역색인뿐 아니라 텍스트·범위 색인, 집계, 랭킹, 분산 동기화까지 직접 만들고
있다면 검색엔진을 직접 구현하는 비용과 외부 인프라 운영 비용을 비교할 시점이다.

Elasticsearch는 필드에 맞는 색인과 분산 검색을 제공한다. 텍스트의 역색인, 반경 조건을
처리하는 geo query 등을 활용할 수 있다. 로컬 배열 조회보다 언제나 빠른 도구라는 뜻은
아니며, 네트워크 왕복·검색 클러스터 운영·DB 변경 동기화·검색 반영 지연이 추가된다.
[Elasticsearch 색인 구조](https://www.elastic.co/docs/manage-data/data-store/index-basics),
[Geo-distance query](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-geo-distance-query)

```text
원본 DB 변경 커밋
  │
  ▼
변경 전달 · 재시도 가능한 동기화       ← 필요하면 Outbox / CDC
  │
  ▼
Elasticsearch 장소 문서 upsert/delete
  │
  ▼
검색에 반영되는 시점 도달
  │
  ▼
API가 조건·정렬·커서를 전달해 조회     ← 전체 장소 모델을 API마다 적재하지 않음
```

전환하더라도 커서 정책은 별도로 설계해야 한다. Elasticsearch의 `search_after`와 PIT는
일관된 페이지 탐색에 사용할 수 있지만, PIT를 오래 유지하면 과거 검색 상태를 이어가게 된다.
현재 서비스의 “최신 조회 기준과 다르면 만료” 정책을 지키려면 검색에 실제 반영된 세대와
커서를 대조하고, DB 커밋 번호만 먼저 올려 미반영 검색 결과를 최신으로 취급하지 않아야 한다.
[Elasticsearch 페이지 탐색](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/paginate-search-results)

SoA는 **저장 표현과 GC**, 역색인은 **후보 탐색**, 외부 검색 인프라는 **데이터 배치와 검색
기능의 운영 책임**을 다룬다. 반드시 순서대로 모두 도입하는 단계가 아니라, 실제로 한계에
도달한 부분에 맞춰 선택할 대안이다.
