# Current 한 벌과 장소 단위 부분 갱신

작성일: 2026-09-10

이 문서는 같은 날짜의 전량 재빌드 유지 판단과 분산 확장 제안보다 우선하는 요구사항이다.
어드민 변경을 빠르게 반영하기 위해 과거 커서의 연속성을 포기하고, 현재 조회 모델 한 벌을 유지한다.
구현 범위는 현재 JVM의 조회 모델이다. Redis 배포·별도 빌더 도입은 포함하지 않는다.

## 보관과 커서

- `SnapshotBox`는 `volatile current` 하나만 보관한다. 완성된 불변 모델을 한 번에 교체한다.
- 요청은 current 참조를 한 번 잡고, 커서 검사·정렬·필터·거리 계산에 같은 참조를 사용한다.
- 커서 버전이 잡아 둔 current 버전과 다르면 `EXPIRED_PLACE_CURSOR`를 반환한다.
  과거 모델을 찾거나 복원하지 않는다. 클라이언트는 기존 목록을 버리고 첫 페이지를 요청한다.
- 전체 재빌드와 실제 후보·필터·좌표 변경은 새 버전을 발급한다. 표시값만 바뀌거나 중복 알림으로
  내용이 그대로이면 부분 갱신은 버전을 발급하지 않는다.
- 버전 증가 폭이 1일 필요는 없다. 발급 실패·다른 발급자 때문에 번호가 비어도 된다.

현재 참조를 교체해도 이미 시작한 요청의 로컬 참조는 유효하다. 따라서 한 벌은 **홀더가 보관하는
개수**다. 느린 요청이 여러 번의 교체를 걸쳐 살아 있으면 과거 모델도 그만큼 살아 있을 수 있다.
표시값은 별도 홀더에서 최신 값을 읽으므로 응답 전체가 한 시점으로 고정되는 것은 아니다.

## 어드민 변경

```text
장소 변경 + place_stats 반영 → DB 커밋 → 변경 장소 ID 수집
  → CacheWriteLock 획득 → 새 읽기 트랜잭션으로 해당 ID의 최신 상태 조회
  → 현재 모델에 부분 적용 → 변경이 있으면 버전 발급
  → 표시값 반영 → 완성된 Snapshot 참조 교체 → 락 해제
```

변경 종류를 세분화한 이벤트 대신 장소 ID를 전달한다. DB 행이 없으면 제거 대상으로 해석한다.
한 트랜잭션의 여러 ID는 중복을 제거해 묶어서 반영한다. 생성·삭제·활성화·동네 이동도 같은 경로다.
이름·썸네일만 바뀐 경우에는 Entry가 같으므로 정렬 구조 복사와 버전 발급을 건너뛴다.
이미지 후처리처럼 표시값만 수정하는 경로와 태그 표시 맵 갱신은 별도로 유지한다.

| 현재 Entry와 최신 상태의 차이 | 적용 |
|---|---|
| 태그·좌표 변경, 동네 동일 | 해당 동네의 정렬 배열을 복사하고 같은 위치의 참조만 교체 |
| 생성·삭제 | 영향받은 동네의 배열 구성 변경 |
| 동네 이동 | 이전 동네에서 제거하고 새 동네에 삽입 |
| 표시값만 변경 또는 내용 동일 | 기존 정렬 구조를 그대로 사용 |

영향받지 않은 동네의 배열과 Entry는 공유한다. 기존 배열이나 Entry를 직접 고치지 않는다.
현재 Entry의 위치는 기존 정렬 축 하나를 탐색해 찾는다. 별도 장소별 인덱스는 두지 않으므로
이 탐색은 최악에 전체 장소 수에 비례한다. 줄어드는 것은 전량 DB 조회·Entry 재생성·전체 동네
재정렬이며, 부분 갱신 전체가 상수 시간이 되는 것은 아니다.

## 정렬 키는 전체 재빌드에서 일괄 반영

부분 조회가 읽은 DB 행에는 배치가 갱신한 통계도 포함될 수 있다. 이 값을 배열의 기존 위치에
그대로 넣으면 이진 탐색과 병합의 정렬 전제가 깨진다. 따라서 기존 장소는 부분 갱신 시
**현재 Entry의 점수·생성일·북마크 수·리뷰 수·평점을 유지**한다. 동네 이동도 같은 원칙이다.
신규 장소는 기존 Entry가 없으므로 DB에서 읽은 초기 키로 삽입한다.

주기적 전체 재빌드가 모든 장소의 정렬 키를 함께 갱신한다. 동시에 DB에서 후보·태그·좌표·
표시값을 다시 읽어, 누락된 알림이나 실패한 부분 갱신을 복구한다. "정렬 키 일괄 반영용"이라는
정책은 reconciliation 때 다른 필드를 읽지 않는다는 뜻이 아니다.

## 갱신 순서와 실패

전체 재빌드·부분 갱신·표시값 갱신은 기존 `CacheWriteLock`을 공유한다. 락을 잡은 뒤 DB를 읽고
모델을 만들고 교체하므로 오래된 상태로 시작한 작업이 최신 부분 갱신을 덮을 수 없다.
읽기 트랜잭션은 버전 발급 전에 닫는다. 조회 요청은 이 쓰기 락을 획득하지 않는다.

모델 생성과 버전 발급에 실패하면 current를 유지한다. 어드민 DB 트랜잭션은 이미 커밋되었으므로
갱신 실패를 로그로 남기고 다음 성공한 전체 재빌드에서 복구한다. 반복 실패까지 포함해
"항상 최대 10분"으로 보장하지 않는다. 새 장소의 표시값은 새 Snapshot보다 먼저 공개한다.

이 락은 JVM 내부의 순서를 보장한다. 여러 API 인스턴스에 어드민 변경을 빠르게 반영하려면
별도 전파 경로가 필요하다. DB에서 유일한 버전을 발급받는 것만으로 내용이나 반영 시점이
동기화되지는 않는다. 분산 배포를 도입하더라도 과거 커서 복원은 추가하지 않는다.

### 별도 경계: 동네 계층 변경

장소의 동네 이동은 위 부분 갱신으로 처리한다. 그러나 `AdminTownService.updateTown`의
상위 지역 변경은 `TownHierarchyResolver`가 요청마다 읽는 후보 동네 집합을 바꾸며,
장소 Entry 자체는 바뀌지 않을 수 있다. 이 경로까지 후보 집합의 버전 고정을 보장하려면
추가 무효화 규칙이 필요하다. 현재 장소 단위 변경 범위와 구분해 후속으로 남기며,
동네 계층 변경까지 커서 일관성이 해결되었다고 주장하지 않는다.

## 검증과 성능 판단

정확성 검증은 과거 커서 만료, 요청이 잡은 참조의 불변성, 영향 없는 배열 공유, 다섯 정렬과
거리·태그 결과, 생성·삭제·이동, 표시값 변경 시 버전 유지, 갱신 직렬화와 실패 복구를 대상으로 한다.

기존 보존 3장 기준 성능 수치는 과거 측정으로 남긴다. current 한 벌 정책의 실측치로 바꾸어
인용하지 않는다. 교체된 모델이 더 이상 참조되지 않고 GC가 회수한 안정 상태에서는 과거 모델의
보존 비용이 줄지만, 재빌드 도중 신구 모델과 중간 결과가 공존하는 비용은 남는다.

다음 성능 검증의 질문은 **주기적 전체 재빌드 구간이 실제 사용자 요청 지연을 높이는가**다.
같은 데이터·JVM·자원 제한·요청 부하에서 재빌드가 없는 구간과 있는 구간을 비교한다.

- Throughput: 완료 요청 수와 오류율, GC 시간·CPU 비중.
- Latency: 요청 p50/p95/p99와 최대 지연, 단일 GC 정지와 재빌드 시점의 겹침.
- Footprint: 안정 상태 힙과 재빌드 중 최대 힙을 구분.
- 원인 확인: 재빌드 시간·CPU·allocation·GC 종류/빈도/정지·Old 변화·스로틀링.

무부하 재빌드는 자원 비용을 보여 주지만 사용자 지연의 무영향을 입증하지 못한다.
CPU·할당·GC의 어느 부분이 지연과 함께 움직이는지 확인한 뒤 로더 최적화나 빌더 분리를 검토한다.

Java 21에서 `./gradlew build` 성공. 전체 테스트 392개, 실패·오류·스킵 0개.
실제 MySQL은 Testcontainers로 검증했다.

- current만 보관하고 재빌드 한 번 뒤 기존 커서가 만료된다. 요청이 잡은 참조는 불변이다.
- 부분 갱신은 영향 없는 동네 배열을 공유하고, 기존 장소의 정렬 키는 유지한다.
- 어드민 생성·삭제·동네 이동·태그·좌표 변경과 표시값 변경을 실제 DB 경로에서 확인했다.
- 전체 재빌드가 먼저 시작한 경우와 부분 갱신이 먼저 시작한 경우를 각각 제어해 직렬화를 확인했다.
- DB 읽기·버전 발급 실패 시 current 유지, 실패 후 락 해제, 표시값만 바뀔 때 버전 유지를 확인했다.

이 결과는 기능·회귀 검증이다. 새 구조의 live heap 감소량이나 사용자 부하 중 재빌드 지연은
측정하지 않았고, 동네 계층 변경과 다중 인스턴스 전파는 위에 적은 별도 경계로 남는다.
