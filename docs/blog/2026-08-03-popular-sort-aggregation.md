# 인기순 정렬을 요청마다 계산하지 않기로 했다

SOLPLY는 혼자 가기 좋은 장소와 코스를 추천하는 서비스다. 장소 목록에는 최신순뿐 아니라
북마크와 리뷰를 반영한 인기순이 필요했다. 문제는 인기순이 단순한 컬럼 정렬이 아니라는 점이었다.
시간이 지나면 북마크의 영향은 줄어들어야 했다. 동시에 화면에 표시할 북마크 수·리뷰 수·평점과
순위용 인기점수는 갱신 주기가 서로 달라도 됐다.

이 글은 인기순 조회를 구현하면서 정한 트래픽과 서버 환경, 요청 시점 집계를 버리고 배치 사전
집계를 선택한 이유, 카운트와 인기점수의 배치 주기를 분리한 이유, 그리고 목표 부하에서 구조를
검증한 과정만 다룬다. 태그 필터의 조인 순서와 실행계획 개선은 별도 글에서 다룬다.

## 먼저 목표를 정했다

실사용자가 없는 서비스였기 때문에 관측된 트래픽으로 서버를 산정할 수는 없었다. 대신 어느 정도의
사용자를 감당할 서비스를 만들 것인지 먼저 가정했다.

```text
DAU 200,000명 × 하루 목록 탐색 30회 ÷ 86,400초 × 피크 계수 5
≈ 피크 시간대 목록 탐색 347회/s
```

정밀한 용량 예측이 아니라 검증할 규모를 정하기 위한 가정이다. 부하 테스트에서는 초당 300회
목록 탐색을 시작하는 조건(`300 arrivals/s`)을 최소 검증 지점으로 정했다. 한 번의 목록 탐색은
첫 페이지 조회로 끝나기도 하고 다음 페이지 조회로 이어지기도 했다. 최종 시나리오에서는 목록
탐색 한 번이 평균 1.55개의 HTTP 요청을 만들었으므로, 서버가 실제로 받은 요청은 초당 약
467건이었다.

따라서 `arrivals/s`와 `HTTP req/s`는 다른 값이다. 앞의 값은 목록 탐색이 시작된 횟수이고,
뒤의 값은 그 과정에서 서버가 실제로 받은 요청 수다. 이후에는 두 수치를 구분해 표기한다.

## 고가용성보다 단순한 운영 구조를 택했다

결제나 주문처럼 잠깐의 중단이 금전 손실이나 데이터 불일치로 이어지는 서비스가 아니다. 따라서 처음부터
서버 이중화, DB 복제, 분산 캐시를 운영하기보다 외부 요청을 받는 프록시 뒤에 애플리케이션 한 대와 MySQL
한 대를 두는 구조로 시작했다. 이중화는 사용자와 장애 비용이 그 복잡성을 정당화할 때 도입하기로
했다.

벤치마크의 최초 자원 상한은 다음과 같았다.

| 구성 | CPU | 메모리 | 내부 예산 |
|---|---:|---:|---|
| 애플리케이션 | 2 vCPU | 2 GiB | JVM 최대 힙 1.25 GiB, Tomcat 50 threads, Hikari 10 |
| MySQL | 2 vCPU | 3 GiB | InnoDB buffer pool 2 GiB, max connections 200 |

이 값은 실사용 관측으로 도출한 정답이 아니다. 단일 서버 안에서 병목을 드러낼 수 있도록 시작점을
제한한 것이다. 앱 메모리는 2 GiB 중 1.25 GiB만 힙에 배정해 metaspace, thread stack, direct
buffer와 JVM 자체 메모리를 남겼다. DB는 3 GiB 중 2 GiB를 buffer pool에 배정해 데이터 캐시
공간과 MySQL 프로세스의 나머지 메모리를 분리했다. CPU는 앱과 DB에 각각 2 vCPU를 주고 어느
계층이 먼저 포화되는지 측정했다.

데이터는 작업이 진행되면서 두 번 바뀌었다. 초기 검증은 장소 719개·북마크 약 400만 건으로
했고, 이후 장소 6,320개, 사용자 100,001명, 북마크 약 1,040만 건, 리뷰 198,191건까지 키웠다.
운영 데이터는 없지만, 데이터가 적어서 집계 비용이 드러나지 않는 일을 피하려고 북마크 데이터를
의도적으로 크게 만들었다. 아래에서 수치를 인용할 때는 어느 쪽 데이터인지 함께 밝힌다.

## 요청마다 계산하는 비용은 데이터와 함께 증가했다

인기순이 없을 때 북마크는 존재 여부만 확인하면 됐다. 인기순을 추가하자 장소별 북마크를 세고,
작성 시각에 따라 감쇠한 값을 더한 뒤 정렬해야 했다.

이를 조회 요청 안에서 계산하면 사용자가 목록을 열 때마다 같은 북마크 데이터를 다시 집계한다.
초기 데이터(장소 719개·북마크 약 400만 건)에서 서울 단위 조회 **한 번**이 장소 435곳에 연결된
북마크 인덱스 엔트리 약 325만 개를 읽는 것을 확인했다. 사용자가 넓은 범위를 고를수록, 그리고
북마크가 쌓일수록 요청 하나의 비용이 함께 증가하는 구조였다.

반면 인기순은 매 요청마다 새로 계산할 정도로 즉시 바뀔 필요가 없었다. 다수 사용자의 북마크와
리뷰가 누적되어 만들어진 상위권은 몇 분 사이에 크게 변하지 않고, 사용자는 한 시간 전의 순위를
오류로 인식하지 않는다. 그래서 북마크와 리뷰는 주기적으로 한 번만 집계하고, 사용자 요청에서는
계산된 결과만 읽도록 분리했다. 즉, 정해진 시각에 실행되는 배치 작업이 점수를 미리 계산하고,
사용자 요청을 처리할 때는 그 결과만 조회한다.

```text
북마크·리뷰 데이터
        │
        │ 카운트: 매시 30분 / 점수: 매일 01:00 KST
        ▼
   place_stats
        │
        │ 사용자 요청에서는 계산 없이 결과만 조회
        ▼
   인기순 장소 목록
```

## 계산은 데이터가 있는 DB에서 끝냈다

배치를 애플리케이션에서 계산하는 방법도 검토했다. 하지만 어느 쪽에서 계산하더라도 북마크와
리뷰 행은 먼저 DB가 읽어야 한다. 애플리케이션으로 가져오면 그 위에 네트워크 전송, JDBC 변환,
Java 객체 생성, 힙 사용과 결과 재저장 비용이 추가된다.

점수 계산은 `GROUP BY`, `SUM`과 시간 감쇠로 표현되는 관계형 집계였다. 복잡한 모델 추론이나
외부 데이터 결합도 없었다. 카운트 배치는 `INSERT ... SELECT ... ON DUPLICATE KEY UPDATE`로
표시용 통계를 적재하고, 인기점수 배치는 `UPDATE ... JOIN`으로 이미 존재하는 행의 점수만 갱신한다.
애플리케이션은 배치의 시작과 트랜잭션 경계만 관리한다.

이 선택은 DB 계산이 언제나 우월하다는 뜻이 아니다. 행별 연산이 복잡해지거나, 배치가 사용자
요청을 처리하는 쿼리와 DB CPU를 두고 경쟁하거나, 여러 작업자로 나눠야 할 정도로 커지면 계산
위치를 다시 검토해야 한다. 현재 규모에서는 데이터를 애플리케이션으로 옮기지 않는 편이 단순하고
저렴했다.

## 다시 계산할 수 있는 통계는 별도 테이블에 저장했다

집계를 배치로 하기로 한 것과 그 결과를 어디에 저장할지는 별개의 결정이다. 후보는 둘이었다.
`places`에 통계 컬럼을 붙이거나, `place_stats`라는 별도 테이블을 만들거나.

`places`에 붙이면 조인이 없어져 조회는 단순해진다. 대신 배치가 도는 동안 문제가 생긴다.
InnoDB에서 수정 흔적(더티)은 행이 아니라 16KB 페이지 단위로 남는다. 통계 컬럼 몇 개만
갱신해도 그 행이 담긴 페이지 전체가 더티가 되는데, 같은 페이지에는 장소명·주소·좌표 같은
정적 데이터가 함께 들어 있다. 결합 구조에서는 전 행을 갱신하는 배치가 돌 때마다 장소
정적 데이터 전체가 쓰기 영향권(더티 페이지 flush, 언두 추적)에 드는 것이다.

이 우려를 이론으로 두지 않고 쟀다. 벤치 DB에만 결합 구조를 흉내 내고(더미 통계 컬럼과
랭킹 인덱스 미러) 같은 집계 배치를 착지점만 바꿔 발화한 뒤, 읽기 부하 위에서 배치 직후
테이블별 더티 페이지 수를 셌다. 골격 캐시는 꺼서 읽기가 실제로 `places`를 읽게 했다.
결합 흉내에서는 `places` 클러스터드 66페이지 중 65~66개 — 사실상 전부 — 가 더티가 됐고,
분리 구조에서는 0이었다. 두 번씩 재현됐고 0 대 전부의 자릿수 차이라 측정 노이즈와
무관하다. 반면 배치 창의 읽기 응답 차이는 이 규모에서 구분되지 않았다 — 창 내 지연
상승(최대 1.83배, 자릿수 악화 없음)의 지배 항은 착지점이 아니라 배치 집계 자체의 DB CPU
경쟁이었다. 그래서 "결합이면 조회가 느려진다"고는 말하지 않는다. 분리가 실측으로 얻는
것은 페이지 오염 격리이고, 나머지 근거는 운영에 있다.

장소는 직접 관리해야 하는 핵심 데이터지만, 인기점수·북마크 수·리뷰 통계는 북마크와 리뷰
데이터에서 언제든 다시 계산할 수 있다. 성격과 갱신 주기가 다른 통계를 장소 정보와 분리하면
배치가 실패했을 때 다시 실행하거나 새 계산식을 적용하기도 쉬워진다.

Redis sorted set도 후보였지만 인기순 저장소로는 선택하지 않았다. 시간 감쇠 점수는 시간이 지나면
저장된 값 자체가 낡기 때문에 DB의 북마크 데이터를 다시 계산하는 작업은 사라지지 않는다. Redis를
추가하면 DB에서 계산한 결과를 캐시에 한 번 더 복제하고, 값이 바뀔 때 기존 캐시를 비우는 작업까지
관리해야 한다. 목표 부하에서 DB 정렬이나 조회가 병목이라는 증거가 없었으므로 운영 복잡도를 늘릴
이유가 없었다.

## 표시 카운트와 인기점수의 주기를 분리했다

카운트와 점수는 같은 북마크·리뷰 데이터를 읽지만 필요한 갱신 주기가 다르다.

| 집계 | 주기 | 결과 |
|---|---|---|
| 카운트 | 매시 30분 KST | `town_id`, 북마크 수, 리뷰 수, 평균 평점 |
| 인기점수 | 매일 01:00 KST | 북마크 감쇠 점수와 리뷰 기반 점수 |

카운트 배치는 활성 장소의 통계를 새로 넣거나 갱신(UPSERT)한 뒤, 이번 실행 대상에 포함되지 않은
`place_stats` 행을 같은 트랜잭션에서 삭제한다. 인기점수 배치는 행을 만들지 않고 기존 행의 `popular_score`와
`score_calculated_at`만 갱신한다. 따라서 카운트 배치가 만든 신규·재활성 장소는 다음 인기점수
배치 전까지 인기순에서 제외되며, 최신순에서는 카운트가 표시된다.

## 인기와 평판의 시간 특성을 분리했다

최종 점수는 북마크와 리뷰를 서로 다르게 다룬다.

```text
인기점수 = 북마크 가중치 × ln(1 + Σ 북마크 시간 감쇠)
         + 리뷰 가중치 × (베이지안 조정평점 - 전체 평균평점)
```

북마크는 최근 관심을 나타내므로 시간이 지나면 영향이 줄어든다. 반면 리뷰는 장소에 대한 누적된
평가다. 리뷰까지 감쇠시키면 소수의 최근 리뷰가 다수의 과거 평가를 지나치게 덮을 수 있어 시간
감쇠를 적용하지 않았다. 리뷰 수가 적은 장소의 극단적인 평점이 상위권을 차지하지 않도록 실제
구현에서는 베이지안 평균을 사용했다. 북마크 합에는 로그를 적용해 행동 수가 많은 장소의 점수가
무한히 선형 증가하지 않게 하고, 범위가 제한된 리뷰 축이 완전히 묻히지 않도록 두 축의 크기를
맞췄다.

핵심은 정확한 상수보다 각 신호의 의미에 맞는 시간 특성을 정의한 것이다. 계산식이 바뀌어도
`place_stats`는 북마크와 리뷰 데이터에서 다시 만들 수 있다. 따라서 사용자 요청을 처리하는 조회
방식은 바꾸지 않고 점수 계산식만 교체할 수 있다.

## 변경분만 반영하지 않고 매번 전체를 다시 계산했다

북마크가 추가될 때마다 통계를 `+1` 하는 증분 방식은 숫자를 더 빨리 반영할 수 있다. 대신 이벤트
누락, 중복 처리, 배치와 증분 갱신의 경합, 음수 방지와 재처리 정책이 필요하다. 현재는 증분
이벤트를 받아 처리할 시스템도 없으므로 관련 이벤트 발행·타입을 제거하고, 실행할 때마다 전체
데이터를 다시 계산하는 배치만 남겼다.

즉시 반영이 꼭 필요한 것은 사용자가 방금 누른 북마크의 체크 상태다. 이것은 실제 북마크 데이터에서
바로 보여줄 수 있다. 목록에 표시되는 누적 수는 한 시간 이내, 인기점수는 하루 이내 지연을 허용했다.
그래서 표시 카운트와 인기점수 배치를 서로 다른 주기로 운영한다. 두 배치는 각각 하나의
트랜잭션으로 실행된다. 중간에 실패하면 그 실행에서 변경한 내용을 모두 되돌리고, 다음 실행에서
전체 데이터를 다시 계산한다.

이 방식은 같은 기준 시각과 데이터로 여러 번 실행해도 결과가 같아서 실패 후 그대로 다시 실행할
수 있다. 북마크의 90일 반감기만 보면 인기점수를 매시간 계산할 필요는 없다. 하루 동안의
감쇠 변화는 약 0.77%이므로 인기점수는 새벽 1회로 내렸다. 카운트는 신규 장소, 동네 변경, 관리자
비활성화가 목록에 반영되는 지연을 한 시간 안으로 제한하기 위해 매시 실행한다.

배치 트랜잭션은 `READ COMMITTED`에서 실행하고 집계 대상에 기준 시각 상한을 둔다. 기본
`REPEATABLE READ`에서 집계 갱신을 실행했을 때 대량의 next-key lock이 발생했던 문제를 피하면서,
한 번의 배치가 어느 시각까지 생성된 데이터를 계산했는지도 명확하게 만들었다.

## 버전 행 대신 최신 행과 단순한 커서를 사용한다

초기 설계에서는 배치를 실행할 때마다 통계 행을 새로 만들고 현재·직전 버전을 함께 보관했다. 그러나
인기점수 배치를 매일 새벽으로 옮기면서 전체 장소의 점수가 한꺼번에 갱신되는 시점을 트래픽이 가장
적은 시간대로 제한할 수 있게 됐다. 그 결과 장소당 최신 행 하나만 유지하고, 현재 통계 버전을
기록하던 레지스터와 커서에 버전을 고정하던 `generation`을 제거했다.

```text
카운트  ──────> 최신 place_stats 행 갱신
점수    ──────> 다음 새벽에 최신 place_stats 행 갱신
```

`place_stats`의 기본키는 `place_id` 하나다. 다음 페이지의 시작점을 나타내는 커서에는 정렬 종류,
정렬 키, 장소 ID와 요청 필터를 식별하는 값만 담는다. 다른 필터에서 발급한 커서의 재사용은 계속
거부하지만, 새벽 점수 갱신과 페이지 이동이 우연히 겹칠 때 발생할 수 있는 중복·누락까지 막지는
않는다. 발생 가능성이 낮은 문제를 막기 위해 통계 버전 전체를 관리하는 복잡성이 더 크다고
판단했다. 배치 주기를 다시 짧게 바꾸면 이 결정을 재검토해야 한다.

조회 인덱스는 지역 조건 뒤에 점수와 장소 ID를 둬 마지막 조회 위치부터 다음 페이지를 읽는
커서 페이지네이션을 지원한다. 여러 동네를 한꺼번에 조회하는 시 단위 목록에는 DB가 결과를
별도로 정렬하는 작업(`filesort`)이 남지만 대상이 수백에서 약
1,800행이어서 수용했다. 이를 없애기 위한 비정규화는 실측 문제가 생길 때로 미뤘다.

## 정확성, 실행계획, 부하를 서로 다른 질문으로 검증했다

먼저 통합 테스트로 다음 계약을 확인했다.

- 카운트 배치의 통계 입력·갱신과 더 이상 유효하지 않은 행의 삭제는 함께 롤백된다.
- 카운트 배치와 인기점수 배치가 서로의 컬럼을 덮어쓰지 않는다.
- 부팅 시 카운트를 먼저 적재하고, 미채점 행이 있으면 점수를 이어서 계산한다.
- 미채점 기본값 0이 음수인 실제 점수보다 위에 노출되지 않는다.
- v4 커서의 필터 지문과 정렬 경계가 검증된다.

실행계획에서는 단일 동네와 시 단위, 첫 페이지와 커서 페이지가 의도한 통계 인덱스를 사용하는지,
실제로 몇 행을 읽고 어디에서 filesort가 발생하는지 확인했다. 다만 기존 실행계획 기록은 버전 행
스키마 기준이며, V32에서 버전 관련 컬럼을 제거한 뒤의 인기순 실행계획과 잠금 범위는 아직
재채취 대상이다. 실행계획의 세부적인 태그 조인 문제와 개선 과정은 이 글의 범위에서 제외한다.

마지막으로 버전 행 조회 구조와 태그 필터 개선이 반영된 당시 코드, 북마크 약 1,040만 건 데이터에서
짧은 최소 안정성 부하 테스트를 했다. 아래 수치는 현재 V32 단일 행 구조의 재측정 결과가 아니라
이전 기준선으로 보존한다.

| 조건 (2026-08-06 측정) | 결과 |
|---|---|
| 앱 2 vCPU, 초당 목록 탐색 시작 300회 | 35,409건 전부 200·실패 0, 그러나 CPU 사용이 제한된 주기 18.2%, p99 391.6ms |
| 앱 4 vCPU, 초당 목록 탐색 시작 300회 | 약 467 HTTP req/s, 35,332건 전부 200, 실패 0 |
| 4 vCPU 응답시간 | p50 6ms, p95 13.9ms, p99 59.7ms |
| 4 vCPU 앱 CPU | 평균 1.198 core, CPU 사용이 제한된 주기 0.8% |
| MySQL (4 vCPU 라운드) | 평균 0.766 core, 락 대기·디스크 임시 테이블·버퍼풀 디스크 읽기 0 |

2 vCPU에서 앱 CPU 상한만 4 vCPU로 올리자 CPU 사용이 제한된 주기는 18.2%에서 0.8%로, p99는
391.6ms에서 59.7ms로 줄었다. DB 구조나 데이터는 바꾸지 않았다. 목표 부하의 병목은 인기순
집계 구조나 DB가 아니라 애플리케이션 CPU 예산에 가까웠다.

이 결과는 약 1분의 짧은 로컬 테스트이므로 장시간 운영에서의 응답시간·성공률 목표를 보장하지
않는다. 또한 실행 중인
컨테이너의 CPU 쿼터만 4 vCPU로 변경했기 때문에 JVM을 처음부터 4 vCPU 환경으로 기동한 실험도
아니다. 다만 2 vCPU 기준으로는 목표 부하를 오류 없이 처리했지만 스로틀 18.2%로 여유가
없었고, DB는 포화되지 않았으며, 앱 CPU 상한을 풀었을 때 꼬리 지연이 함께 줄었다는 방향은
확인했다. 이 "여유 없음"이 다음 글(장소 골격 캐시)의 출발점이 된다.

## 측정 결과 캐시는 도입하지 않았다

목표 부하에서 MySQL은 여유가 있었고 실행계획도 부하에 따라 흔들리지 않았다. 따라서
인기순 첫 페이지를 캐시해 얻을 이익보다 무효화, 정합성, 장애 지점과 운영
복잡도가 더 컸다. Redis는 다른 기능에서 사용하더라도 인기순 결과 캐시에는 사용하지 않았다.

특정 동네·필터 조합에 요청이 집중된다면 캐시의 실익은 생길 수 있다. 다만 현재는 정합성 문제와
무효화 복잡도가 병목보다 크다고 판단해 도입하지 않았다. 향후 캐시를 추가한다면 인기순의
동네·필터별 장소 ID 후보를 캐시하고, 배치 성공 후 버전을 교체하는 방식이 우선 후보이다.
표시 카운트는 캐시에 넣지 않고 DB에서 다시 읽어 한 시간 단위의 갱신 주기를 유지한다.

## 이제 확인할 것은 데이터 증가에 따른 배치 비용이다

사용자 요청은 위 표의 조건에서 목표 부하를 처리했지만, 배치는 여전히 모든 북마크와 리뷰를
읽어 집계한다. 오래된
북마크를 읽지 않는 방안도 검토했지만, 현재 병목으로 관측되지 않았고 인기점수를
하루 1회로 낮추면서 절감 가능한 총량도 작아졌다. 따라서 시간 컷오프는 도입하지 않고 보류한다.
데이터 증가로 배치가 실제 병목이 되면 그때 읽는 행 수, 점수 오차, 인기순 상위 결과가 기존과
같은지를 함께 검증한다.
