# ① **기반을 고정하고 쿼리 구조만 바꾼다.** 세 열 모두 통계 테이블 형태와 커버링
#    인덱스가 V32+V33으로 같다(B만 그 위에 V34의 컬럼·인덱스를 더한다). 묻는 것이
#    '조인 구조가 만든 문제를 각 해법이 얼마나 해결했는가'라서, 조인 구조 말고는
#    다 같아야 하기 때문이다.
#    JOIN 열과 A 열은 **EXISTS 안의 문자열 말고는 바이트 동일한 SQL**이다.
#
# ② **처음 구조를 V29 형상까지 되돌리지 않는다.** 그 형상에는 조인 구조 말고도
#    테이블 2배·PK의 version·인덱스 선두의 version·비커버링 태그 인덱스가 함께 얹혀
#    있어, 되돌리면 각 칸이 '조인을 없앤 몫'이 아니라 '그동안 쌓인 기반 개선분 전체'를
#    재게 된다. 두 질문은 다르고 지금 묻는 것은 앞쪽이다.
#
# ③ **세 열은 서로 비교하라고 만든 것이다.** 같은 컨테이너·같은 데이터·같은 그리드·
#    같은 시간대·같은 술어(그룹 안 OR, 그룹 사이 AND = 확정 스펙)에서 나왔다.
#
# ④ **원 캠페인 기록과 절대값으로 대조하지 않는다.** 2026-08-06_tag-filter-join-order와
#    2026-08-11_tag-bitmask-read-model의 수치는 각자의 창에서 유효하고 그대로 보존한다.
#    그 창들과 이 창 사이에 실측된 드리프트가 있다 — place_tag 프로브 단가가 시간이
#    지나며 싸졌고(단건 커버링 조회 0.622 → 0.266), 형상 전환이
#    idx_place_stats_town_score를 재생성해 갓 만든 인덱스의 이점이 붙는다.
#    아래 [recheck] 줄이 그 드리프트의 크기를 A 열 3칸으로 보여 준다 — 판정이 아니라
#    정보다. 어긋나도 채취를 막지 않는다.
#
# ⑤ JOIN 열의 오추정 재현 여부는 CSV의 tags_nodes·cartesian 열로 읽는다.
#      tags_nodes > 0 — t.id가 IN 리스트라 조인이 상수로 접히지 않고 트리에 남았다
#      cartesian  > 0 — 두 태그 축이 조건 없는 해시 조인으로 곱해졌다(추정이 무너지는 자리)
#    단일 태그 그룹만 있는 칸은 t.id가 PK 등호라 조인이 접혀 tags_nodes=0이 정상이다.
