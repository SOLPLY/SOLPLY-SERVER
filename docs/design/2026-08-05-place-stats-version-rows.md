| **edge proxy는 별도 결정 — 유지** | 프로세스 수와 edge는 다른 축이다. 가용성을 포기해도 edge의 보안·요청 제어(TLS 종단, 헤더, 제한)를 포기할 근거는 아니다 | §6 |

## 1. 왜 바꾸나

두 구조는 같은 것(커서가 발급 시점의 랭킹 버전에 고정되는 무한 스크롤)을 보장한다.
차이는 그 보장을 코드 계약으로 들고 있느냐, 구조로 들고 있느냐다.

| 컬럼 쌍 (현행) | 버전 행 (전환) |
|---|---|
| `ON DUPLICATE KEY UPDATE` 대입 **순서**가 계약 — prev 시프트가 새 값 대입보다 먼저 와야 하고, 뒤집으면 조용히 무의미해진다 | 순서 계약 없음 — 새 버전은 INSERT일 뿐 |
| 점수 컬럼을 동적으로 갈아 끼우는 SQL 조립 (SELECT·커서 술어·ORDER BY 세 자리) | SQL 한 벌 + `WHERE version = :v` 바인딩 |
| 인덱스 정의 2벌 (`town_score` / `town_prev_score`) | 1벌 |
| `prev IS NOT NULL` = "그 세대에 없던 장소"라는 의미론 주석 필요 | 행이 없으면 없는 것 — 의미론이 구조에 내장 |
| 같은 행을 매시 덮어씀 — 읽기 무경합이 MVCC 성질에 의존 | 증분 폐지(§5)와 합치면 **버전 행은 쓰고 나면 불변** — 읽기가 스냅샷 그 자체 |

### 1.1 저장·쓰기 비용 — 동률이 아니다

랭킹 보조 인덱스의 **논리적 엔트리 수**는 양쪽 다 약 2N이다(현행 2벌 × N행, 전환 후
1벌 × 2N행). 그러나 실제 비용이 같다는 뜻은 아니다:

- **테이블 행이 2배가 되고 모든 컬럼이 버전마다 중복**된다 (카운트·평점 포함).
- **인덱스 엔트리 폭이 커진다** — 선두에 `version`(8B)이 추가된다.
- **매시 INSERT + DELETE 패턴**은 in-place UPDATE와 달리 페이지 분할과 purge 부담을
  만들고, DELETE가 행을 지워도 테이블스페이스가 즉시 줄지 않아 **단편화**가 누적될 수 있다.

전환의 목적은 비용 절감이 아니라 계약의 구조화이므로 이 비용을 안고 간다. 다만
근거 없는 "동률" 주장 대신 **배치 소요·테이블/인덱스 크기를 관찰 항목으로 등재**한다(§9).
규모 감각: 버전당 6,320행 × 2 수준이라 절대량은 작고, 매시 지웠다 넣는 양이 일정해
단편화도 유계로 예상하나 — 예상이지 측정이 아니므로 관찰로 확인한다.

보관은 2버전 고정이다. 스크롤 세션이 배치 간격(1h)을 두 번 넘기는 경우는 드물고,
그 경우는 만료 오류로 처리한다(§4).

## 2. 스키마 (V29)

```sql
-- place_stats 재생성 (이관 없음 — §2.1)
CREATE TABLE place_stats (
    place_id       BIGINT         NOT NULL,
    version        BIGINT         NOT NULL,   -- 배치 회차의 calculatedAt을 epoch 초로 좁힌 값
    town_id        BIGINT         NOT NULL,
    popular_score  DECIMAL(18, 6) NOT NULL DEFAULT 0,
    bookmark_count INT            NOT NULL DEFAULT 0,
    review_count   INT            NOT NULL DEFAULT 0,
    avg_rating     DECIMAL(3, 2)  NULL,
    PRIMARY KEY (place_id, version),
    CONSTRAINT fk_place_stats_place
        FOREIGN KEY (place_id) REFERENCES places (id) ON DELETE CASCADE
);

CREATE INDEX idx_place_stats_version_town_score
    ON place_stats (version, town_id, popular_score DESC, place_id, bookmark_count);

-- place_stats_meta: 세대 이름표도 같은 표현으로 통일
ALTER TABLE place_stats_meta
    MODIFY current_generation BIGINT NULL,
    MODIFY prev_generation    BIGINT NULL;
```

- **`version`이 DATETIME(6)이 아니라 BIGINT(epoch 초)인 이유.** 커서는 이미 세대를
  epoch 초로 싣고 다닌다. 컬럼을 DATETIME(6)으로 두면 마이크로초가 저장되는데 커서에는
  초만 실리므로, 커서 값으로 `WHERE version = :v`를 치는 순간 정밀도 왕복이 어긋나
  0행이 된다. 쓰는 시점에 한 번 초로 좁혀 저장하면 함정 자체가 없다. meta 컬럼도 같은
  표현으로 바꿔 변환 코드를 없앤다.
- **`calculated_at` 컬럼은 없앤다.** "이 행을 정산한 회차"라는 뜻이 `version`에 그대로
  흡수된다. 증분 폐지(§5)로 NULL 센티널("아직 정산 안 됨")의 용처도 함께 사라진다.
- **인덱스 선두의 `version`은 저카디널리티(상시 2값)지만 문제가 아니다.** 항상 등호로만
  쓰여 자기 버전의 파티션만 정확히 잘라내고, 그 안에서 기존과 같은
  (town, 점수 DESC, place_id) 정렬 + `bookmark_count` 커버링이 성립한다.

### 2.1 마이그레이션 — 이관 없이 재생성

place_stats는 원본(bookmarks/place_reviews)에서 언제든 전량 복원되는 2급 데이터고,
배치가 부팅 시 최초 적재를 한다. 기존 행을 새 구조로 옮기는 코드를 쓰는 것보다
`DROP TABLE` 후 재생성이 정직하다. meta는 NULL로 리셋한다.

배포 직후 첫 배치 전까지의 공백: 부팅 적재가 수 초 내에 채우고, 그 사이 인기순은
빈 목록(오늘도 ps가 비면 같음), 배포 이전 발급 커서는 만료 오류(§4)로 첫 페이지
재조회를 유도한다 — 배포 1회성 비용으로 수용.

## 3. 배치 (한 트랜잭션, READ COMMITTED 유지)

```
① INSERT 새 버전   — 재계산 SELECT ... FROM places p ... WHERE p.active = 1
② meta 시프트      — prev ← current, current ← 새 버전
③ 옛 버전 청소     — DELETE FROM place_stats WHERE version NOT IN (current, prev)
```

- **점수 공식: 북마크 항만 감쇠, 리뷰 항은 무감쇠.**
  `score = Σ북마크[W_B × 감쇠] + W_R × Σ리뷰(평점−3)` — 리뷰 항은 리뷰수 × (평균−3)으로
  정리되어 감쇠 산술이 사라진다. 3점 중심화(저평점의 음의 기여)는 유지. 이 공식 변경은
  선행 커밋으로 이미 반영되어 있고(§0), 전환 배치는 그대로 옮긴다.
- **①의 `WHERE p.active = 1`이 조인 제거의 불변식을 만든다.** 비활성 장소는 새 버전에
  아예 들어가지 않는다. 현 버전에는 다음 배치까지 남고(≤1h 노출 — 수용), 직전 버전에
  고정된 스크롤에는 계속 보인다 — 그게 스냅샷의 올바른 의미다.
- **① 은 `ON DUPLICATE KEY UPDATE`(전 컬럼 = VALUES)를 유지한다** — 새 버전 행이라
  평시엔 순수 INSERT지만, 같은 `calculatedAt` 재실행(멱등성)이 PK 충돌 대신 동일값
  덮어쓰기가 되게 한다. 현행과 달리 prev 시프트가 없으므로 대입 순서 계약도 없다.
  기존 멱등성 논거(집계 상한 `created_at <= :calculatedAt`)는 그대로 유효하다.
- **③이 비활성 잔행 청소를 겸한다** — 옛 버전이 통째로 죽으면서 함께 사라지므로
  비활성 장소를 골라 지우는 별도 삭제가 필요 없다.
- 격리 수준·binlog 전제·places FK S락(행당, 커밋까지) 논거는 현행 `upsertAll` javadoc의
  실측 그대로 유효하다 — 문장 구조(INSERT ... SELECT)가 같기 때문. 이관 시 압축해 옮긴다.

### 3.1 인기 점수 계산 위치 — DB 집계 유지

점수에 필요한 북마크 1,040만 행은 어디서 계산하든 DB가 스캔해야 한다. **이미 스캔한
행을 애플리케이션으로 가져와 계산할 이유가 없다** — 옮기는 순간 전송·객체 변환 비용이
추가되고, 그 부담은 하필 먼저 포화되는 앱 CPU에 얹힌다. 행별 연산(감쇠×가중치)은 단순해서
DB 산술을 아껴 얻는 것도 없다. 집계·점수 계산은 DB에서 끝내고 앱은 배치 흐름만 관리한다.

재검토 조건: 행당 연산이 수 µs급으로 복잡해지거나 DB CPU가 병목으로 전환될 때. 배치가
무거워지면 계산 위치보다 감쇠 컷오프(읽는 행 수 축소)가 먼저다 — 단, 카운트는 전 기간
집계가 필요해 컷오프는 점수 축에만 적용된다.

## 4. 읽기 경로

- **인기순**: 단일 테이블. `WHERE ps.version = :version AND ps.town_id IN (...)` + 태그
  EXISTS(`ps.place_id` 기준) + 커서 술어 + `ORDER BY popular_score DESC, place_id ASC`.
  동적 점수 컬럼 분기·STRAIGHT_JOIN·`prev IS NOT NULL` 전부 소멸. 커서 플립의 원천이던
  조인 등식 전파도 구조적으로 불가능해진다.
- **다중 town 조회의 filesort는 현행과 동일하게 수용한다.** 인덱스상 결과가 town별로
  묶여 각 range 안에서만 점수순이므로, `town_id IN (...)`이 여러 개면 전역 점수순을
  인덱스가 만들 수 없다 — 정렬 대상이 커버링 엔트리(시 단위 ~1,800건)라 싸다는 것까지
  현행의 실측 논거 그대로다. 전환으로 좋아지지도 나빠지지도 않는 축이지만, 검증(§8)은
  이 사실을 실측으로 다시 확인한다.
- **커서 버전 판정**(`resolveGeneration` 후신): `cursor.generation ∈ {current, prev}`면
  그 값을 그대로 `:version`으로 바인딩한다. **어느 쪽도 아니면 만료 오류를 반환한다**
  (`BusinessException` + 커서 만료 ErrorCode 신설, 기존 커서 필터 불일치 거부와 같은 결).
  강등을 폐지하는 이유: 강등은 과거 버전의 정렬 경계(sortKey)를 현 버전 점수 축에 그대로
  갖다 대는 것이라 경계 부근의 누락·중복을 구조적으로 피할 수 없다. "묵은 커서가 오류 없이
  대충 이어진다"보다 "명시적으로 만료를 알리고 첫 페이지부터 다시"가 정직한 계약이고,
  2시간 넘게 방치된 스크롤이라는 희귀 케이스에 지불하는 비용으로 적절하다.
  클라이언트 계약: 만료 응답을 받으면 커서 없이 재요청한다.
- **카운트를 읽는 다른 경로들은 현 버전을 지목해야 한다.** LATEST의
  `LEFT JOIN place_stats`, 북마크 검색의 `findViewsByPlaceIds`가 해당된다.
  meta를 따로 읽으면 그 경로들에 SQL이 1개씩 늘므로, **스칼라 서브쿼리로 같은 문장에
  접합**한다: `... AND ps.version = (SELECT current_generation FROM place_stats_meta WHERE id = 1)`.
  PK 1행 조회라 비용은 상수고, 요청당 SQL 수가 변하지 않는다.

## 5. 증분 폐지 — 카운트는 배치 전용

증분(+1/-1)을 버전 행 위에서 유지하려면 답해야 하는 질문이 늘어난다: 허용 오차의 정의
(이벤트당 ±1인지 누적 무제한인지), +1/-1이 배치의 INSERT 전·중·후 각각에 착지했을 때의
시나리오, 음수 방지, 교착 시 재시도 주체, 새 버전이 원본 집계와 일치하는 시점. 원자성을
어차피 보장하지 못하는 경로에 이 비용을 지불할 이유가 없다 — **카운트를 배치에 맡긴다.**

- `incrementBookmark`/`decrementBookmark`/`incrementReview`/`decrementReview`와 그 이벤트
  소비자를 제거한다. **이벤트 발행측은 건드리지 않는다** — 다른 소비자가 있을 수 있고,
  발행 코드는 다른 세션이 작업 중인 파일(`BookmarkService`)에 걸쳐 있다.
- 결과: **버전 행은 배치가 쓰고 나면 불변**이다. 쓰기 경로가 배치 하나로 줄어
  드리프트·재대사 개념 자체가 소멸한다.
- 수용하는 것: 표시 북마크 수의 신선도가 배치 간격(≤1h)으로 낮아진다. 본인이 방금 누른
  북마크는 `isBookmarked`(체크 표시)로는 즉시 보이지만 수에는 다음 배치부터 반영된다.
  카운트는 조회수류 표시값이라는 판단, 그리고 정합성 질문 목록을 통째로 지우는 대가로 수용.

## 6. 토폴로지 — 프로세스 수와 edge는 별도 결정

**앱 프로세스는 1개로 줄이되, edge proxy는 유지한다.** 부하 분산(가용성)과 edge의
역할(TLS 종단, 보안 헤더, 요청 제어, 앱 비노출)은 다른 축이고, 전자를 포기한 것이
후자를 포기할 근거가 되지 않는다.

- **운영**: edge proxy 유지. upstream만 단일 앱으로.
- **벤치** (`docker-compose.bench.yml`): `bench-app-2` 제거, nginx는 **LB가 아니라
  운영 경로 재현용 edge**로 유지 — 단일 upstream. 이때 `max_fails` 기반 서킷브레이커를
  무력화한다(`max_fails=0`) — 지난 캠페인에서 포화 모양을 왜곡한(no live upstreams 502)
  파라미터이고, upstream이 하나면 차단이 곧 전면 장애라 의미도 없다.
  진입점은 그대로 `localhost:8082`(edge) — **시나리오 파일의 target이 그대로 유효하다.**
  앱 스펙은 2 vCPU/2G 유지(스펙까지 바꾸면 비교축이 둘이 된다). 헤더 주석의 배정 총합 재계산.
- `load-test/README.md`·`docs/perf/load-test-guide.md`: 토폴로지 서술 갱신(2대+LB → 1대+edge).
  **기존 캠페인 디렉터리는 그 시점 측정의 기록이므로 고치지 않는다.**
- 측정 유의: 이후 부하 수치는 단일 프로세스 기준선이라 기존 캠페인(2대+LB)과 절대값 비교 금지.

## 7. 블로그 (`docs/superpowers/blog/2026-08-03-popular-sort-aggregation.md`)

배경을 단일 프로세스 + edge 구조로 고쳐 쓰고, 다중 인스턴스 전제의 서술을 제거한다.
처방 절은 "STRAIGHT_JOIN 봉합 → 버전 행 전환으로 조인·동적 컬럼·인덱스 2벌이 함께 소멸"로
서사를 잇는다. 코드 구현과 별도로 메인 세션에서 직접 수정한다.

## 9. 이 설계로 말할 수 없는 것 / 관찰 항목

- 성능 개선 여부 — 이 전환의 목적은 구조 단순화이지 성능이 아니다. 부하 수치는
  단일 프로세스 재기준선 이후에만 말할 수 있다.
- **관찰 등재**: 배치 소요(INSERT+DELETE 전환 영향), place_stats 테이블·인덱스 크기 추이,
  매시 DELETE에 따른 단편화(`information_schema` 기준 data_free) — §1.1의 예상을 실측으로 확인.
- 표시 북마크 수의 신선도 저하(≤1h)에 대한 사용자 체감 — 관찰 대상이나 측정 수단은 미정.
