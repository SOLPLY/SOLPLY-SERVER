> 사전 등록·원자료: [`load-test/campaigns/2026-08-09_projection-vs-snapshot/`](../../load-test/campaigns/2026-08-09_projection-vs-snapshot/)
> (README = 측정 전 등록, `results/execution-log.md` = 시간순 실행 기록)
> 형상 `f91081c` · 브랜치 `perf/#383-place-skeleton-cache` · 페이지 크기 10 (운영 기본값)

## 1. 왜 쟀나

골격 스냅샷 캐시의 채택 문서(블로그 §3)의 대안 표에는 CPU 증설·페이지 캐시·장소 캐시만
있고, **표준 첫 수단인 DTO 직접 프로젝션이 없었다.** "캐시가 프로젝션보다 얼마나 더
아끼는가"가 수치 없이 비어 있었고, 이 캠페인이 그 빈칸을 뒤늦게 메운다.

`@Transactional(readOnly = true)`는 측정 대상이 아니다 — 조회 서비스에 캐시 작업보다
52커밋 앞서(`8a4901c`) 붙어 있었으므로, 기존의 모든 베이스라인이 readOnly가 켜진 값이다.
readOnly가 없애는 것(변경 감지용 스냅샷)은 이미 없앤 상태였고, 남아 있던 비용은
readOnly가 건드리지 못하는 컬럼 추출·영속성 컨텍스트 등록·프록시·컬렉션 래퍼 쪽이었다.

## 2. 방법 — 간극이 곧 몫이 되도록 설계했다

같은 빌드에서 `solply.place-list.skeleton-source` 하나로 세 방식를 전환한다(`bedbcea`).

| 방식 | 골격 5필드의 출처 | 요청당 골격 쿼리 |
|---|---|---:|
| `entity` | 캐시 도입 이전 경로 — 태그 페치조인 엔티티 + 이미지 지연로딩 | 2 |
| `projection` | 스냅샷 로더와 **같은 SQL·같은 조립식**을 페이지 id로 제한해 요청마다 실행 | 2 |
| `snapshot` | 채택안 — 배치 회차마다 미리 지은 `volatile Map` | 0 |

`projection`이 로더의 SQL 템플릿과 조립 코드를 공유하므로 값 동치가 구현에서 보장되고,
`entity`와 쿼리 **횟수**(2회)가 같으므로:

```
entity − projection  =  엔티티 하이드레이션 몫   (쿼리 수 동일, 조립만 다름)
projection − snapshot =  쿼리 왕복·커넥션 점유 몫  (조립 동일, 쿼리 유무만 다름)
```

라운드 설계는 직전 캠페인의 미결("세 라운드는 독립 반복이 아니다 — 커넥션 대기 단조 감소")을
반영했다: 매 라운드 `force-recreate`(fresh JVM) → 사다리 워밍업 150초(폐기) → 측정 60초,
순서는 **E→P→S를 한 사이클로 3사이클** — 시간에 따라 데워지는 것(버퍼풀·페이지 캐시)이
세 방식에 균등하게 분배된다. 판정은 사전 등록 §5.1의 1급 지표(요청당 앱 CPU·statements·digest)로
하고, 효과 크기가 2배 미만이므로 응답시간으로는 주장하지 않는다.

## 3. 정합성 게이트 — 통과

- 같은 토큰·같은 5요청의 응답 body와 `nextCursor`가 세 방식에서 완전히 같다 (5/5 × 두 쌍)
- 방식 전환을 설정값이 아니라 **실행된 SQL로** 검증했다 — digest를 비우고 요청 1건:
  `entity`는 페치조인+이미지 문장 각 1.000회/요청, `projection`은 로더 계열 IN 문장 각
  1.000회/요청, `snapshot`은 둘 다 0회 (문장 판별은 테이블명이 아니라 alias 기준 —
  두 경로가 SQL 템플릿을 공유해서 테이블 기준으로는 오검출한다)
- `snapshot` 방식의 요청 1건이 내는 SELECT는 towns·place_stats·bookmarks **3개뿐**

## 5. 해석

### 5.1 사전 등록의 갈래로는 (b) — 다만 앱 CPU 단독으로는 두 몫 다 확정 불가

요청당 앱 CPU에서 **snapshot ≈ projection**(간극 2.2%)이다. 그런데 e−p 간극(20.2%)도
방식 내 산포(21.6%) 안이라, 등록 §5.1을 문면대로 적용하면 앱 CPU로는 **두 몫 모두
"구분 불가"**다. 사이클별 부호도 안정적이지 않다 — e−p가 +0.485 / +0.739 / −0.043,
p−s가 +0.042 / −0.159 / +0.469.

산포가 직전 캠페인(±4.5%)의 3~5배로 벌어진 출처는 무작위가 아니라 **호스트 상시 부하**다
(측정 중 실측: WindowServer·Gemini·Orca 등으로 load average 2.5~5, 구간에 따라 13~19).
스로틀과 요청당 CPU가 같이 움직였고(entity: 스로틀 0.6%인 라운드 2.220 → 9.7%인 라운드
2.588), 부호가 뒤집힌 사이클은 정확히 projection이 유일하게 스로틀 8.3%를 맞은 회차다.
**이 상관을 근거로 라운드를 골라내지는 않았다** — 9라운드 전부 §6 유효성을 통과했다.

### 5.2 원인 지표가 두 몫을 가른다

앱 CPU가 흔들린 것과 달리 **요청당 힙 할당(산포 2.0%)과 statements(0.2%)는 결정적**이다.

```
하이드레이션 제거 몫 (e−p):  힙 −243.7 KB/요청 (−24.2%)     ← 간극이 산포의 12배
쿼리 제거 몫       (p−s):  statements −2.00/요청
                           DB CPU −0.282 ms/요청 (−17.1%, 산포 밖)
                           커넥션 점유 −0.48 ms (−20.3%, 산포 밖)
                           힙 −65.5 KB/요청 (−8.6%)
```

절감의 구조가 그대로 드러난다: **조립을 없앤 몫이 앱 쪽 자원(힙, 그리고 점추정으로 앱
CPU의 대부분)을 돌려주고, 쿼리를 없앤 몫은 앱이 아니라 DB CPU와 커넥션 점유로 나타난다.**

### 5.3 그래서, 프로젝션을 먼저 해봤어야 했나

**앱 CPU 관점에서는 그렇다에 가깝다.** 점추정 기준 e−s 0.527ms 중 e−p가 0.485ms —
절감의 대부분은 프로젝션만으로 얻는다. 스냅샷이 프로젝션 위에 더 얹는 것은 앱 CPU가
아니라 **쿼리 2개를 없애는 일**이고, 그 값은 DB CPU −17%·커넥션 점유 −20%·statements −2로
나타난다. 측정 밖의 이점도 하나 있다 — 스냅샷은 골격 만드는 일을 요청에서 떼어내
배치 주기당 1회로 줄인다. 프로젝션은 싸졌을 뿐, 그 일을 여전히 요청마다 한다.

420 arrivals/s(≈672 req/s) 관찰에서 그 여유 차이가 보였다: entity 스로틀 **58.7%**
(p95 83.9ms) vs projection **3.5%**(p95 7.0ms), 실패는 둘 다 0. **projection은 붕괴하지
않았다.** 단 entity도 붕괴하지 않았다 — 직전 캠페인의 "OFF는 420부터 붕괴(3/3)"가
재현되지 않았는데, 바뀐 축은 워밍업 진입 경로(직전은 480행 사다리의 중간 계단, 이번은
420이 종점)이고 이 캠페인은 그 차이를 규명하지 않았다. 그래서 이번 관찰로 말하는 것은
"projection이 entity보다 뚜렷하게 여유롭다" 하나이고, 직전 결과의 반증으로 쓰지 않는다.

### 5.4 부산물 — 차가운 JVM의 entity 경로는 4.3배 비싸다

fresh-JVM 라운드 설계가 드러낸 값: 기동 직후 entity 방식의 요청당 앱 CPU는 **10.4ms**
(데워진 값 2.4ms의 4.3배)로, 고정 120 arrivals의 워밍업 부하조차 그 자체로 2코어를 소진해
라운드를 무너뜨렸다(폐기 x3·x4). 배포 직후 콜드 구간의 수용량이 정상 상태의 1/4 이하일 수
있다는 뜻이다 — 이번 범위 밖이지만, 무중단 배포나 스케일아웃 설계 때 다시 볼 값이다.

420 관찰을 E·P로 축소)은 사유와 함께 `execution-log.md`에 기록했다.

## 7. 이 테스트로 말할 수 없는 것

- **앱 CPU 간극의 확정 수치.** 호스트 상시 부하로 산포가 11~22%라 두 몫의 ms 값은
  점추정이다. 확정하려면 호스트를 통제하고 다시 재야 하지만, 힙·statements·DB CPU가
  이미 같은 방향의 결론을 주므로 그 재측정의 기대 이득은 작다
- **entity의 420 붕괴 문턱.** 직전 캠페인과 결과가 다른데 원인(워밍업 진입 경로)을
  규명하지 않았다
- **직전 캠페인과의 절대값 비교.** 페이지 크기(10 vs 20)·라운드 설계(fresh JVM vs 연속)가
  다르다. 분해는 이 캠페인 내부의 세 방식 간극으로만 말한다
- **프로젝션의 장시간 특성.** 라운드가 분 단위다
- 부하생성기가 측정 대상과 같은 호스트에서 돈다 (기존 인지된 한계)

## 8. 반영

- 블로그(2026-08-08) §3에 readOnly·프로젝션을 추가하고 §5에 이 측정을 요약했다
- `load-test/README.md` 캠페인 색인에 한 줄 추가
- 스냅샷 유지 판단은 바뀌지 않는다 — 근거의 무게중심이 "앱 CPU"에서
  "쿼리 제거(DB·커넥션) + 요청과 무관한 갱신 주기"로 옮겨졌을 뿐이다
