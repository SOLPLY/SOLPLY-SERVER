# 장소 목록을 메모리에 보관할 때의 갱신·Heap·GC 설계

작성일: 2026-09-09 · 설계 기준: 2026-09-10

솔플리의 장소 목록은 동네와 태그로 후보를 좁히고, 선택한 순서로 한 페이지를 반환한다.
여러 사용자가 공유하는 정렬 순서를 미리 만들어 메모리에 두면 요청은 필요한 위치부터
목록을 찾을 수 있다. 대신 서버는 전체 조회 데이터를 계속 보관하고, 변경될 때 새 상태를
만드는 비용을 감당해야 한다.

이 구조에서 확인할 질문은 세 가지다. **어드민 변경을 조회 중인 요청과 충돌 없이 어떻게
반영할 것인가. 전체 데이터를 만료 시간 없이 힙에 두어도 되는가. 갱신과 GC가 사용자
응답을 늦추기 시작하면 어느 작업을 어디로 옮길 것인가.**

## 1. 어떤 요구사항을 고려했나

목록을 넘기는 동안 정렬·필터 기준이 바뀌면 페이지 경계가 흔들릴 수 있다. 커서에 Snapshot
version을 넣고, 다음 페이지도 같은 version일 때만 이어간다. current가 바뀌면 커서를
만료시키고 첫 페이지 재요청을 요구한다. 어드민 변경을 빠르게 반영하는 서비스 정책에 따라
과거 커서를 위해 별도의 Snapshot을 보존하지 않는다.

반영 시점은 값의 역할에 따라 나눈다.

| 데이터 | 반영 시점과 방식 |
|---|---|
| 장소 생성·삭제·공개 상태, 동네·태그 집합·좌표 | DB 커밋 후 해당 장소를 재조회해 Snapshot 부분 갱신 |
| 기존 장소의 인기 점수·평점·리뷰 수·북마크 수 등 정적 정렬 키 | 주기적 전체 재빌드에서 일괄 반영 |
| 장소 이름·썸네일·대표 태그 ID | Snapshot 밖 `PlaceViewHolder`에 반영 |
| 태그 이름·활성 상태 | Snapshot 밖 `TagViewHolder`를 갱신 |

장소에 부착된 태그 집합은 필터 기준이고, 태그 이름·활성 상태는 대표 태그의 표시 기준이다.
두 변경은 서로 다른 데이터를 갱신한다. 표시값만 바뀌면 Snapshot version은 유지한다.

정합성의 기준은 DB다. 커밋 이후 메모리에 반영되기까지 지연을 허용하되, 롤백한 변경을
공개하지 않는다. 반영에 실패하면 current로 조회를 유지하고 다음 성공한 전체 재빌드에서
조회 모델을 다시 맞춘다.

## 2. 어드민 변경은 어떻게 반영하나

어드민이 바꾼 내용은 빠르게 보여야 하지만, 아직 커밋되지 않은 값이나 반쯤 수정된 목록이
노출돼서는 안 된다. 그래서 변경을 저장하는 단계와 조회용 상태를 공개하는 단계를 나눈다.

```text
① 원본 변경을 DB에 저장
   장소·태그 관계·이미지 정보와 조회 원천 데이터를 같은 트랜잭션에 반영
   → 이번 트랜잭션에서 변경한 장소 ID를 중복 없이 모음

② 커밋이 성공한 뒤 갱신 시작
   롤백한 변경은 반영하지 않음
   → 갱신 차례를 기다린 뒤, 해당 ID의 최신 DB 상태를 다시 읽음

③ 현재 조회 모델과 비교해 필요한 부분만 준비
   표시값만 변경       → 이름·썸네일 등을 별도 표시 저장소에 반영
   태그·좌표 변경      → 해당 동네 배열을 복사하고 같은 위치의 장소 참조를 교체
   생성·삭제·동네 이동 → 영향받은 동네의 구성과 정렬 배열을 다시 준비

④ 완성된 상태 공개
   조회 기준이 바뀌었다면 새 version 발급
   → 필요한 표시값 준비 → current Snapshot 참조를 한 번에 교체
   → 이후 요청부터 새 상태 사용
```

### 변경 내용을 전달하기보다 최신 상태를 다시 읽는다

알리는 것은 “어느 장소가 변경됐다”는 사실이다. 이름 변경·태그 변경·동네 이동을 각각의
이벤트로 모델링하고, 이벤트에 담긴 값을 순서대로 재생하지 않는다. 변경 ID로 DB를 다시
읽으면 현재 존재하는지, 어느 동네에 속하는지, 어떤 태그가 붙었는지를 한곳에서 판단할 수
있다. 삭제한 장소도 ID를 넘기며, 최신 조회 결과에 행이 없으면 목록에서 제거한다.

같은 트랜잭션에서 같은 장소를 여러 번 수정해도 한 번의 갱신에 모아 처리한다. 현재 구현은
커밋 이후 콜백에서 같은 요청 스레드가 이 작업을 수행한다. 따라서 갱신 대기는 어드민
응답 시간에 포함된다. 여러 API 서버로 변경을 전파하는 경로는 별도의 분산 설계에 해당한다.

### 이미 조회 중인 목록을 직접 고치지 않는다

요청이 보고 있는 배열에 장소를 끼워 넣거나 빼면 탐색 도중 순서와 길이가 달라질 수 있다.
갱신은 새 배열을 준비해서 공개하고, 기존 배열은 그대로 둔다. 영향받지 않은 동네의 배열과
바뀌지 않은 장소 객체는 새 Snapshot에서도 공유한다.

태그·좌표만 달라진 기존 장소는 정적 정렬 키를 유지하므로 같은 위치의 참조만 바꿀 수 있다.
생성·삭제·이동은 원소 구성이 바뀌므로 해당 동네의 배열을 다시 만든다. 점수·리뷰 수처럼
계속 변하는 정렬 키는 전체 재빌드에서 일괄 반영한다. 어드민이 수정한 장소만 새 통계로
정렬되는 일을 피하기 위해서다. 신규 장소는 보존할 기존 정렬 키가 없어 DB 값을 사용한다.

이름과 썸네일은 순서·필터·후보 집합을 바꾸지 않으므로 Snapshot 밖에서 갱신한다.
일반 장소 수정에서는 최신 값 비교까지 수행하지만, 표시값만 바뀌었다면 배열 복사와
version 발급 없이 끝난다. 이미지 이동 후 최종 파일 키 반영, 태그 이름 변경도 표시값만
갱신한다.

### 늦게 끝난 재빌드가 최신 수정을 덮지 않게 한다

참조를 한 번에 교체하는 것만으로 갱신 간 충돌까지 해결되지는 않는다. 재빌드가 읽어 둔
값으로 모델을 만드는 사이 부분 갱신을 공개하면, 나중에 끝난 재빌드가 그 수정을 덮을 수 있다.
따라서 전체 재빌드와 부분 갱신은 **DB 조회부터 공개까지 한 번에 하나씩** 실행한다.
표시값 갱신도 같은 순서 제어에 포함한다.

```text
재빌드가 먼저 실행 중
  → 어드민 변경은 DB에 커밋됨
  → 부분 갱신은 차례를 기다림
  → 재빌드 공개 완료
  → 부분 갱신이 최신 DB 상태를 읽어 반영

사용자 조회
  → 위 갱신 차례를 기다리지 않음
  → 자신이 확보한 완성된 Snapshot으로 계속 처리
```

부분 갱신은 최신 상태를 읽은 뒤 준비하므로 오래된 변경 내용을 뒤늦게 적용하지 않는다.
갱신에 실패하면 예외를 기록하고 현재 Snapshot으로 조회를 유지한다. 다음 성공한 전체
재빌드는 DB 기준으로 조회 모델을 다시 맞춘다. 주기적 재빌드가 정렬 키 반영뿐 아니라
누락된 변경의 복구, 즉 reconciliation도 담당하는 이유다.

### 교체 중인 요청과 다음 페이지를 구분한다

진행 중인 요청은 시작할 때 확보한 Snapshot을 끝까지 사용한다. 이후 들어오는 요청은 새
current를 사용하며, 커서 version이 current와 다르면 첫 페이지부터 다시 요청하도록 한다.
표시값은 별도로 최신 값을 읽기 때문에 페이지 전체의 표시 시점까지 고정되지는 않는다.

```text
요청 A가 v10 확보 → v11 공개 → 요청 A는 v10으로 완료
새 요청 B 진입   → v11 확보 → v11으로 조회
v10의 다음 페이지 요청    → current와 version 불일치 → 커서 만료
```

## 3. 전체 데이터를 기한 없이 캐싱하면 Heap이나 GC 문제가 없나

**만료 시간이 없다는 것과 데이터가 끝없이 누적된다는 것은 다르다.** 이 캐시는 요청마다
결과를 추가하는 저장소가 아니라, 현재 장소 집합을 표현하는 조회 모델이다. 보관량은 요청
횟수보다 장소 수·저장 필드·정렬 배열 수에 의해 정해진다. current 한 벌을 보관하고,
교체한 Snapshot을 과거 커서용으로 따로 붙잡지 않는다.

그렇다고 current 한 벌이 힙에 들어간다는 사실만으로 충분하지는 않다. 요청 처리에 필요한
임시 객체와 다음 모델을 만드는 공간까지 같은 힙에서 사용하기 때문이다.

```text
평상시
  current Snapshot + 현재 표시값 + 프레임워크 상주 객체
  + 요청마다 생겼다가 사라지는 후보·결과·응답 객체

전체 재빌드 중
  위 객체들
  + 생성 중인 새 Snapshot·표시값
  + DB 조회 결과·그룹화 리스트·정렬용 임시 공간

참조 교체 후
  새 current로 조회
  → 기존 요청이 끝나면 교체된 모델의 참조도 해제
  → 더 이상 참조되지 않는 객체를 GC가 회수
```

현재 로더는 DB 결과를 전량 받아 모델을 만든다. 따라서 재빌드의 할당량과 순간 점유는
완성된 Snapshot 크기보다 크다. 부분 갱신은 영향 동네의 배열만 복사하고 나머지를 공유하지만,
이 역시 임시 할당이 없는 것은 아니다.

### 상주량과 교체 과정의 비용을 따로 본다

오래 살아남은 객체는 Old 영역에 있을 수 있다. 여전히 참조되는 데이터는 필요한 상태이므로
GC가 제거할 수 없고, 그만큼 새 할당과 GC 작업에 쓸 공간이 줄어든다. 상주 데이터가 크면
살아 있는 객체를 추적하는 비용도 고려해야 한다. 다만 Old에 객체가 있다는 사실만으로
모든 Young GC가 그 전체를 순회하거나 긴 정지를 만든다고 단정할 수는 없다.

교체 시에는 새 객체를 빠르게 할당하는 동안 GC가 발생할 수 있다. 기존 모델의 참조가 끊겨도
메모리는 즉시 회수되지 않는다. G1에서는 Old 영역 회수가 마킹과 이후 회수 단계에 걸쳐
진행될 수 있고, 동시 GC 작업도 애플리케이션과 CPU를 나눠 쓴다.
[Java 21 G1 동작](https://docs.oracle.com/en/java/javase/21/gctuning/garbage-first-g1-garbage-collector1.html)

따라서 **안정 상태의 상주량이 예산에 맞는지**, **재빌드와 회수가 겹칠 여유가 있는지**를
각각 확인해야 한다. 느린 요청이 교체된 Snapshot을 계속 참조하면 회수가 늦어지고, 여러
교체에 걸쳐 요청이 남으면 순간적으로 살아 있는 버전도 두 개를 넘을 수 있다.

TTL을 붙여도 다음 조회를 위해 전체 모델이 필요하다면 생성과 할당은 다시 발생한다.
이 구조의 적합성은 만료 시간 자체보다 실제 데이터 규모에서 상주량·갱신 비용·회수 속도가
사용자 요청과 함께 감당 가능한지로 판단한다.

## 4. 재빌드와 GC가 사용자 latency에 영향을 주기 시작하면

먼저 응답 지연이 늘어난 시점에 무엇이 실행됐는지 확인한다. 재빌드 중 지연이 늘었다고 해서
원인이 모두 GC인 것은 아니다. DB 결과 변환·정렬이 CPU를 사용해 요청이 기다릴 수도 있고,
GC pause가 요청 스레드를 멈추거나 동시 GC가 CPU 경쟁을 더할 수도 있다.

```text
사용자 지연 증가 관측
  → 재빌드 시작·종료, CPU 사용, GC 이벤트를 같은 시간축에서 확인
  → 비용이 집중된 곳을 구분

  DB 결과·중간 객체를 만드는 구간
    → 불필요한 전량 물질화·중복 복사를 줄일 여지가 있는지 확인

  생성·정렬·GC가 요청과 지속적으로 자원을 경쟁하는 구간
    → 모델 생성 작업을 별도 빌더 프로세스로 분리

  안정 상태에서도 전체 모델이 힙 예산을 압박
    → 저장 표현·캐시 범위를 재검토하고, 필요하면 분할 또는 외부 조회 저장소 검토
```

### 빌더를 분리하는 목적은 생성 작업의 자원을 격리하는 것이다

같은 JVM의 다른 스레드에서 재빌드하더라도 힙과 GC는 공유한다. 생성 작업이 사용자 요청에
영향을 준다면 어드민 측의 별도 프로세스에서 조회 모델을 만들고, API는 완성된 모델을
받아 조회하도록 구성한다. CPU도 격리하려면 프로세스뿐 아니라 실행 자원 배치와 한도까지
함께 설계해야 한다.

```text
빌더
  DB 읽기 → 장소 값 생성 → 동네별 정렬 → 배포용 직렬화
  → 생성 중간 객체와 정렬 작업은 빌더의 힙·CPU에서 처리

공유 배포 저장소
  완성된 최신 Snapshot과 표시값 보관
  → 각 API가 최신 상태를 가져갈 수 있게 제공

API
  다운로드 → 검증·복원 → current 참조 교체 → 로컬 조회
  → 최종 모델과 수신·복원 중 할당은 API의 힙에 남음
```

**빌더 분리는 API의 GC를 없애는 설계가 아니다.** DB 조회 결과와 정렬용 임시 객체는
빌더에서 만들지만, API가 사용할 최종 장소 객체·배열은 API에도 필요하다. 수신 버퍼와
역직렬화, 교체된 모델의 회수 비용도 남는다. 따라서 분리 후에는 모델 생성 시간이 아니라
API의 적재 구간이 사용자 latency에 미치는 영향을 확인해야 한다.

적재의 객체 생성·참조 추적이 실제 병목이라면 정렬 순서를 포함한 배포 형식, 더 간결한
필드 표현이나 원시 배열을 검토할 수 있다. 이 선택도 복원 비용과 조회 코드 복잡도를 함께
평가한다. 최종 모델 자체가 가용 힙을 넘어서는 문제는 빌더 위치만 바꿔 해결할 수 없다.

이 책임 분리와 최신 상태의 전파·복구를 구체화한 것이
[Current Snapshot 분산 배포 설계](2026-09-10-distributed-inmemory-snapshot-architecture.md)다.

## 5. 무엇을 측정해서 이 판단을 내리나

측정 목표는 앱 **2 vCPU·메모리 2 GiB·최대 힙 1,280 MB**, 장소 **63,200곳**이다.
동일한 사용자 흐름에서 안정 서빙과 전체 재빌드가 겹치는 구간을 비교한다. 평상시·피크를
나누고, 재빌드 종료 후 발생하는 GC까지 관측한다.

| 판단할 것 | 확인할 결과 | 원인을 좁힐 관측 |
|---|---|---|
| Throughput | 목표 요청률을 계속 처리하는가 | CPU 사용·대기·throttling, GC 시간 |
| Latency | 재빌드 주변 응답이 늦어지는가 | p50·p95·p99, 개별 지연과 GC pause의 시간 관계 |
| Footprint | 상주 상태와 교체 구간이 메모리 예산에 맞는가 | GC 후 점유, Old 변화, 관측된 힙·프로세스 메모리 정점 |

할당량·할당률과 GC 종류·횟수·정지 시간은 위 결과를 설명하는 데 사용한다. 반복 재빌드 후
메모리 회수가 따라오는지도 확인한다. 무부하 재빌드는 자원 사용량을 보여 주지만 사용자
지연이 없다는 근거가 되지는 않는다. 강제 GC나 히스토그램은 별도 진단으로 수행하고,
낮은 빈도의 샘플링으로 관측한 최대값을 실제 순간 최대 힙으로 단정하지 않는다.

어드민 갱신은 변경 반영 시간과 재빌드 대기, 최종 상태를 별도로 확인한다. 커서 만료도
서비스 정책상 예상한 동작인지 확인하고, 첫 페이지 재요청 비용까지 사용자 영향에 포함한다.

## 6. 조회 자료구조와 비용의 핵심

조회 모델은 `정렬 종류 → 동네 ID → 정렬된 장소 참조 배열`이다. 장소 객체 하나를 다섯
정렬 축이 공유하며, 표시값은 ID로 찾는 별도 맵에 둔다.

| 자료구조 | 선택 근거 |
|---|---|
| `EnumMap` | 고정된 정렬 종류를 내부 배열로 연결해 기본 접근 `O(1)` |
| 동네별 `HashMap` | 연속적이지 않은 동네 ID로 배열 탐색, 적절한 해시 분산에서 평균 `O(1)` |
| 장소 참조 배열 | 인덱스 접근·이진 탐색·이어지는 순차 스캔에 적합 |
| 태그 비트마스크 | 고정 폭 정수의 비트 연산으로 후보당 `O(1)` 판정 |
| `PriorityQueue` | 배열 기반 힙으로 다음 후보 유지, 삽입·제거 `O(log h)`, 머리 확인 `O(1)` |
| 표시값 맵 | 장소는 동시 조회·항목 교체가 가능한 `ConcurrentHashMap`, 태그는 불변 맵을 통째로 교체 |

`N`은 전체 장소 수, `A`는 정렬 축 수(5), `T`는 동네 수, `n_t`는 동네별 장소 수다.
조회에서 `k`는 대상 동네 수, `S`는 검사한 원소 수, `L`은 페이지 크기+1이다.

| 흐름 | 주요 비용 |
|---|---|
| 전체 생성 | 읽은 행을 그룹화 `O(N)` → 축별 배열 생성·정렬 `O(A × Σ[n_t log(n_t+1)])` |
| 상주 저장 | 장소 객체 `O(N)` + 정렬 참조 `O(AN)` + 동네 맵 `O(AT)` |
| 한 동네 조회 | 커서 이진 탐색 → 필터 스캔, `O(log(n_t+1) + S)` |
| 여러 동네 조회 | 동네별 이진 탐색 → 크기 k의 힙으로 병합, `O(Σ log(n_t+1) + (k+S) log(k+1))` |
| 거리순 조회 | 대상 `N_q`개 스캔 → 후보 `C`개 거리 계산·상위 L개 유지 → 결과 정렬, `O(N_q + C log(L+1) + L log(L+1))` |

필터 통과율이 낮으면 검사량 `S`가 커진다. 거리순은 후보 리스트와 ID 맵을 만들므로 추가
공간도 `O(C+L)`이다. 부분 갱신은 기존 장소를 찾는 스캔이 최악 `O(N)`이고, 실제 변경 시
동네 맵을 얕게 복사한 뒤 영향 동네의 배열만 복사하거나 정렬한다. 단건 수정 전체가 상수
시간에 끝난다는 의미는 아니다. 동네 해석·태그 검증·사용자 북마크 등 DB 경로는 별도로 남는다.
