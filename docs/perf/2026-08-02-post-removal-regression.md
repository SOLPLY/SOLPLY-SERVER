### 4.3 p50 미달의 귀속 — 코드로는 0.203ms밖에 설명되지 않는다

미달 폭은 +1.9ms(6.0→7.9)인데 **코드가 추가한 DB 작업은 0.203ms**다. 한 자릿수가 모자란다.
1차 세트에서 세웠던 "워밍 부족" 가설은 **판정 세트에서 기각됐다** — 디스크 읽기 0~1의 완전
워밍 상태에서 세 라운드 모두 7.9ms였다.

남은 후보와 판단:

1. **세션(호스트) 간 차이.** 08-01의 6.0ms는 다른 날·다른 세션에서 측정됐고 그때의 호스트
   부하 기록이 없다. 이번 판정 세트는 load 3.84에 macOS 유지관리 데몬이 돌던 상태다.
   **세트 간 p50 비교가 이 측정의 가장 약한 고리**다 (근거는 §4.4).
2. **DB CPU가 실제로 올랐다** (평균 25.7% → 39.5%). 요청당 statements는 +5.8%인데 DB CPU는
   +54%다. statements 수로 설명되지 않는 증가이고, 원인은 §6.4의 풀스캔이 유력하나
   그 스캔은 08-01에도 있었다(`select_scan` 0.51 vs 0.500 — 동일).

결론: **"회귀가 없다"고 선언할 수 없다.** p50이 기준을 넘고 그것이 재현된다. 동시에
**"리팩터링이 회귀를 만들었다"고 단정할 근거도 없다** — 코드가 추가한 비용은 0.203ms로 규명됐고
구조 지표(statements 18.18, `select_scan` 0.500, tmp_disk 0)는 08-01과 사실상 같다.
말할 수 있는 것은 **구조는 그대로이고 p50은 이 환경에서 7.9ms로 재현된다**는 사실이다.

### 4.4 유효성 규칙의 한계 — 새로 발견한 것

**"앱 CPU 200% 초과 샘플이 0개"인 라운드도 호스트 부하에 따라 p50이 달라진다.**

|---|---:|---:|---:|---:|---:|
| 2차 (`regression2-r1·r3`) | ~6.05 | **6.0 / 6.0 ms** | 6 / 0 | **0.007** | 24.9 / 25.9% |
| 3차 (`regression3-r1·r2`) | 6.6~7.6 | **8.9 / 8.9 ms** | 5 / 8 | 0.50 | 42.0 / 44.0% |
| 4차 (판정, `regression4`) | 3.84 | **7.9 ×3** | 1/0/1 | 0.500 | 39.5% |

현행 유효성 규칙은 **순간 급등(스톨)은 걸러내지만 지속적인 호스트 경합은 걸러내지 못한다.**

그래서 **세트 간 p50 절대값 비교는 신뢰 구간이 넓다**고 봐야 한다. 반대로 **구조 지표는
네 세트 전부에서 완전히 안정적**이었다 — `statements` **18.18**이 12라운드 내내 동일했다.
지표 계약(A.3)이 statements를 1급으로, 응답시간을 그보다 약하게 취급한 이유가 이번에 다시 확인됐다.

> **2차 세트의 `select_scan` 0.007 이상치.** 2차만 스캔이 사실상 0이었고(150건/라운드 vs 다른
> 세트 10,300건) p50도 가장 낮았다. 시점상 배치가 방금 돈 뒤라 `place_stats` 통계가 갱신된
> 상태였다는 점이 유력한 설명이지만 **인과를 확인하지 못했다.** 08-01 B는 `select_scan` 0.51

### 7.1 쓰기 유효성 — 이번엔 실제로 걸렸다

세 라운드 모두 `Innodb_rows_updated`가 크게 증가했다(1차는 **0**이었다). 그리고
`rows_inserted`가 **POST 200 건수와 정확히 일치**하고(180: 2,293 = 2,293) `rows_deleted`가
**DELETE 200 건수와 일치**한다(180: 2,521 = 2,521). 즉 **`place_stats` 증분 UPDATE와
인기순 SELECT가 같은 테이블에서 실제로 만났다** — 측정 3의 전제가 재현됐다.

**정정 (2026-08-03, §7.4):** 위 문단의 "증분"은 절반만 맞다. 등록 쪽 증분(+1)은 벤치 잔재 컬럼
때문에 **전 건 실패**했고, `place_stats`에 실제로 걸린 쓰기는 **감분 UPDATE(−1)**다
(`rows_updated` +2,415 ≈ DELETE 200 건수 2,521). 같은 행에 대한 원자 UPDATE라는 경합 성질은
증분과 동일하므로 "쓰기와 정렬 읽기가 같은 테이블에서 만난다"는 전제는 재현됐다고 보되,
쓰기량은 의도(등록+해제)의 약 절반이었다.

CPU에 여유가 남아야 한다. 실측은 반대다 — **양쪽 CPU가 천장을 쳤으므로 구조 한계**다.

### 7.4 500의 원인 — 최초 보고와 정정 (2026-08-03)

**최초 보고:** 북마크 POST의 약 9%가 HTTP 500이고, 앱 로그의 `Column 'bookmark_count' in field
list is ambiguous`(증분 UPSERT) → `UnexpectedRollbackException`을 근거로 "`places`에도 같은
컬럼이 있어 생기는 기능 버그"로 귀속했다.

**정정 — 귀속이 틀렸다.** "운영 스키마의 places에는 bookmark_count가 없다"는 지적을 계기로
재검증한 결과:

1. **`places.bookmark_count`는 마이그레이션에 없다.** 벤치 DB에만 있고, 출처는 2026-07-29
   비정규화 비교 실험(`175ddae`의 `denorm-compare.sql`)이 실행한 `ALTER TABLE places ADD COLUMN
   bookmark_count`다. 롤백 문이 주석으로만 있어 원복되지 않은 채 남았다.
2. **모호성의 메커니즘을 3케이스로 재현했다.** `INSERT ... SELECT ... ON DUPLICATE KEY UPDATE`의
   비한정 컬럼 참조는 대상 테이블과 SELECT 소스 테이블 양쪽에서 해석된다. 소스(`places`)에 같은
   이름이 없으면 정상 동작(운영 스키마 = CASE1 실증), 있으면 ERROR 1052(벤치 = CASE2),
   `place_stats.bookmark_count`로 한정하면 컬럼이 있어도 정상(CASE3)이다.
3. **증분 실패는 요청에 전파되지 않았다.** 오류 로그는 전부 `[task-N]` 비동기 스레드다
   (두 앱 합계 약 18,490건 — 즉 벤치에서 등록 증분은 9%가 아니라 **전 건** 실패했다).
   `@Async` + `REQUIRES_NEW` + AFTER_COMMIT 격리는 설계대로 동작했다.
4. **HTTP 500의 실제 원인은 북마크 중복 등록이다.** 요청 스레드(`exec-N`)의 오류는 전부
   `Duplicate entry '<user>-PLACE-<place>' for key 'bookmarks.uk_bookmark_user_target'`(1062) →
   `DataIntegrityViolationException` → `GlobalExceptionHandler` 500이다(app-1 443건 + app-2 389건).
   `BookmarkService.create`는 대상 존재만 검증하고 **중복 북마크 가드가 없다** — 이미 북마크한
   쌍을 다시 등록하면 500이 난다. 벤치가 아니라 **운영에서도 그대로인 API 결함**이다.
   ~9% 상수는 부하 프로파일의 무작위 (user, place) 쌍이 이미 북마크돼 있을 확률로 설명된다.

최초 보고에서 맞았던 것: 500이 포화가 아니라는 판단(비율이 180/240/300에서 9.04%/7.89%/8.66%로
부하와 무관), 그리고 1차의 프로세서 결함(POST 94.7% 404)이 이 500들을 가리고 있었다는 관찰
(404가 먼저 나서 INSERT까지 도달하지 못했다). 틀렸던 것: 500의 원인 문장(증분 UPSERT가 아니라
북마크 INSERT), "places에도 같은 컬럼"의 출처(앱 스키마가 아니라 벤치 오염), 그리고 격리가
뚫렸다는 함의(격리는 동작했다).

**이 측정의 범위는 보고까지다** — 수정하지 않았다 (§9-1).

## 8. 이 측정으로 말할 수 없는 것

캠페인 README 등록분 8건 + 측정 중 발견 6건.

1. **LATEST 정렬의 부하 특성** — 시나리오가 인기순 중심이다.
2. **북마크 검색의 부하 특성** — 시나리오에 없다. 페이징 없는 소량 조립이고 IT가 기능 등가를 보장한다는 근거로만 말한다.
3. **배치 무해성의 재현성** — 배치 포함 라운드는 1회다. "N회 재현"이 아니라 "실측 1회 + 무부하 2회 + 락 이론 근거"의 결합 주장이다.
4. **로컬 절대치는 운영 SLO가 아니다** (지표 계약 A.3).
5. **한계 부하의 절대값은 이 벤치 사양(컨테이너 2vCPU)의 것이다** — 유효한 것은 "목표의 몇 배"라는 비율과 "무엇이 먼저 포화하는가"라는 구조 특성뿐이다.
6. **한계 탐색은 단계당 1라운드다** — 재현성 주장이 아니라 1회 관찰이다.
7. **쓰기 분산은 균등이다** (실제 장소 id 6,320개 균등) — 핫 플레이스 집중 경합은 2026-07-31 Task 8 실측이 말한다.
8. **변화를 개별 변경에 귀속할 수 없다** — 형상에 캐시 제거와 커서 v3(+V28)가 함께 들어 있다. 비교는 "배포 형상 vs 구형상"의 묶음으로만 읽는다.

측정 중 발견해 추가한 것:

9. **세트 간 p50 절대값 비교는 신뢰 구간이 넓다** (§4.4) — 유효성 규칙이 지속적 호스트 경합을 걸러내지 못한다. 유효 라운드끼리도 6.0/8.9/7.9ms로 갈렸다. **구조 지표(statements 18.18)는 12라운드 내내 완전히 안정적이었다.**
10. **p50 미달의 원인이 완전히 귀속되지 않았다** (§4.3) — 코드가 추가한 비용은 0.203ms로 규명됐으나 미달 폭 +1.9ms는 설명되지 않는다.
11. **2차 세트의 `select_scan` 0.007 이상치는 인과가 확인되지 않았다** (§4.4 각주).
12. **커서 중복·누락 0건은 검증되지 않았다** — 시나리오는 커서를 이어 쓰지만 결과의 중복·누락을 대조하지 않는다. 08-01 §6 같은 별도 정합성 게이트가 필요하다.
13. **직전 세대(`prev_popular_score`) 정렬 경로는 어느 세트에서도 실행되지 않았다** (§0.4).
14. ~~증분 UPSERT 버그의 분기 조건 미특정~~ → **해소 (2026-08-03 정정, §7.4)** — 분기가 아니라 증분 전 건 실패(비동기·무전파)였고, 9%의 정체는 중복 북마크 POST다. 남은 미확인은 "~9%"라는 상수의 정확한 유도(CSV 사용자 1,000명의 시드 북마크 밀도)뿐이다.

## 9. 후속

1. **북마크 중복 등록의 500 변환 수정** (최우선, 운영 결함 — §7.4 정정) — `BookmarkService.create`에
   중복 가드 또는 1062 → 도메인 예외 매핑을 넣어 409/멱등 응답으로 바꾼다. 동시 요청 레이스는
   가드만으로 못 막으므로 제약 위반 catch까지 함께. 회귀 테스트에 중복·동시 토글 케이스 추가.
   1. **벤치 DB 잔재 컬럼 제거** — `ALTER TABLE places DROP COLUMN bookmark_count`
      (`denorm-compare.sql`의 주석 처리된 롤백 실행). 남겨두면 벤치의 모든 증분이 계속 조용히
      실패해 이후 측정을 오염시킨다.
   2. **증분 쿼리 컬럼 한정 (방어)** — `place_stats.bookmark_count = place_stats.bookmark_count + 1`.
      운영 스키마에선 버그가 아니지만, 소스 테이블에 같은 이름이 생기는 순간 깨지는 잠재 취약점이다
      (CASE3으로 동작 확인 완료).
2. **`select_scan` 이상치 인과 규명** — 배치 직후 통계 갱신이 시 단위 쿼리의 실행계획을 바꾸는지
   `ANALYZE TABLE place_stats` 전후로 `EXPLAIN`을 비교한다. 사실이면 "배치가 성능을 안정화한다"는
   운영 함의가 생긴다.
3. **시 단위 인기순 정렬의 풀스캔 제거** (§6.4) — 요청 1건이 12,640행을 검사하고 트래픽의 40%가
   이 경로다. 한계 규모를 올릴 여지가 가장 크다. 08-01에도 있던 기존 특성이므로 회귀 대응이
   아니라 개선 과제로 다룬다.
4. **커서 정합성 게이트** — 스크롤 중복·누락 대조 (사전 등록 항목이었으나 미검증).
5. **p50 판정을 다시 볼 필요가 있다면 전용 환경에서** — 세트 간 p50이 호스트에 흔들리는 것이
   확인됐다(§4.4). 로컬에서 ±1~2ms를 판정 기준으로 쓰는 것 자체의 한계다 (가이드 A.5).
6. **prod 설정 점검** (부하 테스트 밖) — 버퍼풀 128MB 기본값, `mem_limit` 부재,
   Hikari 풀 × 인스턴스 ≤ `max_connections`.
