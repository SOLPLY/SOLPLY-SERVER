# 2026-08-04_saturation-amplification — 포화 증폭의 원인 규명 (플랜 플립 검증)

> **사전 등록 문서다** (2026-08-04, 측정 전 고정). 직전 캠페인(2026-08-04_read-ceiling)의
> 미규명 관찰 — 포화에서 요청당 행 읽기 2배 증가 — 의 원인을 확정한다. 판정 기준은 측정 전에
> 사용자가 제시한 3조건이며, 결과에 맞춰 수정하지 않는다. **캠페인 ②(개선)는 이 진단이 끝날
> 때까지 보류한다** — 개선 설계가 이 원인에 걸려 있다.

## 1. 문제

도착 500/s(시도 554 req/s) 포화에서 전역 카운터 기준 요청당 Innodb_rows_read가 1,101 → 2,253으로
2배, Handler_read_key가 4배, Select_scan이 라운드당 150 → 8,876으로 증가했다. 이 증폭이
실재하면 포화가 요청당 비용 자체를 키우는 악순환이라 병목 해석과 개선 설계가 달라진다.

단, 이 관찰에는 **방법적 결함이 있다**: 전역 카운터를 시도 요청 수로 나눈 값이라
① 어떤 SQL이 증폭됐는지 지목할 수 없고 ② 타임아웃 후에도 DB가 계속 일했으므로 분모 선택에
따라 값이 흔들린다. 이 캠페인은 분모를 바로잡은 뒤 원인을 특정한다.

## 2. 원인 가설

포화 구간에서 인기순 목록 SQL(특히 시 단위 `town_id IN (18)`)의 실행계획이 인덱스 range →
풀스캔(ALL)으로 뒤집혀(플랜 플립) 실행당 rows_examined가 증가한다. 이 쿼리는 비용 경계선
위에 있음이 기존 실측으로 알려져 있다(range cost 1,947 vs 풀스캔 673, V26 커버링 후에도
플랜이 오간 관찰 — 기존 §9-2).

**대립 가설**: 플립은 없고, 타임아웃·동시 실행 누적이 전역 카운터를 키웠거나(측정 허상),
증폭의 주체가 인기순 SQL이 아닌 다른 문장이다.

## 3. 기술적 선택

없음 — 진단이다. 단 **진단 도구 2개를 형상에 추가**한다 (결과 해석 시 명시):

1. **FORCE INDEX 토글** (벤치 전용 env 플래그, 기본 off) — 인기순 쿼리에 인덱스 사용을
   강제하는 스위치. off/on이 실험군 A/B다.
2. **nginx `worker_connections` 상향** — 직전 캠페인에서 확인된 제3의 천장(LB) 제거.
   측정 인프라 결함 수정이라 개선이 아니며, **A/B 모두에 동일 적용**된다.

⚠️ 두 변경으로 직전 캠페인의 500 수치와 직접 비교는 깨진다. 그래서 A(자유 플랜)를 같은
조건에서 **재기준선**으로 다시 잰다. A와 B는 같은 이미지·같은 환경에서 env 플래그 하나만
다르다 — 작업 트리의 미커밋 BookmarkService 수정(중복 가드)이 새 이미지에 포함되지만
읽기 전용 믹스에서 미사용 경로이고 A/B에 공통 상수라 귀속을 해치지 않는다.

## 4. 검증할 주장과 판정 기준 (사용자 제시, 측정 전 고정)

플랜 플립이 포화를 증폭시켰다고 말하려면 **셋 모두** 충족해야 한다:

| # | 조건 | 도구 |
|---|---|---|
| ① | 동일 인기순 SQL digest의 **실행당** rows_examined가 정상(300) → 포화(500-A)에서 증가 | performance_schema `events_statements_summary_by_digest` (라운드 전 TRUNCATE, 후 덤프) |
| ② | 동일 파라미터·동일 세션 설정의 실행계획이 정상 → 포화에서 range → ALL로 변경 | 부하 전 / 정상 중 / 포화 중 / 포화 직후 EXPLAIN (+ 대표 1~2회 EXPLAIN ANALYZE) |
| ③ | 인덱스 고정(500-B) 시 실행당 rows_examined 증가와 붕괴가 **사라짐** | A/B 동일 부하 비교 |

하나라도 빠지면 정황 증거로 남긴다. 해석 분기(사전 등록):
- ①이 불성립(실행당 값 불변) → 증폭은 측정 허상(분모·동시성) — 플립 기각
- ①성립 + 주체가 인기순이 아닌 다른 digest → 그 문장으로 원인 이관
- B에서도 붕괴 유사 → 플랜이 아니라 기본 쿼리량·문장 수·CPU 용량이 한계
- B에서만 통과 → 플립이 주요 증폭원

## 5. 성공 조건 · 규율

- **분모 규율**: 클라이언트 성공 응답 수를 분모로 쓰지 않는다. 실행당 값은 digest의
  COUNT_STAR, CPU 귀속은 cgroup cpu.stat ÷ digest 실행 수 기준.
- **측정 중 ANALYZE TABLE 금지** — 통계 인과(배치→통계→플립) 검증은 조건이 바뀌므로
  별도 캠페인으로 분리한다 (기존 §9-2 후속).
- 라운드 유효성·워밍업 폐기 규칙은 직전 캠페인과 동일. CPU 판정은 cgroup이 정본
  (docker stats 문면 금지 — 함정 목록 등재됨).
- p50 등 결과 지표는 A/B 비교용 참고. 이 캠페인의 판정 지표는 실행당 원인 지표다.

## 6. 실행 프로토콜

0. LB `worker_connections` 상향 + FORCE INDEX 토글 구현 + 이미지 재빌드(1회) + 스택 재기동
   (A/B 공통 형상). 부하 전 EXPLAIN 채취(고정 파라미터 세트: 시 단위 18개 IN + 대표 커서,
   동네 단위, 태그 변형 — 같은 문장·같은 값 재사용).
1. **300 정상 세트** (플래그 off, 2라운드): digest 기준선 + 정상 부하 중 EXPLAIN 1회
2. **500-A 자유 플랜** (플래그 off, 2라운드): digest + 포화 중 EXPLAIN 1~2회(대표 쿼리만,
   추가 부하 최소화) + 포화 직후 EXPLAIN
3. **500-B 인덱스 고정** (플래그 on, 2라운드): digest + 결과 지표(붕괴 여부)
- 라운드 전 digest TRUNCATE, 라운드 후 전체 덤프를 `results/digests/`에 보존.
- 배치 직후 플랜 비교는 이번 범위 밖 — 벤치에서 :30 배치가 발화하지 않는 원인이 미확인이라
  (직전 캠페인 부수 관찰) 전제가 성립하지 않는다. §9-2 후속으로 넘긴다.

## 7. 이 테스트로 말할 수 없는 것

- 플립의 **기제**(통계 갱신 때문인지, 비용 상수의 경계 이동인지) — ②는 플립의 발생만 확정한다.
  기제는 ANALYZE 전후 비교(별도 캠페인) 몫
- 4 vCPU 등 CPU 증설 시의 거동 (별도 실험)
- 타임아웃 후 작업 지속(클라이언트 포기 → JDBC 취소 부재)의 증폭 기여 — 관찰돼도 정량 분리 불가

### 3조건 대조

| # | 조건 | 결과 |
|---|---|---|
| ① 실행당 rows_examined 증가 | **불성립** — digest 기준 cursor 12,663→12,664(+0.008%), nocursor 936→939, tag 131→131. NO_INDEX_USED 전 라운드 0 |
| ② 플랜 range→ALL | **불성립** — 부하 전/정상 중/포화 중/포화 직후 4시점 플랜 완전 동일, ALL 미출현. 포화 중 EXPLAIN ANALYZE도 인덱스 range 1,800행·2.47ms |
| ③ 인덱스 고정 시 증폭·붕괴 소멸 | **부분** — 성공 처리량 155→421 req/s(2.7배), 실패 67.6%→27.0%, p50 8.0→3.6s로 크게 개선되나 **붕괴 자체는 잔존** |

**판정: 플랜 플립(포화 → 플랜 변경 → 증폭) 가설은 기각한다.** 등록 §4의 분기대로, 직전
캠페인의 "요청당 행 읽기 2배"는 **전역 카운터를 클라이언트 관점 분모로 나눈 측정 허상**이다 —
실행당 값은 어느 문장에서도 늘지 않았고, 부하에 따라 요청 믹스(비싼 커서 문장의 비중
16.6%→6.4%)가 변해 "요청당 평균"이 움직였으며, 500A의 총 rows_examined는 300보다 오히려
적었다(122.1M vs 146.5M). 전역 InnoDB 카운터와 digest rows_examined의 집계 의미 차이도
겹쳐 있어, **실행당 원인 지표는 digest를 정본으로 삼는다** (교훈 등재).

### 등록에 없던 발견 — 커서 쿼리는 부하와 무관하게 항상 13.5배 비싸다

등록 분기(①성립+주체 이관)와 형태가 다르다: 같은 인기순 SQL이 **커서 유무로 갈린다.**
`scroll p2`(믹스 20%)의 커서 술어 `ps.place_id > :cursorPlaceId`가 조인 등식(`p.id =
ps.place_id`)을 타고 `p.id > :cursorPlaceId`로 전파되면서 옵티마이저가 주도 테이블을
places로 뒤집는다 — `idx_places_town_active` 전량 스캔(6,342행) + place_stats PK 되짚기
6,342회 + Using temporary. **부하 0인 pre-load에서도 동일**하므로 포화 유발이 아니라 상시
결함이다. 실행당 12,663행 = 비커서(936행)의 13.5배.

FORCE INDEX(idx_place_stats_town_score)가 이 플랜을 ps 주도 range(1,798행)로 되돌리고,
그 효과가 500B의 처리량 2.7배다. **개선 표적 1호가 확정됐다** — 단 500B도 붕괴는 잔존하므로
(등록 분기 "B에서도 붕괴 유사"), 남은 천장은 플랜이 아니라 **기본 문장량 × 문장당 고정
비용**이다: 문장당 MySQL CPU가 193~227us로 세트·플래그와 무관하게 불변인데, 요청당 문장이
~18개라 500 req/s급에서 DB CPU 예산(2코어)이 문장 처리 고정비용만으로 소진된다.

### 부수 관찰

- **배치는 :30이 아니라 :00 부근에 발화한다** (calculated_at 01:59:59.987 균일) — 직전
  캠페인의 ":30 미발화" 관찰의 답일 가능성. 스케줄 설정 확인 후 문서·회피창 수정 필요.

- 형상: 진단 도구 변경분(nginx main conf, compose env, FORCE INDEX 토글)은 미커밋 상태로
