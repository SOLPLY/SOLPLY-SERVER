## 0. 게이트 ① — 부하 테스트가 아니다

가이드 §2로 판정했다. 7개 항목 중 Artillery 부하가 필요한 것은 **0개**다.

| # | 항목 | 적합한 검증 |
|---|---|---|
| 1 | 배치 소요 + 멱등성 | 단발 실행 시간 3회 + 재실행 diff (§4 "배치 작업" 지표) |
| 2 | 실시간 `COUNT` 비용 | `EXPLAIN ANALYZE`. **부하는 이미 [2026-07-29 캠페인](../2026-07-29_place-popular-sort/)이 v0 기각(성공률 1.6%)으로 끝냈다** — 이번엔 그 기각의 *원인 지표*를 남기는 것 |
| 3 | 비정규화 카운터 락 경합 | 동시 DB 세션 실험. 앱 경유 불가 — 카운터 컬럼은 기각안이라 구현체가 없다 |
| 4 | `idx_bookmark_target` | `EXPLAIN` |
| 5·6·7 | 리뷰 락 / FK 부모 S락 / History list length | `SHOW ENGINE INNODB STATUS` + `performance_schema.data_locks` 한 번에 |

부하를 안 걸므로 스킬 §5의 "측정 전 호스트 정리"도 하드 블로커가 아니다 —
**레이턴시를 1급 지표로 쓰는 라운드가 하나도 없다.**

### 재현이 아니다 — 각 항목이 무엇인지

"기존 실측을 재현한다"는 표현이 브리프에 섞여 있으나 정확하지 않다. 재현인 항목은 하나도 없다.

| 성격 | 항목 | 뜻 |
|---|---|---|
| **최초 측정** | 3 · 5 · 7 | 존재한 적 없는 값. 항목 3은 구현된 적 없는 구조라 *만들어서* 잰다 |
| **새 환경 확정치** | 1 · 6 | 과거 값은 환경이 달라 폐기. 비교하지 않고 새로 확정한다 |
| **미완 검증** | 2 · 4 | 그냥 아직 안 한 것 |

항목 3이 "재현"이 아니라 "만들어서 잰다"인 것이 실험 설계를 바꾼다 —
**내가 만든 모형이 실제로 채택했을 구조와 같은 락 거동을 보이는가**가 결과의 타당성을 좌우한다 (§3 참조).

## 1. 문제

`place_stats` 별도 테이블 + 하루 1회 전량 재계산은 세 대안을 기각하고 나온 구조인데,
**기각 근거 중 실측으로 뒷받침된 것이 사실상 없다.**

- **실시간 집계** — v0 부하 테스트로 기각됐으나 그 *원인 지표*(단건 집계 쿼리 비용)가 남아 있지 않다
- **비정규화 카운터** — 설계 §2.3의 근거는 ① 축이 스키마에 샌다 ② 2급 데이터 ③ 정확도 요구 분리로
  **전부 설계 원칙이고 성능·락 근거가 아니다.** 락 경합은 측정된 적도, 근거로 적힌 적도 없다
- **전량 재계산 비용** — 6.0~6.2초 실측이 있으나 시드 스크립트 미보존 + 버퍼풀 1G라 인용 불가
- 채택안의 비용도 환경이 셋으로 갈려 있다 (설계 §2.7 말미 경고). `place_reviews` 락은
  **한 번도 측정된 적이 없다** — 기존 락 덤프의 측정 DB에 리뷰가 0건이었다

## 2. 원인 가설

- **(a)** 실시간 `COUNT`는 1위 장소 69,784행을 인덱스 스캔해야 하고, 시 단위 정렬은 후보
  최대 ~1,800곳에 이를 반복한다 → `place_stats` PK IN 조회와 읽는 행 수의 자릿수가 다르다
- **(b)** `places`에 카운터를 박으면 인기 장소일수록 같은 행에 X락이 몰려 북마크 토글이
  장소 단위로 직렬화된다. Zipf 편중(1위 69,784건)이 이 경합을 증폭한다
- **(c)** 전량 재계산은 두 파생 서브쿼리가 인덱스 전용 스캔이면 북마크 행 수에 선형이고,
  하루 1회 주기의 0.01% 미만이라 감당 가능하다
- **(d)** `place_reviews`는 북마크 축과 쿼리 구조가 같아 RR에서 전 행 next-key 락,
  RC에서 0건일 것이다

## 3. 기술적 선택

**이미 구현된 것이다.** 이번 측정은 사후 정당화가 아니라 기각 근거의 확보다 —
설계 §6.1이 명시하듯 복합 점수는 신규 기능이라 비교할 before가 없다.

채택: `place_stats` 별도 테이블 + 매일 02:00 `INSERT…SELECT ON DUPLICATE KEY UPDATE` 전량 재계산
+ `READ_COMMITTED` + `created_at <= :calculatedAt` 상한.

기각: 실시간 집계 / `places` 비정규화 카운터 / 증분 갱신 / chunk 분할.

### 항목 3의 모형 — 무엇을 만들어 재는가

카운터 컬럼은 구현체가 없으므로 실험용 모형을 만든다. **모형이 실제 구조를 대표해야 한다.**

- 벤치 DB에만 임시 컬럼을 추가하고, 동시 mysql 세션 N개가
  **`INSERT INTO bookmarks` + `UPDATE places SET cnt = cnt + 1`을 한 트랜잭션으로** 실행한다
- 카운터만 때리는 모형은 실제보다 **락 보유 시간이 짧게 나와 기각 근거를 약하게 만든다** —
  실제 구현이라면 북마크 삽입과 카운터 증가가 같은 트랜잭션에 들어간다
- **대조군**은 같은 N 세션의 `INSERT INTO bookmarks` 단독 (= 현행 채택 구조)
- 조건 2종: **핫스팟 1행**(1위 장소, 최악) · **상위 10곳 분산**(현실적)
- 마이그레이션·앱 코드를 건드리지 않으므로 되돌릴 것이 없다

## 4. 검증할 주장

1. 벤치 스택(북마크 1,039만 + 리뷰 20만)에서 전량 재계산 1회는 주기의 1% 미만에 끝나고,
   같은 `calculatedAt`으로 재실행하면 `place_stats` 전 행이 동일하다
2. 1위 장소 실시간 `COUNT(*)`가 읽는 행이 `place_stats` PK 조회 대비 자릿수로 크다 —
   이것이 v0 기각의 원인 지표다
3. `places` 카운터 구조는 동시 토글이 X락으로 직렬화되고, 현행 구조는 같은 부하에서 락 대기가 없다
4. `created_at <= :calculatedAt` 상한 추가 후에도 북마크 축이 `Using index`를 유지한다
   (리뷰 축 `idx_place_reviews_place_created_rating`도 같이 확인)
5. `place_reviews`가 RR에서 전 행 규모 next-key 락 / RC에서 0건 — RC 전환이 리뷰 축까지 커버한다
6. 벤치 규모(장소 6,000 갱신)에서 `places` FK 부모 S락은 6,000건이고, 어드민 `UPDATE places`가
   배치 커밋까지 블록된다
7. 배치 중 History list length를 기록해 purge 지연 baseline을 남긴다

### 효과 크기 가늠 (가이드 부록 A.1)

- **2 · 3 · 5는 자릿수 차이 예상** → 환경 통제에 시간 쓰지 않는다

- 10~20% 차이를 주장하는 항목이 없다 → 로컬 벤치로 충분하다

### 이론으로 이미 답이 나오는 항목이 섞여 있다 (사용자 제기, 2026-07-31)

정직하게 적어 둔다. **이론으로 못 푸는 것은 항목 1·4 둘뿐이다.**

- **항목 1** — 1,039만 행 감쇠 SUM의 실제 소요는 계산으로 안 나온다. 설계 §2.6 전환 임계점의 유일한 수치 근거

5·6·7은 락 덤프 한 번에 딸려 나오고, 2는 EXPLAIN 한 줄이다.

## 8. 리뷰 시드 수량을 20만으로 확정한 근거

설계 문서는 §1.2 규모 산정표에 **20만**, §2.6 과거 실측 행에 30만으로 갈려 있었다.

**20만을 택한다.**

- §1.2의 산정이 유일하게 근거를 가진 숫자다 — 유저 10만 × 2건, 교차검증 DAU 2만 × 0.5%/일 → 3년 11만
- **리뷰/북마크 = 1/50 비대칭**이 설계의 근거 중 하나다(북마크는 탭 1회, 리뷰는 방문+사진+500자).
  30만이면 1/35가 되어 그 논거와 어긋난다
- 30만은 **맞춰야 할 기준이 아니다** — 그 측정은 버퍼풀 1G·시드 미보존으로 이미 폐기됐고,
  비교 대상이 아닌 값에 시드를 맞추면 폐기한 수치에 새 측정을 종속시키는 셈이 된다

## 9. 이 캠페인으로 말할 수 없는 것

- **v0 벤치 경로와 캐시 경로의 랭킹은 더 이상 같지 않다** — v0는 `COUNT(*)`, 서비스 경로는
  `popular_score`. 지연·처리량 비교는 유효하지만 **모드 간 결과 diff 검증은 성립하지 않는다**
- **prod 절대 성능** — 벤치는 버퍼풀 2G, prod는 기본값 128MB (가이드 부록 A.4)
- **항목 3의 결과는 "실제 구현했다면"의 모형값이다** — 실제 애플리케이션 경로(JPA·커넥션 풀·
  트랜잭션 경계)를 거치지 않았으므로 절대 수치가 아니라 **현행 구조와의 상대 비교로만** 읽는다
