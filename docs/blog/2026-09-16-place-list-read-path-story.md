# 장소 목록 조회의 개선 과정 — 요구사항에서 인메모리 조회 모델까지

작성일: 2026-09-16 · 구현 기준: 2026-09-15

이 글은 장소 목록 조회 한 기능을 놓고 "무엇을 만족해야 하는가"를 먼저 정한 뒤, 그 기준으로
구조를 한 단계씩 고른 과정을 정리한 것이다. 출발점은 DB 실행 계획을 분석해 쿼리 형상을
확정한 직후의 구조이고, 종착점은 지금 운영 중인 인메모리 조회 모델이다. 판단마다 근거가 된
측정을 함께 적었다. 서버가 늘거나 데이터·트래픽이 커질 때의 대비는
[별도 문서](2026-09-16-place-list-scale-readiness.md)에 있다.

측정 정본은 `docs/perf/`와 `load-test/campaigns/`에 있고, 이 글의 수치는 전부 그곳에서
옮겼다. 원고 단위의 기록은 [문장 캐시](2026-08-29-stmt-cache-hidden-app-cost.md),
[인메모리 전환](2026-08-29-inmemory-read-model.md),
[조회 모델과 갱신](2026-09-09-admin-rebuild-tradeoff.md),
[스냅샷 구조](2026-09-10-distributed-inmemory-snapshot-architecture.md)에 있다.

## 1. 문제와 요구사항

### 1.1 기능

솔플리의 메인 화면은 장소 목록이다. 사용자는 동네를 하나 또는 여러 개 고르고(시 단위를
고르면 동네 18개), 태그 필터를 걸고(같은 그룹 안은 OR, 그룹 사이는 AND), 정렬 하나를 골라
한 페이지 10건씩 커서로 내려받는다. 정렬은 여섯이다.

| 정렬 | 정렬 키의 출처 | 성격 |
|---|---|---|
| 인기순 | 집계 배치가 계산하는 인기 점수 | 정적 |
| 최신순 | 장소 등록 시각 | 정적 |
| 평점순 | 리뷰 평균 평점 | 정적 |
| 리뷰 수순 | 리뷰 개수 | 정적 |
| 북마크 수순 | 북마크 개수 | 정적 |
| 거리순 | 사용자 좌표와 장소 좌표의 거리 | 요청마다 다름 |

정렬 키의 원천은 배치가 주기적으로 갱신하는 통계 테이블 `place_stats`다. 장소 원본,
태그, 리뷰, 북마크는 각자의 테이블에 있고 목록이 읽는 값만 이 테이블에 모아 둔다.

### 1.2 비기능 요구사항과 목표

기능은 명확했다. 문제는 "이 기능이 어느 부하까지 어떤 여유를 남기고 돌아야 하는가"였고,
그것을 먼저 숫자로 정했다.

**목표 부하.** 평상시 도착 60/s에서 안착한 뒤, 같은 실행 안에서 피크 도착 300/s로 즉시
전환한다. 도착 하나가 첫 페이지와 커서 두 번째 페이지를 이어 부르므로 제공 부하는 약
571 req/s다. 정렬 믹스는 실사용 가정 비율(인기 40 / 거리 20 / 리뷰 15 / 북마크 10 /
평점 10 / 최신 5)이고, 각 정렬을 단일 동네 40% / 시 단위 60%로 나눈다. 급증 전환을
시나리오에 넣은 이유는 JIT 같은 JVM 작업이 전환 중에 겹치는 상황을 피하지 않기
위해서다.

**운영 안전 기준.** 오류 0과 SLO 통과만으로는 "안정적"이라고 부르지 않기로 했다. 목표는
예상보다 큰 순간 트래픽을 받아낼 여유이고, 그 여유를 네 항목으로 정의했다.

| 항목 | 기준 | 이유 |
|---|---|---|
| 앱 CPU 평균 | 2 vCPU 쿼터의 약 50% | 급증과 JIT·GC 같은 JVM 배경 작업이 쓸 몫을 남긴다 |
| CFS 스로틀 | 극소량이고 p99·커넥션 대기에 영향 없음 | 쿼터를 다 쓴 주기가 생기면 그 주기의 요청이 통째로 밀린다 |
| Hikari 커넥션 대기 | 0 | DB 왕복이 요청 스레드를 붙드는 순간 큐가 생긴다 |
| DB 쿼터 소진 주기 | 0 | DB는 쓰기와 다른 기능도 함께 쓰는 자원이다 |

측정 환경은 운영과 같은 CPU 경계다. 앱 2 vCPU + MySQL 8.0 2 vCPU를 Docker cgroup
쿼터로 묶고, cgroup `cpu.stat`의 누적 CPU 시간 차분으로 사용률과 요청당 CPU 단가를,
`nr_throttled / nr_periods`로 스로틀 발생 주기 비율을 잰다. JVM 안에서 그 CPU가 어디에
쓰였는지는 JFR 실행 샘플로 귀속한다. 두 계층을 나눈 이유는, 컨테이너 지표는 "병목이
어디냐"까지만 말하고 "요청 CPU의 어디가 비싸냐"는 말하지 못하기 때문이다.

**데이터 규모.** 이 서비스는 동네 단위로 장소를 골라 보여주는 큐레이션 구조라 등록형
플랫폼처럼 자릿수로 자라지 않는다. 지금 동네당 100곳 안팎(전체 6,320곳)에서 쿼리 형상을
고르는 상한은 2배(동네당 200곳)로 잡았고, 구조의 힙·CPU 여유를 확인하는 상한은 보수적으로
10배(63,200곳)로 잡았다. 그 너머는 "이 구조의 문제"가 아니라 "다른 구조를 논의할 문제"로
범위를 정했다.

### 1.3 조회 결과가 지켜야 할 계약

성능만이 요구사항은 아니다. 구조를 바꿔도 다음은 그대로여야 했다.

- **커서 일관성.** 한 사용자가 스크롤을 내리는 동안 항목이 겹치거나 빠지지 않는다. 정렬
  순서가 통째로 바뀌는 변경(집계)이 있으면 조용히 어긋나게 두지 않고 명시적으로 끊어
  클라이언트가 첫 페이지부터 다시 받게 한다.
- **신선도.** 관리자 수정은 곧 목록에 보인다. 인기 점수·리뷰 수·평점·북마크 수는 집계
  배치 주기로 갱신된다. 이 두 폭은 원래 DB 조회 구조가 제공하던 폭이고, 새 구조가 이보다
  나빠지면 안 된다.
- **응답 동등성.** 조회 경로를 바꿔도 같은 요청에 같은 응답과 같은 커서 토큰을 낸다.
  다르면 성능 비교 자체가 뜻이 없다.
- **확장 비용.** 정렬 기준이나 필터가 하나 늘 때 드는 검증·운영 비용이 작아야 한다. 정렬을
  둘에서 여섯으로 늘리는 요구가 이미 한 번 있었고, 앞으로도 있을 것이기 때문이다.

## 2. 출발점 — DB가 할 수 있는 것을 다 한 구조

출발점은 DB 쪽 최적화가 끝난 구조다. 정렬별 커버링 인덱스를 갖췄고, 태그 판정은 `place_tag`
조인 대신 `place_stats`에 비정규화한 비트마스크로 인덱스 엔트리 안에서 끝내며, 다중 동네
조회는 동네별 브랜치를 `UNION ALL`로 묶어 각 브랜치가 자기 동네에서 11건(10건 + 다음 페이지
판정 1건)을 채우면 멈춘다.

```text
요청 (동네 18개, 태그 2그룹, 인기순, 커서)
  → 동네 조건·태그 조건 검증 (DB)
  → (SELECT ... WHERE town_id = ? AND (tag_mask & ?) != 0 ... ORDER BY score DESC LIMIT 11)
    UNION ALL × 18
    ORDER BY score DESC LIMIT 11                                (DB, 문장 1개)
  → 결과 11건의 장소 엔티티 조립 (JDBC → Hibernate)
  → 사용자 북마크 여부 조회 (DB)
  → 응답
```

이 형상을 고른 근거는 데이터가 자라도 읽는 행이 자라지 않는다는 것이었다. 동네당 100곳에서
200곳으로 시딩을 2배로 키웠을 때, 동네를 `IN`으로 묶은 형상은 처리량이 3,415에서 1,904
QPS로 떨어졌지만 `UNION ALL` 형상은 3,836에서 3,586으로 거의 그대로였다. DB 실행 비용 기준으로는
옳은 선택이었다.

그런데 목표 부하를 앱을 경유해 걸자 병목은 DB가 아니었다.

| 목표 부하 (제공 ~571 req/s) | 값 |
|---|---:|
| 오류 | 0 |
| 앱 CPU 평균 (2 vCPU 쿼터 대비) | 75.5% |
| 앱 CFS 스로틀 발생 주기 / 누적 (피크 90초) | 21.6% / 60.5초 |
| p95 | 308ms |
| 전환 직후 버킷 p50 / 최대, 복귀까지 | 314ms / 879ms, 약 20초 |
| DB CFS 스로틀 | 0.57% |

요청은 다 처리했지만 운영 안전 기준 네 항목 중 통과한 것은 DB 하나였다. 앱 CPU가 쿼터 상한에
근접해 있었고, 급증 순간 20초 동안 지연이 이어졌다. 여기서 확인한 사실은 하나다. **DB 실행을
최적화하는 것만으로는 앱 CPU 여유가 확보되지 않는다.**

## 3. 비용이 발생하는 지점을 특정했다

자원 지표는 "병목이 앱"이라는 것까지만 말한다. 요청 CPU의 어디가 비싼지는 프로파일로
열어야 했다.

### 3.1 반복되는 조회 경로

피크 구간 HTTP 요청 스레드의 JFR 실행 샘플에서 약 32%가 JDBC/MySQL 드라이버, Hibernate
결과 처리, 응답 조립 경로에 귀속됐다. 특정 메서드 하나가 아니라 여러 곳에 분산돼 있었다.
Hibernate의 쿼리 처리, 드라이버의 SQL 문자열 분석, 결과 행의 값 추출과 타입 변환, DB
결과를 자바 객체로 만드는 조립, 영속성 컨텍스트와 세션 관리. 이 범주에는 벤치 환경의 쿼리
로거(p6spy) 비용도 섞여 있어, 32%를 정확한 CPU 시간으로 읽지 않고 "DB 조회와 함께 요청마다
반복되는 경로가 유의미한 hotspot"이라는 근거로만 썼다.

```text
요청
 → Hibernate 쿼리 처리
 → 드라이버의 SQL 분석과 파라미터 바인딩
 → SQL 전송, DB 실행, 결과 수신
 → ResultSet 행 접근, 값 추출과 자바 타입 변환
 → Hibernate가 결과를 객체로 구성
 → DTO 변환, 응답 조립
```

### 3.2 문장 텍스트 자체의 비용

`UNION ALL`은 동네마다 완전한 SELECT 한 벌을 복제한다. 시 단위 요청의 문장은 최대
9,378자, 바인드 자리는 127개였고, 이 문장을 쓰는 요청이 믹스의 48%(시 단위 60% ×
비거리 80%)였다.

프로파일로 후보를 하나씩 제외했다. SQL 문자열을 **만드는** 비용(StringBuilder)은 요청
CPU의 0.07%로 원인이 아니었다. 반환 행 수도 실행당 11행으로 같았다. 남은 것은 만든 문장을
**다루는** 비용이었다. 드라이버는 `prepareStatement()`를 받을 때마다 SQL 텍스트를 문자
단위로 스캔해 `?`의 위치 지도를 만드는데, 이 재파싱이 요청 CPU의 6.8%였다. 값을 끼운 9KB
전문을 실행마다 통째로 서버에 보내는 패킷 조립·송신이 5.6%였다.

같은 문장 하나가 실행될 때 파싱은 세 층에서 따로 일어난다.

| 층 | 파싱해서 만드는 것 | 캐시 | 당시 상태 |
|---|---|---|---|
| Hibernate | `:이름` → 순번 표 | 기본 켜짐 (2,048개) | 이미 쌌다 (0.26~1.0%) |
| MySQL 드라이버 | `?` 위치 지도 | **기본 꺼짐** | 실행마다 9,378자 재파싱 (6.8%) |
| MySQL 서버 | 파스 트리·실행 계획 | 텍스트 프로토콜에선 없음 | 실행마다 재파싱 |

문장이 251자였던 초기 형상에서는 세 층 모두 공짜나 다름없어 이 층 구분을 의식할 일이
없었다. 문장이 37배가 되자 꺼진 층의 반복 비용만 37배로 자란 것이다.

정리하면 비용은 두 겹이었다. **긴 SQL을 매 실행 다시 읽고, 다시 보내고, 다시 파싱하는
값**, 그리고 그 아래에 깔린 **요청마다 SQL을 준비하고 전달하고 결과를 객체로 만드는 조회
경로 전체가 반복되는 값**이다.

### 3.3 선택지는 둘

원인이 "텍스트 길이 × 반복"과 "요청당 조회 경로"라면 선택지도 둘이다.

- **문장을 싸게 만든다.** 텍스트는 그대로 두되 파싱·전송·서버 준비를 한 번만 하고 재사용한다.
  드라이버 설정으로 켜는 문장 캐시와 서버 prepared statement. 코드 무변경.
- **문장을 없앤다.** 목록 조회에 필요한 SQL 자체를 요청 경로에서 줄인다. 정렬·필터·페이징을
  요청 시점의 DB에서 떼어낸다.

작은 변경부터 시도하는 것이 순서다. 첫 번째 선택지를 먼저 적용했다.

## 4. 첫 번째 해법 — 같은 문장을 반복 준비하는 비용을 없앴다

### 4.1 문장을 접는 안은 게이트에서 기각했다

설정을 켜기 전에, 문장이 큰 원인(동네 수가 텍스트에 새겨짐)을 없애는 안도 검토했다. 동네
목록을 JSON 배열 값 하나로 바인딩하고 `JSON_TABLE` + `LATERAL`로 동네마다 상위 11건을
뽑으면 문장이 동네 수와 무관한 상수 크기(533자)가 된다. 구현까지 했다.

그러나 `UNION ALL`을 채택한 근거가 "브랜치가 자기 동네에서 일찍 멈춘다"였으므로, `LATERAL`
조각도 같은 조기 종료를 해줘야 이득이 공짜가 된다. 부하를 걸기 전에 실행 계획으로 게이트를
세웠고, 게이트가 기각했다. `UNION` 브랜치의 `?`는 실행 시점에 확정되는 상수라 옵티마이저가
"이 구간은 이미 점수순"임을 실행 계획에 반영해 11건에서 멈추지만, `LATERAL`의 `towns.town_id`는
바깥 행에 따라 바뀌는 상관 참조라 MySQL 8.0은 동네 구간을 전량 읽고 filesort로 자르는
경로를 반복마다 돌았다(rows=11, loops=1 대 rows=100, loops=18). 2배 시딩에서 읽는 행이
정비례로 되돌아왔고 포화 처리량이 24% 뒤졌다.

수확이 없지는 않았다. 현재 규모에서는 이 형상이 읽기를 8.5배 늘리고도 처리량으로 `UNION`을
이겼다(실행당 DB CPU 658 → 523µs). 읽기를 8.5배 늘리고도 이긴다는 것은 **서버가 긴 문장을
실행마다 다시 파싱하던 비용이 그만큼 컸다**는 뜻이다. 이 관측은 첫 번째 선택지 쪽, 그중에서도
서버 파싱까지 지우는 구성을 지지하는 증거가 됐다.

### 4.2 적용 전에 흔한 반론을 실측으로 검증했다

드라이버 캐시는 흔한 해법이고 흔한 반론이 따른다. 네 가지 일반론을 이 서비스의 실측에
대입했다.

**"커넥션 수 × 캐시 크기만큼 메모리가 급증한다."** 이 캐시는 선할당이 아니라 커넥션당 LRU
상한이다. 점유는 설정값(512)이 아니라 실제로 지나간 문장 집합을 따라간다. 실측 상주 문장은
커넥션 10개 합계 114개(커넥션당 11~12개), 항목당 문장 텍스트 크기(~10KB)이니 합쳐 1MB
남짓이다. GC 후 힙 89~105MB의 한 자릿수 퍼센트에도 못 미친다. 서버 쪽은 상주 114문장이
performance_schema 계기 실측 58MB로 DB 컨테이너 3GB의 2%다. 핸들 개수 상한은 10 × 512 =
5,120으로 `max_prepared_stmt_count` 기본 16,382의 31%다.

**"장수 객체가 늘어 Old 영역을 압박한다."** 방향이 반대였다. 캐시 없는 상태가 요청마다
`QueryInfo`와 9KB 문자열을 새로 할당해 버리고 있었고, 캐시는 그 요청당 할당을 소량의 장수
객체와 맞바꾸는 경감책이다. GC 정지는 피크 창의 0.25~0.44%로 문턱에 자릿수로 못 미쳤다.

**"문장 형상이 무한히 생기면 적중률이 안 오른다."** 이것이 유일하게 타당한 반론이고 설계
전제가 됐다. 이 코드는 동네 id·커서·마스크·LIMIT 전부를 바인딩으로 넘겨 형상이 유한하다
(벤치 실동작 114종). 형상을 늘리는 안(동네 수만큼 `SELECT ?`를 복제하는 변형)을 세우지 않은
이유이기도 하다.

**"통계 갱신 때 구형 실행 계획을 재사용한다."** 실행 계획을 공유 캐시하는 Oracle 계열의
문제를 MySQL에 대입한 것이다. 드라이버 캐시가 담는 것은 `?` 위치 지도뿐이고, 서버 prepared
statement는 테이블 정의 같은 메타데이터가 변하면 자동으로 재준비한다(`Com_stmt_reprepare`).
남는 실체는 서버가 준비 시점에 리터럴 대신 `?`를 본다는 가시성 변화 하나라, 아래 비교에서
클라이언트 캐시만 켠 구성과 서버까지 켠 구성을 분리해 그 값을 따로 쟀다.

### 4.3 설정 네 줄

```text
cachePrepStmts=true          캐시의 주 스위치 (커넥션별 LRU)
prepStmtCacheSqlLimit=16384  이보다 긴 문장은 캐시 제외. 기본값 256자를 안 올리면
                             정작 문제의 9,378자 문장만 조용히 빠진다
prepStmtCacheSize=512        커넥션당 캐시 칸 수 (실사용 11~12형상)
useServerPrepStmts=true      최초 1회만 서버에 준비시키고, 이후엔 문장 핸들 +
                             바이너리 값만 전송
```

네 설정은 함께 적용해야 한다. 클라이언트 캐시만 켜면 드라이버의 `?` 지도 재파싱은 사라지지만 전문
전송과 서버 파싱은 남는다. `useServerPrepStmts`를 켜야 최초 한 번 `COM_STMT_PREPARE`로
준비하고 이후 `COM_STMT_EXECUTE`에 문장 ID와 파라미터만 보낸다. 그리고 prepared statement는
물리 커넥션에 귀속되므로 `cachePrepStmts`가 없으면 요청마다 prepare와 close가 반복된다.
서버에서 준비하는 프로토콜을 쓰고, 그것을 드라이버가 커넥션별로 재사용하도록 묶은 구성이다.

### 4.4 같은 창에서 세 구성을 쟀다

바뀌는 축은 JDBC URL뿐이다. 안착 구간 3라운드 교차, 목표 부하 1라운드.

| 목표 부하 (제공 ~571 req/s) | 캐시 없음 | 드라이버 캐시만 | 드라이버 캐시 + 서버 PS |
|---|---:|---:|---:|
| 오류 | 0 | 0 | 0 |
| p50 / p95 | 5 / 308ms | 5 / 391.6ms | **4 / 7ms** |
| 앱 스로틀 발생 주기 | 21.6% | 17.0% | **1.4%** |
| 요청당 앱 CPU | 2.536ms | 2.424ms | **2.165ms** |
| 요청당 DB CPU | 1.905ms | 1.895ms | **1.539ms** |
| 앱 CPU 평균 | 75.5% | 72.8% | **64.1%** |
| DB CPU 평균 | 56.7% | 56.9% | **45.6%** |

드라이버 캐시만으로는 부족했다. 단가가 조금 내려갈 뿐 tail latency가 그대로였다. 서버 prepared
statement까지 켜야 결과가 달랐다. 이 설정이 목록 문장만이 아니라 거리 후보 조회, 북마크 확인까지
모든 문장의 반복 파싱·전송을 지우기 때문이다. 캐시가 실제로 도는지는 서버 카운터로 확인했다.
판정 창 60초에 실행이 36,030회 도는 동안 `Com_stmt_prepare`는 130에서 멈춰 있었고(증가 0),
상주 문장 114개, 축출 0이었다.

사용률 열과 스로틀 열을 나란히 읽으면 부수 관찰이 하나 나온다. 단, 세 열은 같은 시스템을
사용률만 달리해 관측한 것이 아니라 서로 다른 해법을 적용한 세 구성이므로, 아래는 그 셋을
나란히 놓고 읽은 추론이지 사용률과 스로틀의 관계를 통제해 잰 곡선이 아니다. 평균 사용률
64.1%인 구성은 스로틀 1.4%, 72.8%는 17.0%, 75.5%는 21.6%였다. CFS 스로틀은 평균이 아니라
100ms 주기의 순간 수요로 발생하므로, 평균이 상한에 다가갈수록 쿼터를 다 쓰는 주기가 빠르게
느는 것은 기제상 자연스럽고, 세 점은 그 방향과 어긋나지 않는다. 그래서 "여유"를 평균의 남은
폭이 아니라 스로틀이 붙기 시작하는 자리까지의 거리로 읽었다.

### 4.5 남은 것

효과는 실재했다. 스로틀과 tail latency가 회복됐고 요청당 CPU가 앱 15%, DB 19% 내려갔다. 그러나
이 해법이 손대지 못하는 것이 있었다. **요청당 일의 구조**다.

```text
설정 전   요청당 SQL 문장 10개
설정 후   요청당 SQL 문장 10개
```

문장이 싸졌을 뿐 요청 하나는 여전히 문장 10개를 돌고, 결과 바이트를 엔티티로 조립하고,
커넥션을 오간다. 앱 사용률 64.1%는 운영 안전 기준 50%를 여전히 넘고, 다른 두 구성이
보여 준 대로 여기서 사용률이 10%p만 더 오르면 스로틀이 10배 이상 뛴다. 급증 전환 순간의
흔들림(전환 버킷 p95 63.4ms)도 남았다.
데이터와 기능이 늘면 같은 자리로 돌아온다.

다음 질문은 두 번째 선택지였다. **목록 조회에 필요한 SQL 자체를 요청 경로에서 줄일 수
있는가.**

## 5. DB 정렬 경로에 남아 있던 구조적 비용

인덱스를 더 다듬는 길은 후보가 되지 못했다. 정렬 6종 확장 때 이미 검증한 결과가 있었기
때문이다.

정렬별 인덱스 다섯 개가 공존하는 상태에서 90개 요청 형상(정렬 × 지역 × 태그 × 페이지)의
실행 계획을 확인하니 의도한 인덱스를 탄 것은 42칸이었고, 예상 밖 filesort가 17칸이었다.
신규 정렬의 컬럼 집합이 기존 인기순 인덱스의 부분집합이라 다섯 인덱스가 전부 커버링이
되고, MySQL은 커버링 비용이 비슷하면 정렬 순서를 얻기 위해 인덱스를 바꾸지 않는다.
근소하게 싼 쪽으로 몰리고 순서는 filesort로 만든다.

더 나쁜 발견은 커서 페이지였다. 커서에 실리는 정렬 키 리터럴이 range 추정을 움직여, 같은
요청이 직전 페이지의 이력에 따라 다른 계획을 탔다. **실행 계획이 요청의 순수 함수가
아니게 된다.**

인덱스 크기는 문제가 아니었다. 세컨더리 다섯 개 합계 2.30MB로 운영 버퍼풀의 1.79%다.
문제는 크기가 아니라 변동성이고, **기준이 하나 늘 때마다 이 검증을 반복해야 하고 그 결과를
계획의 변덕에 맡겨야 하는 구조**라는 것이다. 1.3절의 확장 비용 요구사항에 정면으로
걸린다.

거리순은 이 문제의 첫 증거이기도 했다. 기준 좌표가 요청마다 달라 정적 인덱스가 담을 수
없는 축이라, 어느 길을 골라도 앱에서 정렬해야 한다. "정렬 기준마다 인덱스"라는 구조는
애초에 모든 축을 덮지 못한다.

## 6. 두 번째 해법 — 조회 전용 인메모리 정렬

### 6.1 무엇을 옮기고 무엇을 남기는가

DB는 정본으로 남긴다. 옮기는 것은 **조회가 정렬·필터에서 읽는 값**뿐이다. 장소당 정렬 키
다섯·좌표·태그 비트를 담은 엔트리 하나를 만들고, 동네 × 정렬 5종의 참조 배열을 미리
정렬해 둔다. 요청은 그 배열에서 커서 위치를 찾아 태그를 거르며 10건을 채운다.

```text
리빌드 (원본이 바뀌었을 때)
  → place_stats 전량 조회 (문장 하나)
  → 장소당 PlaceEntry 하나 + (정렬 5종 × 동네) 참조 배열 생성
  → 번호를 붙인 스냅샷으로 참조 교체 (volatile 대입 한 번)

요청
  → 동네·태그 조건 검증 (DB)
  → 커서의 번호에 맞는 스냅샷 확인
  → 정렬 배열에서 커서 위치를 이진 탐색
  → 태그 비트마스크로 거르며 11건이 찰 때까지 스캔
  → 표시값(이름·썸네일·대표 태그)은 스냅샷 밖 홀더에서 그 10건만 꺼내 응답 조립
  → 사용자 북마크 여부 (DB)
```

### 6.2 자료구조

```text
SnapshotBox
  └── 최신 Snapshot 한 벌 (volatile 참조 하나)
        ├── 번호 둘 (cursor_version, revision)
        └── SortedPlaces
              └── 정렬 종류 → 동네 ID → PlaceEntry 참조 배열

PlaceEntry   장소 ID·동네·태그 비트마스크·좌표·정렬 키 다섯
             같은 객체를 다섯 배열이 다른 순서로 참조한다

PlaceViewHolder   장소 ID → 이름·썸네일 파일 키·대표 태그 ID   (스냅샷 밖, 한 벌)
TagViewHolder     태그 ID → 이름·활성 상태                     (스냅샷 밖, 한 벌)
```

두 결정이 여기 있다.

**정렬 배열은 참조 배열이다.** 장소 하나의 값 객체를 정렬 축마다 복제하지 않는다. 배열은
순서를, 엔트리는 값을 표현한다. 정렬 기준이 늘어도 장소 데이터가 아니라 참조 배열만
는다. 상주 비용은 장소 N개와 정렬 축 A개에 대해 대략 `O(N + A·N)`이다.

**표시값은 스냅샷 밖에 둔다.** 배열 원소에는 비교와 스캔이 읽는 값(정렬 키·좌표·태그
비트)만 두고, 이름·썸네일·대표 태그처럼 화면에만 쓰이는 값은 별도 홀더에 둔다. 이름 하나를
고치는 관리자 수정이 정렬 배열을 다시 만들지 않고 홀더의 항목 하나만 바꾸게 하기 위해서다.
정렬 일관성이 필요한 데이터와 최신성이 더 중요한 표시 데이터를 서로 다른 갱신 정책으로
관리한다는 뜻이고, 그 대가로 "정렬·필터 기준은 요청이 확보한 스냅샷으로 고정되지만
표시값까지 같은 시점으로 고정되지는 않는다"는 계약을 받아들였다. 커서가 보장하는 것은
정렬 순서의 일관성이고, 표시값은 최신일 수 있다.

### 6.3 페이지 탐색

**정적 정렬 5종.** 동네별로 미리 정렬한 배열을 쓴다.

```text
한 동네
  → 커서(정렬 키, 장소 ID)로 다음 위치를 이진 탐색
  → 그 위치부터 순서대로 읽으며 태그 비트 AND
  → 11건 확보 또는 후보 소진

여러 동네
  → 각 동네에서 커서 다음 위치 탐색
  → 동네별 다음 후보 하나씩 우선순위 큐에 넣기
  → 전체에서 가장 앞선 후보를 꺼내 필터 검사
  → 그 후보가 나온 동네의 위치만 전진시켜 다음 후보 추가
  → 11건 확보 또는 후보 소진
```

여러 동네의 페이지를 각각 완성한 뒤 합치지 않는다. 이미 정렬된 배열의 다음 후보들을 비교해
하나의 순서로 읽는 K-way merge다. 요청마다 전체 후보를 다시 정렬하지 않는다.

**거리순.** 기준 좌표가 요청마다 달라 미리 정렬할 수 없다. 동네·태그·좌표 유효성으로 후보를
먼저 줄이고, 남은 후보의 하버사인 거리를 계산해 크기 제한 최대 힙으로 가까운 11건만 유지한다.
거리를 요청 시점에 계산하지만 전체 후보를 완전히 정렬하지는 않는다.

**태그 필터.** 후보 하나의 판정은 고정 폭 비트 연산이다. 그룹 안 OR는 그룹 마스크와의 AND가
0이 아닌지로, 그룹 사이 AND는 판정을 나란히 거는 것으로 표현된다. 후보 탐색 자체를 없애는
장치는 아니다. 통과율이 낮으면 페이지 하나를 위해 검사하는 후보 수가 는다. 이 한계와 그
다음 대안은 [규모 문서](2026-09-16-place-list-scale-readiness.md)에 있다.

| 작업 | 비용을 결정하는 값 |
|---|---|
| 정적 목록 조회 | 대상 동네 수, 커서 탐색 비용, 필터 통과 전 검사한 후보 수 |
| 거리순 조회 | 대상 후보 수, 거리 계산 수, 유지할 결과 개수 |
| 전체 배열 구성 | 장소 수, 동네별 장소 분포, 정렬 축 수 |
| 상주 메모리 | 장소 객체 수, 정렬 배열의 참조 수, 표시값 크기 |

### 6.4 전환 전에 확인한 두 조건

**신선도 계약이 유지되는가.** 관리자 수정은 커밋 직후 반영되고, 카운트·점수는 어차피 배치
주기로 갱신된다. 조회 축을 메모리로 옮겨도 사용자가 보는 신선도는 그대로다. 새로 잃는 것이
없다는 점이 전환 문턱을 낮췄다. 다만 "그대로"를 지키려면 캐시 적재·갱신에 대한 요구사항을
따로 정의해야 했고, 그것이 7절이다.

**DB 경로와 같은 응답을 내는가.** `sort-source` 스위치로 두 경로를 같은 빌드에 공존시키고,
동점·같은 초 생성·리뷰 0건·좌표 없는 장소·다중 동네 병합·커서 이후 페이지 같은 경계 조건을 포함한
픽스처에서 두 모드를 나란히 돌려 응답과 커서 토큰이 완전히 같은지를 테스트가 검증한다.
기대값을 손으로 적지 않으므로 두 경로가 함께 틀리는 그린은 생기지 않는다. 다르면 캐시가
아니라 버그이고, 그 상태의 측정은 뜻이 없다.

## 7. 캐시 적재·갱신은 무엇을 보장해야 하는가

조회를 메모리로 옮기는 순간, 원래 DB가 요청마다 해 주던 "최신을 읽는다"를 서버가 스스로
책임져야 한다. 어디까지 보장할지를 먼저 정했다.

### 7.1 요구사항

| 번호 | 요구사항 | 근거 |
|---|---|---|
| G1 | 요청은 어느 한 시점의 완결된 스냅샷만 본다. 갱신 중간 상태를 보지 않는다 | 한 페이지 안에 서로 다른 정렬 상태가 섞이면 커서 계약이 깨진다 |
| G2 | 순서가 통째로 바뀌는 변경(집계)은 진행 중인 스크롤을 명시적으로 끊는다 | 200 응답 안에서 항목이 겹치거나 빠지면 클라이언트가 알 방법이 없다 |
| G3 | 관리자의 일상 수정은 스크롤을 끊지 않는다. 끊을지는 관리자가 고른다 | 운영 시간대에 장소 하나 고칠 때마다 사용자를 첫 페이지로 되돌리지 않는다 |
| G4 | 관리자 수정이 다른 서버에 닿는 상한은 폴 간격(1분)이다. 수정한 서버에는 표시값이 즉시 보인다 | 원래 DB 경로의 "커밋 직후 반영"에 가장 가까운 폭 |
| G5 | 집계 결과는 그것을 필요로 하는 첫 요청이 폴과 무관하게 즉시 리빌드를 시작한다 | 15분 격자의 집계가 1분 폴을 기다리면 그 사이 커서 만료만 반복된다 |
| G6 | 같은 시점을 목표로 하는 리빌드는 한 서버에서 한 번만 돈다 | 캐시 미스에 요청이 몰릴 때 전량 읽기가 요청 수만큼 뜨면 안 된다 |
| G7 | 리빌드가 실패해도 기존 스냅샷을 그대로 서빙한다 | 응답 불가보다 stale이 낫다. 다음 폴이나 요청이 다시 시작한다 |
| G8 | 스냅샷이 없는 서버는 트래픽을 받지 않는다 | 빈 목록은 "장소가 없다"와 구분되지 않는 정상 응답이다 |
| G9 | 뒤처진 서버로 온 요청은 정해진 예산(3초) 안에 최신으로 답하거나, 못 하면 503으로 재시도를 유도한다 | 요청 스레드와 DB 커넥션을 점유한 채 무한정 기다리지 않는다 |
| G10 | 번호와 데이터는 언제나 같은 시점이다 | "데이터는 바뀌었는데 번호는 그대로"인 상태가 생기면 어느 서버도 그 변경을 알 수 없다 |

### 7.2 번호 둘

G2와 G3이 서로 다른 질문이라 번호도 둘이다. MySQL의 `place_list_snapshot_metadata` 한 행에
둔다.

```text
cursor_version   "지금 커서를 계속 써도 되나"   진행 중인 스크롤을 끊어야 할 때만 오른다
revision         "다시 지을 것이 있나"         목록에 실리는 무엇이든 바뀌면 오르고,
                                              cursor_version이 오를 때 0으로 돌아간다
```

하나로 합치면 둘 중 하나가 망가진다. `revision`만 두면 이름 한 칸 고친 수정이 모든 스크롤을
끊고(G3 위반), `cursor_version`만 두면 "스크롤을 유지한다"를 고른 수정이 어느 서버에도
반영되지 않는다(G4 위반).

| 쓰기 | revision | cursor_version |
|---|---|---|
| 정기 집계 회차(리뷰 카운트·북마크 델타·인기 점수·안전망) | 0으로 리셋 | +1 |
| 관리자 장소 생성·수정·삭제·동네 활성화, 기본값 | +1 | 유지 |
| 관리자가 "목록 새로 시작"을 명시한 경우 | 0으로 리셋 | +1 |
| 관리자 태그 이름·활성 상태, 이미지 후처리 | +1 | 유지 |

번호를 올리는 문장은 하나이고 DB가 현재 값을 읽어 더한다. 자바로 읽어 더해서 다시 쓰지
않으므로 두 트랜잭션이 같은 값을 읽어 같은 값을 쓰는 유실이 없다.

```sql
SET revision       = IF(? = 1, 0, revision + 1),
    cursor_version = cursor_version + ?
```

리셋을 두는 이유는 로그를 읽기 위해서다. `(13, 3)`은 "13회차의 3번째 변경"이다. 대가는
`revision` 하나로는 새것인지 알 수 없다는 것이라, 두 번호의 전순서는 `(cursor_version,
revision)` 사전식으로 정하고 비교는 `SnapshotMetadata.isNewerThan` 한 메서드에 모았다.
코드 어디에서도 `revision`을 직접 대소 비교하지 않는다. 한 곳이라도 남으면 집계 직후 만든
새 스냅샷이 `revision` 0이라 "낡았다"로 판정돼 버려진다.

### 7.3 번호는 데이터와 같은 트랜잭션에서 오른다 (G10)

번호를 올리는 UPDATE는 데이터를 고친 그 트랜잭션의 마지막 문장이다. 롤백되면 번호도 없던
일이 되고, 커밋되면 반드시 올라 있다. 마지막에 두는 이유는 그 UPDATE가 모든 쓰기 경로가
만나는 한 행을 잠그기 때문이다. 앞에서 잠그면 남은 작업(태그 재삽입·이미지 정리·통계 수천
행 UPDATE)이 도는 내내 다른 쓰기가 기다린다.

읽는 쪽도 같은 시점을 본다. 리빌드는 REPEATABLE READ 트랜잭션 하나에서 번호 한 행을 첫
문장으로 읽고, 같은 read view로 `place_stats`와 태그를 전량 읽는다. InnoDB는 첫 SELECT에서
read view를 만들고 그 뒤 모든 문장이 같은 시점을 보므로, 이 read view가 어떤 변경을 보았다면
그 변경의 번호도 함께 본다. 설치하는 것은 실제로 읽은 번호다. 폴에서 본 번호나 완료 시점의
최신 번호를 붙이지 않는다.

### 7.4 갱신 경로 — 폴, 요청, 관리자 패치 (G1, G4, G5)

```text
각 서버의 폴 (1분마다)
  → 번호 한 행 조회
  ├── 설치한 번호보다 새것이 아니다 → 끝. 원본 테이블을 건드리지 않는다
  └── 새것이다 → 이 번호를 목표로 리빌드를 부른다

리빌드
  → 새 트랜잭션 (REPEATABLE READ, readOnly)
      → 번호 읽기 → 읽은 번호를 알린다 → place_stats 전량 → tags 전량
  → 행을 PlaceEntry·표시값·태그 맵으로 조립, 정렬 배열 구성   (잠금 밖)
  → 로컬 갱신 잠금 안에서                                   (잠금 안은 대입뿐)
      ├── 읽어 온 번호가 설치한 것보다 새것이 아니면 버린다
      ├── 새 표시값 맵 위에 그 시점 뒤에 커밋된 표시값 패치를 먼저 적용한다
      └── 표시값 맵 교체 → 스냅샷 채택
```

리빌드의 읽기·조립·정렬은 전부 잠금 밖에서 끝내고, 잠금 안에서는 완성된 것을 대입만 한다.
중간에 터지면 아무것도 바뀌지 않은 채로 끝나고 지금 스냅샷이 그대로 서빙된다(G7). 사용자
조회는 이 잠금을 잡지 않고 불변 데이터를 읽는다. 이미 스냅샷 참조를 잡은 요청은 그 참조로
끝까지 간다(G1).

정렬 배열을 메모리에서 부분 수정하는 경로는 두지 않았다. 그 순간 "스냅샷은 어느 한 시점의
완결된 것"이라는 G1이 깨지고, 적용할 기준 배열이 어느 시점의 것인지를 따로 관리해야 한다.
순서에 영향을 주는 변경은 리빌드가 통째로 다시 읽는다. 폴 간격 안의 변경은 한 번에 묶인다.
관리자가 장소 열 건을 연달아 고쳐도 서버마다 리빌드는 한 번이다.

관리자 수정의 표시값만 예외다. 커밋 직후 그 서버가 손댄 장소의 표시값을 새 트랜잭션에서
다시 읽어 홀더에 바로 적용한다. 패치에 기록하는 번호는 값을 읽은 트랜잭션이 관측한 번호다.
리빌드가 관리자 커밋보다 앞선 시점을 읽고 있었을 수 있으므로, 적용한 패치는 번호와 함께
보관했다가 리빌드가 새 표시값 맵으로 홀더를 교체하기 **전에** 그 위에 미리 적용한다. 순서를 반대로 하면 조회가
락을 잡지 않으므로 그 사이에 옛 표시값이 보인다. 패치는 설치한 번호를 올리지 않는다. 올리면
그 번호까지의 리빌드가 전부 "이미 설치했다"로 막히는데, 그 사이 번호에는 표시값이 아닌
변경이 섞여 있다. 패치가 실패해도 던지지 않는다. 다음 리빌드가 원본에서 가져오므로 손실이
아니라 지연이다.

### 7.5 요청은 어느 회차로 답하는가 (G2, G5, G9)

메모리 목록을 쓰는 요청은 예외 없이 `cursor_version` 한 행을 DB에서 읽는다. "로컬과 커서가
맞으면 건너뛰자"는 최적화는 정확히 틀린 경우를 놓친다. 이 서버가 뒤처져 있고 커서도 그만큼
낡은 경우 둘이 서로 맞으므로, 옛 회차를 최신이라 말하며 서빙한다.

```text
목록 요청
  → 동네·태그·정렬·필터·커서 형식 검증                           ← 대기보다 먼저
  → 공유 cursor_version = shared, 이 서버의 설치 회차 = mine

첫 페이지
  ├── mine >= shared → 지금 스냅샷으로 응답
  └── mine <  shared → shared 설치를 기다렸다가 로컬 스냅샷으로 응답

커서가 있는 요청 (커서의 회차 = wanted)
  ├── wanted != shared → 400 만료. 뒤처졌으면 리빌드는 시작해 두되 기다리지 않는다
  ├── mine == shared   → 지금 스냅샷으로 응답
  ├── mine >  shared   → 400 만료. 번호를 읽은 뒤 이 서버가 더 나아갔다
  └── mine <  shared   → shared 설치를 기다렸다가 로컬 스냅샷으로 응답
```

검증이 대기보다 먼저인 이유는, 잘못된 요청이 예산을 다 쓰고 503으로 나가면 클라이언트가
고칠 곳을 잘못 짚기 때문이다. 요청 판정은 `cursor_version`만 본다. 공유 회차와 로컬 회차가
같으면 `revision`이 달라도 기다리지 않는다. 표시값이나 소속이 조금 낡았을 수 있지만, 그것을
요청이 기다려서 보완하는 순간 모든 첫 페이지가 리빌드를 기다리게 된다. 반영은 폴이 맡는다(G4).

기다리는 요청은 대기표를 하나 등록하고, 읽은 번호를 목표로 리빌드를 부른다. 대기표는 설치된
`cursor_version`이 목표 이상일 때만 깨어나고, 깨어난 요청은 번호를 다시 읽지 않는다. 목표가
설치됐다는 것이 깨어난 조건 자체라 확인할 것이 없다. 요청 하나가 내는 번호 조회는 언제나 한
번이고, 규칙은 둘뿐이다. 목표가 설치되면 답하고, 예산 3초를 넘기면 503이다. 재판정 루프도 그
횟수 상한도 없다. 서블릿 비동기 응답이라 기다리는 동안 요청 스레드도 DB 커넥션도 잡지
않는다. 503을 받은 클라이언트는 같은 커서로 다시 시도하면 된다.

### 7.6 같은 시점을 목표로 하는 리빌드는 하나만 (G6)

리빌드를 호출하는 곳은 기동·폴·목록 요청 셋이고, 셋 다 같은 진입점을 거친다. 진입점에는 지금
실행 중인 리빌드 목록이 있고, 호출하는 쪽은 방금 DB에서 읽은 번호를 목표로 가져온다.

```text
리빌드를 호출한다 (목표 = 방금 읽은 번호)
  → 실행 중인 리빌드를 확인한다
  ├── 읽은 번호가 아직 비어 있는 것이 있다      → 거기 합류한다
  ├── 읽은 번호가 내 목표보다 낡지 않은 것이 있다 → 거기 합류한다
  └── 둘 다 없다                              → 하나 더 시작한다
```

읽은 번호가 비어 있는데도 합류해도 되는 근거는 read view다. 그 리빌드의 첫 SELECT는 내가
DB를 읽은 뒤에 도니, 내가 본 최신을 반드시 담는다. 로더는 첫 SELECT 직후, 원본을 읽기
전에 읽은 번호를 알려 준다. 하나 더 시작하는 경우는 실행 중인 것들이 전부 내 목표보다 앞선 시점을
읽고 있을 때뿐이다. 그래서 동시에 도는 리빌드 수의 상한은 "리빌드 한 번 도는 동안 커밋된
서로 다른 버전의 수"이고 요청 수와 무관하다. 캐시 미스에 요청 수백 개가 몰려도 전량 읽기는
첫 하나다.

실행기는 스레드 둘 고정이다. 셋 이상이 겹치는 일은 드물지만, 겹치면 힙 압박은 확실하기
때문이다(8.4절의 리빌드 한 번 250MB 할당). 셋째는 대기열에서 앞의 것을 기다리고, 그동안
오는 쪽은 읽은 번호가 비어 있는 그 셋째에 전부 합류하므로 대기열 길이는 규칙상 최대 1이다.
여러 리빌드가 병렬로 끝나도 설치자가 설치된 것보다 새로운 결과만 채택하므로 스냅샷이
역행하지 않는다.

### 7.7 기동 (G8)

포트를 열기 전에 부르는 스레드에서 동기로 첫 리빌드를 한다. 실패하면 폴 간격만큼 쉬고 다시
시도하고, 60초 안에 성공하지 못하면 컨텍스트 기동이 실패한다. 스냅샷을 만들지 못한 서버는 트래픽을 한
건도 받지 않는다. 신규 서버는 남을 기다리지 않는다. 기다릴 대상은 DB가 응답하는 것뿐이다.

## 8. 두 해법을 같은 자로 쟀다

### 8.1 목표 피크

세 구성을 같은 시나리오·같은 부하 지점(도착 300/s)으로 쟀다. 인메모리 열은 DB 정렬 두
구성과 다른 날의 측정이다. 두 창 모두에서 재진 동일한 대조 구성이 있어 눈금을 댈 수 있는데
나중 창이 더 후하게 나왔고(같은 구성의 요청당 앱 CPU 2.56 → 2.29ms), 인메모리 구성은 문장
캐시가 없던 시절의 측정이라 지금 형상에서는 이보다 좋다. 둘 다 인메모리의 격차를 실제보다
작게 읽는 방향이라 표의 격차는 하한으로 읽는다.

| 목표 피크 (전환 포함 90초) | DB 정렬 (캐시 없음) | DB 정렬 + 문장 캐시 | **인메모리 정렬** |
|---|---:|---:|---:|
| 앱 CPU 평균 (2 vCPU 쿼터 대비) | 75.5% | 64.1% | **43.2%** |
| DB CPU 평균 | 56.7% | 45.6% | **19.2%** |
| 앱 스로틀 발생 주기 / 누적 | 21.6% / 60.5초 | 1.4% / 0.9초 | **0.46% / 0.3초** |
| DB 스로틀 | 0.57% | 0% | **0%** |
| 전환 버킷 p50 / p95 | 92.8 / 340ms | 5.0 / 63.4ms | **3.0 / 4.0ms** |
| 피크 버킷 p50 | 5.0ms | 4.0ms | **3.0ms** |
| Hikari 커넥션 대기 최대 | (미수집) | (미수집) | **0** |
| 요청당 SQL 문장 수 | 10 | 10 | **7** |
| 오류 | 0 | 0 | 0 |
| 운영 안전 기준 통과 | 1/4 | 1/4 | **4/4** |

급증 전환조차 안착 구간과 구분되지 않았다(전환 버킷 3.0ms). 운영 안전 기준을 문면 그대로
통과한 것은 인메모리뿐이다.

### 8.2 요청당 비용

| 요청당 CPU (피크) | DB 정렬 (캐시 없음) | DB 정렬 + 문장 캐시 | **인메모리 정렬** |
|---|---:|---:|---:|
| 앱 | 2.54ms | 2.17ms (−15%) | **1.44ms (−43%)** |
| DB | 1.91ms | 1.54ms (−19%) | **0.64ms (−66%)** |
| 합 | 4.44ms | 3.70ms (−17%) | **2.08ms (−53%)** |
| 앱 축 산술 상한 (2,000ms/s ÷ 단가) | 789 req/s | 924 req/s | **1,389 req/s** |

요청당 단가는 부하량과 무관한 값이라 쿼터 환경 밖에서도 처리 여유의 산술적 기반이 된다.
산술 상한은 실제 최대 처리량이 아니라 같은 CPU 쿼터에서 확보한 여유를 비교하는 참고치다.

문장 수 10 → 10 → 7이 원인 지표다. 문장 캐시는 문장을 싸게 만들 뿐 수를 줄이지 못하고,
인메모리 전환이 엔티티 조립 2문장과 정렬 쿼리 1문장을 지운다. 사라진 정렬 문장은 평균보다
훨씬 무거운 문장이었다. 브랜치가 11행에서 멈추도록 다듬은 `UNION ALL` 문장조차 다중 동네
1회 실행에 214행(태그 없는 첫 페이지, 필터가 빡빡하면 1,800행대)을 읽는데, 인메모리 구조가
요청 전체에서 DB에 읽히는 행은 16.8행(행정구역 확장 12행 + 북마크 여부 5행)이다.

### 8.3 "정렬을 앱으로 가져오면 앱 CPU를 내주는 것 아닌가"

이 직관은 JFR로 검증했다. 정렬 이관의 몫만 떼기 위해 엔티티 조립은 양쪽 다 같게 두고 정렬만
DB/메모리로 가른 두 구성을 피크에서 대조했다.

| 정렬만 가른 프로파일 대조 (피크, 물리 코어 환산) | |
|---|---:|
| 사라진 것 — JDBC 드라이버·커넥션풀·Hibernate 결과 처리 | −32.4%코어 (감소분의 91%) |
| 새로 생긴 것 — 사전 정렬 배열 탐색·병합·거리 계산 | **+1.5%코어 (감소분의 4.3%)** |

쿼리를 던지고 결과 바이트를 객체로 조립하는 왕복 비용이, 이미 정렬돼 있는 배열을 탐색하는
비용보다 훨씬 컸다. 이 규모에서 정렬 이관은 앱을 내주고 DB를 사는 교환이 아니라 **양쪽에서
일을 지우는 선택**이다.

### 8.4 할당과 GC, 스냅샷 교체, 리빌드 비용

위 비교는 관측자 효과를 줄이기 위해 GC 이벤트를 기록하지 않았다. 남은 질문에 별도 캠페인으로
답했다. 캐시 없는 DB 정렬과 인메모리를 같은 90초 피크 창에서 각 3라운드씩 재고, JFR에는 GC
이벤트와 스레드 할당 통계만 넣었다. 계측이 결과를 바꾸지 않았는지는 비계측 라운드 대조로
가뒀다(요청당 앱 CPU 차이 +9.50% / −0.91%, 사전 기준 ±15% 안).

**요청당 할당은 절반이 됐다.**

| 지표 | DB 정렬 (캐시 없음) | 인메모리 정렬 | 변화 |
|---|---:|---:|---:|
| 요청당 힙 할당 | 1,537.6KB | 748.5KB | −51% |
| 할당 속도 | 845.9MB/s | 427.9MB/s | −49% |

앱 정렬은 새 객체(거리 계산 후보·정렬 후보·확정 결과)를 만들지만 전체 할당의 약 3.0~3.4%로
절감을 뒤집지 않았다.

**GC는 줄었지만 원래부터 주된 병목이 아니었다.** 판정은 서비스가 멈춘 시간과 CPU에 직접
연결되는 두 지표로 했다.

| 지표 | DB 정렬 (캐시 없음) | 인메모리 정렬 |
|---|---:|---:|
| GC pause 합 (피크 창 대비) | 395.1ms (0.44%) | 224.9ms (0.25%) |
| 최대 GC pause | 29.8ms | 17.6ms |
| GC 스레드 CPU (2 vCPU 쿼터 대비) | 0.306% | 0.200% |
| 승격 속도 | 0.13MB/s | 0.09MB/s |
| GC 전 / 후 평균 힙 | 724 / 105MB | 644 / 89MB |

인메모리에서 둘 다 낮아졌지만 DB 정렬 쪽 값도 이미 작았다. **CPU 여유 개선의 주된 원인을
GC 감소로 해석하지 않는다.** 주요 변화는 매 요청 반복하던 DB/JDBC/Hibernate 처리를 지운 데서
났고, 할당 감소는 그 노동이 사라진 증상이다. 상주 스냅샷이 old 영역 부담을 키운 흔적도
없었다(승격 속도와 GC 후 힙 모두 인메모리 쪽이 낮음). 다만 90초 로컬 벤치라 장시간 운영의
힙 증가·누수까지 검증한 것은 아니다.

**스냅샷 통째 교체를 피크에 겹쳤다.** 교체가 피크 90초 창 한가운데 실행되도록 맞춘 두
라운드 모두 교체 버킷은 p50 2ms·p95 4ms·오류 0이었다. 교체 직후 young GC pause는 한 라운드
4.2ms, 다른 라운드 41.6ms로 갈려 재현되지 않았으므로 교체의 GC 정지가 항상 작다고 결론
내리지 않는다.

**리빌드 한 번의 비용은 10배 규모에서 쟀다.** 63,200 장소, 2 vCPU / Xmx 1,280MB, 무부하,
15회 실행.

| 항목 | 값 |
|---|---:|
| 리빌드 소요 중앙값 (읽기·조립·정렬·설치 합) | 185ms (범위 173~215) |
| CPU 시간 | 0.246초 |
| 리빌드 구간의 JVM CPU 최대 (200ms 표본) | 0.9~1.1 core (2 vCPU의 45~55%) |
| CFS 쿼터를 채운 실행 | 0 / 15 |
| 창 안 Full GC | 0 / 15 |
| 창 안 Young GC | 3 / 15 (정지 30.1~37.3ms) |
| 리빌드 스레드 할당 | 250.3~253.2MB |
| 스냅샷 한 벌의 몫 | 8.93MB |
| Full GC 직후 live heap | 96.5~97.8MB (Xmx의 7.5~7.6%) |

리빌드 한 번이 250MB를 할당하지만 살아남는 것은 스냅샷 한 벌 8.93MB다. 나머지는 중간
결과이고 Young GC가 회수한다. 실행기를 둘로 묶은 근거가 이 산수다. 둘이면 한 창의 할당이 약
500MB, 셋이면 약 750MB이고, Xmx 1,280MB에서 셋은 여유를 말할 수 없는 자리다. 이 수치는
무부하 측정이라 사용자 요청이 함께 도는 동안의 여유를 말하지 않는다. 그 한계와 대안은
[규모 문서](2026-09-16-place-list-scale-readiness.md)에 있다.

## 9. 최종 구조와 확장 방향

```text
쓰기      RDBMS가 정본. 변경 트랜잭션이 번호를 함께 올린다
조회      각 서버의 인메모리 스냅샷에서 정렬·필터·페이징. 표시값은 홀더
갱신      번호를 보고 각 서버가 전량 리빌드. 관리자 표시값은 즉시 패치
DB 경로   요청 흐름에는 연결하지 않는다. 코드와 등가 테스트(스냅샷 경로와 응답·커서 대조)로만
          남겨, 스냅샷 경로가 낸 답이 DB가 낸 답과 같다는 것을 계속 묻는 기준으로 쓴다
문장 캐시 네 줄은 남은 DB 문장(동네 검증·번호·북마크 여부)과 폴백 재배선 시를 위해 그대로 둔다
```

처음 구조(캐시 없는 DB 정렬)와 최종 구조를 놓으면 요청당 CPU 합계 4.44 → 2.08ms, 앱·DB
사용률 75.5%/56.7% → 43.2%/19.2%, 스로틀 21.6% → 0.46%, 요청당 문장 10 → 7이다. 이
감소에는 엔티티 조립 제거와 정렬 이관 두 몫이 함께 있고, 몫의 경계는 프로파일(감소분의
91%가 JDBC·ORM)과 문장 수 산술이 긋는다.

설계를 마치고 보니 이 구조는 알려진 패턴에 해당했다. 쓰기는 RDBMS가 정본이고, 조회 축만 미리
계산된 읽기 모델이 담당한다. 조회와 명령의 책임 분리, CQRS다. 다만 Redis 같은 외부 저장소
없이 인프로세스 배열과 참조 교체로 같은 계약을 얻었다. 목표가 패턴 적용이 아니라 "요청
시점의 반복 작업 제거"였기 때문에 패턴은 결과로 따라왔다.

1.3절의 확장 비용 요구사항은 이렇게 답한다. 정렬 기준이 하나 더 늘면 인덱스와 실행 계획
검증이 아니라 **사전 정렬 배열이 하나** 는다. 필터가 늘면 비트 하나가 는다. "영업 중"처럼
시각에 따라 변하는 조건이 들어와도 검색 엔진을 도입하는 것이 아니라 같은 구조로 처리한다. 서버가
늘 때, 데이터가 늘 때, 트래픽이 늘 때의 대비는 [규모 문서](2026-09-16-place-list-scale-readiness.md)에
정리했다.

## 10. 측정 방법과 이 기록이 말할 수 없는 것

- 판정 라운드는 구성별 1회다. 스로틀 비율은 이 호스트에서 라운드 간 흔들림이 실측돼 있으므로
  개별 수치는 "이 기준을 충족하는 라운드가 실재한다"의 증명으로 읽는다.
- 8.1절의 인메모리 열은 DB 정렬 두 구성과 다른 날의 측정이다(방향은 한정됨). 칸 사이 1할
  미만의 차이는 이 표로 판정하지 않는다.
- GC·할당 대조(08-28)와 DB 정렬 두 구성의 대조(08-29)는 서로 다른 창이라 절대값을 한 표에
  섞지 않았다.
- p99는 기록만 하고 판정에 쓰지 않았다. 재현성이 증명된 적이 없다.
- 문장 텍스트 비용의 몫(재파싱 6.8%·전송 5.6%)은 부하 판정과 다른 날의 채집이라 비중으로만
  말한다.
- 리빌드 x10 수치는 무부하 측정이고, 현재 코드로 다시 잰 값은 아니다.
- 각 요소의 기여도를 독립적인 A/B로 분리해 측정하지 않았으므로 전체 감소분을 특정 구현
  하나의 효과로 귀속하지 않는다.
