# 2026-08-17 · 북마크 증분 집계 검토 — 소프트 딜리트 반려, 아웃박스 델타는 초안으로

> 행 수"였고, 같은 날 이어진 검토에서 **트리거를 기다리지 않는 조기 채택**으로 바뀌었다(8장).

## 1. 출발점 — 두 갈래 구상

세션은 두 구상으로 시작했다.

1. 북마크 등록/삭제를 행 생성·삭제 대신 **상태 변경(소프트 딜리트)** 으로 바꾼다.
2. 매시 카운트 배치가 **어느 규모부터 버퍼풀 문제를 일으키는지** 재고, 배치를 더 효율적으로
   처리할 방법을 찾는다. 새벽 1회인 점수 배치와 달리 카운트 배치는 실서비스가 활발한
   시간에 돌기 때문이다.

검토가 끝났을 때 1은 반려됐고, 2는 형태를 바꿔 살아남았다. 그 과정을 순서대로 남긴다.

## 2. 소프트 딜리트의 동기를 좁히다

동기 후보는 넷이었다 — 재등록 churn 감소, 증분 집계의 발판, 이력 보존, 프로젝트 컨벤션
일관성. 확정된 동기는 **증분 집계의 발판** 하나다. 하드 DELETE는 행이 사라져 "지난 1시간
동안 무엇이 바뀌었나"를 추적할 수 없으니, 모든 상태 변화를 UPDATE로 남겨 매시 전량 스캔을
변경분 스캔으로 바꾸자는 구상이다.

곁들였던 근거 하나는 검토에서 기각됐다. **"삭제 연산이 더 비싸다"는 이 설계에서 성립하지
않는다.** InnoDB의 DELETE는 delete-mark 후 purge가 지우는 지연 삭제고, UPDATE도 언두 기록과
구버전 purge를 치른다. 차이는 UPDATE가 인덱스에 안 걸린 컬럼만 건드릴 때 세컨더리 인덱스
유지비가 빠지는 것뿐인데, 배치 필터를 위해 `is_deleted`를 인덱스에 넣는 순간 토글 UPDATE도
세컨더리 인덱스에서 delete-mark + insert를 치러 같아진다.

그리고 처음부터 걸려 있던 구조적 긴장이 있었다. 소프트 딜리트는 행을 지우지 않으므로
`bookmarks` 행 수가 **단조 증가**하는데, 배치 비용은 스캔 행 수에 선형이고(08-15 문서 5-1)
버퍼풀 우려도 인덱스 크기가 분모다. **구상 1이 구상 2의 문제를 앞당기는 셈이었다.** 이
대가를 치를 명분은 증분 집계 하나뿐이었고, 그래서 다음 질문이 그 명분을 검증하는 자리가 됐다.

## 3. 델타는 소프트 딜리트 위에서 계산되지 않는다

증분의 형태를 둘로 갈라 검토했다.

**변경 장소만 재계산하는 안**은 계산은 성립하지만 절감이 얇다. 서비스 특성상 북마크가 몇몇
장소에 몰리고(Zipf), 그 인기 장소들은 거의 매시 변경이 있을 텐데 행 질량의 대부분을 그들이
쥐고 있다. "변경 장소만"의 절감폭은 변경 장소 수가 아니라 **변경 장소들이 가진 행 수 합**이
정하므로, 몰림이 심할수록 전량 스캔과의 차이가 사라진다.

**델타 적용(±를 더하는 안)** 은 절감은 크지만, 소프트 딜리트 위에서는 **아예 계산이 안 된다.**
델타는 정의상 `f(지금 상태) − f(지난 워터마크 시점 상태)`인데, 소프트 딜리트는 마지막 상태만
남기는 스키마라 워터마크 시점의 상태가 어디에도 없다. `created_at ≤ W`이고 지금
`is_deleted=1`, `updated_at > W`인 행을 보자 — 워터마크 시점에 활성이었다가 꺼진 건지(δ=−1),
이미 꺼져 있었는데 켜졌다 다시 꺼진 건지(δ=0) 구분할 수 없다. 토글 이력이 마지막 상태에
뭉개져 사라졌기 때문이다.

델타의 올바른 기반은 **append-only 이벤트 로그**다 — 토글 한 번이 행 하나로 남아야 ±가
세어진다. 그리고 이 결론이 소프트 딜리트의 유일한 동기를 걷어 간다. 변경 추적을 이벤트
테이블이 맡으면 `bookmarks`는 지금처럼 하드 DELETE로 두면 된다 — 유니크 제약, 내 북마크
목록, `isBookmarked`, 새벽 점수 배치(행별 `created_at` 감쇠 합)까지 전부 무변경이고, 행 수
단조 증가라는 대가도 치르지 않는다.

**판정 — 소프트 딜리트는 반려한다.** 동기였던 증분 집계는 아웃박스가 맡고, 그쪽이 원본을
건드리지 않으면서 더 정확하다.

## 4. 아웃박스 델타 — 설계 초안

지금 구현하지 않는다(5장). 트리거가 당겨졌을 때 꺼낼 초안으로만 남긴다.

### 4-1. 테이블과 쓰기 경로

```sql
CREATE TABLE bookmark_count_events (
    id          BIGINT AUTO_INCREMENT PRIMARY KEY,
    target_type VARCHAR(30) NOT NULL,
    target_id   BIGINT NOT NULL,
    delta       TINYINT NOT NULL,        -- +1 / -1
    created_at  DATETIME NOT NULL
);
```

보조 인덱스는 두지 않는다 — 배치가 전체를 읽고 지우므로 PK면 족하고, 인덱스가 없어야 쓰기
경로에 얹는 비용이 진짜로 INSERT 하나다. 테이블은 늘 "마지막 소비 이후 토글"만 들고 있어
작다. COURSE 이벤트는 내지 않는다 — 코스는 카운트를 노출하지 않는다.

쓰기 경로는 북마크 변경과 **같은 트랜잭션**에서 이벤트를 남긴다. 둘 다 남거나 둘 다 안
남는다.

- `create`: `saveAndFlush` 성공 뒤 `+1`. 409로 튕긴 경로는 이벤트를 내지 않는다 — 유니크
  제약이 "실제 INSERT 1건 = +1 이벤트 1건"을 보장한다.
- `delete`: **DELETE의 영향 행 수가 1일 때만** `−1`. exists 검사 결과에 걸면 안 된다 —
  동시 삭제 둘이 검사를 함께 통과해도 행을 지운 쪽은 하나이므로, 영향 행 수에 걸어야 −1이
  두 번 쌓이는 표류가 원천 차단된다.

### 4-2. 배치 — 읽고, 접고, 더하고, 읽은 것만 지운다

> **2026-09-12 갱신:** 아래 1·2단계가 "표식을 찍고 DB가 접는다"로 바뀌었다
> ([아웃박스 DB 집계](2026-09-12-stats-commit-snapshot-and-db-delta.md)). 트랜잭션 경계,
> 순서 계약, 범위 삭제 금지, 4-4의 표류 방어 3겹은 그대로다 — 갈린 것은 접는 자리가
> JVM이냐 DB냐 하나다.

```
한 트랜잭션에서:
  1. 소비할 이벤트를 읽는다 (id 목록 확보)
  2. 장소별 SUM(delta)로 접는다
  3. UPDATE place_stats SET bookmark_count = GREATEST(0, bookmark_count + n) WHERE place_id = …
  4. 1에서 읽은 id들만 DELETE
커밋 → 정렬 스냅샷 재빌드 훅 (기존 그대로. 이벤트 0건이면 회차 전체가 no-op)
```

적용과 삭제가 한 트랜잭션이라 exactly-once가 트랜잭션으로 성립한다 — 중간에 죽으면 이벤트가
남아 다음 회차가 그대로 소비하고, 이중 적용도 유실도 없다. 회차를 놓치면 쌓였다가 한 번에
소비될 뿐이다.

**함정 1 — 워터마크를 `id <= MAX(id)`로 잡으면 안 된다.** auto_increment는 커밋 순서를
보장하지 않으므로, MAX(id)를 읽는 순간 그보다 작은 id의 이벤트가 아직 커밋 전일 수 있다.
RC 읽기는 그 행을 집계에서 빠뜨리는데 범위 DELETE는 커밋을 기다렸다가 지운다 — **적용 안 된
이벤트가 소비되는 유실**이다. 그래서 4단계는 범위 조건이 아니라 읽은 id 목록으로만 지운다.
늦게 커밋된 이벤트는 다음 회차 몫으로 남는다.

**함정 2 — 안전망 전량 재계산과의 이중 적용.** 전량 재계산이 시각 T의 원본을 세어 카운트를
덮었는데 아웃박스에 T 이전 이벤트가 미소비로 남아 있으면, 다음 델타 회차가 이미 셈에 들어간
토글을 또 더한다. 그래서 안전망 회차는 **재계산과 함께, 자기가 읽은 시점까지의 아웃박스를
같은 트랜잭션에서 비워야 한다.**

### 4-3. 실시간 증분과 무엇이 다른가 — 덧셈의 시점과 주체

"증분"이라는 말이 같아 헷갈리는 자리라 남긴다. 실시간 증분(카운터 컬럼 UPDATE든 Redis
INCR이든)은 **요청 시점에 공유 카운터를 고친다** — 인기 장소의 동시 북마크들이 카운터라는
공유 지점 앞에 줄을 선다. DB 증분이면 핫 로우 X 락 경합이고, Redis면 락은 없지만 DB 커밋과
INCR이 다른 시스템의 두 연산이라 원자성을 잃는다. 이 프로젝트가 08-15 문서 6-2에서 의도적으로
걷어낸 구조다.

아웃박스는 요청 시점에 아무 공유 지점도 건드리지 않는다. 토글은 append-only 테이블에 자기만의
새 행을 남길 뿐이라 같은 장소에 백 명이 동시에 북마크해도 서로 기다리지 않고, 덧셈 — 경합이
생길 수 있는 유일한 연산 — 은 배치라는 **단일 쓰기 주체**가 회차마다 한 번 수행한다.
`bookmark_count`를 고치는 손이 하나뿐이니 카운터의 동시성 문제가 성립할 여지가 없다. 이벤트가
북마크와 같은 DB, 같은 트랜잭션이라 원자성도 잃지 않는다. 요컨대 프로젝트의 기존 철학 —
신선도를 늦추는 대가로 쓰기 경합을 없앤다 — 그대로이고, 지연 창만 1시간에서 회차 간격으로
줄인다.

남는 동시성 지점은 셋이고 셋 다 답이 있다. 동시 이벤트 INSERT끼리는 append-only라 경합이
없고, 배치 도중의 신규 INSERT는 "읽은 id만 지운다"가 처리하고, 배치 중복 실행은 ShedLock이
이미 막는다(원하면 이벤트 읽기를 `FOR UPDATE`로 한 겹 더).

### 4-4. 표류 방어 3겹과 기존 배치의 자리

| 겹 | 자리 | 막는 것 |
|---|---|---|
| 영향 행 수 기반 발행 | 쓰기 경로 | 동시 요청의 이중 이벤트 |
| 트랜잭션 소비 (적용+삭제) | 델타 배치 | 이중 적용·유실 |
| 새벽 전량 재계산 + 아웃박스 비우기 | 안전망 | 버그로 생긴 표류의 상한을 하루로 |

기존 `recalculateCounts`는 지워지는 게 아니라 **매시에서 새벽 1회 안전망으로 강등**된다 —
어차피 새벽 1시에 점수 배치가 `bookmarks`를 전량 스캔하는 창이 있으니 거기 얹으면 된다.
매시 자리는 델타 배치가 대신하는데, 비용이 총 행 수가 아니라 시간당 토글 수에 붙으므로
**회차를 매시에서 5분 단위로 당길 수도 있다.** 스냅샷 채택(#389) 이후 카운트 신선도의 병목이
정확히 배치 주기이므로, 델타의 값어치에는 해악 감소만이 아니라 신선도 개선도 들어간다.

## 5. 왜 지금이 아닌가 — 저울

저울의 비대칭이 판정을 정한다. **델타의 비용은 규모에 거의 상수다** — 테이블 하나, 배치
재작성, 쓰기당 INSERT 하나, 그리고 복잡도. **전량 재계산의 비용은 행 수에 선형으로 자란다.**
그러니 물을 것은 지금 시점의 절대값 비교가 아니라 "전량 재계산이 언제부터 아프기 시작하고,
거기 실제로 도달하는가"다.

지금은 아프지 않다. 순수 UPDATE 형상의 카운트 배치가 1,040만 행에서
3,514ms인데([2026-08-15 실측](../perf/2026-08-15-count-batch-duration-lock.md)), 그
1,040만조차 부하 테스트용 합성 시드이고 실서비스는 한참 아래다.

여기에 #388/#389가 저울을 한 번 더 눌렀다. 인메모리 정렬 스냅샷이 채택되면서
(`sort-source=memory`, PR #390) **사용자 읽기 경로가 `place_stats`를 더는 읽지 않는다.**
카운트 공급 사슬은 `bookmarks` → 매시 배치 → `place_stats` → 스냅샷 재빌드(6,320행,
94~302ms) → 메모리로 완결됐고, 배치 소요는 사용자 지연이 아니라 신선도 지연으로만 나타난다.
배치와 같은 시간에 DB를 쓰는 트래픽은 북마크 쓰기, `isBookmarked` 포인트 조회, 상세,
마이페이지 정도로 좁아졌다.

다만 이것이 측정 무용론은 아니다 — **DB는 목록 기능만의 것이 아니므로, 배치가 공유
자원(디스크·코어)에서 빼 가는 세금은 전경이 누구든 존재한다.** 이 관점이 아래 측정 계획을
두 층으로 가른 이유다.

## 6. 측정 계획 — 두 층

판정 변수 합의가 먼저 있었다. **배치 소요시간 단독으로는 "문제다"를 판정할 수 없다** —
배치는 백그라운드라 30초가 걸려도 사용자가 안 아프면 문제가 아니고, 5초라도 사용자 p99를
흔들면 문제다. 주 판정 변수는 배치가 도는 동안의 사용자 경로 p99 악화이고, 소요시간·히트율은
해석용 보조다. **반대 결과 — 어느 풀 크기에서도 안 아프다 — 가 나오면 "전량 재계산은 수년치
성장을 버틴다"로 받아들이기로 했다.**

배치가 사용자 경로를 건드리는 채널도 정리해 뒀다.

| 채널 | 크기 | 근거 |
|---|---|---|
| 디스크 IO 경합 | 인덱스가 풀을 넘는 순간부터 지배적 | 배치의 물리 읽기가 사용자 캐시 미스와 IOPS 예산을 다툰다. 보호 장치 없는 공유 자원 |
| 버퍼풀 오염 | 상한 있음 | 풀스캔 페이지는 LRU 미드포인트(old sublist, 기본 37%)로 들어가 young의 핫 셋을 통째로 밀지 못한다. 실제 크기는 실측 대상 |
| CPU | 한 코어 상한 | MySQL은 문장 하나가 싱글 스레드. 크기는 코드가 아니라 인스턴스 스펙이 정한다 |
| 락 | 사용자 영향 없음 | 사용자는 `place_stats`를 읽기만 하고 읽기는 MVCC라 락을 안 기다린다. 소스 스캔 락은 RC가 막는다 |
| purge 지연 | 지금은 무시, 성장 시 동반 증가 | 배치 리드 뷰가 언두 정리를 막는 시간 = 배치 소요 |

### 6-1. 1층 — 배치의 자원 프로파일 (전경 무관, 먼저 돌린다)

데이터를 100배 키우는 대신 **버퍼풀을 1/K로 줄여 같은 히트율 상태를 만든다** — 시드 생성
비용이 없고 다른 변수가 안 섞인다. 사다리는 2G(기준선 3,514ms) → 512M → 256M → 128M → 64M,
각 단에서 배치 단독 소요·물리 읽기(`innodb_data_reads` 델타)·히트율을 채취한다
(`metrics-snapshot.sh`가 이미 뽑는 지표들). 선행 조건은 `idx_bookmark_target` 실측 크기다 —
행당 바이트가 나와야 풀 크기 ↔ 행 수 환산이 산수가 된다.

여기서 나오는 핵심은 **국면 전환점**이다 — 어느 인덱스/풀 비율부터 배치가 CPU 국면에서 IO
국면으로 넘어가고, IO 국면에서 초당 몇 페이지를 디스크에 요구하는가. 전경 믹스와 무관한
물리량이라 읽기 경로 형상이 바뀌어도 낡지 않는다.

**축소 모사의 한계도 미리 적는다.** 버퍼풀 축소는 행 수를 고정하므로 행당 비용 악화만 잰다.
실제 성장은 총 소요 = 행 수 × 행당 비용으로 두 인자가 곱해지고 인덱스 트리 깊이도 한 단 늘
수 있으므로, 여기서 나오는 투영은 하한이다. 특히 **교란의 강도는 모사되지만 교란의 지속
시간은 K배로 늘어난다** — 보고는 "악화 폭"(실측)과 "지속 시간"(행 수 선형 투영)의 두 축으로
가른다.

### 6-2. 2층 — 간섭 측정 (전경 의존, 필요 시)

1층의 IO 수요를 "사용자가 얼마나 아픈가"로 번역하는 층. 전경 부하는 채택된 MEMORY 모드의
트래픽 믹스여야 한다 — DB 모드 믹스로 재면 없어진 세계를 재는 셈이다. 설계는 풀 크기마다
대조군을 둔다:

```
각 풀 크기에서: 워밍업 → [대조: 전경만, p99] → [실험: 전경 + 배치, p99]
판정값 = 실험 − 대조    ← 배치에게만 귀속되는 악화분
```

같은 풀 크기 안에서 빼므로 "풀이 작아 전경 워킹셋 자체가 안 들어가는" 교란이 상쇄된다.
단, **1층 결과 + 인스턴스 IOPS 예산 산수로 결론이 명백하면 2층 실측은 생략할 수 있다.**

실행은 두 층 모두 `load-test` 스킬의 게이트(문제·가설·선택·주장·성공조건 사전 등록)를
통과한 뒤다.

## 7. 판정 (초판) — 현행 유지, 전환 트리거는 절대 행 수

> **이 판정은 8장 추기로 바뀌었다.** 본문은 당시의 근거를 남기기 위해 그대로 둔다.

**전량 재계산을 유지한다. 단, 유효기간이 아니라 트리거가 달린 판정이다.**

트리거를 "성장 K배"로 쓰지 않는 이유: 기준선 1,040만 행이 합성 시드라 분모가 부실하고,
실서비스 환산에 필요한 성장률 가정을 뒷받침할 실측이 없다. 대신 1층 측정이 주는 **절대 행
수**로 적는다.

- **N₁** — `idx_bookmark_target`이 운영 버퍼풀을 넘어 배치가 IO 국면에 들어가는 행 수
- **N₂** — 배치의 IO 수요가 인스턴스 IOPS 예산의 유의미한 몫을 먹기 시작하는 행 수

두 수치는 1층 측정 후 이 문서에 채워 넣는다. **북마크가 그 규모에 접근하면 4장의 아웃박스
델타로 전환한다** — 소프트 딜리트 없이, `bookmarks` 무변경으로 성립한다는 것이 이 문서가
미리 확인해 둔 바다.

트리거 전에 판정이 다시 열리는 조건은 둘이다.

1. **카운트 신선도가 제품 요구로 올 때** — "북마크 수가 바로 보여야 한다"가 오면, 배치 주기
   단축이 필요해지고 델타 없이는 주기를 못 당긴다 (4-4).
2. **어드민 대량 작업 등으로 배치와 겹치는 쓰기 프로파일이 바뀔 때.**

08-15 문서와의 관계를 마지막으로 적는다. 그 문서의 재개봉 조건 2("행 수가 크게 늘 때")가
가리키던 응답은 캐시 전환이었는데, 이 검토를 지나며 **응답이 아웃박스 델타로 바뀌었다.**
스냅샷 채택으로 사용자 읽기가 이미 메모리에서 공급되는 세계에서는, 행 수 성장이 아프게 하는
것이 읽기 경로가 아니라 배치 자신이고, 그 처방은 읽기를 캐시로 옮기는 것이 아니라 배치를
변경분 소비로 바꾸는 것이기 때문이다.

## 8. 추기 — 트리거를 기다리지 않고 채택한다

같은 날 이어진 검토에서 판정을 바꿨다. **4장의 아웃박스 델타를 조기 채택한다.** 결정의
출발은 성능이 아니라 설계 감각이었다 — "누적된 것을 매시 처음부터 다시 세는" 구조가
비효율로 느껴진다는 것. 그 감각을 그대로 근거로 쓰지 않고, 반대 근거 둘을 먼저 세워 밟았다.

### 8-1. 밟고 지나간 반대 근거 둘

**반대 1 — 전량 재계산은 이 코드베이스에서 비효율의 상징이 아니라 승자의 패턴이다.**
정렬 스냅샷(#389)은 변경분 갱신이 아니라 매번 전량을 다시 짓고(6,320행 94~302ms, 부분 갱신
진입점을 의도적으로 배제), `rebuildRowsFromSource`도 같은 사진-다시-찍기다. 그 단순함이
멱등성과 자기 복구를 공짜로 줬다. 즉 재세기는 입력이 작을 때 우월하고 입력이 클 때만
열등해지는 패턴이며, "설계적으로 낡은 방식"이라는 인상만으로 버릴 것이 아니다. — **인정한다.
그래서 이 채택의 근거에 "재세기는 나쁜 설계"를 쓰지 않는다.** 실제로 재세기는 버려지지 않고
새벽 안전망으로 남는다(4-4).

**반대 2 — "배치 성능 비교에서 이기면 채택"은 게이트가 될 수 없다.** 델타 배치는 시간당
토글 수를 읽고 전량 재계산은 천만 행을 읽는다. 비교하면 자릿수 차이로 델타가 이기고, 그
결과는 돌리기 전에 안다. 이길 수밖에 없는 측정은 채택의 근거가 아니라 이미 내린 결정의
포장이다. — **인정한다. 그래서 성능 비교를 채택의 게이트로 삼지 않는다.** 전후 측정은
채택 뒤 효과의 기록으로만 남긴다.

### 8-2. 그럼에도 당기는 근거

채택의 근거는 성능 승부가 아니라 **설계 판단**이다. 사는 것은 둘이다.

1. **배치 상시 비용의 성격 전환.** 활발한 시간대에 도는 작업의 비용이 "총 누적 행 수에
   선형"에서 "시간당 변경량에 선형"으로 바뀐다. 트리거 판정(7장)은 그 선형 성장이 아프기
   시작하는 지점을 기다리자는 것이었는데, 어차피 도달이 시간 문제라면(08-15 문서 5-1:
   "북마크는 서비스가 살아 있는 한 쌓인다") 지금 당기는 것은 시점 선택의 재량이다.
2. **신선도 여지.** 스냅샷 세계에서 카운트 신선도의 병목은 정확히 배치 주기이고, 델타 없이는
   주기를 못 당긴다. 회차를 5분 단위로 줄일 길이 열린다 — 지금 제품 요구는 아니지만, 요구가
   왔을 때 구조 변경 없이 설정으로 응답할 수 있게 된다.

치르는 것은 4장에 적힌 복잡도 전부다 — 테이블 하나, 쓰기 경로 결합, 함정 둘, 표류 방어
3겹. 이것을 "아무도 안 아픈 3.5초"와 바꾸는 거래라는 초판의 지적은 여전히 사실이고, 그
거래를 알고도 하는 것이 이 추기다.

### 8-3. 초판에서 무엇이 살고 무엇이 죽는가

- **1층 버퍼풀 측정(6-1)은 존재 이유를 잃는다.** 산출물이 전환 트리거 N₁·N₂였는데 전환을
  이미 결정했다. 매시 전량 스캔 자체가 사라지므로 "활발한 시간대 배치의 버퍼풀 임계"라는
  질문도 소멸한다 — 전량 스캔은 새벽 1시 안전망으로만 남고, 그 시각의 부하 프로파일은 다른
  문제다.
- **2층(6-2)도 함께 소멸한다.** 델타 배치의 간섭 표면은 시간당 이벤트 수백 행 읽기라 잴
  것이 없다.
- **측정으로 남는 것은 전후 기록이다** — 채택 전 매시 배치의 소요·읽기량과 채택 후 델타
  회차의 것. 게이트가 아니라 효과 문서화이며, `load-test` 게이트에는 그렇게 등록한다.
- **3장(소프트 딜리트 반려)과 4장(설계 초안)은 그대로 구현 스펙이 된다.** 6장의 간섭 채널
  정리는 새벽 안전망 회차를 볼 일이 생기면 재사용한다.

### 8-4. 구현에서 갈린 세부 (같은 날 구현, #391)

구현에 들어가서야 보인 것 셋을 기록한다.

**매시 회차는 북마크 축만이 아니었다.** 옛 매시 문장은 북마크 수·리뷰 수·평점 셋을 함께
재계산한다. 델타가 매시 자리를 통째로 대체하면 리뷰 축 신선도가 1시간에서 24시간으로
후퇴한다 — 설계 단계에서 놓친 회귀다. 리뷰 축은 실측 117ms(행 수 비 1.9%)로 아픈 축이
아니므로, 매시 회차를 **"리뷰 축 전량 재계산 + 북마크 축 델타 소비"** 둘로 구성했다.
전량 스캔에서 비용의 98%였던 북마크 축만 델타로 넘어간다.

> 이후 갱신 — **2026-09-12에 그 한 회차가 두 회차로 갈렸다.** 리뷰 축은 :30에 남고 북마크 델타
> 소비는 :15로 옮겼다. 두 축이 한 메서드 안에 순차로 있던 구성은 이 문단까지가 정본이고,
> 현재 동작은 [2026-09-12-stats-schedule-split.md](./2026-09-12-stats-schedule-split.md)를 본다.

**아웃박스를 비우는 규칙은 안전망만의 것이 아니다.** 원본에서 카운트를 다시 짓는
트랜잭션은 셋 있다 — 새벽 안전망, 기동 백필, 운영 복구(`rebuildRowsFromSource`). 함정 2의
이중 적용은 셋 모두에서 성립하므로, 규칙을 하나로 세웠다: **원본 재계산 트랜잭션은 자기가
읽은 시점까지의 아웃박스를 같은 트랜잭션에서 비운다.**

**안전망의 한계는 이중 적용 한 방향이 아니다.** 전표 읽기와 재계산이 다른 문장이라 그 사이에
커밋된 토글은 이중 반영되고(함정 2), 반대로 재계산 상한(`calculatedAt`) 뒤에 생긴 전표가
읽기에 잡혀 지워지면 유실된다. 두 방향 모두 창이 문장 사이 밀리초이고(회차 내 재시도 시
수 초), 새벽에 돌며, 다음 안전망이 지운다 — 쓰기를 막지 않고는 없앨 수 없어 수용한 한계로
코드 javadoc에 남겼다.
