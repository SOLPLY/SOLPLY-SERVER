# 장소 목록 조회 구조는 규모가 커질 때 무엇으로 버티는가 — 서버 수·데이터·트래픽

작성일: 2026-09-16 · 구현 기준: 2026-09-15

[개선 과정 문서](2026-09-16-place-list-read-path-story.md)는 장소 목록 조회가 지금의
인메모리 조회 모델에 이르기까지의 판단을 다뤘다. 이 글은 그 구조를 세 축으로 밀어 본다.
**서버가 여러 대일 때**, **데이터가 늘 때**, **트래픽이 늘 때**. 축마다 지금 구조가 무엇을
보장하는지, 어느 값까지 측정으로 확인했는지, 그 너머에서 어떤 대안을 어떤 순서로 적용할지를
적었다. 측정하지 않은 것은 측정하지 않았다고 썼다.

## 1. 서버가 여러 대일 때

### 1.1 공유하는 것은 번호 둘뿐이다

스냅샷의 내용은 서버끼리 주고받지 않는다. 각 서버가 MySQL 원본을 직접 읽어 자기 스냅샷을
만들고, MySQL이 서버들에게 공유하는 것은 "무엇이 바뀌었나"를 말하는 번호 둘뿐이다.

```text
MySQL place_list_snapshot_metadata (id = 1)
  cursor_version   진행 중인 스크롤을 끊어야 할 때만 오른다
  revision         목록에 실리는 무엇이든 바뀌면 오른다. cursor_version이 오를 때 0으로

서버 A ── 폴(1분) ──┐
서버 B ── 폴(1분) ──┼── 번호 한 행 읽기 → 자기 것보다 새것이면 원본 전량 읽어 자기 스냅샷
서버 C ── 폴(1분) ──┘
```

이 선택이 없애는 것과 남기는 것을 나눠 보면 이렇다.

| 없앤 것 | 남긴 것 |
|---|---|
| 스냅샷 payload의 저장·전송·복원 | 서버마다 원본 전량 읽기와 정렬 (n대면 n번) |
| 발행 포인터 경쟁, 소비자 소유권 같은 공유 기준 | 같은 번호 변경에 서버들이 몰려 읽을 때의 DB 부하 (미측정) |
| Redis 같은 추가 인프라와 그것의 장애 모드 | 서버별 수렴 시차 (1.3절) |

### 1.2 번호와 데이터가 어긋나지 않는 근거

**쓰기 쪽.** 번호를 올리는 UPDATE는 데이터를 고친 그 트랜잭션의 마지막 문장이다. 롤백되면
번호도 없던 일이 되고, 커밋되면 반드시 올라 있다. "데이터는 바뀌었는데 번호는 그대로"인
상태가 없으므로 어느 서버도 변경을 놓치지 않는다. DB가 현재 값을 읽어 더하는 한 문장이라
두 서버의 쓰기가 같은 값을 읽어 같은 값을 쓰는 유실도 없다.

**읽기 쪽.** 리빌드는 REPEATABLE READ 트랜잭션 하나에서 번호를 첫 문장으로 읽고 같은 read
view로 원본을 읽는다. 이 read view가 어떤 변경을 보았다면 그 변경의 번호도 함께 본다.
설치하는 것은 실제로 읽은 번호다. 읽은 뒤에 더 많은 변경이 커밋됐다면 다음 폴이 번호
차이로 알아본다.

**집계 쪽.** `place_stats`를 고치는 정기 회차는 넷이고 ShedLock으로 "정시에 한 인스턴스만
돈다"를 지킨다. 못 잡으면 블록 없이 건너뛴다.

| 회차 | 기본 실행 시각 | 하는 일 |
|---|---|---|
| 북마크 델타 소비 | 매시 :00 :15 :30 :45 | 아웃박스 이벤트를 소비해 `bookmark_count`에 더한다 |
| 리뷰 카운트 | 매시 :05 :20 :35 :50 | `review_count`·`avg_rating` 전량 재계산 |
| 인기 점수 | 매시 :10 | 인기 점수 채점 |
| 카운트 안전망 | 매일 01:25 | `bookmark_count`를 원본에서 다시 세고 아웃박스를 비운다 |

네 회차 모두 그 시점의 원본에서 값을 다시 만드는 재계산이라, 인스턴스가 실행 시점에 죽어
회차를 놓쳐도 다음 실행 한 번의 결과와 같다. 놓친 회차를 복구하는 장치가 없어도 되는
이유다. 북마크만 델타로 처리하는 이유는 전량 재계산 비용이 장소 수가 아니라 누적된 북마크
행 수에 비례하기 때문이다(벤치 1,040만 행에서 매시 배치 3.5초). 북마크는 서비스가 살아 있는
한 쌓이기만 하니 그 비용은 가만히 둬도 자란다. 대신 그 정확성이 아웃박스 이벤트의 발행·소비 규칙 위에
서게 되므로 하루 한 번 안전망이 표류의 상한을 자른다. `lockAtMostFor`는 임대라 회차가 그 상한을 넘겨 돌면 다른 인스턴스가 같은
회차를 시작할 수 있고, 그 겹침을 막는 장치는 없다. 겹쳤을 때는 나중에 커밋한 쪽이 이긴다.

### 1.3 보장하는 것은 수렴이지 동시성이 아니다

서버마다 폴 시점과 리빌드 시점이 다르므로 같은 순간에 모든 서버가 같은 회차를 들고 있지는
않다. 정상 갱신이 이어지는 한 모든 서버가 최신 번호로 수렴한다는 것이 보장이고, 동시에
같아진다는 것은 아니다. 그 차이를 보완하는 것이 요청 경로다.

```text
목록 요청 (어느 서버로 오든)
  → 공유 cursor_version 한 행을 DB에서 읽는다 = shared      ← 예외 없이, 요청당 한 번
  → 이 서버의 설치 회차 = mine

  mine >= shared           → 지금 스냅샷으로 답한다
  mine <  shared           → 대기표를 걸고 리빌드를 부른다. 3초 안에 설치되면 답하고, 아니면 503
  커서의 회차 != shared    → 400 만료. 클라이언트는 첫 페이지부터
```

이 판정이 서버 간에도 성립하는 이유는 커서 토큰이 `cursor_version`을 싣고 다니고 그 값이
공유 번호이기 때문이다. 서버 A에서 발급한 커서가 서버 B로 와도, B는 공유 번호와 대조해
같으면 자기 스냅샷으로 이어 주고 다르면 만료로 끊는다. 두 서버가 같은 회차를 들고 있다면
같은 원본 시점을 읽어 같은 순서를 만들었으므로 페이지가 이어진다.

"로컬과 커서가 맞으면 DB 조회를 건너뛰자"는 최적화를 하지 않는 이유가 여기 있다. 뒤처진
서버와 낡은 커서는 서로 맞으므로, 그 최적화는 정확히 그 서버가 옛 회차를 최신이라 말하게
만든다. 요청당 DB 한 행 조회는 그 오판을 막는 비용이다.

신규 서버는 남을 기다리지 않는다. 포트를 열기 전에 동기로 첫 리빌드를 하고, 60초 안에
못 만들면 기동하지 않는다. 스냅샷을 만들지 못한 서버가 빈 목록을 내보내면 클라이언트는 오류인 줄도
모르기 때문이다.

### 1.3.1 이 시차 자체를 없애는 길

위 규칙들은 전부 "서버마다 스냅샷이 따로 있다"는 구조에서 나온 것이다. 그 구조를 바꾸면
규칙도 같이 사라진다. 정렬·필터·페이징을 각 서버의 메모리가 아니라 **모든 서버가 함께 읽는
외부 조회 저장소**(검색 엔진이나 공유 읽기 모델)에 두면, 어느 서버로 요청이 오든 같은 한
곳을 읽으므로 서버 간 회차 차이라는 개념이 없어진다. 요청마다 공유 번호를 대조하는 한 행
조회, 뒤처진 서버가 거는 대기표와 3초 예산, 그에 따른 503, 다른 서버에서 발급된 커서를
회차로 가려내는 일이 전부 필요 없어진다. 신규 서버도 기동 시 전량 리빌드 없이 바로 트래픽을
받는다.

그러니 외부 조회 인프라는 2.3절의 "데이터가 단일 JVM 힙을 넘었을 때"만의 답이 아니다.
**서버 수가 늘어 수렴 시차와 그것을 보완하는 요청 경로의 규칙이 운영 부담이 될 때**도 같은
답이 된다. 두 축의 압력이 같은 대안에서 만난다.

대신 새로 부담하는 것이 있다. 정합성의 질문이 "서버들이 언제 같아지나"에서 "DB와 외부 저장소가 언제
같아지나"로 옮겨 갈 뿐 없어지지 않는다. 원본 변경을 저장소에 반영하는 동기화 경로와 그
지연(검색 엔진이면 색인 갱신 주기), 동기화가 실패했을 때의 복구 기준, 그리고 요청마다
네트워크 왕복 하나가 새로 추가된다. 지금 구조가 요청당 앱 CPU 1.44ms에 DB 왕복 셋으로 끝나는
것은 조회가 프로세스 안에서 끝나기 때문이고, 외부 저장소로 옮기면 그 왕복이 응답 시간의
하한이 된다. 지금 서버 수와 요구사항(관리자 수정 반영 상한 1분, 집계는 15분 격자)에서는
번호 한 행 대조로 얻는 정합성이 그 비용보다 싸서 이 길을 고르지 않았다.

### 1.4 Redis를 두지 않은 이유와 둔다면 어디까지

이 구조에 필요한 것은 둘이다. 지금 어떤 번호가 최신인지 알 수 있어야 하고, 각 서버가
자기 스냅샷이 뒤처졌는지 판단해 복구할 수 있어야 한다. MySQL의 번호 한 행이 최신의 기준
역할을 하고 각 서버가 그것을 확인해 리빌드하므로, Redis 없이 정합성이 선다. 그 행을 고치는
쓰기가 원본을 고치는 트랜잭션 안에 있다는 것이 핵심이고, Redis로는 그 원자성을 얻을 수
없다.

Redis Pub/Sub을 두면 새 번호 발생을 폴 간격보다 빨리 알리는 용도로는 쓸 수 있다. 그러나
Pub/Sub 메시지는 인스턴스 장애나 재시작 시 놓칠 수 있어 정합성의 기준이 될 수 없다.
둔다면 역할은 이렇게 제한된다.

```text
DB 번호 한 행      정합성의 기준 (source of truth)
Redis Pub/Sub      빠른 갱신을 위한 best-effort 알림. 놓쳐도 폴이 메운다
```

지금은 폴 간격 1분이 관리자 표시값 수정이 다른 서버에 닿는 상한이고, 그 폭이 요구사항
안이라 알림 채널을 추가하지 않았다.

### 1.5 서버 수가 늘면 무엇이 자라는가

| 자원 | n대일 때 | 근거·한계 |
|---|---|---|
| 리빌드 CPU·힙 | 서버당 독립. 대당 리빌드 한 번 0.246초 CPU, 250MB 할당 (10배 규모) | 서버가 늘어도 대당 비용은 그대로 |
| 원본 전량 읽기 | n번. 같은 번호 변경에 n대가 폴 시점에 따라 흩어져 읽는다 | 몰려 읽을 때의 DB 부하는 **미측정** |
| 번호 조회 | 요청마다 한 행. 요청 수에 비례 | PK 한 행 SELECT, 요청당 DB 0.64ms 안에 포함된 값 |
| 집계 회차 | 한 인스턴스만. 서버 수와 무관 | ShedLock |
| 관리자 표시값 패치 | 수정한 서버만 즉시, 나머지는 폴 | 상한 1분 |

n번의 전량 읽기가 문제가 되는 규모에서 대안은 **정렬 결과까지 직렬화하는 공유 빌더**다.
별도의 빌더가 DB를 읽어 완성된 버전별 스냅샷을 만들어 공유 저장소에 두고, API 서버는 새
버전을 받아 역직렬화해 올린다. 서버마다 반복되는 DB 전량 조회와 정렬이 사라지는 대신
다운로드·역직렬화·메모리 할당과 발행 기준 관리가 남는다. Redis를 두는 것 자체가 정렬 비용을
없애지는 않는다. 정렬 결과를 재사용할 수 있는 저장 형식이 핵심이고, 그것은 저장소가
MySQL이든 Redis든 같은 질문이다. 이 후보는 "n대가 몰려 읽을 때의 DB 부하"가 측정으로
확인될 때 선택지가 된다.

## 2. 데이터가 늘 때

### 2.1 무엇이 어떻게 자라는가

| 비용 | 따라가는 값 | 성격 |
|---|---|---|
| 상주 메모리 | 장소 수 N, 정렬 축 수 A → `O(N + A·N)` | 참조 배열이라 A가 늘어도 장소 객체는 그대로 |
| 리빌드 시간·할당 | N (전량 읽기·조립·정렬) | 선형. 힙 정점은 중간 결과 + 새 스냅샷 + 옛 스냅샷 |
| 정적 정렬 조회 | 대상 동네 수, 커서 탐색(이진 탐색), 필터 통과 전 검사한 후보 수 | 동네당 장소 수에 로그로, 통과율에 반비례 |
| 거리순 조회 | 대상 동네의 후보 수 | 후보 전량에 거리 계산 |
| 태그 필터 | 후보당 비트 AND 한 번 | 후보 탐색을 없애지는 않는다 |

### 2.2 확인한 규모와 관찰

**10배(63,200 장소)는 확인했다.** 2 vCPU / Xmx 1,280MB, 무부하, 15회 실행.

| 항목 | 값 |
|---|---:|
| 리빌드 소요 중앙값 | 185ms (173~215) |
| 리빌드 구간 JVM CPU 최대 (200ms 표본) | 0.9~1.1 core (2 vCPU의 45~55%), 앞뒤는 0.05 core |
| CFS 쿼터를 채운 실행 | 0 / 15 |
| Full GC | 0 / 15 |
| Young GC | 3 / 15, 정지 30.1~37.3ms |
| 리빌드 스레드 할당 | 250.3~253.2MB |
| Full GC 직후 live heap | 96.5~97.8MB (Xmx의 7.5~7.6%), 스냅샷 한 벌 8.93MB |

읽을 것이 셋이다. 첫째, **리빌드 CPU는 창에 고르게 퍼지지 않고 200~400ms에 몰린다.** 그
구간에 로더 스레드 1 core에 Young GC 워커·JIT이 더해져 1~1.1 core를 쓰고, 서빙에 남는 몫은
0.9~1 core다. 둘째, **힙 정점은 스냅샷이 아니라 중간 결과다.** 250MB를 할당하지만 살아남는
것은 8.93MB이고, 그 창은 할당이 리빌드 몫뿐이라 Young GC가 드물어 힙이 531~767MB까지
차오른 뒤에야 회수가 돈다. 겹치는 리빌드가 늘 때 쌓이는 것은 이 중간 결과라, 실행기를
둘로 묶었다(둘이면 약 500MB, 셋이면 약 750MB). 셋째, 이 값은 **무부하**다. 사용자 요청이
함께 도는 동안 리빌드가 p50·p95에 주는 영향은 이 숫자로 말할 수 없다.

**100배(632,000 장소)는 요구사항 밖이지만 옛 형상으로 한 번 봤다.** 스냅샷을 3장 보존하던
형상에서 리빌드 한 번이 4.3~5.2초 걸렸고 힙이 상한 1,280MB에 도달해 Full GC가 났다. 지금의
한 벌 보존 형상으로는 다시 재지 않았다. 이 규모라면 리빌드 소요가 요청 대기 예산 3초를
넘어, 뒤처진 서버로 온 요청이 503으로 빠지기 시작한다는 뜻이다. 그 규모는 "이 구조의
매개변수를 조정할 문제"가 아니라 "구조를 바꿀 문제"로 구분했다.

### 2.3 규모가 커질 때 당기는 순서

데이터가 늘어 리빌드가 사용자 지연에 영향을 주기 시작하면, GC 옵션부터 만지지 않고 **어떤
비용이 병목인지 먼저 나눈다.** 재빌드 중의 일시적인 할당이 문제인지, 완성된 스냅샷의 live
객체 자체가 큰 것인지.

**1단계 — 빌더를 API JVM에서 분리한다.** 지금은 DB 전량 조회, 결과 변환, 객체 생성, 정렬,
교체까지 사용자 API와 같은 JVM에서 수행하므로 리빌드 순간 CPU와 힙을 사용자 요청과
경쟁한다. 별도 빌더가 완성된 버전별 스냅샷을 만들어 공유 저장소에 배포하고 API 서버는
받아서 올리기만 하면, DB 조회·JDBC/Hibernate 처리·정렬·중간 객체 생성이 빌더로 격리된다.
1.5절의 공유 빌더와 같은 후보이고, 서버 수 축과 데이터 축이 같은 대안에서 만난다.
빌더는 지연보다 처리량이 중요하므로 API 서버와 다른 GC(예: Parallel GC)를 고를 여지가
생긴다. 다만 API JVM에 최종 스냅샷을 역직렬화해 올리는 비용은 남는다. "빌더 분리 = GC
문제 완전 제거"가 아니다.

**2단계 — 스냅샷 표현을 객체 배열에서 열 배열로 바꾼다.** 빌더를 분리한 뒤에도 API JVM에
올라가는 최종 스냅샷의 객체 수 자체가 GC 병목이라면, 장소마다 객체를 하나씩 만드는 대신
컬럼별 primitive 배열 몇 개(`long[] placeId`, `long[] tagMask`, `double[] score`, 정렬별
`int[]` 순서)로 표현해 GC가 추적할 객체 수와 live heap을 줄인다. 필요한 필드만 연속으로
읽어 적은 캐시 라인으로 더 많은 행을 처리한다는 이점도 따라온다.

이 표현은 한 번 시도했다가 객체 배열로 되돌렸다. 근거는 조기 종료다. 조회는 커서 위치를
이진 탐색으로 잡고, K-way merge는 동네마다 현재 원소 하나만 힙에 올려 앞선 것을 꺼낼 때 그
동네의 다음 하나만 읽으며, 10건이 차면 즉시 멈춘다. 그래서 후보 상한(동네 18 × 동네당
장소 수)과 요청이 실제로 읽는 수는 다르다. 실제 검사 수는 대략 결과 10건 ÷ 필터 통과율이라
통과율 50%면 20건 안팎, 10%면 100건 안팎이다. 현재 조회 경로에서 실제로 접근하는 엔트리
수가 이만큼 작다면 열 배열의 캐시 지역성 이득도 제한적일 가능성이 있고, 실제 검사 건수나
cache miss가 병목이라는 관측이 없는 상태에서 데이터 표현을 복잡하게 바꿀 근거가 부족했다.
거리순만 예외인데, 커서와 무관하게 후보 전량의 좌표를 매번 읽으므로 그쪽은 거리 계산이
비용이다. 다시 검토할 신호는 요청당 검사한 엔트리 수 p95가 수천에 이르거나, 재빌드
할당량·Old GC 표시 시간·GC 빈도가 늘거나, 힙 때문에 컨테이너 메모리가 부담이 될 때다.

같은 단계의 더 저렴한 대안으로 JDK 25의 Compact Object Headers가 있다. 객체 헤더를 12바이트에서
8바이트로 줄이는 옵션이라 같은 힙에 더 많은 객체가 들어가고 GC 빈도가 줄며 캐시 적중에도
도움이 된다. 코드 변경 없이 버전업과 플래그로 얻는 것이라 열 배열보다 먼저 시도할 만하다.
이 프로젝트에서 측정한 것은 아니다.

**3단계 — 외부 조회 인프라.** 그 뒤에도 단일 JVM 힙이 감당하기 어려운 규모라면, 데이터
규모 자체가 이 구조의 범위를 넘은 것이므로 Elasticsearch 같은 외부 조회 인프라로 확장한다.
단순히 데이터가 커졌다고 바로 가지는 않는다. 한 JVM에 조회 모델을 유지하는 비용이 커지거나,
자유 검색·복잡한 필터·facet처럼 고정형 조회 모델이 감당하기 어려운 질의가 늘 때다. 그리고
1.3.1절에서 본 대로, 서버가 늘어 인스턴스별 스냅샷의 수렴 시차를 보완하는 규칙이 부담이 될
때도 같은 답이다. 데이터 축과 서버 수 축의 압력이 이 대안에서 만나므로, 어느 한쪽만 보고
시점을 정하지 않는다.

**로더 최적화는 우선순위가 뒤다.** 결과 전량을 `List<Object[]>`로 쌓지 않고 행 단위로
소비하는 streaming, 그 다음 Hibernate 대신 JDBC primitive getter로 직접 읽는 방법이 있다.
streaming은 10배 규모에서 같은 창 비교로 재 봤는데, 리빌드 소요·CPU·힙·GC 모두 같은 구성
두 라운드 사이의 흔들림 안에 들어가 구분되지 않았다(리빌드 스레드 할당만 240.0 대 254.2MB로
5.9% 차이). 100배에서는 Full GC를 줄였지만 그 규모는 요구사항 밖이다. 그래서 지금 로더는
전량을 행 배열로 읽는 단순한 형태이고, JDBC로 내려가는 것은 타입·null 처리·ResultSet
생명주기를 직접 책임지는 비용이 있으므로 프로파일에서 병목으로 확인됐을 때만 한다.

### 2.4 조회 쪽 대안

**동네 단위 부분 재생성.** 지금은 전체 스냅샷을 한 버전으로 관리한다. 동네별로 쪼개
변경된 동네만 다시 지으면 재생성 범위가 줄지만, 한 인스턴스 안에 서로 다른 버전의 스냅샷이
공존하고 여러 동네를 합쳐 조회하는 커서가 어떤 버전 조합으로 만들어졌는지까지 관리해야
한다. 현재 규모에서 전량 재빌드가 185ms라 그 복잡도를 살 이유가 없었고, 리빌드 비용이
병목이 되는 시점에 검토한다.

**태그 역색인.** 태그 조건이 복잡해지고 통과율이 낮아지면, 정렬 배열을 따라가며 장소마다
태그를 검사하는 방식은 페이지 하나를 위해 검사하는 후보가 는다. 최악은 후보를 끝까지
순회하는 것이고 이것은 현재 구조의 한계다. 그때는 `태그 → 그 태그를 가진 장소 집합`을 bitmap으로
두고 AND·OR로 후보를 먼저 줄인 뒤 기존 정렬 순서를 쓰는 방식을 검토한다. 다만 bitmap을
정렬 배열의 인덱스와 맞추려면 정렬 축마다 별도 bitmap이 필요할 수 있고, 장소의 태그나 순서가
바뀔 때 배열과 bitmap을 함께 갱신해야 해서 관리할 상태가 는다. 이런 인덱스를 계속 직접
추가해야 할 정도로 조건이 복잡해지면 검색 엔진을 직접 만들 것이 아니라 도입할 때다.

**태그 비트마스크의 64개 한계.** `tag_mask`는 BIGINT라 태그가 64종을 넘으면 담을 수 없다.
"더 큰 정수형으로 바꾼다"는 답이 아니다. MySQL에 그보다 큰 정수형이 없고, 자바 쪽도 마찬가지다.
답은 마스크 컬럼을 하나 더 두어 128비트로 넓히거나(판정이 AND 둘로 는다), 태그 축이 그
이상 자라면 검색 엔진으로 이관하는 것이다. 태그가 큐레이션 어휘라 수십 종에서 관리된다는
전제 위에 선 설계다.

## 3. 트래픽이 늘 때

### 3.1 먼저 한계에 닿는 자원은 앱이다

요청당 단가는 부하량과 무관한 값이라 처리 여유의 산술적 기반이 된다.

| 요청당 CPU (피크) | 앱 | DB | 앱 축 산술 상한 | DB 축 산술 상한 |
|---|---:|---:|---:|---:|
| 인메모리 정렬 | 1.44ms | 0.64ms | 약 1,389 req/s | 약 3,125 req/s |

2 vCPU 쿼터가 초당 주는 2,000ms를 단가로 나눈 값이고 실제 최대 처리량 측정값은 아니다.
목표 피크 571 req/s는 앱 축 산술 상한의 약 41%다. 세 구성 모두 먼저 한계에 닿는 자원이 앱이라는 것이
개선 과정에서 확인된 사실이고, 그래서 트래픽 축의 수평 확장 단위는 API 서버다.

산술 상한에 다가가기 전에 스로틀이 먼저 온다. CFS 스로틀은 평균이 아니라 100ms 주기의 순간
수요로 발생하므로 평균이 상한에 가까워질수록 쿼터를 다 쓰는 주기가 빠르게 는다. 같은 부하에서
서로 다른 해법을 적용한 세 구성이 평균 64.1 / 72.8 / 75.5%에서 스로틀 1.4 / 17.0 / 21.6%를
보인 것이 그 방향과 맞는다. 세 구성이라 통제된 곡선은 아니지만, 운영 안전 기준을 평균 50%로
잡은 근거가 여기 있고 현재 43.2%는 그 아래다.

### 3.2 스케일 아웃하면 무엇이 그대로이고 무엇이 자라는가

| 항목 | 서버를 늘릴 때 |
|---|---|
| 요청 처리 CPU | 서버당 독립. 조회는 로컬 메모리, 잠금 없음 |
| 리빌드 | 서버당 독립. 요청 수와 무관하게 서버당 "리빌드 한 번 도는 동안 커밋된 버전 수"만큼 |
| DB 부하 | 요청당 남은 문장 7개 중 실쿼리는 동네 검증(약 12행)·북마크 여부(약 5행)·번호 한 행. 요청 수에 비례해 자라는 것은 이것뿐 |
| 캐시 미스 스탬피드 | 서버당 전량 읽기 하나. 요청 수백 개가 몰려도 첫 하나에 합류한다 |
| 대기 중인 요청 | 서블릿 비동기라 요청 스레드도 DB 커넥션도 잡지 않는다. 대기표만 쌓인다 |

요청당 DB 문장 7개 중 5개는 트랜잭션·세션 관리이고 실쿼리는 셋이다. 트래픽이 커질 때 DB
부하의 축은 이 세 문장이고, 전부 PK 또는 작은 range 조회라 문장 캐시(server-side prepared
statement)로 파싱·전송 비용이 지워져 있다.

DB 정렬 경로는 코드로 남아 있지만 운영 요청 흐름에는 연결돼 있지 않다. 남긴 용도는 등가
테스트다. 스냅샷 경로와 DB 경로를 같은 픽스처에서 나란히 돌려 응답과 커서가 같은지 계속
검증한다. 스냅샷이 없을 때 자동으로 DB로 가는 폴백은 두지 않았는데, 그 이유는 4절에 있다.
문장 캐시 네 줄은 그 경로가 목표 부하에서 스로틀 1.4%·p95 7ms로 돌게 만든 설정이라, 언젠가
재배선할 때 경로가 그 형태로 살아 있게 하는 값이기도 하다.

### 3.3 리빌드와 트래픽이 겹칠 때

리빌드는 사용자 조회를 막지 않는다. 조회는 이미 완성된 불변 스냅샷 참조를 잡고 끝까지
읽고, 갱신 잠금은 리빌드 설치와 표시값 패치 같은 writer끼리만 직렬화한다. **논리적으로
요청이 막히는 구조는 아니다.** 그러나 같은 JVM의 CPU와 힙은 공유하므로 자원 경쟁과 GC를
통해 응답에 영향을 줄 수 있고, 그 영향이 실재하는지는 부하와 리빌드를 겹쳐 재야 안다.

확인한 것과 못 한 것을 나누면 이렇다.

| 확인함 | 못 함 |
|---|---|
| 현재 규모에서 스냅샷 교체를 피크 90초 한가운데 겹친 두 라운드: 교체 버킷 p50 2ms·p95 4ms·오류 0 | 교체 직후 young GC 정지가 4.2ms와 41.6ms로 갈려 재현되지 않음. "항상 작다"고 결론 내리지 않는다 |
| 10배 무부하에서 리빌드 창의 스로틀 0, Full GC 0, 서빙에 0.9~1 core 남음 | 10배에서 부하와 리빌드를 겹친 측정. 대기표의 실제 완료 시간, 503 비율 |
| 요청당 할당 −51%, GC pause 0.44 → 0.25%로 평상시 GC가 새 병목이 아님 | 장시간 운영의 힙 증가·누수·장기적 GC 변화 |

리빌드가 p95·p99에 영향을 주기 시작하면 대안의 순서는 2.3절과 같다. GC 옵션이 아니라
빌더 분리가 먼저다.

### 3.4 트래픽이 커질 때 지켜볼 지표

CPU 사용률 하나만 보지 않는다. 포화는 "요청이 늘어도 처리량이 그대로이고 지연이 급증하는
지점"이고, 그것을 앞서 알리는 지표를 같이 본다.

| 지표 | 의미 | 이 구조에서 보는 이유 |
|---|---|---|
| 앱 CPU 평균과 CFS 스로틀 비율 | 쿼터 대비 여유, 스로틀이 발생하기 시작하는 지점까지의 거리 | 앱이 먼저 한계에 닿는다 |
| Hikari 커넥션 대기 | DB 왕복이 요청 스레드를 붙드는지 | 남은 실쿼리 셋의 축 |
| GC 정지 합·GC 스레드 CPU·승격 속도·Old 점유 | 할당 압력과 장수 객체 누적 | 상주 스냅샷 + 리빌드 중간 결과 |
| 리빌드 소요와 대기 예산 3초의 간격 | 뒤처진 서버의 요청이 503으로 빠지기 시작하는 지점 | 데이터 축과 트래픽 축이 만나는 자리 |
| 503(PLACE-007) 비율, 커서 만료(PLACE-006) 빈도 | 대기 예산 초과, 집계 회차마다 끊기는 스크롤 | 15분 격자의 집계가 스크롤을 얼마나 끊는가 |
| `Prepared_stmt_count` 정체값, `Com_stmt_prepare` 증가율 | 문장 캐시가 축출 순환에 들어갔는지 | 운영 형상 수는 벤치(114종)보다 많다 |

CPU나 지연 이상이 보이면 JFR로 어떤 코드 경로가 CPU와 할당을 쓰는지 좁히고, 서비스가
멈췄는데 CPU가 높지 않으면 스레드 덤프를 여러 번 떠서 DB 커넥션·락·외부 I/O 중 어디에서
기다리는지 본다.

## 4. 실패 지점과 남는 상태

규모가 커질수록 "실패했을 때 무엇이 남는가"가 곧 대비다.

| 실패 지점 | 남는 상태와 후속 처리 |
|---|---|
| 관리자 트랜잭션 실패 | 원본과 번호 함께 롤백. 아무 서버도 변경을 보지 않는다 |
| 관리자 커밋 뒤 표시값 패치 실패 | 번호는 올라 있음. 다음 리빌드가 원본에서 가져온다. 손실이 아니라 지연 |
| 집계 트랜잭션 실패 | 통계·아웃박스 소비·번호 함께 롤백. 회차 내 재시도, 끝까지 실패하면 다음 정시 실행 |
| 실행 시점 인스턴스 종료·실행 지연 | 그 회차는 없던 일. 다음 실행이 최신 원본으로 다시 만든다 |
| 서버의 리빌드 실패 | 기존 스냅샷 유지, 경고 로그. 다음 폴이나 다음 요청이 다시 시작한다. 따로 쉬는 시간도 재시도 횟수도 없다 |
| 번호 조회 실패 (요청 경로) | 로컬 회차를 최신이라 말하지 않고 503. 로컬 폴백 없음 |
| 리빌드가 계속 실패해 목표 회차가 오지 않는다 | 뒤처진 서버로 오는 첫 페이지 요청은 매번 3초 뒤 503이다. 목록만의 유사 장애이고, 조용하지 않다. 리빌드 실패 경고 로그와 PLACE-007 비율이 뛴다. 원인이 DB(접속 불가·타임아웃)면 DB를 읽는 폴백도 같이 실패하므로 폴백이 도움이 되지 않고, 원인이 앱(리빌드 중 힙 부족·조립 예외·전량 읽기가 3초를 넘는 규모)이면 그것은 인메모리 구조나 태그 표현이 한계에 닿았다는 신호라 폴백으로 가릴 일이 아니다. 그래서 자동 DB 폴백을 두지 않았다. 복구는 원인 쪽에서 한다. DB면 DB 복구, 코드 결함이면 롤백, 규모면 2.3절의 손잡이 |
| 기동 리빌드 실패 | 60초 안에 재시도, 실패하면 그 서버는 뜨지 않는다 |
| 리빌드 실행기가 작업을 거절 | 실질적으로 닿지 않는 경로다. 대기열이 무제한이라 포화로는 거절되지 않고, 실행기는 컨텍스트 종료 때만 내려가는데 graceful shutdown이 그 전에 새 요청을 막고 처리 중인 요청(3초 예산)을 기다려 준다. 그래도 예외가 오면 거절된 리빌드 항목을 목록에서 제거하고 기다리던 대기표를 즉시 실패시켜, 뒤에 오는 요청이 실행되지 않는 항목에 합류해 기다리는 일이 없게 한다 |

리빌드 실패에 백오프·최소 간격·목표 기억 같은 장치를 두지 않은 것은 의도다. 폴이 시작하는
리빌드는 간격마다 하나이므로 실패가 연달아 나도 폴이 내는 전량 읽기는 간격당 한 번을 넘지
않고, 요청이 시작하는 리빌드는 같은 목표에 합류하므로 요청 수만큼 늘지 않는다. 상한이 구조에서
이미 나오는 것에 장치를 더 추가하지 않았다.

## 5. 측정하지 않은 것

이 문서가 "대비돼 있다"고 말할 수 있는 범위는 위 표들의 "확인함" 열까지다. 다음은
측정하지 않았고, 규모가 그 방향으로 자랄 때 먼저 재야 할 것들이다.

| 측정 대상 | 함께 확인할 값 |
|---|---|
| 여러 서버가 같은 번호 변경에 몰려 읽을 때 | DB CPU·버퍼풀 읽기, 서버별 수렴 시차 |
| 부하 중 리빌드 (10배) | 리빌드 중 조회 p50·p95, 북마크 쓰기 지연, 대기표 완료 시간, 503 비율 |
| 지금 형상(한 벌 보존)의 100배 | 리빌드 소요가 대기 예산 3초를 넘는 지점 |
| 장시간 운영 | GC 후 힙 사용량의 상승, 누수, Old 점유 추세 |
| 집계 회차 | 15분 격자에서 회차별 소요, 회차 겹침 여부, 커서 만료 빈도 |
| 운영 문장 형상 수 | 동네 수 2~18이 살아날 때 이론 최대 약 1,440형상 대 캐시 512 |
| 리빌드 성공률 | 실패 빈도와 그때 사용자 요청이 낡은 스냅샷으로 답한 시간 |

기본값 1분·3초·60초·실행기 2는 위 실측과 예산 위의 초기값이지 검증된 상한이 아니다.
