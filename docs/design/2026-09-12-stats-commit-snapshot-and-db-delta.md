# 북마크 아웃박스를 DB에서 접고, 스냅샷을 MySQL로 발행한다

2026-09-12 · 이슈 #404 · PR #405 추가 구현 · main·docs·마이그레이션만.
테스트 작성·수정·실행과 빌드는 후속 작업자가 맡는다.

두 갈래다. **아웃박스 집계를 DB로 내리는 것**(1~3장)과 **10분 무조건 재빌드를 걷어내고 스냅샷
자체를 MySQL에 발행하는 것**(4~9장)이다.

앞 갈래는 이미 구현돼 있다(V42). 뒤 갈래는 초안에서 "Redis 채널로 커밋을 알린다"였는데, 그
정책은 **알림이 유실되면 복구할 저장소가 없고, 스냅샷 내용이 여전히 인스턴스 힙에만 있어
새 배포마다 전량 재빌드와 새 버전 발급이 반복된다**는 두 구멍이 있었다. 그래서 알림이 아니라
**발행물 자체를 MySQL에 두는 쪽**으로 갈았다. Redis 초안(`SnapshotRefreshSignal`·`Notifier`·
`ListenerConfig`)은 이 문서와 함께 삭제한다. 인증·세션 등 **다른 Redis 용처는 그대로다.**

---

## 1. 무엇이 갈렸나

| | 이전 | 이후 |
|---|---|---|
| 소비 경계 | `SELECT … ORDER BY id FOR UPDATE` 전량 | `UPDATE … SET consumption_id = :uuid` (표식 claim) |
| 접기 | 전표 전량을 JVM으로 읽어 `Map`에 합산 | `GROUP BY target_id` — DB가 접고 장소별 합만 올라온다 |
| 삭제 | 읽어 둔 id 목록으로 `IN` 삭제 | `WHERE consumption_id = :uuid` |
| 스냅샷 전량 재빌드 | 기동 1회 + **10분 무조건** | **DB에 쌓인 재빌드 요청이 있을 때만** |
| 재빌드 요청 | 없음(각자 타이머) | **MySQL 한 행의 카운터.** 통계 트랜잭션이 같은 트랜잭션에서 올린다 |
| 스냅샷 내용 | 인스턴스 힙에만 존재 | **MySQL 한 행에 전량 발행.** 모든 인스턴스가 같은 내용을 내려받는다 |
| 배포 기동 | 매번 전량 재빌드 + 새 번호 발급 | **마지막 발행물을 그대로 복원.** 커서 회차도 그대로 |
| 인스턴스 간 전파 | 없음 | 발행물 폴(기본 5초) |
| 회차 번호 | 전용 발급 테이블(V39) | **발행물 행의 AUTO_INCREMENT id.** 발급소를 따로 두지 않는다 |
| 커서 형식 | `v6` | `v7` — 옛 번호 네임스페이스와 섞이지 않게 가른다(4-6) |

바뀌지 않은 것: 인증 전부, 리뷰 축·점수·안전망의 집계 SQL과 시각, 네 회차의 cron·ShedLock·
재시도·로그, **커서 만료 정책**(회차가 다르면 만료), 부분 패치와 표시값 분리,
`@Scheduled` 단일 스레드, 인증·세션 등 다른 Redis 용처.

## 2. 한 회차의 트랜잭션 (아웃박스)

```sql
-- ① 표식을 짓는다: UUID.randomUUID() — 회차마다 다르기만 하면 되고, 커밋 뒤에는 남지 않는다
-- ② claim
UPDATE bookmark_count_events SET consumption_id = :uuid;
-- ③ 집계 — JVM에 올라오는 유일한 결과
SELECT target_id, CAST(SUM(delta) AS SIGNED) AS delta
  FROM bookmark_count_events
 WHERE consumption_id = :uuid AND target_type = 'PLACE'
 GROUP BY target_id HAVING SUM(delta) <> 0;
-- ④ 적용(기존 청크 UPDATE 그대로) 후 표식으로 삭제
DELETE FROM bookmark_count_events WHERE consumption_id = :uuid;
-- ⑤ 재빌드 요청 (4장) — 같은 트랜잭션의 마지막
UPDATE place_list_rebuild_requests SET requested_seq = requested_seq + 1 WHERE id = 1;
```

**다섯이 한 트랜잭션이라 exactly-once가 트랜잭션으로 성립한다.** 실패하면 표식도 요청도 통째로
롤백돼 전표가 처음 상태로 남고 다음 회차가 다시 삼킨다. 재시도가 안전한 근거는 멱등성이 아니라
이 원자성이다.

**표식이 커밋된 채로 남는 상태가 존재하지 않는다.** 커밋되면 그 행들은 ④에서 이미 지워졌고,
실패하면 표식도 없던 일이 된다. 그래서 `PROCESSING` 상태값도, lease도, 남은 표식을 회수하는
배치도 없다. 순서에 의미가 없고 값이 회차 밖으로 살아남지 않으므로 `UUID`(기존 `jti`·`state`와
같은 `CHAR(36)` 규약)로 족하다.

## 3. 아웃박스의 근거와 대가

**무엇을 얻나 — 전표와 id 목록이 JVM에 올라오지 않는다.** 힙에 싣는 양이 "전표 수"가 아니라
"그 전표가 건드린 장소 수"에 붙는다. 같은 장소를 천 번 토글한 회차가 행 하나가 된다.

**무엇을 치르나 — 전표마다 UPDATE 한 번(undo/redo 포함)과 보조 인덱스 하나.** V38은 "보조
인덱스도 FK도 두지 않는 것이 이 테이블의 계약"이라고 적었고, 그 근거였던 "쓰기 경로가 INSERT
하나"에 이제 인덱스 항목 하나가 붙는다. **DB가 하는 일이 줄었다는 주장은 하지 않는다 —
저울질한 측정이 없다.** 바꾼 이유는 속도가 아니라 회차 비용이 힙에 매이지 않게 하는 것이다.

**READ COMMITTED에서 성립하는 근거**

- *동시 소비자* — ②는 현재 읽기라 다른 회차가 잠근 행을 기다린다. 앞 회차가 커밋하면 그 행은
  같은 트랜잭션에서 이미 지워져 있어 걸리지 않는다. 뒤에 온 회차는 0행을 표시하고 끝난다 —
  `FOR UPDATE`가 하던 델타 회차 ↔ 안전망 직렬화가 그대로 남는다.
- *빈 claim* — 표시한 행이 0이면 집계·적용·삭제를 건너뛴다.
- *늦게 커밋된 작은 id* — ②는 그 시점에 커밋된 행만 표시하고, 표시되지 않은 행은 ④도 지우지
  않는다. 다음 회차 몫이다. `id <= MAX(id)` 범위 삭제가 유실인 이유(V38)는 그대로 유효하다.
  **auto_increment 순서를 커밋 순서로 읽는 가정은 이 문서 어디에도 없다.**
- *사용자 쓰기* — RC에는 갭 락이 없어 ②가 도는 동안에도 INSERT가 들어온다.
- *합의 타입* — `SUM(TINYINT)`는 DECIMAL이라 `CAST(… AS SIGNED)`로 못 박고 `long`으로 받는다.
  `bookmark_count`가 `INT`인 것과 음수 바닥 `GREATEST(0, …)`는 그대로다.

**`WHERE consumption_id IS NULL`을 달지 않았다.** 표식이 커밋된 채 남을 수 없으므로 정상
상태에서 두 문장은 같은 집합을 고른다. 다만 어떤 이유로든 표식이 남은 행이 생기면 `IS NULL`은
그 행을 집계에서도 삭제에서도 영영 빼놓는다. 전량 표시는 그 구멍이 없다.

**안전망·기동 백필·운영 복구도 같은 관문을 쓴다.** 순서 계약(claim → 전량 재계산 → 표식 삭제)과
그 근거는 그대로다. claim을 재계산 뒤로 옮기면 재계산에 들어가지 않은 전표를 지우는 유실이 된다.

**그대로 남는 한계 — 새로 해결한 것이 아니다.** 안전망의 두 창(claim과 재계산 사이에 커밋된
토글의 이중 반영, `calculatedAt` 이후에 생겨 claim에 걸린 전표의 유실)은 `FOR UPDATE` 시절
수용한 그대로다. 좁아지지도 넓어지지도 않았다.

## 4. 스냅샷을 MySQL에 발행한다

### 4-1. 무엇을 저장소로 옮겼나

지금까지 스냅샷은 **번호만 공유되고 내용은 각 인스턴스의 힙에만** 있었다(V39 주석: "사진의
내용은 어디에도 저장되지 않는다"). 그래서 배포마다 새 인스턴스가 전량을 다시 읽어 짓고 새
번호를 발급했고, 같은 데이터인데 번호가 갈리니 진행 중이던 커서가 전부 만료됐다.

**옮기는 것은 번호가 아니라 내용이다.** 발행물 한 행이 스냅샷 한 벌을 통째로 들고, 모든
인스턴스가 그 한 벌을 내려받아 같은 배열을 짓는다. 배포로 올라온 인스턴스도 짓지 않고 복원만
한다.

**번호 발급 전용 테이블(V39)은 새 코드에서 쓰지 않는다.** 발행물을 INSERT하면 그 행의
AUTO_INCREMENT id가 곧 그 발행의 신원이다 — 내용을 저장하는 곳과 신원을 내주는 곳을 하나로
합치면 "번호는 받았는데 내용이 없다"가 성립하지 않는다. 옛 테이블은 **물리적으로 남긴다**
(4-6).

### 4-2. 세 가지 durable 상태

| 테이블 | 행 수 | 누가 쓰나 | 무엇 |
|---|---|---|---|
| `place_list_publications` | 현재 1 + 정리 대기 | 발행 트랜잭션 | 발행물 전량 + 형식 + 커서 회차 |
| `place_list_publication_pointer` | 1 | 발행 트랜잭션 | **명시 현재 포인터.** `MAX(id)`를 쓰지 않는다 |
| `place_list_rebuild_requests` | 1 | 통계·어드민 트랜잭션 | 코얼레싱되는 요청/처리 카운터 |

**포인터를 `MAX(id)`로 대신하지 않는 이유**: 롤백된 행은 테이블에 남지 않으므로 "죽은 큰 id"가
문제인 것이 아니다. 문제는 **번호를 받은 순서와 커밋·채택 순서가 같지 않다**는 것이다. 두 발행이
겹치면 나중에 번호를 받은 쪽이 먼저 커밋될 수 있고, 커밋되지 않은 INSERT가 진행 중인 순간에도
다른 세션의 `MAX`는 그 행을 보지 못한다. **"가장 큰 id"와 "채택된 현재"는 같은 것이 아니다** —
채택은 CAS가 정하고, 그 결과를 한 행이 명시로 말한다. 아웃박스에서 id 범위 삭제를 금지한 것
(V38)과 같은 종류의 착각이다.

**요청 카운터를 따로 둔 이유**: 통계 트랜잭션이 커밋 직전에 잠그는 뜨거운 행이라, 발행물·포인터
와 섞으면 통계가 커밋할 때까지 발행 경로가 그 락을 기다린다.

### 4-3. 두 개의 번호 — 발행 id와 커서 회차

| | `place_list_publications.id` | `cursor_version` |
|---|---|---|
| 뜻 | **이 발행의 신원.** 내용이 한 칸이라도 바뀌면 새 값 | **정렬 순서의 신원.** 커서가 싣는 값 |
| 누가 보나 | 각 인스턴스의 폴 — "새 내용이 있나" | `PlaceListCursor` — "같은 회차인가" |
| 구조가 바뀐 발행 | 새 id | `= id` (같이 새 값) |
| 표시값만 바뀐 발행 | 새 id | **직전 발행의 값을 그대로 이어받는다** |

**이 둘을 가른 것이 "표시값만 바뀐 수정은 커서를 끊지 않는다"를 지키는 자리다.** 발행할 때마다
커서 회차가 바뀌면 이름 하나 고친 어드민 수정이 스크롤 세션을 전부 끊는다(2026-09-09 결정).
그렇다고 표시값 변경을 발행하지 않으면 다른 인스턴스와 새 배포가 그 수정을 영영 못 본다.

두 값이 **같은 AUTO_INCREMENT 네임스페이스**에서 나오므로 별도 발급소가 필요 없다. 구조가
바뀐 발행은 자기 id를 커서 회차로 쓰고, 표시값만 바뀐 발행은 앞의 값을 물려받는다. 커서 회차는
그래서 단조 증가하되 발행마다 오르지는 않는다.

### 4-4. 스키마

```sql
CREATE TABLE place_list_publications
(
    id             BIGINT      NOT NULL AUTO_INCREMENT,  -- 이 발행의 신원
    cursor_version BIGINT          NULL,                 -- INSERT 직후 같은 트랜잭션에서 채운다
    format_version INT         NOT NULL,
    entry_count    INT         NOT NULL,
    payload_bytes  INT         NOT NULL,
    payload_sha256 CHAR(64)    NOT NULL,
    payload        LONGBLOB    NOT NULL,                 -- gzip(JSON)
    published_at   DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    PRIMARY KEY (id)
);

CREATE TABLE place_list_publication_pointer
(
    id             TINYINT     NOT NULL,
    publication_id BIGINT          NULL,   -- NULL = 아직 아무도 발행하지 않았다
    updated_at     DATETIME(3) NOT NULL,
    PRIMARY KEY (id),
    CONSTRAINT fk_place_list_publication_pointer
        FOREIGN KEY (publication_id) REFERENCES place_list_publications (id)
);
INSERT INTO place_list_publication_pointer (id, publication_id, updated_at)
VALUES (1, NULL, CURRENT_TIMESTAMP(3));
```

**FK가 하는 일**: 가리켜지고 있는 발행물은 지워지지 않는다. 정리 배치가 실수로 현재를 지우는
경로를 DB가 막는다.

**포인터와 payload를 한 문장으로 조인해 읽는다.**

```sql
SELECT p.id, p.cursor_version, p.format_version, p.entry_count,
       p.payload_bytes, p.payload_sha256, p.payload
  FROM place_list_publication_pointer ptr
  JOIN place_list_publications p ON p.id = ptr.publication_id
 WHERE ptr.id = 1;
```

**"한 트랜잭션에서 읽는다"로는 부족하다.** READ COMMITTED에서는 문장마다 새 시야를 받으므로,
SELECT를 둘로 나누면 그 사이에 포인터가 옮겨가고 옛 행이 정리될 수 있다 — 격리 수준이 운영
설정에 달린 성질에 기대는 대신 **한 문장으로 만들어 원자성을 문장 자체가 갖게 한다.** 현재 행은
FK가 지키므로 "포인터는 있는데 payload가 없다"가 성립하지 않는다.

### 4-5. payload 형식 — 계약을 명시한다

`format_version = 1`. **gzip으로 감싼 JSON**이고 필드 이름이 형식이다. `Serializable`을 쓰지
않는다 — 클래스 모양이 바뀌면 옛 payload를 못 읽고 그 실패가 런타임에야 드러난다.

```json
{"formatVersion":1,
 "entries":[{"placeId":1,"townId":7,"tagBitmask":12,"popularScore":3.5,
   "createdAtEpochSecond":1757000000,"bookmarkCount":10,"reviewCount":3,
   "ratingToInt":450,"latitude":37.5,"longitude":127.0}],
 "places":[{"placeId":1,"name":"…","thumbnailFileKey":"…","mainTagId":9}],
 "tags":[{"tagId":9,"name":"…","active":true}]}
```

**필수·선택을 못 박는다.** "모르는 필드를 무시한다"만으로는 호환이 아니다 — 빠진 필드를
`0`·`false`로 채우면 **같은 커서 회차를 달고 다른 내용이 복원된다.** 그것이 이 형식에서 가장
위험한 실패다.

- **모든 필드가 반드시 존재해야 한다**(`@JsonProperty(required = true)`). 하나라도 없으면
  디코딩이 예외로 끝난다.
- **primitive 자리에 `null`이 오면 예외다**(`FAIL_ON_NULL_FOR_PRIMITIVES`). 조용한 0이 없다.
- **null이 허용되는 자리는 넷뿐이다**: `latitude`·`longitude`(좌표 미상), `mainTagId`(대표
  태그 없음), `thumbnailFileKey`(썸네일 없음). 이 넷도 **키는 있어야 하고 값만 null**이다.
- **모르는 필드는 무시한다**(`FAIL_ON_UNKNOWN_PROPERTIES=false`). 새 배포가 필드를 늘려도
  옛 배포가 읽는 방향만 열어 둔 것이다.
- **디코딩 뒤 `entries.size()`가 행의 `entry_count`와 다르면 거절한다.**
- **장소 id가 겹치면 거절한다.** 같은 장소가 배열에 두 번 들어가면 페이지가 항목을 겹쳐 낸다.
  태그 id도 같다.
- **`popularScore`가 유한하지 않으면 거절한다.** `NaN`은 `Double.compare`의 전순서를 깨서
  `Arrays.sort`가 계약 위반으로 던지거나 조용히 뒤섞인다.

**payload에 커서 회차를 싣지 않는다.** 구조 발행의 회차는 INSERT가 정하는 id라 payload를 만드는
시점에 알 수 없고, 두 곳에 두면 어느 쪽이 정본인지 물어야 한다. **회차는 `cursor_version` 컬럼이
정본이고 payload는 내용만 싣는다** — payload는 언제나 자기 행과 함께 읽히므로 부족하지 않다.

**단위와 뜻**(값이 같아야 순서가 같다):

- `createdAtEpochSecond` — `createdAt`을 UTC로 간주한 epoch 초. 커서가 싣는 값과 같은 식이다.
- `ratingToInt` — 평점 × 100의 정수. 스케일 2를 응답에서 되씌운다.
- `popularScore` — `double` 그대로. 정렬 비교가 `Double.compare`이므로 재직렬화가 값을 바꾸면
  순서가 갈린다.
- `tagBitmask` — 태그 비트마스크 `long`.
- **엔트리의 배열 순서에는 뜻이 없다.** 복원은 `SortedPlaces.of()`가 다섯 축으로 다시 정렬하고,
  다섯 축 모두 `placeId` 타이브레이크로 끝난다. 그래서 **같은 엔트리 집합이면 같은 배열**이고,
  두 인스턴스가 같은 발행물에서 같은 순서·같은 커서를 낸다.

**형식을 바꿀 때의 규칙**: 필드를 늘리는 것은 같은 `format_version`에서 허용하되, **그 필드가
순서·필터·커서 해석에 끼어들지 않을 때만이다.** 비교자·단위·소속 판정을 건드리는 변경은 옛
배포가 **같은 회차 번호로 다른 순서를 내게** 하므로, 필드를 늘리는 모양이더라도 형식을 올리고
전환 계획을 함께 세워야 한다 — "모르는 필드를 무시한다"가 그 경우를 덮어 주지 않는다. 지우거나
뜻·단위를 바꾸면 언제나 올린다. 지원 목록 밖 형식은 읽지 않는다 — 기동이면 실패시키고,
폴이면 지금 스냅샷을 유지한 채 다음 폴에 다시 시도한다. 체크섬은 **저장된(=압축된) 바이트**에
대해 잡아 "바이트가 깨졌다"와 "디코딩 버그"를 가른다.

**크기와 패킷 한계 — 재보지 않은 수치는 적지 않는다.** 막는 것은 컬럼이 아니라 패킷이다.
`LONGBLOB`은 4GB까지 담지만 값 하나가 한 패킷에 실려야 하므로 서버 `max_allowed_packet`
(MySQL 8 기본 64MB)과 JDBC `maxAllowedPacket`이 실질 상한이다. `payload_bytes`를 컬럼과
로그에 남겨 배포 전에 실제 값을 대조할 것. **압축비도 바이트 수도 예측하지 않는다.**

### 4-6. 옛 번호 네임스페이스를 어떻게 건너나

롤아웃 중에는 **옛 바이너리가 아직 `place_list_snapshot_versions`에 번호를 발급하며 돌고 있다.**
그 인스턴스의 커서는 옛 네임스페이스 번호를 싣고, 새 인스턴스의 커서는 발행 id를 싣는다. 둘이
**우연히 같은 숫자가 되면** 서로의 커서가 통과해 버린다 — 좌표계가 다른 채로 200을 내는,
클라이언트가 알아챌 수 없는 실패다.

**커서 형식을 `v6`에서 `v7`로 올려 그 우연을 없앤다.** 옛 바이너리가 낸 `v6` 커서는 새
바이너리가 형식 불일치로 거절하고, 그 반대도 같다. 두 네임스페이스가 만나지 않는다.
**이 배포의 진행 중 커서가 만료되는 것은 이미 받아들인 대가다**(9장) — 그 대가를 치르는 김에
네임스페이스 문제도 같이 닫는다.

**AUTO_INCREMENT 시작값을 옛 테이블 위로 띄우지 않았다.** 그런 여유는 "옛 테이블의 현재 최댓값이
그보다 한참 작다"는 세어 보기에 기대는 값이라, 배포 전 확인이라는 절차를 하나 만들면서 보장은
주지 않는다. **형식 번호가 이미 완전한 분리를 주므로 그 위에 반쯤 되는 장치를 얹지 않는다.**

**옛 테이블을 지우지 않는다.** V43은 `place_list_snapshot_versions`를 `DROP`하지 않는다 —
롤백해서 옛 바이너리가 다시 뜨면 그 테이블에 INSERT한다. 새 코드는 이 테이블을 읽지도 쓰지도
않으며(`SnapshotVersionIssuer`는 삭제), **롤아웃이 끝나고 롤백 창이 닫힌 뒤 별도
마이그레이션으로 지운다.** 그때까지 이 테이블은 죽은 채로 남는다.

## 5. 발행 — 한 트랜잭션이 전부 한다

`SnapshotPublisher`가 폴(기본 5초)로 돌고 **공유 ShedLock**을 건다 — 짓는 일이 `place_stats`
전량 읽기라 인스턴스 수만큼 돌 이유가 없다.

```
① SELECT requested_seq, processed_seq                        -- 락 없음
②   pending 없으면 그 자리에서 끝. 발행물도 포인터도 읽지 않는다
③ observed = requested_seq                                   ← 코얼레싱 지점
④ basePublicationId = 포인터를 읽는다        ★ 원본을 읽기 "전"에 잡는다
⑤ place_stats·tags 전량을 읽어 엔트리·표시값·태그를 짓고 payload를 인코딩한다
                                                             ← 락을 하나도 들지 않는다
⑥ 발행 트랜잭션 하나 (아래)
⑦ 성공하면 옛 발행물 정리 (별도 짧은 트랜잭션)
```

**④를 ⑤ 앞에 두는 것이 이 순서의 핵심이다.** 발행 직전에 포인터를 읽으면, ⑤가 도는 동안
어드민이나 다른 발행자가 올린 **더 새로운 내용을 낡은 후보가 덮는다.** 빌드 중에 아무도
발행하지 않았다는 것을 CAS로 확인하려면 **기준을 빌드 시작 시점에 잡아야** 한다. ⑤가 길수록
CAS가 깨질 확률이 오르지만, 그 깨짐이 곧 "그동안 새 내용이 있었다"이므로 버리는 것이 맞다.

**`version <= candidate` 같은 조건은 쓰지 않는다.** 번호 크기는 신선도가 아니다. 판정은
**"내가 잡은 기준 발행이 아직 현재인가"** 하나로 한다.

**⑥ 발행 트랜잭션 — 넷이 한 트랜잭션이다.**

```sql
-- ⑥-1 payload를 넣는다. 여기서 id가 정해진다
INSERT INTO place_list_publications
  (cursor_version, format_version, entry_count, payload_bytes, payload_sha256, payload)
VALUES (:carriedCursorVersion, :fmt, :count, :bytes, :sha, :payload);
-- ⑥-2 구조가 바뀐 발행이면 커서 회차를 자기 id로 채운다 (표시값만 바뀐 발행은 ⑥-1이 이미 채웠다)
UPDATE place_list_publications SET cursor_version = id WHERE id = :newId AND cursor_version IS NULL;
-- ⑥-3 CAS — 내가 기준으로 잡은 발행이 아직 현재일 때만 옮긴다. <=> 는 NULL(미발행)까지 다룬다
UPDATE place_list_publication_pointer
   SET publication_id = :newId, updated_at = CURRENT_TIMESTAMP(3)
 WHERE id = 1 AND publication_id <=> :basePublicationId;
-- 0행이면 트랜잭션을 통째로 롤백한다 → ⑥-1의 payload 행도 없던 일이 된다
-- ⑥-4 처리 표시
UPDATE place_list_rebuild_requests SET processed_seq = :observed
 WHERE id = 1 AND processed_seq < :observed;
```

**넷을 한 트랜잭션에 묶는 것이 계약이다.** 나누면 세 가지가 생긴다 — CAS에 진 발행물 행이
고아로 남고, 발행은 됐는데 처리 표시가 안 된 창(다음 회차가 헛빌드)이나 그 반대 창(요청이
사라졌는데 내용은 안 올라감)이 생긴다. 리포지토리 메서드에 전파 설정을 달지 않고 **발행 서비스
하나가 트랜잭션을 소유한다.**

**그 트랜잭션은 `REQUIRES_NEW`다.** 어드민 훅은 커밋 뒤 `afterCommit`에서 발행하는데, 그 시점에도
끝난 트랜잭션의 자원이 스레드에 묶여 있다. `REQUIRED`로 두면 이미 커밋된 트랜잭션에 다시 붙어
커밋되지 않는다.

**`processed_seq < :observed`**는 만료된 ShedLock을 들고 늦게 깨어난 발행자가 표시를 뒤로
되돌리지 못하게 한다. **③에서 읽은 값만 표시하므로 빌드 중에 도착한 요청은 처리됐다고 표시될
수 없다** — `requested_seq`가 `observed` 너머에 있어 다음 회차가 가져간다.

**실패하면 아무것도 남기지 않는다.** CAS가 지든 어디서 던지든 트랜잭션이 통째로 롤백돼 직전
발행물과 밀린 요청이 그대로다. 로그만 남는다.

**락 순서를 한 방향으로 고정한다:** `publications` → `pointer` → `rebuild_requests`.
발행 트랜잭션(발행자·어드민 훅 공통)이 이 순서로만 잡고, 통계·어드민 쓰기 트랜잭션은
`rebuild_requests`를 **자기 마지막 쓰기로** 잡는다. 이 셋을 걸친 순환이 없다.

**그 "마지막"이 저절로 되지는 않는다.** 어드민 경로는 엔티티 변경(장소 삭제·태그 수정·이미지
교체)을 들고 요청 증가에 오는데, JPA는 그 UPDATE/DELETE를 커밋까지 미룬다. 그대로 두면 실제
쓰기 순서가 **요청 행 → `places`/`tags`**가 되고, 같은 장소를 걸친 두 어드민 트랜잭션이 서로의
락을 마주 본다. 그래서 요청 증가가 **먼저 영속성 컨텍스트를 flush한다** — 이 트랜잭션이
마지막으로 잡는 행을 요청 행 하나로 고정하는 장치다. 네이티브 SQL만 쓰는 통계 경로에서는
flush할 것이 없어 아무 일도 일어나지 않는다.

정리(`deleteOlderThan`)는 `publications`의 옛 행만 건드리고 포인터를 FK로 읽기만 하므로, 발행을
기다릴 수는 있어도 발행이 정리를 기다리지는 않는다.

**발행자의 전량 재빌드는 언제나 구조 발행이다** — 새 id를 커서 회차로 쓴다. 그래서 **통계 회차
마다 진행 중이던 커서가 만료된다.** 옛 10분 무조건 재빌드도 같은 일을 했고 통계 회차는 시간
단위라 빈도가 더 낮지만, **줄어들었다고 주장하지는 않는다** — 세어 본 적이 없다. 없애려면 새로
지은 엔트리 집합이 현재 발행물과 같은지 비교해 같으면 회차를 이어받아야 하는데, 그 비교 비용과
이득을 재지 않았으므로 넣지 않았다.

**⑦ 정리 — 현재만 남긴다.**

```sql
DELETE FROM place_list_publications WHERE id < :currentId;
```

FK가 현재 행을 지키고, 내려받기는 한 문장이라 이 삭제가 진행 중인 내려받기를 깨지 않는다.
**이력을 쌓지 않는다** — 옛 발행물을 되찾는 소비자가 없다(커서는 옛 회차로 돌아가지 않고
만료된다).

**정리 실패는 발행 실패가 아니다.** 발행 트랜잭션 밖에서 따로 돌고, 던지면 로그만 남긴다 —
이미 커밋된 발행을 되돌릴 이유가 없고 배치를 다시 돌릴 이유도 없다. 남은 행은 다음 회차의 정리가
가져간다.

## 6. 어드민 수정 — 부분 패치를 발행까지 잇는다

어드민 훅 셋은 지금까지 **요청을 받은 인스턴스의 힙만** 고쳤고, 그래서 새로 뜬 인스턴스는 그
수정이 빠진 상태를 복원하게 된다. 셋의 성격이 달라 처리도 다르다.

| 훅 | 무엇이 바뀌나 | 커서 회차 | 발행 |
|---|---|---|---|
| `refreshPlacesAfterCommit` | 정렬 배열(구조) + 그 장소들의 표시값 | 배열이 실제로 바뀌었으면 새 값 | 한다 |
| `patchPlaceViewAfterCommit` | 그 장소의 표시값만 | **이어받는다** | 한다 |
| `refreshTagViewsAfterCommit` | 태그 맵 전체 | **이어받는다** | 한다 |

### 6-1. 공유 발행이 성공하기 전에는 로컬 힙을 고치지 않는다

**순서가 뒤집히면 로컬만 앞서 나간다.** 먼저 힙을 갈고 발행에 실패하면, 그 인스턴스는 공유되지
않은 더 높은 커서 회차를 들게 되고, 뒤이어 내려오는 (더 낮거나 같은) 공유 발행물을 단조 가드가
거절한다 — 그 인스턴스만 영영 다른 것을 서빙한다. 그래서:

```
CacheWriteLock 안에서
  ① 밀린 발행물이 있으면 먼저 채택한다 (공통 채택 경로)   ← 낡은 바탕 위에 패치하지 않는다
  ② base = 그 채택으로 확정된 발행 id
  ③ 바뀐 장소 id로 원본을 다시 읽어 후보를 계산한다
       — 순수 계산이다. SnapshotBox도 홀더도 건드리지 않는다
  ④ 발행 트랜잭션 (5장 ⑥과 같은 것)
  ⑤ 성공했을 때만 공통 채택 경로로 내려받아 설치한다
     실패하면 홀더는 손대지 않은 채로 남고 요청은 열린 채로 둔다
```

**③이 순수 계산이라는 것이 이 순서를 가능하게 한다.** 기존 `SnapshotLoader.patch`는 읽기·
`SortedPlaces.patch`·힙 교체를 한 몸에 했다. 그중 **읽기와 계산만** 남기고 교체를 떼어내
채택 경로 하나로 모은다. `SortedPlaces.patch(changedIds, latestEntries)` 자체는 이미 새
객체를 돌려주는 순수 함수라 그대로 쓴다.

**부분 패치의 성질은 그대로다.** 바뀐 장소 id만 다시 읽고(전량 집계가 아니다), 나머지 항목의
정렬 키는 배열에서 그대로 옮겨 오며, 표시값만 바뀐 수정은 배열을 바꾸지 않는다.

### 6-2. 요청을 언제 닫는가 — 남의 요청을 대신 닫지 않는다

어드민은 **쓰기 트랜잭션 안에서** `requested_seq`를 올리고 그 값(`mySeq`)을 훅에 넘긴다.
프로세스가 커밋과 훅 사이에 죽어도 요청이 남아 발행자가 메운다.

발행에 성공한 훅이 자기 요청을 닫을 수 있는 조건은 **둘 다** 참일 때뿐이다.

```sql
UPDATE place_list_rebuild_requests SET processed_seq = :mySeq
 WHERE id = 1
   AND processed_seq = :mySeq - 1     -- 내 앞에 밀린 일이 없었다
   AND requested_seq = :mySeq;        -- 내 뒤로 아무도 올리지 않았다
```

**앞 조건이 없으면 남의 요청을 지운다.** 통계 회차가 `seq=1`을 올려 두고 아직 발행되지 않은
상태에서, 어드민이 `seq=2`로 자기 장소만 패치해 발행한 뒤 `requested_seq == 2`만 보고
`processed_seq = 2`로 올리면 — 어드민 후보에 들어 있지도 않은 **통계 변경이 처리됐다고
표시된다.** 그 통계 갱신은 다음 통계 회차까지 공유되지 않는다.

`processed_seq = :mySeq - 1`은 "내 앞의 모든 요청이 이미 처리됐다"를 뜻한다. 그렇지 않으면
**아무것도 닫지 않고** 발행자에게 넘긴다 — 발행자가 원본에서 전량으로 지으면 밀린 것이 전부
반영된다. 조용한 경우(대부분의 어드민 수정)에는 그 전량 재빌드가 돌지 않는다.

**실패했을 때 거짓 성공을 말하지 않는다.** 계산·인코딩·발행 중 어디서 실패하든 훅은 예외를
삼키되 **요청을 닫지 않고**, 로그에 "요청을 열어 둔다"를 남긴다. "갱신 완료"를 남기지 않는다.

### 6-3. 대가

**payload를 만드는 비용이 어드민 요청 스레드에 붙는다.** 커밋 뒤 훅이라 사용자가 기다리는
시간에 들어가고, 성공하면 내려받기가 한 번 더 붙는다. 지금 규모에서 문제라고 볼 근거도, 문제가
아니라고 볼 측정도 없다. **payload가 커지면 여기가 먼저 아프다.** 그때의 대안은 훅에서 발행을
떼고 요청만 남기는 것이고(발행자가 전량으로 짓는다), 되돌리기 쉬운 결정이다.

## 7. 채택 — 모든 인스턴스가 따로 내려받는다

폴(기본 5초)이 인스턴스마다 돈다. **ShedLock을 걸지 않는다** — 고치는 것이 자기 힙이다.
발행자 노릇을 하는 인스턴스도 자기가 방금 발행한 것을 이 경로로 내려받는다. **설치 경로를
하나로 두는 것이 "모든 인스턴스가 같은 배열을 짓는다"의 근거다.**

```
① SELECT publication_id FROM place_list_publication_pointer   -- 작은 조회
② 마지막으로 설치한 id와 같으면 끝. payload를 읽지 않는다
③ 한 트랜잭션에서 포인터와 그 행을 함께 읽는다
④ 체크섬 → 형식 번호 → 디코딩 → entry_count 대조 → SortedPlaces.of()
   ← 여기까지 실패하면 홀더를 하나도 건드리지 않았다
⑤ CacheWriteLock 안에서
     내려받은 id <= 이미 설치한 id 이면 버린다        ★ 락 안에서 다시 본다
     표시값 홀더 · 태그 홀더 · SnapshotBox 를 함께 갈고 설치 id를 올린다
```

**⑤의 재확인이 필요한 이유**: ③·④는 락 밖에서 돈다. 그 사이 어드민 훅이 더 새 발행물을
설치했을 수 있고, 그러면 늦게 도착한 옛 payload가 새 표시값·태그를 덮는다. **설치 id를 락
안에서 읽고 쓰는 것**이 그 창을 닫는다.

**세 홀더 전부가 발행 id 하나로 보호된다.** `SnapshotBox`의 단조 가드는 커서 회차를 보는데,
표시값만 바뀐 발행은 커서 회차가 같아 그 가드로는 걸러지지 않는다. **순서를 정하는 값은 발행
id 하나**로 두고, `SnapshotBox`의 기존 가드는 그대로 남겨 "같은 커서 회차면 스냅샷 참조를
바꾸지 않는다"를 지킨다 — 그래서 표시값만 바뀐 발행이 진행 중인 커서를 끊지 않는다.

**로컬은 언제나 한 벌만 든다.** 옛 회차를 보관하거나 커서에 실린 회차로 옛 발행물을 찾아 주는
경로는 만들지 않는다.

## 8. 기동 — 짓지 않고 복원한다

`@PostConstruct`가 한다. 여기서 던지면 컨텍스트가 뜨지 않는다 — **스냅샷이 빈 인스턴스가
트래픽을 받는 상태를 만들지 않는 것**이 요점이다.

```
① 포인터를 읽는다
② 가리키는 발행물이 있으면 복원해 설치하고 끝
   — 원본을 읽지도, 새 발행을 만들지도 않는다. 커서 회차가 그대로다
③ 포인터가 NULL이면 부트스트랩
     발행자 ShedLock을 프로그램적으로 잡아 본다
       획득 → 포인터를 다시 확인하고(기다리는 사이 남이 발행했을 수 있다)
              여전히 NULL이면 원본에서 지어 발행(base = NULL)
       실패 → 폴 간격으로 포인터를 다시 본다
     bootstrap-timeout(기본 60초) 안에 발행물이 안 생기면 예외를 던져 기동을 접는다
④ 설치 뒤 포인터를 한 번 더 본다. 그 사이 바뀌었으면 한 번 더 설치한다
```

- **배포마다 커서 회차가 갈리지 않는다.** ②가 그대로 복원하므로 같은 발행물을 보는 인스턴스가
  같은 회차를 든다.
- **최초 부트스트랩의 발행물은 비어 있을 수 있다.** `place_stats` 백필은
  `ApplicationReadyEvent`에서 도는데 그것은 `@PostConstruct` 뒤다. 백필 트랜잭션이 요청을
  올리므로 발행자가 곧 채운다 — 지금도 같은 순서다.
- **④는 한 번만 한다.** 확인과 준비 완료 사이의 창은 폴 간격이 있는 한 없앨 수 없다. 한 번 더
  보는 것으로 "뜨자마자 명백히 낡은 상태"만 걷어내고 나머지는 폴에 맡긴다.
- **형식이 지원 밖이거나 payload가 깨졌으면 기동을 실패시킨다.** 폴에서는 지금 것을 유지하지만
  기동에는 유지할 "지금 것"이 없다. 어느 쪽도 payload를 재해석하지 않는다.

## 9. 한계 — 정확히 적어 둔다

- **반영은 0ms가 아니다.** 통계 커밋 → 발행 폴(≤5초) → 빌드 → 각 인스턴스의 채택 폴(≤5초)이다.
  `@Scheduled` 스레드가 하나(Boot 기본 `spring.task.scheduling.pool.size=1`)라 앞 작업이 길면
  그만큼 밀린다. **새 스레드 풀을 만들지 않았다.**
- **인스턴스 간 교체가 동시에 일어나지 않는다.** 폴 시점이 제각각이라 새 발행 뒤 최대 폴 간격
  동안 인스턴스마다 다른 회차를 서빙하고, 그 창에 걸친 사용자는 커서 만료를 볼 수 있다.
  **줄이려면 폴 간격을 줄이는 수밖에 없고, 없애는 방법은 이 구조에 없다.**
- **이번 배포의 커서는 지켜 주지 못한다.** 지금 떠 있는 인스턴스는 발행물 없이 자기 힙에만
  스냅샷을 들고 있고, 커서 형식도 `v6`에서 `v7`로 올린다(4-6). **다음 배포부터** 같은 형식의
  발행물을 복원하는 한 커서가 이어진다.
- **롤아웃 동안 옛·새 바이너리가 섞인다.** 옛 바이너리는 발행물을 보지 않고 자기 힙만 서빙하며
  옛 번호 테이블에 계속 발급한다. 커서 형식이 달라 서로의 커서를 받지 않는 것이 유일한 보호다.
- **형식이 갈린 배포가 섞이면 옛 인스턴스는 새 발행물을 받지 않는다.** 지원 목록 밖이라
  거절하고 자기 것을 유지한다 — 조용히 오독하는 것보다 낫지만, 롤아웃 동안 옛 인스턴스가
  굳는다는 뜻이기도 하다.
- **어드민 훅이 죽는 창.** 커밋과 훅 사이에 프로세스가 죽으면 그 수정은 로컬에도 발행물에도
  반영되지 않는다. 트랜잭션 안에 올려 둔 요청이 남아 **발행자가 메운다**.
- **발행 payload는 통짜다.** 표시값 한 칸이 바뀌어도 전량을 다시 싣는다. 부분 발행은 만들지
  않았다 — 부분 적용의 순서와 유실을 관리할 상태가 하나 더 생긴다.
- **옛 번호 테이블이 죽은 채 남는다.** 롤백 창이 닫힐 때까지 지우지 않는다(4-6).

**검증에서 더 붙은 둘** (`docs/verification/2026-09-12-mysql-snapshot-publication.md`)

- **동시 부트스트랩에서 후보 빌드가 두 번 돈 회차가 관측됐다**(검증 §4, 5회 중 4회). 같은 JVM에
  노드 둘을 세운 하네스에서의 관측이고 **원인은 규명하지 못했다** — ShedLock 획득이 어느 경로로
  갔는지부터 확정되지 않았다. **발행물은 그래도 하나만 남는다**: 이 경로의 보장 주체가 락이 아니라
  포인터 CAS이기 때문이고, §11-20은 그 성질로 통과했다. 남는 것은 정확성이 아니라 **중복 비용**이다
  — 함께 뜬 인스턴스 수만큼 원본 전량 읽기와 인코딩이 헛돌 수 있다.
- **최초 부트스트랩은 발행 직후 한 채택 폴만큼 늦다.** `restoreOnStartup`이 자기 발행에
  성공한 회차에도 곧바로 설치하지 않고 폴 간격을 한 번 잔다 — 기본값 5초에서는 기동이 그만큼
  밀린다. 발행물이 이미 있는 평소 기동에는 해당되지 않는다(그 경우 첫 확인에서 바로 설치한다).

## 11. 후속 작업자가 볼 검증 항목

> **상태(2026-09-12): 이 목록으로 테스트를 다 썼고 `./gradlew clean build`가 564개 통과했다.**
> 실행 결과·수치·남은 한계는 `docs/verification/2026-09-12-mysql-snapshot-publication.md`가
> 정본이다. 아래 목록은 무엇을 왜 확인해야 했는지의 정본으로 남긴다.

MySQL 실물 위에서 확인한다(H2 대체 금지는 #404의 기존 방침 그대로). 동시성 항목은 **독립
커넥션과 래치**로 실제 경쟁을 만든다. **환경 미비로 건너뛰는 스킵을 두지 않는다.**

**아웃박스 (V42, 이미 구현됨)**

1. **claim 배타** — 두 세션이 동시에 소비하면 뒤에 온 쪽이 0행 claim으로 끝나고 카운트가 두 번
   더해지지 않는다.
2. **늦게 커밋된 작은 id** — claim 뒤에 커밋된 전표는 그 회차에 지워지지 않는다.
3. **롤백** — 적용·삭제 중 실패하면 표식도 `requested_seq`도 되돌아온다.
4. **접힘** — +1/−1 왕복이 0으로 접히고 전표는 지워진다.
5. **비-PLACE 전표** — 집계에서 빠지되 표식 삭제에는 포함된다.
6. **안전망·기동 백필** — claim 관문을 지나고 재계산 뒤 전표가 빈다.
7. **데드락 없음** — 안전망과 델타 회차가 겹쳐도 `Innodb_deadlocks`가 늘지 않는다.

**요청**

8. **커밋된 회차만 요청한다** — 롤백된 통계 트랜잭션은 `requested_seq`를 올리지 않는다.
9. **트랜잭션 밖 호출은 거절된다** — `request()`가 `MANDATORY`라 예외가 난다.
9-1. **어드민 데드락 없음** — 같은 장소를 걸친 두 어드민 요청이 동시에 커밋해도
    `ERROR 1213`이 나지 않는다. 요청 증가가 먼저 flush해 실제 쓰기 순서를 고정하는 것이 근거이므로,
    그 flush를 빼면 실패하도록 만들어 둘 것.

**발행**

10. **코얼레싱** — 빌드 중에 요청이 셋 더 들어오면 그 회차는 하나만 발행하고 `processed_seq`는
    자기가 본 값까지만 오르며, 다음 회차가 남은 셋을 한 번에 처리한다.
11. **기준을 빌드 전에 잡는다** — 빌드 도중 다른 발행이 끼면 CAS가 지고, **낡은 후보가 새
    내용을 덮지 않는다.**
12. **발행 원자성** — CAS에 진 회차는 `place_list_publications`에 고아 행을 남기지 않고
    `processed_seq`도 올리지 않는다(트랜잭션 전체 롤백).
13. **처리 표시가 발행과 한 트랜잭션이다** — 발행만 되고 표시가 안 된 상태, 표시만 되고 발행이
    안 된 상태가 만들어지지 않는다.
14. **빌드 실패** — 원본 읽기가 던지면 포인터도 `processed_seq`도 그대로다.
15. **낡은 발행자 펜싱** — ShedLock 만료 뒤 깨어난 발행자의 후보가 CAS에 지고 `processed_seq`를
    되돌리지 못한다.
16. **정리** — 발행 뒤 옛 행이 지워지고, 현재 행은 FK 때문에 지워지지 않는다. 정리와 겹친
    내려받기가 실패하지 않는다. **정리가 실패해도 발행은 성공으로 남고 배치가 재시도되지 않는다.**
17. **포인터가 명시다** — 롤백된 INSERT로 커진 AUTO_INCREMENT가 "현재"로 읽히지 않는다.

**채택·기동**

18. **두 노드 복원 일치** — 같은 발행물을 복원한 두 컨텍스트가 같은 커서 회차를 들고 같은
    정렬·같은 페이지·**같은 커서 문자열**을 낸다.
19. **재기동에 새 발행이 없다** — 발행물이 있는 상태로 다시 띄우면 `place_list_publications`에
    행이 늘지 않고 커서 회차가 그대로다.
20. **부트스트랩 경쟁** — 미발행 상태에서 두 컨텍스트가 동시에 뜨면 발행물이 하나만 생긴다.
21. **지원하지 않는 형식** — `format_version`을 올려 두면 폴은 지금 스냅샷을 유지하고 기동은
    실패한다. 어느 쪽도 payload를 재해석하지 않는다.
22. **깨진 payload** — 체크섬 불일치, `entry_count` 불일치, 필수 필드 누락, primitive 자리의
    `null`, **장소·태그 id 중복**, **유한하지 않은 `popularScore`** 여섯 모두 예외로 끝나고 설치
    id가 오르지 않는다.
23. **내려받기 실패** — 조회가 던져도 직전 스냅샷이 그대로 서빙되고 다음 폴이 재시도한다.
24. **늦게 도착한 옛 payload** — 락 밖에서 내려받는 사이 더 새 발행이 설치되면, 옛 payload가
    표시값·태그를 덮지 못한다.
25. **폴의 무부하** — 요청이 없는 발행 폴은 포인터를 읽지 않고, 포인터가 그대로인 채택 폴은
    payload를 읽지 않는다.

**어드민**

26. **표시값만 바뀐 발행** — 발행 id는 오르고 **커서 회차는 그대로**이며, 다른 노드의 이름·
    썸네일이 갱신되고 **그 노드의 커서가 만료되지 않는다.**
27. **구조가 바뀐 발행** — 새 커서 회차로 발행되고, 다른 노드가 복원했을 때 정렬 결과가 패치한
    노드와 같다. 바뀌지 않은 항목의 정렬 키가 보존된다.
28. **발행 전에 로컬을 고치지 않는다** — 발행을 실패시키면 그 인스턴스의 홀더·`SnapshotBox`가
    한 칸도 바뀌지 않고, 이어지는 공유 발행물을 정상으로 받는다.
29. **남의 요청을 닫지 않는다** — 통계 요청이 밀린 상태에서 어드민이 발행해도 `processed_seq`가
    오르지 않고, 다음 발행자 회차가 통계 변경까지 반영한다.
30. **자기 요청은 조용할 때만 닫는다** — 앞에 밀린 것도 뒤에 끼어든 것도 없으면 닫히고, 그
    경우 발행자의 전량 재빌드가 돌지 않는다.
31. **훅 실패의 복구** — 발행이 실패하면 요청이 닫히지 않고 다음 발행자 회차가 원본에서 같은
    상태로 되돌린다.

**전환·기타**

32. **커서 형식 v7** — `v6` 토큰이 새 코드에서 만료로 거절되고, `v7` 토큰은 같은 발행물을 복원한
    다른 노드에서도 통과한다.
33. **V39를 지우지 않았다** — 마이그레이션 뒤에도 `place_list_snapshot_versions`가 남아 있고,
    새 코드는 그 테이블에 쓰지 않는다.
34. **Redis 없이 동작한다** — Redis 자동설정을 뺀 컨텍스트에서 발행·채택·기동 복원이 전부 돈다.

**⚠️ 기존 IT 주의.** 폴이 기본 5초라 프로세서를 직접 부르는 IT에 백그라운드 발행·채택이
끼어들 수 있다. 스위트에서는 `publish-poll-interval-ms`·`adopt-poll-interval-ms`를 크게 잡아
폴을 사실상 끄고 발행·채택은 테스트가 명시적으로 부른다. 설정 키가 `poll-interval-ms` 하나에서
둘로 갈렸고 `refresh-notification-enabled`는 사라졌다 — `application-test.yml`을 그에 맞게
고쳐야 한다.

**→ 처리됨.** `application-test.yml`이 `publish-poll-interval-ms: 3600000`(사실상 정지)과
`adopt-poll-interval-ms: 1500`을 쓴다. 채택 폴을 크게 잡지 않은 이유는 위 §9의 "최초 부트스트랩은
발행 직후 한 채택 폴만큼 늦다" 때문이다 — 크게 잡으면 컨텍스트 기동이 그만큼 멈춘다.
