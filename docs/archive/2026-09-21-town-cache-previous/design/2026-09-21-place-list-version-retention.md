# 장소 목록 조회 — 이번 작업의 구현 기준

상태: 사용자 뼈대와 후속 지시를 옮긴 기준서. 구현 완료 문서가 아니다.
작성: 2026-09-21.
사용자가 진행 상황을 읽는 정본: [뼈대와 근거를 쌓는 블로그 문서](../../../blog/2026-09-21-place-list-design-evidence.md). 이 기준서는 작업자가 지킬 계약의 요약이며, 판단 근거와 결과는 블로그 문서에 누적한다.
실행 계획: [단계별 계획](../../../superpowers/plans/2026-09-21-place-list-version-retention.md).

## 1. 기준과 목적

- 사용자가 이번 대화에서 제공한 「장소 목록 조회의 CPU 비용을 줄이면서 사용자가 보던 목록을 유지하기 위한 설계」가 기준이다. 이 문서는 그 뼈대의 실행용 요약이다.
- 기존 설계 문서의 정책은 철회된 이력이다. 특히 버전 변경 즉시 커서 만료, 최신 버전 한 벌만 보관, 요청마다 정렬을 이번 요구로 가져오지 않는다.
- 성능 비교의 출발점은 캐시 도입 전 DB만으로 목록을 조회하던 구조다. 현재 브랜치의 전역 스냅샷을 기존 구조로 부르지 않는다.
- 목표는 반복 DB 조회·JDBC 처리·객체 매핑을 줄여 요청당 앱 CPU 여유를 확보하는 것이다. DB CPU 감소만으로 목표 달성을 주장하지 않는다.
- 이미 선택한 방향의 근거 수집과 구현에 집중한다. 요구사항을 만족하지 못하거나 비용이 선택을 뒤집는 증거가 있을 때만 대안을 재검토한다.

## 2. 반드시 지킬 목록 동작

| 상황 | 동작 |
|---|---|
| 첫 페이지·명시적 새로고침 | 요청 처리 중 관측한 최신 동네별 버전으로 조회 |
| 다음 페이지 | 첫 페이지의 동네별 버전 조합과 필터·정렬 기준 유지 |
| 더 최신 버전이 생겼고 기존 버전이 남아 있음 | 기존 버전으로 계속 조회 |
| 커서가 요구한 버전이 캐시에서 사라짐 | 다른 버전을 붙이지 않고 첫 페이지부터 다시 조회하도록 새로고침 요구 |
| 첫 페이지에 필요한 최신 데이터가 없음 | 필요한 동네를 적재하고, 제한 시간 초과·실패 시 명시적 오류 |

정상 응답에서 페이지 사이의 변경 때문에 장소가 중복·누락되지 않아야 한다.
같은 목록을 무기한 보관하지 않는다. TTL 이전에도 용량 때문에 제거될 수 있다.
캐시에서 사라진 커서 버전을 DB 재조회로 복구해 계속 제공하는 정책은 이번 기준에 포함하지 않는다.

## 3. 구현할 구조

1. 동네·버전별로 장소 집합, 필터 값, 정렬 값을 불변 데이터로 보관한다.
2. 새 버전은 갱신이 필요한 해당 동네의 모든 장소를 DB에서 조회해 만든다. 다른 동네까지 무조건 조회하지 않는다.
3. 데이터 변경과 영향 동네 버전 증가는 같은 쓰기 트랜잭션에 둔다. 동네 이동은 출발·도착 동네 모두 반영한다.
4. 첫 페이지에서 관측한 동네별 버전 조합과 실제 적재한 버전을 맞춘다. 원본과 버전은 같은 DB 읽기 상태에서 얻는다.
5. 기존 버전 객체는 수정하지 않는다. 늦게 완료된 적재로 최신 버전 선택이 뒤로 돌아가지 않아야 한다.
6. 정적 정렬 배열은 동네·버전·정렬별 첫 요청에서 생성하고 재사용한다. 여러 배열은 동일 장소 객체를 참조한다.
7. 데이터는 있고 정렬 배열만 없으면 DB를 다시 조회하지 않는다. 동일 적재·배열 생성 요청은 작업을 공유한다.
8. 로컬 보관을 구현 대상으로 삼는다. 다른 인스턴스나 배포 후 필요한 과거 버전이 없으면 새로고침을 요구할 수 있다. 공유 저장소는 추가하지 않는다.
9. 보관 시간과 용량, 동시 적재와 대기 시간을 제한한다. 요청 하나의 취소·timeout이 공용 작업을 취소하지 않게 한다.
10. 거리순은 정적 배열 방식에 억지로 포함하지 않는다. 기존 거리순 경로에 미치는 영향은 최종 회귀로 확인하고, 이 작업의 정적 목록 보장을 거리순에도 검증한 것처럼 적지 않는다.

## 4. 확정 요구와 아직 근거가 필요한 값

확정된 것은 위 동작과 구조다. 다음은 아직 사용자 확정값 또는 측정 근거가 없다.

- 이전 버전 보관 시간, 캐시 메모리 예산, 대기 시간, 적재 동시 실행 수·대기열 크기.
- 목표 부하·성장 규모, 실제 관리자 변경 빈도·사용자 스크롤 시간.
- 삭제·노출 중단을 진행 중인 과거 목록에서도 즉시 차단해야 하는 별도 예외의 존재.

작업자는 설정 가능한 제한과 일반 버전 갱신 동작을 구현할 수 있다. 운영 수치나 즉시 차단 예외는 임의로 확정하지 않는다.
기존 1초·4스레드·20만 장소 값은 현재 코드의 값일 뿐 이번 요구의 확정값이 아니다.
예외가 필요하면 행을 조용히 제거해 정상 응답하지 말고, 일관성 계약과 함께 별도 조율한다.

## 5. 근거와 기록 규칙

- 현재 코드, 제안, 코드로 확인한 사실, 측정, 추론, 미검증을 구분한다.
- 과거 측정에는 당시 형상·자원·데이터·측정 범위를 붙인다. 변경된 구현의 성능으로 인용하지 않는다.
- 모든 대안을 구현하거나 부하 시험하지 않는다. 부분 갱신·공유 캐시는 구조적 비교로 먼저 판단한다.
- 수치가 필요한 곳만 측정하고, 실행 전에 주장·최소 실험·결과의 쓰임을 사용자에게 제시한다.
- 각 단계 기록: 결정과 근거 / 반영한 구현 / 검증 결과 / 남은 한계. 아직 실행하지 않은 검증은 예정으로 적는다.

## 6. 진행 방식

메인은 계획·작업 지시·보고 검토·최종 계약 확인을 담당한다. 구현과 테스트는 Claude Opus가 수행한다.
사용자에게 작업 범위를 보여 주고 시작 컨펌을 받은 뒤 할당한다. 승인된 단계 안의 일반 구현 선택은 작업자가 처리한다.
구현 단계 사이에는 보고와 변경 범위를 확인하고 다음 단계로 연결한다. 단계마다 전체 빌드·회귀·부하 시험을 반복하지 않는다.
요구사항·핵심 정책을 바꿔야 할 때만 메인에게 구체적 근거와 함께 올린다.
