# 골격 절감의 분해 — 엔티티·프로젝션·스냅샷 세 방식 비교 (사전 등록)

> **이 문서는 첫 요청 이전에 작성됐다.** 결과를 보고 고치지 않는다.
> 이슈 [#383](https://github.com/SOLPLY/SOLPLY-SERVER/issues/383) 후속 · 브랜치 `perf/#383-place-skeleton-cache`

## 1. 문제

채택 문서([블로그](../../../docs/blog/2026-08-08-place-skeleton-cache.md) §3)의 대안 표에
CPU 증설·페이지 캐시·장소 캐시만 있고, **표준 첫 수단인 DTO 직접 프로젝션이 검토된 기록이 없다.**
"캐시가 프로젝션 대비 얼마나 더 아끼는가"가 수치 없이 비어 있다.

`@Transactional(readOnly = true)`는 이 캠페인의 측정 대상이 **아니다** — `PlaceService`에
클래스 레벨로 이미 붙어 있고(캐시 작업보다 52커밋 앞선 `8a4901c`), 따라서 기존 베이스라인
2.576ms는 readOnly가 켜진 상태의 값이다. 이 사실은 문서에 명시만 하면 된다.

## 2. 원인 가설

목표 부하(300 arrivals/s, size 10)에서의 절감 **0.656ms(2.576 → 1.920)** 의 주성분은
엔티티 하이드레이션 제거 몫이다. 프로젝션도 그 몫의 대부분을 가져간다:

- 27컬럼 × 35.6행 펼침 → 필요한 5필드만 (컬럼 추출 ~960회 → ~50회)
- 요청당 String 약 280개 → 30개 안팎
- 영속성 컨텍스트 등록·LAZY 프록시·컬렉션 래퍼 전부

그러나 프로젝션이 **못 없애는 것**이 있다 — 쿼리 2회의 JDBC 왕복과 커넥션 점유.
[후속 분석](../../../docs/perf/2026-08-08-skeleton-cache-followup.md)이 규명했듯 붕괴 구간의
상황을 키운 것은 "CFS가 창을 자를 때 커넥션을 쥔 스레드가 같이 멈춰 반납이 늦어지는"
일이었고, 이것은 쿼리를 0회로 만든 스냅샷만 없앤다.

## 3. 기술적 선택 (비교 대상)

같은 빌드에서 설정 하나(`solply.place-list.skeleton-source`)로 세 방식 전환:

| 방식 | 골격 5필드의 출처 | 요청당 골격 쿼리 |
|---|---|---:|
| `entity` | 기존 폴백 — 태그 페치조인 엔티티 + 이미지 지연로딩 | 2 |
| `projection` | 스냅샷 로더와 **같은 SQL·같은 조립식**을 페이지 id로 제한해 요청마다 실행 | 2 |
| `snapshot` | 채택안 — 배치 회차마다 미리 지은 `volatile Map` | 0 |

`projection`이 로더의 산출식을 공유하는 것이 설계의 핵심이다 — 값 동치가 구현 공유로
보장되고, `entity`와 쿼리 **횟수**(2회)가 같으므로 두 방식의 차이가 **하이드레이션 비용만**
분리해 보여준다. `snapshot`과 `projection`의 차이는 **쿼리 왕복·커넥션 점유 몫**이다.

## 4. 검증할 주장

> **절감 0.656ms를 분해한다: 하이드레이션 제거 몫(entity−projection)과
> 쿼리 제거 몫(projection−snapshot)을 각각 수치로 기록한다.**

목적은 분해이지 재채택 판정이 아니다. 프로젝션이 절감의 대부분을 가져간다고 나오면
채택 문서의 서사가 그렇게 바뀐다 — 결과에 맞춰 주장을 조정하지 않도록 갈래를 미리 적는다:

- (a) snapshot < projection < entity, 간극 모두 산포 밖 → 두 몫을 각각 수치로 기록
- (b) snapshot ≈ projection → 절감의 사실상 전부가 하이드레이션 몫. "프로젝션을 먼저
  했어야 했다"가 성능 관점에서는 참이 되고, 스냅샷의 남는 근거는 성능이 아니라
  운영 특성(요청당 일이 트래픽과 무관, DB 동반 절감)으로 좁혀진다
- (c) projection ≈ entity → 하이드레이션 가설 자체를 재검토 (JDBC 왕복·파싱이 지배)

**부수 관찰 (420 arrivals/s):** entity는 420부터 붕괴했다(스로틀 100%, p50 1,790ms, 3/3 재현).
쿼리 2회가 남는 projection이 같은 부하에서 붕괴하는지 관찰한다 — 붕괴하면 커넥션
점유 논증이 강화되고, 버티면 붕괴의 지배 요인은 조립 CPU였던 것으로 좁혀진다.

## 5. 성공 조건

### 5.0 전제 — 정합성 게이트

세 방식의 **응답 body와 커서 토큰이 동일**해야 한다. IT(세 방식 × 2정렬 × 2페이지)가 먼저 물고,
벤치 데이터에서 `bench/capture-responses.sh` 방식으로 한 번 더 확인한다.
diff 실행 전에 각 방식의 전환이 실제 반영됐는지 SQL로 검증한다(§7).

### 5.1 지표 계약

효과 크기 예상: projection vs snapshot 차이 **0.2~0.4ms (2배 미만)** →
가이드 A.1에 따라 **응답시간으로 판정하지 않는다.**

| 구분 | 지표 | 근거 |
|---|---|---|
| **1급 (판정)** | 요청당 앱 CPU ms (cgroup `cpu.stat` 누적 ÷ 요청 수), 요청당 statements·digest 실행수 | 가이드 A.3의 1급 기준선. statements는 결정론적 값이라 방식 전환 확인을 겸한다 |
| **보조 (원인)** | 요청당 힙 할당, 커넥션 획득 대기·점유 시간 | 하이드레이션 몫·커넥션 점유 몫의 방향 확인 |
| **참고 (인용 주의)** | 앱 스로틀 비율, p50 | 스로틀은 부분 포화 구간에서 라운드 간 2~3배 산포(직전 캠페인 실측). p50은 목표 부하에서 이미 5ms |
| **주장하지 않음** | p95·p99, 처리량 절대값 | 재현성 미증명·단일 호스트 |

**간극 < 산포면 "구분 불가"로 기록한다.** 직전 캠페인에서 앱 코어의 라운드 간 산포는
±4.5%였다. 세 라운드 중앙값의 간극이 이 폭 안이면 그 몫은 수치로 주장하지 않는다 —
그것도 결과다.

### 5.2 판정

이 캠페인에는 채택/기각이 없다(스냅샷은 이미 채택됐다). 산출물은 §4의 갈래 중
어디에 떨어졌는지와 두 몫의 수치(또는 "구분 불가")다. 결과는 채택 문서(블로그 §3)의
대안 표에 프로젝션 행으로 반영한다.

## 6. 무효 조건 (라운드 유효성)

직전 캠페인 규칙을 그대로 재사용한다.

| 조건 | 판정 |
|---|---|
| 구간 평균 절대 코어가 배정 상한(2.0) 초과 (**cgroup `cpu.stat` 기준**, docker stats 문면 금지) | 라운드 무효 |
| 도착률 결손 2% 초과 (300 구간) 또는 p50 급등이 방식과 무관하게 발생 | 라운드 무효 |
| 컨테이너 재시작·OOM | 라운드 무효 |
| 앱과 DB가 같은 샘플에서 동시 급등 (호스트 스톨 서명) | 라운드 무효 |
| 스냅샷 빌드가 라운드 창과 겹침 (카운트 배치 `cron 0 30 * * * *`) | 라운드 무효 |

**오염 구간만 잘라내지 않는다.** 라운드 전체를 폐기하고 재실행한다.

## 7. 형상과 전환

- 브랜치 `perf/#383-place-skeleton-cache`. 커밋 해시는 실행 시각에 기록한다
- 페이지 크기 **10 (운영 기본값).** 직전 캠페인의 size=20 라운드와 절대값을 비교하지 않는다 —
  세 방식를 이번에 전부 새로 재므로 비교는 캠페인 내부에서 완결된다
- 전환은 `BENCH_APP_JSON`의 `solply.place-list.skeleton-source` + `up -d --force-recreate`
  (`docker restart`로는 환경변수가 반영되지 않는다)
- **전환 검증은 설정값이 아니라 실행된 SQL로 한다.** 매 전환마다 digest를 비우고 요청
  1건을 보내 확인한다: `entity` = 페치조인+이미지 문장, `projection` = 로더 계열 IN 문장,
  `snapshot` = 둘 다 0회
- **라운드 설계 — 방식 교대 + 라운드마다 재생성.** TODO의 미결("세 라운드는 독립 반복이
  아니다 — 커넥션 대기 단조 감소")의 처방을 반영한다:
  - 매 라운드 = `force-recreate`(fresh JVM) → 라운드 내 워밍업 구간(폐기) → 측정 구간
  - 순서는 E→P→S를 한 사이클로 **3사이클** (300 arrivals/s, 판정용) — JVM 밖에서 데워지는
    것(버퍼풀·페이지 캐시)의 추세가 세 방식에 균등하게 분배된다
  - 420 arrivals/s는 방식당 1라운드 관찰, 갈래 판정이 모호할 때만 1회 추가
- 앱 컨테이너 재생성이 라운드마다 있으므로 TODO의 "측정 전 재기동(힙덤프 attach 오염)"은
  자동 충족된다
- 부하 진입점은 edge(`localhost:8082`) 고정. 앱 포트에 직접 쏘지 않는다

## 8. 이 측정으로 말할 수 없는 것

(결과 문서에 그대로 옮긴다)

- **단일 호스트에서 Artillery가 측정 대상과 자원을 공유한다.** 절대 처리량은 운영 용량이 아니다
- **응답시간 개선·차이를 주장하지 않는다** (§5.1 — 효과 크기가 2배 미만)
- **직전 캠페인 수치와의 절대값 비교** — 페이지 크기·라운드 설계가 다르다. 절감의 분해는
  이 캠페인 내부의 세 방식 간극으로만 말한다
- **프로젝션의 장시간 특성** — 라운드가 분 단위다
