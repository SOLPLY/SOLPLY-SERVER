# 태그 필터 목록 조회 — 실행 계획이 흔들리던 문제 (요약판)

## 문제 — 인덱스 검증에서 발견한 잘못된 비용 구조

목록 조회(지역 + 태그 필터 + 정렬 + 페이징)는 이 서비스의 메인 기능이라,
정렬·필터 조합마다 의도한 인덱스를 타는지 실제 API가 만드는 SQL에
`EXPLAIN ANALYZE`를 돌려 검증했다. 무태그·단일 태그 조회는 설계대로였다 —
지역·정렬 인덱스를 순서대로 읽다 11건을 채우면 멈춘다(동네 1곳 57건 확인,
0.076ms).

태그를 세 개 걸자 같은 동네 조회가 `place_tag` 엔트리 **10,536건**을 읽었다.
후보를 좁히는 조건을 더했는데 읽기가 185배 늘었다. 더 이상한 것은 이 10,536이
동네 1곳 조회와 시 단위 18곳 조회에서 똑같았다는 점이다 — 비용이 요청 지역이
아니라 **그 태그가 전국에 몇 곳 붙었는지**를 따라가고 있었다. 조건을 더하면
읽기가 늘고, 조회 범위를 18배 넓혀도 읽기가 그대로다. 크기가 아니라 구조가
틀린 신호였다.

절대 시간은 최악 22.9ms(시 단위 + 메인·옵션 2그룹)로, 지금 트래픽에서 사용자가
체감할 문제는 아니다. 그런데도 파고든 근거는 셋이다.

1. **용량 산수가 성립하지 않는다.** 같은 쿼리의 비용이 입력에 따라
   0.03~23ms(700배)로 흔들리고, 그 폭을 정하는 것이 요청 크기가 아니라
   옵티마이저의 계획 선택이었다. 최악을 약속할 수 없으면 부하 목표(300 arrivals/s,
   DB 2 vCPU) 기준의 용량 계획이 성립하지 않는다.
2. **배포 없이 회귀할 수 있다.** 계획 선택의 입력에는 통계와 버퍼풀 상태가
   들어가므로 코드가 바뀌지 않아도 계획이 뒤집힌다. 실제로 같은 쿼리·같은
   데이터가 측정 창에 따라 0.34ms와 11.3ms를 오가는 입력이 있었다(뒤의 곁가지
   절). 운영에서 이것은 "특정 조합만 가끔 느린데 재현이 안 된다"는 얼굴로
   나타난다.
3. **메인 조회 경로다.** 데이터·트래픽이 자라는 모든 방향이 이 격차를 키운다.

## 배경 둘

**이 쿼리의 성능은 "일찍 멈추기"에서 나온다.** 한 페이지는 11건(10건 + 다음
페이지 판정 1건)이면 된다. 지역·정렬 인덱스를 순서대로 읽으며 조건을 확인하다
11건이 차면 멈추는 것이 설계 의도고, 잘 되면 후보 1,800건 중 47건만 읽고 끝난다.

**그 읽는 순서는 옵티마이저가 정한다.** 당시 쿼리는 장소·통계·태그
매핑(`place_tag`)·태그(`tags`) 4개 테이블을 조인했고, 조인이 있으면 옵티마이저가
어느 테이블부터 읽을지 고른다. 느린 케이스는 이 선택이 뒤집힌 것이었다 —
지역으로 좁힌 뒤 태그를 확인하는 대신, **태그에 붙은 장소를 전국 단위로 모은 뒤
지역으로 걸러냈다.** 읽는 양이 요청한 지역이 아니라 그 태그의 전국 규모를
따라가고, 정렬이 맨 뒤로 밀려 11건에서 멈추는 이점도 사라진다.

## 원인 1 — 옵티마이저에게 준 숫자가 틀렸다

태그 술어는 그룹마다 이런 EXISTS였다.

```sql
EXISTS (SELECT 1 FROM place_tag pt JOIN tags t ON t.id = pt.tag_id
         WHERE pt.place_id = ? AND t.id = :tagId AND t.active = 1)
```

한 술어에 질문 두 개가 섞여 있다. "이 장소에 이 태그가 붙었나"(장소마다 답이
다르다)와 "이 태그가 유효한가"(요청당 한 번이면 되고 어느 장소든 답이 같다).
문제는 뒤쪽이다. `active`에 인덱스도 통계도 없어 MySQL이 고정 어림값 10%를
썼는데 실제 통과율은 100%였고, 태그 세 개가 조합되며 이 오차가 곱해져 태그
후보를 실제 24행 대신 **0.024행**으로 예상했다. 태그부터 읽는 쪽이 압도적으로
싸 보였던 것이다.

이 질문은 요청 검증 단계가 이미 답하고 있었다(비활성·미존재 태그는 저장소 호출
전에 404). 존재는 외래키가 보장한다. 그래서 `tags` 조인을 뗐다.

```sql
EXISTS (SELECT 1 FROM place_tag pt WHERE pt.place_id = ? AND pt.tag_id = :tagId)
```

오추정으로 뒤집히던 케이스가 3.6~49배 돌아왔다(최악 22.9 → 6.44ms). 히스토그램을
만들어도 같은 효과가 나지만(22.6 → 2.62ms), 히스토그램은 자동 갱신되지 않고
덤프에도 안 실려 DB 복원 후 `ANALYZE`를 빠뜨리면 에러 없이 22ms로 되돌아간다 —
성능이 코드에 담기는 조인 제거를 택했다.

## 원인 2 — 숫자를 고쳐도 넓은 지역에서는 여전히 틀렸다

시 단위에서는 지역 후보 1,800 대 태그 후보 1,146이라, 정확한 숫자로도 태그
주도가 선택된다. 그런데 강제로 지역 주도를 돌려 보면 실측은 1.5~1.8배 빠르다.
옵티마이저의 비용 계산에 **"11건 차면 멈춘다"는 항목이 없어서**, 지역부터 읽으면
47건에서 끝난다는 것을 모르고 1,800건 전부를 읽는 것으로 계상하기 때문이다.
통계가 정확해도 남는 비용 공식의 구멍이라 쿼리 수정으로는 닿지 않는다.

### 곁가지 — 버퍼풀이 계획 선택을 뒤집는 메커니즘

계획이 둘인 상태는 비용의 크기만이 아니라 **선택의 변동**도 안고 있었다. 원리는
비용식에 있다.

```text
계획의 계산 비용 = 예상 행 수 × 페이지 읽기 단가
페이지 읽기 단가 = 적재율 × 0.25 + (1 − 적재율) × 1.0
```

옵티마이저는 계획을 고르는 순간 InnoDB에게 "그 계획이 탈 인덱스의 페이지가 지금
버퍼풀에 몇 % 있는가"를 조회해 단가를 섞는다(메모리 0.25 대 디스크 1.0, 4배 폭).
두 후보 계획은 서로 다른 인덱스를 타므로 적재율이 최근 트래픽·배치를 따라 따로
움직이고, 상대 단가가 날마다 달라진다. 대부분의 입력에서는 두 계획의 계산값
격차가 커서 단가가 흔들려도 승자가 안 바뀌지만, **계산값이 접전인 입력(경계
칸)** 에서는 이 흔들림이 심판이 된다. 성립 조건을 나열하면 셋이다 — ① 후보
계획이 둘 이상, ② 계산 비용이 접전인 입력의 존재, ③ 비용식에 날마다 변하는 입력
(적재율).

실례가 **동네 1곳 · 인기순 · 다중 그룹** 조회다. 태그 주도의 계산값은 오추정이
1,000배 깎아 내렸고 지역 주도의 계산값은 조기 종료 미계상이 부풀렸다 — 반대
방향의 오류 둘이 겹쳐, 실제로는 33배 차이(0.34 vs 11.3ms)인 두 계획이 장부상
접전이 됐다. 그 상태에서 측정 창이 다르자 선택이 갈렸다: 발견 당시 창에서는 태그
주도(11.3ms), 재측정 창에서는 지역 주도(0.34ms).

구조가 바뀔 때 이 현상이 어떻게 되는지가 판단의 근거였다.

| | tags 조인 제거까지 (원인 1 해소) | 비트마스크 (원인 2 해소) |
|---|---|---|
| 후보 계획 | 여전히 둘 — 조건 ① 그대로 | **하나** — 조건 ①이 부서짐 |
| 장부의 정확도 | 반만 정직 — 오추정은 지워졌으나 조기 종료 미계상은 잔존 | 비교 자체가 없어 무의미 |
| 경계 칸 | 소멸이 아니라 이동 — 교차점이 태그 규모 700~1,146 구간(지역 후보 1,800 기준)으로 옮겨감. 접전 지대의 실측 격차가 1.5~1.8배로 줄어 독성은 약해졌으나, 교차점이 데이터 분포를 따라 움직여 오늘의 안전 칸이 내일의 경계 칸이 된다 | 선이 하나라 교차점이 없다 — 경계 칸이라는 개념 자체가 소멸 |
| 버퍼풀의 역할 | 여전히 선택을 흔드는 변수 | 같은 계획의 속도 노이즈로 강등 |

통계는 ANALYZE로 고정할 수 있어도 버퍼풀은 고정할 수 없다. 그래서 이 비결정성은
계획이 둘인 한 지울 수 없고, 성능을 좌우하던 변수 목록에서 "측정 창"이 빠진 것은
비트마스크 이후다.

## 선택지 — 판단을 대신하거나, 봉인하거나, 없애거나

옵티마이저의 계획 선택에 개입하는 안이 셋 있었다. 판단을 앱이 대신하거나(동적
힌트), 판단을 강제로 봉인하거나(고정 힌트), 판단 대상 자체를 없애거나(비정규화).
(태그 매핑을 앱 캐시에 두고 앱에서 거르는 네 번째 안은 계획 개입이 아니라 필터
위치의 문제라 아래 별도 절에서 다룬다.)

| | 동적 힌트 | 고정 힌트 | 비정규화 (비트마스크) |
|---|---|---|---|
| 개입 방식 | 태그 카운트 임계 판정으로 조건부 플랜 강제 | 전 구간 플랜 강제 (`JOIN_PREFIX` + `SEMIJOIN(FIRSTMATCH)`) | 조인 제거 — 실행 계획이 하나 |
| 최악 (실측) | 오발 시 42.6배 손해 | 2.6ms (전수 스캔 + 행당 probe) | 0.76ms (전수 스캔, 커버링 인덱스 내 비트 연산) |
| 계획 분산 | 미발동 구간에 잔존 (자연 선택) | 소멸 (강제) | 소멸 (구조) |
| 복잡도 | 임계 정책 + 카운트 캐시 + 힌트 2벌 | 힌트 2벌 + 실행 트리 검증 절차 | 컬럼 1 + 술어 3 + 쓰기 경로 갱신 1 |
| 신선도 의존 판단 입력 | 카운트 캐시 — 낡으면 몇 ms 느린 계획 | 없음 (대신 강제 유효성을 사람이 검증) | 없음 |
| 유지 조건 | 분포 변화마다 임계 재측정 | MySQL 업그레이드·인덱스 변경마다 플랜 검증 | 쓰기 트랜잭션의 마스크 갱신 누락 방지 |
| 새 조회 형태 추가 시 | 형태마다 판정 로직·힌트 배선 추가 | 문장마다 힌트 배선·검증 추가 | 술어 재사용 — 정렬 2종 → 6종 확장에서 태그 필터 무변경 |

**동적 힌트 — 구현 후 철회.** 발동 임계(태그 규모 1,000)가 지역 후보 1,800을
상수로 전제한 값이었는데, 실측하니 전환점이 지역 크기를 따라 이동했다(전환 비율
동네 3곳 0.8~1.0 → 60곳 0.22~0.30). 임계를 정확히 유지하려면 태그×지역 결합
분포까지 읽어야 하고, 그건 옵티마이저의 통계·비용 모델을 애플리케이션에
재구현하는 일이다. 구조적 한계도 있다 — 이 안은 옵티마이저의 판단이 흔들리는
문제(낡는 통계, 버퍼풀 적재율이 흔드는 단가)를 앱의 판단으로 대체하는데, 그 앱의
판단도 신선도에 의존하는 입력(태그별 연결 장소 수 카운트 캐시)을 새로 들인다.
판단 주체만 DB에서 앱으로 옮겨졌을 뿐 "판단 + 낡을 수 있는 입력"이라는 구조가
복제되는 것이다. 캐시를 계획 선택에만 쓰고 결과에는 쓰지 않는 격리로 오발 피해를
"몇 ms 느린 계획"에 가뒀지만, 그 격리가 재측정 부채까지 없애 주지는 않았다.
얻는 것이 최악 2ms → 1ms라 부채가 이득을 초과, 철회.

**고정 힌트 — 근접한 2등.** 최악을 2.6ms로 캡핑하고 계획 분산도 없앤다. 성능
격차는 비정규화 대비 행당 단가 3.4배(행마다 `place_tag` probe vs 커버링 인덱스 안
비트 AND)가 전부다. 탈락 사유는 계약의 성질이다. 힌트는 지목한 자유도만
고정한다 — `JOIN_PREFIX` 단독으로는 세미 조인 전략이 FirstMatch에서
Materialization으로 바뀌어 자연 플랜보다 느려졌고(1.99 → 2.12ms), 의도한 실행
형태를 얻으려면 고정할 자유도를 전부 지목하고 실행 트리로 검증해야 한다. 그리고
문장 단위 계약이라 인덱스 이름·쿼리 블록에 결합되므로 정렬 축 추가, 인덱스
마이그레이션, MySQL 마이너 업그레이드가 각각 재검증 트리거다 — 실제로 비트마스크
도입 닷새 뒤 정렬이 2종에서 6종이 되고 인덱스가 재구성됐다(V36). MySQL 옵티마이저
내부 용어로 쓰인 계약이라 서빙 구조가 바뀌면(인메모리 경로, 검색 엔진) 가져갈
것도 없다.

**비정규화 — 채택.** 조인이 없으면 순서를 고를 일 자체가 없다. 판단을 더 잘하는
대신 판단할 문제를 없앤다. `place_tag` 원본은 source of truth로 남고 마스크는
`BIT_OR` 한 문장으로 리빌드 가능한 투영이라, 마스크로 못 답하는 질의는 원본으로
가면 된다. 같은 마스크 술어를 SQL 경로와 인메모리 정렬 스냅샷이 한
구현(`TagMasks`)으로 공유하고, 평평한 행 구조는 검색 엔진 이관 시 문서 매핑과
1:1이다. 대가는 정합성 계약 둘 — 마스크 신선도와 비트 자리 상한 62 — 인데, 쓰기
경로 하나와 태그 생성 가드 하나에 격리된다(한계 절에서 상술).

**요약.** 세 안 모두 최악 수 ms는 달성한다. 갈린 것은 비용을 어디에 두느냐다 —
동적 힌트는 판정 정확도 유지(재측정 부채 + 판단 입력의 신선도), 고정 힌트는 플랜
검증 절차(문장 수 × 환경 변화), 비정규화는 파생 데이터 정합성(쓰기 경로 계약).
앞의 둘은 시스템이 변할 때마다 반복 지불하고 검증 실패가 조용한 성능 회귀로
나타나는 반면, 비정규화의 계약은 위반이 정합성 문제로 나타나 테스트에 잡히고 지불
지점이 고정돼 있다. 조회 형태와 서빙 구조가 계속 변하는 단계에서는 비용이 변화
횟수에 비례하지 않는 안이 남는다.

### 왜 캐시가 아니라 비정규화였나

캐시로 풀려는 안은 형태를 바꿔 가며 세 번 검토됐고, 각각 다른 자리에서 막힌다.

- **태그 매핑을 캐시하고 앱에서 거른다** — 불가. 거르기는 11건에서 멈추는 반복문 안,
  즉 DB 안에 있어야 하는데 캐시는 그 반복문 밖이다. 앱에서 거르면 DB가 태그를 모른 채
  자른 페이지에서 탈락분이 생길 때마다 다시 채우러 가야 한다.
- **매칭되는 장소 id를 캐시에서 뽑아 SQL `IN`으로 밀어넣는다** — 흔한 태그면 IN 리스트가
  수천 개가 되고, 옵티마이저가 그 리스트와 지역 인덱스 중 무엇으로 갈지 다시 고른다.
  없애려던 계획 선택 문제가 그대로 돌아온다. 캐시가 낡으면 결과가 틀리는 계약도 마스크와
  똑같이 지면서, 얻는 것이 없다.
- **장소 전체를 메모리에 올리고 정렬·필터를 앱에서 한다** — 이건 실제로 나중에 갔던 길이다
  (인메모리 정렬 스냅샷). 다만 순서가 반대면 성립하지 않는다. 결정 시점의 서빙 경로는 DB뿐이었고,
  DB 경로를 먼저 고쳐 둬야 스냅샷이 "실패하면 되돌리면 되는" 부담 없는 실험이 된다. 그리고
  스냅샷에 태그 정보를 싣는 표현이 결국 비트마스크다 — 별도 태그 캐시로 두면 정렬 사진과 태그
  값이 딴 살림이 되어, 한 커밋이 둘 다 바꿀 때 "한 번도 존재한 적 없는 상태"를 읽는 창이 생긴다.

공통 뿌리는 하나다. **캐시는 데이터의 위치를 바꾸고, 비정규화는 표현을 바꾼다.** 이 문제는
"태그 소속이 다른 테이블에 있다"는 표현의 문제였지, 데이터가 멀리 있다는 위치의 문제가
아니었다. 위치를 바꾼 것(스냅샷)은 그다음 단계의 답이었고, 그때도 바뀐 표현 위에서였다.

## 해결 — 태그 집합을 정수 하나로 접었다

태그 id를 비트 자리로 삼아(i번 태그 보유 = i번째 비트가 1) 장소별 태그 집합을
통계 테이블 `place_stats`의 BIGINT 컬럼 하나(`tag_bitmask`)로 비정규화했다. id의
값을 2진수로 바꾼 것이 아니라, BIGINT 64칸을 태그별 체크박스로 쓴 것이다.

```text
장소:  ...0100100  (2번·5번 태그 보유)
요청:  ...0000100  (5번 태그를 찾음)
AND:   ...0000100  ≠ 0 → 통과
```

필터 의미론 "메인 1개 AND (옵션A 중 하나) AND (옵션B 중 하나)"는 그룹별 마스크
세 개가 된다 — 그룹 안의 OR는 마스크 하나가 흡수하고(비트 합집합), 그룹 사이의
AND는 술어 세 개가 만든다.

```sql
AND (ps.tag_bitmask & :mainMask) != 0
AND (ps.tag_bitmask & :subAMask) != 0
AND (ps.tag_bitmask & :subBMask) != 0
```

이제 쿼리는 지역·정렬 인덱스를 순서대로 읽으며 엔트리 안의 마스크에 AND를 걸고,
11건 차면 멈춘다. 거르기가 반복문 안으로 들어왔으니 옵티마이저가 무엇을 알든
상관없다 — 조인이 없어 계획이 하나뿐이다. **행마다 붙던 룩업도 함께 사라졌다.**
조인은 중첩 반복문으로 실행되어 바깥 행마다 안쪽 인덱스를 한 번씩 찾아가는데
(후보 1,800이면 1,800번의 B-트리 탐색), 마스크는 방금 읽은 엔트리 안의 8바이트라
어디도 가지 않는다. 계획 모양이 같은 칸끼리 비교하면 이 단가 차이만으로 2~3배다 —
"최악 = 후보 전수 스캔"을 수용할 수 있었던 건 이 행당 단가가 싸졌기 때문이기도 하다.

읽기의 무늬도 함께 바뀌었다. B-트리 인덱스는 키 순서로 저장되므로
`(town_id, 정렬 키, …)` 인덱스에서 **같은 동네의 엔트리들은 리프 페이지에 이웃해
있다** — 스캔은 구간의 시작을 한 번 찾은 뒤 옆 엔트리로 이동만 하는 연속 읽기고,
시 단위 1,800엔트리도 이웃한 페이지 수십 장이면 덮는다. 반면 조인의 룩업은 전국에
흩어진 place_id로 매번 트리를 새로 내려가 서로 다른 페이지에 착지하는 랜덤
읽기다. 이 차이는 버퍼풀이 식었을 때 벌어진다 — I/O는 페이지 단위라, 연속 스캔은
미스가 나도 수십 장(이웃이라 미리 읽기도 걸린다)이고 랜덤 룩업은 최악이 룩업
수만큼의 미스다. 콜드 상태의 첫 요청까지 조인 구조보다 순하게 만드는 부수
효과다.

이 연속 스캔이 성립하는 전제가 **커버링 인덱스**다. 판정과 반환에 필요한 값이
하나라도 인덱스에 없으면 행마다 테이블 본문(PRIMARY)으로 점프해야 해서 — 그
점프가 곧 랜덤 룩업이라 — 연속 읽기라는 성질이 깨진다. `tag_bitmask`를 두 정렬
인덱스의 **말단**에 실은 이유가 이것이다(V34): 마스크는 탐색 범위를 좁히는 키가
아니라 구간 안에서 행마다 평가되는 필터라 순서상 뒤에 와야 하고, 그럼에도
인덱스에 실려 있어야 걸러낼 행마다 본문 룩업이 붙지 않는다. 스캔 한 번이 필터와
정렬과 반환을 전부 끝내는 구조는 인덱스가 그 셋을 모두 싣고 있을 때만 성립한다.

반대 방향(정렬용 컬럼들을 `place_tag`로 복사해 태그 출발 스캔을 빠르게)도
비정규화로는 대칭이지만, 장소당 매핑 행이 여러 개라 복사가 곱으로 불고 정렬 축
6종마다 인덱스가 새로 서며, 무태그 조회가 여전히 다른 형태로 남아 계획 선택
문제가 되돌아온다. 태그 집합은 정수 한 칸에 들어가지만 정렬 컬럼들은 어디에도
가볍게 들어가지 않는다 — 옮기는 짐의 크기가 방향을 정했다.

## 결과

```text
조인 4개 (tags 포함)          22.9ms   오추정 + 조기 종료 맹점
tags만 제거                    6.44ms   오추정 소멸, 태그 주도는 여전 (분산도 여전)
비트마스크 (place_tag 제거)     0.76ms   계획이 하나로
```

- **비용의 기준이 바뀌었다.** 읽는 양이 "태그가 전국에 몇 곳 붙었나"에서 "요청
  지역에 후보가 몇 곳인가"로.
- **최악이 예측 가능해졌다.** 어떤 태그 조합·정렬이든 계획이 하나라, 최악 =
  지역 후보를 한 번 읽는 비용(시 단위 0.76ms)으로 상한이 잡힌다. 버퍼풀 상태도
  "계획을 뒤집는 변수"에서 "같은 계획의 속도 노이즈"로 내려갔다. 개선 배수보다
  이 분산의 소멸이 더 중요한 결과다.
- **지운 것들.** 힌트 두 벌, 발동 판단 정책, 판단용 카운트 캐시가 전부 삭제됐다.

## 한계와 대가

- **태그에서 출발하는 빠른 경로가 사라졌다.** 매치가 11건이 안 되는 희귀 태그는
  지역 후보를 끝까지 읽는다. 상대적으로 최대 51배 후퇴지만 절대값은 상한(0.76ms)
  안이라 수용했다 — 근거는 요청 빈도가 아니라 최악의 상한이다.
- **마스크는 사본이라 낡으면 결과가 틀린다.** 장소·태그를 고치는 어드민
  트랜잭션이 그 자리에서 원본(`place_tag`)으로부터 다시 계산한다. 원본은 그대로
  있어 마스크는 언제든 다시 만들 수 있는 투영이다.
- **비트 자리는 62개다**(부호 비트 제외). 태그 생성 경로가 초과를 거부한다.
  태그가 어드민이 관리하는 소수 어휘(현재 34개)로 남는다는 전제 위의 설계다.
- **재검토 조건.** NOT 조건은 비트 연산으로 공짜고(`& mask = 0`), 수치 범위는
  컬럼 추가로 같은 스캔에 실린다. 진짜 한계는 지역 후보 수 — 한 요청이 훑는
  후보가 수십만이 되면 전수 스캔이 새 병목이 되고, 그때는 태그별 장소 집합을
  압축 비트맵으로 든 역색인이 다음 칸, 그마저 넘으면(텍스트 검색, 단일 노드
  메모리 초과) 검색 엔진 이관이다. 읽기 모델이 이미 장소 하나 = 행 하나로
  평평해서 행이 곧 문서로 옮겨진다.
