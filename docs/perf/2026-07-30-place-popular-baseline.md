# 인기순 장소 조회 baseline (새 벤치 환경)

> 측정일 2026-07-30 · 설계 [인기순 복합 점수](../superpowers/specs/2026-07-30-place-popular-score-design.md)
> 후속 측정의 기준선. **애플리케이션 코드는 현 develop 상태 그대로다.**

> ## ⚠️ 결론 먼저 — baseline을 확정하지 못했다
>
> 5회 측정에서 전체 p99가 **58.6ms ~ 944ms (16.1배)** 로 흩어졌다. 판정 기준(편차 30% 이내)을
> 크게 벗어난다. **이 문서의 p99·max를 후속 비교의 기준선으로 쓰면 안 된다.**
>
> 원인은 서비스가 아니라 **측정 호스트**다 (§2.3). 라운드마다 1~2회, 앱 2대와 MySQL이
> **동시에** 수 초간 멈췄다가 한꺼번에 밀린 요청을 처리하는 구간이 나타난다.
> 앱 CPU는 그 순간에도 2 vCPU 상한에 닿지 않았고, MySQL은 라운드 전체에서 디스크를
> 2~8블록만 읽었으며, 앱·nginx 로그에 오류가 한 줄도 없다. 호스트(macOS 11코어/18GB)는
> 스왑 26,742MB / 27,648MB(96.7%)를 쓰는 상태였다.
>
> **반면 정상 구간의 수치는 5회 모두 일관되고, 이쪽은 기준선으로 쓸 수 있다** (§2.2).
> 10초 버킷 p99 중앙값 26.8~43.4ms, p50 4~5ms, 오류 0건, 120 req/s 유지.
> 확정 baseline은 호스트를 정리한 뒤 재측정해야 한다 (§2.4).

## 0. 이전 측정을 폐기한 이유

두 차례의 측정을 폐기했다. **수치는 승계하지 않되 폐기 판단은 남긴다** — 신뢰할 수 없는 숫자가
인용되는 위험은 없애면서 "왜 다시 측정했는가"를 보존하기 위함이다.

### (a) `#381` 캐시 벤치 (2026-07-13) — 환경 불일치

| 항목 | #381 캐시 벤치 | 현 기준 |
|---|---|---|
| 실행 환경 | 호스트 `bootRun` (리소스 제한 없음) | 컨테이너 2 vCPU / 2GiB |
| 인스턴스 | 1대 | 2대 + nginx LB |
| 부하 | 50 req/s | 120 req/s |
| 데이터 | 북마크 100만 / 장소 719 | 북마크 1,040만 / 장소 6,000 |
| 조회 범위 | `townId=2` 단일 동네 | 동네 / 시 / 태그 / 스크롤 믹스 |
| 반복 | 상태별 1회 | 3회 + 편차 확인 (실제 5회 수행) |
| 부하 프로파일 | Artillery `environments` 병합 버그로 의도(55초)와 다르게 175초 실행 | `phases` 단독 정의 |

환경이 이만큼 다르면 **상대 비교조차 성립하지 않는다.** 산출물(시나리오·리포트·쿼리로그·문서)을
제거하고 전면 재측정했다. `#379` 인덱스 벤치는 V19 인덱스 확정의 근거이므로 유지한다.
인기순 벤치(2026-07-30)는 수치를 승계하지 않고 **결론만 인용**한다 — v0 기각(매 요청 실시간
집계는 이 규모에서 성립 불가)은 규모가 커질수록 강해지는 결론이다.

### (b) 2026-07-30 1차 baseline — p6spy 쿼리 로깅 오염

새 벤치 환경(앱 2대 + LB)에서 측정했으나 **p6spy 쿼리 로깅이 켜진 채였다.**
`application.yml`의 `logging.level.p6spy: INFO`가 컨테이너에도 그대로 적용돼,
초당 약 240개 쿼리를 **전문(full SQL text)으로** 로깅했다.

당시 실측된 증상:

| 증상 | 값 |
|---|---|
| 앱 CPU | 2 vCPU 포화 |
| PK 단건 조회 응답 | 최대 495ms |
| 전체 42,959쿼리 중 100ms 초과 | **7건** |
| r1 p99 vs r2 p99 | 149.9ms vs 804.5ms (**437% 어긋남**) |

**DB가 아니라 앱이 정체한 것**이 핵심이다. 42,959쿼리 중 100ms를 넘긴 것이 7건뿐인데
응답은 수백 ms였다 — 느린 것은 쿼리가 아니라 그 쿼리를 로깅하는 앱이었다.

조치로 `docker/docker-compose.bench.yml`에 `LOGGING_LEVEL_P6SPY: "OFF"`를 추가했다.
**환경변수는 `docker restart`로 반영되지 않는다** — 컨테이너를 재생성(`up -d --force-recreate`)해야 한다.
이번 측정 전 재생성 후 검증한 결과는 아래와 같다.

```
재생성 전 : docker logs solply-bench-app-1 | grep -c p6spy  → 92,316
재생성 후 : LOGGING_LEVEL_P6SPY=OFF 적용 확인
            요청 20건 전송(모두 200) 후 grep -c p6spy → app-1: 0, app-2: 0
```

> 쿼리 **개수**를 세야 할 때만 `LOGGING_LEVEL_P6SPY=INFO`로 별도 라운드를 돌리고,
> 그 라운드의 레이턴시는 다른 라운드와 비교하지 않는다.

## 1. 환경

### 구성

| 구성요소 | 스펙 |
|---|---|
| 앱 (`solply-bench-app-1` / `-2`) | 컨테이너 **2 vCPU / 2GiB** × 2대, heap `-Xmx1280m`, Tomcat max 50, Hikari 10 |
| LB (`solply-bench-lb`) | nginx 1.27-alpine, `least_conn`, keepalive 64, 액세스 로그 off |
| MySQL (`solply-bench-mysql`) | 8.0, **2 CPU / 3GiB**, `innodb_buffer_pool_size=2G`, redo 1G, max_connections 200 |
| Redis (`solply-bench-redis`) | 7, 1 CPU / 512MiB (앱 기동 의존성. 이 경로에서는 사용하지 않음) |
| 네트워크 | 전용 브리지 `172.28.0.0/24`, 컨테이너별 고정 IP (nginx upstream IP 캐시 함정 회피) |
| 측정 호스트 | macOS, 11 코어 / 18GB. Docker Desktop VM 11 vCPU / 7.65GiB |

부하는 **항상 LB(`localhost:8082`)로** 보낸다. 개별 인스턴스 포트는 노출하지 않는다 —
실환경에서 클라이언트가 인스턴스를 지정할 수 없는 조건을 그대로 재현하기 위함이다.

> **MySQL 스펙을 4 CPU / 4GiB → 2 CPU / 3GiB로 낮췄다 (2026-07-30).**
> 종전 값은 `#379` 인덱스 벤치 때 "DB가 병목이 되지 않게" 잡은 것인데 캐시 도입 후 근거가 사라졌다.
> 이 문서의 측정은 **4 CPU 시절에 수행됐으나 결론은 바뀌지 않는다** — 깨끗한 라운드의 MySQL CPU 피크가
> 31.5~41.6%(0.32~0.42코어)로 400% 배정 대비 활용률이 10%였고, 요청당 MySQL CPU 2.01ms 기준
> 2 vCPU의 70%면 약 697 req/s를 감당해 앱 쪽 한계(559 req/s)보다 높다. 병목은 계속 앱이다.
> 부수 효과로 컨테이너 메모리 배정 총합이 8.5GiB → **7.5GiB**가 되어 Docker VM 용량(7.65GiB) 안에 들어왔다.

### ⚠️ 이 환경의 구조적 한계 — DB가 "논리적으로만" 분리돼 있다

| | 분리됨 | 공유됨 |
|---|---|---|
| 프로세스·컨테이너·cgroup 한도 | ✅ | |
| 접근 방식 (TCP, 공유 메모리 아님) | ✅ | |
| 물리 호스트 · 커널 · 디스크 | | ❌ 같은 맥북 / 같은 Docker VM |
| 네트워크 | | ❌ docker bridge (호스트 내부) |

두 방향으로 실제와 어긋난다.

**① 측정이 실제보다 유리하다 — 네트워크 지연이 사실상 없다.**
docker bridge RTT는 0.05~0.1ms인데 실제 RDS는 같은 AZ여도 0.3~1ms다.
baseline에서 **요청당 14.2 statements**가 나가므로:

```
현재:  14.2 × 0.05ms ≈ 0.7ms
실제:  14.2 × 0.5ms  ≈ 7.1ms      →  요청당 +6ms
```

**p50이 5ms인 상황에서 +6ms는 두 배**다. 실제 분리 환경으로 옮기면 이 문서의 절대치는 크게 나빠진다.
요청당 문 수를 줄이는 것이 네트워크 지연을 줄이는 가장 직접적인 수단이므로,
플랜 C에서 캐시 구조를 볼 때 14.2라는 수치를 함께 다룬다.

**② 측정이 실제보다 불리하다 — 앱과 DB가 같은 디스크·커널을 공유한다.**
호스트 스왑이 터지면 앱과 DB가 **동시에** 멈춘다(§2.3). 실제 분리 환경에서는 앱 서버가
스왑해도 DB 인스턴스는 영향을 받지 않는다.

### 부하 프로파일

`load-test/scenarios/place-list-popular.yml`

- 웜업 30초 @ 20 req/s → 램프 30초 @ 30→120 → 지속 120초 @ 120 req/s (총 180초)
- 시나리오 믹스: 동네 40 / 시 단위 20 / 태그 필터 20 / 무한 스크롤 20
- 매 라운드 전 캐시 워밍 (`townId` 201 및 301~318 × 4회)

**부하 목표 산정 (설계 §1.1)**

```
일일 총 요청 = DAU 20,000 × 세션 1.5회/일 × 세션당 8호출 = 240,000
평균 RPS     = 240,000 / 86,400                          = 2.8
예상 피크    = 2.8 × 8 (여가 앱 저녁·주말 집중)           = 22 req/s
목표 120 req/s = 예상 피크의 5.5배 = DAU 약 11만까지의 헤드룸
```

→ 결과는 **"지금 충분한가"가 아니라 "언제까지 충분한가"** 로 읽는다.
반대로 22 req/s에서 이미 힘든 설계라면 즉시 기각할 근거가 된다.

### 버퍼풀 판정 — 스키마가 버퍼풀보다 큰데 왜 올리지 않았는가

| 테이블 | data | index | 합계 |
|---|---:|---:|---:|
| `bookmarks` | 627MB | 2,107MB | **2,734MB** |
| `users` | 11MB | 21MB | 32MB |
| `places` | 2MB | 1MB | 2MB |
| 그 외 | <1MB | <1MB | <1MB |
| **스키마 합계** | | | **2,770MB** |

스키마 2,770MB > 버퍼풀 2,048MB다. 플랜 Task 4 Step 5의 기준(1,900MB 초과 시 3G로 증설)에
걸리는 수치다. **그러나 증설하지 않았고, 그 판단이 실측으로 정당화됐다.**

| 근거 | 내용 |
|---|---|
| hit rate | 5라운드 전부 **99.9999% ~ 100.0000%** |
| 라운드당 디스크 읽기 | **2 ~ 8 블록** (`Innodb_buffer_pool_reads`) |
| 라운드당 쓰기·fsync | **0** |

북마크 분포가 Zipf(동네 가중치 × 동네 내 Zipf 0.9)라 **hot working set만 상주하면 충분**하다.
전체 2,770MB가 아니라 실제로 접근되는 부분집합만 버퍼풀에 올라오면 되고, 그것이 2GB에 들어간다.

물리적으로도 올릴 여지가 없었다 — Docker Desktop VM 가용 메모리가 7.65GiB인데
이미 앱 2×2GiB + MySQL 4GiB + Redis 0.5GiB를 배정한 상태다.
**올릴 여지가 없었으나 올릴 필요도 없음이 실측으로 확인됐다.**

### 2.1 라운드별 집계 (5회)

r1~r3이 계획된 3회, **r4·r5는 불안정 원인을 조사하려고 추가한 라운드**다.

|---|---:|---:|---:|---:|---:|
| 요청 수 | 20,785 | 20,798 | 20,660 | 20,732 | 20,752 |
| HTTP 200 | 20,785 | 20,798 | 20,660 | 20,732 | 20,752 |
| **성공률** | **100%** | **100%** | **100%** | **100%** | **100%** |
| 오류 | 없음 | 없음 | 없음 | 없음 | 없음 |
| 실측 RPS | 118 | 110 | 118 | 116 | 113 |

**p99 편차 판정: 불합격.** 최소 58.6ms / 최대 944ms = **16.1배**. 기준 30%를 크게 초과한다.
p50은 5회 모두 5~7ms로 일치하는데 p99만 16배 벌어졌다 — 처리 능력의 문제가 아니라
**소수의 극단 지연이 라운드마다 다르게 섞여 들어온 것**이다.

**엔드포인트 간 차이가 없다.** 시 단위(정렬 대상 1,800개)와 동네 단위(100개)의 p99가 사실상 같고,

**같은 세션에서 p1 직후에 실행돼 스톨 구간에 걸릴 확률이 낮기 때문**이다.

**\* 200%를 넘는 값은 cgroup 상한상 물리적으로 불가능하다.**
`cpus: 2`는 CFS 쿼터(100ms 주기당 200ms)로 강제되므로 6초 샘플 구간의 평균이 200%를 넘을 수 없다.
문제의 샘플은 r1 `17:03:18`(app1 278.6% / app2 281.1% / MySQL 133.5%)과
r2 `17:10:01`(173.5% / 220.2% / 105.2%) — **세 컨테이너가 같은 한 샘플에서 동시에 튀었다.**
호스트 스톨로 `docker stats`의 측정 구간 자체가 왜곡된 것으로 본다 (§2.3).

`Threads_connected`가 5회 모두 정확히 21인 것은 **Hikari 10 × 2 인스턴스 + 샘플러 1**이다 —
두 인스턴스가 모두 DB에 붙어 있었다는 교차 확인이 된다.

### 2.2 정상 구간 — 이쪽은 일관된다

Artillery의 10초 버킷을 라운드별로 펼치면, 흩어진 것은 **전체가 아니라 소수 버킷**이다.

| 라운드 | 버킷 p99 중앙값 | 버킷 p99 최소 | 버킷 p99 최대 | p99 > 100ms 버킷 |
|---|---:|---:|---:|---:|
| r1 | 141.2 ms | 12.1 ms | 727.9 ms | 10 / 19 |
| r2 | 37.7 ms | 18 ms | 2,101.1 ms | 8 / 19 |
| r3 | **32.8 ms** | 12.1 ms | 273.2 ms | 3 / 19 |
| r4 | **26.8 ms** | 10.1 ms | 584.2 ms | 4 / 19 |
| r5 | **43.4 ms** | 21.1 ms | 1,587.9 ms | 6 / 19 |

r1을 제외하면 버킷 p99 중앙값이 **26.8 ~ 43.4ms** 로 모인다. 가장 깨끗했던 r3의
지속 부하 구간(120 req/s, 12개 버킷)은 다음과 같다.

```

17:15:50  1456 req   p50 4   p95 10.1  p99 16     max  38
17:16:00  1435 req   p50 5   p95 12.1  p99 23.8   max  70
17:16:10  1449 req   p50 4   p95 10.1  p99 16.9   max  63
```

**스톨 구간을 빼면 p95 7~16ms / p99 12~38ms**로, 120 req/s 지속 부하에서 매우 안정적이다.

> **r1만 유별난 이유는 JIT 워밍업이다.** r1은 컨테이너 재생성 직후 첫 라운드였고,
> 열화가 `17:03:10 ~ 17:04:40`에 몰렸다가 이후 p99 25~40ms로 **단조 회복**했다.
> 이 형태는 스톨(급격한 스파이크 후 즉시 복귀)과 구별된다.
> → **재측정 시 첫 라운드는 워밍업으로 간주하고 버려야 한다.**

### 2.3 스톨의 원인 — 서비스가 아니라 측정 호스트다

r5의 스톨(`17:27:00 ~ 17:27:20`, p99 1,587.9ms / max 2,603ms) 직전·직후 CPU 시계열이다.

```
시각        app1     app2    mysql
17:26:47   19.29%   15.75%  12.68%
17:26:52   99.74%   90.01%  56.51%   ← 세 컨테이너 동시 급등
17:26:57   20.56%   23.02%  15.64%
17:27:03   95.75%   96.21%  23.79%   ← 스톨 구간
17:27:09   99.86%   86.50%  57.33%
17:27:15   18.40%   22.32%  16.05%
17:27:21   80.16%   87.07%  49.60%
17:27:26   19.27%   19.92%  15.81%   ← 정상 복귀
```

**서비스 병목이라면 나올 수 없는 조합이다.**

| 관찰 | 서비스 병목 가설이 설명하지 못하는 이유 |
|---|---|
| 앱 CPU가 스톨 중에도 **100% / 200%** (= 절반) | CPU 포화라면 200%에 붙어 있어야 한다 |
| 앱 2대가 **동시에** 느려짐 | 한 인스턴스의 GC/JIT이라면 LB가 다른 쪽으로 흘려 반쪽만 느려진다 |
| MySQL도 **같은 순간** 급등 | 앱이 원인이면 DB는 오히려 한가해진다 |
| 라운드 전체 디스크 읽기 **2~8블록**, 쓰기 **0** | I/O 대기가 원인일 수 없다 |
| 앱·nginx 로그에 오류·경고 **0건** | 타임아웃·커넥션 고갈이라면 로그가 남는다 |
| `Threads_running` 피크 **3~5** | DB 큐잉이 아니다 |
| p50까지 함께 상승 (r2 한 버킷에서 5ms → 115.6ms) | 꼬리만이 아니라 **모든 요청이 함께 멈췄다** |
| HTTP 200 **100%**, 5xx·타임아웃 0 | 실패가 아니라 순수한 지연 |

**모든 요청·모든 컨테이너가 동시에 멈췄다가 함께 풀린다** — Docker Desktop VM 전체가
호스트에 의해 잠시 밀려난 형태다. 측정 중 호스트 상태:

| 항목 | 값 |
|---|---|
| 호스트 | macOS, 11 코어 / 18GB |
| load average (r3 시작 / 종료) | 4.96 → 9.81 |
| **스왑 사용** | **26,742MB / 27,648MB (96.7%)** — 18GB 머신에 27GB 스왑 |
| 누적 pageout | 19,334,161 |
| 동시 실행 중인 호스트 앱 | ChatGPT/Codex, Orca, IntelliJ IDEA, Chrome, Docker Desktop |

컨테이너 cgroup 쓰로틀링도 확인했다. 5라운드 누적:

| 컨테이너 | 쓰로틀된 주기 | 비율 | 누적 쓰로틀 시간 |
|---|---:|---:|---:|
| app-1 | 426 / 15,402 | 2.8% | 122.9s |
| app-2 | 461 / 15,400 | 3.0% | 120.9s |

r3 한 라운드만 떼어내면 app-1은 14주기(3.8s) / app-2는 18주기(2.2s)로 **1~2%**에 불과하다.
쓰로틀링이 존재하긴 하나 그것만으로 1.5초 지연을 설명하지 못한다.
호스트 스톨이 주 원인이고 쓰로틀링은 부차적이다.

### 2.4 이 baseline을 어떻게 쓸 것인가

| 지표 | 기준선으로 쓸 수 있는가 | 값 |
|---|---|---|
| 성공률·오류 | ✅ | 100% / 0건, 5회 전부 |
| 처리량 | ✅ | 120 req/s 목표 대비 실측 110~118 유지 |

| 정상 구간 p99 (10초 버킷 중앙값) | ✅ | 26.8 ~ 43.4 ms (r1 제외) |

| **전체 p99 · max** | ❌ | 호스트 스톨에 오염됨 (58.6 ~ 944ms) |

**재측정 조건 (확정 baseline을 얻으려면)**

1. 호스트의 다른 애플리케이션(IDE·브라우저·에이전트)을 종료하고 스왑 압박을 해소한다.

4. 라운드 중 `docker stats`가 컨테이너 CPU 상한(앱 200%)을 넘는 샘플을 내면
   그 라운드는 호스트 스톨에 오염된 것으로 보고 폐기한다. — 편차 판정보다 빠른 조기 경보다.

부하와 별개로, `townId=201`(서울 전체, 정렬 대상 1,800개)을 LB 경유로 15페이지 순회했다.

| **중복 검출** | **0** |
| 누락 | 0 (15 × 20 = 300, 전부 채워짐) |

두 인스턴스에 실제로 분산됐음을 순차 30요청의 CPU 사용량 증가분으로 확인했다
(app-1 136,689µs / app-2 235,689µs — 양쪽 모두 증가).
같은 요청을 두 번 보냈을 때 상위 5개 장소의 `placeId:bookmarkCount`도 완전히 일치했다.

```
10001:69784 10901:64533 10501:62006 11001:51885 10002:48264
10001:69784 10901:64533 10501:62006 11001:51885 10002:48264
```

> **⚠️ 이 결과를 "정합성 문제 없음"으로 읽으면 안 된다.**
> 설계 §3.2가 예측한 결함은 *인스턴스별 캐시 스냅샷의 세대가 어긋날 때* 발생한다.
> 이번 조건에서는 그 전제가 성립하지 않았다.
>
> - `TownPlacesCache`는 `refreshAfterWrite` 10분 / `expireAfterWrite` 1시간이다.
> - 두 인스턴스가 **같은 워밍 사이클에서 몇 초 차이로** 스냅샷을 적재했다.
> - 벤치 시드는 정적이고, 측정 중 `Innodb_data_writes`가 **0**이었다 — 쓰기가 한 건도 없었다.
>
> 즉 두 스냅샷이 **구조적으로 동일할 수밖에 없는 상태**에서 잰 것이다.
> 중복 0은 "이 조건에서 재현되지 않았다"는 사실일 뿐, §3.2의 예측을 반증하지 않는다.
> 결함을 실측하려면 **한쪽 인스턴스의 soft TTL이 만료돼 재적재되는 순간에 북마크 쓰기를 섞어
> 스냅샷 세대를 어긋나게 한 뒤** 커서 페이징을 순회해야 한다. 이 시나리오는 별도로 설계한다.

## 4. 해석

### 4.1 부하 분산은 균등하다

nginx `least_conn`이 두 인스턴스에 고르게 분산했다. cgroup 누적 CPU 사용량 기준:

| 구간 | app-1 | app-2 | 비율 |
|---|---:|---:|---|
| r3 한 라운드 | 49.37 CPU-s | 54.60 CPU-s | 47.5% / 52.5% |
| r1~r5 누적 | 376.29 CPU-s | 388.50 CPU-s | 49.2% / 50.8% |

메모리도 546~592MiB로 두 인스턴스가 나란하고, `Threads_connected`가 5회 모두 21
(Hikari 10 × 2 + 샘플러 1)로 양쪽 풀이 모두 살아 있었다.
**LB 구성 자체는 병목이 아니다** — LB CPU 피크가 최대 36.2%다.

### 4.2 병목은 앱도 DB도 아니다 — 이 부하에서는 병목이 없다

DB는 확실히 병목이 아니다.

- 버퍼풀 hit rate 99.9999~100%, 라운드당 디스크 읽기 **2~8블록**, 쓰기·fsync **0**
- `created_tmp_disk_tables` **0** — filesort가 디스크로 내려가지 않았다
- `Threads_running` 피크 **3~5** (max_connections 200)
- MySQL CPU는 깨끗한 라운드(r3·r4)에서 **31.5~41.6% / 400%**

앱도 포화와 거리가 멀다. r3의 CPU-초를 요청 수로 나누면:

| 항목 | 값 |
|---|---:|
| 앱 2대 합계 CPU 소비 (r3) | 103.97 CPU-s |
| MySQL CPU 소비 (r3) | 41.66 CPU-s |
| 처리 요청 (워밍 포함) | 20,736 |
| **요청당 앱 CPU** | **5.01 ms** |
| **요청당 MySQL CPU** | **2.01 ms** |

요청당 앱 CPU 5.01ms가 p50 응답 5ms와 거의 같다 — **대기가 아니라 계산이 전부**라는 뜻이다.
캐시 히트 경로라 I/O 대기가 없고, 응답 시간이 곧 CPU 시간이다.

병목이 있다면 그것은 **측정 호스트**다 (§2.3). 서비스 자체는 120 req/s에서 여유가 있다.

### 4.3 성장 헤드룸 — 실제로 몇 배인가

**측정된 CPU 예산으로 계산한 값이며, 그 부하를 실제로 걸어보지는 않았다.**

```
앱 CPU 예산  = 2 vCPU × 2대 = 4 vCPU
요청당 앱 CPU = 5.01 ms (r3 실측)

CPU 이론 상한 = 4,000 ms/s ÷ 5.01 ms = 약 800 req/s
운영 목표(70%)= 약 560 req/s
```

| 기준 | req/s | 대응 DAU | 현 목표 대비 |
|---|---:|---:|---|
| 설계상 예상 피크 (DAU 2만) | 22 | 20,000 | — |
| **이번 측정 부하** | **120** | 약 110,000 | 예상 피크의 **5.5배** |
| r3 실측 시 앱 CPU 사용률 | — | — | **4 vCPU의 15%** |
| CPU 예산 기준 운영 상한(70%) | 약 560 | 약 510,000 | 목표 120의 **약 4.7배** |
| CPU 예산 기준 이론 상한 | 약 800 | 약 730,000 | 목표 120의 **약 6.7배** |

MySQL 쪽은 더 여유롭다 — 요청당 2.01ms, 4 CPU 예산이면 120 req/s에서 **6%**다.

**읽는 법.** "지금 충분한가"의 답은 명백히 예다(예상 피크 22 req/s의 5.5배에서 CPU 15%).
"언제까지 충분한가"의 답은 **DAU 50만 부근까지 현 구조로 버틴다**는 것이다.
다만 이 계산에는 두 가지 조건이 붙는다.

1. **캐시가 계속 히트한다는 전제**다. 요청당 5ms는 `TownPlacesCache`가 스냅샷을 들고 있어서
   나온 값이다. 캐시를 걷어내거나 스냅샷이 커지면 이 수치가 통째로 바뀐다 (설계 §3.3, 플랜 C).
2. **CPU만 본 상한**이다. 실제로는 그 전에 메모리·GC·커넥션 풀이 먼저 걸릴 수 있다.
   현재 heap 사용량은 550~592MiB / 1,280MB로 여유가 있으나, 스냅샷 크기가 town 수와
   장소 수에 비례해 늘어난다는 점은 감시 대상이다.

### 4.4 플랜 B·C로 넘기는 것

| 항목 | 판단 |
|---|---|
| 확정 baseline | 호스트 정리 후 재측정 필요 (§2.4). 이 문서의 정상 구간 수치는 잠정 기준선으로 쓴다 |
| 무한 스크롤 정합성 | 중복 0. **단 결함이 드러날 조건에서 재지 않았다** (§3). 세대 어긋남 시나리오를 따로 설계 |
| 성장 헤드룸 | 예상 피크의 25배 수준. **플랜 B의 범위를 늘릴 근거는 없다** |
| 요청당 14.2 statements | 캐시 히트 경로임에도 요청당 14개 문이 나간다. 인증·북마크 여부 조회 등이 섞인 것으로 보이며, 플랜 C에서 캐시 구조를 볼 때 함께 확인한다 |
| 네트워크 지연 부재 | 이 환경은 DB가 논리적으로만 분리돼 있다(§1). 실제 분리 환경에서는 요청당 약 **+6ms**가 예상되므로 절대치를 그대로 옮기지 않는다 |
| MySQL 스펙 하향 | 4 CPU / 4G → 2 CPU / 3G. 결론 불변이나 **확정 baseline은 새 스펙으로 다시 잰다** |

### 무한 스크롤 정합성

```bash
TOKEN=$(sed -n '2p' data/users.csv)
node -e "
const token = process.argv[1];
const base = 'http://localhost:8082/api/places?townId=201&isBookmarkSearch=false&sort=POPULAR&size=20';
(async () => {
  const seen = new Map();
  let cursor = null, page = 0, dup = 0;
  while (page < 15) {
    const url = base + (cursor ? '&cursor=' + encodeURIComponent(cursor) : '');
    const body = await (await fetch(url, { headers: { Authorization: 'Bearer ' + token } })).json();
    for (const it of (body.data?.places ?? [])) {
      if (seen.has(it.placeId)) { dup++; console.log('DUP', it.placeId, 'page', page, '최초', seen.get(it.placeId)); }
      else seen.set(it.placeId, page);
    }
    cursor = body.data?.nextCursor; page++;
    if (!cursor) break;
  }
  console.log('pages=' + page + ' unique=' + seen.size + ' duplicates=' + dup);
})();
" "$TOKEN"
```
