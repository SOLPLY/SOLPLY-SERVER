# 실행 기록

측정 순서·판정·폐기 사유의 원장. 사전 등록(README)은 고치지 않고 여기에만 적는다.

## 검출력 게이트 (P-gate)

- `P-gate` (18:03): **무효 — 폭주 미발화.** `30-hot-page-storm.sh`가 30행 `$N행`에서 죽음.
  이 로케일의 bash 5.2가 `$N` 뒤 한글을 변수명으로 파싱(`bash -uc 'N=3; echo "($N행)"'`로 재현,
  LC_ALL=C에서는 정상). `${N}행`으로 수정. 이 라운드의 0들은 판정에 쓰지 않는다.
- `P-gate2` (18:05): **통과.** 무부하 폭주 15초, 적용 UPDATE 1,081,254회(초당 72,083).
  synch 대기 Δ 1.249억 회 / 4,967ms (`undo_space_rseg_mutex` 686만/456ms,
  `index_tree_rw_lock` 337만/131ms 등), 히스토리 리스트 0→최대 1,166 진동,
  전역 더티 0→약 940, 행 락 대기 0→10,985. **판명 2건**: ① `innodb_rwlock_*` 전역 카운터는
  폭주 중에도 전부 0 — 판정 제외(README §5 주석 반영) ② `buffer_page_read_undo_log`는 읽기
  동시성이 없어 0이 정상 — 이 카운터의 검출력은 마지막 P 라운드(부하 위 폭주)에서 확정한다.
- 오염 복구: B팔 배치 1회 발화(18:09), 무부하 소요 **2.518s**. place_id=1 카운트 1로 복귀 확인.

## 스로틀 게이트 (r0-warmup, 300 arrivals)

- `r0-warmup` separated, 300 arrivals (18:10~18:15): 폐기 라운드(설계상 JIT 워밍업).
  100,702요청 전부 200·실패 0·p50 6ms. 그러나 앱 cgroup 스로틀 **24.2%** (662/2,735 주기,
  라운드 전체 창) ≫ 기준 5% → **게이트 발동, 이후 전 라운드 240 arrivals/s로 하향.**
  p95 459.5ms·p99 1,495.5ms는 스로틀 오염 값이라 인용 금지. MySQL 스로틀은 1.6%.
  부수 관찰(폐기 라운드라 참고만): 배치(B팔) 부하 중 소요 3.103s, 배치 직후 census —
  `places` 전 인덱스 dirty 0 / `place_stats` PRIMARY만 dirty 12
  (`idx_place_stats_town_score`는 dirty 0 — `count_calculated_at`이 인덱스 말단에 없어
  카운트 불변이면 세컨더리 엔트리가 안 바뀐다). cron 오염 없음.

## 부하점 확정 (r0b-warmup240)

- `r0b-warmup240` separated, 240 arrivals (18:17~18:22): 앱 스로틀 **5.6%** (153/2,728,
  라운드 전체 창 — 사다리 포함 과대측정). 기준 5%를 근소 초과하지만 **240으로 확정**한다.
  사유: ① 측정창 분해 수단이 없어 5.6%는 상한값이다 ② 지연 판정의 1급 지표는 DB 내부
  digest 실행당 값이라 앱 스로틀과 독립이다 ③ 더 내리면 목표 부하(300 arrivals)와의 거리만
  커진다. **이 근소 초과는 클라이언트 지연(p50 포함)을 판정에 쓰지 않는 기존 계약을 재확인
  하는 근거로 남긴다.** 결과 문서 "말할 수 없는 것"에 명시할 것.
  배치 소요 3.740s, places dirty 0 / place_stats PRIMARY dirty 14 — r0과 재현 일치.

## 본 라운드 (240 arrivals, 18:23~19:03)

- 실행 순서: r1-sep → r2-col → r3-sep → r4-col → (r5-storm) → r5b-storm. 라운드 간 60초 휴식.
- **r5-storm 폐기**: 배치 창이 열린 직후(18:50:45) 실행 셸이 외부에서 종료됨. 폭주는 이미
  발화된 상태였고(구간 카운트 403,276 vs 원본 100), 복구 배치 후 r5b로 재실행. r5의
  잔존 산출물(C창 diff·pre census)은 판정에 쓰지 않는다.
- **r5b 폭주 소요 이상**: 설계 15초가 244.3초로 늘어짐. 발화 클라이언트 파이프에 선적재된
  문장이 경합 속 소비 지연으로 늘어진 것으로 추정(미규명). 결과적으로 B창이 "부하 위 79초 +
  부하 없는 165초"의 혼합 창이라 r5b의 digest 비율은 인용하지 않는다. 검출력 목적(부하 위
  겹침에서 카운터 반응)은 앞 79초로 충족: row_lock_waits +14,267, history_len 최대 1,623,
  MySQL 스로틀 54.7%, 그리고 실패 0.
- 라운드 유효성: 전 라운드 도착 결손 0·실패 0·cron 오염 없음·cgroup 상한 초과 없음.
  앱 스로틀 r1 5.75%로 기준 5% 근소 초과(r3 4.80, r2 4.25, r4 3.48) — r0b에서 수용한
  논리(측정창 분해 불가한 상한값 + 판정은 DB 내부 지표) 그대로 유효 처리하고 기록.

## 계측 판명 (판정 제외 목록)

1. `buf_block_lock`(페이지 래치) 인스트루먼트가 이 빌드에 없음 → PFS synch 창 diff로 근사.
2. `innodb_rwlock_*` 전역 카운터: 전 라운드·전 창에서 0 — 죽은 채널, 판정 제외.
3. `buffer_page_read_undo_log`: 최강 양성 대조에서도 0. 언두 "순회"가 아니라 언두 페이지
   **디스크 읽기** 카운터라 전 데이터 상주 풀에서 구조적 0 — 0을 "순회 없음"의 증거로 쓰지 않는다.
4. `Innodb_buffer_pool_pages_dirty`(전역): pre-census(버퍼 풀 전수 조회) 실행에 오염되어
   배치 신호와 분리 불가 — 더티 판정은 테이블 귀속 census로만 한다.

## 판정 (사전 등록 §5 대응)

- 성공조건 1 **성립**: B팔 places Δdirty 0/0, A팔 places Δdirty +126/+65
  (PRIMARY 66페이지 중 66/65 = 사실상 전부). 자릿수 차이·2/2 재현.
  r2의 +126에는 미러 인덱스 최초 정착(18→60페이지 분할) 몫 60이 포함 — r4(정착 후)의
  65가 정상 상태 값. B팔 place_stats Δdirty 45 vs 12는 페이지 클리너의 커밋 전 flush
  진행도 차이로 폭이 있으나 "0 vs 전부" 판정에 무관.
- 성공조건 2 **성립**: 검출력 게이트 P-gate2 + r5b 겹침 79초에서 카운터 반응 확인.
- 성공조건 3 **성립 (240 arrivals 한정)**: B팔 2라운드 실패 0·결손 0, 배치 창 실행당
  레이턴시 최대 1.83배(자릿수 악화 없음).
- 성공조건 4: 팔 간 읽기 지연 차이 **구분 불가** — A팔 내 재현 깨짐(r2 1.31~1.59x vs
  r4 1.05~1.20x), B팔(1.32~1.83x)이 A팔 r4보다 높음. 창 내 상승의 지배 항은 착지점이
  아니라 배치 집계의 DB CPU 경쟁으로 보이나 단정하지 않는다. **갈래 (b)** 해당.
- 추가 관측: A팔 배치창에서만 `lock_sys_page_mutex` 0→1.86M~2.16M/s,
  `lock_sys_global_rw_lock` 0→1.85M~2.15M/s, `trx_sys_mutex` ~400/s→1.85M~2.15M/s.
  B팔은 lock_sys 7.7~8.4k/s(배치 자신의 행 락 몫)·trx_sys 기준선 유지. 초당 대기 시간
  합계는 A팔 54~57ms/s vs B팔 13~15ms/s(약 4배). 기제 규명은 후속 과제로 남긴다.
