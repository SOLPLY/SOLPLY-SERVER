## 1. 요구와 기준

솔플리에서 가장 많이 불리는 API는 장소 목록 조회다. 앱 서버 2 vCPU · 힙 1,280 MB에서 평상시
초당 60명, 피크 초당 300명(요청으로는 600건)이 들어와도 느려지지 않아야 한다. 그래서 목록 조회는
요청 시점에 DB를 정렬하지 않고, 장소 전체를 미리 읽어 동네별·정렬별로 정렬해 둔 배열 묶음
(**스냅샷**)을 메모리에 두고 거기서 10건을 꺼낸다.

어드민은 그 반대편이다. 하루 수십 번, 장소 이름을 고치거나 동네를 옮기거나 새 장소를 등록하고,
고친 내용은 사용자에게 바로 보여야 한다. 처음에는 무엇을 고치든 스냅샷을 통째로 다시 만들었다.
이름 한 글자를 고쳐도 6,320곳을 DB에서 다시 읽고 다섯 번 정렬했다. 그 비용은 장소 수에 비례하고,
재빌드가 도는 동안 사용자 요청과 같은 JVM의 CPU와 힙을 나눠 쓴다.

목표는 이것이었다. **어드민이 실서비스 데이터를 즉시 반영하되, 그 과정이 사용자 조회의 속도와
사용성에 영향을 주지 않게 한다.** 판단 기준은 질문 하나로 세웠다.

> 이 값을 바꾸면 사용자 목록의 **정렬 순서**나 **태그 필터 결과**가 바뀌는가?

| 어드민이 바꾼 것 | 순서·필터에 영향 | 처리 |
|---|---|---|
| 장소 이름, 썸네일 | 없음 | 그 장소 하나만 DB에서 다시 읽어 **표시 맵**에 넣는다 |
| 태그 이름, 활성/비활성 | 없음 | **태그 맵**(수십 개)을 통째로 다시 읽어 교체한다 |
| 장소 생성·삭제, 동네 이동, 좌표 변경, 태그 집합 변경 | 있음 | 스냅샷 전량 재빌드 |
| 인기 점수, 리뷰 수, 북마크 수 | 있음(정렬 키) | 배치가 채우는 값이라 배치 뒤 타이머 재빌드 |
| 태그 타입(MAIN ↔ OPTION) | 있음 | 쓰이지 않는 기능이라 **수정 자체를 막았다** |

사용자에게 하는 약속도 한 문장이다. **커서는 정렬 순서의 일관성을 보장한다. 표시값과 소속은
최신 값일 수 있다.** 스크롤 중에 같은 장소가 두 번 나오거나 봤던 장소가 다시 나오지 않아야 하고,
이름이 스크롤 도중 바뀌는 것은 오히려 어드민이 원하는 동작이다.

## 2. 데이터는 어떤 구조에 담겨 있고, 어떻게 정렬·검색하나

앱 서버 하나에 싱글톤 빈 셋이 있다.

```
SnapshotBox                                      ← 조회는 여기서 시작한다
  └ volatile List<Snapshot>                       최신이 0번, 최근 3장 보존
       └ Snapshot(version, SortedPlaces)          불변
            ├ 장소 값: PlaceEntry 객체 N개          정렬 키 다섯, 좌표, 태그 비트마스크
            └ 정렬 순서: 정렬 5종 × 동네 → PlaceEntry[]   같은 객체를 다섯 배열이 다른 순서로 참조

PlaceViewHolder  (스냅샷 밖, 한 벌)  placeId → 이름, 썸네일 파일 키, 대표 태그 id
TagViewHolder    (스냅샷 밖, 한 벌)  tagId   → 이름, 활성
```

**배열 원소에 두는 값의 기준은 "조회가 비교하거나 필터링하면서 읽는가"다.** 정렬 키는 이진
탐색이 읽고, 태그 비트는 순차 스캔이 원소마다 읽고, 좌표는 거리순이 후보 전부에서 읽는다. 이름과
썸네일은 최종 10건에만 필요하니 스냅샷 밖 맵에서 10번만 꺼낸다. 이 분리 덕에 이름을 고칠 때
배열 다섯 개를 건드리지 않고, 스냅샷을 3장 들고 있어도 표시값은 한 벌이다.

요청 하나의 일은 이렇다. 커서가 없으면 0번 스냅샷, 있으면 커서에 실린 버전의 스냅샷을 고른다.
그 동네·그 정렬의 배열에서 커서 위치를 **이진 탐색**(동네당 비교 8~9회)으로 찾고, 거기서부터
**순차 스캔**하며 태그 비트마스크 AND 세 번으로 거르고, 10건이 차면 **즉시 멈춘다**. 동네가 여럿이면
동네마다 이진 탐색한 뒤 크기 k인 최소 힙으로 병합한다. 거리순만 사전 정렬이 없어 후보 전량에
거리를 계산하고 크기 10인 힙으로 가까운 것만 남긴다. DB 0회, 락 0회다. 실제로 검사하는 원소 수는
대략 10 ÷ 필터 통과율이라 통과율 50%면 20개 안팎이고, 동네 장소 수가 10배가 돼도 이진 탐색
비교가 3~4회 느는 것이 전부다.

이 구조에서 택하지 않은 것 셋을 적어 둔다.

- **요청마다 정렬**(첫 구조). 후보 전량에 n log n. 부하 측정에서 앱 CPU가 병목이었고, 정렬을 앱의
  사전 배열로 옮기자 DB 정렬 문장 11종이 사라지고 rows examined가 80분의 1이 됐다.
- **열별 원시 배열(SoA).** 객체 N개가 0개가 되어 GC 마킹 대상과 재빌드 할당이 사라진다는 매력이
  있어 실제로 구현해 게이트까지 통과시킨 뒤 되돌렸다. 조회가 전량을 스캔하지 않고 10건에서 끊기
  때문에 캐시 지역성이 요청 비용을 정하는 구조가 아니고, 값 하나에 첨자를 두 번 타고 필드 하나
  추가가 생성·재빌드·복사·접근자·테스트를 전부 건드리는 대가가 컸다. "객체가 많으면 GC가 힘들
  수 있으니 미리"는 병목 확인과 프로파일을 건너뛴 과최적화였다. 다시 꺼낼 자리는 6장에 있다.
- **캐시 라이브러리로 스냅샷 보관.** 갓 만든 스냅샷을 접근 빈도가 낮다고 축출할 수 있고 청소
  시점이 비결정적이다. 3장은 `volatile List` 하나로 충분하다.

## 3. 어드민 수정과 재빌드 사이의 트레이드오프 — 정합성·단순성 대 성능

여기서 고른 것은 **정합성 규칙 하나와 단순성**이고, 내준 것은 **소속이 바뀌는 수정의 재빌드 비용**이다.

**전량 재빌드의 정확성 모델은 한 문장이다.** DB가 원천이고, 지금 상태로 새 스냅샷을 만들어 참조를
한 번 바꿔 끼운다. 조회는 락을 잡지 않고 옛것 아니면 새것만 본다. 어떤 종류의 수정이든 중간에
실패하면 다음 재빌드가 고친다. 표시 맵 갱신과 재빌드가 겹쳐 수정이 사라지는 경우 하나만 락으로
줄 세우고, 맵 갱신은 락을 잡은 뒤 DB를 다시 읽어 넣는다. 락을 기다리는 쪽은 커밋 뒤의 어드민
훅이라 어느 화면에도 보이지 않는다.

**장소 단위 패치는 두 번 검토하고 접었다.** 동네 이동이나 생성·삭제도 그 동네의 배열 다섯 개에서
장소 하나만 넣거나 빼자는 설계였다. 아끼는 것은 "DB 전량 읽기와 전 배열 재정렬"인데 그 총량은
재빌드 한 번의 비용 × 어드민 빈도, 즉 하루 수십 회 × 0.1초다. 사는 것은 생성·삭제·동네 이동마다
다른 배열 갱신 분기, 정렬 키가 바뀌었는지 판별, 배열의 copy-on-write와 요청 중 일관성, 재빌드와
패치의 동시 실행 제어, 과거 커서가 가리키는 스냅샷과 현재 데이터의 의미, 부분 실패의 되돌림이고,
무엇보다 정합성 규칙이 하나에서 둘로 는다. 표시값 분리만으로 어드민 수정의 대부분(이름·썸네일·
태그 이름)이 재빌드 없이 반영되므로, 재빌드가 남는 것은 소속이 바뀌는 드문 수정뿐이다.

이 판단이 성립하는 조건은 하나다. **재빌드 비용이 현실적 규모에서 사용자 조회가 쓸 몫 안에 든다.**
그것을 4장과 5장에서 잰다.

## 4. 통째로, 기한 없이 힙에 두는 것이 사용자 API에 해가 되지 않는가

걱정은 둘이다. **상주 객체**는 교체될 때까지 Old 영역에 눌러앉아 장소 수만큼 GC 마킹 대상이 된다.
**재빌드 순간**에는 DB 행이 객체로 바뀌며 힙이 출렁이고 그 스레드가 CPU를 쓰며, 옛 스냅샷은 죽어도
Old에 남아 Young GC로는 걷히지 않는다.

순서를 지켜 봤다. 먼저 **GC 성능이 괜찮은가**를 네 축(Throughput·Latency·Footprint·Promptness)으로
읽고, 그 다음에 **왜인가**를 GC 빈도·할당률·GC 전후 힙·Old 증가·Full GC로 내려간다. 왼쪽은 부하
아래 serving 정상 상태(현재 규모 6,320곳, 초당 600 요청), 오른쪽은 현실적 최대인 10배(63,200곳)에서
보존 3장이 찬 뒤 재빌드를 다섯 번씩 태운 창(무부하)이다. 다른 창·다른 규모라 나란히 놓되 빼지 않는다.

| 축 | serving 정상 상태 (현재 규모, 부하 중) | 재빌드 창 (10배, 보존 3장이 찬 뒤) |
|---|---|---|
| **Throughput** — GC에 뺏기는 시간 | 정지 합이 90초 창의 0.25%, GC 스레드 CPU가 2 vCPU의 0.20% | 재빌드 한 번(0.27~0.39초)에 Young 정지 합 중앙값 0~95 ms, 최대 245 ms |
| **Latency** — 단일 정지 최대 | 재빌드를 피크 한가운데서 발화했을 때 직후 Young 정지 4.2 / 41.6 ms | Young 단일 최대 204 ms. **Full GC 0회** |
| **Footprint** — 붙드는 힙 | GC 후 바닥 89 MB | Full GC 직후 live **112 MB(힙의 8.8%)**, 그중 스냅샷 3장 26.8 MB(2.1%). 재빌드 한 번의 할당 240 MB |
| **Promptness** — 죽은 것을 얼마나 빨리 걷나 | 재지 않음 | 보존이 3장으로 찬 뒤에도 GC 후 바닥이 147 → 204 → 257 MB로 오르다 Full GC에서 112 MB로 돌아옴 |
| **CPU** — 재빌드가 도는 동안 | 요청당 앱 CPU 1.8~1.9 ms, 앱 코어 0.85 | 재빌드가 도는 200~400 ms 동안 JVM이 **1.0~1.65 core**(중앙 1.33). 100 ms 쿼터 포화는 20회 중 3회에서 각 1회 |
| **부하 중 재빌드 시 p50** | 발화 버킷 p50 2 ms · p95 4 ms · 에러 0 (이웃 버킷과 같음) | **미측정** |

**serving 정상 상태에서 GC는 주항이 아니다.** 등록한 문턱(10%)의 40분의 1이고, 재빌드를 피크에
끼워 넣어도 그 버킷의 지연이 움직이지 않았다. 상주 객체가 Old에 있다는 것 자체는 비용이 아니었다.
**재빌드 창은 다르다.** 300 ms 남짓 JVM이 코어 하나 반을 쓰고 Young GC가 0~2번 와서 최대 200 ms를
멈춘다. 그 순간 serving에 남는 것은 코어 0.35~1개와 힙 1,100 MB 이상이다. 힙은 넉넉하고 CPU는
짧게 좁아진다.

원인 지표로 내려가면 이렇다.

- **GC 빈도.** 재빌드 한 번의 할당 240 MB는 Eden을 0~2번 채우는 양이라 Young GC가 0~2회다. 창 안에
  GC가 오느냐는 그 순간 Eden이 얼마나 차 있었냐의 우연이라 "0회"를 보장으로 읽지 않는다.
- **할당률.** 240 MB ÷ 0.27초 ≈ 0.9 GB/s. serving이 초당 600 요청에서 428 MB/s를 할당하는 것과 같은
  자릿수이고 1초 미만이다.
- **GC 전후 힙.** Young GC 직전 값은 641~962 MB까지 올라가지만 재빌드가 만든 정점이 아니라 그때까지
  쌓인 쓰레기의 높이다. 판정에 쓸 값은 Full GC 직후 112 MB다.
- **Old 증가.** 스냅샷 객체는 만들어지는 동안 전부 살아 있어 Survivor에 담기지 않고 Young GC 한두 번
  만에 Old로 조기 승격된다. 교체돼 죽은 뒤에도 Old에 남아 동시 마킹 뒤 mixed GC나 Full GC가 와야
  걷힌다. 10배에서는 그 누적이 Full GC를 부르기 전에 라운드가 끝났다.
- **Full GC.** 10배에서는 없다. 100배에서는 있었고, 그것이 5장이다.

답은 이렇다. 상주는 해가 아니고, 재빌드는 300 ms짜리 CPU 목을 만든다. 그 목이 부하 중 사용자
지연으로 드러나는지는 10배에서 직접 재지 않았고, 현재 규모의 "무영향"이 유일한 간접 증거다.
어드민 수정은 빈도가 불규칙한 소수의 사건이라 지금 구조를 바꾸지 않고, 드러나는 날의 답을
6장에 적어 둔다.

## 5. 규모가 커지면 어디가 먼저 아픈가 — 10배 실측과 100배 한계

| | 10배 63,200곳 실측 | 100배 632,000곳 (옛 로더 형상) |
|---|---|---|
| 재빌드 소요 | 0.27~0.39초 | 4.4~5.2초 |
| 스냅샷 한 장 | 8.9 MB (`PlaceEntry` 4.8 + 정렬 배열 1.2 + 좌표 `Double` 박싱 2.9) | 약 89 MB(산술) |
| Full GC 직후 live | 112 MB (8.8%) — 3장 26.8 + 표시 홀더 한 벌 8.2 + 프레임워크 77 | 720 MB (56%) |
| GC | Young 0~2회, Full 0 | 힙 상한, **Full GC(정지 약 380 ms)**, 스로틀 |
| 재빌드 중 CPU | 200~400 ms 동안 1.0~1.65 core | 4~5초 동안 상한 근처 |

초안의 추정은 두 군데 빗나갔다. 10배 재빌드는 1~3초일 줄 알았는데 0.3초였다(문장 하나가 한
테이블만 읽게 바꾼 뒤다). "표시 맵이 스냅샷보다 먼저 커진다"도 아니었다. URL을 미리 만들지 않고
파일 키만 두면서 가벼워졌고, 대신 스냅샷 한 장의 32%가 좌표 `Double` 박싱이라는 것을 히스토그램이
보여 줬다. 원시 `double`로 바꾸면 한 장에서 2.9 MB가 빠지지만 10배에서는 들일 이유가 없다.

100배에서 Full GC의 원인은 둘이 겹친 것이었다. 결과 전량을 `List<Object[]>`로 받는 방식이 "드라이버
버퍼 + 행 배열 전량 + 만들어지는 스냅샷"을 한 순간에 힙에 두었고, 행 단위 streaming으로 바꾸자
정상 상태 Full GC가 2회 → 1회가 됐다. 그러나 남은 1회는 살아 있는 스냅샷 4장(보존 3 + 건설 중 1)의
몫이라 로더로는 더 내려가지 않았다. streaming은 10배에서 다시 재 보니 할당 5.9%만 갈리고 시간·CPU·
힙·GC는 구분 불가여서 되돌렸다. 드라이버 전용 fetch size 약속과 "스트림을 닫기 전 같은 커넥션에
다른 문장 금지" 계약을 코드에 남길 이유가 없었고, 기록은 설계 문서에 있다.

정리하면 **10배까지는 힙도 시간도 논점이 아니고, 재빌드가 도는 300 ms의 CPU 경합만 남는다.**
100배는 로더만 고쳐서는 늘어나지 않는 구조적 한계이고, 그 규모가 요구가 되는 날의 답도 6장이다.

## 6. 재빌드가 지연에 나타나기 시작하면 — 원인은 "같은 JVM", 답은 빌더 분리

4장과 5장을 한 줄로 줄이면, **재빌드의 DB 조회·객체 생성·정렬·중간 할당이 전부 사용자 요청을
처리하는 JVM 안에서 일어난다.** 로더를 아무리 깎아도 같은 힙, 같은 두 코어를 나눠 쓴다. 근본
원인은 어드민 기능(쓰기와 재빌드)과 사용자 API(읽기)가 한 서버에 있다는 것이고, 답도 로더가
아니라 배치에 있다.

### 6-1. 짓는 곳과 서빙하는 곳을 나눈다

```
              Primary DB
                  │ replication
                  ▼
             Read Replica
                  │
                  ▼
           Snapshot Builder            ← 어드민 서버 / 별도 워커. 어드민 수정 커밋과 10분 타이머가 여기서 돈다
                  │  전체 스냅샷 생성 → 버전 발급 → 직렬화
                  ▼
                Redis                  SET snapshot:123 <binary> · SET snapshot:latest 123
                  │                    PUBLISH snapshot-updated 123
          ┌───────┼───────┐
          ▼       ▼       ▼
        API-1   API-2   API-3          "123 나왔음" 수신 → 현재 버전과 비교 → snapshot:123 fetch → 검증
        local   local   local          → 역직렬화 → 참조 교체
        cache   cache   cache
```

Pub/Sub은 스냅샷을 나르는 통로가 아니라 **"새 버전이 나왔다"는 신호**다. 유실될 수 있는 채널이지만
정확성에 닿지 않는다. 놓친 인스턴스는 주기적으로 `snapshot:latest`를 확인해 따라잡고, 그 사이
낡았지만 완결된 스냅샷을 서빙할 뿐이다. 버전은 빌더만 발급하고 각 인스턴스는 자기 최신보다 큰
번호만 채택하므로 어드민 수정과 타이머가 겹쳐도 순서가 꼬이지 않는다. 커서에 실린 버전이 로컬에
없으면 Redis에서 한 번 받아 이어받고, 거기도 없으면 만료시켜 1페이지로 돌린다. 첫 페이지 핫패스에는
Redis가 없다. 빌더가 읽는 DB는 조회 전용 스냅샷이라 read replica여도 된다.

**Redis는 조회 가속기이지 정본이 아니다.** 정본은 MySQL이고, Redis가 죽으면 각 인스턴스는 로컬
스냅샷으로 정속 서빙을 계속하면서 자기 타이머로 DB에서 직접 짓는 경로로 후퇴한다. 내주는 것은
어드민 수정이 다른 서버에 10분까지 늦게 보이는 것과 서버를 넘어간 옛 커서의 만료뿐이다.

### 6-2. API 서버에서 무엇이 빠지고 무엇이 남나 — 중간 객체와 최종 객체를 갈라야 한다

이 구조가 GC 문제를 없애 주는 것은 아니다. 재빌드의 객체는 두 종류이고 운명이 다르다.

| | 지금 (같은 JVM) | 빌더 분리 뒤 API JVM |
|---|---|---|
| **재빌드 중간 객체** — DB ResultSet, `Object[]` 행, 리스트, 정렬 임시 객체 | serving 힙에서 생겼다 버려진다(10배 240 MB 중 대부분) | **빌더로 옮겨진다.** API 서버의 GC 부담에서 빠진다 |
| **재빌드 CPU** — DB 조회, 타입 변환, 정렬 | 200~400 ms 동안 1.0~1.65 core | **빌더로 옮겨진다** |
| **최종 스냅샷 객체** — `PlaceEntry` N개, 정렬 배열, 표시 맵 | serving 힙에 생긴다 | **여전히 serving 힙에 생긴다.** API 서버가 조회에 쓰는 것이라 역직렬화로 다시 만들어야 한다(10배 한 장 8.9 MB + 표시 홀더 8.2 MB) |
| 옛 스냅샷의 Old 잔류 | 교체마다 한 장 | 같다 |

흐름으로 보면 "DB → JDBC/Hibernate → `PlaceEntry` → 정렬"이 "Redis → 역직렬화 → `PlaceEntry`"로
바뀌는 것이다. DB·Hibernate·정렬 비용은 사라지지만 **최종 객체 N개를 만드는 할당은 API 서버에
남는다.** 그래서 트레이드오프는 "직렬화 때문에 별 차이 없나"가 아니라 세 줄로 적는 것이 맞다.

- **얻는 것.** API 서버에서 DB 전량 조회, Hibernate/JDBC 처리, 정렬, 중간 할당을 제거하고 재빌드의
  CPU와 힙 부하를 빌더로 격리한다. 빌더 JVM은 지연 목표가 없는 배치형이라 처리량 우선의
  Parallel GC를 쓰는 선택도 열린다(제안이고 측정 전이다).
- **남는 것.** API 서버가 새 스냅샷을 쓰려면 최종 데이터를 로컬 힙에 올려야 하므로 다운로드·
  역직렬화·최종 객체 할당은 남는다.
- **새로 생기는 것.** 직렬화 포맷과 그 스키마 관리, Redis 메모리와 네트워크, 버전 관리, Pub/Sub
  유실 대응, 인스턴스 간 버전 전환 시점 차이라는 운영 복잡도.

### 6-3. 여기서 SoA가 다시 등장한다

2장에서 접은 열별 원시 배열은 이 구조에서 자리가 생긴다. 빌더가 스냅샷을 처음부터
`long[] placeIds`, `long[] tagMasks`, `double[] scores`, `int[] popularOrder` 같은 원시 배열로 만들어
compact binary로 Redis에 올리면, API 서버는 그것을 **배열 몇 개로 복원해 참조를 바꾸는 것**으로
끝난다. `PlaceEntry` N개를 역직렬화해 만드는 것보다 객체 수와 GC 부담을 자릿수로 줄일 여지가 있고,
2장에서 SoA를 접은 이유였던 "조회 경로의 복잡도 대가"는 그대로지만 "얻는 것"이 조회 지역성이
아니라 **API 힙의 할당과 마킹 대상 제거**로 바뀐다. 그 너머의 `byte[]`·off-heap·memory-mapped처럼
역직렬화 자체를 없애는 조회 모델은 이론적으로 가능하지만 지금 서비스에는 과하다.

로더 최적화(행 단위 streaming, JDBC primitive getter)는 이 그림에서 자리가 옮겨진다. 재빌드 CPU가
serving JVM에 들어오는 순간은 **Redis 장애로 API 인스턴스가 직접 짓는 강등 경로**뿐이므로, 그
경로를 가볍게 하는 안전장치이자 빌더가 100배 같은 규모에서 버티게 하는 수단이 된다.

### 6-4. 언제 시작하고, 그 다음은 무엇인가

둘 중 하나가 켜지면 착수한다. **인스턴스를 2대 이상으로 늘리기로 하는 날**, 또는 **부하 중
재빌드 버킷의 p50이 이웃 버킷의 2배를 넘는 관측이 나오는 날**이다. 지금은 둘 다 아니다. 착수하는
날 먼저 정할 것은 직렬화 포맷(객체판인가 원시 배열판인가)과 왕복 등가 테스트, 표시 홀더를 blob에
같이 실을지 장소 id 이벤트로 전파할지, 역직렬화와 재조립이 API JVM에 얹는 할당과 시간의 실측이다.

이 전환은 규모의 답이 아니다. 빌더 분리와 공유 저장소는 "재빌드가 serving을 건드린다"와
"인스턴스가 여러 대다"를 푼다. **데이터 규모 자체가 단일 JVM 힙의 범위를 넘어가거나**(장소가
수십만, 태그가 비트마스크 예산 62개 초과) **질의가 닫힌 집합을 벗어나면**(검색어, 임의 반경) 외부
조회 인프라, 곧 검색 엔진 계열로 나간다. 그때 어드민 수정은 문서 하나의 upsert가 되어 "재빌드냐
표시값 갱신이냐"는 문제 자체가 없어지고, 커서 계약(회차 고정·명시 만료)은 point-in-time reader에
같은 모양으로 이식된다.

## 7. 네 문장으로

**어떤 자료구조에, 어떤 근거로.** 조회가 비교·필터에서 읽는 값만 장소당 객체 하나에 담고 동네 ×
정렬 5종의 참조 배열을 미리 정렬해 둔다. 이진 탐색으로 시작점을 찾아 10건이 차면 멈추고, 표시값은
스냅샷 밖 한 벌에서 마지막 10건만 꺼낸다.

**어드민 수정과 재빌드 사이에서 무엇을 골랐나.** 순서·필터를 바꾸는 수정만 전량 재빌드하고
나머지는 표시값만 바꾼다. 장소 단위 패치는 하루 몇 초를 아끼려고 정합성 규칙을 둘로 늘리는 거래라
접었고, "DB대로 다시 만들어 한 번에 바꿔 끼운다"는 규칙 하나를 지켰다.

**왜 괜찮다고 봤나.** 부하 아래 serving에서 GC는 정지 합 0.25%·GC CPU 0.20%로 주항이 아니고,
10배에서 보존 3장이 찬 뒤 재빌드를 태워도 live 힙 8.8%, Full GC 0회, 재빌드 300 ms 동안 코어 1.3개다.
재지 않은 것은 10배 부하 중 발화의 p50 하나다.

**아프기 시작하면.** 원인은 어드민과 API가 같은 JVM이라는 것이므로 빌더를 떼어 Redis를 공유
저장소로 두고 API 인스턴스는 받아서 서빙만 한다. 중간 객체와 CPU는 빌더로 가고 최종 객체 할당은
남으며, 그 남는 것을 줄이는 자리가 원시 배열 스냅샷이다. 데이터가 단일 JVM 힙을 넘어가면 외부 조회
인프라로 나간다.
