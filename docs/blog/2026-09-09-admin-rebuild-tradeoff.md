# 장소 목록의 메모리 조회 모델과 갱신·Heap·GC 설계

작성일: 2026-09-09 · 구현 기준: 2026-09-12

솔플리의 장소 목록은 동네와 태그로 후보를 좁히고, 선택한 순서로 한 페이지를 반환한다.
여러 사용자가 공유하는 정렬·필터 데이터를 메모리에 두면 요청마다 전체 장소를 읽고 정렬할
필요가 없다. 대신 서버는 조회 데이터를 상주시켜야 하고, 새 데이터를 발행하고 복원하는
과정에서 CPU·메모리·DB 비용을 부담한다.

이 글은 현재 조회 자료구조와 관리자 수정 경로, 객체 수명과 측정 범위를 다룬다.
MySQL의 발행 데이터와 여러 서버의 복원 절차는
[스냅샷 발행·복원 구조](2026-09-10-distributed-inmemory-snapshot-architecture.md)에 정리한다.

## 1. 한 요청이 어떤 상태를 읽는가

장소 목록에는 모든 사용자가 공유하는 값과 요청마다 달라지는 값이 함께 있다.

| 값 | 조회 위치 |
|---|---|
| 장소의 소속 동네·좌표·태그 비트마스크·정렬 키 | current Snapshot |
| 장소 이름·썸네일 파일 키·대표 태그 ID | PlaceViewHolder |
| 태그 이름·활성 상태 | TagViewHolder |
| 동네 범위와 전달된 태그 조건의 유효성 | MySQL |
| 해당 사용자가 이번 페이지의 장소를 북마크했는지 | MySQL |
| 공유 현재 발행 ID·커서 버전 | MySQL — 일반 첫 페이지 또는 커서 불일치 시 |

따라서 메모리 조회 모델을 쓴다고 요청 전체에서 DB 접근이 없어지는 것은 아니다.
일반 장소 목록은 조건 검증 뒤 메모리에서 페이지를 고르고, 사용자별 북마크 여부를 붙인다.
내 북마크만 조회하는 요청은 별도의 조회 분기를 사용한다.

다음은 `PlaceService`가 페이지를 한 번 구성하는 흐름이다. HTTP 요청의 최신성 확인과
적재 대기는 이 바깥에서 처리한다.

```text
페이지 구성 시도
  → 동네 범위·태그 조건 확인
  → 정렬·필터 조건과 커서 확인
  → current Snapshot 참조를 한 번 확보
  → 같은 참조로 후보 탐색·필터링·페이지 추출
  → 표시 홀더에서 이름·이미지 키·태그 이름 조회
  → MySQL에서 페이지 내 사용자 북마크 여부 조회
  → 목록·이미지 URL·다음 커서 반환
```

일반 첫 페이지는 페이지 구성 후 공유 발행 ID를 확인한다. 이미 설치한 상태보다 새 발행이
있으면 적재를 기다렸다가 페이지를 다시 구성한다. 커서 요청은 로컬 회차가 다를 때만 공유
현재 커서와 비교하며, 서버의 적재 지연과 실제 만료를 구분한다. 북마크 검색은 이 확인을
거치지 않는다.

각 페이지 구성 시도는 확보한 Snapshot으로 끝까지 정렬·필터·커서 경계를 계산한다. 갱신 도중 다시
current를 읽어 한 페이지에 서로 다른 정렬 상태가 섞이지 않게 한다. 썸네일은 파일 키로
CloudFront URL을 조합해 반환하고, 이미지 다운로드는 클라이언트가 별도로 수행한다.

표시값은 Snapshot 밖에서 읽는다. 따라서 **정렬·필터 기준은 요청이 확보한 상태로 고정되지만,
표시값까지 같은 시점으로 고정되는 것은 아니다.** 표시 홀더와 Snapshot은 서로 다른 참조이며,
세 참조의 교체가 모든 독자에게 하나의 원자적 교체로 보인다는 보장은 없다.

## 2. 상주 자료구조와 페이지 탐색

```text
SnapshotBox
  └── current Snapshot 한 벌
        ├── version: 커서가 참조하는 버전
        └── SortedPlaces
              └── 정렬 종류 → 동네 ID → PlaceEntry 참조 배열

PlaceEntry
  └── 장소 ID·동네·태그 비트마스크·좌표·정렬 키와 표시 통계

PlaceViewHolder
  └── 장소 ID → 이름·썸네일 파일 키·대표 태그 ID

TagViewHolder
  └── 태그 ID → 이름·활성 상태
```

장소 하나의 `PlaceEntry`를 여러 정렬 배열이 참조한다. 같은 장소의 값 객체를 정렬 축마다
복제하는 방식이 아니다. 배열은 정렬 순서를, 엔트리는 장소의 값을 표현한다.

정적 정렬은 동네별로 미리 정렬한 배열을 사용한다. 커서가 있으면 정렬 키와 장소 ID를
비교해 다음 위치를 이진 탐색하고, 그 위치부터 태그 조건을 적용한다.

```text
한 동네
  → 커서 다음 위치 탐색
  → 배열을 순서대로 읽으며 태그 필터 적용
  → 페이지 크기 + 1개 확보 또는 후보 소진

여러 동네
  → 각 동네에서 커서 다음 위치 탐색
  → 동네별 다음 후보 하나씩 우선순위 큐에 넣기
  → 전체에서 가장 앞선 후보를 꺼내 필터 검사
  → 그 후보가 나온 동네의 위치를 전진시켜 다음 후보 추가
  → 페이지 크기 + 1개 확보 또는 후보 소진
```

여러 동네의 페이지를 각각 완성한 뒤 합치지 않는다. 이미 정렬된 배열의 다음 후보들을
비교해 하나의 순서로 읽는다. 필터에서 탈락한 후보도 탐색 위치는 전진한다.
태그 조건을 통과하는 장소가 적으면 페이지 하나를 위해 검사하는 후보 수가 늘어난다.

거리순은 기준 좌표가 요청마다 달라 정적 배열의 순서만으로 해결할 수 없다. 대상 동네의
후보를 확인하고 거리를 계산한 뒤, 필요한 개수의 가까운 후보를 힙에 유지해 결과를 만든다.

| 작업 | 비용을 결정하는 값 |
|---|---|
| 정적 목록 조회 | 대상 동네 수, 커서 탐색 비용, 필터 통과 전 검사한 후보 수 |
| 거리순 조회 | 대상 후보 수, 거리 계산 수, 유지할 결과 개수 |
| 전체 배열 구성 | 장소 수, 동네별 장소 분포, 정렬 축 수 |
| 상주 메모리 | 장소 객체 수, 정렬 배열의 참조 수, 표시값 크기 |

태그 비트마스크는 후보 하나의 판정을 고정 폭 비트 연산으로 처리한다. 후보 탐색 자체를
없애는 장치는 아니다. 요청별 힙과 탐색 위치는 공유 배열을 변경하지 않는다.

## 3. 변경의 종류와 반영 경로

공유하는 완성된 조회 데이터는 MySQL의 발행물로 저장한다. 각 서버는 발행물을 복원해
자신의 current와 표시 홀더에 반영한다. 이 경로의 저장·전파에 Redis는 필요하지 않다.

| 변경 | 후보 구성 방식 | 커서 버전 |
|---|---|---|
| 통계 배치 결과 | 원본과 place_stats를 읽어 전체 후보 구성 | 새 버전 |
| 장소 생성·삭제·동네 이동·태그 집합·좌표 수정 | 변경 장소를 다시 읽어 부분 수정 후보 구성 | 배열의 기준·구성이 바뀌면 새 버전 |
| 장소 이름·썸네일·대표 태그 표시 정보 | 표시값을 수정한 발행 후보 구성 | 유지 |
| 태그 이름·활성 상태 | 태그 표시 맵을 읽어 발행 후보 구성 | 유지 |

인기 점수·리뷰 수·평균 평점·북마크 수 같은 기존 장소의 정렬 키는 통계 재생성 경로에서
일괄 반영한다. 관리자 부분 수정은 기존 엔트리의 정렬 키를 유지하면서 소속·필터·좌표 등의
변경을 반영한다. 표시값만 바뀌어도 발행물은 새로 생기지만 커서 버전은 유지한다.

통계 트랜잭션은 데이터 갱신과 재생성 요청을 함께 커밋한다. 생성 스케줄러는 기본 5초
간격으로 미처리 요청을 확인하며, 요청이 없으면 원본을 전량 조회하지 않는다.
리뷰 집계는 매시 30분, 북마크 델타는 매시 15분이고, 인기 점수와 안전망 배치는 각각
매일 01:00과 01:45에 실행한다. 각 성공 경로가 필요한 재생성 요청을 남긴다.

## 4. 관리자 부분 수정과 발행 순서

관리자 요청은 변경된 장소 ID를 전달한다. 후보에 넣을 값은 커밋된 DB에서 다시 읽는다.
한 트랜잭션의 여러 장소 ID는 모아서 처리하며, 조회 중인 기존 엔트리와 배열은 수정하지 않는다.

```text
관리자 쓰기 트랜잭션
  → 장소·관계·표시값 변경
  → 엔티티 변경을 flush
  → 재생성 요청 번호 기록
  → 함께 커밋

관리자 afterCommit 훅
  → 로컬 갱신 차례 확보
  → 현재 공유 발행물을 로컬에 반영하고 기준 발행 ID 확보
  → 변경 장소만 DB에서 읽기
  → 기존 조회 모델을 직접 바꾸지 않고 수정 후보 구성
  → 완성된 후보를 MySQL에 조건부 발행
  → 성공한 공유 발행물을 공통 설치 경로로 복원
```

`SortedPlaces.patch`는 변경된 장소를 찾아 영향 동네의 배열을 준비한다. 태그·좌표 수정은
기존 위치에서 참조를 바꾸고, 생성·삭제·동네 이동은 해당 동네의 구성과 정렬을 조정한다.
이 단계에서는 변경되지 않은 배열과 엔트리를 공유할 수 있다.

다만 **부분 수정이라는 말은 발행·복원 비용까지 변경된 장소 수에 비례한다는 뜻이 아니다.**
후보를 저장할 때는 전체 엔트리·표시값·태그를 JSON으로 직렬화하고 압축한다. 설치할 때도
전체 발행물을 읽고 객체와 정렬 배열을 다시 구성한다. 후보 계산의 부분 갱신과 완성본의
전량 전송·복원은 서로 다른 단계다.

발행 전에 로컬 current를 먼저 바꾸지 않는다. 다른 작업이 기준 발행물을 이미 교체했으면
포인터의 조건부 갱신이 실패하고, 후보 저장도 롤백한다. 이 경우 원본 쓰기는 이미 커밋됐지만
공유되지 않은 후보를 로컬에 공개하지는 않는다.

관리자 훅은 자신의 요청만 남아 있고 앞선 미처리 요청이 없는 경우에만 완료 표시를 한다.
미처리 통계 요청까지 관리자 부분 수정으로 처리했다고 표시할 수는 없기 때문이다.
남은 요청은 생성 스케줄러가 원본 전체를 읽어 처리한다. 공유 발행 후 로컬 설치만 실패했다면
각 서버의 설치 폴이 다시 내려받는다.

## 5. 로컬 잠금과 조회 중인 객체의 수명

`CacheWriteLock`은 한 JVM의 갱신 작업끼리 순서를 맞춘다. 사용자 조회는 이 잠금을 잡지
않고 current의 불변 데이터를 읽는다. 다른 서버와의 발행 경쟁은 MySQL 포인터의 조건부
갱신으로 판정한다. 로컬 잠금만으로 분산 발행 순서를 보장하지 않는다.

일반 설치 경로는 다운로드·검증·디코딩·배열 구성을 준비한 뒤 로컬 잠금 안에서 발행 ID를
다시 확인한다. 늦게 도착한 발행물이 더 최근에 설치한 표시값과 current를 덮지 않도록 한다.
관리자 훅은 이보다 넓은 범위를 로컬 잠금으로 감싸며, 후보 구성·발행·재설치가 그 안에서
실행될 수 있다. 따라서 갱신 잠금이 언제나 짧게 끝난다고 가정할 수는 없다.

관리자 afterCommit에서 별도 트랜잭션을 열 때 원래 트랜잭션의 커넥션이 아직 반환되지
않을 수 있다. 동시 관리자 쓰기가 많으면 추가 커넥션 확보가 지연되거나 시간 초과될 수
있다. 현재 경로는 동기 훅을 유지하며, 이 경우에도 원본과 재생성 요청은 이미 커밋되어
후속 발행이 복구한다. 관리자 트래픽이 적다는 가정만으로 풀 고갈 가능성이 없다고 단정하지 않는다.

조회가 잠금을 기다리지 않는다는 사실과 조회 지연에 영향이 없다는 주장은 다르다.
갱신도 같은 JVM에서 CPU·힙을 사용하므로 자원 경쟁과 GC를 통해 응답에 영향을 줄 수 있다.
별도의 빌더 서버나 스케줄러 풀 확대는 포함하지 않는다. 사용자 요청과 설치 폴이 시작하는
복원 작업에는 전용 적재 스레드 한 개를 사용한다.

로컬이 공유 현재 발행물보다 뒤처진 요청은 적재 완료를 비동기로 기다릴 수 있다. 요청과
설치 폴은 CAS로 등록한 하나의 Future를 공유하므로 같은 적재를 중복 시작하지 않는다.
일반 첫 페이지는 MySQL의 현재 발행 ID를 확인하고, 커서 요청은 로컬 버전이 맞지 않을
때만 공유 커서 버전을 확인한다. 적재 지연에는 기본 2초의 대기 예산을 적용하고, 초과하면 503으로 재시도하게 한다.
공유 현재 버전에서도 유효하지 않은 커서는 만료로 처리한다. 사용자 조회가 직접
갱신 잠금을 잡지는 않지만, 기다리는 적재는 설치 시 그 잠금이 필요하므로 관리자 갱신이
길어지면 적재 대기도 길어질 수 있다. 관리자 훅은 이 Future를 기다리지 않고 직접 설치한다.

```text
교체 전
  current → Snapshot A
  진행 중인 요청 → Snapshot A

교체 후
  current → Snapshot B
  이미 시작한 요청 → Snapshot A로 처리 계속

기존 요청 종료
  Snapshot A를 붙잡는 참조가 없어지면 GC 회수 대상
```

current를 한 벌만 보관해도 교체 순간 힙에 Snapshot 한 벌만 존재하는 것은 아니다.
진행 중인 요청과 갱신 작업이 기존 객체를 참조할 수 있다. 참조가 끊겼다고 즉시 메모리가
회수되는 것도 아니다. 실제 회수 시점은 GC 실행에 달려 있다.

## 6. Heap·GC 비용은 어디에서 생기는가

상주량과 갱신 중 최대 점유를 나누어 봐야 한다. 상주량은 현재 엔트리·정렬 배열·표시값에
주로 붙고, 갱신 중에는 원본 조회 결과와 직렬화·복원용 객체가 추가된다.

```text
발행하는 서버
  기존 current·표시값
  + DB 조회 결과 또는 부분 수정 후보
  + payload DTO·직렬화 버퍼·압축 바이트

발행물을 설치하는 서버
  기존 current·표시값과 진행 중인 요청의 참조
  + 내려받은 압축 바이트·디코딩 결과
  + 새 PlaceEntry·표시 맵·정렬 배열
```

이 항목들이 항상 전부 같은 시점에 최대 크기로 존재하는 것은 아니다. 하지만 압축된
payload 크기만 보고 복원에 필요한 힙을 추정해서는 안 된다. 저장 바이트와 JVM 객체·참조
배열의 크기는 다르고, 버퍼 복사와 임시 객체도 할당된다.

TTL 없이 current를 보관하는 이유는 다음 요청이 즉시 조회할 완성본이 필요하기 때문이다.
일정 시간이 지났다고 모델을 비우기보다 새 발행물을 준비한 뒤 교체한다. 메모리 안전성은
TTL 유무가 아니라 데이터 크기, 갱신 중 동시 점유, 요청이 참조를 유지하는 시간, JVM 여유와
GC 동작으로 확인해야 한다.

## 7. 확인한 것과 추가로 측정할 것

현재 발행 형식의 고정 합성 데이터로 압축·MySQL 저장·조회·디코딩을 확인했다.

| 장소 엔트리 | 압축 전 JSON | gzip payload |
|---:|---:|---:|
| 1,000 | 356,422바이트 | 43,505바이트 |
| 10,000 | 3,548,602바이트 | 422,779바이트 |

개발 노트북의 MySQL Testcontainers에서 1만 엔트리의 인코딩·DB 조회·디코딩은 각각
31.6ms·5.0ms·13.1ms를 기록했다. 시간은 5회 중 최소값이며, DB 저장 트랜잭션 전체 시간이나
정렬 배열 설치까지 포함한 지연 지표가 아니다. 테스트는 왕복 정합성을 확인하며 운영 응답
시간이나 충분한 Heap 여유를 보장하지 않는다.

실제 구조의 비용 판단에는 다음 관측이 더 필요하다.

| 측정 대상 | 함께 확인할 값 |
|---|---|
| 발행 한 회차 | 원본 조회·인코딩·DB 저장 시간, CPU, 저장 바이트 |
| 인스턴스의 설치 | 다운로드·디코딩·정렬·교체 시간과 실패율 |
| 갱신 중 메모리 | 최대 점유, 높은 점유의 지속 시간, 자연 GC 횟수·정지 시간 |
| 사용자 영향 | 조회와 북마크 쓰기의 지연 분포, DB 잠금 대기 |
| 반복 실행 | 요청이 쌓이는 속도, 발행 지연, 여러 서버의 동시 다운로드 부하 |

진단을 위해 강제 실행한 GC는 자연 GC 결과와 분리해야 한다. 무부하에서 갱신이 끝난 시간만으로
사용자 요청이 섞인 상황의 지연을 판단할 수도 없다. 현재 구조의 운영 비용은 이 측정으로
확인할 대상이며, 갱신 빈도나 압축 크기 하나만으로 충분히 작다고 단정하지 않는다.
